= Models
:description: The LinkML models of rdf-persistence: the metamodel an application imports, with a generated class diagram per module, and the technical schemas of the toolkit's own records.

_Which models does the toolkit have, and what is in each?_

Every model of the toolkit is a LinkML schema; the code, shapes, contexts and the diagrams below
are generated from it (xref:architecture/generation.adoc[Model to code]). There are two kinds
(xref:architecture/generation.adoc#kinds[why]):

* the *metamodel*, a domain model: what an application's own schema imports, and what is stored
  as RDF;
* the *technical schemas*: the toolkit's settings, request bodies, wire records and other plain
  records, never stored as RDF.

== The metamodel

`rdf_persistence/model/rp.yaml` imports the nine modules; an application imports it, or only the
modules it uses (xref:user-manual/model.adoc[Write the model]). The Python classes of the modules
are generated per theme (xref:architecture/index.adoc#models-in-themes[Where a model lives]); the
diagrams below stay one set, generated from `rp.yaml`, whichever theme holds a module's classes. How the modules import each other,
the annotations and the checks at generation are explained in
xref:architecture/generation.adoc#metamodel[The metamodel].

[cols="2,5",options="header"]
|===
|Module |What it holds

|`rp_core` |The base of everything: aggregate roots and owned parts, identity, labels and descriptions, write tracking.
|`rp_annotations` |The annotations a schema uses to steer generation and storage, on SKOS and DCTerms.
|`rp_provenance` |Activities, on PROV-O: one per commit, and the commands of each area as activity subclasses.
|`rp_access` |Access records, grants and prohibitions, on an ODRL subset.
|`rp_tenancy` |The tenant root and the tenant's state.
|`rp_files` |Stored files and the graphs loaded from RDF files.
|`rp_collections` |Collections of aggregates the collection does not own.
|`rp_discussion` |Comments and replies, on Web Annotation.
|`rp_workflow` |Workflow states and transitions, on ADMS and PROV-O.
|===

The diagrams are generated by `rp-generate` with the classes; `<<root>>` marks an aggregate root,
`<<owned>>` a class an aggregate owns.

== The technical schemas

They sit under `rdf_persistence/model/technical/<theme>/`, one schema per theme and layer
(`rp_<theme>_<layer>.yaml`, or `rp_<theme>_settings.yaml` and `rp_<theme>_templates.yaml` for the
records that are not served), plus `technical/testkit/rp_testkit.yaml` for the testkit and
`rdf_persistence_generation/model/rp_generation.yaml` for the generator. They hold the deployment
settings (xref:howto/settings.adoc[Configure the deployment values]), the request and response
bodies of the service, the shapes of the foreign APIs the adapters speak, the attributes of the
toolkit's spans and log records (xref:howto/observability.adoc[Observability]) and the SPARQL term
bundles of the query templates. Each is generated into the lowest layer every user of it may
import, in the lowest theme that uses it; the full list, theme by theme, is in
xref:architecture/generation.adoc#kinds[Two kinds of model].
