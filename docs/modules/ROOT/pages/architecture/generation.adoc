= Model to code: the generation workflow
:description: How an application's own LinkML model becomes typed, persistable code with rdf-persistence.

Status: *draft*, Proposed (2026-11-05). Settles open decision O-1 of
xref:architecture/index.adoc[architecture v1] with its smallest option. Every step below was run in a
throwaway spike (LinkML 1.12.1, Fuseki 5.1.0); its findings are marked _(spike)_. It is revised
in <<revision>> (developer, 2026-11-05: decisions D-2 and D-6 to D-9 of
xref:architecture/open-decisions.adoc[the decisions of 2026-11-05]).

An application using rdf-persistence writes its domain once, in LinkML. A deterministic, build-time
toolchain turns it into domain classes and shapes; at run time the toolkit reads the same schema to
map objects to RDF. No generated file is edited by hand, and no LLM sits in the generation path.

LinkML is the single source of specification
(xref:architecture/open-decisions.adoc[D-13]): every artefact that restates the model is generated,
by a stock generator or a toolkit extension (<<extensions>>), and nothing that restates it is
written or edited by hand (<<guarding>>).

The running example is a toy library application: each library is a tenant holding `Book`
aggregates, each book with owned chapters and a reference to a scan file; librarians hold the tenant
role `librarian`.

[#decision]
== The decision (O-1)

*Generated domain classes, runtime mapper.* Only LinkML's standard generators run, through the
toolkit's templates. Since 2026-11-05 (D-2) the classes and the mapper serve *domain services* only;
the API path needs neither (xref:architecture/api.adoc[API]). The mapper, the repositories and the routes are not generated: they are generic
code that reads the schema at run time. A per-aggregate generator (repositories, routes) is built only
if hand-written routes start repeating themselves across applications.

Rejected for v1: generating mappers, repositories and routes per aggregate (the background study's
"approach B"), because it means owning a code generator before a second application exists; and a
fully generic service without typed classes ("approach C"), because domain logic then has no types.

[#metamodel]
== The metamodel

A small LinkML schema shipped inside the package (`rdf_persistence/model/`, split into modules
since the <<revision,revision of 2026-11-05>>; namespace `https://meaningfy.ws/ns/rdf-persistence#`). Its classes are generated once, into the toolkit's own
package; an application's generated code imports them rather than regenerating them.

[cols="2,5",options="header"]
|===
|Element |Meaning
|`AggregateRoot` (mixin) |Instances are aggregate roots: each is one named graph, whose IRI `graph_iri(root)` is derived from the root's IRI (for example `<root>/graph`; background DEC-29), versioned, loaded and saved as a whole.
|`owned` (slot annotation) |The slot's values are part of this aggregate and live in its graph (as blank nodes; a commit replaces the whole graph). Any other slot whose range is a class refers to another aggregate root, by IRI.
|`database` (class annotation) |`tenant` (default) or `system`: which database the aggregate lives in.
|`graph: meta` (class annotation) |The tenant's root object lives in the tenant database's designated `meta` graph instead of a graph of its own.
|`internal` (slot annotation) |The slot never appears in the API contract (e.g. file keys).
|`rp_path` (class annotation) |Required on every aggregate root: its path segment in the API and in its IRIs (`{tenant}/{rp_path}/{uuid}`).
|`rp_unlabelled` (class annotation) |An owned value class whose instances need no label of their own.
|`Principal` |A reference to a user account in the identity provider, by IRI only.
|`StoredFile` (mixin) |The current content of a kept file: `file_name`, `media_type`, `byte_size`, `sha256`, `uploaded`, `uploaded_by`, `file_key` (internal).
|`loaded_graph` (slot) |A graph whose lifecycle belongs to the aggregate (e.g. the triples of a loaded RDF file).
|`TenantAccess`, `Grant` |The tenancy records of the system database (N-11): label, state (`TenantState`: `active`, `deleting`), database name, owned grants and prohibitions (ODRL). Role names come from the consumer's role definitions; an application may narrow `role` to an enum by subclassing (`is_a` with `slot_usage`), but need not.
|`RegistryEntry` |An entry of a tenant's `registry` graph: the graph's IRI, its kind (`aggregate`, `loaded_graph`) and the aggregate that owns it. Written by the session, never by the application.
|`version` (slot) |The version token of every aggregate, stated about its graph IRI (not the root), written by the session; not part of any domain class.
|===

Slots of the metamodel (IRIs in the `rp:` namespace unless shown):

[cols="2,2,3",options="header"]
|===
|Slot |IRI |Range, cardinality
|`id` |— (identifier) |uri, required on every aggregate root
|`label` |`skos:prefLabel` |string, from `Described`; required on `TenantAccess` (1–200 characters) and on described roots
|`state` |`rp:state` |`TenantState`, required
|`database_name` |`rp:databaseName` |string, required
|`grants` |`rp:grant` |`Grant`, multivalued, owned (blank nodes; one per assignee, target and role-or-action by `unique_keys`)
|`assignee` |`odrl:assignee` |`Principal` (IRI), required (a grant is an `odrl:Permission`, D-5)
|`target` |`odrl:target` |uri: the tenant IRI, or an aggregate's graph IRI; required
|`role` |`rp:role` |string, matched against the consumer's role definitions; an application may narrow it to an enum by `slot_usage`; exactly one of `role` and `action`
|`action` |`odrl:action` |`Action`, for a direct permission
|`file_name`, `media_type`, `byte_size`, `sha256`, `uploaded`, `uploaded_by`, `file_key` |`rp:fileName`, `rp:mediaType`, `rp:byteSize`, `rp:sha256`, `dcterms:dateSubmitted`, `rp:uploadedBy`, `rp:fileKey` |as in the consumer model's slot table; `file_key` internal
|`loaded_graph` |`rp:loadedGraph` |uri
|`version` |`rp:version` |string, written by the session only
|===

Annotations are resolved over the *induced* class: a class inherits `AggregateRoot`, `database` and
`graph` from its ancestors and mixins, so an abstract root's annotations reach its subclasses. LinkML
itself does not inherit class annotations; the boundary check and the mapper do.

[#revision]
== Revision of 2026-11-05 (accepted)

The developer asked for four things on top of the metamodel above: a default set of annotation
vocabularies everywhere (SKOS, DCTerms, PROV-O, and ODRL for access), models that always carry IRIs,
labels and definitions (a hard check), the access model in a module of its own, and every generated
artefact in the package that uses it.

[#annotations]
=== Annotations: two layers that are easy to confuse

[cols="1,2,3",options="header"]
|===
|Layer |About |How
|*Schema metadata* |the model's own classes and slots ("what is a Book?") |LinkML's own fields already map to the standard vocabularies: `title` → `dcterms:title`, `description` → `skos:definition`, `aliases` → `skos:altLabel`, `comments` → `skos:note`, `exact_mappings` → `skos:exactMatch`, `source` → `dcterms:source`, `contributors` → `dcterms:contributor`. The OWL and SHACL generators emit them. Nothing to add: *require* them (hard check below).
|*Instance data* |the data ("what is this book called, who wrote it into the store, when?") |Not covered by LinkML: the toolkit ships mixins with ordinary slots.
|===

Instance mixins:

[cols="1,3,2",options="header"]
|===
|Mixin |Slots (IRIs) |Written by
|`Described` |`id` (required), `label` (`skos:prefLabel`, required), `description` (`dcterms:description`, required on roots), `alt_label` (`skos:altLabel`), `definition` (`skos:definition`, for concept-like classes), `exact_match` (`skos:exactMatch`) |the application
|`Tracked` |`created`, `modified` (`dcterms:`), `creator`, `contributor` (`dcterms:`, range `Principal`) |the session, *about the graph IRI* (DEC-29: statements about the graph are kept apart from the entity)
|`Provenanced` |`was_derived_from`, `was_generated_by` (range `Activity`), `was_attributed_to` (range `prov:Agent`), `generated_at_time` (`prov:`) |the application, about the entity
|===

`Principal` is a `prov:Agent` and `AggregateRoot` a `prov:Entity`, so the provenance of a write
(who, when, which graph) is PROV-O without extra classes.

[#hard-check]
=== The hard check: IRIs, labels and definitions

`linkml-lint` cannot load extra rules, so the check is `linkml-lint` with its relevant rules raised to
errors (`no_empty_title`, `recommended`, `canonical_prefixes`, `standard_naming`) plus about 100
lines in `rp-generate` over `SchemaView`. It fails generation when:

. an element has no IRI: no `default_prefix` declared in `prefixes`, and no explicit `class_uri` or
  `slot_uri`;
. a class, slot, enum or permissible value has no `title` or no `description`;
. a permissible value has no `meaning` (an IRI);
. an aggregate root or owned class does not include `Described`, so instances without IRI, label and
  description are refused by the generated classes and shapes; an owned value class without a label
  of its own (a chapter's number) opts out explicitly with `rp_unlabelled: true`;
. a module annotated `module_kind: domain` imports one annotated `technical` or `access`.

[#extensions]
=== Generated artefacts, extensions and where they go

Each gap in a stock LinkML generator is closed by an extension in `rdf_persistence/generation/`: a
subclass or a template, never a patch to generated output. Each extension has a row here and a
golden test on the toy schema; a test fails if an extension module has neither. Modules not yet
written are listed at their planned paths.

[cols="3,2,2,4,2,1",options="header"]
|===
|Module |Artefact |Generator |Extension needed |Placed in (default) |Effort
|`rdf_persistence/generation/extensions/pydantic_split.py` |Python classes |`gen-pydantic`, split mode |templates (`rdf_persistence/generation/templates/pydantic/`) and a hook (`internal` fields excluded from the API) |the backend package, `<pkg>/domain/generated/` |S
|`rdf_persistence/generation/extensions/pydantic_validators.py` |Model validators for declared rules |`gen-pydantic`, template |the stock generator enforces neither `exactly_one_of` nor `unique_keys`: `exactly_one_of` and `any_of` become a model validator on the declaring class; `unique_keys` becomes a model validator on every class with a multivalued slot whose range declares them, refusing two items with equal key values (an absent value counts, and two absent values are equal) |with the Python classes |M
|`rdf_persistence/generation/extensions/typescript.py` |TypeScript types |`gen-typescript` |a subclass with our own template: the stock template is fixed, has no split mode and handles enums and dates poorly |the frontend package, `src/domain/generated/` |M
|`rdf_persistence/generation/extensions/shacl.py` |SHACL shapes |`gen-shacl` |a subclass that adds the toolkit's bookkeeping predicates (`rp:version`, `dcterms:created`, `dcterms:modified`, `dcterms:creator`, `dcterms:contributor`) to the ignored list of closed shapes |the backend package |S
|`rdf_persistence/generation/extensions/shacl_constraints.py` |Shape constraints for declared rules |`gen-shacl` |the stock generator translates neither rule: `exactly_one_of` becomes `sh:xone`, `any_of` becomes `sh:or`, `unique_keys` becomes a SPARQL constraint on the owning class (absent values treated as in the validators) |with the shapes |M
|`rdf_persistence/generation/extensions/jsonld_context.py` |JSON-LD context and frames |`gen-jsonld-context` |`id`/`type` aliases, `internal` slots left out, one frame per aggregate type |the backend package; copied to the frontend when needed |S
|`rdf_persistence/generation/extensions/mermaid.py` |Diagrams, one per module |`gen-mermaid-class-diagram` (D-8) |a template marking aggregate roots and owned parts, and keeping each diagram small (one module, its links to other modules shown as names only) |the docs, next to the model pages |S
|`rdf_persistence/generation/checks/` |Hard and boundary checks |`linkml-lint` + `rp-generate` |not a generator extension: about 100 lines over `SchemaView` |— |S
|===

LinkML `rules` (pre- and postconditions) are not supported in v1: `rp-generate` exits 1, naming the
class, when a schema uses them.

*The toolkit's own data types are generated too.* Each is its own `[[tool.rp-generate]]` entry, and
`rp.yaml` imports neither, so an application's model does not carry them. Like the metamodel, they
are exempt from the hard check. They are schemas, not extensions, so they have no row above.

[cols="2,3,2",options="header"]
|===
|Schema |Classes |Generated into
|`rdf_persistence/model/rp_service.yaml` |`ServiceSettings` (the settings of `install_service`), `VerifiedCaller` (what the token verifier returns), and the toolkit's request and response bodies: `TenantCreate`, `TenantSummary`, `LabelUpdate`, `GrantSet`, `Page`, `Problem` |`rdf_persistence/domain/generated/service/`
|`rdf_persistence/generation/model/rp_generation.yaml` |`GenerationManifest`, `ConstraintCase`, `ClassShape` (see <<guarding>>) |`rdf_persistence/generation/generated/`
|===

*Placement is declared, not guessed*: the application's `pyproject.toml` gets a
`[tool.rp-generate]` table mapping each target to a path; command-line flags override it. LinkML's
`gen-project` writes everything under one directory, so `rp-generate` does the placing.

*Diagrams are Mermaid* (D-8): no rendering service is needed and the docs already draw Mermaid
(`gen-plantuml` would call the public kroki.io service). A diagram that grows past about a dozen
classes is split by module. In AsciiDoc pages, escape `<` as an HTML entity inside a diagram: the
page delivers the source as HTML, and a raw `+<<stereotype>>+` breaks it.

*Extending the generators* means subclassing LinkML internals (`serialize`, the ignored-properties
method), which can change in a minor release. The pin on `linkml` and the checks of <<guarding>>
guard this; each extension gets a golden test on the toy schema.

[#application-schema]
== What the application writes

[source,yaml]
----
# models/library.yaml — the application's schema (toy example)
id: https://example.org/ns/library
name: library
prefixes:
  lib: https://example.org/ns/library#
  dcterms: http://purl.org/dc/terms/
  linkml: https://w3id.org/linkml/
default_prefix: lib
imports:
  - linkml:types
  - rdf_persistence/model/rp         # resolved through the toolkit's import map
classes:
  Book:
    description: A book held by a library.
    mixins: [AggregateRoot]
    slots: [id, title, author, chapters, scan]
  Chapter:
    description: A chapter of a book; part of the book's aggregate.
    slots: [title, number]
  Scan:
    description: A scanned copy of a book.
    mixins: [AggregateRoot, StoredFile]
  LibraryAccess:
    is_a: TenantAccess
    slot_usage: {grants: {range: LibraryGrant}}
  LibraryGrant:
    is_a: Grant
    slot_usage: {role: {range: LibraryRole}}
slots:
  title: {slot_uri: dcterms:title, range: string, required: true, description: The title.}
  author: {range: string, description: The author's name.}
  number: {range: integer, description: Position of a chapter in its book.}
  chapters:
    description: The book's chapters.
    range: Chapter
    multivalued: true
    inlined_as_list: true
    annotations: {owned: true}       # chapters live inside the book's graph
  scan:
    description: The book's scan, another aggregate, stored as its IRI.
    range: Scan
enums:
  LibraryRole:
    description: Tenant roles of the library application.
    permissible_values:
      librarian: {meaning: lib:Librarian}
----

[#toolchain]
== The toolchain

One command, run from the application's `make generate-models`, regenerates everything:

[source,shell]
----
rp-generate --schema models/library.yaml --package library.domain.generated \
            --typescript-out web/src/domain/generated --diagrams-out docs/images/model
----

`rp-generate` is a thin Python wrapper around LinkML's generator API, not a shell script, because
split generation (importing the metamodel's classes from the toolkit instead of regenerating them) is
available only through the Python API _(spike)_.

[mermaid]
....
flowchart TB
    S["schema + metamodel"] --> L["1 lint"] --> B["2 boundary and hard check"]
    B --> P["3 Python"]
    B --> H["4 shapes"]
    B --> C["5 context"]
    B --> T["6 TypeScript"]
    B --> D["7 diagrams"]
....

[cols="1,4,3",options="header"]
|===
|Step |What it does |Fails when
|1 Lint |`linkml-lint` with the toolkit's lint configuration: canonical prefixes (`dcterms`, not `dct`), descriptions on every element, snake_case enum values _(spike)_ |the schema has lint errors
|2 Boundary check |Over LinkML's `SchemaView` (about 40 lines in the spike): roots are the classes whose induced ancestors include `AggregateRoot`; every other non-mixin class is reachable only through `owned` slots (it may be owned by several root classes, e.g. a reusable value class); a non-owned slot whose range is a class must point to a root |a class is reachable through a non-owned slot without being a root, or is owned by nothing, or a module annotated `module_kind: domain` imports one annotated `module_kind: technical` or `access`
|3 Domain classes |`gen-pydantic` in split mode with the toolkit's template directory: a one-line `base_model.py.jinja` makes every class inherit the toolkit's strict base (no extra fields, validation on assignment); metadata mode off; metamodel classes imported from the top-level `rdf_persistence` _(spike: split generation works; the spike pointed it at a submodule)_ |generation fails
|4 Shapes |`gen-shacl`. Shapes are closed (`sh:closed true`) _(spike)_, and the version token sits on the graph IRI, not the root, so the domain triples validate on their own |generation fails
|5 JSON-LD context |`gen-jsonld-context`, with `id` and `type` aliased to `@id` and `@type`; served by the service kit (O-2). Known gaps (no `@language` containers, inlined collections keyed by `@index`) need template fixes before a schema uses those features _(not yet run)_ |generation fails
|6 TypeScript types |`gen-typescript` with the toolkit's template, which fixes enums and dates (the stock output is weak on both); interfaces only, into the client package the application names _(not yet run)_ |generation fails
|7 Diagrams |`gen-mermaid-class-diagram`, once per schema module, so each diagram shows one module's classes and their links to other modules _(per-module output not yet run)_ |generation fails
|===

Each step writes to a temporary file and moves it into place only on success, so a failed run leaves
the previous output intact. The package also receives a copy of the schema: the mapper reads it at run
time, so code and mapping always come from the same schema version.

*Modules.* An application splits its schema into one file per module: a *domain module* per
aggregate (its root and the classes it owns) and *technical modules* for concerns such as paging or
API envelopes, written as mixins. A root schema imports the modules. Domain modules never import
technical ones (step 2). The metamodel's mixins (`AggregateRoot`, `StoredFile`) are usable in domain
modules: they say how a class is persisted, not what it means.

*Not generated:* mappers, repositories, routes and API clients (O-1); the client calls the API with
the generated types.

[#run-time]
== At run time

[source,python]
----
from rdf_persistence import open_session            # public API only
from library.domain.generated import Book, SCHEMA

async with open_session(store, schema=SCHEMA, tenant=library_iri, caller=caller) as session:
    book = await session.get(Book, book_iri)        # loads the book's graph, maps it to Book
    book.title = "New title"
    await session.commit()                           # one guarded update; conflict if the version moved
----

* *Mapping* _(spike: about 70 lines, round trip equal)_: class and slot IRIs come from the schema
  (`class_uri`, `slot_uri`, or the default prefix); owned parts become blank nodes in the root's graph;
  references to other aggregates are IRIs; multi-valued slots are sets, so order is not kept (model an
  order slot when order matters).
* *Commit* _(spike, Fuseki 5.1.0)_: one update deletes the graph's triples and inserts the new ones
  with a fresh version token, guarded by the old token; Fuseki answers 204 even when the guard
  matches nothing, so an `ASK` for the new token tells committed from conflict.
* *Kinds*: an abstract root with a `designates_type` slot (`rdf:type`) lets `session.get` return the
  concrete subclass.

[#guarding]
== Guarding the generated code

The rule of xref:architecture/open-decisions.adoc[D-13] comes from
https://meaningfy.atlassian.net/wiki/spaces/MR/pages/2107342856[the model-driven development runbook]:
generated models are not hand-written and not modified; a change starts in the model; generation
runs at build and test time; a model change makes the unit tests fail until it is reviewed.

=== Freshness: the manifest and `rp-generate --check`

Every `[tool.rp-generate]` entry writes a manifest, `rp-manifest.json`, in its `python` folder (model:
`GenerationManifest`). It records the `linkml` version and the path and SHA-256 of every input and
output, sorted by path, with paths relative to the `pyproject.toml`.

[cols="1,4",options="header"]
|===
|Recorded |Files
|Inputs |the schema's import closure (metamodel files as `rdf_persistence/<path>`, so the manifest does not depend on where the package is installed), the template directories, and every module under `rdf_persistence/generation/` except `generated/`
|Outputs |every file the run wrote, in every target folder, except the manifest. A run deletes only the files its previous manifest lists, never a whole folder.
|===

`rp-generate --check` writes nothing: it runs lint and the hard and boundary checks, then recomputes
the hashes. A changed input or a different `linkml` version means *stale*; a changed output means
*edited by hand*. Either exits 1, naming the files and the command that fixes them. Without the
`generate` extra, only the hashes are compared.

[cols="2,3",options="header"]
|===
|Where |What runs
|`make check-quality` (before every PR, and in CI) |the full `--check`
|every pytest session |the manifest comparison, by the plugin `rdf_persistence.testkit.freshness` in `pytest_sessionstart`; it stops the run on anything stale or edited. A consumer enables it with `pytest_plugins = ["rdf_persistence.testkit.freshness"]`; the ini option `rp_generate_projects` lists the `pyproject.toml` files to read (default: the rootdir's).
|pre-commit hook `rp-generate-check` |the check, on commits touching the model, the generation package, the toy library or a `generated/` folder
|`make check-generated` (CI) |a regeneration from scratch and a diff, which catches a generator that is not deterministic
|===

Generation is part of the build: `make generate` regenerates every entry, and `make build` runs it
first.

=== Correctness of the generated code

. *Schema gates first*: lint, then the hard and boundary checks; nothing is generated from a schema
  that fails them.
. *Golden tests per extension*: RDF output compared by graph isomorphism, other output as exact
  text, and the set of files compared exactly.
. *Classes and shapes agree*: for every row of `tests/fixtures/conformance/cases.yaml`
  (`ConstraintCase`: a constraint kind, a class, valid and invalid instances), the generated class and
  the generated shape both accept the valid instances and refuse the invalid ones. The kinds of v1
  are `required`, `cardinality`, `range_type`, `range_enum`, `pattern`, `value_bounds`, `identifier`,
  `closed`, `exactly_one_of`, `any_of` and `unique_keys`; the test fails, naming the kind, when a
  schema uses a kind with no row. A consumer runs it with `testkit.conformance.run(schema, cases)`.
. *Round trips*: an instance drawn by Hypothesis from the schema goes to JSON, is expanded with the
  generated context to RDF, then framed and compacted back; the objects compare equal and the RDF
  graphs are isomorphic.
. *Model shape*: every generated class's pydantic fields match the schema's induced slots (name,
  required, multivalued, range), which catches stale or edited code even without the manifest.
. *A model change fails the tests until acknowledged*: `tests/fixtures/model-shape.yaml` holds the
  last reviewed shape of every class (`ClassShape` rows). Any model change fails the test until
  `make refresh-snapshot` rewrites the file and its diff is reviewed in the PR.
. *Generated code compiles*: every generated module imports and passes mypy with the
  `mypy-generated.ini` profile (the main run excludes generated folders); the TypeScript output
  passes `tsc --noEmit --strict` in CI.

=== Guards against hand-written models

Both guards are `testkit.assert_models_generated(package, *, roots, allow=())`, so applications get
them too.

* *Model guard*: parses every module of `domain`, `services` and `entrypoints`, skipping paths with a
  `generated` segment, and fails, naming the class, on a class deriving from `pydantic.BaseModel`,
  `RpModel`, `enum.Enum`, `enum.StrEnum`, `enum.IntEnum`, `typing.TypedDict` or `typing.NamedTuple`,
  or decorated with `dataclasses.dataclass`. Import aliases are resolved. The only default exception
  is `RpModel` in `rdf_persistence/domain/base.py`; an application passes its own with `allow=`.
* *File guard*: fails on `*.shacl.ttl`, `*shapes*.ttl`, `*.context.jsonld`, `*.frame.jsonld`,
  `*.schema.json`, `openapi*.json`, `openapi*.yaml` and `*.ts` (except `*.test.ts` and `*.spec.ts`)
  outside a folder named `generated`. This repository scans `rdf_persistence/` and `tests/`, with
  `tests/fixtures/` exempt.

=== Versions and commits

* `linkml` and `linkml-runtime` are pinned together (mismatched versions fail at import _(spike)_).
  Bumping them is a deliberate change: bump, regenerate, review the diff, accept.
* The schema and the regenerated code are committed together.
* Generated code sits in the domain layer and imports nothing from services, adapters or entrypoints.

[#adoption]
== How an application adopts it

. Write `models/<app>.yaml` and one file per module, importing the metamodel; mark aggregate roots, owned slots, databases;
  write the application's role definitions (and, optionally, narrow `role` by subclassing `Grant`).
. Add `make generate-models` calling `rp-generate`, and the freshness check to CI.
. Write use-case services against `open_session` and the generated classes.
. Write routes with the service kit; publish the OpenAPI contract and the JSON-LD context; use the generated TypeScript types in the client, checked against the contract.
