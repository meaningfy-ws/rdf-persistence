= Model to code: the generation workflow
:description: How an application's own LinkML model becomes typed, persistable code with rdf-persistence.

An application using rdf-persistence writes its domain once, in LinkML. A deterministic, build-time
toolchain turns it into domain classes and shapes; at run time the toolkit reads the same schema to
map objects to RDF. No generated file is edited by hand, and no LLM sits in the generation path.
This page explains what is generated, what is written once in the toolkit and why
(<<decision>>), what the application writes (<<application-schema>>), how the toolchain runs
(<<toolchain>>), what the run time reads from the schema (<<run-time>>), and how the generated code
is guarded (<<guarding>>). To work on the toolchain itself, see
xref:develop/index.adoc[Working on the library]. How the design got here is in <<history>>.

LinkML is the single source of specification
(xref:architecture/open-decisions.adoc[D-13]): every artefact that restates the model is generated,
by a stock generator or a toolkit extension (<<extensions>>), and nothing that restates it is
written or edited by hand (<<guarding>>).

The running example is a toy library application: each library is a tenant holding `Book`
aggregates, each book with owned chapters, and `Scan` aggregates that keep a scanned copy of a
book as a stored file; librarians hold the tenant role `librarian` (`tests/fixtures/library/`).

[#decision]
== The decision (O-1)

_Which code is generated, and which is written once in the toolkit?_

*Generated domain classes, runtime mapper.* Only LinkML's standard generators run, through the
toolkit's templates. Since 2026-11-05 (D-2) the classes and the mapper serve *domain services* only;
the API path needs neither (xref:architecture/api.adoc[API]). The mapper, the repositories and the routes are not generated: they are generic
code that reads the schema at run time. A per-aggregate generator (repositories, routes) is built only
if hand-written routes start repeating themselves across applications.

Rejected for v1: generating mappers, repositories and routes per aggregate (the background study's
"approach B"), because it means owning a code generator before a second application exists; and a
fully generic service without typed classes ("approach C"), because domain logic then has no types.

[#metamodel]
== The metamodel

_What does the toolkit give a schema to build on?_

A small LinkML schema shipped inside the package (`rdf_persistence/model/`, split into modules
since the <<revision,revision of 2026-11-05>>; namespace `https://meaningfy.ws/ns/rdf-persistence#`). Its classes are generated once, into the toolkit's own
package; an application's generated code imports them rather than regenerating them.

[cols="2,5",options="header"]
|===
|Element |Meaning
|`AggregateRoot` (mixin) |Instances are aggregate roots: each is one named graph, whose IRI `graph_iri(root)` is derived from the root's IRI (for example `<root>/graph`; background DEC-29), versioned, loaded and saved as a whole.
|`owned` (slot annotation)
|The slot's values are part of this aggregate and live in its graph (a commit replaces the whole
graph). A part whose class includes `Described` has an IRI, by default `{root_iri}/parts/{uuid4}`
(the IRI policy's part template), minted by the toolkit when it has none and kept across commits; a
part without an identifier slot (a grant, a prohibition) is a blank node, skolemised on write (PD-6,
PD-8a). Any other slot whose range is a class refers to another aggregate root, by IRI.
|`database` (class annotation) |`tenant` (default) or `system`: which database the aggregate lives in.
|`graph: meta` (class annotation) |The tenant's root object lives in the tenant database's designated `meta` graph instead of a graph of its own.
|`internal` (slot annotation) |Only the service sets the slot (e.g. file keys, a tenant's database name): it never appears in the API contract or a response, a request body that sets it is refused (422), the tenant-create body included, and a replace keeps its stored value on the root and on the parts that persist, matched by IRI. The mapper writes it, so a domain service can set it.
|`rp_path` (class annotation) |Required on every aggregate root: the collection's segment in the API, and by default in the aggregate's IRI, `{tenant}/{rp_path}/{uuid}` (see `rp_iri_type`).
|`rp_writes: service` (class annotation) |An aggregate root the consumer writes through a session: the API serves its `GET` and listing but no `POST`, `PUT` or `DELETE`. A root that includes `StoredFile` is service-written without it. There is no value that turns this off.
|`rp_writes: toolkit` (class annotation) |An aggregate root the toolkit writes and reads itself: a `Comment`. No route serves it (`served_roots` in `schema_structure.py` leaves it out) and the consumer does not write it, because who may see or make one is decided by rules a generic route does not know. The two values are the enum `WritesKind`.
|`workflow` (class annotation) |On an aggregate root that includes `UnderWorkflow`: the name of the workflow its instances follow. A subclass inherits it along `is_a` (`workflow_name_of` in `schema_structure.py`). The workflow itself is a file given to the service, not part of the schema; see xref:howto/workflow.adoc[Put a resource through review].
|`rp_unlabelled` (class annotation) |An owned value class whose instances need no label of their own.
|`Principal` |A reference to a user account in the identity provider, by IRI only.
|`Activity`, `Generation`, `Invalidation`, `Add`, `Replace`, `Remove` |The record of a use case that changed the store (`rp_provenance`, PROV-O). An `Activity` has a start, an end, a principal, and the `generations` and `invalidations` it caused. `Generation` and `Invalidation` name the entity versions an activity produced or ended; `Add`, `Replace` and `Remove` are the three kinds of change to an aggregate. An activity is no aggregate root: the toolkit stores it in the tenant's provenance graph. A consumer's use-case activity descends from `Activity` and lives in a sibling module `<domain>_activities.yaml`; see xref:howto/event-driven.adoc[the event-driven how-to].
|`toolkit_filled` (slot annotation) |The toolkit sets the slot of an activity's record (who, when, which versions). A caller's value is refused or overwritten.
|`payload` (slot annotation, in a command class's `slot_usage`) |The command carries the slot, but the stored record does not. A payload slot is never required.
|`StoredFile` (mixin) |The current content of a kept file: `file_name`, `media_type`, `byte_size`, `sha256`, `uploaded`, `uploaded_by`, `file_key` (internal).
|`loaded_graph` (slot) |A graph whose lifecycle belongs to the aggregate (e.g. the triples of a loaded RDF file).
|`TenantAccess`, `Grant`, `Prohibition` |The tenancy records of the system database (N-11): label, state (`TenantState`: `active`, `deleting`), database name, owned grants and prohibitions (ODRL). `TenantAccess` is a `Policy`; an application subclasses it once, in an access module. Role names come from the consumer's role definitions; an application may narrow `role` to an enum by subclassing (`is_a` with `slot_usage`), but need not.
|`RoleDefinition` |One entry of the application's role definitions: a `role`, the `level` it applies at (`RoleLevel`: `system`, `tenant`, `aggregate`) and the `actions` it permits. Supplied as a YAML file, read by `load_role_definitions`, never stored.
|`RegistryEntry` |An entry of a tenant's `registry` graph: the graph's IRI, its kind (`aggregate`, `loaded_graph`) and the aggregate that owns it. Written by the session, never by the application.
|`ReferenceCollection` (mixin), `MembershipRule`, `SlotEquality` |An aggregate that groups other aggregates of one class (`member_class`) without owning them: the members it names by IRI (`has_part`, `dcterms:hasPart`; the mixin's class is `dcmitype:Collection`) and an owned rule of slot equalities (`SlotEquality`: `equals_slot`, `equals_value`). The application writes it. See xref:howto/reference-collections.adoc[Group resources you do not own].
|`Comment` |A remark on an aggregate, or a reply to one: an aggregate root of its own (`oa:Annotation`, path `rp-comments`), `rp_writes: toolkit`. See xref:howto/discussion.adoc[Comment on a resource without editing it].
|`UnderWorkflow` (mixin), `Workflow`, `WorkflowTransition`, `Transition` |`UnderWorkflow` gives an aggregate root its current state (`workflow_status`, `adms:status`, the IRI of a state). `Workflow` and `WorkflowTransition` are the definition read from a file at start-up and never stored. `Transition` (`is_a: Activity`, `class_uri: rp:Transition`) is the record of one move. It is no aggregate root and has no path: it is an activity, stored in the tenant's provenance graph. See xref:howto/workflow.adoc[Put a resource through review].
|`version` (slot) |The version token of every aggregate, stated about its graph IRI (not the root), written by the session; not part of any domain class.
|`module_kind` (schema annotation) |`domain`, `technical` or `access`: what a schema module holds; the boundary check uses it (<<toolchain>>).
|`bookkeeping` (slot annotation) |The session writes the slot about a graph (`version`, `created`, `modified`, `creator`, `contributor`); closed shapes ignore it.
|`python_package` (schema annotation) |On a schema module of the toolkit's own targets: the Python package its classes are generated into. A toolkit run imports a metamodel class from `<python_package>.<module name>`. It equals the `package` of the `\[[tool.rp-generate]]` entry that generates the module; the hard check compares them (<<hard-check>>).
|`public_package` (schema annotation) |On the metamodel's root schema, `rp.yaml`: the package an application's generated code imports the metamodel's classes from, which re-exports them. Only the toolkit sets it.
|===

The annotation names are the generated enum `RpAnnotation`, and their values the enums
`ModuleKind`, `DatabaseKind`, `GraphKind` and `WritesKind`: a value outside them fails the hard check, so no code
compares free strings. The rules that read a schema's aggregate structure (roots, the tenant root,
owned, internal and bookkeeping slots, PD-11's defaults, the presence alternatives and keyed slots
of a class) live once, in `rdf_persistence/schema/services/schema_structure.py`, beside `load_schema` in
`schema.py`; the checks, the extensions, the testkit and the mapper all use them.

Slots of the metamodel (IRIs in the `rp:` namespace unless shown):

[cols="2,2,3",options="header"]
|===
|Slot |IRI |Range, cardinality
|`id` |— (identifier) |uri, required on every aggregate root
|`label` |`skos:prefLabel` |string, from `Described`; required on `TenantAccess` (1–200 characters) and on described roots
|`state` |`rp:state` |`TenantState`, required
|`database_name` |`rp:databaseName` |string, required
|`grants` |`rp:grant` |`Grant`, multivalued, owned (blank nodes, skolemised to `{graph_iri}/.well-known/genid/{uuid4}` on write; one per assignee, target and role-or-action by `unique_keys`)
|`assignee` |`odrl:assignee` |`Principal` (IRI), required (a grant is an `odrl:Permission`, D-5)
|`target` |`odrl:target` |uri: the tenant IRI, or an aggregate's graph IRI; required
|`role` |`rp:role` |string, matched against the consumer's role definitions; an application may narrow it to an enum by `slot_usage`; exactly one of `role` and `action`
|`action` |`odrl:action` |`Action` (`read`, `modify`, `delete`, `administer`, `annotate`; fixed by the toolkit): for a direct permission, or the action a prohibition forbids (required there)
|`prohibitions` |`rp:prohibition` |`Prohibition`, multivalued, owned (blank nodes, skolemised like `grants`)
|`level` |`rp:level` |`RoleLevel`, required, on `RoleDefinition`
|`actions` |`rp:permits` |`Action`, multivalued, required (and not empty), on `RoleDefinition`
|`file_name`, `media_type`, `byte_size`, `sha256`, `uploaded`, `uploaded_by`, `file_key` |`rp:fileName`, `rp:mediaType`, `rp:byteSize`, `rp:sha256`, `dcterms:dateSubmitted`, `rp:uploadedBy`, `rp:fileKey` |as in the consumer model's slot table; `file_key` internal
|`loaded_graph` |`rp:loadedGraph` |uri
|`version` |`rp:version` |string, written by the session only
|===

Annotations are resolved over the *induced* class: a class inherits `AggregateRoot`, `database` and
`graph` from its ancestors and mixins, so an abstract root's annotations reach its subclasses. LinkML
itself does not inherit class annotations; the boundary check and the mapper do.

The developer asked for four things on top of the metamodel above: a default set of annotation

artefact in the package that uses it.

An arrow is an import; an import a module already gets through another one is not drawn
(`rp_tenancy` reaches `rp_core` through `rp_access`).

`rp.yaml` imports all nine modules (`rp_core`, `rp_annotations`, `rp_provenance`, `rp_access`,
`rp_tenancy`, `rp_files`, `rp_collections`, `rp_discussion` and `rp_workflow`); an application
imports `rp.yaml`, or only the modules it uses. The toolkit's own schema is at version `"2"`;
`rdf_persistence/model/migrations/1__2.yaml` is the step from version 1 and has no operations.

`rp_provenance` holds the activity classes (`Activity`, `Generation`, `Invalidation`, `Add`,
`Replace`, `Remove`). `rp_discussion` (`PostComment`, `PostReply`) and `rp_files` (`DeleteFile`)
hold the commands of their area as activities, so both import it.

The last three hold what a collaborative application needs beyond aggregates that own their parts:
a group of aggregates it does not own (`rp_collections`), comments (`rp_discussion`) and review
states (`rp_workflow`). Each is optional: a schema that does not import a module gets none of its
behaviour, and the call that needs it raises `LookupError`. `rp_workflow` imports `rp_provenance`
because a `Transition` is an `Activity`, and `rp_discussion` because a transition may post a
comment: the two slots that say which state was left and which was entered (`from_state_iri`,
`to_state_iri`) are defined once, in `rp_discussion`, and used by the comment and by the record.

[#annotations]
=== Annotations: two layers that are easy to confuse

[cols="1,2,3",options="header"]
|===
|Layer |About |How
|*Schema metadata* |the model's own classes and slots ("what is a Book?") |LinkML's own fields already map to the standard vocabularies: `title` → `dcterms:title`, `description` → `skos:definition`, `aliases` → `skos:altLabel`, `comments` → `skos:note`, `exact_mappings` → `skos:exactMatch`, `source` → `dcterms:source`, `contributors` → `dcterms:contributor`. The OWL and SHACL generators emit them. Nothing to add: *require* them (hard check below).
|*Instance data* |the data ("what is this book called, who wrote it into the store, when?") |Not covered by LinkML: the toolkit ships mixins with ordinary slots.
|===

Instance mixins:

[cols="1,3,2",options="header"]
|===
|Mixin |Slots (IRIs) |Written by
|`Described` |`id` (required), `label` (`skos:prefLabel`, required), `description` (`dcterms:description`, optional everywhere), `alt_label` (`skos:altLabel`), `definition` (`skos:definition`, for concept-like classes), `exact_match` (`skos:exactMatch`) |the application
|`Tracked` |`created`, `modified` (`dcterms:`), `creator`, `contributor` (`dcterms:`, range `Principal`) |the session, *about the graph IRI* (DEC-29: statements about the graph are kept apart from the entity)
|`Provenanced` |`was_derived_from`, `was_generated_by` (range `Activity`), `was_attributed_to` (range `prov:Agent`), `generated_at_time` (`prov:`) |the application, about the entity
|===

`Principal` is a `prov:Agent` and `AggregateRoot` a `prov:Entity`, so the provenance of a write
(who, when, which graph) is PROV-O without extra classes.

[#hard-check]
=== The hard check: IRIs, labels and definitions

`linkml-lint` cannot load extra rules, so the check is `linkml-lint` with the rule sets of
`rdf_persistence_generation/lint.yaml` raised to errors (`recommended`, `standard_naming`,
`canonical_prefixes`) plus `rdf_persistence_generation/checks/hard.py` over `SchemaView`. Its rules
are the generated enum `HardRule`. It fails generation when:

. an element has no IRI: no `default_prefix` declared in `prefixes`, and no explicit `class_uri` or
  `slot_uri`;
. a class, slot, enum or permissible value has no `title` or no `description`;
. a permissible value has no `meaning` (an IRI);
. an aggregate root or owned class does not include `Described`, so instances without IRI and label are refused by the generated classes and shapes; an owned value class without a label
  of its own (a chapter's number) opts out explicitly with `rp_unlabelled: true`;
. an aggregate root has no `rp_path`, or an `rp_path` that is not a URL segment;
. an annotation value is not one of its allowed values, or a `workflow` name is not a URL segment;
. a `unique_keys` name is not an identifier (generated validators carry it);
. a key annotated `rp_unique_scope` (a key across aggregates) has a scope other than `tenant`; sits
  on a class that is not a tenant-database aggregate root or an ancestor of one; names a slot that
  is not a slot of every such root, is multivalued, is the identifier, is bookkeeping or holds an
  owned part; or sets `consider_nulls_inequal: false`. An unscoped `unique_keys` declared on a
  tenant-database aggregate root class itself is refused too, since it would enforce nothing. Each
  problem names the class, the key and, for a slot, the slot;
. the `rp_path` or the `rp_iri_type` (the type segment of a class's IRIs) of a class starts with
  `rp-` (rule `RESERVED_SEGMENT`). The prefix belongs to the toolkit's own roots (`rp-comments`), so a
  path or an IRI of an application never meets one of theirs;
. a class of the application breaks the activity contract (rule `TOOLKIT_FILLED`): it gives a
  `toolkit_filled` slot a `slot_usage`, an `ifabsent`, an attribute of its own or a `slot_uri` alias,
  or it has a slot that is both `payload` and required;
. a slot annotated `default_instance` (a `GenerationAnnotation`) cannot default to a new instance of
  its range (rule `DEFAULT_INSTANCE`): it is multivalued, its range is not a class, a required slot
  of the range class has no `ifabsent`, or the range class is declared after the class that holds the
  slot in the same module (the generated module builds the default where the class is defined). The
  problem names the slot;
. the `workflow` annotation and the `UnderWorkflow` mixin do not come together (rule `WORKFLOW`):
  a class names a workflow but is not an aggregate root, is the tenant root, or does not include
  `UnderWorkflow`; or an aggregate root includes `UnderWorkflow` and neither it nor an `is_a`
  ancestor names a workflow. The check knows the name only: that a file defines the workflow is
  checked when the service starts (`InvalidWorkflow`);
. a schema that defines aggregate roots of its own is generated by an entry with no `migrations`
  (rule `MIGRATIONS_FOLDER`); the problem names the roots and the schema;
. the root schema of an entry with `migrations` has no `version`, or one that is not a quoted string
  in the YAML source (rule `QUOTED_VERSION`), since `1.10` unquoted is read as 1.1;
. in a run of the toolkit's own targets (`checks/python_package.py`), a schema module has no
  `python_package` annotation (rule `PYTHON_PACKAGE`), or one that differs from the `package` of the
  entry that generates it (rule `PYTHON_PACKAGE_MISMATCH`). The problem names the module and both
  packages. A module generated by another target (it sits beside the root and names another
  package) must name the package of one of the toolkit's targets; otherwise the same rule fails with
  `<module> names python_package <package>, which no toolkit target generates`. An application's run does not apply these two rules: the toolkit's `pyproject.toml` is
  not in the wheel, so it has nothing to compare the annotation with.

The checks cover the schema's own modules only; the metamodel's are exempt. The two
`python_package` rules apply to every module of a toolkit target, `rp.yaml` among them. The `module_kind`
import rule belongs to the boundary check (<<toolchain>>, step 2).

[#extensions]
=== Generated artefacts, extensions and where they go

Each gap in a stock LinkML generator is closed by an extension in `rdf_persistence_generation/`: a
subclass or a template, never a patch to generated output. Each extension has a row here and a
golden test; a test fails if an extension module has neither. For the toy schema the golden is the
committed generated tree itself (a test renders afresh and compares: Turtle by meaning, everything
else by exact text, the file set exactly), so `make generate` is what refreshes it. A schema that is
not the toy keeps a golden folder, rewritten by `make refresh-golden`; the served OpenAPI and
TypeScript goldens are rewritten only by `make refresh-served-golden`, which resets the baseline that
guards the thematic move. Each extension exposes one
`render(schema_path)` that returns the files it makes; `steps.py` composes the steps from them.

*Rules the generated code would silently ignore fail instead* (`checks/rules.py`). On a class only
`exactly_one_of`, `any_of` and `unique_keys` are enforced; LinkML `rules` (pre- and postconditions),
`all_of` and `none_of` make `rp-generate` exit 1, naming the class. On a slot, only `any_of` as a
union of ranges passes, since both the classes (`Union[...]`) and the shapes (`sh:or`) render it.

*The toolkit's own data types are generated too.* They are the technical models of <<kinds>>: each
group is its own `\[[tool.rp-generate]]` entry, and `rp.yaml` imports none, so an application's model
does not carry them. Like the metamodel, they are exempt from the hard check's class rules, but not
from the two `python_package` rules (<<hard-check>>). They are schemas, not
extensions, so they have no row above. Hand-written types remain only where a field holds a foreign
run-time object LinkML cannot express (a `SchemaView`, a callable, an rdflib graph), or where the type
subclasses a LinkML generator; each is named in the model guard's allow-list (<<guarding>>).

_How does a reader tell a class a consumer persists as RDF from a record bound to a technology?_

Every settings group sits in a `services` layer, since an adapter and the service kit both use it;
the allowed JWS algorithms of `JwksSettings` are a list that refuses `none` and every `HS*` name.
The served schemas are eight, in the order of `SERVED_SCHEMAS` (`schema/services/schema.py`):
`rp_iris_services`, `rp_persistence_services`, `rp_migrations_services`, `rp_access_services`,
`rp_tenancy_services`, `rp_events_services`, `rp_collaboration_services`, `rp_api_entrypoints`. A
schema is listed before the ones that import it, and listing one before a schema it imports is an
error naming both; a class declared by two served schemas is an error too. `api/services/components.py` merges
their OpenAPI components into one document, and the TypeScript step copies their classes, all into
`rp_service.ts`, in that order.

The testkit group is separate from `rp_generation.yaml` so that the testkit's records do not come from
the generator's models: the runtime layers import neither (contract `runtime-without-extras`), and the
testkit's own modules read `testkit.generated`. The two testkit modules that need the generator's
logic, `freshness.py` and `conformance.py`, now live in the generator's package
(<<generator-package>>). `rp_generation.yaml`
(`rdf_persistence_generation/model/`, into `rdf_persistence_generation/generated/`) is the generator's
own technical target, and holds what the toolchain uses: `GenerationTarget`, `GenerationManifest`,
`GeneratedFile`, `CheckProblem`, `CliFlag`, the rule, frame, TypeScript and Mermaid view-models, and the
conformance suite's `ConstraintCase` and `ConstraintKind`.

*Why one target for each schema.* `rp-generate` generates one folder for each target, and only a
served schema has OpenAPI components and reaches a consumer's TypeScript, so a setting or a template
record must not join a served one: it would appear in the served OpenAPI document. That is why a
theme with served records and settings has two targets (`access/services/generated/` and its
`settings/` folder). A new technical schema is one more file under `model/technical/<theme>/` and one
more `\[[tool.rp-generate]]` entry. Each module of the schema also carries the `python_package`
annotation, set to the `package` of that entry; without it the hard check refuses the run.

[#cross-target]
==== Imports between targets

A schema may import a module that another target generates. When the imported module declares
`python_package`, the generated code imports its classes from `<python_package>.<module>` and does
not generate them again; the manifest lists the imported module's YAML as an input, so the freshness
check sees a change to it. `rp_api_settings.yaml` imports four settings schemas this way
(`rp_core_services`, `rp_persistence_settings`, `rp_access_settings`, `rp_events_settings`), and
`rp_tenancy_services.yaml` imports `rp_iris_services` and `rp_migrations_services`. An imported module
without `python_package` is generated into the importing target, as before, and so is a module in
the same folder as the target's root schema, unless it names another `python_package` than the
root's. A consumer's run uses the same rule, so a consumer's
technical target can import its own domain target when the domain schema sits in another folder and
declares `python_package`.

The toolkit's own metamodel uses the same import beside the root. A module in the root's folder
that names another `python_package` than the root's is imported from that package, not generated
into the root's: `rp_tenancy.yaml`'s target imports `rp_core`'s classes from
`rdf_persistence.core.domain.generated` and writes no file for `rp_core`. A consumer's import of
the metamodel still goes through `rdf_persistence`.

That needs two sets of modules, and each step uses one:

* `generated_schemas`: the modules of the closure whose `python_package` is absent or equal to the
  root's. They are the ones a target writes as Python, and the ones the `python_package` check
  tests against the entry's `package`.
* `own_schemas`: the whole closure in the root's folder. The shapes, the context, the frames, the
  lock and the diagrams use it, so a theme target's root still sees every class below it.

On the toolkit's run the package check also reads the packages of all the toolkit's entries. A
module of the closure that another target generates must name one of them; otherwise the run fails
with `PYTHON_PACKAGE_MISMATCH`, "names python_package ..., which no toolkit target generates".

The stored-schema check and the lock stay with `rp.yaml`, whose closure holds every domain module
and so every aggregate root: only that target declares `migrations` and writes the one lock. A
theme target is skipped by the check only when `rp.yaml` already checks all its roots. A theme's
root writes a module only for the classes it declares itself (`rp_tenancy.yaml`, `rp_files.yaml`,
`rp_provenance.yaml`), importing just what it uses; a root with no classes, such as
`rp_collaboration.yaml`, writes none.

The combined `shapes.ttl`, `context.jsonld` and frames are generated from all the domain modules
into `core/domain/generated/`, and those are the ones to load. Each theme target writes partial
copies in its own folder, which miss other themes' shapes and must not be loaded.

[#target-kind]
==== The kind of a target

A `\[[tool.rp-generate]]` entry has no `kind` key: the kind of a target is derived from the modules
it generates: the modules its root schema imports from its own folder. A target is `technical` when
every one of them is annotated `module_kind: technical`, and `domain` otherwise (an unannotated module, or
one annotated `domain` or `access`).

[source,toml]
----
[[tool.rp-generate]]
schema = "rdf_persistence/model/technical/api/rp_api_settings.yaml"
package = "rdf_persistence.api.entrypoints.generated.settings"
regenerate-command = "make generate"
openapi = false
----

A target generates one kind. When some of its modules are annotated `module_kind: technical` and
others are not, `rp-generate` fails in the boundary check (rule `TARGET_KIND`), naming the target's
schema and the technical modules; nothing is written. Move the technical modules to a folder and an
entry of their own (xref:user-manual/generate.adoc#technical-target[Keep technical models in a target of their own]).

The derived kind then decides the folder, for every target, a consumer's included. In the target's
`package`, the segment before `generated` is `domain` for a `domain` target, and `services`,
`adapters` or `entrypoints` for a `technical` one. A package with no layer before `generated`
(`app.generated`, `generated`) fails, and so does a layer of the other kind; when a `domain` target
sits in a technical layer, the problem adds a hint to annotate its modules `module_kind: technical`,
since the derivation may have read modules that are meant to be technical as domain. A segment after
`generated`, such as `settings`, is allowed. The problem names the target's package.

For the toolkit's own targets the same rule also checks the theme: the segment before the layer is a
theme of the library (`rdf_persistence.<theme>.<layer>.generated`). Two packages sit outside the
themes and are exempt from the whole rule: `rdf_persistence.testkit` and `rdf_persistence_generation`.
A consumer's target has no theme to check: `app.catalogue.domain.generated` and
`app.services.generated` are both fine.

[#python-import]
==== Two annotations for technical models

Both are values of the `GenerationAnnotation` enum, and a consumer's schema may use them too.

* `python_import` on a type. A model whose field must hold a class that is not a LinkML scalar names
  the class in the type's `repr` and its module in `python_import`; the generated module imports it
  and the field has that class. `rp_schema_templates.yaml` declares a field's type this way, so a bundle of
  SPARQL terms holds `SparqlTerm` values, not strings, and a raw string fails validation:
+
[source,yaml]
----
types:
  sparql_term:
    typeof: string
    repr: SparqlTerm
    uri: rp:SparqlTerm
    annotations:
      python_import: rdf_persistence.core.domain.sparql
----
+
A type with a `repr` and no `python_import` adds no import, and the generated module then fails to
import its name; `make check-generated` catches it.
* `default_instance: 'true'` on a slot whose range is a class. The slot defaults to a new instance
  of the class (`Field(default_factory=<Range>)`), so `ToolkitSettings().http` is an `HttpSettings`
  with its defaults and not `None`. The hard check (rule `DEFAULT_INSTANCE`, <<hard-check>>) refuses the
  annotation on a multivalued slot, on a slot whose range is not a class, when a required slot of the
  range class has no `ifabsent`, and when the range class is declared after the class that holds the slot.

The default of a *list* is its own gap in the stock generator: it writes the `ifabsent` of a
multivalued slot as the one string `"a, b"`. The toolkit's extension writes `ifabsent: string(a, b, ...)`
as the list `['a', 'b']`, and refuses any other form on a multivalued slot (`JwksSettings.allowed_algorithms`
is declared this way).

*Placement is declared, not guessed*: the application's `pyproject.toml` gets a
`[tool.rp-generate]` table (or an array of tables, one per schema) with the keys `schema`,
`package`, `python` (default: the package's path), `migrations` (the folder of the schema lock and the migration files; required when the schema defines roots of its own, and then the root schema has a quoted `version`), `typescript`, `diagrams`, `regenerate-command` (the command a failed freshness check tells you to run; default `rp-generate`) and `openapi` (default
`true`; `false` skips step 5b for a schema no service serves, as for the toolkit's metamodel,
and every technical schema that is not served, <<kinds>>); there is no `kind` key, the kind of a target is derived (<<target-kind>>). Paths are relative to the `pyproject.toml`. The flags `--schema`, `--package`, `--python-out`, `--typescript-out` and
`--diagrams-out` override the keys of a single entry; with several entries a flag is an error. LinkML's
`gen-project` writes everything under one directory, so `rp-generate` does the placing.

*Diagrams are Mermaid* (D-8): no rendering service is needed and the docs already draw Mermaid
(`gen-plantuml` would call the public kroki.io service). A diagram that grows past about a dozen
classes is split by module. In AsciiDoc pages, escape `<` as an HTML entity inside a diagram: the
page delivers the source as HTML, and a raw `+<<stereotype>>+` breaks it.

*Extending the generators* means subclassing LinkML internals (`serialize`, the ignored-properties
method), which can change in a minor release. The pin on `linkml` and the checks of <<guarding>>
guard this; each extension gets a golden test.

[#application-schema]
== What the application writes

_What does an application write by hand?_

One file per module and a root schema that imports them, each element with an IRI, a `title` and
a `description` (<<hard-check>>). How to write them, with a `books` module and a root schema that
pass `rp-generate`, is in xref:user-manual/model.adoc[Write the model]; the toy library in
`tests/fixtures/library/` is the full version (a tenant root, a stored file, an access module, an
enum, a workflow).

An application may narrow `Grant.role` to an enum of its own roles by subclassing (`is_a` with
`slot_usage`); the toy library keeps plain strings, matched against its role definitions.

[#generator-package]
== The generator's package

_Where does the generator live, and what does the library know about it?_

The generator is its own top-level package, `rdf_persistence_generation`, beside `rdf_persistence`.
Both ship in the one `rdf-persistence` wheel (`module-name` lists the two), and each has a
`py.typed`. The library is the runtime; the generator is build-time and test-time code that needs
the `generate` extra. `rp-generate` is `rdf_persistence_generation.cli:main`. The package holds the
CLI, the steps, the checks, the extensions and templates, the lint config, the generator's own
model (`model/rp_generation.yaml`, into `generated/`) and its own testkit.

*The generator's testkit.* `rdf_persistence_generation/testkit/` holds `freshness.py` (the pytest
plugin), `conformance.py`, `roundtrip.py` and `strategies.py`. Its `__init__` loads `Conformance`,
`conformance_problems`, `round_trip` and `aggregate` on first use, so `pyshacl` and `hypothesis` are
imported only when needed. The plugin path is `rdf_persistence_generation.testkit.freshness`.

*The old paths.* Version 0.5.0 kept the same four modules in `rdf_persistence/testkit/` as shims;
0.6.0 removed them. `rdf_persistence.testkit` has no `freshness`, `conformance`, `roundtrip` or
`strategies` module and exports none of their names; only `assert_isomorphic` stays, in
`rdf_persistence.testkit.graphs`.

*Toolkit schemas.* The library's `is_toolkit_schema`, `apply_defaults` and `generation_view` take a
`roots` argument, the folders that count as the toolkit's. It defaults to the library's own folder.
The generator passes `TOOLKIT_ROOTS` (its own folder and the library's) at every call site, so the
library never has to name the generator. Manifests record a library file as
`rdf_persistence/...` and a generator file as `rdf_persistence_generation/...`.

*Contracts.* Three import-linter contracts keep the two packages apart (`make check-architecture`):

* `library-never-imports-the-generator`: `rdf_persistence` does not import
  `rdf_persistence_generation`, with no exception (`ignore_imports` is empty).
* `runtime-without-extras`: the runtime layers import neither the testkit, nor
  `rdf_persistence_generation`, nor `pytest`, `testcontainers` or `linkml`.
* `works-without-the-generate-extra`: the modules that must run without the `generate` extra
  (`cli`, `config`, `manifest`, `pipeline`, `exceptions`, `problems`, `generated` and `testkit` of
  the generator, `rdf_persistence.testkit`, `rdf_persistence.schema.services.schema` and
  `schema_structure`) do not import `linkml` (only `linkml_runtime`). The one `cli` to `steps` edge
  is excepted: it loads the steps only when it generates.

[#toolchain]
== The toolchain

_What does `rp-generate` run, in which order?_

One command, run from the application's `make generate-models`, regenerates every entry of the
`[tool.rp-generate]` table:

[source,toml]
----
# pyproject.toml
[tool.rp-generate]
schema = "models/library.yaml"
package = "library.domain.generated"
typescript = "web/src/domain/generated"
diagrams = "docs/images/model"
----

[source,shell]
----
rp-generate                    # every entry of ./pyproject.toml
rp-generate --project other/pyproject.toml
rp-generate --check            # write nothing; exit 1 if anything is stale or edited (<<guarding>>)
----

`rp-generate` is a thin Python wrapper around LinkML's generator API, not a shell script, because
split generation (importing the metamodel's classes from the toolkit instead of regenerating them) is
available only through the Python API. It is always installed; without the `generate` extra it exits
2 and says so. Its steps are listed in order in `rdf_persistence_generation/steps.py`.

....

|Step |What it does |Fails when

Each step writes to a temporary file and moves it into place only on success, so a failed run leaves
the previous output intact. The package also receives a copy of the schema: the mapper reads it at run
time, so code and mapping always come from the same schema version.

*Modules.* An application splits its schema into one file per module: a *domain module* per
aggregate (its root and the classes it owns) and *technical modules* for concerns such as paging or
API envelopes, written as mixins. A root schema imports the modules. Domain modules never import
technical ones (step 2). The metamodel's mixins (`AggregateRoot`, `StoredFile`) are usable in domain
modules: they say how a class is persisted, not what it means.

A technical module's class may hold another class, such as a page of terms, with a plain slot: a
technical class is never stored, so it needs neither `owned: true` nor `Described`, and the root, owned
and reference rules do not apply to the classes of a module annotated `module_kind: technical`. Two
rules guard the boundary the other way: a technical module declares no root (`AggregateRoot` is
refused there), and a module that is not annotated technical may not hold a technical class.

[source,yaml]
----
classes:
  Terms:
    attributes:
      items:
        range: Term
        multivalued: true
        inlined_as_list: true
        annotations:
          owned: true
----

*Not generated:* mappers, repositories, routes and API clients (O-1); the client calls the API with
the generated types.

[#run-time]
== At run time

_What does the run time read from the schema?_

The generated classes carry the fields; the mapping to RDF is not generated. The `Mapper` reads
the schema at run time, as a `SchemaView` (`kit.view` in a service), beside the generated classes
it is given. How a domain service stores and reads aggregates with it is in
xref:user-manual/store-and-read.adoc[Store and read aggregates]; how a commit is guarded, in
xref:architecture/commits.adoc[How commits and conflicts work]. What the mapper takes from the
schema:

* *Mapping* (implemented: `rdf_persistence/persistence/services/mapper.py`, `Mapper`): class and slot IRIs come
  from the schema (`class_uri`, `slot_uri`, or the default prefix); owned parts live in the root's
  graph, by IRI when their class includes `Described` and as skolemised blank nodes otherwise
  (PD-6, PD-8a); references to other aggregates are IRIs; multi-valued slots are sets, so order is
  not kept (model an order slot when order matters). `internal` slots are written; the tracking
  slots are not, since the session writes them about the graph IRI.

* *Kinds*: the mapper reads the class the caller asks for; it does not use `designates_type`. An owned
  part is read as its slot's range class, so a subclass in an owned slot comes back as its parent (a
  known limit of `rdf_persistence/persistence/services/mapper.py`, lifted when a schema owns a class hierarchy).

[#guarding]
== Guarding the generated code

_How is generated code kept fresh and correct?_

The rule of xref:architecture/open-decisions.adoc[D-13] comes from
https://meaningfy.atlassian.net/wiki/spaces/MR/pages/2107342856[the model-driven development runbook]:
generated models are not hand-written and not modified; a change starts in the model; generation
runs at build and test time; a model change makes the unit tests fail until it is reviewed.

=== Freshness: the manifest and `rp-generate --check`

Every `[tool.rp-generate]` entry writes a manifest, `rp-manifest.json`, in its `python` folder (model:
`GenerationManifest`). It records the `linkml` version and the path and SHA-256 of every input and
output, sorted by path, with paths relative to the `pyproject.toml`.

[cols="1,4",options="header"]
|===
|Recorded |Files
|Inputs |the schema's import closure (metamodel files as `rdf_persistence/<path>`, so the manifest does not depend on where the package is installed), the template directories, every module under `rdf_persistence_generation/` except `generated/` and `testkit/` (the testkit never shapes the output), and every `rdf_persistence/schema/services/schema*.py` module (they decide how a schema is read)
|Outputs |every file the run wrote, in every target folder, except the manifest. A run deletes only the files its previous manifest lists, never a whole folder.
|===

`rp-generate --check` writes nothing: it runs lint, the checks and the lock check, then recomputes
the hashes. A changed input or a different `linkml` version means *stale*; a changed output means
*edited by hand*. Either exits 1, naming the files and the command that fixes them. Without the
`generate` extra, only the hashes are compared.

`rp-generate` does not trust its own inputs: manifest paths must be relative POSIX paths without
`..` and hashes 64 hex digits; a run removes a listed file only if it lies under the project and
still has its recorded hash; configured folders are relative, without `..`; the package is a dotted
identifier; every staged file must stay inside the staging folder.

[cols="2,3",options="header"]
|===
|Where |What runs
|`make check-quality` (before every PR, and in CI) |the full `--check`
|every pytest session |the manifest comparison, by the plugin `rdf_persistence_generation.testkit.freshness` in `pytest_sessionstart`; it stops the run on anything stale or edited. A consumer enables it with `pytest_plugins = ["rdf_persistence_generation.testkit.freshness"]` (the old path, `rdf_persistence.testkit.freshness`, is a shim that warns); the ini option `rp_generate_projects` lists the `pyproject.toml` files to read (default: the rootdir's).
|pre-commit hook `rp-generate-check` |the check, on commits touching the generator's inputs (a model, any module, template or lint config of the generation package except its `testkit/` and `generated/` folders, which are no inputs, and the toy library) or a `generated/` folder (a hand edit of generated code); not every manifest input: the library's `schema/services/schema.py` and `schema_structure.py` are inputs the hook does not match
|`make check-generated` (CI) |a regeneration from scratch and a diff, which catches a generator that is not deterministic
|===

Generation is part of the build: `make generate` regenerates every entry, and `make build` runs it
first.

=== Correctness of the generated code

. *Schema gates first*: lint, then the hard and boundary checks; nothing is generated from a schema
  that fails them.
. *Golden tests per extension*: RDF output compared by graph isomorphism, other output as exact
  text, and the set of files compared exactly.
. *Classes and shapes agree*: for every row of `tests/fixtures/conformance/cases.yaml`
  (`ConstraintCase`: a constraint kind, a class, valid and invalid instances), the generated class and
  the generated shape both accept the valid instances and refuse the invalid ones. The kinds of v1
  are `required`, `cardinality`, `range_type`, `range_enum`, `pattern`, `value_bounds`, `identifier`,
  `closed`, `exactly_one_of`, `any_of` and `unique_keys`; the test fails, naming the kind, when a
  schema uses a kind with no row. A consumer runs it on its own schema with
  `conformance_problems(schema, cases)` (from `rdf_persistence_generation.testkit`), which returns the
  problems found, empty when all pass.
. *Round trips*: an instance drawn by Hypothesis from the schema (the strategy is `aggregate` in
  `rdf_persistence_generation.testkit`) goes to JSON, is expanded with the generated context to RDF,
  then framed and compacted back; the objects compare equal on their public projection (internal
  slots never cross the context) and the RDF graphs are isomorphic. Run on the toy library's
  aggregates and the metamodel's `TenantAccess`.
. *Model shape*: every generated class's pydantic fields match the schema's induced slots (name,
  required, multivalued, range), which catches stale or edited code even without the manifest.
. *Python and the API document agree on required fields*: `model_schema_diff(components, models)`
  (from `rdf_persistence.testkit`) compares each generated class's required fields with the
  `required` list of its JSON Schema in `openapi-components.json`, and returns one line per
  difference, empty when they agree. It is what caught a root's description being required in
  Python only (#59) and an unlabelled class's label being required in the JSON Schema only.
. *A model change fails the tests until acknowledged*: `tests/fixtures/model-shape.yaml` holds the
  last reviewed shape of every class (`ClassShape` rows). Any model change fails the test until
  `make refresh-snapshot` rewrites the file and its diff is reviewed in the PR. The public
  surface's snapshot, `tests/fixtures/public-surface.json`, is a baseline of the thematic move and
  has its own target, `make refresh-surface`.
. *Generated code compiles*: every generated module imports and passes mypy with the
  `mypy-generated.ini` profile (the main run excludes generated folders); the TypeScript output
  passes `tsc --noEmit --strict` in CI.

=== Guards against hand-written models

Both guards are `testkit.assert_models_generated(package, *, roots, allow=(), exempt=(), layers=...)`
(in `rdf_persistence.testkit`), so applications get them too.

* *Model guard*: parses every module of `domain`, `services` and `entrypoints`, skipping paths with a
  `generated` segment, and fails, naming the class, on a class deriving from `pydantic.BaseModel`,
  `RpModel`, `enum.Enum`, `enum.StrEnum`, `enum.IntEnum`, `typing.TypedDict` or `typing.NamedTuple`,
  or decorated with `dataclasses.dataclass`. Import aliases are resolved. The only default exception
  is `RpModel` in `rdf_persistence/core/domain/base.py`; an application passes its own with `allow=`, as
  `"<path>:<ClassName>"`. This repository also scans `rdf_persistence_generation` and `testkit`, with the
  foreign-object types of <<extensions>> in its allow-list (`tests/unit/testkit/test_model_guard.py`);
  a subclass of a LinkML generator is not flagged, so it needs no entry.
* *File guard*: fails on `*.shacl.ttl`, `*shapes*.ttl`, `context.jsonld`, `*.context.jsonld`, `*.frame.jsonld`,
  `*.schema.json`, `openapi*.json`, `openapi*.yaml` and `*.ts` (except `*.test.ts` and `*.spec.ts`)
  outside a folder named `generated`. This repository scans `rdf_persistence/` and `tests/`, with
  `tests/fixtures/` exempt (`exempt=`).

=== Versions and commits

* `linkml` and `linkml-runtime` are pinned together (mismatched versions fail at import).
  Bumping them is a deliberate change: bump, regenerate, review the diff, accept.
* The schema and the regenerated code are committed together.
* Generated code sits in the domain layer and imports nothing from services, adapters or entrypoints.

[#adoption]
== How an application adopts it

An application models its domain on the metamodel, generates with `rp-generate` (and checks
freshness in CI), writes its use-case services on the generated classes, and serves the schema
with `install_service`. The steps, with examples that run, are the
xref:user-manual/index.adoc[user manual]; the shortest walk is
xref:tutorials/getting-started.adoc[Getting started].
