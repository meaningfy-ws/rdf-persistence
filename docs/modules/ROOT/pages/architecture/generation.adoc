= Model to code: the generation workflow
:description: How an application's own LinkML model becomes typed, persistable code with rdf-persistence.

Status: *accepted*; build time *implemented* (2026-11-05); run time *implemented* (2026-11-06). Settles open decision O-1 of
xref:architecture/index.adoc[architecture v1] with its smallest option, revised in <<revision>>
(developer, 2026-11-05: decisions D-2 and D-6 to D-9 of
xref:architecture/open-decisions.adoc[the decisions of 2026-11-05]). The metamodel, `rp-generate`
and the guards are implemented (stage 1 of the change `toolkit-v1-foundation`). The run-time parts
(<<run-time>>), first tried in a throwaway spike (LinkML 1.12.1, Fuseki 5.1.0), are implemented
since stage 2: the mapper, the session and the unit of work. To work on the toolchain itself, see
xref:develop/index.adoc[Working on the toolkit].

An application using rdf-persistence writes its domain once, in LinkML. A deterministic, build-time
toolchain turns it into domain classes and shapes; at run time the toolkit reads the same schema to
map objects to RDF. No generated file is edited by hand, and no LLM sits in the generation path.

LinkML is the single source of specification
(xref:architecture/open-decisions.adoc[D-13]): every artefact that restates the model is generated,
by a stock generator or a toolkit extension (<<extensions>>), and nothing that restates it is
written or edited by hand (<<guarding>>).

The running example is a toy library application: each library is a tenant holding `Book`
aggregates, each book with owned chapters and a reference to a scan file; librarians hold the tenant
role `librarian`.

[#decision]
== The decision (O-1)

_Which code is generated, and which is written once in the toolkit?_

*Generated domain classes, runtime mapper.* Only LinkML's standard generators run, through the
toolkit's templates. Since 2026-11-05 (D-2) the classes and the mapper serve *domain services* only;
the API path needs neither (xref:architecture/api.adoc[API]). The mapper, the repositories and the routes are not generated: they are generic
code that reads the schema at run time. A per-aggregate generator (repositories, routes) is built only
if hand-written routes start repeating themselves across applications.

Rejected for v1: generating mappers, repositories and routes per aggregate (the background study's
"approach B"), because it means owning a code generator before a second application exists; and a
fully generic service without typed classes ("approach C"), because domain logic then has no types.

[#metamodel]
== The metamodel

_What does the toolkit give a schema to build on?_

A small LinkML schema shipped inside the package (`rdf_persistence/model/`, split into modules
since the <<revision,revision of 2026-11-05>>; namespace `https://meaningfy.ws/ns/rdf-persistence#`). Its classes are generated once, into the toolkit's own
package; an application's generated code imports them rather than regenerating them.

[cols="2,5",options="header"]
|===
|Element |Meaning
|`AggregateRoot` (mixin) |Instances are aggregate roots: each is one named graph, whose IRI `graph_iri(root)` is derived from the root's IRI (for example `<root>/graph`; background DEC-29), versioned, loaded and saved as a whole.
|`owned` (slot annotation)
|The slot's values are part of this aggregate and live in its graph (a commit replaces the whole
graph). A part whose class includes `Described` has an IRI, by default `{root_iri}/parts/{uuid4}`
(the IRI policy's part template), minted by the toolkit when it has none and kept across commits; a
part without an identifier slot (a grant, a prohibition) is a blank node, skolemised on write (PD-6,
PD-8a). Any other slot whose range is a class refers to another aggregate root, by IRI.
|`database` (class annotation) |`tenant` (default) or `system`: which database the aggregate lives in.
|`graph: meta` (class annotation) |The tenant's root object lives in the tenant database's designated `meta` graph instead of a graph of its own.
|`internal` (slot annotation) |Only the service sets the slot (e.g. file keys, a tenant's database name): it never appears in the API contract or a response, a request body that sets it is refused (422), the tenant-create body included, and a replace keeps its stored value on the root and on the parts that persist, matched by IRI. The mapper writes it, so a domain service can set it.
|`rp_path` (class annotation) |Required on every aggregate root: its path segment in the API and in its IRIs (`{tenant}/{rp_path}/{uuid}`).
|`rp_unlabelled` (class annotation) |An owned value class whose instances need no label of their own.
|`Principal` |A reference to a user account in the identity provider, by IRI only.
|`StoredFile` (mixin) |The current content of a kept file: `file_name`, `media_type`, `byte_size`, `sha256`, `uploaded`, `uploaded_by`, `file_key` (internal).
|`loaded_graph` (slot) |A graph whose lifecycle belongs to the aggregate (e.g. the triples of a loaded RDF file).
|`TenantAccess`, `Grant`, `Prohibition` |The tenancy records of the system database (N-11): label, state (`TenantState`: `active`, `deleting`), database name, owned grants and prohibitions (ODRL). `TenantAccess` is a `Policy`; an application subclasses it once, in an access module. Role names come from the consumer's role definitions; an application may narrow `role` to an enum by subclassing (`is_a` with `slot_usage`), but need not.
|`RoleDefinition` |One entry of the application's role definitions: a `role`, the `level` it applies at (`RoleLevel`: `system`, `tenant`, `aggregate`) and the `actions` it permits. Supplied as a YAML file, read by `load_role_definitions`, never stored.
|`RegistryEntry` |An entry of a tenant's `registry` graph: the graph's IRI, its kind (`aggregate`, `loaded_graph`) and the aggregate that owns it. Written by the session, never by the application.
|`version` (slot) |The version token of every aggregate, stated about its graph IRI (not the root), written by the session; not part of any domain class.
|`module_kind` (schema annotation) |`domain`, `technical` or `access`: what a schema module holds; the boundary check uses it (<<toolchain>>).
|`bookkeeping` (slot annotation) |The session writes the slot about a graph (`version`, `created`, `modified`, `creator`, `contributor`); closed shapes ignore it.
|===

The annotation names are the generated enum `RpAnnotation`, and their values the enums
`ModuleKind`, `DatabaseKind` and `GraphKind`: a value outside them fails the hard check, so no code
compares free strings. The rules that read a schema's aggregate structure (roots, the tenant root,
owned, internal and bookkeeping slots, PD-11's defaults, the presence alternatives and keyed slots
of a class) live once, in `rdf_persistence/services/schema_structure.py`, beside `load_schema` in
`schema.py`; the checks, the extensions, the testkit and the mapper all use them.

Slots of the metamodel (IRIs in the `rp:` namespace unless shown):

[cols="2,2,3",options="header"]
|===
|Slot |IRI |Range, cardinality
|`id` |— (identifier) |uri, required on every aggregate root
|`label` |`skos:prefLabel` |string, from `Described`; required on `TenantAccess` (1–200 characters) and on described roots
|`state` |`rp:state` |`TenantState`, required
|`database_name` |`rp:databaseName` |string, required
|`grants` |`rp:grant` |`Grant`, multivalued, owned (blank nodes, skolemised to `{graph_iri}/.well-known/genid/{uuid4}` on write; one per assignee, target and role-or-action by `unique_keys`)
|`assignee` |`odrl:assignee` |`Principal` (IRI), required (a grant is an `odrl:Permission`, D-5)
|`target` |`odrl:target` |uri: the tenant IRI, or an aggregate's graph IRI; required
|`role` |`rp:role` |string, matched against the consumer's role definitions; an application may narrow it to an enum by `slot_usage`; exactly one of `role` and `action`
|`action` |`odrl:action` |`Action` (`read`, `modify`, `delete`, `administer`; fixed by the toolkit): for a direct permission, or the action a prohibition forbids (required there)
|`prohibitions` |`rp:prohibition` |`Prohibition`, multivalued, owned (blank nodes, skolemised like `grants`)
|`level` |`rp:level` |`RoleLevel`, required, on `RoleDefinition`
|`actions` |`rp:permits` |`Action`, multivalued, required (and not empty), on `RoleDefinition`
|`file_name`, `media_type`, `byte_size`, `sha256`, `uploaded`, `uploaded_by`, `file_key` |`rp:fileName`, `rp:mediaType`, `rp:byteSize`, `rp:sha256`, `dcterms:dateSubmitted`, `rp:uploadedBy`, `rp:fileKey` |as in the consumer model's slot table; `file_key` internal
|`loaded_graph` |`rp:loadedGraph` |uri
|`version` |`rp:version` |string, written by the session only
|===

Annotations are resolved over the *induced* class: a class inherits `AggregateRoot`, `database` and
`graph` from its ancestors and mixins, so an abstract root's annotations reach its subclasses. LinkML
itself does not inherit class annotations; the boundary check and the mapper do.

[#revision]
== Revision of 2026-11-05 (accepted)

The developer asked for four things on top of the metamodel above: a default set of annotation
vocabularies everywhere (SKOS, DCTerms, PROV-O, and ODRL for access), models that always carry IRIs,
labels and definitions (a hard check), the access model in a module of its own, and every generated
artefact in the package that uses it.

[#annotations]
=== Annotations: two layers that are easy to confuse

[cols="1,2,3",options="header"]
|===
|Layer |About |How
|*Schema metadata* |the model's own classes and slots ("what is a Book?") |LinkML's own fields already map to the standard vocabularies: `title` → `dcterms:title`, `description` → `skos:definition`, `aliases` → `skos:altLabel`, `comments` → `skos:note`, `exact_mappings` → `skos:exactMatch`, `source` → `dcterms:source`, `contributors` → `dcterms:contributor`. The OWL and SHACL generators emit them. Nothing to add: *require* them (hard check below).
|*Instance data* |the data ("what is this book called, who wrote it into the store, when?") |Not covered by LinkML: the toolkit ships mixins with ordinary slots.
|===

Instance mixins:

[cols="1,3,2",options="header"]
|===
|Mixin |Slots (IRIs) |Written by
|`Described` |`id` (required), `label` (`skos:prefLabel`, required), `description` (`dcterms:description`, required on roots), `alt_label` (`skos:altLabel`), `definition` (`skos:definition`, for concept-like classes), `exact_match` (`skos:exactMatch`) |the application
|`Tracked` |`created`, `modified` (`dcterms:`), `creator`, `contributor` (`dcterms:`, range `Principal`) |the session, *about the graph IRI* (DEC-29: statements about the graph are kept apart from the entity)
|`Provenanced` |`was_derived_from`, `was_generated_by` (range `Activity`), `was_attributed_to` (range `prov:Agent`), `generated_at_time` (`prov:`) |the application, about the entity
|===

`Principal` is a `prov:Agent` and `AggregateRoot` a `prov:Entity`, so the provenance of a write
(who, when, which graph) is PROV-O without extra classes.

[#hard-check]
=== The hard check: IRIs, labels and definitions

`linkml-lint` cannot load extra rules, so the check is `linkml-lint` with the rule sets of
`rdf_persistence/generation/lint.yaml` raised to errors (`recommended`, `standard_naming`,
`canonical_prefixes`) plus `rdf_persistence/generation/checks/hard.py` over `SchemaView`. Its rules
are the generated enum `HardRule`. It fails generation when:

. an element has no IRI: no `default_prefix` declared in `prefixes`, and no explicit `class_uri` or
  `slot_uri`;
. a class, slot, enum or permissible value has no `title` or no `description`;
. a permissible value has no `meaning` (an IRI);
. an aggregate root or owned class does not include `Described`, so instances without IRI, label and
  description are refused by the generated classes and shapes; an owned value class without a label
  of its own (a chapter's number) opts out explicitly with `rp_unlabelled: true`;
. an aggregate root has no `rp_path`, or an `rp_path` that is not a URL segment;
. an annotation value is not one of its allowed values;
. a `unique_keys` name is not an identifier (generated validators carry it).

The checks cover the schema's own modules only; the metamodel's are exempt. The `module_kind`
import rule belongs to the boundary check (<<toolchain>>, step 2).

[#extensions]
=== Generated artefacts, extensions and where they go

Each gap in a stock LinkML generator is closed by an extension in `rdf_persistence/generation/`: a
subclass or a template, never a patch to generated output. Each extension has a row here and a
golden test; a test fails if an extension module has neither. For the toy schema the golden is the
committed generated tree itself (a test renders afresh and compares: Turtle by meaning, everything
else by exact text, the file set exactly), so `make generate` is what refreshes it. A schema that is
not the toy keeps a golden folder, rewritten by `make refresh-golden`. Each extension exposes one
`render(schema_path)` that returns the files it makes; `steps.py` composes the steps from them.

[cols="3,2,2,4,2,1",options="header"]
|===
|Module |Artefact |Generator |Extension needed |Placed in (default) |Effort
|`rdf_persistence/generation/extensions/pydantic_split.py` |Python classes |`gen-pydantic`, split mode |templates (`rdf_persistence/generation/templates/pydantic/`): the metamodel's classes imported from the toolkit, never regenerated; enum members named after the value keys; an `internal` slot marked `rp_internal` for the API layer (still dumped, since the mapper persists it); a `secret` slot kept out of the repr |the backend package, `<pkg>/domain/generated/` |S
|`rdf_persistence/generation/extensions/pydantic_validators.py` |Model validators for declared rules |`gen-pydantic`, template |the stock generator enforces neither `exactly_one_of` nor `unique_keys`: `exactly_one_of` and `any_of` become a model validator on the declaring class; `unique_keys` becomes a model validator on every class with a multivalued slot whose range declares them, refusing two items with equal key values (an absent value counts, and two absent values are equal) |with the Python classes |M
|`rdf_persistence/generation/extensions/typescript.py` |TypeScript types |`gen-typescript` |a subclass with our own template (the stock one is fixed and has no split mode): one file per module and an index; enums as string-literal unions, dates as ISO strings, owned parts nested and any other class an IRI string, `internal` slots left out |the frontend package, `src/domain/generated/` |M
|`rdf_persistence/generation/extensions/shacl.py` |SHACL shapes |`gen-shacl` |a subclass: the `bookkeeping` predicates added to the ignored list of closed shapes; a shape per class, named by its own IRI (classes may share a `class_uri`); a reference to another aggregate checked as an IRI only, so a graph validates on its own; an `internal` slot optional; a `pattern` matched against the whole value, as the classes do |the backend package |S
|`rdf_persistence/generation/extensions/shacl_constraints.py` |Shape constraints for declared rules |`gen-shacl` |the stock generator translates neither rule: `exactly_one_of` becomes `sh:xone`, `any_of` becomes `sh:or`, `unique_keys` becomes a SPARQL constraint on the owning class (absent values treated as in the validators) |with the shapes |M
|`rdf_persistence/generation/extensions/jsonld_context.py` |JSON-LD context and frames |`gen-jsonld-context` |`id`/`type` aliases, `internal` slots left out, integers and booleans kept as native JSON, a `uri` read as an IRI and an enum as its meaning IRI (as the shapes expect), one frame per aggregate type |the backend package; copied to the frontend when needed |S
|`rdf_persistence/generation/extensions/mermaid.py` |Diagrams, one per module |`gen-mermaid-class-diagram` (D-8) |a template marking aggregate roots and owned parts, and keeping each diagram small (one module, its links to other modules shown as names only) |the docs, next to the model pages |S
|`rdf_persistence/generation/components.py` |OpenAPI component schemas |`gen-json-schema` |not under `extensions/`, since it adds no subclass or template: it trims the stock output to what the API shows (bookkeeping and `internal` slots dropped, the identifier read-only, since the service assigns it) and points its references into `#/components/schemas` (PD-24). It runs at generation time because the generators are an extra (PD-2): the running service only reads the file |`openapi-components.json`, beside the context |S
|`rdf_persistence/generation/checks/` |Boundary, hard and rules checks |`linkml-lint` + `rp-generate` |not a generator extension: three checks over `SchemaView` (`boundary.py`, `hard.py`, `rules.py`) |— |S
|===

*Rules the generated code would silently ignore fail instead* (`checks/rules.py`). On a class only
`exactly_one_of`, `any_of` and `unique_keys` are enforced; LinkML `rules` (pre- and postconditions),
`all_of` and `none_of` make `rp-generate` exit 1, naming the class. On a slot, only `any_of` as a
union of ranges passes, since both the classes (`Union[...]`) and the shapes (`sh:or`) render it.

*The toolkit's own data types are generated too.* Each is its own `[[tool.rp-generate]]` entry, and
`rp.yaml` imports neither, so an application's model does not carry them. Like the metamodel, they
are exempt from the hard check. They are schemas, not extensions, so they have no row above.
Hand-written types remain only where a field holds a foreign run-time object LinkML cannot express
(a `SchemaView`, a callable, an rdflib graph), or where the type subclasses a LinkML generator; each
is named in the model guard's allow-list (<<guarding>>).

[cols="2,3,2",options="header"]
|===
|Schema |Classes |Generated into
|`rdf_persistence/model/service/rp_service.yaml` |`ServiceSettings` (the settings of `install_service`), `VerifiedCaller` (what the token verifier returns), and the toolkit's request and response bodies: `TenantCreate`, `TenantSummary`, `LabelUpdate`, `GrantSet`, `Page`, `Problem` |`rdf_persistence/domain/generated/service/`
|`rdf_persistence/generation/model/rp_generation.yaml` |The data of the toolchain and the testkit: `GenerationTarget`, `GenerationManifest`, `ConstraintCase`, `ClassShape` (see <<guarding>>); `GeneratedFile`, `CheckProblem`, `CliFlag`, the rule, frame, TypeScript and Mermaid view-models, `ContainerMarker` and the guard's `Violation` |`rdf_persistence/generation/generated/`
|===

*Placement is declared, not guessed*: the application's `pyproject.toml` gets a
`[tool.rp-generate]` table (or an array of tables, one per schema) with the keys `schema`,
`package`, `python` (default: the package's path), `typescript`, `diagrams`, `regenerate-command` (the command a failed freshness check tells you to run; default `rp-generate`) and `openapi` (default
`true`; `false` skips step 5b for a schema no service serves, as for the toolkit's metamodel,
generation and wire schemas); paths are relative to the `pyproject.toml`. The flags `--schema`, `--package`, `--python-out`, `--typescript-out` and
`--diagrams-out` override the keys of a single entry; with several entries a flag is an error. LinkML's
`gen-project` writes everything under one directory, so `rp-generate` does the placing.

*Diagrams are Mermaid* (D-8): no rendering service is needed and the docs already draw Mermaid
(`gen-plantuml` would call the public kroki.io service). A diagram that grows past about a dozen
classes is split by module. In AsciiDoc pages, escape `<` as an HTML entity inside a diagram: the
page delivers the source as HTML, and a raw `+<<stereotype>>+` breaks it.

*Extending the generators* means subclassing LinkML internals (`serialize`, the ignored-properties
method), which can change in a minor release. The pin on `linkml` and the checks of <<guarding>>
guard this; each extension gets a golden test.

[#application-schema]
== What the application writes

_What does an application write by hand?_

One file per module and a root schema that imports them. Every element carries an IRI, a `title`
and a `description` (<<hard-check>>). This example passes `rp-generate`; the toy library in
`tests/fixtures/library/` is the full version (a tenant root, a stored file, an access module, an
enum).

[source,yaml]
----
# models/books.yaml — one domain module of the application's schema (toy example)
id: https://example.org/ns/library/books
name: books
title: Books module
description: Books and their chapters; the book is the aggregate root.
prefixes:
  lib: https://example.org/ns/library#
  linkml: https://w3id.org/linkml/
  dcterms: http://purl.org/dc/terms/
default_prefix: lib
default_range: string
imports:
  - linkml:types
  - rdf_persistence/model/rp_core           # resolved through the toolkit's import map
  - rdf_persistence/model/rp_annotations
annotations:
  module_kind: domain
classes:
  Book:
    title: Book
    description: A book held by a library; an aggregate root that owns its chapters.
    mixins: [AggregateRoot, Described, Tracked]
    slots: [author, chapters]
    annotations:
      rp_path: books                         # its path segment in the API and in its IRIs
  Chapter:
    title: Chapter
    description: A chapter of a book; part of the book's aggregate.
    mixins: [Described]
    slots: [number]
    annotations:
      rp_unlabelled: true                    # known by its number, needs no label
slots:
  author:
    title: Author
    description: The author's name.
    slot_uri: dcterms:creator
  number:
    title: Chapter number
    description: The position of a chapter in its book.
    range: integer
  chapters:
    title: Chapters
    description: The book's chapters; they live in the book's graph.
    range: Chapter
    multivalued: true
    inlined_as_list: true
    annotations:
      owned: true
----

[source,yaml]
----
# models/library.yaml — the root schema
id: https://example.org/ns/library
name: library
title: Library
description: The root schema of a toy library application.
prefixes:
  lib: https://example.org/ns/library#
  linkml: https://w3id.org/linkml/
default_prefix: lib
default_range: string
imports:
  - linkml:types
  - books
----

An application may narrow `Grant.role` to an enum of its own roles by subclassing (`is_a` with
`slot_usage`); the toy library keeps plain strings, matched against its role definitions.

[#toolchain]
== The toolchain

_What does `rp-generate` run, in which order?_

One command, run from the application's `make generate-models`, regenerates every entry of the
`[tool.rp-generate]` table:

[source,toml]
----
# pyproject.toml
[tool.rp-generate]
schema = "models/library.yaml"
package = "library.domain.generated"
typescript = "web/src/domain/generated"
diagrams = "docs/images/model"
----

[source,shell]
----
rp-generate                    # every entry of ./pyproject.toml
rp-generate --project other/pyproject.toml
rp-generate --check            # write nothing; exit 1 if anything is stale or edited (<<guarding>>)
----

`rp-generate` is a thin Python wrapper around LinkML's generator API, not a shell script, because
split generation (importing the metamodel's classes from the toolkit instead of regenerating them) is
available only through the Python API. It is always installed; without the `generate` extra it exits
2 and says so. Its steps are listed in order in `rdf_persistence/generation/steps.py`.

[mermaid]
....
flowchart TB
    S["schema + metamodel"] --> L["1 lint"] --> B["2 boundary, hard and rules checks"]
    B --> P["3 Python"]
    B --> H["4 shapes"]
    B --> C["5 context"]
    B --> O["5b OpenAPI components"]
    B --> T["6 TypeScript"]
    B --> D["7 diagrams"]
....

[cols="1,4,3",options="header"]
|===
|Step |What it does |Fails when
|1 Lint |`linkml-lint` with `rdf_persistence/generation/lint.yaml` (<<hard-check>>), on the schema and each of its own modules; the metamodel is opened through the toolkit's import map |the schema has lint errors
|2 Checks |Over LinkML's `SchemaView`. *Boundary* (`BoundaryRule`): roots are the classes whose induced ancestors include `AggregateRoot`; every other non-mixin class is reachable only through `owned` slots (it may be owned by several root classes, e.g. a reusable value class); a non-owned slot whose range is a class must point to a root or to a reference class (`Principal`, `Activity`). *Hard*: <<hard-check>>. *Rules*: <<extensions>> |a class is owned by nothing, or reached through a non-owned slot without being a root; a module annotated `module_kind: domain` imports one annotated `technical` or `access`; a hard-check rule fails; a schema uses a rule the generated code would ignore
|3 Domain classes |`gen-pydantic` in split mode with the toolkit's template directory: `base_model.py.jinja` makes every class inherit the toolkit's strict base `RpModel` (no extra fields, validation on assignment); metadata off; metamodel classes imported from the top-level `rdf_persistence` in an application's run; model validators for `exactly_one_of`, `any_of` and `unique_keys` |generation fails
|4 Shapes |`gen-shacl` through `RpShaclGenerator`. Shapes are closed (`sh:closed true`), and the version token sits on the graph IRI, not the root, so the domain triples validate on their own |generation fails
|5 JSON-LD context |`gen-jsonld-context`, with `id` and `type` aliased to `@id` and `@type`, and one frame per aggregate type (`<Class>.frame.jsonld`, with `@omitDefault`); served by the service kit (O-2). Known gaps (no `@language` containers, inlined collections keyed by `@index`) need template fixes before a schema uses those features |generation fails
|5b OpenAPI components |`gen-json-schema`, trimmed by `rdf_persistence/generation/components.py` (<<extensions>>), into `openapi-components.json` (skipped when the entry sets `openapi = false`); the service's OpenAPI document (xref:architecture/api.adoc#serving[API]) reads it |generation fails
|6 TypeScript types |`gen-typescript` with the toolkit's template: interfaces only, one file per module and an `index.ts`, into the client package the application names |generation fails
|7 Diagrams |`gen-mermaid-class-diagram`, one `.mmd` file per schema module, each showing one module's classes and their links to other modules |generation fails
|===

Each step writes to a temporary file and moves it into place only on success, so a failed run leaves
the previous output intact. The package also receives a copy of the schema: the mapper reads it at run
time, so code and mapping always come from the same schema version.

*Modules.* An application splits its schema into one file per module: a *domain module* per
aggregate (its root and the classes it owns) and *technical modules* for concerns such as paging or
API envelopes, written as mixins. A root schema imports the modules. Domain modules never import
technical ones (step 2). The metamodel's mixins (`AggregateRoot`, `StoredFile`) are usable in domain
modules: they say how a class is persisted, not what it means.

*Not generated:* mappers, repositories, routes and API clients (O-1); the client calls the API with
the generated types.

[#run-time]
== At run time

_How does a domain service read and commit an aggregate?_

[source,python]
----
from rdf_persistence import Mapper, UnitOfWork, generated_models, open_session

from library.domain.generated import books
from library.domain.generated.books import Book

mapper = Mapper(view, generated_models(books))    # view: the schema's SchemaView (kit.view)
async with open_session(
    store, database=database, tenant_iri=library_iri, principal=principal, clock=clock
) as session:
    work = UnitOfWork(session, mapper)
    book = await work.get(Book, book_iri)         # loads the book's graph, maps it to Book
    book.label = "New title"
    work.add(book)
    await work.commit()                           # one guarded update; Conflict if the version moved
----

The signature is `open_session(store, *, database, tenant_iri, principal, clock)`, where `principal` is a `Principal`; `clock` defaults
to the current UTC time. In a service, `kit.session(tenant, principal)` opens it with the tenant's
database name (xref:howto/adopt.adoc#session[Build an application, step 8]).

* *Mapping* (implemented: `rdf_persistence/services/mapper.py`, `Mapper`): class and slot IRIs come
  from the schema (`class_uri`, `slot_uri`, or the default prefix); owned parts live in the root's
  graph, by IRI when their class includes `Described` and as skolemised blank nodes otherwise
  (PD-6, PD-8a); references to other aggregates are IRIs; multi-valued slots are sets, so order is
  not kept (model an order slot when order matters). `internal` slots are written; the tracking
  slots are not, since the session writes them about the graph IRI.
* *Commit* (implemented: `Session.replace_graph` and `add_graph` in
  `rdf_persistence/services/session.py`, driven by `UnitOfWork.commit`): a replace is one SPARQL
  update request of several `;`-joined operations, each guarded by the old version token, that
  replaces the graph and the root's registry entries and writes a fresh token; Fuseki answers 204
  even when the guard matches nothing, so an `ASK` for the new token tells committed from
  conflict. Each aggregate is committed on its own: a conflict on one leaves those committed
  before it in place.
* *Kinds*: the mapper reads the class the caller asks for; it does not use `designates_type`. An owned
  part is read as its slot's range class, so a subclass in an owned slot comes back as its parent (a
  known limit of `rdf_persistence/services/mapper.py`, lifted when a schema owns a class hierarchy).

[#guarding]
== Guarding the generated code

_How is generated code kept fresh and correct?_

The rule of xref:architecture/open-decisions.adoc[D-13] comes from
https://meaningfy.atlassian.net/wiki/spaces/MR/pages/2107342856[the model-driven development runbook]:
generated models are not hand-written and not modified; a change starts in the model; generation
runs at build and test time; a model change makes the unit tests fail until it is reviewed.

=== Freshness: the manifest and `rp-generate --check`

Every `[tool.rp-generate]` entry writes a manifest, `rp-manifest.json`, in its `python` folder (model:
`GenerationManifest`). It records the `linkml` version and the path and SHA-256 of every input and
output, sorted by path, with paths relative to the `pyproject.toml`.

[cols="1,4",options="header"]
|===
|Recorded |Files
|Inputs |the schema's import closure (metamodel files as `rdf_persistence/<path>`, so the manifest does not depend on where the package is installed), the template directories, every module under `rdf_persistence/generation/` except `generated/`, and every `rdf_persistence/services/schema*.py` module (they decide how a schema is read)
|Outputs |every file the run wrote, in every target folder, except the manifest. A run deletes only the files its previous manifest lists, never a whole folder.
|===

`rp-generate --check` writes nothing: it runs lint and the hard and boundary checks, then recomputes
the hashes. A changed input or a different `linkml` version means *stale*; a changed output means
*edited by hand*. Either exits 1, naming the files and the command that fixes them. Without the
`generate` extra, only the hashes are compared.

`rp-generate` does not trust its own inputs: manifest paths must be relative POSIX paths without
`..` and hashes 64 hex digits; a run removes a listed file only if it lies under the project and
still has its recorded hash; configured folders are relative, without `..`; the package is a dotted
identifier; every staged file must stay inside the staging folder.

[cols="2,3",options="header"]
|===
|Where |What runs
|`make check-quality` (before every PR, and in CI) |the full `--check`
|every pytest session |the manifest comparison, by the plugin `rdf_persistence.testkit.freshness` in `pytest_sessionstart`; it stops the run on anything stale or edited. A consumer enables it with `pytest_plugins = ["rdf_persistence.testkit.freshness"]`; the ini option `rp_generate_projects` lists the `pyproject.toml` files to read (default: the rootdir's).
|pre-commit hook `rp-generate-check` |the check, on commits touching the model, the generation package, the toy library or a `generated/` folder
|`make check-generated` (CI) |a regeneration from scratch and a diff, which catches a generator that is not deterministic
|===

Generation is part of the build: `make generate` regenerates every entry, and `make build` runs it
first.

=== Correctness of the generated code

. *Schema gates first*: lint, then the hard and boundary checks; nothing is generated from a schema
  that fails them.
. *Golden tests per extension*: RDF output compared by graph isomorphism, other output as exact
  text, and the set of files compared exactly.
. *Classes and shapes agree*: for every row of `tests/fixtures/conformance/cases.yaml`
  (`ConstraintCase`: a constraint kind, a class, valid and invalid instances), the generated class and
  the generated shape both accept the valid instances and refuse the invalid ones. The kinds of v1
  are `required`, `cardinality`, `range_type`, `range_enum`, `pattern`, `value_bounds`, `identifier`,
  `closed`, `exactly_one_of`, `any_of` and `unique_keys`; the test fails, naming the kind, when a
  schema uses a kind with no row. A consumer runs it on its own schema with
  `conformance_problems(schema, cases)` (from `rdf_persistence.testkit`), which returns the
  problems found, empty when all pass.
. *Round trips*: an instance drawn by Hypothesis from the schema (the strategy is `aggregate` in
  `rdf_persistence.testkit`) goes to JSON, is expanded with the generated context to RDF,
  then framed and compacted back; the objects compare equal on their public projection (internal
  slots never cross the context) and the RDF graphs are isomorphic. Run on the toy library's
  aggregates and the metamodel's `TenantAccess`.
. *Model shape*: every generated class's pydantic fields match the schema's induced slots (name,
  required, multivalued, range), which catches stale or edited code even without the manifest.
. *A model change fails the tests until acknowledged*: `tests/fixtures/model-shape.yaml` holds the
  last reviewed shape of every class (`ClassShape` rows). Any model change fails the test until
  `make refresh-snapshot` rewrites the file and its diff is reviewed in the PR.
. *Generated code compiles*: every generated module imports and passes mypy with the
  `mypy-generated.ini` profile (the main run excludes generated folders); the TypeScript output
  passes `tsc --noEmit --strict` in CI.

=== Guards against hand-written models

Both guards are `testkit.assert_models_generated(package, *, roots, allow=(), exempt=(), layers=...)`
(in `rdf_persistence.testkit`), so applications get them too.

* *Model guard*: parses every module of `domain`, `services` and `entrypoints`, skipping paths with a
  `generated` segment, and fails, naming the class, on a class deriving from `pydantic.BaseModel`,
  `RpModel`, `enum.Enum`, `enum.StrEnum`, `enum.IntEnum`, `typing.TypedDict` or `typing.NamedTuple`,
  or decorated with `dataclasses.dataclass`. Import aliases are resolved. The only default exception
  is `RpModel` in `rdf_persistence/domain/base.py`; an application passes its own with `allow=`, as
  `"<path>:<ClassName>"`. This repository also scans `generation` and `testkit`, with the
  foreign-object types of <<extensions>> in its allow-list (`tests/unit/generation/test_model_guard.py`);
  a subclass of a LinkML generator is not flagged, so it needs no entry.
* *File guard*: fails on `*.shacl.ttl`, `*shapes*.ttl`, `context.jsonld`, `*.context.jsonld`, `*.frame.jsonld`,
  `*.schema.json`, `openapi*.json`, `openapi*.yaml` and `*.ts` (except `*.test.ts` and `*.spec.ts`)
  outside a folder named `generated`. This repository scans `rdf_persistence/` and `tests/`, with
  `tests/fixtures/` exempt (`exempt=`).

=== Versions and commits

* `linkml` and `linkml-runtime` are pinned together (mismatched versions fail at import).
  Bumping them is a deliberate change: bump, regenerate, review the diff, accept.
* The schema and the regenerated code are committed together.
* Generated code sits in the domain layer and imports nothing from services, adapters or entrypoints.

[#adoption]
== How an application adopts it

_How do I start?_

The steps, with examples that run, are in xref:howto/adopt.adoc[Build an application with
rdf-persistence]. In short:

. Write `models/<app>.yaml` and one file per module, importing the metamodel; mark aggregate roots, owned slots, databases;
  write the application's role definitions (and, optionally, narrow `role` by subclassing `Grant`).
. Add a target that calls `rp-generate` (any name; set it as `regenerate-command` so a failed freshness check names it), and the freshness check to CI.
. Write use-case services against a session (`kit.session` or `open_session`), `UnitOfWork` and the generated classes.
. Serve the schema with `install_service`, and write any extra routes with the `ServiceKit` it returns; publish the OpenAPI contract and the JSON-LD context; use the generated TypeScript types in the client, checked against the contract.
