= rdf-persistence architecture v1
:description: The modest first commitments of the rdf-persistence toolkit.

Status: *draft*, Proposed (2026-11-05); revised the same day by the developer's
xref:architecture/open-decisions.adoc[decisions of 2026-11-05] (Accepted), worked out in
xref:architecture/api.adoc[a lightweight API], xref:architecture/access-control.adoc[access control
and identity] and the xref:architecture/generation.adoc#revision[model-to-code revision]. Every
block marked v1 below is *implemented* (stages 1 to 5 of the change `toolkit-v1-foundation`,
2026-11-06); xref:howto/adopt.adoc[Build an application] shows how a consumer uses them.

This version commits only to what the toolkit's first consumer needs in its first iteration. The
xref:background/soa/index.adoc[background study] is not a commitment: a block is built only when a
need below requires it. Each block is *v1* (built now) or *deferred* (not built until a need forces
it).

== Consumer needs

_What must the toolkit do for its first consumer?_

What the first consumer requires, in generic terms. The consumer's own architecture maps its decisions
and use cases to these ids; this toolkit does not know the consumer.

[cols="1,6",options="header"]
|===
|Id |Need
|N-1 |Store domain objects as RDF, one aggregate per named graph, and read them back as typed objects.
|N-2 |Refuse a change made on stale data with a conflict, never a silent overwrite.
|N-3 |Keep each tenant's data in its own database: create it when the tenant is created, drop it when the tenant is deleted, never read across tenants.
|N-4 |Keep designated graphs in each tenant database: a metadata graph for the tenant's own details and a registry of the other graphs.
|N-5 |Load an RDF file into a named graph of its own, replace it and drop it.
|N-6 |Keep uploaded files byte for byte, per tenant, next to the RDF metadata that describes them.
|N-7 |Authenticate every request with an OpenID Connect access token, and administer accounts through the identity provider.
|N-8 |Allow or refuse each action from the caller's roles, global or per tenant, with the rules supplied by the consumer as data.
|N-9 |Serve all of this over an HTTP API with a published contract, explicit error responses and version-checked writes.
|N-10 |Test all of the above quickly without servers, and against the real store in CI.
|N-11 |Keep a catalogue of tenants with their lifecycle state and the role grants of each user in each tenant, in a system database, so that listing a user's tenants and checking access never open a tenant database.
|===

Ports (rounded) are interfaces owned by the toolkit (`Store`, `FileStore`, `Identity`,
`TokenVerifier`); each names its v1 adapter, chosen by the consumer's composition root. The service
kit reaches the store through the session and tenancy, and the access check reads the system
database directly (one `CONSTRUCT` per request). Graph loading is `Session.load_graph`. The
consumer calls only the public API (<<public-api>>): `install_service` and the `ServiceKit` it
returns (with `kit.collaboration`), `open_session`, `UnitOfWork` and `Mapper`, the ports and the
adapters.

*Collaboration* is the one public face of what a caller may ask of a tenant beyond one aggregate
at a time: who refers to a resource, the members of a collection, comments, and moves through a
workflow. It holds one session and the caller it acts for, and hands the work to three classes
behind it; `Workflows` holds the workflow files and the rule that keeps a state. The session knows
no schema and checks no access, so these classes carry both: each asks the access rules and reads
or writes through the session (the arrows that leave the box: access rules, mapper, session). They are kept out of the session so that the generic routes and the
unit of work, which do not pass through them, stay as they were. *Write guards* are the checks a
session runs on every add and replace (a collection's members, a state that only a transition
changes). The kit builds them once and hands them to every session it opens; the session calls
them through a protocol of its own (`WriteGuard`) and imports none of them. An import contract
(`collaboration-layers` in `.importlinter`) fixes the order: collaboration, then transitions and
write guards, then discussion, reference collections and workflows, then access, then the session.

== Building blocks

_What is built in v1, and what waits for a need?_

Where each block keeps its data, and what every operation does step by step, is in
xref:architecture/data-flows.adoc[Where data lives and what each operation does].

[cols="2,1,6,1",options="header"]
|===
|Block |State |v1 commitment |Needs

|Store port
|v1
|One asynchronous interface, `Store` (`services/store.py`): SPARQL 1.1 query and update, a Graph Store Protocol `PUT` of one named graph (`put_graph`), dataset administration (create, drop, list), and, on the whole dataset, a Graph Store `GET` (`export_quads`: every named graph as N-Quads in one read) and `POST` (`import_quads`: adds N-Quads). There is no Graph Store get or drop of one graph: a graph is read with `CONSTRUCT` and emptied with an update. `ToolkitStore` wraps it for the SPARQL the toolkit writes: a refusal of such text is a fault of the service (500), not the caller's `BadQuery` (400).
|N-1, N-3, N-5

|Fuseki adapter
|v1
|`FusekiStore`: one Fuseki dataset (TDB2) per database, administered through the Fuseki administration API; maps Fuseki's answers (`409` exists, `404` or `405` missing, `400` refused text, `5xx` unavailable) to the port's errors. The store conformance suite checks the port's behaviour, including `DatabaseGone` for a query, an update or a put on a dropped dataset; no case checks what a dropped dataset leaves on disk.
|N-3

|Mapper
|v1
|Domain object to triples and back, IRIs taken from the LinkML schema at run time (implemented, task
2.5: `rdf_persistence/services/mapper.py`). Owned parts live in the root's graph: by an IRI minted
under the root's (by default `{root_iri}/parts/{uuid4}`, per the IRI policy) when their class
includes `Described`, otherwise as blank nodes skolemised on write; references to other aggregates
are IRIs; multi-valued slots are sets. The mapper reads the class the caller asks for (it does not
use `designates_type`), and an owned part as its slot's range class, so a subclass in an owned slot
comes back as its parent: a known limit, lifted when a schema owns a class hierarchy.
|N-1

|Session and unit of work
|v1
|`Session` (`services/session.py`) reads and commits whole graphs of one tenant database for one principal; `UnitOfWork(session, mapper)` (`services/mapper.py`) gives object-level `get`, `add`, `remove` and `commit`, all its roots in one commit. There are no repositories beyond these two. The aggregate's graph IRI is `graph_iri(root)`, `<root>/graph` (background DEC-29), so statements about the graph and about the entity never share a subject. Every write goes through a `Transaction` (`Session.transaction()`; `add_graph`, `replace_graph` and `remove` of the session are one-change transactions), which sends *one* SPARQL update request, built by `request_text`, so a store applies all its changes or none. The request has three parts, joined with `;`: a guard operation that writes a commit marker only if every change's guard holds (a replace or a remove: the graph is at the *version token* read; an add: the graph is empty; a claimed key value: no other aggregate of the tenant holds it), the changes' operations, each matching only while the marker is there (a replace empties loaded graphs no longer listed, the root's registry entries and the graph, writes the new triples, a fresh version token and the tracking statements about the graph IRI, and drops the old token last), and a release that deletes the marker. An `ASK` for the new tokens then tells committed from conflict (Fuseki does not fail an update whose `WHERE` matched nothing), and a diagnosis names the roots that conflicted. A session enforces the keys it is given (`keys`; the tenancy passes those of the schema) and `key_duplicates()` reports the duplicates stored. The marker guard and the diagnosis are in xref:architecture/data-flows.adoc#commit[Committing several aggregates at once]. The session also loads and pages (`page`, one `CONSTRUCT` per listing page).
|N-1, N-2

|Tenancy
|v1
|`Tenancy` (`services/tenancy.py`). A system database (one per deployment) holding one *tenant access record* per tenant (`{tenant}/access`): label, database name, state (`active`, `deleting`) and owned *grants* (ODRL Permissions: assignee, target, role or action; one per assignee, target and role-or-action), and prohibitions. The tenant's root object lives in the designated `meta` graph (`graph: meta`); the `registry` graph comes into being with its first entry. *Create* writes the access record last, directly `active`; *delete* marks it `deleting` first and removes it last. A *start-up sweep*, run by the consumer's single instance before it serves, finishes `deleting` tenants and drops tenant databases and buckets that no record names; it never touches anything inside a live tenant. *Restore* (`Tenancy.restore`) creates a new tenant from a dump in the same order, record last: it draws a free tenant, rewrites the IRIs, checks the graphs and the root, writes the data, then the record with the restorer as the only grantee; a refusal or failure after the database exists drops the new database and bucket. `ServiceKit.dump_tenant` and `ServiceKit.restore_tenant` are its Python calls, with no route (see xref:architecture/data-flows.adoc#dump-restore[Dump and restore a tenant]).
|N-3, N-4, N-11

|Graph loading
|v1
|`Session.load_graph`: parse an RDF file (Turtle, RDF/XML, N-Triples, JSON-LD) in a worker thread;
refuse it with `InvalidGraph` if it does not parse, writing nothing; otherwise `PUT` it into a new
named graph, by default `{root}/content/{uuid4}` (per the IRI policy). A later commit registers it
by naming it in `loaded_graphs`; the commit is refused (`InvalidIri`, nothing written) if the policy
would not mint that graph for the aggregate or if another aggregate already owns it, which one `ASK`
on the registry settles (PD-7). A loaded graph no commit registers stays, unseen, until its tenant
is deleted or until `sweep_tenant` removes it: the start-up sweep drops only whole tenant databases
and buckets, and the sweep inside a live tenant is the next building block (below).
|N-5

|File store port and S3 adapter
|v1
|`FileStore` and `S3FileStore`: put, get and delete a blob by a key in a bucket per tenant, over the S3 protocol (any S3-compatible store); a put never creates a missing bucket (it is created with the tenant); dropping a tenant empties and deletes its bucket.
|N-6

|Token validation, identity port and Zitadel adapter
|v1
|`TokenVerifier` and `JwksTokenVerifier`: validate JWT access tokens (signature, issuer, audience, expiry) against the provider's cached published keys; read global roles from the `roles_claim`. `Identity` and `ZitadelIdentity`: find an account by exact email, list accounts, disable and re-enable, grant and remove a global role.
|N-7

|Access check
|v1
|A route dependency in the service kit: each route declares its action; the check evaluates the toolkit's ODRL subset (`rp_access`): the caller's global roles (token), their Permissions and Prohibitions on the tenant and on the aggregate (`graph_iri(root)`), and the consumer's role definitions. In order: 404 for a target outside the tenant or a tenant that is not `active`, 403 for a matching Prohibition, 404 when the caller's grants and global roles permit nothing, 403 when they do not permit the action (`AccessRules.require` in `services/access.py`). Tenant isolation comes from N-3, so queries are not rewritten. See xref:architecture/access-control.adoc[access control].
|N-8

|Collaboration
|v1
|`Collaboration` (`services/collaboration.py`), opened with `kit.collaboration(authorised)` for a caller the gate has authorised; it checks access itself on every call. Eight methods and no route: `referrers` (itself); `members`, `collections_of` and `delete_cascade` (`services/reference_collections.py`); `comment` and `thread` (`services/discussion.py`); `transition` and `transitions` (`services/transitions.py`). `Workflows` (`services/workflows.py`, `kit.workflows`) loads the workflow files given to `install_service(workflows=…)` and refuses a bad one before the service serves (`InvalidWorkflow`). `WriteGuards` (`services/write_guards.py`) composes the rules of a write. What a caller may not read is counted and never named (xref:architecture/access-control.adoc#collaboration[access control]). The session gained only generic reads for them (`referrer_rows`, `heads`, `matches`, `graphs_with`, `root_values`, `not_aggregates`), `principal`, `now()`, optional `guards` and `dependents`, and three private pieces of a transaction (xref:architecture/data-flows.adoc#private-pieces[the three, side by side]). A comment and a transition record are aggregates the toolkit writes itself; a delete through the kit takes them with their aggregate. How to use each: xref:howto/reverse-references.adoc[reverse references], xref:howto/reference-collections.adoc[reference collections], xref:howto/discussion.adoc[discussion], xref:howto/workflow.adoc[workflow].
|

|Service kit
|v1
|FastAPI helpers and one *generic router* driven by the schema at run time (tenant-scoped: `/{tenant_segment}/{t}/{rp_path}` and `…/{id}`; IRIs minted on create): RFC 9457 problem responses, the aggregate version as `ETag` with `If-Match` required on updates and deletes (428 when missing, 409 on conflict), token validation and access check as dependencies, bodies validated with the generated shapes, listings with equality filters and paging, an OpenAPI document from a hook over the schema. Plain JSON with an `id` holding the IRI by default, JSON-LD and Turtle by content negotiation (O-2). See xref:architecture/api.adoc[API].
|N-9

|Test kit
|v1
|`rdf_persistence.testkit`: `FakeStore`, `FakeFileStore`, `FakeIdentity` and `fake_session` (pure Python) for consumers' unit tests; `TokenSigner` for test tokens; three conformance suites, for a store, a file store and an identity adapter, run on the fakes and on Fuseki, Garage and Zitadel in containers; the freshness plugin and the model guards. The toolkit's own tests use a toy domain.
|N-10

|Model to code
|v1
|The xref:architecture/generation.adoc#metamodel[metamodel] and the `rp-generate` toolchain: xref:architecture/generation.adoc[generation workflow] (O-1); implemented (stage 1).
|N-1

|Typed query builder
|deferred
|v1 lists by class with equality filters, from templates with escaped terms, never by concatenating input.
|

|Unique keys across aggregates (e.g. a name unique within a kind)
|v1
|A key declared in the schema with `rp_unique_scope: tenant` (a book's ISBN, unique among a tenant's books) stays unique across the tenant's aggregates of that type. The commit's guard operation holds one guard per claimed value, so the check and the write are one request; a clash raises `KeyConflict`, a 409 `key-conflict`. `Session.key_duplicates()` lists the duplicates a new key meets in stored data. Design `cross-aggregate-unique-keys`.
|

|Sweep of orphans inside a live tenant (blobs, loaded graphs no aggregate names)
|v1
|`sweep_tenant` (`services/tenant_sweep.py`, `ServiceKit.sweep_tenant`): a dry run by default; finds loaded graphs no registry entry owns and blobs no `rp:fileKey` names, older than a grace period (1 hour), and removes graphs with `remove` and blobs with `remove_blobs`. `ServiceKit.remove_with_files` removes a file aggregate with the blobs only it names. Design `live-tenant-sweep`.
|

|Dump and restore of a tenant
|v1
|`dump` and `restore` (`services/tenant_dump.py`, `ServiceKit.dump_tenant`, `ServiceKit.restore_tenant`): one gzipped tar (`manifest.json`, `graphs.nq`, `blobs/<key>`, an empty `end` member). A restore always makes a new tenant with a new id and IRIs; it refuses an archive of another schema or IRI policy, a malformed or cut-short one, or one over `max_restore_bytes`. It checks structure, not each aggregate's shapes. Design `tenant-dump-restore`.
|

|Second store (Oxigraph, Virtuoso) and a capability descriptor
|deferred
|Needs an adapter mapping a database to a set of graphs; the descriptor arrives with it.
|

|Outbox, event bus and relay
|deferred
|No v1 need reacts to a change in another aggregate.
|

|Property- or triple-level access; OpenFGA as the decision engine
|deferred
|Per-aggregate access is v1 (access check). OpenFGA is reused if a cheap opportunity appears (D-4).
|

|GraphQL, read-only, over the same schema and context
|deferred
|The backup option C of xref:architecture/api.adoc[API] (D-1).
|N-9

|Annotation sets, forms from shapes, schema migrations, server-sent events
|deferred
|No v1 need.
|
|===

== Decisions taken

_Which choices shape everything else?_

[cols="1,4",options="header"]
|===
|Id |Decision
|O-1 |Generated domain classes, runtime mapper: only the standard LinkML generators run, through the toolkit's templates (extended where needed); no generated mappers, repositories or routes. The classes and the mapper serve domain services only; the API path needs neither (D-2). See xref:architecture/generation.adoc[generation workflow].
|O-2 |Plain JSON with an `id` field holding the IRI, described by OpenAPI, and JSON-LD through a context generated from the schema: the body stays `application/json`, and a `Link` header (`rel="http://www.w3.org/ns/json-ld#context"`) points to the context. Plain clients are unaffected; JSON-LD processors read the body as RDF. The same routes serve `application/ld+json` and `text/turtle` by content negotiation (D-1).
|===

== Public API and layer map

Everything a consumer uses is exported from the top-level package `rdf_persistence`; nothing else
may be imported (capability `rp-package-boundaries`). Generated consumer code imports the metamodel classes from the
top level too: `rp-generate`'s split pattern points at `rdf_persistence`.

The adapters, services and entrypoints are loaded on first use, so importing
`rdf_persistence.domain`, as every consumer's generated module does, loads no HTTP client or
service. Graph loading has no function of its own: it is `Session.load_graph`.

Layers import downward only: entrypoints → services → domain; adapters → services' ports and
domain; `testkit` and `generation` may import any layer. The consumer's composition root imports the
adapters from the top level.

== Layering and boundaries

Normative: capability `rp-package-boundaries` (layers import downward; no
consumer imports or terms; consumers use the public API only).
