= Architecture overview
:description: What rdf-persistence commits to: the needs it serves, its components and building blocks, the decisions that shape them, its public API and its layers.

_What does the toolkit commit to, and where is each part explained?_

rdf-persistence is a library and a code generator, shipped in one wheel as two sibling top-level
packages: `rdf_persistence` (the run-time library) and `rdf_persistence_generation` (the
`rp-generate` toolchain, used at build time). It has a repository of its own; its consumers depend
on it, never the reverse. This page is the overview of the architecture section: the needs the
toolkit serves, its components, the blocks that are built and those that wait for a need, the
decisions that shape everything else, and the public API with its layers. How a consumer uses the
blocks is in the xref:user-manual/index.adoc[user manual].

The architecture was proposed on 2026-11-05, revised the same day by the
xref:architecture/open-decisions.adoc[decision log of 2026-11-05], and first built by the change
`toolkit-v1-foundation` (2026-11-06); later changes added blocks, and this page follows the code.
The toolkit commits only to what a consumer needs: a block is built only when a need below requires
it. Each block is *built* or *deferred* (not built until a need forces it). The
xref:background/soa/index.adoc[background study] is research, not a commitment.

== Consumer needs

_What must the toolkit do for its consumers?_

What the first consumer required, in generic terms. The consumer's own architecture, in its own
repository, maps its decisions and use cases to these ids; this toolkit does not know the consumer.
The xref:requirements/use-cases.adoc[use cases] state the same needs from the side of the people who
use the toolkit.

[cols="1,6",options="header"]
|===
|Id |Need
|N-1 |Store domain objects as RDF, one aggregate per named graph, and read them back as typed objects.
|N-2 |Refuse a change made on stale data with a conflict, never a silent overwrite.
|N-3 |Keep each tenant's data in its own database: create it when the tenant is created, drop it when the tenant is deleted, never read across tenants.
|N-4 |Keep designated graphs in each tenant database: a metadata graph for the tenant's own details and a registry of the other graphs.
|N-5 |Load an RDF file into a named graph of its own, replace it and drop it.
|N-6 |Keep uploaded files byte for byte, per tenant, next to the RDF metadata that describes them.
|N-7 |Authenticate every request with an OpenID Connect access token, and administer accounts through the identity provider.
|N-8 |Allow or refuse each action from the caller's roles, global or per tenant, with the rules supplied by the consumer as data.
|N-9 |Serve all of this over an HTTP API with a published contract, explicit error responses and version-checked writes.
|N-10 |Test all of the above quickly without servers, and against the real store in CI.
|N-11 |Keep a catalogue of tenants with their lifecycle state and the role grants of each user in each tenant, in a system database, so that listing a user's tenants and checking access never open a tenant database.
|===

Ports (rounded) are interfaces owned by the toolkit (`Store`, `FileStore`, `Identity`,
`TokenVerifier`, `EventBus`); each names the adapter the toolkit ships, chosen by the consumer's
composition root (the event bus is optional). The service
kit reaches the store through the session and tenancy, and the access check reads the system
database directly (one `CONSTRUCT` per request). Graph loading is `Session.load_graph`. The
consumer calls only the public API (<<public-api>>): `install_service` and the `ServiceKit` it
returns (with `kit.collaboration`), `open_session`, `UnitOfWork` and `Mapper`, the ports and the
adapters.

*Collaboration* is the one public face of what a caller may ask of a tenant beyond one aggregate
at a time: who refers to a resource, the members of a collection, comments, and moves through a
workflow. It holds one session and the caller it acts for, and hands the work to three classes
behind it; `Workflows` holds the workflow files and the rule that keeps a state. The session knows
no schema and checks no access, so these classes carry both: each asks the access rules and reads
or writes through the session (the arrows that leave the box: access rules, mapper, session). They are kept out of the session so that the generic routes and the
unit of work, which do not pass through them, stay as they were. *Write guards* are the checks a
session runs on every add and replace (a collection's members, a state that only a transition
changes). The kit builds them once and hands them to every session it opens; the session calls
them through a protocol of its own (`WriteGuard`) and imports none of them. The second thing the
kit builds for the session is the refusal of a removal that others still refer to: the session
declares the port `RemovalRefusal` (the classes that refuse, and the `InUse` that names the
referrers), `ReferencedRemovals` (`collaboration/services/referenced_removals.py`) implements it
from the schema, and the kit hands it to `Tenancy`, which gives it to every session it opens (the
dotted arrow is that handover, not an import). The session imports no schema. An import contract
(`collaboration-layers` in `.importlinter`) fixes the order: collaboration, then transitions and
write guards, then discussion, reference collections and workflows, then access, then the session.

== Building blocks

_What is built, and what waits for a need?_

Where each block keeps its data, and what every operation does step by step, is in
xref:architecture/data-flows.adoc[Where data lives and what each operation does].

[cols="2,1,6,1",options="header"]
|===
|Block |State |Commitment |Needs

|Store port
|built
|One asynchronous interface, `Store` (`persistence/services/store.py`): SPARQL 1.1 query and update, a Graph Store Protocol `PUT` of one named graph (`put_graph`), dataset administration (create, drop, list), and, on the whole dataset, a Graph Store `GET` (`export_quads`: every named graph as N-Quads in one read) and `POST` (`import_quads`: adds N-Quads). There is no Graph Store get or drop of one graph: a graph is read with `CONSTRUCT` and emptied with an update. `ToolkitStore` wraps it for the SPARQL the toolkit writes: a refusal of such text is a fault of the service (500), not the caller's `BadQuery` (400).
|N-1, N-3, N-5

|Fuseki adapter
|built
|`FusekiStore` (`persistence/adapters/fuseki.py`, over the SPARQL 1.1 Protocol base `SparqlProtocolStore` in `persistence/adapters/sparql_protocol.py`): one Fuseki dataset (TDB2) per database, administered through the Fuseki administration API; maps Fuseki's answers (`409` exists, `404` or `405` missing, `400` refused text, `5xx` unavailable) to the port's errors. The store conformance suite checks the port's behaviour, including `DatabaseGone` for a query, an update or a put on a dropped dataset; no case checks what a dropped dataset leaves on disk.
|N-3

|Mapper
|built
|Domain object to triples and back, IRIs taken from the LinkML schema at run time
(`rdf_persistence/persistence/services/mapper.py`). Owned parts live in the root's graph: by an IRI minted
under the root's (by default `{root_iri}/parts/{uuid4}`, per the IRI policy) when their class
includes `Described`, otherwise as blank nodes skolemised on write; references to other aggregates
are IRIs; multi-valued slots are sets. The mapper reads the class the caller asks for (it does not
use `designates_type`), and an owned part as its slot's range class, so a subclass in an owned slot
comes back as its parent: a known limit, lifted when a schema owns a class hierarchy.
|N-1

|Session and unit of work
|built
|`Session` (`persistence/services/session.py`) reads, pages and commits whole graphs of one tenant database for one principal, and `UnitOfWork(session, mapper)` (`persistence/services/mapper.py`) gives object-level `get`, `add`, `remove` and `commit`; there are no repositories beyond these two. Every commit is one guarded SPARQL update request, so the store applies all its changes or none and a change made on a stale version token raises `Conflict`: what a commit guarantees is in xref:architecture/commits.adoc[Commits and conflicts], and the request step by step in xref:architecture/data-flows.adoc#commit[Committing several aggregates at once].
|N-1, N-2

|Tenancy
|built
|`Tenancy` (`tenancy/services/tenancy.py`). A system database (one per deployment) holding one *tenant access record* per tenant (`{tenant}/access`): label, database name, the name of the store that holds the database (absent means `default`), state (`active`, `deleting`) and owned *grants* (ODRL Permissions: assignee, target, role or action; one per assignee, target and role-or-action), and prohibitions. The tenant's root object lives in the designated `meta` graph (`graph: meta`); the `registry` graph comes into being with its first entry. *Create* writes the access record last, directly `active`; *delete* marks it `deleting` first and removes it last. Tenant databases may live on several named triple stores wired beside the `default` one; a tenant stays on the store its record names, and the system and application databases stay on `default`. A *start-up sweep*, run by the consumer's single instance before it serves, covers every wired store: it stops if a record names a store that is not wired, finishes `deleting` tenants on their own store and drops tenant databases (on any wired store) and buckets that no record names; it never touches anything inside a live tenant. *Restore* (`Tenancy.restore`) creates a new tenant from a dump in the same order, record last: it draws a free tenant, rewrites the IRIs, checks the graphs and the root, writes the data, then the record with the restorer as the only grantee; a refusal or failure after the database exists drops the new database and bucket. `ServiceKit.dump_tenant` and `ServiceKit.restore_tenant` are its Python calls, with no route (see xref:architecture/data-flows.adoc#dump-restore[Dump and restore a tenant]). It also keeps the application database, one per deployment, for the classes the schema marks `database: application` (see xref:howto/application-data.adoc[Keep data that belongs to no tenant]).
|N-3, N-4, N-11

|Schema migrations
|built
|The change of stored data when a schema changes. At build time, `rp-generate` keeps a *schema lock* (`schema.lock.json`, in `rdf_persistence_generation/lock.py` and `lock_step.py`) next to the migration files, compares it with the schema, refuses the changes that need a new `version:` and drafts a migration for those that need a step. At run time, the migration files (`migrations/services/migrations.py`) form one chain per schema, the toolkit's own and the consumer's, and the runner (`tenancy/services/migration_runner.py`) applies them. Each database holds a *stamp* per schema id, the version its data follows, in the graph `{base}toolkit/schema-stamps` (see xref:architecture/data-flows.adoc#migrations[Start-up migrations]). `install_service` creates the system database, guards the IRI policy, creates the application database, migrates the shared databases, runs the sweep, then migrates the tenants, before it serves; its argument `migrations` is the folder of the consumer's files. A tenant whose migration fails is set aside (`Tenancy.behind`) and answers `503`. See xref:howto/migrate.adoc[Change a schema that has stored data].
|

|Graph loading
|built
|`Session.load_graph`: parse an RDF file (Turtle, RDF/XML, N-Triples, JSON-LD) in a worker thread;
refuse it with `InvalidGraph` if it does not parse, writing nothing (a JSON-LD file is also refused
if it declares a graph of its own, holds a relative or invalid IRI, gives a `@context` that is not
in the document, or is not an object or array; see xref:user-manual/files.adoc[Keep files] for each
message); otherwise `PUT` it into a new
named graph, by default `{root}/content/{uuid4}` (per the IRI policy). A later commit registers it
by naming it in `loaded_graphs`; the commit is refused (`InvalidIri`, nothing written) if the policy
would not mint that graph for the aggregate or if another aggregate already owns it, which one `ASK`
on the registry settles (PD-7). A loaded graph no commit registers stays, unseen, until its tenant
is deleted or until `sweep_tenant` removes it: the start-up sweep drops only whole tenant databases
and buckets, and the sweep inside a live tenant is the next building block (below).
|N-5

|File store port and S3 adapter
|built
|`FileStore` and `S3FileStore`: put, get and delete a blob by a key in a bucket per tenant, over the S3 protocol (any S3-compatible store); a put never creates a missing bucket (it is created with the tenant); dropping a tenant empties and deletes its bucket.
|N-6

|Token validation, identity port and Zitadel adapter
|built
|`TokenVerifier` and `JwksTokenVerifier`: validate JWT access tokens (signature, issuer, audience, expiry) against the provider's cached published keys; read global roles from the `roles_claim`. `Identity` and `ZitadelIdentity`: find an account by exact email, list accounts, disable and re-enable, grant and remove a global role.
|N-7

|Access check
|built
|A route dependency in the service kit: each route declares its action; the check evaluates the toolkit's ODRL subset (`rp_access`): the caller's global roles (token), their Permissions and Prohibitions on the tenant and on the aggregate (`graph_iri(root)`), and the consumer's role definitions. In order: 404 for a target outside the tenant or a tenant that is not `active`, 403 for a matching Prohibition, 404 when the caller's grants and global roles permit nothing, 403 when they do not permit the action (`AccessRules.require` in `access/services/access.py`). Tenant isolation comes from N-3, so queries are not rewritten. See xref:architecture/access-control.adoc[access control].
|N-8

|Collaboration
|built
|`Collaboration` (`collaboration/services/collaboration.py`), opened with `kit.collaboration(authorised)` for a caller the gate has authorised; it checks access itself on every call. Eight methods and no route (`comment` and `transition` take `command=`, the command whose class and slots the record keeps): `referrers` (itself); `members`, `collections_of` and `delete_cascade` (`collaboration/services/reference_collections.py`); `comment` and `thread` (`collaboration/services/discussion.py`); `transition` and `transitions` (`collaboration/services/transitions.py`). `Workflows` (`collaboration/services/workflows.py`, `kit.workflows`) loads the workflow files given to `install_service(workflows=…)` and refuses a bad one before the service serves (`InvalidWorkflow`). `WriteGuards` (`collaboration/services/write_guards.py`) composes the rules of a write. `ReferencedRemovals` (`collaboration/services/referenced_removals.py`) names the classes that refuse deletion while referred to and builds the `InUse` that names the referrers; it implements the session's `RemovalRefusal` port, and the kit passes it to `Tenancy`. What a caller may not read is counted and never named (xref:architecture/access-control.adoc#collaboration[access control]). The session gained only generic reads for them (`referrer_rows`, `heads`, `matches`, `graphs_with`, `activities`, `root_values`, `not_aggregates`), `principal`, `now()`, optional `guards` and `dependents`, and three private pieces of a transaction (xref:architecture/data-flows.adoc#private-pieces[the three, side by side]). A comment is an aggregate the toolkit writes itself, and a delete through the kit takes it with its aggregate. A transition is a `Transition` activity in the tenant's provenance graph (`iris.provenance(tenant)`), kept when its aggregate is deleted; `transitions` reads it only for a stored aggregate. How to use each: xref:howto/reverse-references.adoc[reverse references], xref:howto/reference-collections.adoc[reference collections], xref:howto/discussion.adoc[discussion], xref:howto/workflow.adoc[workflow].
|

|Message bus
|built
|`MessageBus` (`messaging/services/messagebus.py`), in process and built by `bootstrap`. A *command* is a subclass of the toolkit's `Activity` (modelled in a sibling `<domain>_activities.yaml`); `handle(command, collaboration)` runs the handler of its nearest class, and the handler changes aggregates through a unit of work, one command and one commit. Every commit of a tenant database or of the application database records one activity in the provenance graph (its class is the command's, with a generation or invalidation per aggregate and references only, never content); after a commit that held, the kit hands that activity to `bus.publish`, which calls the observers of its class and of each ancestor. An observer's error is logged and does not undo the commit; commands an observer sends are queued and bounded by a limit per `handle` call. Delivery in process is at most once; the relay (the outbox block below) carries each commit to other deployments at least once. See xref:howto/event-driven.adoc[React to changes with commands and observers] and xref:architecture/data-flows.adoc#command[A command through the bus].
|N-9

|Service kit
|built
|FastAPI helpers and one *generic router* driven by the schema at run time (tenant-scoped: `/{tenant_segment}/{t}/{rp_path}` and `…/{id}`; IRIs minted on create): RFC 9457 problem responses, the aggregate version as `ETag` with `If-Match` required on updates and deletes (428 when missing, 409 on conflict), token validation and access check as dependencies, bodies validated with the generated shapes, listings with equality filters and paging, an OpenAPI document from a hook over the schema. Plain JSON with an `id` holding the IRI by default, and six more media types by content negotiation: JSON-LD, Turtle, N-Triples, N-Quads, TriG and RDF/XML (O-2; xref:architecture/api.adoc#representations[Representations]). See xref:architecture/api.adoc[API].
|N-9

|Test kit
|built
|`rdf_persistence.testkit`: `FakeStore`, `FakeFileStore`, `FakeIdentity` and `fake_session` (pure Python) for consumers' unit tests; `TokenSigner` for test tokens; four conformance suites, for a store, a file store, an identity adapter and an event bus, run on the fakes and on Fuseki, Garage, Zitadel and Redis in containers; the model guards; the freshness plugin lives in `rdf_persistence_generation.testkit.freshness`. The toolkit's own tests use a toy domain.
|N-10

|Model to code
|built
|The xref:architecture/generation.adoc#metamodel[metamodel] and the `rp-generate` toolchain: xref:architecture/generation.adoc[generation workflow] (O-1).
|N-1

|Typed query builder
|deferred
|The router lists by class with equality and contains filters, from templates with escaped terms, never by concatenating input.
|

|Unique keys across aggregates (e.g. a name unique within a kind)
|built
|A key declared in the schema with `rp_unique_scope: tenant` (a book's ISBN, unique among a tenant's books) stays unique across the tenant's aggregates of that type. The commit's guard operation holds one guard per claimed value, so the check and the write are one request; a clash raises `KeyConflict`, a 409 `key-conflict`. `Session.key_duplicates()` lists the duplicates a new key meets in stored data. Design `cross-aggregate-unique-keys`.
|

|Sweep of orphans inside a live tenant (blobs, loaded graphs no aggregate names)
|built
|`sweep_tenant` (`tenancy/services/tenant_sweep.py`, `ServiceKit.sweep_tenant`): a dry run by default; finds loaded graphs no registry entry owns and blobs no `rp:fileKey` names, older than a grace period (1 hour), and removes graphs with `remove` and blobs with `remove_blobs`. `ServiceKit.remove_with_files` removes a file aggregate with the blobs only it names. Design `live-tenant-sweep`.
|

|Dump and restore of a tenant
|built
|`dump` and `restore` (`tenancy/services/tenant_dump.py`, `ServiceKit.dump_tenant`, `ServiceKit.restore_tenant`): one gzipped tar (`manifest.json`, `graphs.nq`, `blobs/<key>`, an empty `end` member). A restore always makes a new tenant with a new id and IRIs; it refuses an archive of another schema or IRI policy, a malformed or cut-short one, or one over `max_restore_bytes`. It checks structure, not each aggregate's shapes. Design `tenant-dump-restore`.
|

|Second store (Oxigraph, Virtuoso) and a capability descriptor
|deferred
|Needs an adapter mapping a database to a set of graphs; the descriptor arrives with it.
|

|Outbox, event bus and relay
|built
|The commit marks its activity as pending, in the same update. A relay publishes each marked activity to an event bus (a port; a Redis Streams adapter) and offers it to the live hub. See xref:howto/event-driven.adoc#relay[Carry commits to other deployments and to browsers].
|

|Property- or triple-level access; OpenFGA as the decision engine
|deferred
|Per-aggregate access is built (access check). OpenFGA is reused if a cheap opportunity appears (D-4).
|

|GraphQL, read-only, over the same schema and context
|deferred
|The backup option C of xref:architecture/api.adoc[API] (D-1).
|N-9

|Server-sent events
|built
|`GET /tenants/{tenant}/rp-events`, filtered to what the reader may read, resumable with `Last-Event-ID`. See xref:howto/event-driven.adoc#sse[Follow a tenant in the browser].
|

|Annotation sets, forms from shapes
|deferred
|No need yet.
|
|===

== Decisions taken

_Which choices shape everything else?_

[cols="1,4",options="header"]
|===
|Id |Decision
|O-1 |Generated domain classes, runtime mapper: only the standard LinkML generators run, through the toolkit's templates (extended where needed); no generated mappers, repositories or routes. The classes and the mapper serve domain services only; the API path needs neither (D-2). See xref:architecture/generation.adoc[generation workflow].
|O-2 |Plain JSON with an `id` field holding the IRI, described by OpenAPI, and JSON-LD through a context generated from the schema: the body stays `application/json`, and a `Link` header (`rel="http://www.w3.org/ns/json-ld#context"`) points to the context. Plain clients are unaffected; JSON-LD processors read the body as RDF. By content negotiation (D-1), a route that answers one aggregate serves seven representations: JSON, JSON-LD, Turtle, N-Triples, N-Quads, TriG and RDF/XML; a listing stays JSON and JSON-LD (xref:adr/adr-005-representations.adoc[ADR-005]).
|===

[#platform-fit]
== Fit and limits for a platform

_I build a platform whose users define their own models: can the toolkit be its data layer, and what
does it leave to me?_

This section answers the system architect of the xref:requirements/use-cases.adoc#system-architect[use cases]
(UC-24, UC-25, UC-29).

*One model per running service.* `install_service` (and `ServiceKit`) takes one root LinkML schema
(`schema=`) and the one package `rp-generate` wrote for it (`generated=`), at start-up. The routes,
the shapes, the context and the mapper's IRIs come from that pair, and every tenant of the service
shares it. A platform that serves several models runs one service per model.

*Generation is build time.* `rp-generate` is a command run when the application is built
(xref:architecture/generation.adoc[Model to code]); the running service never generates. So a model
a platform's user defines or changes becomes a running data service by the same path as any schema
change: regenerate, write the migration the change needs (xref:howto/migrate.adoc[Change a schema
that has stored data]; adding a class or an optional slot needs none), and redeploy. The service
reads the schema at start-up, so a change is served only after a restart.

*One process per deployment.* A deployment runs as one process (one uvicorn worker, one pod). The
events relay starts with the service whether or not an event bus is wired, so several workers or
pods would each relay every activity, and each browser would see only the activities of the
instance it is connected to. The tenants a failed migration set aside (`tenant-behind`) are also
held in each process's memory. See xref:howto/event-driven.adoc#relay-limits[Limits of the relay].

*What ships, and what you can plug in.* The ports are interfaces of the toolkit; the composition
root picks the adapter for each:

[cols="2,3",options="header"]
|===
|Port |Adapter shipped
|`Store` (triple store) |`FusekiStore` (Fuseki, one TDB2 dataset per database); several named stores are possible, all Fuseki (xref:howto/tenant-stores.adoc[Put tenants on several stores])
|`FileStore` |`S3FileStore` (any S3-compatible store)
|`Identity` |`ZitadelIdentity` (Zitadel)
|`TokenVerifier` |`JwksTokenVerifier` (the published keys of an OpenID Connect issuer)
|`EventBus` (optional) |`RedisEventBus` (Redis Streams, `rdf_persistence.events.adapters.redis_events`)
|===

To put the platform's own store, file store, identity provider or event bus behind a port, write an
adapter and run the testkit's conformance suite for that port on it: see the user manual, step 13,
xref:user-manual/test.adoc#check-an-adapter-of-your-own[Check an adapter of your own].

*What is not there yet.* Each is a candidate change in `openspec/changes/`, not planned (the list
of xref:questions.adoc#what-could-strengthen-it-in-the-future[possible future work]):

* another triple-store product (Oxigraph, Virtuoso) with a capability descriptor (`second-store`);
* a client library over the generated TypeScript types and the OpenAPI document
  (`typescript-client`); today the toolkit generates the types and serves the OpenAPI document;
* a read-only GraphQL API (`graphql-read-api`); today the API is the generic REST router;
* property- or triple-level access and OpenFGA (`fine-grained-access`); today access is per tenant
  and per aggregate.

[#public-api]
== Public API and theme map

Everything a consumer uses is exported from the top-level package `rdf_persistence`; nothing else
may be imported (capability `rp-package-boundaries`). Generated consumer code imports `RpModel` and
the metamodel classes from the top level too: in a consumer's run, `rp-generate` writes
`from rdf_persistence import ...`.

[#themes]
=== Where a module lives

_Where does a module live?_

Every hand-written module of the library sits in a theme, and inside the theme in a layer:
`rdf_persistence/<theme>/<layer>/<module>.py`. The layer is `domain`, `services`, `adapters` or
`entrypoints`, and a theme has only the layers it needs. There are thirteen themes. The table lists
them from the lowest up. A theme imports only the themes of the rows above it; two themes on the
same row import neither the other.

[cols="1,2,4,5,2,4",options="header"]
|===
|Order |Theme |`domain` |`services` |`adapters` |`entrypoints`
|1 |`core` |`base` (`RpModel`), `exceptions`, `media`, `sparql`, `sparql_parsing`; `rp_core`, `rp_annotations` and the combined artefacts (`generated/`) |`artifacts`, `yaml_files`, `telemetry` |`_http` |
|2 |`iris` |`layout` |`iris` | |
|2 |`schema` | |`schema`, `schema_structure`, `vocabulary` | |
|3 |`provenance` |`rp_provenance` (`generated/`) |`provenance`, `visible_part` | |
|4 |`files` |`blob_keys`; `rp_files` (`generated/`) |`files` (port) |`s3` |
|5 |`persistence` | |`store` (port), `session`, `mapper`, `listing`, `loading`, `jsonld`, `decoding`, `unique_keys` |`sparql_protocol`, `fuseki` |
|6 |`access` |`rp_access`, `rp_tenancy` (`generated/`) |`access`, `identity` (port), `tokens` (port) |`jwks`, `zitadel` |
|6 |`migrations` | |`migrations` | |
|7 |`tenancy` | |`tenancy`, `sweep`, `tenant_sweep`, `tenant_dump`, `tenant_move`, `migration_runner`, `iri_policy_guard` | |
|8 |`collaboration` |`rp_collections`, `rp_discussion`, `rp_workflow` (`generated/`) |`collaboration`, `transitions`, `write_guards`, `discussion`, `reference_collections`, `workflows` | |
|8 |`events` | |`events` (port), `event_hub`, `event_stream`, `relay` |`redis_events` |
|9 |`messaging` | |`messagebus` | |
|10 |`api` | |`aggregates`, `documents`, `file_removal`, `components`, `shacl` | |`kit`, `service`, `router`, `auth`, `negotiation`, `responses`, `problems`, `openapi`, `sse`, `environment`
|===

Each theme that owns domain concepts has its own domain package, `<theme>.domain.generated`:
`core`, `access`, `provenance`, `files` and `collaboration` (xref:architecture/index.adoc#models-in-themes[which module is in which]). `files` is above `provenance` because `rp_files` imports `rp_provenance`.

A new module goes to the lowest theme that uses it, in the layer its imports allow. Its unit tests go
to `tests/unit/<theme>/`; a test of several themes goes to the folder of the highest. Each
`__init__.py` of a theme or a layer holds a docstring and nothing else, so importing a theme imports
nothing more.

Three things sit outside the themes. `testkit/` is outside the layers and may import any of them.
`model/` holds the schemas, shipped as package data. `rdf_persistence_generation`, the generator, is
a sibling package. Every old path (`rdf_persistence.services.*`, `rdf_persistence.entrypoints.*`,
`rdf_persistence.adapters.*` and `rdf_persistence.domain.*`, `RpModel` and `FusekiStore` included) is
gone, with no shim: `RpModel` is `from rdf_persistence import RpModel`, and `FusekiStore` is in
`rdf_persistence.persistence.adapters.fuseki`.

[#models-in-themes]
=== Where a model lives

_Where does a generated model go?_

The kind of a model shows in its path (xref:architecture/generation.adoc#kinds[Two kinds of model]):

* A *domain model*, a class the toolkit stores as RDF, sits only in a `domain/generated/` folder.
  The metamodel is generated one theme at a time, each theme into its own
  `<theme>.domain.generated` package, and a theme's classes import those of the themes below it:
  `core` (`rp_core`, `rp_annotations`), `access` (`rp_access`, `rp_tenancy`), `provenance`
  (`rp_provenance`), `files` (`rp_files`) and `collaboration` (`rp_collections`, `rp_discussion`,
  `rp_workflow`, which the root `rp_collaboration.yaml` imports so that one target generates them).
  `rp_tenancy` is in `access` because a tenant is an access boundary, and `rp_tenancy` builds on
  `rp_access`: the two generate together. `files` ranks above `provenance` in the order of
  <<themes>>, because `rp_files` imports `rp_provenance`. The RDF artefacts stay one set,
  built from all the domain modules and written to `core/domain/generated/`: `shapes.ttl`,
  `context.jsonld` and the frames. Load those. The other four targets write partial copies of them
  in their own folders, which the toolkit never loads, as they miss the shapes of other themes.
  `schema` imports no generated class of a theme above it: it reads the stored-file class and the
  tenant states from the schema itself, through the SchemaView.
* A *technical model* (a setting, a wire record, a request or response body, a SPARQL term bundle)
  sits in `<theme>/<layer>/generated/`, where the layer is `services`, `adapters` or `entrypoints`:
  the lowest layer every user of the model may import, in the lowest theme that uses it. A wire
  record only an adapter uses goes to `adapters`; a body only the entrypoints use goes to
  `entrypoints`; a model that an adapter and an entrypoint both use goes to `services`, since
  neither imports the other. So every settings group is in a `services` layer, and `ToolkitSettings`,
  which composes them, is in `api/entrypoints/generated/settings/`.

Hand-written code in a `domain` layer that needs a technical model is not domain code: it moves up
a layer. That is why the IRI layout that no policy changes is in `iris/domain/layout.py`, and `Iris`,
its policy and its templates are in `iris/services/iris.py`. Two checks hold the rule: `rp-generate`
refuses a target whose package is in a folder its derived kind does not allow (rule `TARGET_KIND`,
xref:architecture/generation.adoc#target-kind[The kind of a target]), and the contracts
`layers-across-themes` forbid every `rdf_persistence.*.domain` from importing a `services`,
`adapters` or `entrypoints` package, `generated` ones included. The folder of each technical target
is in xref:architecture/generation.adoc#kinds[Two kinds of model].

The metamodel's classes and the errors are imported at once; every other name is loaded on first
use. So importing `rdf_persistence`, as every consumer's generated module does, loads no HTTP client
or service. Graph loading has no function of its own: it is `Session.load_graph`.

[#layering]
=== The contracts

_What keeps the themes and the layers in order?_

Inside each theme, layers import downward only: `entrypoints | adapters` → `services` → `domain`.
The ports live in `services` and their implementations in `adapters`; `entrypoints` and `adapters`
import neither the other, so the consumer's composition root wires them, importing the adapters from
the top level. Between themes, a theme imports only the themes below it (<<themes>>). `testkit` and
the generator package may import any layer.

`.importlinter` holds these contracts; `make check-architecture` runs them:

[cols="2,5",options="header"]
|===
|Contract |What it forbids
|`themes-layered` |In each of the thirteen themes, a lower layer importing a higher one. It is
exhaustive: a theme holds no module outside its four layers.
|`themes-ordered` |A theme importing a theme above it, or a theme of its own row (the order of <<themes>>).
|`layers-across-themes` (four forbidden contracts) |The `domain` of any theme importing the `services`,
`adapters` or `entrypoints` of any theme; the `services` of any theme importing `adapters` or
`entrypoints`; the `adapters` importing `entrypoints`, and the `entrypoints` importing `adapters`.
Since every technical model sits in a `services`, `adapters` or `entrypoints` folder, no domain
imports one (<<models-in-themes>>).
|`domain-pure` |A `domain` importing an I/O, web, token or validation
library (`httpx`, `boto3`, `fastapi`, `jwt`, `pyshacl`, `anyio`).
|`runtime-without-extras` |The runtime layers importing the testkit, the
generator, `pytest`, `testcontainers` or `linkml`.
|`works-without-the-generate-extra` |What is installed without the `generate` extra importing `linkml`.
|`library-never-imports-the-generator` |`rdf_persistence` importing `rdf_persistence_generation`
(xref:architecture/generation.adoc#generator-package[The generator's package]).
|`collaboration-layers` |The order inside the collaboration services: message bus, collaboration,
transitions and write guards, discussion, reference collections and workflows, access, session.
|`session-and-provenance-without-mapper` |The session or the activity shape importing the mapper,
which imports the session.
|`tenancy-without-the-runner` |The tenancy importing the migration runner, which imports the tenancy.
|`event-bus-libraries-in-one-module` |Any module but the Redis adapter importing `faststream`, and
any module importing `redis`.
|`api-services-never-import-the-bus` |The four `api` services modules (`aggregates`, `components`,
`documents`, `file_removal`) importing the message bus. `api` sits above `messaging`, so the theme
order alone allows it.
|`domain-tests-stay-in-the-domain` |The domain tests importing anything above the domain.
|`sparql-parser-only-through-the-wrappers` |Any module but the wrappers (`core/domain/sparql_parsing.py`,
`api/services/shacl.py`) importing `rdflib.plugins.sparql` or `pyshacl`.
|===

The file has seventeen contract sections: `layers-across-themes` is four of them. A failure names
the contract that broke and the import chain.

== Layering and boundaries

Normative: capability `rp-package-boundaries` (layers import downward; no
consumer imports or terms; consumers use the public API only).
