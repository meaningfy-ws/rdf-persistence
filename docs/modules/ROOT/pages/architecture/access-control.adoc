= Access control and identity
:description: How the toolkit decides who may do what, at which granularity, with which policy model, and how users and API clients sign in.

Status: *Accepted* (developer, 2026-11-05: decisions D-4, D-5 and D-10 of
xref:architecture/open-decisions.adoc[the decisions of 2026-11-05]). Research behind this page: the
xref:background/soa/angles/authz.adoc[identity and authorization angle] of the background study,
updated on 2026-11-05.

== Decisions

* *Own check over ODRL* (D-4): the toolkit evaluates its own minimal ODRL subset, per tenant and per
  aggregate, in process. Policies are RDF, our own specification.
* *OpenFGA is deferred*, unless a cheap opportunity to reuse it appears (for example a need for access
  that flows through relationships). The policy data is shaped so it can be compiled to OpenFGA then,
  without a migration.
* *One model* (D-5): a grant is an ODRL Permission.
* *No login endpoint of our own* (D-10): the API accepts any valid token from the identity provider,
  however it was obtained.

== The access model is its own module

The toolkit ships `rp_access.yaml`. An application keeps its roles and rules in its own access module,
which imports `rp_access` and the domain modules. A domain module never imports an access module: the
boundary check of xref:architecture/generation.adoc[`rp-generate`] refuses it.

....

    RA["rp_access<br/>(toolkit)"]
    AA["app access module<br/>roles and rules"]
    D["app domain modules"]
    AA --> RA
    AA --> D
    D -. refused .-> AA
....

== Lessons from Fluree and semantic.works

[cols="1,3,3",options="header"]
|===
| |How it works |What we take
|*Fluree v4* |Policies are RDF (`f:AccessPolicy`): an action (`f:view`, `f:modify`), a static `f:allow` or a condition query with `?$this` and `?$identity` bound, targets `f:onClass`, `f:onProperty`, `f:onSubject` that intersect, and `f:required` for policies that must allow. A JWT claim names the identity, which points to its policy classes. Enforcement is triple-level, inside the database. BUSL-1.1 licence. |Identity → policy class → policies; intersecting targets; a choice of seeing the state before or after a write.
|*semantic.works mu-authorization* |Group specs: a group is granted when a SPARQL query over the session succeeds (`AccessByQuery`); each group reads or writes a set of graphs, whose IRIs are built from the query's variables (one graph per tenant), constrained by types and predicates. Enforced by a SPARQL-rewriting proxy. |Roles derived from data by a query over the grants; graph IRIs built from parameters, which fits `graph_iri(root)` (DEC-29).
|===

Neither is a library we can embed: Fluree is a database, mu-authorization a Lisp proxy (5★).

== The ODRL subset

ODRL 2.2 (W3C Recommendation, 2018) is the standard RDF vocabulary for policies. The toolkit uses a
minimal subset, so its access data is readable by any ODRL tool and can be compiled to another engine
later.

[mermaid]
....
classDiagram
    direction LR
    class Policy {
      uid
    }
    class Permission {
      assignee
      action
      target
    }
    class Prohibition {
      assignee
      action
      target
    }
    class Scope {
      level
      target_iri
    }
    Policy *-- Permission
    Policy *-- Prohibition
    Permission --> Scope : target
    Prohibition --> Scope : target
....

[cols="1,2,3",options="header"]
|===
|Class |ODRL term |Meaning
|`Policy` |`odrl:Set` |A set of rules. Conflict resolution is fixed: denial wins, and everything not permitted is denied.
|`Permission` |`odrl:Permission` |An assignee may perform an action on a target. A grant is a Permission (D-5).
|`Prohibition` |`odrl:Prohibition` |An assignee may not perform an action on a target.
|`Principal` |`odrl:Party`, `prov:Agent` |A user or service account of the identity provider, by IRI.
|`Role` |`odrl:PartyCollection` |A named set of principals; an assignee may be a role.
|`Scope` |`odrl:AssetCollection` |A target at a level: `system`, `tenant` or `aggregate` (the aggregate's graph, `graph_iri(root)`).
|`Action` (enum) |`odrl:read`, `odrl:modify`, `odrl:delete`, extended by the application |What is done.
|`RoleDefinition` |— (toolkit) |Which actions a role permits at which scope level: the application's permission matrix as data (need N-8).
|===

Left out for now: Duty, Offer and Agreement, constraints, assigner. No LinkML ODRL schema exists to
reuse, and no ODRL evaluator is mature enough to depend on (FORCE/SolidLab odrl-evaluator, ODRE,
ODRL-PAP to Rego: all small or research-grade).

== How OpenFGA and ODRL would fit together

*ODRL is the record* (what is allowed, stored as RDF with the data); *OpenFGA is an engine* (it
answers "may this user do this to that object?", including through relationships). If OpenFGA is
added later, data flows one way:

[mermaid]
....
flowchart LR
    O["ODRL policies<br/>(RDF)"] -->|"permission → tuple"| F["OpenFGA"]
    T["role definitions"] -->|"→ model"| F
....

* Constraints map only partly (to CEL conditions); prohibitions have no direct counterpart (only
  `but not`).
* Prior work compiles ODRL to OpenFGA (Plaza-Ortiz et al., 2025); no code is published.

== The check

Each route declares its action; the check runs before the handler.

[mermaid]
....
flowchart LR
    Q["caller, action,<br/>aggregate"] --> P{"prohibited?"}
    P -- yes --> D403["403"]
    P -- no --> T{"grant in<br/>this tenant?"}
    T -- no --> D404["404"]
    T -- yes --> R{"role permits?"}
    R -- yes --> OK["allow"]
    R -- no --> D403
....

* A *global role* from the token (an administrator) that the rules allow passes without a grant.
* A caller without a grant, or a tenant that is not `active`, gets 404, so the tenant's existence is
  not revealed.
* *Per aggregate*: a Permission whose target is an aggregate's scope applies to that aggregate only;
  the check looks up the caller's permissions for the tenant and for `graph_iri(root)`.

== Identity: signing in from the browser and from the API

Both are needed: people use a web app, programs and scripts call the API. Zitadel (v4) supports every
flow below; it has no password grant.

[cols="2,3,2",options="header"]
|===
|Who |Flow |Token reaches the API as
|A person in a browser |Authorization code with PKCE, by the web app's *server* (a confidential client; the backend-for-frontend pattern the IETF's guidance for browser apps ranks first). Tokens stay on the server; the browser holds an HTTP-only session cookie. |Bearer token, sent by the web app's server
|A person at a command line |Device authorization flow |Bearer token
|A program (service account) |Private-key JWT, or client credentials |Bearer token
|A script |Personal access token (service accounts only) |Bearer token
|===

[mermaid]
....
flowchart LR
    C["browser (via its server),<br/>CLI, program, script"] -->|"get a token"| Z["Zitadel"]
    C -->|"Bearer token"| A["API"]
    A -.->|"published keys"| Z
....

The API checks signature, issuer, audience and expiry against the provider's published keys (cached).
Signing in "through the API" therefore means obtaining a token with one of these flows. Token exchange
(acting on behalf of another user) is not used: Zitadel's support is a first iteration.
