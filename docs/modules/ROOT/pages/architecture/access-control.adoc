= Access control and identity
:description: How the toolkit decides who may do what, at which granularity, with which policy model, and how users and API clients sign in.

Status: *Accepted* (developer, 2026-11-05: decisions D-4, D-5 and D-10 of
xref:architecture/open-decisions.adoc[the decisions of 2026-11-05]). Research behind this page: the
xref:background/soa/angles/authz.adoc[identity and authorization angle] of the background study,
updated on 2026-11-05. The access model, the check and the token verification are *implemented*
(stages 3 and 4 of the change `toolkit-v1-foundation`: `rdf_persistence/model/rp_access.yaml`,
`rdf_persistence/services/access.py`, `rdf_persistence/adapters/jwks.py`). How an application
writes its roles and grants is in xref:howto/adopt.adoc#access[Build an application, step 11].

== Decisions

_Which engine decides access, and where do policies live?_

* *Own check over ODRL* (D-4): the toolkit evaluates its own minimal ODRL subset, per tenant and per
  aggregate, in process. Policies are RDF, our own specification.
* *OpenFGA is deferred*, unless a cheap opportunity to reuse it appears (for example a need for access
  that flows through relationships). The policy data is shaped so it can be compiled to OpenFGA then,
  without a migration.
* *One model* (D-5): a grant is an ODRL Permission.
* *No login endpoint of our own* (D-10): the API accepts any valid token from the identity provider,
  however it was obtained.

== The access model is its own module

_Where does an application keep its roles and rules?_

The toolkit ships `rp_access.yaml`. An application keeps its roles and rules in its own access module,
which imports `rp_access` and the domain modules. A domain module never imports an access module: the
boundary check of xref:architecture/generation.adoc[`rp-generate`] refuses it.

== Lessons from Fluree and semantic.works

[cols="1,3,3",options="header"]
|===
| |How it works |What we take
|*Fluree v4* |Policies are RDF (`f:AccessPolicy`): an action (`f:view`, `f:modify`), a static `f:allow` or a condition query with `?$this` and `?$identity` bound, targets `f:onClass`, `f:onProperty`, `f:onSubject` that intersect, and `f:required` for policies that must allow. A JWT claim names the identity, which points to its policy classes. Enforcement is triple-level, inside the database. BUSL-1.1 licence. |Identity → policy class → policies; intersecting targets; a choice of seeing the state before or after a write.
|*semantic.works mu-authorization* |Group specs: a group is granted when a SPARQL query over the session succeeds (`AccessByQuery`); each group reads or writes a set of graphs, whose IRIs are built from the query's variables (one graph per tenant), constrained by types and predicates. |===

Neither is a library we can embed: Fluree is a database, mu-authorization a Lisp proxy (5★).

== The ODRL subset

_What can a policy say?_

ODRL 2.2 (W3C Recommendation, 2018) is the standard RDF vocabulary for policies. The toolkit uses a
minimal subset, so its access data is readable by any ODRL tool and can be compiled to another engine
later.

[mermaid]
....
classDiagram
    direction LR
    class Policy
    class TenantAccess {
      label
      state
      database_name
    }
    class Grant {
      assignee
      target
      role or action
    }
    class Prohibition {
      assignee
      target
      action
    }
    class RoleDefinition {
      role
      level
      actions
    }
    Policy <|-- TenantAccess
    TenantAccess *-- Grant : grants
    TenantAccess *-- Prohibition : prohibitions
....

[cols="1,2,3",options="header"]
|===
|Class |ODRL term |Meaning
|`Policy` |`odrl:Set` |An abstract set of rules, with no slots of its own. Conflict resolution is fixed: denial wins, and everything not permitted is denied.
|`TenantAccess` |`rp:TenantAccess`, `is_a: Policy` |The tenant's access record in the system database: label, state, database name, and the owned `grants` and `prohibitions`. An application subclasses it (the toy library's `LibraryAccess`).
|`Grant` |`odrl:Permission` |An assignee may perform an action on a target, by a `role` or a direct `action`: exactly one of the two. One grant per assignee, target and role or action (`unique_keys`). A grant is a Permission (D-5).
|`Prohibition` |`odrl:Prohibition` |An assignee may not perform an action on a target.
|`Principal` |`odrl:Party`, `prov:Agent` |A user or service account of the identity provider, by IRI.
|`Role` |`rp:role` on a grant |A role a principal holds in a tenant. In v1 the assignee is always a principal; roles as ODRL party collections are later.
|Target |`odrl:target` |An IRI: a tenant, or an aggregate's graph (`graph_iri(root)`). The level follows from the IRI. The system level comes only from global roles in the token.
|`Action` (enum) |`odrl:read`, `odrl:modify` (at tenant scope, also create), `odrl:delete`, `rp:administer` (change a tenant's grants, or delete the tenant), and `odrl:annotate` (add a comment to an object without changing it; `modify` does not imply it) |What is done. The set is fixed by the toolkit; an application cannot add an action.
|`RoleDefinition` |`rp:RoleDefinition` |Which `actions` (`rp:permits`) a `role` permits at which `level` (`RoleLevel`: `system`, `tenant`, `aggregate`): the application's permission matrix, supplied as a YAML file and never stored (need N-8). A `system` role comes from the token's global roles and cannot be granted.
|===

Left out for now: Duty, Offer and Agreement, constraints, assigner. No LinkML ODRL schema exists to
reuse, and no ODRL evaluator is mature enough to depend on (FORCE/SolidLab odrl-evaluator, ODRE,
ODRL-PAP to Rego: all small or research-grade).

== How OpenFGA and ODRL would fit together

*ODRL is the record* (what is allowed, stored as RDF with the data); *OpenFGA is an engine* (it
answers "may this user do this to that object?", including through relationships). If OpenFGA is
added later, data flows one way:

[mermaid]
....
flowchart LR
    O["ODRL policies<br/>(RDF)"] -->|"permission → tuple"| F["OpenFGA"]
    T["role definitions"] -->|"→ model"| F
....

* Constraints map only partly (to CEL conditions); prohibitions have no direct counterpart (only
  `but not`).
* Prior work compiles ODRL to OpenFGA (Plaza-Ortiz et al., 2025); no code is published.

== The check

_In which order is a request refused, and with which status?_

Each route declares its action; the check runs as a route dependency, after the token is verified
and before the handler (`entrypoints/auth.py`, `Gate.check`). It loads the caller's access to the
tenant in one query (`load_caller_access`) and decides in `AccessRules.require`
(`rdf_persistence/services/access.py`), in this order:

[mermaid]
....
flowchart LR
    Q["request"] --> S{"target in<br/>the tenant?"}
    S -- no --> N1["404"]
    S -- yes --> A{"tenant<br/>active?"}
    A -- no --> N2["404"]
    A -- yes --> P{"prohibited?"}
    P -- yes --> F1["403"]
    P -- no --> E{"any action<br/>permitted?"}
    E -- no --> N3["404"]
    E -- yes --> R{"this action<br/>permitted?"}
    R -- yes --> OK["allow"]
    R -- no --> F2["403"]
....

. *Scope.* The target is the tenant IRI, or an aggregate IRI the toolkit mints in that tenant;
  anything else is 404. The scope of the rules is the tenant, plus the aggregate's graph IRI
  (`graph_iri(root)`) for an action on one aggregate.
. *State.* A tenant that is not `active` is 404.
. *Prohibition.* A Prohibition in scope for the caller and the action is 403. A Prohibition of
  `read` forbids every action, since each implies `read`.
. *Nothing permitted.* The actions permitted by the caller's grants in scope (by role, through the
  role definitions at the target's level, or directly) and by its global roles (system-level role
  definitions) form one set. An empty set is 404, so a hidden tenant answers like a missing one.
. *Action missing.* An action not in the set is 403; `read` passes when any other action is in it.

* *Application data.* Access to application data is decided by `AccessRules.require_application`
  from the caller's global roles at level `system` alone. No grant and no prohibition is read. The
  answer is `Forbidden` (403), never `NotFound`. A role at level `system` permits its actions in every
  tenant as well, so there is no role for application data only.
* A *global role* from the token (an administrator) that the rules allow passes without a grant.
  A role name in a token counts only if the roles file defines it at system level: for a comment's
  audience too, so a token role named like a tenant role opens nothing.
* *Per aggregate*: a Permission whose target is an aggregate's graph IRI applies to that aggregate
  only.
* A *read* of a tenant's root or of an aggregate lists in its `Allowed-Actions` header the actions the
  routes on it allow the caller (`AccessRules.allowed_actions`): on a tenant `delete` is listed when the
  caller may `administer`, which deleting a tenant needs; on an aggregate `administer` is never listed. A
  UI thus knows which buttons to show; the tenant listing repeats it per item as `allowed_actions`. The stored document stays free of it.
* A *listing* needs `read` on the tenant, and leaves out the aggregates a `read` Prohibition hides
  from the caller before it counts and pages (`AccessRules.hidden_graphs`).
* *Grants are validated* when they are written (`AccessRules.validate_grants`): a target must be the
  tenant, its access record or an aggregate graph of it (else `InvalidGrant`, 422), an assignee an IRI, and a role
  defined at its target's level (else `UnknownRole`, 422).

An application adds its own rules on tenant writes through `install_service`'s
`grant_validators` and `root_validators`. They run in the
toolkit's write path before the write (on create, before the tenant's database exists); raising
`InvalidBody` refuses the write with 422 and nothing is written. Grant validators see every
replacement of a tenant's grants; root validators see a tenant's create (the creator is the caller),
root replacement and rename. Validators are plain functions that must not block, and get copies of
the old and new objects, so they can only refuse. Any other exception, a toolkit error such as
`Forbidden` or an `HTTPException` included, is a bug and answers 500. Atomicity comes from the conditional write itself:
two writes at one version cannot both land.

== Comments, transitions and what stays hidden

_What does the check decide for a comment, a move through a workflow, and a list that holds things
the caller may not read?_

These calls have no route. They are methods of `Collaboration` (`kit.collaboration(authorised)`),
which asks the same `AccessRules` on every call, with the caller and the access the gate loaded.

*`annotate`* is the action that lets a caller comment on an aggregate without the right to change
it. It is checked like any other action (`AccessRules.require` in `Discussion.comment`):

* It implies `read`, as every action other than `read` does, so a Prohibition of `read` forbids it.
* It is not `modify`, and `modify` does not permit it: a role comments only if its definition
  names `annotate`, or by a direct grant of the action.
* A Prohibition of `annotate` refuses a comment and leaves the thread readable.
* Reading a thread needs `read` on the aggregate, nothing more.

*A comment's audience* is a list of role names; a comment with none is for everyone who may read
the aggregate. A caller sees a comment with an audience when it holds one of those roles on the
aggregate (`AccessRules.roles`): a role granted to it on the tenant or on the aggregate, or a role
of its token that the roles file defines at system level. A direct grant of an action gives no
role name, and a token role named like a tenant role counts for nothing, because token roles are
chosen by the identity provider's administrator, outside the roles file. A reply is
seen only when its parent is. An audience narrows and never grants: the caller must first be able
to read the aggregate. A role named in an audience must be defined in the roles file, at any level
(`AccessRules.defines`, else `UnknownRole`). The how-to is
xref:howto/discussion.adoc#who-may-comment[Who may comment].

*A transition* moves an aggregate along an edge of its workflow (a transition of the workflow
file, from one state to another, with the roles that may make it). The roles on the edge decide
who may make it, not `modify`: a reviewer moves a book to `accepted` without the right to edit it.
`Transitions.transition` checks in this order (a schema that does not import the workflow module
raises `LookupError` before all of them):

. `read` on the aggregate (404 or 403 as in <<check>>).
. No Prohibition of `modify` on the aggregate or the tenant (`AccessRules.prohibits`): it freezes
  the aggregate, its state included (`Forbidden`).
. With a comment that is not blank, no Prohibition of `annotate`. The comment of a transition
  needs no `annotate` right, since the role on the edge stands in for it, but an explicit ban
  still holds (`Forbidden`).
. The aggregate is at the version the caller read (`Conflict`). This comes before everything
  about the workflow, so a caller on stale data is told to read again, not that its move is
  refused.
. The aggregate is under exactly one workflow and holds at most one state (`InvalidBody` if under
  none; `StoredDataInvalid` if under two, or with two stored states).
. The state asked for is a state of the workflow, and the workflow has an edge to it from the
  current state (`Conflict`).
. The caller holds one of the roles on that edge, by the same `AccessRules.roles` as an audience
  (`Forbidden`). The edge is looked up before the role: with no such edge the answer is a
  `Conflict`, whoever asks.
. If the edge needs a comment, one that is not blank is given (`InvalidBody`).

The how-to is xref:howto/workflow.adoc#make-a-transition[Make a transition].

*Hidden things are counted, never named.* A list that would hold what the caller may not read
leaves it out and says how many it left out, in `hidden_count`: no IRI, no class, no slot.

[cols="2,3,3",options="header"]
|===
|Call |Counted in `hidden_count` |Neither listed nor counted
|`referrers` |Every referrer the caller may not read, once each. The count is the same whatever class or slot the call narrows by; a count that followed the narrowing would tell the class and slot of a hidden referrer. A comment that references the resource counts here when the caller does not see it in its thread. |—
|`members` |The members the collection names that the caller may not read. |An aggregate that only meets the collection's rule. The rule is written by whoever may modify the collection, so a count of its hidden matches would tell that caller, slot value by slot value, what it may not read.
|`collections_of` |The collections that hold the resource, by name or by rule, that the caller may not read. |—
|`thread` |— (it has no count) |The comments the caller does not see.
|`delete_cascade` |The members the collection names that the caller may not delete and may not read: the refusal names the ones it may read and counts the others. |An aggregate that only meets the rule and that the caller may not read: it stays, and refuses nothing.
|===

One thing is accepted: a save of a collection is refused unless each member it names is a stored
aggregate of the member class. Whoever may modify a collection can thus learn, by trying member
classes, the class of a hidden aggregate whose IRI it already holds, never its content. The how-to
pages are
xref:howto/reverse-references.adoc#hidden[Referrers the caller may not read] and
xref:howto/reference-collections.adoc#members-and-collections-the-caller-may-not-read[Members and collections the caller may not read].

== Identity: signing in from the browser and from the API

_How do people and programs get a token the API accepts?_

Both are needed: people use a web app, programs and scripts call the API. Zitadel (v4) supports every
flow below; it has no password grant.

[cols="2,3,2",options="header"]
|===
|Who |Flow |Token reaches the API as
|A person in a browser |Authorization code with PKCE, by the web app's *server* (a confidential client; the backend-for-frontend pattern the IETF's guidance for browser apps ranks first). Tokens stay on the server; the browser holds an HTTP-only session cookie. |Bearer token, sent by the web app's server
|A person at a command line |Device authorization flow |Bearer token
|A program (service account) |Private-key JWT, or client credentials |Bearer token
|A script |Not in v1: Zitadel's personal access tokens are opaque, and checking them needs token introspection; a script uses a service account's private-key JWT |—
|===

[mermaid]
....
flowchart LR
    C["browser (via its server),<br/>CLI, program, script"] -->|"get a token"| Z["Zitadel"]
    C -->|"Bearer token"| A["API"]
    A -.->|"published keys"| Z
....

The API checks signature, issuer, audience and expiry against the provider's published keys (cached).
This needs *JWT* access tokens: Zitadel issues opaque ones by default, so each application is set to
the JWT access-token type, and clients request the project audience and roles scopes.
Signing in "through the API" therefore means obtaining a token with one of these flows. Token exchange
(acting on behalf of another user) is not used: Zitadel's support is a first iteration.
