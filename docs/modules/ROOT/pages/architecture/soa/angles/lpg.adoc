= Labelled property graphs
:description: How hard a labelled-property-graph (Neo4j-style) backend behind the same ports would be, what is backend-neutral and what is RDF-specific, and which seams to shape now so an LPG adapter stays an additive change.

== Purpose of the angle

A side question (DEC-14). The product stays triple-store-first.
The angle asks: how hard would a labelled property graph (LPG) backend be, and what must the ports look like now so it can be added later?
It covers layer L1 (mapper, query builder) and layer L2 (store port, transactions).

Deep dives with clone and code reading: neosemantics (n10s, GitNexus-indexed), the linkml-store Neo4j adapter and rdflib-neo4j (both read directly).
Compare xref:architecture/soa/libraries/neomodel.adoc[neomodel], the Neo4j OGM analysed earlier.

*Headline findings.*

. *No Python mapper targets both RDF and LPG.* linkml-store has Neo4j but no RDF store; neomodel and gqlalchemy are LPG-only; every RDF mapper is RDF-only. The only "both models" products are stores: Amazon Neptune runs SPARQL and openCypher/Gremlin, and Neptune Analytics runs openCypher over RDF (since 2024-08, the "OneGraph" research line).
. *The de-facto RDF→LPG mapping is n10s's, and it is lossy by default.* Every RDF corner rdf-persistence cares about needs an explicit encoding choice. The n10s conventions are reusable as a specification for an LPG adapter even if n10s itself is not used.
. *There is no standard RDF↔LPG mapping.* GQL (ISO/IEC 39075:2024) standardises the LPG query language, not the mapping. RDF 1.2 triple terms (Candidate Recommendation 2026-04-07; later status not confirmed) make edge properties expressible in RDF. The RDF 1.2 Interoperability note is a draft and deals with RDF Full↔Basic, not with property graphs.
. *LPG is the easier store for transactions, the harder one for semantics.* Neo4j (Bolt) has real multi-statement ACID transactions, which the SPARQL 1.1 _protocol_ lacks (RDF4J, GraphDB and Stardog add them through vendor APIs; see the xref:architecture/soa/angles/stores.adoc[stores angle]). Named graphs, language tags, custom datatypes, IRIs as identity and open-world multi-valued properties all need encodings. The unit of work and store port port easily; the mapper and query builder carry the cost.
. *Recommendation: do not build an LPG adapter now; shape four seams now.* They cost almost nothing because the RDF design needs them anyway, and they keep an LPG adapter an additive change later.

== Purpose and origin

* *neosemantics (n10s):* a Neo4j Labs server plugin by Jesús Barrasa (Neo4j). It imports RDF, OWL and SKOS into an LPG, exports the LPG as RDF, maps vocabularies, validates with SHACL and runs light inference. Angle: store-side bridge (Cypher procedures inside Neo4j). Fit: L2 import/export path; it does not touch L1.
* *rdflib-neo4j:* Neo4j Labs, same author. An rdflib `Store` that streams triples into Neo4j with the n10s conventions, from Python, without the plugin. Angle: bulk loader. Fit: L2 loader only.
* *linkml-store:* the LinkML org (Chris Mungall et al.). A document and collection API over many backends (DuckDB, MongoDB, Solr, ChromaDB, Neo4j, …) driven by a LinkML schema. Angle: schema-first data access for AI and data-science pipelines. Fit: L1-ish, but a collection API, not a Data Mapper with a unit of work. It has no RDF or SPARQL backend (`src/linkml_store/api/stores/`), though it can still _export_ Turtle through its format utilities (`utils/format_utils.py:37`).

== Deep-dive findings

=== neosemantics (n10s)

*Architecture.* Cypher procedures grouped by concern under `src/main/java/n10s/`: mapping config (`graphconfig/GraphConfig.java`), RDF load/delete/export/stream, a named-graph mode (`quadrdf/`), vocabulary mappings, ontology and SKOS importers, SHACL compiled to Cypher checks, inference, and an HTTP endpoint that returns RDF.
The core is an rdf4j `RDFHandler` (`RDFToLPGStatementProcessor.java`) that buffers labels, properties and relationships per subject and flushes them.
Commit `d5cfd2a` (v2025.06.1, Neo4j 2025.06.2).

*How each RDF corner is mapped.*

[cols="2,4,3,2",options="header"]
|===
|RDF feature |n10s encoding |Evidence |Loss
|Resource identity (IRI) |Node `:Resource +{uri}+` with a uniqueness constraint, required before import |`CommonProcedures.java:41-65` |none
|Vocabulary IRIs |SHORTEN (`ns0__name`), SHORTEN_STRICT, IGNORE (local name), MAP (custom mapping), KEEP (full IRI) |`GraphConfig.java:30-34, 229-255` |IGNORE and MAP lose the namespace
|`rdf:type` |Labels (default), `:Class` nodes with `rdf__type` relationships, or both |`GraphConfig.java:43-49, 271-280` |none in node mode
|Multi-valued literals |OVERWRITE (default, keeps the last value) or ARRAY; a REIFY mode is commented out |`GraphConfig.java:36-41, 92-93` |*default is lossy*; arrays add an order RDF does not have
|Language tags |`"text@en"` string if `keepLangTag`, otherwise dropped; optional language filter |`RDFToLPGStatementProcessor.java:101-113` |*lossy by default*; a string hack
|Datatypes |xsd integers → long, decimals → double, boolean, dateTime, WKT → point; custom types as `"value^^<dt>"` strings |`RDFToLPGStatementProcessor.java:94-140` |`xsd:decimal` precision lost
|Named graphs |Separate quad procedures: node key becomes `+{uri, graphUri}+`, so one resource in two graphs is two nodes |`quadrdf/RDFQuadDirectStatementLoader.java:61-87` |identity model changes
|Blank nodes |Skolemised as `bnode://<id>` |`RDFToLPGStatementProcessor.java:412-415` |none
|RDF-star / edge properties |Import: annotated object triples become relationship properties; annotated datatype statements are ignored. Export: relationship properties as RDF-star |`RDFToLPGStatementProcessor.java:405-420`; `RDFExportProcedures.java:49` |partial on import
|Deletes |`n10s.rdf.delete.*` removes the LPG image of a triple set |`rdf/delete/DirectStatementDeleter.java` |—
|SPARQL |*None* (no SPARQL endpoint over Neo4j) |grep `sparql` in `src/main` |—
|===

*Scores (as a bridge, not a mapper):* C1 3 · C2 3 · C3 3 · C4 2 (plugin version-locked to Neo4j, `pom.xml:37`) · C5 5 · C6 2 · C7 0 · C8 4 · C9 3 · C10 3 (Labs status).

*Verdict: borrow ideas.* Use its mapping config as the specification of an LPG encoding (identity, vocabulary shortening, multi-values, language tags, datatypes, quad mode).
*Not a unit-of-work flush.* n10s opens its own inner transactions: the loader commits every `commitSize` triples (default 25,000; `rdf/load/DirectStatementLoader.java:215-243`, `graphconfig/RDFParserConfig.java:14,37-39`) and the deleter does the same (`rdf/delete/DirectStatementDeleter.java:241`). So `n10s.rdf.delete.inline` and `n10s.rdf.import.inline` are not atomic together, a large payload commits partially, and with `abortOnError=false` a failed batch is logged as "triples lost". The procedures are built for bulk ingestion. Use n10s only for one-way projections (a rebuildable read replica or export), never as the write path.

=== linkml-store Neo4j adapter

The only LinkML-driven LPG mapper (625 LOC, commit `f19c1d9`).

* *Model:* a collection is a node collection or an edge collection (`graphs/graph_map.py`: node projection with `id` and `category`; edge projection with subject, predicate, object). Labels come from each object's `category`.
* *Writes:* one `CREATE` per object; edges `MATCH s, o CREATE (s)-[r:pred]->(o)` with a delete policy (cascade, error, stub) for dangling ends.
* *Transactions:* none. `commit()` is a no-op ("Neo4j uses auto-commit", `neo4j_database.py:66-68`). `apply_patches` reloads the whole collection and replaces it (`api/collection.py:1187-1202`), so patching is O(collection), not O(change).
* *Quality:* query values are interpolated into Cypher (`neo4j_collection.py:215`, injection risk). The JSON import builds a relationship query that is not an f-string (`neo4j_database.py:150`), so it cannot work. No IRIs, language tags or named graphs: it maps LinkML JSON objects, not RDF.

*Scores:* C1 2 · C2 2 · C3 3 · C4 3 · C5 3 · C6 3 · C7 0 · C8 2 · C9 2 · C10 2.

*Verdict: borrow ideas.* The node/edge projection split is the right minimal vocabulary for "which LinkML classes become nodes and which become relationships with properties". Avoid as a dependency.

=== rdflib-neo4j

An rdflib `Store` (`Neo4jStore.py:18`) that buffers triples and flushes batched `UNWIND … MERGE` Cypher with the n10s conventions.
`remove()` raises `NotImplementedError("This is a streamer …")` (`Neo4jStore.py:134-135`) and there is no `triples()`: a write-only bulk loader.
It cannot sit behind a read/write store port.

*Verdict: integrate only as an optional bulk-export tool.*

== Backend-neutral or RDF-specific

Parts as in xref:architecture/soa/building-blocks.adoc[building blocks] L1 and L2.
Difficulty is the effort to add an LPG (Cypher over Bolt) adapter later, assuming the seams below exist.

[cols="3,2,4,1",options="header"]
|===
|Part |Neutral or RDF-specific |What an LPG adapter needs |Difficulty
|Domain classes (LinkML → Pydantic) |neutral |nothing |low
|Mapper metadata (`class_uri`, `slot_uri`, range, multivalued, inverse) |neutral metadata, RDF rendering |A name policy IRI → label, property key, relationship type (n10s SHORTEN/MAP), and a projection: which classes are nodes, which are relationships (linkml-store idea) |medium
|Identity (IRI) |neutral if the key is an opaque IRI string |`uri` property plus a uniqueness constraint per node |low
|Identity map |neutral (keyed by IRI) |nothing |low
|Unit of work and change-set |neutral *if* the unit of work produces an abstract change-set, not SPARQL strings |A Cypher renderer of the change-set, run in one Bolt transaction (stronger than the SPARQL 1.1 protocol; vendor RDF stores add transactions too) |low–medium
|Optimistic concurrency (P5) |neutral concept |`WHERE n.version = $v` on `MATCH` |low
|Typed literals |mostly neutral |xsd → Neo4j types; decimals and custom datatypes need a string encoding |medium
|Language-tagged literals |RDF-specific |An encoding choice: `"text@en"` (n10s), per-language keys (`+title__en+`), or a side node; none is natural |medium, and query semantics are lossy
|Multi-valued slots |neutral |Homogeneous arrays for literals (order is LPG-only); several relationships for object slots |low
|Edge properties, qualified relations (R7) |LPG-native, RDF-hard |Native relationship properties |low on LPG
|Named graphs (P6) |RDF-specific |One of: a database per graph (Neo4j multi-db), the graph IRI in the key (n10s quad mode, changes identity), or a label or property as scope; each changes semantics |high
|Query builder |neutral only as an AST with SPARQL as one renderer |A Cypher renderer of the same AST (neomodel's `QueryAST`, `match.py:520`, is the model) |medium; high if the builder emits SPARQL text directly
|Raw SPARQL, CONSTRUCT reads |RDF-specific |none: keep them on a separate RDF-only port |n.a.
|JSON-LD in and out |neutral (from domain objects and the generated `@context`) |nothing |low
|SHACL validation |neutral if run on domain objects or graphs before flush |nothing (n10s also has in-database SHACL) |low
|Authorization scope (DEC-8) |graph scope is RDF-specific |The scope as an abstract partition id; LPG maps it to a database or label (Neo4j Enterprise fine-grained RBAC, per Neo4j documentation, not checked) |medium
|Store port (capabilities, T7) |neutral |Report multi-statement transactions, named graphs absent or emulated, query language Cypher |low
|===

*Overall estimate.* A usable Neo4j adapter (CRUD, relationships, identity, unit of work in one transaction, simple filters) is *medium* effort if the seams exist.
Full RDF fidelity (named graphs, language tags with SPARQL-like semantics, round-trip to RDF) is *high* and probably not worth it.
Neptune is the cheap route to "both models": keep the SPARQL adapter and read the same data with openCypher there. No adapter work, but AWS lock-in.

=== Four seams to shape now

They are cheap because the RDF design needs them anyway.

. *Abstract change-set.* The unit of work emits, per subject, slot adds and removes and a version check. The store adapter, not the unit of work, writes the SPARQL Update text.
. *Query AST with renderers.* The query builder compiles to an AST; SPARQL is the only renderer shipped.
. *Raw SPARQL on its own port.* A separate SPARQL port, not part of `Repository[T]`, so the repository API never promises SPARQL.
. *Scopes and declared capabilities.* "Named graph" appears in the public API as a scope or partition, which the RDF adapter maps to a graph IRI. The store port declares its capabilities (transactions, named graphs, query language). This also serves DEC-8 (ACL-agnostic scopes).

Do not build now: a Cypher renderer, a property-name policy, LPG schema install, any Gremlin path (YAGNI until a project asks).

== Patterns catalogue

[cols="3,3,3",options="header"]
|===
|Pattern |Where seen |Use for rdf-persistence
|IRI as unique node property plus a database constraint |n10s `CommonProcedures.java:41-65`; rdflib-neo4j |LPG identity
|Configurable vocabulary-IRI shortening or mapping |n10s `GraphConfig` `handleVocabUris` |Name policy for labels and keys
|Type as label vs type as node |n10s `handleRDFTypes` |Polymorphism on LPG (labels = class and ancestors, as neomodel does)
|Node vs edge projection of classes |linkml-store `graph_map.py` |Which LinkML classes become relationships with properties

|Edge properties ↔ RDF-star |n10s `RDFExportProcedures.java:49` |Round-trip of qualified relations
|RDF change-set as delete + insert payloads (not atomic: n10s commits in its own batches) |n10s `rdf.delete.inline` + `rdf.import.inline` |One-way LPG projection
|One store, two query languages over one graph |Neptune Analytics, OneGraph |"Both models" without a second adapter
|Query AST → language renderer |neomodel `match.py:520` |SPARQL now, Cypher later
|===

*Features from this angle* (v4 ids):

* B8 a backend-neutral change-set: the unit of work yields an abstract change-set and each store adapter renders it (SPARQL Update, Cypher, n10s RDF payload).
* PG1 a query AST with pluggable renderers; SPARQL is one renderer.
* T7 (extended) a store capability descriptor that also declares named-graph support, query languages and edge-property support.
* PG2 an LPG projection config per LinkML class and slot: node or relationship, label and key naming from IRIs, language-tag and multi-value encoding (n10s-style).
* PG3 edge-property mapping: a LinkML class marked as a relationship with properties maps to an LPG edge, and to RDF 1.2 triple terms or an n-ary node on RDF (relates to R7).
* PG4 a scope abstraction for partitions: named graph ↔ database, label or property partition, used by both persistence and authorization (relates to P6 and DEC-8).

== Options for an LPG backend

These are LPG options, not the system variants of xref:architecture/soa/variants.adoc[architecture variants].

[cols="2,4,3",options="header"]
|===
|Option |Shape |Cost
|*RDF only* (baseline) |No change; the four seams are internal hygiene |none
|*Neptune "both models"* |SPARQL adapter as-is against Neptune; analysts use openCypher or Gremlin on the same data; authorization stays at the service (DEC-8) |AWS lock-in
|*Neo4j via n10s* |No SPARQL. The change-set is serialised as Turtle and applied with n10s procedures, batch-committed (not atomic); reads through a Cypher renderer; n10s config pinned per project |Needs the plugin; language tags and named graphs as n10s encodes them; no atomic writes: fit for a projection, not for the system of record
|*Native LPG adapter* |Cypher via the `neo4j` driver; Memgraph, FalkorDB, AGE and LadybugDB speak openCypher-like dialects. Gremlin only if a JanusGraph, Cosmos or Neptune-Gremlin target appears |Cleanest LPG model, highest effort
|===

At L0, LinkML has no PG-schema or Cypher generator. Constraints (unique `uri`, indexes) would need a small new generator (compare neomodel `install_labels`; see xref:architecture/soa/angles/codegen.adoc[code generation]).

== Open questions

. Is there a real project need for Neo4j or LPG, or is "analysts want Cypher" enough to choose Neptune instead of building an adapter?
. Must LPG data round-trip back to RDF losslessly (then named graphs and language tags force high effort), or is LPG a one-way projection for analytics (then n10s or rdflib-neo4j export suffices)?
. Does the domain model need edge properties (qualified relations)? If so, decide the RDF encoding (RDF 1.2 triple terms or an n-ary class) independently of LPG.

*Not checked.* Exact licences of the Neo4j driver, Memgraph and FalkorDB (GitHub reports "Other"); whether n10s installs on Neo4j Aura; Stardog and GraphDB LPG features beyond RDF-star; OneGraph in Neptune Database (only the 2024 Analytics announcement and paper were found); the GQL text itself. No code was run.

== Final verdict

*Verdict: ideas.* n10s: its mapping config is the specification for any future LPG encoding, and it is an optional one-way export to Neo4j. linkml-store Neo4j adapter: ideas only (node/edge projection, neutral `Query` object). rdflib-neo4j: optional append-only bulk loader. No LPG adapter now.

. *There is no standard RDF↔LPG mapping, and every practical one is lossy* (language tags, named graphs, `xsd:decimal`, multi-valued literals under the n10s default). Treat Neo4j as a one-way projection unless a project proves it needs round-trips.
. *n10s writes are not transactional with the caller* (independent 25k-triple batches), and rdflib-neo4j cannot delete. Neither can be the write path of a system of record.
. *LPG readiness costs only four seams the RDF design needs anyway:* a backend-neutral change-set (B8), a query AST (PG1), raw SPARQL on its own port, partitions as scopes plus a capability descriptor (PG4, T7). Keep SPARQL out of `Repository[T]` and the option stays open.
