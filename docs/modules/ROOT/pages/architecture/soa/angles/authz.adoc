= Identity and authorization (L3)
:description: How identity and access control are done over RDF and graph data today, which engines to borrow, and where an ACL-agnostic rdf-persistence puts its enforcement seam.

== Purpose of the angle

DEC-8 says authorization is never reinvented: we survey, borrow and integrate.
The persistence layer must stay ACL-agnostic. It must work behind an authorizing proxy, or with a pluggable policy enforcement point (PEP).
The preferred policy style is declarative, SPARQL-like and data-centric.

This page answers four questions:
which identity providers (IdPs), policy engines (PDPs) and store-native mechanisms exist;
at which granularity each works (graph, resource, triple);
where the PEP can sit;
and which coherent stacks follow for the architecture variants.

Four candidates were deep-dived (clone, GitNexus, code): Fluree DB v4, Community Solid Server, Apache Jena `jena-fuseki-access`, OpenFGA.
semantic.works sparql-parser is compared only; see xref:architecture/soa/libraries/semantic-works.adoc[semantic.works].

== Key findings

* *No standard exists for triple-level RDF authorization.* Every store-native mechanism is vendor-specific. Solid WAC/ACP is a community spec, but it works at document level.
* *Graph level is the only portable granularity.* Every store can enforce it the same way: restrict the dataset (`FROM` / `FROM NAMED`, or a filtered dataset view).
* *Fluree v4 is the closest match to DEC-8.* Policies are RDF data, conditions can be SPARQL ASK, enforcement is triple-level, identity comes from OIDC. The catch is the licence: BUSL-1.1, not OSI open source.
* *No generic PDP knows RDF.* Zanzibar engines (OpenFGA, SpiceDB, Keto, Permify) fit graph- and resource-level access. Cerbos and OPA return list-filter ASTs, but their adapters target SQL and ORMs only. *A SPARQL adapter for those ASTs exists nowhere.* That translator is the one piece we might build; it is not an engine.
* *IdPs give identity and coarse roles only.* Zitadel, Keycloak, Authentik and Ory know nothing of graphs. Their claims must feed a PDP or map to graph tokens or policy classes.
* *For rdf-persistence:* one port, `AccessScope` / `PolicyEnforcementPoint`. It narrows the dataset per request and, optionally, checks a write changeset before commit.

== Deep-dive findings

=== Fluree DB v4 — policy engine

*How it works.* Policies are JSON-LD nodes (`@type f:AccessPolicy`) stored in the ledger.
Each request selects policies by identity → `f:policyClass`.
A policy targets flakes (triples) by property, class (with RDFS entailment) or subject.
It allows them statically (`f:allow`) or when a condition query (`f:query`) succeeds.
Conditions can be JSON-LD, SPARQL ASK/SELECT or read-only Cypher, with `$this`, `$identity`, `$value` and `$op` pre-bound.
Enforcement runs inside the scan operators, so results come back already filtered; there is no query rewriting.

Evidence:

* Combining algorithm (required gates, deny-overrides, allow-overrides, `default_allow` fallback): `fluree-db-policy/src/lib.rs:1-40`, `evaluate.rs:309-398, 459-522, 679-770`. Code matches the docs.
* Read enforcement, confirmed with GitNexus: `QueryPolicyEnforcer::filter_flakes_for_graph` (`enforcer.rs:104`) is called from the binary index scan (`binary_scan.rs:1082`). History, commit contents and JSON-LD hydration are filtered too. Counts and aggregates therefore see filtered data (tested: `fluree-db-api/tests/it_policy_indexed.rs:375`, COUNT over a join under a restricted view).
* Fast path for predicates no policy covers: `classify_view_predicate` (`enforcer.rs:71`, called from `fast_path_common.rs:3982`).
* Caching of `f:query` results is a TODO in code (`enforcer.rs:37-44`), so cost is per flake times condition. Subject-class lookups are cached.
* Write enforcement per flake at staging, confirmed: `fluree-db-transact/src/stage.rs:2861` (`enforce_modify_policy_per_flake`).
* OIDC: RS256 JWT with JWKS, `fluree-db-credential/src/oidc_jwt.rs:1-33`; claims `fluree.identity`, `fluree.policy.class`, ledger scopes.
* Request headers `fluree-identity`, `fluree-policy-class`, `fluree-policy`, …: `fluree-db-server/src/extract/headers.rs:199-291`. A *trusted application credential* lets a backend choose identity and policy class per request.
* Python governed handle: `ledger.with_policy(...)`; a query that names its own policy raises `InvalidRequestError` (`_fluree.pyi:34-118`, README).
* SPARQL Query, Update and Graph Store Protocol on Fluree's own paths (`/v1/fluree/query/<ledger>`), `docs/api/overview.md:68-96`.
* *A policy cannot target a named graph directly.* "Policies apply per-flake, regardless of which named graph" (`docs/security/policy-in-queries.md:220`); grep for `onGraph` finds nothing. Enforcement is graph-aware, though: classes are resolved in the flake's own graph. Per-graph *defaults* exist through `f:graphOverrides` (see the xref:architecture/soa/angles/stores.adoc[stores angle]). Otherwise graph isolation comes from ledger scopes or a condition that reads an ACL graph.
* SPARQL conditions, confirmed in code: dispatch at `fluree-db-query/src/policy/executor.rs:224-225`, `evaluate_sparql` at l.459-465.
* Deletes: v4 cascades only edge annotations (`docs/transactions/retractions.md:198-208`); there is no general cascade delete.

*Verdict: integrate as one store option, and borrow ideas in every case.*
Borrow the vocabulary shape (`onProperty/onClass/onSubject` plus SPARQL ASK with `$this/$identity/$value/$op`), the combining algorithm, default deny and the non-widenable governed handle.
Internal use, and a deployment a client runs for its own applications, appear permitted under BUSL-1.1. A commercial offering where third parties create databases or define their own schemas, ontologies or data models on Fluree is a "Database Service" (`LICENSE:12-30`), so a Meaningfy product where customers model their own data needs a legal reading per product.

=== Community Solid Server — WAC and ACP

*How it works.* A chain of `PermissionReader`s (8 implementations: WebAcl, Acp, Owner, ParentContainer, PathBased, AllStatic, AuthAuxiliary, Union) feeds `PermissionBasedAuthorizer`, called from `AuthorizingHttpHandler` (`src/server/AuthorizingHttpHandler.ts:50`).

* WAC modes and the effective-ACL walk up containers: `src/authorization/WebAclReader.ts`; agent, agent-class and group checkers in `access/`.
* ACP: `src/authorization/AcpReader.ts:39-160` via `@solid/access-control-policy`.
* Required modes per operation: `permissions/SparqlUpdateModesExtractor.ts`, `N3PatchModesExtractor.ts`. SPARQL Update is accepted only as a PATCH on one document; there is no dataset-wide query endpoint.
* One named graph per document in the SPARQL backend: `src/storage/accessors/SparqlDataAccessor.ts:47-225`. So WAC/ACP over SPARQL is *graph-level ACL with policies as RDF*.
* Identity: Solid-OIDC with DPoP tokens; the agent is a WebID.

Scores: C1 3 · C2 5 · C3 3 · C4 2 · C5 4 · C6 4 · C7 2 · C8 4 · C9 4 · C10 3.

*Verdict: borrow ideas.* Use WAC/ACP as a candidate standard vocabulary for graph-level grants. Use the reader chain as the shape of our PEP. Do not adopt the server: it is a resource server, not a dataset ACL.
See also xref:architecture/soa/angles/service.adoc[the service angle].

=== Apache Jena Fuseki — `jena-fuseki-access`

*How it works.* A security context is a set of visible graph names plus a default-graph flag (`SecurityContextView.java`).
On TDB it pushes a quad filter down to the index (`GraphFilterTDB2.java:38-62`); otherwise it wraps the dataset in `DatasetGraphFilteredView`.
Policy configuration is RDF (assembler vocabulary, `VocabSecurity.java:39-44`).

* Updates on access-controlled datasets are rejected (`AccessCtl_DenyUpdate.java`): *read-only only*.
* Denied operations answer HTTP 400 "Not supported" (`AccessCtl_Deny.java:43`, `AccessCtl_AllowGET.java:71-73`), not 403. Clients that expect 403 must handle this.
* User resolution is pluggable in code (`DataAccessCtl.java:60-66`), which the docs do not mention. OIDC would need a custom Java servlet filter (not checked against Fuseki 5 modules or Jetty 12 OIDC support).

Scores: C1 2 · C2 4 · C3 2 · C4 3 · C5 5 · C6 3 · C7 4 · C8 5 · C9 3 · C10 4.

*Verdict: integrate as a read-side graph-level option; borrow the dataset-view idea.*
It is the clearest open-source case of "authorization = restrict the dataset", applied below the query engine so `GRAPH ?g` cannot leak.
Our in-process adapter (rdflib, pyoxigraph) can copy it with a filtered `Dataset` view.

=== OpenFGA — Zanzibar PDP

*How it works.* `ListObjects` runs a reverse expansion over relation tuples (`pkg/server/commands/list_objects.go:63-246`, `reverseexpand/reverse_expand_weighted.go:457-503`) with a default cap of 1,000 results and a 3 s deadline (`pkg/server/config/config.go:27-28`).
Conditions use CEL (`go.mod:19`, `internal/condition/`).
Tuples live in their own store (memory, Postgres, MySQL, SQLite): they must be kept in sync with the RDF graph.

*Mapping to RDF.* Model a named graph as type `graph` and an aggregate root as type `resource`.
`ListObjects(user:alice, reader, graph)` returns the graph IRIs to inject as `FROM` / `FROM NAMED` or `VALUES ?g`.
Triple-level rules fit badly: they need one tuple per (subject, predicate).

Scores: C1 4 · C2 5 · C3 4 · C4 3 · C5 n.a. · C6 2 · C7 n.a. · C8 5 · C9 4 · C10 4.

*Verdict: integrate* as the graph- and resource-level PDP for store-agnostic variants. Keep tuples in sync from domain events (L6).

=== Desk-only notes

* *GraphDB FGAC:* ordered rules on statement, clear-graph, plugin and system scopes; first match wins; *default allow*; roles from OpenID `roles_claim` (JSONPath). Strongest commercial triple-level option behind standard SPARQL.
* *Stardog:* unreadable graphs silently drop from the dataset; writes to unauthorized graphs fail all-or-nothing.
* *AllegroGraph:* filtered triples "appear as if they weren't in the store"; writes to them error.
* *Virtuoso:* identity is a SQL user; no IdP claim mapping found in docs.
* *Cerbos `PlanResources`:* returns `ALWAYS_ALLOWED` / `ALWAYS_DENIED` / `CONDITIONAL` plus an AST. No SPARQL adapter exists.
* *OPA:* partial evaluation to SQL, UCAST or Lucene. UCAST would be the input of a SPARQL translator.
* *pycasbin:* `keyMatch2` / `regexMatch` over graph IRIs gives cheap graph-level RBAC with no extra service.
* *Keycloak Authorization Services:* resource/scope/policy and UMA; duplicates Zanzibar, no list filter over external data.

=== Purpose and origin

* *Fluree DB v4.* Fluree PBC (Winston-Salem, NC). Began as a Clojure ledger graph database (v1–v3); v4 is a Rust rewrite (v4.0.0 on 2026-04-22; Python wheel `fluree` first on PyPI 2026-10-08). Angle: data-centric security and provenance; policies, identities and history live in the ledger with the data. Fits L2 + L3 (+ L4 HTTP, L6 head events) in V3. A database we would run, not a library we build on.
* *Community Solid Server.* IDLab (imec – Ghent University), commissioned by Inrupt as the modular Solid reference server (from project history, not stated in the repo). Angle: personal data pods, one document = one resource with its own ACL. Idea source for L3 (reader pipeline, WAC/ACP, `WAC-Allow`) and L4/L6; serves pod products only.
* *OpenFGA.* Built at Auth0 (Okta) after Google's Zanzibar paper; now a CNCF project. Angle: relationship-based authorization as a service, store-agnostic. Fits the L3 PDP in V1 and V5; knows nothing of RDF, so tuples must be synced (AZ28).
* *Jena `jena-fuseki-access`.* Andy Seaborne, Apache Jena (ASF; Jena began at HP Labs). Angle: publishing, where each user sees a fixed set of named graphs, read-only. Fits the V5 read path and is the reference design for AZ1 in our in-process adapter.
* Desk-scanned origins worth noting: Casbin was created by Yang Luo (2017) and is now Apache Casbin (ASF). ODRL-Evaluator comes from the `odrl-force` org (repo created 2024-12; main contributors Slabbinck and Herweg, GitHub `woutslabbinck` and `jvherweg`, IDLab Ghent / SolidLab — affiliation inferred, not stated in the repo).

*Rule.* Rewriting (P-B to P-E) keeps pagination and counts correct; post-filtering does not.
If end users or the UI can send free SPARQL, the PEP *must* be store-native (P-A) or a rewriting proxy (P-B).
P-C, P-D and P-E are safe only for queries rdf-persistence generates.

== How it plugs into rdf-persistence

* *Identity, in every variant:* the IdP issues OIDC tokens; a FastAPI dependency validates the JWT (Authlib or PyJWT plus JWKS) and builds a `Principal(sub, org, roles, raw_claims)`.
* *Port (proposal):* an `AccessScope` value object (`readable_graphs`, `writable_graphs`, `forward_headers`, `principal_ref`; `None` means "the store or proxy decides") and a `PolicyEnforcementPoint` with `scope_for(principal, action, aggregate_type)` and `authorize_write(principal, changeset)`.
* *Adapters:* `PassThroughPEP` (headers only: sparql-parser, Fluree, GraphDB), `GraphListPEP(pdp)` (OpenFGA, SpiceDB, Casbin → `FROM` graphs), later `PlanPEP` (Cerbos, OPA → SPARQL `FILTER`).
* Scope is applied structurally (dataset clause or `VALUES ?g`), never by string splicing. The unit of work calls `authorize_write` with the computed delta.
* LinkML annotations can generate *configuration* for an existing engine (graph placement, OpenFGA/Cerbos/Fluree artefacts, per-role projections). See xref:architecture/soa/angles/codegen.adoc[the code-generation angle].

|V3 Fluree-native |Zitadel |Fluree policies (RDF, SPARQL ASK) |Store-native; backend holds a trusted app credential and sends identity and policy class per request, or embedded `with_policy` |triple |Best DEC-8 fit; safe for free UI SPARQL. Risks: BUSL-1.1, one vendor, vocabulary lock-in, per-flake cost.
|V4 Commercial triple-level |Zitadel → `roles_claim` |GraphDB FGAC |Store-native |quad |When a client already licenses GraphDB Enterprise.
|V5 Graph-direct reads |Zitadel |Store or proxy policy |Read path through Jena `jena-fuseki-access`, sparql-parser or Fluree |graph (triple with Fluree) |The read endpoint must enforce policy itself, because clients send their own SPARQL.
|===

Reuse shortlist:

* *Adopt:* Zitadel with standard OIDC validation (Authlib or PyJWT); Keycloak if AGPL is unwanted.
* *Integrate:* Fluree v4 (V3), OpenFGA or SpiceDB (V1), pycasbin (V1 lite), GraphDB FGAC (V4), `jena-fuseki-access` for read-only publishing (V5).
* *Borrow ideas:* sparql-parser, WAC/ACP vocabularies, Fluree's vocabulary and combining algorithm, the plan-AST to SPARQL translation.
* *Avoid:* Oso, any sub-200★ SPARQL authz proxy as a dependency, our own policy language.

Features from this angle in xref:architecture/soa/feature-taxonomy.adoc[taxonomy v4]: AZ1 access-scope port, AZ5 write authorization on the changeset, AZ8 triple-level targeting, AZ9 SPARQL-condition policies, AZ10 policy as data, AZ4 list-filter integration, AZ11 combining algorithm and default deny, AZ17 non-widenable session, AZ18 claim → policy selector, AZ28 tuple sync from domain events, AZ25 read masking, AZ26 policy-aware explain, AZ27 decision audit trail.

Round-4 proposals, now v4 ids:

* AZ30: class resolution per graph: a policy that targets a class uses the type triples of the flake's own graph, not a union (Fluree `enforcer.rs:104`);
* AZ31: policy inheritance down containers or a graph hierarchy: the nearest ancestor's policy applies (CSS `WebAclReader`, WAC effective ACL);
* AZ32: skip the per-triple check for predicates that no policy covers (Fluree `classify_view_predicate`);
* AZ33: answer 404 instead of 403 for out-of-scope graphs, so a denial does not reveal that the data exists (Fluree `docs/api/overview.md:288`);
* AZ35: a policy-filter equivalence test: for every generated query family (page items, count, single item, nested sub-queries), a restricted caller gets the same totals and rows as the same query run directly on the restricted dataset. It makes AZ2 checkable (seen as a gap in rdfproxy, see xref:architecture/soa/libraries/rdfproxy.adoc[rdfproxy]).

== Open questions

. Is BUSL-1.1 acceptable for Meaningfy deliveries? This decides V3.
. Will the UI send free SPARQL? If yes, only V3, V4 or V2 are safe; V1 needs a proxy in front.
. Is graph-per-tenant enough, or is triple level truly required (store-specific only)?
. Should policies be generated from the LinkML model?
. Is Zitadel's AGPL acceptable as a deployed service, or is Keycloak the default?
. Is a Cerbos-plan or OPA-UCAST → SPARQL translator worth building, or are graph lists (P-D) enough?
. In V3, are Fluree's per-graph defaults (`f:graphOverrides`) plus ledger scopes enough for graph isolation, given that policies cannot target a graph?
. Do clients of a Jena access-controlled endpoint need to map its 400 "Not supported" to 403?

*Not checked:* closed stores from docs only; Keto reverse lookup, Permify and Topaz not verified in code; nothing was run.

== Final verdict

*Fluree DB v4 policies: integrate* (V3 only), ideas everywhere. *Community Solid Server: ideas.* *OpenFGA: integrate* (V1, V5). *Jena `jena-fuseki-access`: integrate* (V5 read path).

. *Pick the granularity first, then the variant.* Graph-level access is portable (any store with OpenFGA or pycasbin and our scope port, or Jena access for reads). Triple-level access exists only store-native (Fluree, GraphDB) and locks the policy into that vendor.
. *Free SPARQL from the UI changes everything.* Our in-process enforcement port protects only the queries rdf-persistence generates. If any client can send its own SPARQL, enforcement must be in the store (Fluree, GraphDB, Jena access) or in a rewriting proxy (sparql-parser).
. *Identity must reach the enforcement point unforgeably.* For Fluree, use a policy-authority credential plus per-request identity; for a proxy, strip client-sent internal headers at the edge (AZ36); for OpenFGA, keep the tuples synced from domain events (AZ28). Otherwise the policies silently stop applying.
