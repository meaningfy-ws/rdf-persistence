= DDD boundaries and transactions
:description: How DDD aggregates, transaction boundaries and bounded contexts map onto an RDF graph and a SPARQL store, and how thin the unit of work for rdf-persistence can be.

== Purpose of the angle

This angle covers layer L1 (domain and persistence), with consequences for L0 (how boundaries are declared in LinkML), L2 (what the store can make atomic), L4 (ETag, nested writes) and L6 (domain events, outbox).
It answers the developer's question (DEC-13): which classes depend on each other, which change together in one transaction, which can change independently through a message or a separate transaction? SQLAlchemy handles transactions across many tables. Do we need a Unit of Work and the other cosmic-python patterns, or is there something better?

Deep dives with clone, GitNexus index and code reading: SQLAlchemy 2.x, Spring Data JDBC, Ecto, cosmic-python, plus the LinkML metamodel (`SchemaView.is_inlined`, `meta.yaml`).
Hibernate, Django, Prisma, Marten, Axon, Eventuous and pyeventsourcing are desk-only (public docs).

*Headline findings.*

. *Most of SQLAlchemy's Unit of Work is not needed for RDF.* Its hardest part, the topological sort of flush actions (`orm/unitofwork.py:390-466`), exists because foreign-key constraints require parent rows before child rows (reverse order for deletes), and because parent keys, often generated by the database, must be copied into child foreign keys (`orm/dependency.py:616-640`). Client-assigned keys still need the order in SQL. RDF has neither constraint: IRIs are minted on the client, triples are a set, order inside one update does not matter. What remains is small: identity map, snapshot diff, cascades along composition, a version check, `commit()`.
. *Portable SPARQL has no flush separate from commit.* SQLAlchemy flushes many times inside one database transaction (`session.py:4577-4680`). Over plain SPARQL 1.1 every request is its own transaction, so flush and commit are one step and autoflush is impossible.
. *Spring Data JDBC is the closest model to copy:* one repository per aggregate root, whole-aggregate save, version on the root only, references to other aggregates by id, no lazy loading. In RDF that is one `+DELETE … INSERT … WHERE+` per commit.
. *Ecto shows the commit as a value.* An `Ecto.Multi` can be inspected and unit-tested without a database. For us the commit becomes a pure change set that compiles to one SPARQL Update and doubles as the event delta and the dry-run preview.
. *The DDD rules hold in RDF for modelling reasons, not technical ones.* One SPARQL Update can change several aggregates atomically at no extra cost, but with a larger conflict surface: one stale guard aborts the whole commit, and requests grow. "One aggregate per transaction" is about contention and coupling, so enforce it by *policy* (strict / warn / allow).
. *New: several guarded operations in one request are not all-or-nothing.* A guard that matches nothing skips only its own operation; the next one still runs. An all-or-nothing commit needs *one single guarded operation* whose WHERE joins every guard, with ground delete and insert templates. No library implements this yet; it follows from SPARQL 1.1 Update semantics and is untested on real stores.
. *LinkML has no composition construct.* `identifier` separates entities from value objects; `inlined` and `shared` hint at ownership, but `inlined` is serialization-only by its own definition (`meta.yaml:1783-1800`), and `tree_root` is a document container, not an aggregate root (`meta.yaml:1298-1311`). Boundaries need an annotation convention, ideally sourced from UML composition, plus generation-time checks.

== Deep-dive findings

=== SQLAlchemy 2.x — session and unit of work

*Purpose and origin.* Built by Mike Bayer since 2005 as a SQL toolkit plus a Data Mapper ORM modelled on Fowler's _PoEAA_. Design angle: database-first Data Mapper with an implicit UoW. Fit: L1 benchmark for UoW mechanics and developer experience, not a dependency.

* `Session` owns a weak identity map plus `_new` and `_deleted` (`session.py:1817-1826`). `begin_nested()` gives savepoints (`:2018`); `expire_on_commit=True` by default (`:1549`).
* `Session._flush` (`session.py:4577`) collects new, dirty and deleted states, detects orphans and runs a `UOWTransaction` (`unitofwork.py:155-487`): presort to a fixpoint, find cycles, topological sort (`:390-466`).
* Dependency processors (`dependency.py:336, 645, 987`) exist to copy primary keys into foreign keys in the right order.
* Optimistic concurrency: `version_id_col`; a row-count mismatch raises `StaleDataError` (`persistence.py:963-969`). *If the driver reports no row count, SQLAlchemy only warns that "versioning cannot be verified"* (`persistence.py:971-975`) — the exact analogue of SPARQL Update, which returns no match count.
* Cascades: `save-update, merge` by default; `delete`, `delete-orphan` opt-in (`util.py:189-250`).
* Implicit tracking hides when SQL runs: autoflush before queries (`session.py:3192`), with `no_autoflush` as the escape (`:3159`).

*RDF translation.* Keep the identity map (I3), snapshot diff (P9), `commit()`, orphan deletion along composition (P11) and the version check. Drop the topological sort and dependency processors (IRIs are client-minted, I1). Drop autoflush: over portable SPARQL a flush would be a separate, irreversible commit. Drop savepoints unless the store has vendor transactions (T8).

*Scores:* C1 5 · C2 5 · C3 4 · C6 3 · C8 5 · C9 3 · C10 4.

*Verdict: borrow ideas* (identity map, `with Session() as s, s.begin():`, cascade vocabulary, the "cannot verify" warning). Avoid the topological flush and autoflush.

=== Spring Data JDBC — aggregate-oriented persistence

*Purpose and origin.* A Spring Data module led by Jens Schauder (VMware, now Broadcom), built as a DDD-first alternative to JPA: "simple, limited, opinionated" (`README.adoc:6-7`). No persistence context, no lazy loading, no dirty checking ("No lazy loading or caching is done", "There is no dirty tracking and no session", `jdbc/why.adoc:21,25`). Design angle: aggregate-first. Fit: the L1 design model for rdf-persistence repositories (approach B generates one per root).

* `WritingContext.save()` (`…/conversion/WritingContext.java:45`): new → `InsertRoot` + `insertReferenced()`; else `UpdateRoot` + `deleteReferenced()` + `insertReferenced()`. GitNexus confirms the callees. Docs: owned entities "are deleted and recreated".
* Version on the root only: `updateWithVersion` and `deleteWithVersion` (`JdbcAggregateChangeExecutionContext.java:127-140, 384-390`).
* Cross-aggregate references: `AggregateReference<T, ID>`; references across aggregates "are guaranteed to become consistent eventually". Mapping assumption: no other entity points at non-root entities.
* One repository call is one transaction (`SimpleJdbcRepository.java:51, 71, 77, 108`) unless an outer `@Transactional` widens it.
* Domain events from `@DomainEvents` on the root, published on `save*` and `delete*`, not on `deleteById` (no aggregate instance). Publication happens inside the repository call; after-commit delivery needs `@TransactionalEventListener(AFTER_COMMIT)` (docs, not code-checked). This strengthens the case for an outbox.

*RDF translation (almost one-to-one).* Aggregate = root plus owned closure. `save(root)` = one guarded `+DELETE {old owned triples} INSERT {new owned triples} WHERE {root version guard}+`. `AggregateReference` = an IRI-typed slot (`Ref[T]`). No lazy loading = one CONSTRUCT loads the aggregate. Improve on delete-and-reinsert with a snapshot diff (P9) that keeps foreign triples (P8).

*Scores:* C1 3 · C2 5 · C3 4 · C6 5 · C8 4 · C9 3 · C10 5.

*Verdict: borrow ideas — the primary design model.*

=== Ecto — explicit changesets and `Ecto.Multi`

*Purpose and origin.* Elixir's data-mapping library, created at Plataformatec in 2013, now Dashbit; maintainers Eric Meadows-Jönsson, José Valim, Felipe Stival, Greg Rychlewski (`README.md:203-204`, `mix.exs:44`). Functional: no mutable objects, no identity map, no UoW. Design angle: change as explicit data. Fit: L1 idea for an inspectable commit and store-free domain tests.

* `Ecto.Multi` (`lib/ecto/multi.ex:1-120`): "a data structure for grouping multiple Repo operations … and provides a way to introspect the queued operations without actually performing them". Changesets are checked before the transaction starts; "we can also easily unit test our transaction without actually running it".
* `optimistic_lock/3` (`changeset.ex:3644`) → `Ecto.StaleEntryError` (`repo/schema.ex:1120-1130`).
* Owned children: `cast_assoc` with `on_replace: :delete | :nilify | :raise` (`changeset.ex:199-225, 1215`) makes replace semantics explicit per association. GitNexus parsed Elixir poorly; evidence is from source reading.

*RDF translation.* The UoW produces a change set value: removed and added quads, guards, events, touched aggregates. `commit()` compiles it to one SPARQL Update; `uow.preview()` prints it; domain tests assert on it with no store; the same value feeds the outbox (E1), RDF Patch (E2) and a JSON:API Atomic Operations response. `on_replace` maps to how a composition slot behaves when its value is replaced.

*Scores:* C2 5 · C3 4 · C6 4 · C8 5 · C10 5. *Verdict: borrow ideas* (change set as a value, validate before commit, `on_replace`).

=== cosmic-python (Percival and Gregory)

*Purpose and origin.* The code companion to _Architecture Patterns with Python_ (O'Reilly, 2020), teaching DDD, ports and adapters and event-driven architecture. It is Meaningfy's house style (skill `cosmic-python`). Design angle: teaching patterns. Fit: the L1 service-layer patterns of the generated backend.

* `AbstractUnitOfWork` (`service_layer/unit_of_work.py`): context manager, `__exit__` rolls back, `commit()` is explicit, `collect_new_events()` drains events of every aggregate in `products.seen` (GitNexus confirms).
* The repository tracks `seen` on `add` and `get` (`adapters/repository.py:9-24`). The aggregate `Product` holds `version_number` and `events` (`domain/model.py:8-30`).
* `MessageBus.handle` keeps an in-memory queue; event-handler errors are logged and swallowed, command-handler errors raised.
* Book ch. 7: one aggregate = one repository; one transaction changes one aggregate; version number in the domain; retry on conflict; "the smaller, the better".
* *Gap:* events are dispatched in memory after commit. A crash between commit and handlers loses them; there is no outbox in the code.

*RDF translation.* Adopt the repository per aggregate and the UoW (thin). `seen` becomes the identity map's touched-aggregate set. Persist collected events as outbox triples *in the same update* (E1), closing the crash window. *We disagree on the version:* LinkML-generated classes must stay persistence-free, so the mapper keeps it as session metadata (`uow.version_of(order)`), which also gives the L4 ETag.

*Scores:* C2 5 · C3 4 · C6 5 · C8 2 · C10 4. *Verdict: adopt the patterns* (the house standard), adding the outbox it leaves out.

== Aggregates in a graph — three options

DDD rules (Vernon, _Effective Aggregate Design_ III, p. 15): model true invariants in consistency boundaries; design small aggregates; reference other aggregates by identity; use eventual consistency outside the boundary.
Vernon also notes (p. 12) that with document-like storage the root is modified every time a part is: a root version triple makes contention per aggregate, so keep aggregates small.

[cols="2,3,2,3,2,3",options="header"]
|===
|Option |Definition |Load |Save and concurrency |ACL fit (DEC-8) |Costs

|*A1 Root + owned closure* (recommended default)
|Root IRI plus the transitive closure over owned (composition) slots; children get IRIs derived from the root (`<root>/lines/1`)
|One CONSTRUCT along owned predicates (property paths generated from the model)
|One guarded update with ground templates; version guard on the root, confirmed by an append-only commit record (T2)
|Graph-level ACL stays free for tenancy and context
|Delete set comes from the loaded snapshot (P9); foreign triples kept (P8)

|*A2 Named graph per aggregate*
|All triples of the aggregate in its own graph
|GSP `GET` or a graph-scoped CONSTRUCT
|GSP `PUT` (atomic replace, stores pattern P-f) or a graph-scoped guarded update; ETag per graph (P-g)
|*Conflicts* with graph-as-ACL-unit (semantic.works, graph-based authz); Fluree policies cannot target a named graph
|Many graphs; cross-aggregate queries need `GRAPH ?g` or a union default graph; the graph is no longer free for provenance or tenancy

|*A3 Concise Bounded Description*
|Subject plus blank-node closure
|`DESCRIBE` (store-specific)
|Cannot be guarded: blank nodes are not allowed in DELETE templates
|as A1
|Skolemise blank nodes (I4) and it becomes A1
|===

*Recommendation:* A1 by default; A2 as an opt-in storage strategy for document-like aggregates where graphs are not already used for tenancy or ACL. Keep graph placement a deployment decision (P12), not hard-coded in the model. OldMan's document-centric grouping (X15) is a precedent for A2; see xref:architecture/soa/libraries/oldman.adoc[OldMan].

== Transaction boundaries — what the store allows

From the xref:architecture/soa/angles/stores.adoc[stores angle]:

* *One SPARQL Update request = one atomic transaction* is the only portable guarantee. So commit = one request, and an aggregate is naturally the content of one commit.
* *Several aggregates in one request are equally atomic.* The "one aggregate per transaction" rule must therefore be a policy, not a technical limit.
* *Guards do not abort a request.* In `+DELETE {…} INSERT {…} WHERE {g1} ; DELETE {…} INSERT {…} WHERE {g2}+`, a failed `g1` skips only the first operation; the second still runs. This refines stores pattern P-b (guarded update).
* *Vendor transactions* (RDF4J/GraphDB T3, Fluree embedded) add read-your-writes (T5) and real multi-request work. The aggregate rule stays a policy there too.
* *Chunking proxies* (semantic.works `sparql-parser`, Virtuoso autocommit) break the single operation: guard and writes can land in different chunks (T11). Refuse by default, or degrade with a warning (T4, T7).
* *Writers outside the library* that do not bump versions defeat the guard. Document it; an append-only commit record per commit at least detects our own concurrent writers.

=== The single guarded operation

All-or-nothing over any SPARQL 1.1 store needs *one* operation whose WHERE joins every guard:

[source,sparql]
----
DELETE { <ground triples removed, all aggregates> }
INSERT { <ground triples added> ; <outbox triples> ; <root> rp:version 8 ; <urn:uuid:T> a rp:Commit }
WHERE  { <rootA> rp:version 7 . <rootB> rp:version 3 }   # every guard; 1 solution or 0
----

* With constant guards the WHERE yields exactly one empty solution or none. Zero solutions → nothing is written.
* A constant guard cannot say "does not exist yet". Creation guards use `+FILTER NOT EXISTS { <root> rp:version ?v }+`, which keeps one-or-zero solutions.
* Afterwards `+ASK { <urn:uuid:T> a rp:Commit }+` tells "committed" from "conflict" — a second round trip, used only for detection (Update returns no match count). Confirm against an *append-only* commit record written in the same update (for example the outbox entry), never against an overwritable triple on the root such as `rp:lastTx`: another writer committing to the same root between our update and the ASK would overwrite it and cause a *false conflict*.
* The delete template must be ground, so owned children need IRIs (I4 skolemisation).
* Cascade targets found dynamically (for example inbound references) must be read *before* commit. Inbound references from other aggregates lie outside the boundary: leave them, or clean them up eventually.

*Status: implemented nowhere yet.* It follows from SPARQL 1.1 Update semantics (zero solutions write nothing; no blank nodes in DELETE templates). Test it on Oxigraph, Fuseki, GraphDB and Fluree before relying on it.

== Do we need a Unit of Work?

*Yes, but a thin "aggregate session".* It combines Spring Data JDBC's boundaries, SQLAlchemy's convenience (identity map and automatic change detection on the aggregates you loaded) and Ecto's explicit change set as its product. Event sourcing and an implicit SQLAlchemy-style UoW with autoflush are both rejected.

[source,python]
----
with uow:                                        # new identity map; nothing sent yet
    order = uow.orders.get(order_iri)            # 1 CONSTRUCT: root + owned closure; snapshot kept
    customer_ref = order.customer                # Ref[Customer] — an IRI, not a loaded object
    order.add_line(sku, qty)                     # domain method; appends OrderLineAdded event
    print(uow.preview())                         # ChangeSet: −/+ triples, guards, events (dry-run)
    uow.commit()                                 # 1 SPARQL Update (single guarded op + outbox)
                                                 # → ASK commit record → on_commit hooks → bus dispatch
# leaving without commit = rollback = discard the in-memory ChangeSet
----

. *Load.* `repo.get` loads the whole aggregate in one query. No lazy loading inside an aggregate, none across aggregates.
. *Track.* The UoW records aggregates touched through its repositories (cosmic `seen`) and diffs each against its snapshot (P9). Writes cover only owned, mapped predicates (P8).
. *Compile.* The change set becomes one single guarded operation carrying version guards, the append-only commit record and outbox triples (T1, T2, E1). The aggregates-per-commit policy is applied here.
. *Confirm.* An ASK on the append-only commit record tells success from `ConcurrencyConflict`; a retry decorator replays the handler (T6).
. *After commit.* Clear the identity map (or keep it, `expire_on_commit=False`), run `on_commit` hooks, dispatch domain events in process. Handlers that change *other* aggregates open *new* UoWs (eventual consistency). The outbox relay delivers externally.
. *Capability-driven* (T7). RDF4J/GraphDB: the same change set inside a vendor transaction, with read-your-writes. Fluree embedded: `transact(fn)`. Chunking proxy: refuse unless `allow_degraded=True`, then compensations (T4) and a warning.
. *Version as metadata.* The mapper owns the version; `uow.version_of(order)` gives the ETag for L4 `If-Match` (B11; HTTP side X19). Generated domain classes stay persistence-free.
. *Reads that cross aggregates* go to read models or queries (X10), not repositories.

Developers write a repository call, domain methods and `commit()`. They see one request per commit and can print it. No ordering rules, autoflush or lazy-load traps remain.

== Declaring boundaries in LinkML

[cols="2,3,3,2",options="header"]
|===
|LinkML construct |Meaning |Use for boundaries |Evidence
|`identifier` / `key` |The class is an entity with a stable id |A class without one is a value object, always inlined |`schemaview.py:2147-2160`
|`inlined` / `inlined_as_list` |By value vs by reference *in tree serializations* |Candidate marker for "owned" — but this overloads a serialization hint |`meta.yaml:1783-1800`
|`shared` |Range may be referenced by many |`shared: true` → never owned |`meta.yaml:1861-1871`
|`tree_root` |Container class of a serialized document |*Not* an aggregate root; at most one per schema |`meta.yaml:1298-1311`
|`annotations` |Free-form extension point |Explicit `aggregate_root: true` (class), `owned: true`, `on_replace: delete` (slot) |metamodel
|===

There is no composition construct. UML composite aggregation would be the natural source in the MWBv2 chain (UML → model2owl → LinkML); whether that chain carries `aggregationKind=composite` was *not checked*.

*Proposed derivation rules.*

. A slot is *owned* if annotated `owned: true`, or by convention `inlined: true` with `shared` not true, or if its range has no identifier.
. *Aggregate roots* are classes with an identifier that are never the range of an owned slot, or classes annotated `aggregate_root: true`.
. *Aggregate* = root plus the transitive closure over owned slots.
. Every other slot whose range has an identifier is a *reference by IRI*, generated as `Ref[T]`, not a navigable object.
. Fail the build on: a class owned by two roots; a cycle through owned slots; an owned entity without derivable IRIs. Warn on a reference from outside an aggregate to a non-root entity.

See xref:architecture/soa/angles/codegen.adoc[code generation] for where these rules would run.

== Bounded contexts

* A bounded context maps to a LinkML schema module, with its own repositories and its own graph set or dataset.
* Only IRIs (references) and events cross contexts. No shared Python classes.
* The repo's `.importlinter` discipline applies: contexts become packages with contracts, so code generation emits one package per context.

*Features from this angle* (the Boundaries area, v4 ids B1–B16):

* B1 aggregate declaration in the model (root classes, owned slots) from annotations, the `inlined`+`shared` convention or UML composition;
* B2 boundary validation at generation time (single owner, no owned cycles, no outside references to non-root entities, derivable IRIs);
* B3 whole-aggregate load in one query, with no lazy loading inside the boundary;
* B4 whole-aggregate save with replace-owned-subtree semantics, minimised by snapshot diff;
* B5 typed cross-aggregate references resolved explicitly;
* B6 an aggregates-per-commit policy (strict / warn / allow);
* B7 the single conjunctive guarded operation (refines T1, T2), confirmed through an append-only commit record, with `FILTER NOT EXISTS` creation guards;
* B8 an inspectable change set and dry-run, unit-testable without a store;
* B9 domain events collected on aggregates, written to the outbox in the same request, dispatched after commit (refines E1);
* B10 an aggregate storage strategy: shared graph (A1) or graph per aggregate (A2);
* B11 a mapper-managed aggregate version exposed as an ETag;
* B12 after-commit hooks;
* B13 boundary-aware delete: cascade inside, inbound references refused, left dangling or cleaned up eventually (refines R4, P11);
* B14 bounded-context partitioning (per-context schema module, package, repositories and graphs);
* B15 a no-autoflush contract: warn when a query runs with pending changes;
* B16 process manager / saga support.

== How it plugs into MWBv2

See xref:architecture/soa/building-blocks.adoc[building blocks] for the layers.

* *L0:* UML composition → LinkML annotations (`aggregate_root`, `owned`) or the `inlined`+`shared` convention. The generator derives and validates aggregates and emits property paths for loading and ground-template builders for saving.
* *L1:* the aggregate session. Repositories generated per root (approach B) or generic, reading `SchemaView` at runtime (approach A).
* *L2:* one request per commit on any SPARQL 1.1 store; vendor adapters optional.
* *L3 (DEC-8):* the session is ACL-agnostic; the enforcement port scopes the graphs the CONSTRUCT and the Update touch. A1 leaves graphs free for tenancy and ACL; A2 competes with them. See xref:architecture/soa/angles/authz.adoc[authorization].
* *L4:* one resource per aggregate root; owned parts as included or embedded resources (JSON:API `include`, JSON-LD framing, G7). Writes are nested writes or Atomic Operations → one aggregate save. ETag / `If-Match` from the root version (B11; HTTP side X19).
* *L6:* outbox triples → relay → SSE or webhooks; the payload is the change set (RDF Patch E2, or mu change sets X12).

== Open questions

. *Boundary source:* explicit LinkML annotations (`aggregate_root`, `owned`) or inference from `inlined`+`shared`? Can UML composition be carried through model2owl or uml2linkml (not checked)?
. *Multi-aggregate commits:* default policy `warn` or `strict`?
. *Storage strategy:* A1 by default with A2 opt-in? A2 conflicts with graphs used for ACL or tenancy (DEC-8, V2).
. *Version location:* mapper metadata (recommended, keeps LinkML classes clean) or a domain field as in cosmic-python?
. *Event dispatch:* in-process message bus, outbox relay only, or both?
. *Blank nodes:* require IRIs for all owned entities (needed for guarded deletes) and skolemise blank nodes on import?
. Does the single guarded operation behave as expected on Oxigraph, Fuseki, GraphDB and Fluree?

*Not checked.* Hibernate, Django, Prisma, Marten, Axon, Eventuous and pyeventsourcing were not cloned; claims come from docs. The cosmic-python code licence is unknown (GitHub reports NOASSERTION). The single guarded operation was not tested on real stores. Ecto evidence is from direct source reading.

== Final verdict

*Verdict: ideas.* None is a dependency. Spring Data JDBC is the design model, Ecto the change-set model, SQLAlchemy the developer-experience benchmark, cosmic-python the house patterns for the service layer.

. *The UoW to build is small:* identity map, snapshot diff, cascades along owned slots, one guarded request per commit. No dependency sort, no autoflush, no savepoints. Do not port SQLAlchemy's machinery.
. *Atomicity comes from one single guarded operation, not from one request.* Several guarded operations in one request can half-apply. Owned parts need IRIs. Confirm the commit through an append-only commit record, not an overwritable root triple.
. *Boundaries must be declared, because LinkML cannot express them:* annotations or a convention, validated at build time. Cross-aggregate effects go through an outbox written in the same update; no benchmark ships one.
