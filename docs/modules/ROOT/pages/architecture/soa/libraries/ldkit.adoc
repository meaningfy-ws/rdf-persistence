= LDkit
:description: A small, fully typed TypeScript object-graph mapper over plain SPARQL 1.1: one schema literal, inferred types, a Lens per type. The JavaScript client for graph-direct reads (V5); an idea source otherwise.

== Purpose and origin

*Built for* letting web developers read and write Linked Data as typed plain JS objects without learning SPARQL, against any SPARQL endpoint, from the browser, Deno or Node (README; the ISWC 2023 paper "Linked Data Object Graph Mapping Toolkit for Web Applications").

*Who and in which context.* Karel Klíma, with co-authors Ruben Taelman and Martin Nečaský (`CITATION.cff`, which lists names only, no affiliation). An academic-plus-open-source setting; CITATION version 2.4.0 (2025-05-21), repository activity to 2026-10.

*Design angle.* Client-first and zero-backend: the browser talks SPARQL directly, types are inferred from the schema, and the bundle stays small (its own ~160-LOC engine).

*Where it fits.* L5, and only for graph-direct reads (V5). It assumes a raw SPARQL Update endpoint for writes, so it does not fit any variant where domain rules and authorization run in the backend for writes.

== How it works

*Schema as a value.* A schema is a JSON-LD-context-like literal: `{"@type": …, name: {"@id": …, "@type": xsd.string, "@optional": true}}` with `@array`, `@multilang`, `@inverse`, `@schema`, `@enum` (`schema/schema.ts`).
TS conditional types infer the entity interface from it, with no codegen step (`schema/interface.ts`).

*Lens.* `Lens<T>` (`lens/lens.ts:86-556`) exposes `find / findOne / findByIri(s) / count / insert / update / delete`, plus raw `insertData / deleteData` and `query`.
Each method calls exactly one `QueryBuilder` method (GitNexus `context(QueryBuilder)`), and each call is one SPARQL request.

*Reads.* `CONSTRUCT { ?iri a ldkit:Resource . <shape> } WHERE { { SELECT DISTINCT ?iri WHERE { required shape + filters } LIMIT n OFFSET m } <full shape with OPTIONALs> }` (`query_builder.ts:245-300`).
Optional properties sit as UNION branches inside one OPTIONAL, avoiding cartesian blow-up (`:118-124`). `findByIris` uses `VALUES`.
Filters: `$equals $in $lt $contains $strStarts $regex $langMatches $filter` and more (`lens/search_helper.ts`).

*Writes.* `insert` is `INSERT DATA` with no existence check (`query_builder.ts:312-319`).
`update` is one `+DELETE {old} INSERT {new} WHERE {old}+` per call; arrays support `$set`, `$add`, `$remove` (`update_helper.ts:161-189`).
`delete` removes only the subject's own triples (`query_builder.ts:331-339`).

*Encode/decode.* `encoder.ts` emits RDF/JS quads; nested objects without `$id` become blank nodes (`encoder.ts:136`). `decoder.ts` rebuilds objects and picks language variants (`decoder.ts:137-212`).

*Engine.* `IQueryEngine = RDF.StringSparqlQueryable` (`engine/types.ts`), the RDF/JS standard. The default is LDkit's own ~160-LOC `fetch` client POSTing `application/sparql-query` / `sparql-update`; Comunica is a drop-in.
The brief's phrase "CRUD over SPARQL endpoints via Comunica" is inaccurate: Comunica is optional.

*Graphs, identity, transactions.* One `defaultGraph` per Lens (`query_builder.ts:57-80`). The caller supplies `$id`; no minting, no session identity map. No transactions: a multi-entity call is atomic only because it is one Update request.

== What to borrow

* *The Lens surface* as a minimal repository interface: `find({where, take, skip})`, `findByIri(s)`, `count`, `insert`, `update`, `delete`, `insertData`, `deleteData`, raw `query`. Mirror it in Python for symmetry.
* *CONSTRUCT around a paged SELECT*, and *UNION-in-OPTIONAL* for optional fields.
* *Per-property DELETE/INSERT/WHERE patches* and `$set/$add/$remove` for collections (P10).
* *The compact mapping vocabulary* `@optional/@array/@multilang/@inverse`, close to LinkML `required`, `multivalued`, `inverse`, `range`.
* *A pluggable engine behind a community interface*; the Python analogue is a store port over rdflib, pyoxigraph and SPARQLWrapper.
* *Values only through the tagged-template builder*, with escaped literals (`sparql/stringify.ts`).

== What to avoid

* *Delete leaves debris:* nested blank nodes and incoming links stay (`query_builder.ts:331-339`).
* *Insert merges silently* on a duplicate `$id` (`INSERT DATA`, `:317`).
* *Required by default:* entities missing any non-`@optional` property silently drop out of `find()` (`query_builder.ts:233-243`). `update()` on such an entity probably matches nothing (inferred from `update_helper.ts:60-77`, not tested).
* *Silent truncation:* default `take` is 1000.
* *Swallowed store errors:* `Invalid query response status` discards the endpoint's error body (`engine/query_engine.ts:95`).
* *An open write surface:* writes need a raw SPARQL Update endpoint exposed to browsers.
* *No runtime validation*, no transactions.
* *No streaming:* `Lens.find()` buffers the whole CONSTRUCT result before decoding.
* *Leaky logs:* the `logQuery` callback receives the full query with literal values, so personal data can reach logs.

== Authorization seams

* *No PEP inside LDkit*, which is right for a client (DEC-8).
* *Credential seam:* a custom `fetch` in options or query context (`engine/query_engine.ts` `getFetch`), where an OIDC bearer token is attached and refreshed. Each Lens can carry its own context.
* *Behind a proxy:* plain SPARQL Protocol POSTs; no `GRAPH` unless `defaultGraph` is set (A2). A JWT-checking proxy that filters graphs, rewrites queries or delegates to store ACLs works unchanged.
* *Risk and recommendation:* per-entity policy on arbitrary DELETE/INSERT WHERE is hard. Give LDkit clients a *read* SPARQL endpoint behind the proxy and route *writes* through entity endpoints (L4), where the Python PEP and validation run.

== Code-generation fit

*High; works today in two steps.* LinkML slot metadata maps almost one-to-one onto LDkit's `@optional`, `@array`, `@inverse`, `@type`/`@schema`, `@id`.

* `gen-shacl` → `ldkit shacl-to-schema` keeps cardinalities and nested shapes (`scripts/shacl_to_schema.ts`). Preferred.
* `gen-jsonld-context` → `ldkit context-to-schema` makes every property required, because contexts carry no cardinality.
* A direct LinkML `gen-ldkit` (about 200–300 LOC of Jinja) would remove the experimental step.
* `schema-to-package` publishes the generated schema as an npm package for UI teams.

== Final verdict

*Integrate for V5 graph-direct reads only, behind a replaceable seam (DEC-5 exception needed); ideas otherwise.*

. LDkit assumes a *raw SPARQL endpoint*. Use it for *reads* behind a policy-filtering proxy or store-native ACLs, never for writes that must pass backend domain rules and validation.
. *Silent-data footguns:* required-by-default properties drop entities from `find()`, `insert` merges duplicates, `delete` orphans blank nodes, the store's error body is discarded, and `take` defaults to 1000.
. Its schema *can be generated from our LinkML model* (`gen-shacl` → `shacl-to-schema`, or a small direct generator). Its Lens API (`find/findByIri/count/insert/update/delete`, `$set/$add/$remove`) is the shape to mirror in Python.
