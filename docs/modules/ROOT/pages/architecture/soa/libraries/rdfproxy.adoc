= rdfproxy
:description: A read-only adapter that turns a SPARQL SELECT into nested, paginated Pydantic models for FastAPI; a clean read side, no write path, GPL-3.0.

== Purpose and origin

* *Built for:* exposing SPARQL endpoints as conventional, paginated JSON REST APIs (FastAPI) for digital-humanities projects at the Austrian Centre for Digital Humanities (ACDH-OEAW). The examples query Wikidata and GND authors (README) and the RELEVEN project's person data (`examples/releven_person_example.py`).
* *Who and when:* ACDH-OEAW, principal author Lukas Plank (who also maintains sparqlx). Releases from 2024 to 2026 under release-please.
* *Design angle:* read-model-first. A curated SELECT plus a Pydantic model gives a typed API resource for web front ends that do not want to speak SPARQL. Writes are out of scope by design; identity and predicate mapping do not matter because the query defines the shape.
* *Where it fits:* L4 read endpoints and the L1 read side (X10 projections): the CQRS query side next to rdf-persistence's write model. Not L1 writes, L2 transactions, L3 or L6. It fails DEC-5 (7 stars) and is GPL-3.0: ideas only.

== How it works

*Mapping is projection.* Model fields bind to SPARQL variables by name, or by `Annotated[T, SPARQLBinding("var")]` (`utils/_types.py:26-43`).
There is no predicate mapping, `rdf:type` or IRI identity: the query defines the shape, the model defines the nesting.
`list[Model]` fields with `ConfigDict(group_by=...)` aggregate rows into nested objects (`mapper.py:189-226`).

*Page flow.* `SPARQLModelAdapter.get_page` (`adapter.py:80-109`):

. builds a count query by replacing the SELECT clause (`constructor.py:151-168`);
. adds ORDER BY, LIMIT and OFFSET; for grouped models it injects a `select distinct ?group` subquery so pages count groups, not rows (`constructor.py:181-218`);
. sends items and count queries in one sparqlx `queries()` call (`adapter.py:93-94`);
. loads bindings into a pandas DataFrame, groups them and builds models recursively (`mapper.py:317-341`).

*Item flow.* `get_item` appends a `filter(str(?k) = "v")` before the final `}` and expects exactly one result (`adapter.py:55-78`, `constructor.py:70-94`).

*SPARQL handling.* rdflib `parseQuery` validates the query (SELECT only, no top-level modifiers; `query_checker.py:12-56`).
Rewriting is regex and string surgery (`sparql_utils.py:14-81`); the code admits the prefix limitation (`sparql_utils.py:36-39`).
Key values are escaped with the private `Literal._quote_encode` (`constructor.py:76-78`); `xsd_type` and `lang_tag` are interpolated raw.
The generic filter `_compute_filter_clause` is a stub returning `None` (`constructor.py:229-231`).

*Integrity guard.* `_check_grouping_consistency` raises when a non-aggregated field differs inside a group (`mapper.py:253-290`).

*Stores.* sparqlx takes an endpoint URL or an rdflib `Graph` (`adapter.py:39-53`).
The same test suite runs against in-memory rdflib, an Oxigraph container and a Fuseki container (`tests/conftest.py:59-112`).
No Update, no transactions.

== What to borrow

* The read side: query-defined Pydantic projections with `group_by` aggregation and group-aware pagination. It fits a cosmic-python "views" module.
* Fail-fast checkers at adapter construction: `check_query`, `check_model`, `check_key` (`adapter.py:47-48`, `utils/checkers/`).
* The `Page{items,page,size,total,pages}` and `QueryParameters[Model]` contract, with an `order_by` enum per model in OpenAPI (`utils/models.py:12, 60-68`).
* The three-target testcontainers matrix (rdflib, Oxigraph, Fuseki) as our conformance setup.
* Concurrent dispatch of independent queries (items plus count) in one client call.
* Specific error messages, e.g. `UnprojectedKeyBindingException: SPARQL binding 'gnd' for model field 'Author.gnd' not in query projection.` (`item_checker.py:33-35`).
* The sparqlx design (one thin client for a URL or an rdflib `Graph` target, sync and async, SPARQL Query and Update, streaming). As a dependency it is ruled out: GPL-3.0, one maintainer, about 6 stars.

== What to avoid

* *Regex query surgery* can break valid queries: a `FROM` clause is dropped from the count query, so totals come from a different dataset than the items (`sparql_utils.py:16-17`); a query without the optional `WHERE` keyword is rejected (`sparql_utils.py:20-21`); prefixes are stripped from grouped subqueries (`sparql_utils.py:36-39`); a trailing comment containing `}` misplaces injected filters.
* *Private and unescaped interpolation:* `Literal._quote_encode` (`constructor.py:76-78`); raw `xsd_type` and `lang_tag` (`constructor.py:84-86`).
* *Fragile grouping assumption:* scalars come from the first row of a group (`mapper.py:95-110`); consistency errors surface at request time when data changes.
* *pandas as a runtime dependency* only for groupby.
* *Count over the full user query* and OFFSET paging; slow on large endpoints.
* *Exception hierarchy gap:* `NoResultsFound`, `MultipleResultsFound`, `UnprojectedKeyBindingException` and `InconsistentGroupingException` do not inherit `RDFProxyBaseException` (`utils/exceptions.py:51-64`).
* *Thin docs:* the docs site's Concept and Tutorial pages are empty (0 lines in `docs/concept.md`, `docs/tutorial.md`).

== Authorization seams

* *Behind an authorizing proxy:* works, with fixed credentials only. Headers go through `aclient_config` once at construction (`adapter.py:39-53`); examples build adapters at module level, so per-user tokens need an adapter per request or a contextvar-based `httpx.Auth`.
* *No GRAPH clauses* are generated (A2), so a graph-filtering proxy behaves like a direct endpoint.
* *PEP site 1, FastAPI dependencies* in the user's app: coarse authz per endpoint; works today.
* *PEP site 2, the query pipeline:* `_compute_filter_clause` (`constructor.py:229-231`) is where a policy `FILTER` / `VALUES` would go. Three defects make it unsafe today:
** the count query ignores the filter, so totals leak (`constructor.py:151-168`);
** in grouped models the filter reaches only the paging subquery, not the outer query (`constructor.py:188-202`);
** `get_item` uses a separate constructor with no filter hook (`constructor.py:28-94`).
* *PEP site 3, post-mapping filtering:* too late for rows (breaks totals); fine only for field redaction.
* So totals, single-item lookups and nested group rows would all leak.
* *Verdict.* Borrow the seam location (query construction plus FastAPI dependency), not the implementation. A sound PEP must apply one policy to every generated query, preferably on a parsed algebra.

== Code-generation fit

*Partial.* Any Pydantic class, including LinkML `gen-pydantic` output, works as a projection target.

Gaps for a generator:

* Queries are not generated: a SELECT with variables matching field names must be derived from `class_uri` and `slot_uri` (OPTIONAL per optional slot, joins per object range).
* `ConfigDict(group_by=<identifier slot>)` must be added to every class with multivalued slots.
* The identifier slot must be projected as a variable.
* LinkML write models rarely equal API read projections; rdfproxy-style classes fit best as *generated views* beside the write model.

== Final verdict

*Ideas.* GPL-3.0, below DEC-5, pandas and regex rewriting rule out a dependency.

Three things to remember:

. *The read side (X10/Q10) is the transferable idea:* query-defined Pydantic projections with group-aware pagination belong in a cosmic-python "views" module beside the write model. In approach B the SELECTs and grouping keys are generated from LinkML (G14), not hand-written.
. *Policy must be injected into every generated query or it leaks:* rdfproxy's filter seam misses the count, item and grouped outer queries, and even drops a `FROM` clause from its count query. Any rdf-persistence PEP needs the AZ35 equivalence test across all query families.
. *Identity must flow per request, not per adapter:* credentials fixed at construction work behind a static-identity proxy (V2) but block per-user store policies (V3 Fluree, V4 GraphDB). The store port takes the caller's identity on every call (AZ19).
