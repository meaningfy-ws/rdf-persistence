= Owlready2
:description: Ontology-oriented programming over an embedded SQLite quadstore, with its own SPARQL engine and bundled OWL reasoners; a build-time tool for us, not a runtime store.

== Purpose and origin

*Built for* ontology-oriented programming in biomedical informatics.
Jean-Baptiste Lamy (LIMICS research lab, per `README.rst`) wrote it so that OWL ontologies (GO, UMLS via PyMedTermino2, drug ontologies) could be loaded, edited, reasoned over and scripted as plain Python objects.
Reference paper: Lamy, _Artificial Intelligence in Medicine_ 2017;80:11-28 (`README.rst`).
Single academic maintainer since about 2017 (Owlready 1 predates it; per the 2017 paper, history not visible in the shallow clone); distributed via PyPI and conda-forge.

*Design angle.* Ontology-first (TBox and ABox are one Python object graph), store-first (its own SQLite quadstore, for speed on large ontologies), reasoning-first (HermiT and Pellet bundled).
Web APIs, remote stores, multi-user transactions and authorization were never goals.
That explains the zero dependencies, the reimplemented RDF stack, Active Record write-through and the missing store and ACL seams.

*Where it fits.* Only L0, as an offline build or modeller tool: reasoner quality gate (G19), inference materialisation (G20), ontology exploration, import resolution (O7).
It fits no L1/L2 role in any variant (no SPARQL 1.1 client, no store port, Active Record coupling, no rollback, DEC-4), and none of L3–L6 (no authz, a GET endpoint read-only by default, no web UI, in-process observers only).

== How it works

*Mapping.* A metaclass (`EntityClass.__new__`, `entity.py:110-166`) creates Python classes for OWL classes inside `with onto:` and writes `rdf:type owl:Class` and `rdfs:subClassOf` *immediately* (`entity.py:157-159`).
Multi-parent classes use a custom MRO (`entity.py:100-108`); multi-typed individuals get a synthetic `FusionClass` (`individual.py:422-470`).
Properties are classes, indexed by `python_name` in one flat namespace per World.
`Thing.__getattr__` returns a scalar for functional properties, a `CallbackList` otherwise; `INVERSE_` and `INDIRECT_` prefixes give inverse and inferred values (`individual.py:264-298`).
`Thing.__setattr__` writes triples at once (`individual.py:300-…`).

*Identity.* Each IRI becomes an integer *storid* in a `resources` table (`triplelite.py:356-366`); blank nodes get negative ints.
A weak identity map `World._entities` (WeakValueDictionary) keeps one object per storid (`namespace.py:377`).

*Storage.* SQLite tables `objs(c,s,p,o)` and `datas(c,s,p,o,d)` with `d` as datatype or language; the `c` column is the ontology as named graph (`triplelite.py:178-205`).
Optional FTS5 tables per property. `locking_mode=EXCLUSIVE` by default (`triplelite.py:87-103`).

*Transactions.* `with onto:` opens `BEGIN IMMEDIATE` (`namespace.py:69-82`; default lock only: with a custom `lock=`, e.g. gevent, it only acquires the lock, `triplelite.py:306-308`); leaving it does *not* commit; `World.save()` commits (`namespace.py:458-460`).
There is *no rollback API* (grep finds none); `destroy_entity(e, undoable=True)` is the only undo (`prop.py:912`).
Other processes' writes never refresh loaded objects.

*Querying.* `world.search(...)` compiles to SQL (`triplelite.py:1391-1850`).
`world.sparql(q)` compiles SPARQL to *one SQL query*, with recursive CTEs for property paths, LRU-cached (`sparql/main.py:30-100, 1490-1604`; `namespace.py:482`).
Not supported: ASK, CONSTRUCT, DESCRIBE, INSERT DATA / DELETE DATA, SERVICE, FROM; MINUS is parsed but never translated.
Non-standard extensions: `LIKE`, `FTS`, `STORID`, `NEWINSTANCEIRI`, `PY_FUNC_*`, `INDEXED BY`.

*Stores.* `set_backend` accepts `"sqlite"` only (`namespace.py:396-405`). No SPARQL client. `sparql/endpoint.py` *serves* a GET SPARQL endpoint, read-only by default (`read_only=True`); with `read_only=False` it also runs INSERT/DELETE via GET, with no authentication (`sparql/endpoint.py:35,50`).
`world.as_rdflib_graph()` exposes the quadstore to rdflib (`rdflib_store.py:27-240`); the reverse direction does not exist.

*Reasoning.* `sync_reasoner_hermit/pellet` serialise the world, or the listed ontologies, to N-Triples (`reasoning.py:162-180`), run Java as a subprocess, and write inferences into `http://inferrences/` (`reasoning.py:161-…, 269-…`). Batch, not incremental. SWRL in `rule.py`, closed-world closure in `close.py`.

*Serialisation.* RDF/XML, OWL/XML and N-Triples in; N-Triples, N-Quads and RDF/XML out (`driver.py:337-401`). No Turtle, TriG or JSON-LD natively.

== What to borrow

* *Runtime class materialisation from an ontology (M6)* as an alternative to codegen; our version would produce Pydantic models.
* *Asserted vs inferred separation (O4):* inferences in a dedicated named graph; direct vs indirect values in the API.
* *Reasoner as an out-of-process port:* snapshot → reasoner → write back to an inference graph; behind a `Reasoner` port in cosmic-python.
* *Weak identity map keyed by IRI* (`WeakValueDictionary`) per session.
* *Functional vs non-functional properties decide scalar vs collection*, with automatic inverse maintenance.
* *Prepared, parameterised SPARQL* (`??` parameters, LRU cache) and Python-registered functions, over SPARQL 1.1 bindings.
* *Change observation* (`observe.py`, `CoalescedObservations`) as a model for domain events.
* *IRI refactoring* (`set_iri`, `set_base_iri(rename_entities=True)`) and *reload-if-newer* (`ontologies.last_update`).
* Actionable errors, e.g. `Property '%s' is not functional, cannot assign directly (use .append() or assign a list).` (`individual.py:343`).

== What to avoid

* *Write-through on attribute set* with commit only on `World.save()` and *no rollback*; after a failure SQLite and cached Python state diverge.
* *Global mutable state:* `default_world`, `LOADING`, module-level caches.
* *Flat property namespace:* `python_name` collides across ontologies.
* *Dynamic method injection* (`setattr` of backend methods, `namespace.py:410-416`): defeats static analysis and IDE completion.
* *Magic attribute prefixes* (`INVERSE_`, `INDIRECT_`) and bare `except:` with stderr diagnostics.
* *SPARQL dialect lock-in* through non-standard extensions.
* *Java dependency* and whole-world serialisation on every reasoning call.
* *Unverified claims.* "Tested up to 1 billion RDF triples" is *claimed, not found in code or tests*. "Beats Neo4J, MongoDB, SQLObject and SQLAlchemy" is *claimed, not reproducible from the repo* (benchmark scripts exist, results do not). "~60× faster than RDFlib" was not verified.

== Authorization seams

* *No access control of any kind;* only a `read_only` flag on the endpoint (`sparql/endpoint.py:35, 50`) and SQLite `mode=ro`.
* *Embedded in-process:* no network hop where a PEP could intercept queries. Dynamic method injection and write-through `__setattr__` leave no single choke point.
* The exposed endpoint could sit behind an authorizing reverse proxy, but it is a GET endpoint, read-only only by default (`read_only=False` runs INSERT/DELETE), with no authentication and no named-graph filtering.
* *DEC-8 implication:* it cannot be the runtime store of an ACL-agnostic rdf-persistence. Keep it out of the request path, where authorization is irrelevant.

== Code-generation fit

*Not a codegen target; a build-time companion.* It has no LinkML, SHACL or Pydantic output. In an MWBv2 chain it fits as an offline L0 step:

. *Consistency and classification* of the model2owl/LinkML-generated OWL with HermiT or Pellet; inconsistency fails the build.
. *Materialising inferences* into an `inferred` named graph, exported as N-Triples or N-Quads and loaded into the real store.
. *Ontology exploration* for modellers in notebooks, including import resolution.

*Prerequisites.* Even build-time use needs an explicit DEC-5 exception (see Activity) and a Java runtime in CI (`reasoning.py:182,293`).
ROBOT (`robot reason`) runs HermiT or ELK from the command line and is an alternative for the same gate; *not analysed*.

A runtime ontology-driven variant should use rdflib with an owlrl or HermiT reasoner port, borrowing M6 and the class-expression API (O3) as design references only.

== Variant fit

See xref:architecture/soa/variants.adoc[variants]. Supports no runtime variant and blocks none while it stays an offline L0 tool; as a runtime store it would block V1, V3, V4 and V5.

== Final verdict

*Build-time.* An offline L0 reasoner check and inference export, only with an explicit DEC-5 exception and a Java runtime in CI; otherwise ideas only. Never a runtime store or ORM for rdf-persistence.

Three things to remember:

. *It is its own triple store, not an ORM over yours:* embedded SQLite, own parsers, a SPARQL subset compiled to SQL; no SPARQL 1.1 client, no store port, no ACL seam, so it cannot sit behind rdf-persistence or a PEP.
. *Its persistence semantics are unsafe for services:* attribute writes go straight to SQLite, only `World.save()` commits, there is no rollback, and cached objects go stale across processes and after a failure.
. *Its lasting value is OWL reasoning at build time:* HermiT/Pellet consistency and classification on the generated OWL, inferences in a separate named graph. The JVM is still needed; ROBOT is the unanalysed alternative.
