= Open decisions (2026-11-05)
:description: What the developer's comments of 2026-11-05 leave to decide, with the options and a recommendation for each.

The developer reviewed the metamodel and asked for a richer metamodel, mandatory IRIs, labels and
definitions, an access model of its own, fine-grained access in this iteration, generated artefacts
in the right packages, and a lighter API. Three research passes (API styles, access control,
metamodel and generators) produced the pages linked below. These are the decisions they leave.

Already decided by the developer, so not asked again:

* The access model lives in rdf-persistence as its own module; applications import it and keep their
  access rules in a module apart from the domain.
* Models must carry IRIs, labels and definitions, checked at generation.
* SKOS, DCTerms, PROV-O and ODRL are the default annotation vocabularies.
* The generator produces Python and TypeScript classes, diagrams, shapes and the JSON-LD context,
  each in the package that uses it; LinkML generators are extended where needed.
* JSON-LD and GraphQL are considered now, not deferred.

== The decisions

[cols="1,3,4,3",options="header"]
|===
|Id |Question |Options |Recommendation

|D-1
|Which API contract? (xref:architecture/api.adoc[API])
|A. JSON-LD documents from a generic router. B. Plain JSON, typed by classes, with the context by `Link` header. C. GraphQL with the JSON-LD context. D. JSON:API from configuration.
|*A and B together*: one generic router driven by the schema, plain JSON by default, JSON-LD and Turtle by content negotiation; GraphQL later as a read-only endpoint over the same schema.

|D-2
|Do we need generated Python classes and the mapper? (xref:architecture/api.adoc#mapper[API])
|Always (current O-1). Only for domain services. Never.
|*Only for domain services*: the API path uses the context and the shapes; classes and mapper stay, optional, for rules that are more than CRUD.

|D-3
|Where does the OpenAPI document come from?
|A small hook of our own over the schema. linkml-openapi (complete, but months old, one author).
|*Our own hook now*, and a short spike of linkml-openapi to see whether it can replace it.

|D-4
|Which engine decides fine-grained access this iteration? (xref:architecture/access-control.adoc[access control])
|A. Our own check over ODRL-shaped grants (tenant, aggregate, action). B. A with OpenFGA. C. A plus property-level rules. D. Fluree's native policies.
|*A*, with the data shaped as ODRL so B or C can be compiled from it later without a migration.

|D-5
|How do v1's grants and ODRL relate?
|One model: a grant *is* an ODRL Permission (assignee, action through a role, target). Two models side by side.
|*One model*: fewer concepts, one record to audit, one thing to compile to OpenFGA later.

|D-6
|Which instance annotations are required? (xref:architecture/generation.adoc#revision[model to code])
|Label and description required on every class. Required on aggregate roots and owned classes, with an explicit opt-out for small value classes. Recommended only.
|*Required on roots and owned classes, with the opt-out* (`rp_unlabelled: true`).

|D-7
|Who writes created, modified and creator?
|The session, about the graph IRI. The application, about the entity.
|*The session, about the graph IRI*: these are facts about the write, which DEC-29 keeps apart from the entity; PROV-O derivation stays the application's.

|D-8
|Which diagram format?
|PlantUML (asked for): `.puml` files, rendered locally by a container, never by the public kroki.io service. Mermaid: rendered in the browser, as the docs already do.
|*Mermaid*, because it needs no rendering service and matches the rest of the docs. PlantUML is equally possible if you prefer it: say so.

|D-9
|How is output placement configured?
|A `[tool.rp-generate]` table in the application's `pyproject.toml`. Command-line flags only.
|*The table*, with flags as overrides.

|D-10
|How do people and programs sign in? (xref:architecture/access-control.adoc#identity[identity])
|The browser through the web app's server (code + PKCE); a command line by the device flow; programs by private-key JWT or client credentials; scripts by personal access tokens. Or an own login endpoint on the API.
|*The provider's flows, no login endpoint of our own*: the API accepts any valid token, however it was obtained.

|D-11
|Start implementing the adapters now?
|Now: Fuseki store, S3 file store (Garage), token validation and the Zitadel identity port, then the access check. After all decisions above.
|*Now*: the adapters do not depend on D-1 to D-10; the access check follows D-4 and D-5.

|D-12
|Where is that implementation planned?
|In the consumer's spine, as agreed earlier (toolkit capabilities `rp-*`, tasks tagged `[rp]`). In this repository's own `openspec/`.
|*Your call*: the earlier rule says the consumer's spine; for work that touches only the toolkit, this repository's spine keeps it next to its code.
|===

== What changes in architecture v1 once these are taken

* Decision O-1 narrows to domain services (D-2); O-2 widens to content negotiation (D-1).
* The deferred list loses "JSON-LD representation" and "GraphQL" (D-1), and "fine-grained access"
  (D-4).
* The metamodel splits into the modules of xref:architecture/generation.adoc#revision[model to code].
* The access check works per aggregate as well as per tenant (D-4).
