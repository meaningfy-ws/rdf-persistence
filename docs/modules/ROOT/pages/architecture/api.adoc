= A lightweight API over a triple store
:description: How the toolkit serves CRUD and access control over a generic triple store with as little generated code as possible: options, the recommendation and what it means for the mapper.

Status: *Accepted* (developer, 2026-11-05: decisions D-1 to D-3 of
xref:architecture/open-decisions.adoc[the decisions of 2026-11-05]): options A and B together; option C
kept as the backup for a later implementation. Research behind this page: the
xref:background/soa/angles/service.adoc[service angle] of the background study, updated on 2026-11-05.
Options A and B are *implemented* (stage 5 of the change `toolkit-v1-foundation`); <<serving>>
describes the service as built, and <<anatomy>> traces one request through it.

== The question

_How light can the API over a triple store be?_

An application on this toolkit controls three things: its *model* (LinkML), how the model is
*served* (an HTTP API), and *who may do what* (access control). Everything else should be generic.
So: how light can the API be, which contract should it speak (plain JSON, JSON-LD, GraphQL), and
does the API need generated Python classes and a mapper at all?

== What is generic and what is not

The router reads the model at run time, so adding a class to the model adds its endpoints. Code is
written only where an application has rules that are more than CRUD, and that code calls the same
session.

== Options

[cols="1,4",options="header"]
|===
|Option |How it works
|*A. JSON-LD documents* |One generic router over aggregates, scoped by tenant (`/{tenant_segment}/{t}/{rp_path}/{id}`; the path segment of each type is the annotation `rp_path`). `GET` returns the aggregate's graph as compacted JSON-LD (or Turtle); `PUT` replaces it under `If-Match`; a listing per type with equality filters and paging. Bodies are validated with SHACL. No Python classes on the API path.
|*B. Plain JSON resources* |The same routes, typed by generated Pydantic classes; the JSON-LD context is linked by a `Link` header, so the plain JSON is also JSON-LD (current O-2). OpenAPI describes it.
|*C. GraphQL with the JSON-LD context* |A GraphQL schema built at run time from LinkML (Ariadne, schema-first); queries compiled to SPARQL `CONSTRUCT`; mutations replace an aggregate and carry a `version` argument. Field names follow the JSON-LD context, as GraphQL-LD does.
|*D. JSON:API from configuration* |A resource configuration derived from LinkML, in the semantic.works mu-cl-resources style; filtering, `include` and paging.
|===

[cols="1,2,2,2,1,2,2",options="header"]
|===
|Option |Generated artefacts |Maturity of the parts |Access check seam |JSON-LD native |Client ergonomics |Main risk
|A |context, shapes |high (RDFLib, PyLD, FastAPI) |one dependency per route |yes |medium: JSON-LD aware clients |the listing and filter grammar is ours; nested parts need framing
|B |classes, context, TypeScript types, shapes |high |one dependency per route |by `Link` |best: OpenAPI → typed client |two shapes to keep aligned (class and graph)
|C |context; schema built at run time |parts mature, the RDF binding is ours |per resolver, per field |context reused; wire format is not JSON-LD |good |no HTTP ETags or status codes; the SPARQL compiler and its N+1 queries are ours
|D |resource configuration |low (18★, Common Lisp, no releases) |a proxy |no |good for JSON:API clients |opaque ids instead of IRIs; dialect lock-in
|===

=== What already exists, and why none of it is the whole answer

* *SPARQL Graph Store Protocol* is aggregate CRUD on its own (`GET`/`PUT`/`DELETE` a named graph),
  but Fuseki sends no `ETag` and does not check `If-Match`
  (https://github.com/apache/jena/issues/2305[Jena issue #2305], open), it has no listing, paging or
  problem responses, and it authenticates only with its own users. A thin layer must hold the version
  token, which the aggregate session already does.
* *LinkedDataHub* (Java, Apache-2.0, active) shows the whole pattern done right: the Graph Store
  Protocol with `If-Match` and SPARQL-based access control. It is an application, not a library.
* *Prez* (Python, FastAPI, profile-driven) is read-only.
* *Community Solid Server* has `ETag`/`If-Match` and document-level access rules, but no listing by
  class, and Solid-OIDC instead of a plain OIDC provider.
* *HyperGraphQL* is dormant; *GraphQL-LD* (Comunica) is query-only and runs in the client against an
  open SPARQL endpoint.
* *linkml-store* has no write routes, no authentication and no RDF backend. *linkml-openapi* emits a
  complete OpenAPI 3.1 document from LinkML, with CRUD paths, paging, problem responses and
  `application/ld+json`, but it is a few months old with one author and no runtime. A spike found it
  cannot replace our own OpenAPI hook (<<linkml-openapi>>).

No maintained Python library serves read-write CRUD with access control over a triple store from
configuration. The parts to build it are mature.

== Decision

*A and B together: one generic router, driven by the schema, serving plain JSON by default and JSON-LD
or Turtle by content negotiation.* No generated routes.

[mermaid]
....
%%{init: {"sequence": {"actorMargin": 25, "width": 110}}}%%
sequenceDiagram
    participant Cl as Client
    participant R as Router
    participant Se as Session
    participant St as Store
    Cl->>R: PUT /books/1 (If-Match v7)
    R->>R: check access, validate
    R->>Se: replace if v7
    Se->>St: update + ASK
    Se-->>R: v8
    R-->>Cl: 200, ETag v8
....

* *The wire stays simple.* Plain JSON with `id` as the IRI is also JSON-LD with the generated context,
  so a JSON-LD client reads it as RDF. `Accept: text/turtle` returns the graph itself.
* *The fewest generated artefacts.* Context and shapes are generated already. OpenAPI comes from a
  small hook of our own over the schema (D-3); a spike showed linkml-openapi cannot replace it
  (<<linkml-openapi>>).
* *Access control stays in one place*: one dependency per route action
  (xref:architecture/access-control.adoc[access control]).
* *Option C is the backup* for a later implementation: when a client needs deep nested reads, a
  read-only GraphQL endpoint over the same schema and context.

[#mapper]
== Do we need a mapper and Python classes?

_Does the API path need generated Python classes?_

*Not on the API path.* With the recommendation, the router turns JSON into triples with the JSON-LD
context and validates them with the shapes; reading returns the graph. Nothing there needs a class.

*Yes for domain services* (D-2). Where an application writes rules that are more than CRUD (a check across
two objects, a computed value), typed classes make that code safe and testable without a store. The
generated Pydantic classes and the mapper (O-1) stay for that, and they are optional: an application
with only CRUD needs none.

[cols="2,1,1",options="header"]
|===
|Path |Classes needed |Mapper needed
|Generic CRUD over the API |no |no (context + shapes)
|Domain service in the backend |yes (Pydantic) |yes
|Client code |TypeScript types (generated) |no
|===

== Consequences

* Decision O-1 narrows: the mapper serves domain services, not the API.
* Decision O-2 widens: JSON-LD and Turtle by content negotiation, not only the `Link` header.
* The listing and filter grammar is ours to define: equality filters, paging, sort, as in v1.
* JSON-LD and Turtle by content negotiation are in v1; GraphQL (option C) is the backup, deferred.

[#serving]
== Serving it

_How do I serve my schema over HTTP, and what does a client meet?_

An application serves its schema with one call to `install_service` in its composition root. The
call builds the routes from the schema, so a class added to the model is served after a restart.

[source,python]
----
from rdf_persistence import install_service

kit = install_service(
    app,                                  # the application's FastAPI app
    schema=Path("models/library.yaml"),   # the root schema
    generated=library.domain.generated,   # the package rp-generate wrote
    store=store, files=files, identity=identity, verifier=verifier,
    rules=Path("models/library_roles.yaml"),
    settings=settings,
    prefix="",                            # optional mount prefix
)
----

[cols="1,4",options="header"]
|===
|Argument |Meaning
|`schema` |The application's root LinkML file.
|`generated` |The package `rp-generate` wrote for it. The context, frames, shapes and `openapi-components.json` are read from its folder; a missing file stops the call with `OSError`.
|`store`, `files`, `identity`, `verifier` |The adapters: a `Store` (Fuseki), a `FileStore` (S3), an `Identity` (the identity provider) and a `TokenVerifier` (JWT access tokens).
|`rules` |An `AccessRules`, or the path of the role-definitions file. A path is loaded and validated in the call, so an invalid file stops the service before anything touches the store.
|`settings` |A `ServiceSettings`: `base` (the IRI under which identifiers and problem types are minted), `prefix` (the database and bucket name prefix), `tenant_segment`, `creator_role`, `roles_claim` (the token claim that carries the global roles, specific to the identity provider) and `max_body_bytes` (the largest request body, default 1 MiB).
|`prefix` |A path prefix under which the routes are mounted.
|===

At start-up, before the application's own lifespan, the service creates the system database if it is
missing and runs the sweep. `install_service` returns a `ServiceKit` (its tenancy, store, files and
identity, and `bucket_of` for a tenant's bucket) for the application's own routes. Such a route
checks its caller through the kit, so the toolkit's access rules apply to it too:

[source,python]
----
@app.get("/libraries/{t}/scan-files/{scan_id}")
async def get_file(t: str, scan_id: str, request: Request) -> Response:
    checked = await kit.require_aggregate(
        request.headers.get("authorization"), t, "scans", scan_id, Action.READ
    )                                     # 401, 404 or 403 as a problem response, or an Authorised
    bucket = await kit.bucket_of(checked.caller_access.tenant)
    return Response(await kit.files.get(bucket, scan_id), media_type="application/octet-stream")
----

`kit.require(authorization, tenant_id, action)` does the same for an action in the tenant. Both
return an `Authorised` carrying the caller's `principal` (for a domain service) and its access; `require_aggregate` also applies a prohibition on the aggregate and
returns, in `checked_target`, the IRI it checked, which the route then acts on.

*Routes* (PD-13), with `{t}` the UUID of the tenant's IRI:

[cols="2,3",options="header"]
|===
|Route |Methods
|`/{tenant_segment}` |`GET` the caller's tenants; `POST` a new tenant
|`/{tenant_segment}/{t}` |`GET`, `PUT` the tenant's root object; `DELETE` the tenant
|`/{tenant_segment}/{t}/grants` |`GET`, `PUT` the tenant's grant set
|`/{tenant_segment}/{t}/label` |`PUT` the tenant's label
|`/{tenant_segment}/{t}/{rp_path}` |`GET` a listing; `POST` a new aggregate
|`/{tenant_segment}/{t}/{rp_path}/{id}` |`GET`, `PUT`, `DELETE` one aggregate
|`/context.jsonld` |`GET` the generated JSON-LD context
|===

A read of one object answers with its `ETag`; every `PUT` and `DELETE` needs `If-Match` (428 without it, 409 on a
stale version); a create answers 201 with a `Location`. Plain JSON points at the context by a `Link`
header, so it is also JSON-LD. The link is built from `settings.base` and the mount prefix, never
from the request's `Host` header, so a deployment sets `base` to the address it is reached at; `Accept: application/ld+json` and `text/turtle` are served too (406
for anything else, 415 for a body in another type).

*Bodies are strict* (PD-14b). A body larger than `max_body_bytes`, or holding more than 10 000
objects and list values together (a list of strings counts each string), is refused with 413. A plain-JSON body may use only its class's slot names and the JSON-LD
keywords, at every level. Only the root and the owned parts reached from it, each typed with a class
of the schema, may appear; any other subject is 422. An `internal` slot is refused in a body (422
naming it) and never appears in a response. A replace keeps the stored values of the `internal`
slots of the root and of the parts that persist, matched by their IRI (a scan keeps its file key);
a part sent without its IRI is a new part, so it has no stored internal values to keep. This is by
design: every owned part is `Described`, so it has an IRI, and a `GET` returns it for the client
to send back. An IRI in a body that SPARQL cannot carry (a space, `<`, `>`, `"`, `{`, `}`,
`|`, `\`, `^` or a backtick) is refused with 422 before anything is sent to the store.

*Problem responses* (RFC 9457) have a fixed `type` (`{base}problems/<slug>`) and title, and every
error answers with one: the toolkit's own, the framework's (an unknown path, 405
`method-not-allowed` with its `Allow` header) and those of the application's routes. Only the
statuses that say what to fix in the request (400, 406, 413, 415, 422, 428) carry a `detail`. A
refusal (401, 403, 404, 409), an outage (503) or a fault of the service (500 `internal-error`)
carries none, so a hidden tenant and an absent one answer alike, and no answer tells an outsider
where the store is. A fault is anything the caller cannot fix: SPARQL the toolkit wrote that the
store refuses (`ToolkitStore` in `services/store.py` turns the store's `BadQuery` into a
`SparqlError`), or stored data that does not validate. A bad query string from the caller stays 400
`bad-query`; so does a filter on an IRI-valued slot whose value is not an IRI SPARQL can carry.

*Listings* (PD-15, PD-15a). A query takes `limit` (1 to 200, default 50), `offset` (default 0),
`sort` (a slot name, descending with a leading `-`; by IRI when absent) and `?<slot>=<value>`
equality filters. Filters are typed by the slot's range: an enum value is matched by its meaning
IRI, a reference by its IRI, anything else as a typed literal. The `id`, bookkeeping, `internal` and
owned-part slots cannot be filtered on. One SPARQL `CONSTRUCT` per page counts the matches and
selects the page. A `read` prohibition on an aggregate hides it from that caller's listing and
total. The tenant listing takes only `limit` and `offset`, and is paged in one query too. A listing has no Turtle form (406).

*The OpenAPI document* is FastAPI's (`/openapi.json`), completed from the schema. It lists every
aggregate type's routes with their request and response bodies, a query parameter per filterable
slot, the problem responses of each route (413 on every operation with a body), the `ETag`,
`If-Match` and `Location` headers, and a
bearer security scheme. Its component schemas come from `openapi-components.json`, which
`rp-generate` writes with `gen-json-schema` (xref:architecture/generation.adoc#toolchain[step 5b]),
so a running service needs no LinkML generator.

[#anatomy]
== Anatomy of a request

_What happens, in which order, when a client replaces an aggregate?_

One `PUT /{tenant_segment}/{t}/{rp_path}/{id}`, traced through the code. FastAPI resolves a route's
dependencies before it runs the route, so the token and the access check come before the body is
read. Each step that fails answers its problem at once; later steps do not run.

[mermaid]
....
%%{init: {"sequence": {"actorMargin": 25, "width": 110}}}%%
sequenceDiagram
    participant Cl as Client
    participant G as Gate
    participant R as DocumentApi
    participant D as Documents
    participant Se as Session
    participant St as Store
    Cl->>G: PUT …/books/{id} (If-Match v7)
    G->>St: CONSTRUCT the caller's access
    G->>G: AccessRules.require
    G->>R: Authorised (principal, CallerAccess, aggregate IRI)
    R->>R: negotiate, If-Match, read body (size limit)
    R->>D: parse (node cap, context, strict checks)
    D->>D: validate (SHACL)
    R->>Se: get_graph, replace_graph if v7
    Se->>St: update + ASK
    Se-->>R: v8
    R-->>Cl: 200, ETag v8
....

[cols="1,3,3,1",options="header"]
|===
|# |Step |Where |Refusal

|1
|Verify the bearer token.
|`entrypoints/auth.py`, `Gate.caller`, which calls the `TokenVerifier` (`JwksTokenVerifier.verify`)
|401

|2
|Turn the path into IRIs: the tenant's, then the aggregate's. An id that is not a canonical UUID
names nothing.
|`ServiceKit.tenant_iri`; `domain/iris.py`, `aggregate_iri`; called by `Gate.aggregate_access`
|404

|3
|Load what the caller may do in the tenant: one `CONSTRUCT` on the system database for the access
record's state and the rules that name the caller.
|`services/access.py`, `load_caller_access`, called by `Gate.check`
|404

|4
|The access check for `modify` on the aggregate, in the order of
xref:architecture/access-control.adoc#check[the check].
|`services/access.py`, `AccessRules.require`
|404, 403

|5
|Pick the response type from `Accept`.
|`entrypoints/negotiation.py`, `accepted_media_type`, in `DocumentApi.replace` (`entrypoints/router.py`)
|406

|6
|Read the expected version from `If-Match`.
|`negotiation.py`, `expected_version`
|428

|7
|Check the body's `Content-Type` (JSON or JSON-LD), then read the body with its size limit: a
`Content-Length` over `max_body_bytes` is refused before a byte is read, a chunked body as soon as
it outgrows the limit.
|`negotiation.py`, `request_media_type`; `router.py`, `limited_body`; both in `DocumentApi._body`
|415, 413

|8
|Parse the JSON, and count its objects and list values against the cap of 10 000.
|`services/documents.py`, `Documents._document` and `_bound`, called by `Documents.parse` from
`Aggregates.replace` (`services/aggregates.py`)
|422, 413

|9
|For plain JSON: type every node by the schema and refuse any key that is not a slot of its class,
and any `internal` slot. Then expand the document with the generated JSON-LD context into triples;
a remote context is refused. A JSON-LD body is expanded with its own inline context.
|`Documents._plain_document` and `_typed`; `Documents._triples` (pyld `to_rdf`)
|422

|10
|The strict-body checks on the triples: no `internal` predicate in any key form; exactly one root,
whose IRI is the path's; bookkeeping statements dropped; a part without an IRI gets
one from the IRI policy (by default `{root}/parts/{uuid4}`; its `{type}` is the part's `rdf:type`, else 422); every IRI one SPARQL can carry; every subject inside the aggregate and
reached from the root through owned-part slots, typed with a class the slot takes.
|`Documents.parse` (the internal-slot refusal), `Documents._settled`, `_root`, `_refuse_strays`
|422

|11
|Validate the triples against the generated SHACL shapes; the message names up to five slots.
|`Documents.validate` (pyshacl)
|422

|12
|Open a session on the tenant's database, read the stored graph, and add back the stored values
of the `internal` slots of the nodes the body still describes.
|`Aggregates.replace`: `Tenancy.tenant_session`, `Session.get_graph`, `Documents.internal_values`
|404

|13
|Commit: one SPARQL update of several `;`-joined operations, each guarded by the version from
`If-Match`, that replaces the graph and the root's registry entries and writes a fresh version
token and the tracking statements; then an `ASK` for the new token.
|`services/session.py`, `Session.replace_graph` (`replace_text`, `payload_triples`), through
`ToolkitStore`
|409; 500 if the store refuses the text

|14
|Read the aggregate back and answer it in the negotiated type: framed JSON (with the context's
`Link` header) or JSON-LD, or Turtle; the bookkeeping and `internal` values left out. The `ETag`
is the new version token, in quotes; `Vary: Accept` is set.
|`Session.get_graph`; `entrypoints/responses.py`, `document_response`, with `negotiation.py`,
`etag_of`, and `Documents.render`
|—
|===

A `POST` takes the same path without step 6, with `modify` on the tenant instead of on the
aggregate in step 4, a minted IRI in step 10 (a body that names an `id` is refused) and
`Session.add_graph` in step 13; it answers 201 with a `Location`.

[#linkml-openapi]
== linkml-openapi: not used (spike, task 5.6)

A spike on 2026-11-06 ran linkml-openapi 0.12.0 on the toy library. *Verdict: do not depend on
it.*

* *Versions.* 0.12.0 is the newest release that installs beside `linkml` 1.12.1: from 0.13 on it
  requires `pydantic` below 2.13, and the toolkit pins 2.14.2.
* *Run unchanged*, it stops on the shared `contributor` slot: `Principal` is reachable from
  several classes, and the tool wants one parent path per class.
* *Restricted to the aggregate classes*, it emits a document we would not serve:
** untenanted paths (`/books/\{id}`) and nested sub-resource routes;
** only 404 and 422 problem responses;
** no `ETag` or `If-Match` headers;
** JSON bodies only;
** the LinkML bookkeeping and the metamodel classes left in.

Closing those gaps would need tool-specific annotations in every consumer's model, plus a
post-processor: more code than our own hook. The toolkit therefore keeps the small OpenAPI hook of
task 5.5, whose component schemas come from `gen-json-schema` (PD-24).
