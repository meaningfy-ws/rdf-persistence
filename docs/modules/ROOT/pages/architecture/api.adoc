= A lightweight API over a triple store
:description: How the toolkit serves CRUD and access control over a triple store from the schema alone: one generic router, the contract a client meets, one request traced through the code, and why it is built this way.

An application on this toolkit controls three things: its *model* (LinkML), how the model is
*served* (an HTTP API), and *who may do what* (access control). Everything else is generic: one
router, driven by the schema at run time, serves every aggregate root that has an `rp_path`, as
plain JSON by default, and
as JSON-LD or an RDF serialisation by content negotiation. No route is generated.

How to wire the service is step 12 of the user manual,
xref:user-manual/serve.adoc[Serve the application]. This page explains what the service does:
<<serving>> describes the contract a client meets, <<anatomy>> traces one request through the code,
and <<why>> gives the reasons.

== What is generic and what is not

[mermaid]
....
flowchart TB
    subgraph app["the application"]
        direction LR
        M["model"]
        A["access module"]
        S["domain services"]
    end
    subgraph rp["rdf-persistence"]
        direction LR
        R["router"] --> C["check"] --> V["shapes"] --> P["session"]
    end
    ST[("store")]
    M --> R
    A --> C
    S --> P
    P --> ST
....

The router reads the model at run time, so adding a class to the model adds its endpoints. Code is
written only where an application has rules that are more than CRUD, and that code calls the same
session.

A write, in short:

[mermaid]
....
%%{init: {"sequence": {"actorMargin": 25, "width": 110}}}%%
sequenceDiagram
    participant Cl as Client
    participant R as Router
    participant Se as Session
    participant St as Store
    Cl->>R: PUT /books/1 (If-Match v7)
    R->>R: check access, validate
    R->>Se: replace if v7
    Se->>St: update + ASK
    Se-->>R: v8
    R-->>Cl: 200, ETag v8
....

* *The wire stays simple.* Plain JSON with `id` as the IRI is also JSON-LD with the generated context,
  so a JSON-LD client reads it as RDF; an RDF client asks for Turtle, N-Quads or another
  serialisation (<<representations>>).
* *Few generated artefacts.* The API path reads only the context, the frames, the shapes and the
  OpenAPI component schemas that `rp-generate` writes; no route and no class is generated for it
  (<<serving>>).
* *Access control stays in one place*: one dependency per route action
  (xref:architecture/access-control.adoc[access control]).

[#mapper]
== Where classes and the mapper are needed

_Does the API path need generated Python classes?_

*Not on the API path.* The router turns JSON into triples with the JSON-LD context and validates
them with the shapes; reading returns the graph. Nothing there needs a class.

*Yes for domain services.* Where an application writes rules that are more than CRUD (a check across
two objects, a computed value), typed classes make that code safe and testable without a store. The
generated Pydantic classes and the mapper serve that, and they are optional: an application with
only CRUD needs none.

[cols="2,1,1",options="header"]
|===
|Path |Classes needed |Mapper needed
|Generic CRUD over the API |no |no (context + shapes)
|Domain service in the backend |yes (Pydantic) |yes
|Client code |TypeScript types (generated) |no
|===

[#serving]
== Serving it

_What does a client meet?_

An application serves its schema with one call to `install_service` in its composition root; the
call, its arguments, what it does at start-up and the `ServiceKit` it returns are in
xref:user-manual/serve.adoc[Serve the application]. The routes are built from the schema when the
service starts, so a class added to the model is served after a restart. A route of the
application's own checks its caller through the kit, so the toolkit's access rules apply to it too.

*Start-up.* Before the application's own lifespan, the service guards the IRI policy, migrates
every database, sweeps and starts the events relay, in a fixed order whose steps, reasons and
failures (`503` `tenant-behind` for a tenant whose migration failed) are in
xref:architecture/data-flows.adoc#migrations[Start-up migrations].

*Routes.* The routes are listed in xref:user-manual/serve.adoc#routes[The routes]; `{t}` is the id in
the tenant's IRI, as the IRI policy mints it (a UUID by default). Deleting a tenant needs
`administer`.

*Service-written roots.* A root annotated `rp_writes: service`, and every root that includes
`StoredFile`, gets the listing and the read but not the generic `POST`, `PUT` and `DELETE`: the
record and the bytes of a file must change together, which only the consumer's own route can do, in
a session (xref:user-manual/serve.adoc#the-composition-root[the composition root] shows the kit calls). The routes are not mounted, so they are also absent from
the OpenAPI document, and the framework answers 405 with `Allow: GET`. There is no way to opt back
in. See xref:user-manual/files.adoc[Keep files]. The annotation's other value, `rp_writes: toolkit`
(on the toolkit's `Comment`), marks a root the toolkit writes and reads itself: no route is mounted
for it at all, so its path answers 404.

A read of one object answers with its `ETag`; the read of a tenant's root also answers with `Record-ETag`, the version of its access record, to send as `If-Match` to the label route. The read of a tenant's root and of an aggregate also answers `Allowed-Actions`, the actions the caller may take on it (`read, modify, delete, administer`, in that order; on a tenant `delete` means deleting the tenant and needs `administer`, on an aggregate `administer` is not listed; no header on a refused read), and each item of the tenant listing carries the same list as `allowed_actions`. A root `PUT` whose label is not the tenant's gets 422: a tenant is renamed through its label route. Every `PUT` and `DELETE` needs `If-Match` (428 without it, 409 on a
stale version); a create answers 201 with a `Location`. Plain JSON points at the context by a `Link`
header, so it is also JSON-LD. The link is built from `settings.base` and the mount prefix, never
from the request's `Host` header, so a deployment sets `base` to the address it is reached at. The
other representations are served by `Accept` (<<representations>>); 406 for a type that is not one of
them, 415 for a body in another type.

[#representations]
*Representations* (ADR-005, xref:adr/adr-005-representations.adoc[the record]). A route that answers
one aggregate (read, create, replace and the tenant root) serves seven media types:
`application/json` (the default), `application/ld+json`, `text/turtle`, `application/n-triples`,
`application/n-quads`, `application/trig` and `application/rdf+xml`. On a tie the order is that
one. JSON and JSON-LD are framed with the generated frames. The other five serialise the aggregate's triples, and
N-Quads and TriG name the aggregate's own graph, so a reader gets the triples together with the
graph they came from. A listing stays JSON and JSON-LD: a page carries its total and paging, which
no RDF serialisation holds, so any other type answers 406. RDF/XML cannot write a predicate that has
no XML local name, nor a value holding a character XML 1.0 forbids; an aggregate that holds one
answers 406 naming the type, and the other six forms still work. On a create or a replace the 406
comes before anything is written, so the client is never told a stored write failed. The OpenAPI document lists each type as a string response.

*Bodies are strict.* A body larger than `max_body_bytes`, or holding more than
`max_document_nodes` objects and list values together (10 000 by default,
xref:howto/settings.adoc[a toolkit setting]) (a list of strings counts each string), is refused with 413. A plain-JSON body may use only its class's slot names and the JSON-LD
keywords, at every level. Only the root and the owned parts reached from it, each typed with a class
of the schema, may appear; any other subject is 422. An `internal` slot is refused in a body (422
naming it) and never appears in a response. A replace keeps the stored values of the `internal`
slots of the root and of the parts that persist, matched by their IRI (a scan keeps its file key);
a part sent without its IRI is a new part, so it has no stored internal values to keep. This is by
design: every owned part is `Described`, so it has an IRI, and a `GET` returns it for the client
to send back. An IRI in a body that SPARQL cannot carry (a space, `<`, `>`, `"`, `{`, `}`,
`|`, `\`, `^` or a backtick) is refused with 422 before anything is sent to the store.

*Problem responses* (RFC 9457) have a fixed `type` (`{base}problems/<slug>`) and title, and every
error answers with one: the toolkit's own, the framework's (an unknown path, 405
`method-not-allowed` with its `Allow` header) and those of the application's routes. Only the
statuses that say what to fix in the request (400, 406, 413, 415, 422, 428) carry a `detail`. A
refusal (401, 403, 404, 409), an outage (503) or a fault of the service (500 `internal-error`)
carries none, so a hidden tenant and an absent one answer alike, and no answer tells an outsider
where the store is. Two refusals share 409 and differ in `type`: `conflict` ("Version conflict": a
stale version) and `key-conflict` ("Key conflict": a write claims a unique key value another
aggregate of the tenant holds). Neither carries a detail, so the answer names neither the value nor
the holder. A fault is anything the caller cannot fix: SPARQL the toolkit wrote that the
store refuses (`ToolkitStore` in `persistence/services/store.py` turns the store's `BadQuery` into a
`SparqlError`), or stored data that does not validate. A bad query string from the caller stays 400
`bad-query`; so does a filter on an IRI-valued slot whose value is not an IRI SPARQL can carry.

*Listings.* A query takes `limit` (1 to 200, default 50), `offset` (default 0),
`sort` (a slot name, descending with a leading `-`; by IRI when absent) and `?<slot>=<value>`
equality filters. Filters are typed by the slot's range: an enum value is matched by its meaning
IRI, a reference by its IRI, anything else as a typed literal. The `id`, bookkeeping, `internal` and
owned-part slots cannot be filtered on. A string-ranged slot also takes a contains filter,
`?<slot>~=<text>` (`Session.find` takes `Contains(text=...)`): it matches the aggregates whose value
holds the text, ignoring case. Filters combine with AND, paging and the total are unchanged, and an
aggregate is listed once however many of its values match. A slot that is not a string, or an empty
text, answers 400 `bad-query`. The text reaches SPARQL only as an escaped literal. One SPARQL `CONSTRUCT` per page counts the matches and
selects the page. The query states, for each subject, the graph it found it in (`rp:listedIn`), and
the toolkit gives each aggregate the subjects of its own graph; no IRI is read to find a subject's
root, so parts beside their root are listed with it. A `read` prohibition on an aggregate hides it
from that caller's listing and
total. The tenant listing takes only `limit` and `offset`, and is paged in one query too. A listing has only its JSON and JSON-LD forms (406 for an RDF type).

*The OpenAPI document* is FastAPI's (`/openapi.json`), completed from the schema. It lists every
aggregate type's routes with their request and response bodies, a query parameter per filterable
slot (and a `<slot>~` parameter, `minLength: 1`, per string-ranged slot), the problem responses of each route (413 on every operation with a body), the `ETag`,
`If-Match` and `Location` headers, and a
bearer security scheme. Its component schemas come from `openapi-components.json`, which
`rp-generate` writes with `gen-json-schema` (xref:architecture/generation.adoc#toolchain[step 5b]),
so a running service needs no LinkML generator.

[#anatomy]
== Anatomy of a request

_What happens, in which order, when a client replaces an aggregate?_

One `PUT /{tenant_segment}/{t}/{rp_path}/{id}`, traced through the code. FastAPI resolves a route's
dependencies before it runs the route, so the token and the access check come before the body is
read. Each step that fails answers its problem at once; later steps do not run.

[mermaid]
....
%%{init: {"sequence": {"actorMargin": 25, "width": 110}}}%%
sequenceDiagram
    participant Cl as Client
    participant G as Gate
    participant R as DocumentApi
    participant D as Documents
    participant Se as Session
    participant St as Store
    Cl->>G: PUT …/books/{id} (If-Match v7)
    G->>St: CONSTRUCT the caller's access
    G->>G: AccessRules.require
    G->>R: Authorised (principal, CallerAccess, aggregate IRI)
    R->>R: negotiate, If-Match, read body (size limit)
    R->>D: parse (node cap, context, strict checks)
    D->>D: validate (SHACL)
    R->>Se: get_graph, replace_graph if v7
    Se->>St: update + ASK
    Se-->>R: v8
    R-->>Cl: 200, ETag v8
....

[cols="1,3,3,1",options="header"]
|===
|# |Step |Where |Refusal

|1
|Verify the bearer token.
|`api/entrypoints/auth.py`, `Gate.caller`, which calls the `TokenVerifier` (`JwksTokenVerifier.verify`)
|401

|2
|Turn the path into IRIs: the tenant's, then the aggregate's. An id that is not a canonical UUID
names nothing; the policy decides what a valid id is, so under another policy a UUID may name
nothing.
|`ServiceKit.tenant_iri`, `Iris.tenant` and `Iris.aggregate` (`iris/services/iris.py`) on the kit's one
`Iris` (`ServiceKit.iris`); called by `Gate.aggregate_access`
|404

|3
|Load what the caller may do in the tenant: one `CONSTRUCT` on the system database for the access
record's state and the rules that name the caller.
|`access/services/access.py`, `load_caller_access`, called by `Gate.check`
|404

|4
|The access check for `modify` on the aggregate, in the order of
xref:architecture/access-control.adoc#check[the check].
|`access/services/access.py`, `AccessRules.require`
|404, 403

|5
|Pick the response type from `Accept`.
|`api/entrypoints/negotiation.py`, `accepted_media_type`, in `DocumentApi.replace` (`api/entrypoints/router.py`)
|406

|6
|Match `If-Match` to the one version the write takes: `*`, or a list of entity tags, by strong
comparison. A single strong tag is that version with no read; `*` or a list reads the current version
once. A weak tag names no version. A consumer's own route takes one strong tag with `expected_version`.
|`negotiation.py`, `matched_version` (`expected_version` for a consumer's route)
|428 (missing or malformed), 409 (weak, or none names the current version)

|7
|Check the body's `Content-Type` (JSON or JSON-LD), then read the body with its size limit: a
`Content-Length` over `max_body_bytes` is refused before a byte is read, a chunked body as soon as
it outgrows the limit.
|`negotiation.py`, `request_media_type`; `router.py`, `limited_body`; both in `DocumentApi._body`
|415, 413

|8
|Parse the JSON, and count its objects and list values against `max_document_nodes` (10 000 by
default).
|`api/services/documents.py`, `Documents._document` and `_bound`, called by `Documents.parse` from
`Aggregates.replace` (`api/services/aggregates.py`)
|422, 413

|9
|For plain JSON: type every node by the schema and refuse any key that is not a slot of its class,
and any `internal` slot. Then expand the document with the generated JSON-LD context into triples;
a remote context is refused. A JSON-LD body is expanded with its own inline context. A body, like a
loaded JSON-LD file, goes through one function that refuses a remote context, a second graph, a
relative IRI that has no `@base`, an IRI that is not valid and a document that is not an object or
array.
|`Documents._plain_document` and `_typed`; `Documents._triples` and `persistence/services/jsonld.py` (`triples_of`, pyld `to_rdf`)
|422

|10
|The strict-body checks on the triples: no `internal` predicate in any key form; exactly one root,
whose IRI is the path's; bookkeeping statements dropped; a part without an IRI gets
one from the IRI policy (by default `{root}/parts/{uuid4}`; its `{type}` is the part's `rdf:type`,
else 422); every IRI one SPARQL can carry; every subject reached from the root through owned-part
slots, typed with a class the slot takes, and, when the part template starts with `{root}/` (the
default), inside the aggregate. With parts beside their root, a body may name only parts its
aggregate stores: a create names none, a replace names none that the stored graph lacks (422).
|`Documents.parse` (the internal-slot refusal), `Documents._settled`, `_root`, `_refuse_strays`
|422

|11
|Validate the triples against the generated SHACL shapes; the message names up to five slots.
|`Documents.validate` (pyshacl)
|422

|12
|Open a session on the tenant's database, read the stored graph, and add back the stored values
of the `internal` slots of the nodes the body still describes.
|`Aggregates.replace`: `Tenancy.tenant_session`, `Session.get_graph`, `Documents.internal_values`
|404

|13
|Commit: a one-change `Transaction` sends one SPARQL update request (`request_text`) of `;`-joined
operations: a guard operation that writes a commit marker only if the graph is at the version from
`If-Match`, the operations that replace the graph and the root's registry entries and write a fresh
version token and the tracking statements, each matching only while the marker is there, and the
release of the marker; then an `ASK` for the new token (see
xref:architecture/data-flows.adoc#commit[Committing several aggregates at once]).
|`persistence/services/session.py`, `Session.replace_graph`, `Transaction.replace_graph`
(`replace_parts`, `request_text`, `payload_triples`), through `ToolkitStore`
|409; 500 if the store refuses the text

|14
|Read the aggregate back and answer it in the negotiated type: framed JSON (with the context's
`Link` header) or JSON-LD, or one of the five RDF forms (<<representations>>); the bookkeeping and `internal` values left out. The `ETag`
is the new version token, in quotes; `Vary: Accept` is set.
|`Session.get_graph`; `api/entrypoints/responses.py`, `document_response`, with `negotiation.py`,
`etag_of`, and `Documents.render`
|—
|===

A `POST` takes the same path without step 6, with `modify` on the tenant instead of on the
aggregate in step 4, a minted IRI in step 10 (a body that names an `id` is refused) and
`Session.add_graph` in step 13; it answers 201 with a `Location`.

[#why]
== Why it is built this way

_Why one generic router, and not GraphQL, JSON:API or an existing server?_

The developer took the decisions on 2026-11-05: D-1 to D-3 of the
xref:architecture/open-decisions.adoc[decision log], which lists the options weighed.
xref:adr/adr-003-fastapi-not-connexion.adoc[ADR-003] explains FastAPI over a spec-first library, and
xref:adr/adr-005-representations.adoc[ADR-005] widened the representations to seven. The research
behind them is the xref:background/soa/angles/service.adoc[service angle] of the background study.

Four contracts were weighed: JSON-LD documents from a generic router (A), plain JSON typed by the
generated classes with the context linked by a `Link` header (B), GraphQL with the JSON-LD context
(C), and JSON:API from a configuration derived from LinkML (D). *A and B were taken together*:
they need the fewest generated artefacts, their parts are mature (RDFLib, PyLD, FastAPI), and each
route checks access through one dependency. C is the backup, for a client that needs deep nested
reads: a read-only GraphQL endpoint over the same schema and context. It would bring no HTTP
`ETag` or status codes, and its SPARQL compiler would be ours. D was too immature (one small Common
Lisp project with no releases) and names resources by opaque ids instead of IRIs.

Nothing that exists does the whole job. The SPARQL Graph Store Protocol gives aggregate CRUD, but
Fuseki sends no `ETag` and does not check `If-Match`
(https://github.com/apache/jena/issues/2305[Jena issue #2305]), and the protocol has no listing,
paging or problem responses. LinkedDataHub does the whole pattern, but as an application, not a
library; Prez is read-only; the Community Solid Server has no listing by class and needs Solid-OIDC;
linkml-store has no write routes and no RDF backend. No maintained Python library serves read-write
CRUD with access control over a triple store from configuration; the parts to build it are mature.

The decisions narrowed and widened two earlier ones of the
xref:architecture/index.adoc#decisions-taken[architecture overview]: the mapper serves domain
services, not the API (O-1), and the API serves more than plain JSON by content negotiation (O-2).

[#linkml-openapi]
=== linkml-openapi: not used

The OpenAPI document is completed from the schema by a small hook of the toolkit's own (D-3), with
component schemas from `gen-json-schema` (<<serving>>). A spike on 2026-11-06 ran linkml-openapi 0.12.0 on the toy library and found that it cannot
replace the hook:

* 0.12.0 is the newest release that installs beside `linkml` 1.12.1; from 0.13 on it requires
  `pydantic` below 2.13, and the toolkit pins 2.14.2.
* Run unchanged, it stops on the shared `contributor` slot: `Principal` is reachable from several
  classes, and the tool wants one parent path per class.
* Restricted to the aggregate classes, it emits a document the toolkit would not serve: untenanted
  paths (`/books/\{id}`) and nested sub-resource routes, only 404 and 422 problem responses, no
  `ETag` or `If-Match` headers, JSON bodies only, and the LinkML bookkeeping and metamodel classes
  left in.

Closing those gaps would need tool-specific annotations in every consumer's model, plus a
post-processor: more code than the toolkit's own hook.
