= Where data lives and what each operation does
:description: The databases, graphs and buckets the toolkit writes, shown on the toy library, and what each operation does from the HTTP call or Python call down to the triple store.
:page-revised: 2026-11-10 by the developer

_Where does the toolkit keep tenants, their data and its own bookkeeping? What happens, step by
step, when an aggregate is created, read, listed, replaced or deleted, and when a tenant is?_

This page describes the toolkit on `develop` as of 2026-11-10 (after `live-tenant-sweep`).

The examples use the toolkit's own toy library (`tests/toy.py`, `tests/fixtures/library/`):
settings `base="https://example.org/library/"`, `prefix="lib"`, `tenant_segment="libraries"`,
`creator_role="librarian"`; a tenant is a library; its aggregates are books (`rp_path: books`) and
scans (`rp_path: scans`, a file aggregate). Every IRI below comes from the default
IRI policy (`IriPolicy` in `model/service/`); a consumer may set other templates.

== Terms

[cols="1,4",options="header"]
|===
|Term |Meaning

|Tenant
|One isolated workspace: its own database, its own bucket, and one access record. The toolkit never
reads across tenants. What a tenant stands for (a library, a customer, a project) is the
consumer's choice. There is one level: a tenant holds no tenants.

|Aggregate
|One object tree that is stored, versioned and deleted as a whole: a root (a book) and the parts it
owns (its chapters). It lives in one named graph.

|Tenant root
|The tenant's own object (a `Library`), the class annotated `graph: meta` in the schema. It is
stored like an aggregate, in the tenant's `meta` graph, but `T/meta` has no registry entry, so the
root appears in no listing. Graphs loaded for the root (`load_graph(T, …)`) are registered like any
aggregate's, owned by `T`.

|File aggregate
|An aggregate whose class includes `StoredFile` (the toy library's `Scan`): its triples describe a
file, and its `rp:fileKey` names the blob in the bucket.

|Version token
|A fresh UUID written on every commit of an aggregate, of a tenant root and of an access record.
HTTP shows it as the `ETag`; a write must send it back in `If-Match`, and a stale one is refused
with 409. A tenant has two: its root's (`ETag` of `GET /libraries/{t}`, sent to replace the root)
and its access record's (`Record-ETag`, sent to rename, change grants or delete the tenant).

|`kit`
|The `ServiceKit` that `install_service(app, …)` returns: the consumer's handle on the store, the
file store, the IRI policy (`kit.iris`), sessions and the gate.

|Principal
|The caller, as an IRI made from the token's issuer and subject. Its *global roles* come from the
token; its *grants* (permissions) and *prohibitions* on a tenant or an aggregate come from the
tenant's access record.

|`internal` slot
|A slot the schema marks `internal`: the service writes it, a request body never can.

|Prefixes
|`rp:` is `https://meaningfy.ws/ns/rdf-persistence#`; `dcterms:` is `http://purl.org/dc/terms/`.

|Registry
|A graph in each tenant database that says which graph belongs to which aggregate.

|Loaded graph
|A graph parsed from an RDF file (`Session.load_graph`) for one aggregate, kept beside its graph.

|Blob
|A file's bytes, kept in the tenant's bucket under a key; the aggregate that describes it names
the key in `rp:fileKey`.

|Tracking statements
|What the session writes about a graph on every commit: its version token, `dcterms:created` and
`dcterms:creator` (first commit), `dcterms:modified` and `dcterms:contributor` (later commits).

|Transaction
|The writes of several aggregates of one tenant (adds, replaces, removes), collected by
`Session.transaction()` and sent as one SPARQL update request. The store applies the request as one
unit, so every change is stored or none is.

|`rp:CommitMarker`
|One statement pair in `T/registry`, `<urn:uuid:…> a rp:CommitMarker ; rp:startedAt <time>`, with a
fresh IRI per transaction. The first operation of the request writes it only if every guard holds;
every later operation matches only while it is there; the last operation deletes it. It never
outlives a request. A `rp:CommitMarker` that stays in the registry means the store did not apply
the request as one unit. It is not a load marker.

|Load marker, grace period
|A load marker is one statement in the registry, written by `load_graph`: "this graph was loaded
at this time". The live-tenant sweep leaves alone anything younger than its grace period (one
hour by default), so work still waiting for its commit survives.
|===

Who writes what:

* *Only the toolkit* writes the access records, the registry, the version token and the tracking
  statements. A body that sends them has them dropped or refused.
* *The consumer's data* is the aggregates' triples, the loaded graphs and the blobs.
* A slot marked `internal` is written by the consumer's code through a session, never by a body.

[#gate]
== The gate every route passes

Every generic route under `/libraries` runs these steps as FastAPI dependencies, before its own
code (`entrypoints/auth.py`, `Gate`). Each failure answers at once.

. *Token.* `Gate.caller` verifies the bearer token with the `TokenVerifier` (signature, issuer,
  audience, expiry) and reads the global roles. 401 if it fails.
. *IRIs.* The path's `{t}` and `{id}` become the tenant and aggregate IRIs (`Iris.tenant`,
  `Iris.aggregate`). An id the policy does not mint is 404.
. *Access.* `load_caller_access` runs one `CONSTRUCT` on the system database: the access record's
  state and the grants and prohibitions that name the caller.
. *Check.* `AccessRules.require` decides for the route's action (`read`, `modify`, `delete`,
  `administer`): 404 if the tenant is not `active` or the caller may do nothing there, 403 for a
  prohibition or a missing permission. See xref:architecture/access-control.adoc#check[the check].

The route then answers `Allowed-Actions` with what the caller may do. Create a tenant and list
tenants check only the token.

A consumer's own route calls the same gate through `kit.require(authorization, t, action)` or
`kit.require_aggregate(...)`. Code that opens `kit.session(tenant, principal)` directly is not
checked: the session trusts its caller.

[#aggregates]
== Aggregate operations

The HTTP routes are `/libraries/{t}/books` and `/libraries/{t}/books/{id}` (`entrypoints/router.py`,
`DocumentApi`); the use cases are in `services/aggregates.py`, `Aggregates`; the SPARQL is in
`services/session.py`, `Session`. From Python, the same operations are `UnitOfWork.get`, `add`, `remove` and
`commit` over `kit.session(...)`, which skip the HTTP steps and the gate. Every write below is a
one-change transaction; <<commit>> shows how several changes share one request.

*Create.* The service mints the IRI, checks the body, and writes the graph and its registry
entries in one update request (a guard that `B/graph` is empty, the insert, the release of the
marker, see <<commit>>):

|Create
|`POST …/books` (action `modify` on the tenant); `UnitOfWork.add` + `commit`

`ASK` for the new token (409 if another add won). 201, `Location`, `ETag`.

|Read
|`GET …/books/{id}` (`read` on the book)
|`Session.get_graph`: a `SELECT` of the version and tracking, then a `CONSTRUCT` of `B/graph`.
Answered as framed JSON, JSON-LD or Turtle, without bookkeeping and `internal` values.
|Nothing.

|List
|`GET …/books?…` (`read` on the tenant)
|Equality filters, sort and paging from the query string (`list_request`); `Session.page` sends one
`CONSTRUCT` that reads the registry for the books and their graphs, and the total.
|Nothing.

|Replace
|`PUT …/books/{id}` with `If-Match` (`modify` on the book); `UnitOfWork.commit` of a changed object
|As create, but the root is `B` and parts must already be stored; the stored `internal` values are
added back. Every step is in xref:architecture/api.adoc#anatomy[Anatomy of a request].
|One update request (<<commit>>). Its guard operation checks that `B/graph` still holds the old
token and writes the marker. Five operations follow, each matching only while the marker is there:
empty the loaded graphs no longer listed, drop `B`'s registry entries, empty `B/graph` except the
old token, write the new triples, token, tracking (created and creator kept, modified and the
caller as contributor added) and registry entries, then drop the old token. The last operation
drops the marker. With a stale token the guard writes no marker, so no later operation matches and
nothing changes; the `ASK` for the new token then fails and the answer is 409.

|Delete
|`DELETE …/books/{id}` with `If-Match` (`delete` on the book); `Session.remove`
|`Session.remove` reads the version (404 if there is none).
|One update request (<<commit>>), guarded by the version: empty every loaded graph `B` owns, drop
its registry entries, empty `B/graph`. 409 if the graph is still there. Blobs are *not* deleted: use `remove_with_files`.
|===

*No change history is kept.* A replace overwrites; only the current version and the tracking
statements remain.

*Some aggregates have no write routes.* A class annotated `rp_writes: service`, or a file
aggregate, gets only `GET` routes; a `POST`, `PUT` or `DELETE` on them answers 405. The consumer
writes it through a session in its own route (`is_service_written`,
`services/schema_structure.py`).

[#commit]
== Committing several aggregates at once

_How can one commit change several aggregates and still be all or nothing?_ A transaction
(`Session.transaction()`) collects the changes and sends them as *one* update request. A store
applies one request as one unit, so a store failure leaves nothing half-written. The difficulty
is the guards. Repeating each root's guard in every operation, as a single replace could, fails
across roots: once the new book `C` is inserted, "`C/graph` is empty" is false for every later
operation, and once `A`'s old token is dropped, "`A` is at its old token" is false. So the guards
are checked once, at the start, and a marker carries the result through the request.

The example: the library changes book `A` (stored at `a1`), adds a new book `C`, and removes book
`B` (stored at `b1`), in one transaction.

[mermaid]
....
sequenceDiagram
  participant S as Session (Transaction)
  participant F as Fuseki (lib-t-…)
  Note over S: collect: replace A at a1, add C, remove B at b1<br/>(nothing sent yet, the pre-checks are reads)
  S->>F: one request of joined operations
  Note over F: 1 guard: A at a1, C/graph empty, B at b1 → write the rp:CommitMarker<br/>2 the marked operations of A, C and B<br/>3 release: delete the marker
  S->>F: ASK A at its new token, C at its new token, B/graph empty?
  alt true
    S-->>S: committed
  else false
    S->>F: SELECT the version each graph holds now
    alt a changed graph holds this transaction's token
      S-->>S: committed (another writer changed it afterwards)
    else
      S-->>S: Conflict, iris = the roots whose guard failed
    end
  end
....

*The request.* Three parts, joined with `;`:

. *The guard operation.* `INSERT { GRAPH T/registry { <marker> a rp:CommitMarker ; rp:startedAt … } } WHERE { … }`.
  The `WHERE` holds one pattern per change: `GRAPH A/graph { A/graph rp:version "a1" }` for a
  replace or a remove, and `FILTER NOT EXISTS { GRAPH C/graph { ?s ?p ?o } }` for an add. If any
  pattern fails, the `WHERE` has no row and no marker is written. The marker's IRI is a fresh
  `urn:uuid` for every transaction, so two transactions never share one.
. *The marked operations.* The operations of each change (for a replace, the five of the table
  above), each with `GRAPH T/registry { <marker> a rp:CommitMarker }` in place of its own guard.
  Without a marker they match nothing, so a refused transaction changes nothing, whatever the
  order of the operations.
. *The release.* `DELETE` of the marker's statements. The marker lives in `T/registry` for the
  length of the request only; the registry listings and the sweeps never see it.

*The confirmation.* Fuseki answers 204 whether the guard matched or not, so one `ASK` tells
which happened. It holds, for each added or replaced graph, `GRAPH G { G rp:version <new token> }`,
and for each removed graph, that nothing is in it. True: done.

*The diagnosis.* A false `ASK` has two possible causes. Either nothing was written (a guard
failed), or the commit applied and another writer changed one of its graphs before the `ASK` ran.
The session reads the version of every graph of the transaction with one `SELECT`. If any added or
replaced graph holds this transaction's new token, the commit applied (all or nothing, so the
other changes applied too) and the call succeeds. A transaction that only removes roots is never
taken as a success after a false `ASK`. Otherwise nothing was written, and the session raises
`Conflict` with `iris` set to the roots whose guard failed: a replaced or removed root no longer at
the version read, an added root that now exists. The list is sorted.

[IMPORTANT]
====
`Conflict.iris` is a diagnosis read *after* the refusal, so another writer can change the graphs
between the refusal and the read, and the list can be wrong or empty (the message then says the
commit lost a race). That nothing was written is the guarantee; the list is help for the
caller. One known gap: if the commit applied and every added or replaced graph was then
overwritten by others before the `ASK`, the call raises a `Conflict` although the data is
consistent; a re-read shows the others' versions.
====

*Before the request.* Each `add_graph`, `replace_graph` and `remove` of the transaction runs its
pre-checks at once, as a single call always did: the IRI policy, the loaded graphs the root may
own, the stored tracking. Giving one root twice (even once as a `str` and once as a `URIRef`) is a
`ValueError` at the second call; an exception inside the `async with` block sends nothing; an
empty transaction sends nothing. The pre-checks are reads before the request, so they are one
read per root and can race with other writers as before; the guards in the request are what
protect the commit.

*Limits.* One tenant only: nothing spans two tenants, or a tenant and the system database. Files
are not part of it: a blob keeps its write order and its sweep (<<files>>). Nothing is read inside
the request; the guards are the version tokens the caller read. A store must apply a multi-operation
update as one transaction (Fuseki does); the store conformance suite checks it.

first and the record second; removal goes the other way:

== Tenant operations

The routes are `/libraries` and `/libraries/{t}` (`TenantApi`); the use cases are in
`services/tenancy.py`, `Tenancy`. A tenant's life, and the order of writes that makes a crash
safe at every step:

[mermaid]
....
stateDiagram-v2
  [*] --> Creating: POST /libraries
  Creating --> Active: database, bucket and root written, access record written last
  Creating --> [*]: crash, start-up sweep drops the unnamed database and bucket
  Active --> Active: rename, grants, replace root, aggregate writes
  Active --> Deleting: DELETE /libraries/{t} marks the record
  Deleting --> [*]: database and bucket dropped, record removed last
  note right of Creating
    not a stored state: no record exists yet
  end note
  note right of Deleting
    answers 404 from now on;
    after a crash here, the next start-up sweep finishes it
  end note
....

[mermaid]
....
sequenceDiagram
  participant Cl as Client
  participant G as Gate
  participant T as Tenancy
  participant F as Fuseki
  participant O as S3
  Cl->>G: POST /libraries {label, root}
  G->>T: create (token checked only)
  T->>T: validate root, run root validators, mint T
  T->>F: create database lib-t-…
  T->>O: create bucket lib-t-…
  T->>F: lib-t-…: write the root into T/meta
  T->>F: lib-system: write the access record (active, creator is librarian)
  T-->>Cl: 201, Location
....

[cols="1,2,5",options="header"]
|===
|Operation |Call (action) |Steps, in order

|Create
|`POST /libraries` (token only)
|Validate the label and the root's slots, and run the consumer's root validators. Mint `T`, unused by
any database or record. Create the database `lib-t-…`; create the bucket; add the root to `T/meta`;
*last*, add the access record (state `active`, the creator as `librarian`) to `lib-system`. A crash
before the last step leaves a database and bucket no record names; they stay until the next
start, whose start-up sweep drops them.

|List
|`GET /libraries` (token only)
|One `CONSTRUCT` of every access record; the rules are applied in memory to the caller's global
roles and to each record's grants and prohibitions; the page holds the tenants the caller may
`read`, with their `allowed_actions`. A global role that permits `read` on every tenant shows
them all.

|Read
|`GET /libraries/{t}` (`read`)
|The root from `T/meta`; the root's version in `ETag`, the record's in `Record-ETag`.

|Replace the root
|`PUT /libraries/{t}` (`modify`)
|As an aggregate replace on `T/meta`; the label must stay the record's (`Tenancy.vet_root`).

|Rename
|`PUT /libraries/{t}/label` (`modify`)
|Check the record's version (`If-Match` carries `Record-ETag`); write the label to the root, then
to the record, so both versions change. These are two writes, not one: a crash between them
leaves the root renamed and the record not, and repeating the rename writes both. Renaming needs
`modify` like any edit of the tenant; changing grants needs `administer`.

|Grants
|`GET` and `PUT /libraries/{t}/grants` (`administer`)
|Read, or validate (the consumer's grant validators) and replace, the grants and prohibitions in
the access record, guarded by its version.

|Delete
|`DELETE /libraries/{t}` (`administer`)
|Mark the record `deleting` (from then on the tenant answers 404); drop the database; drop the
bucket; *last*, remove the record. After a crash midway, the tenant answers 404 to every route,
including another `DELETE`; the next start-up sweep finishes it.
|===

[#dump-restore]
== Dump and restore a tenant

`kit.dump_tenant` and `kit.restore_tenant` (`services/tenant_dump.py`) are Python calls with no
route and no gate; the consumer decides who may call them (see
xref:howto/dump-restore.adoc[Back up or copy a project]). A dump is one gzipped tar: `manifest.json`,
`graphs.nq`, then `blobs/<key>`, then an empty member `end` that shows the dump finished. A restore
always creates a new tenant, in the same order as `create`: database, bucket, data, access record
last.

[mermaid]
....
sequenceDiagram
  participant C as Caller
  participant D as tenant_dump
  participant T as Tenancy
  participant F as Fuseki
  participant O as S3
  Note over C,O: dump_tenant(T, out)
  C->>D: dump
  D->>T: get the access record (NotFound, or Conflict if deleting)
  D->>F: lib-t-…: export every named graph as N-Quads, one read
  D->>O: list the bucket's blobs
  D-->>C: out: manifest.json, graphs.nq
  loop each blob
    D->>O: get the blob (gone since the listing, so skipped and logged)
    D-->>C: out: blobs/key
  end
  D-->>C: out: end (empty)
  Note over C,O: restore_tenant(src, creator)
  C->>D: restore
  D->>D: read manifest.json, check format, schema, IRI policy
  D->>D: read graphs.nq, parse the N-Quads
  D->>T: restore(parsed quads, blob iterator)
  T->>T: draw T2, unused (private)
  T->>T: rewrite the IRIs from T to T2, check the graphs and the root
  T->>F: create database lib-t-… for T2
  T->>O: create bucket lib-t-…
  T->>F: import the N-Quads
  loop each blob member
    T->>D: next blob from the iterator
    D-->>T: key and bytes (each member charged against the budget)
    T->>O: put the blob
  end
  T->>D: iterator end: the end member follows, the gzip trailer checks
  T->>T: database and bucket still exist?
  T->>F: lib-system: write the access record (active, creator is librarian)
  T-->>C: TenantSummary of T2
....

[cols="1,2,5",options="header"]
|===
|Operation |Call |Steps, in order

|Dump
|`kit.dump_tenant(T, out)`
|Read the access record (unknown tenant is `NotFound`, a `deleting` one is `Conflict`; nothing is written).
Export every named graph of the tenant's database as N-Quads in one read, so the graphs agree with each
other. List the bucket. Write the manifest, the N-Quads, then each blob as it is read, then the empty
`end` member. Blobs are copied after the graphs, as found. The access record and its grants are not
dumped. A dump that fails half-way has no `end`, so a restore refuses it.

|Restore, checks
|`kit.restore_tenant(src, creator)`
|Before anything is created: the first member is `manifest.json` (at most 64 KiB) and the second
`graphs.nq`, both regular files with UTF-8 names; the manifest's format, schema id and version and
effective IRI policy equal the service's, and its `source_tenant_id` is the id of its
`source_tenant`; the policy does not glue the tenant id to a letter, digit or variable. Mint `T2`
(`Conflict` later if a concurrent create takes it first). Rewrite each IRI term of the graph names,
subjects and objects under the base, replacing the old tenant id between delimiters with the new one
(predicates, datatypes and literals are untouched). Every quad must be in a graph the policy mints
for `T2`, none in the default graph; the root must decode and pass the root validators. Restore
checks this structure, not each aggregate against its shapes, so it trusts the graph content (only
restore archives a deployment you trust wrote). The size budget: before each member is read, its size
plus a tar block is charged against `max_restore_bytes` (default 1 GiB, a `ServiceSettings` slot), and
the restore is refused when the total passes it. Any failure here is `InvalidBody` and nothing exists
yet.

|Restore, writes
|same call
|Create the database and the bucket; import the N-Quads; put each blob as it is read from the
archive; require the empty `end` member after the blobs, nothing after it, and read the gzip stream
to its trailer; check that the database and bucket still exist; *last*, write the access record with
the caller as the only grantee, in the creator role.

*When the new database and bucket are dropped.* A refusal or failure from the moment the database
exists up to the existence check drops them (best effort, failures logged) and writes no record. That
covers: a blob member that is not a regular file under `blobs/`; a key with a `.` or `..` segment, a
key seen twice, a name that is not UTF-8, or a key the object store refuses; no `end` member, or
anything after it, or a gzip stream that does not end properly; more bytes than `max_restore_bytes`;
and a failure of the store or the object store. The access record is written after that cleanup
block, so a failed record write leaves the database and bucket, with no record, for the next
start-up sweep; so does a crash. A start-up sweep that runs during a long restore would drop them,
which the existence check turns into a `PersistenceError`.
|===

The graphs are held in memory during both calls; blobs are streamed one at a time.

[#rules]
== Rules and checks

_Which rules does each operation apply, and what does a refusal answer?_ Over HTTP, a refusal is an
RFC 9457 problem; from Python, the exception named. Each rule runs before anything is written,
except the version match of the optimistic lock and one aggregate per IRI: those are guards inside
the update itself, so a refused update changes nothing. (Whether `If-Match` is present at all is
checked first, before the body.)

The order a write to an aggregate over HTTP meets them, and the answer at each refusal (the access check itself is
drawn in xref:architecture/access-control.adoc#check[the check]):

[mermaid]
....
flowchart LR
  A["token valid?"] -- no --> E401["401"]
  A -- yes --> B["ids minted by<br/>the IRI policy?"]
  B -- no --> E404["404"]
  B -- yes --> C["tenant active and<br/>action permitted?"]
  C -- no --> E4034["404 or 403"]
  C -- yes --> D["If-Match present?<br/>(replace, delete)"]
  D -- no --> E428["428"]
  D -- yes --> E["body: size, type,<br/>shape, SHACL"]
  E -- no --> E4xx["413, 415 or 422"]
  E -- yes --> F["IRI policy and<br/>loaded-graph checks"]
  F -- no --> E422["422"]
  F -- yes --> G["guarded update,<br/>then ASK"]
  G -- "stale or taken" --> E409["409"]
  G -- ok --> OK["200, 201 or 204"]
....

[cols="2,3,3,1",options="header"]
|===
|Rule |Applied by |Refuses |Answer

|*Token* valid: signature, issuer, audience, expiry
|Every route (`Gate.caller`)
|A missing or bad token (`InvalidToken`)
|401

|*IRI policy: ids.* An id in a path must be one the policy mints (by default a canonical UUID)
|Every route with `{t}` or `{id}` (`Iris.tenant`, `Iris.aggregate`)
|Any other id: it names nothing (`NotFound`)
|404

|*IRI policy: what a session touches.* A session reads and writes only the tenant root and IRIs the
aggregate template mints for its own tenant
|`Session.get_graph`, `add_graph`, `replace_graph`, `remove`, `load_graph`
|An IRI of another tenant, or not an aggregate IRI (`InvalidIri`)
|422

|*IRI policy: what the service mints.* New tenants, aggregates, parts and loaded graphs get IRIs
from the templates; a create body may not name an `id` or a part
|Create tenant, create aggregate, `load_graph`
|A body naming the root's or a part's IRI on create (`InvalidBody`)
|422

|*IRI policy: the templates themselves*, checked once when the service starts
|`check_iri_policy`, `Iris`; see xref:howto/adopt.adoc#iri-policy[Configure the IRI policy]
|`{deployment}` without a slug, colliding graphs, an id with no length
|start-up error

|*Tenant state.* Only an `active` tenant serves
|The access check
|A `deleting` or missing tenant (`NotFound`)
|404

|*No live sweep of a dying tenant*
|`kit.sweep_tenant` (a Python call, no HTTP route)
|A `deleting` tenant (`Conflict`)
|exception

|*Access.* The caller's roles, grants and prohibitions permit the route's action
|The access check (`AccessRules.require`)
|Nothing permitted: `NotFound`; a prohibition or a missing permission: `Forbidden`
|404, 403

|*Body size and type*
|Writes with a body
|Over `max_body_bytes` (413); a `Content-Type` other than JSON or JSON-LD (415)
|413, 415

|*Body shape*: at most 10 000 objects and list values; only slots of the class; no `internal`
slot; one root, the path's; every node reached from the root through owned slots; parts only
those the aggregate stores; no remote JSON-LD context
|Create and replace (`Documents.parse`); steps 8 to 10 of
xref:architecture/api.adoc#anatomy[Anatomy of a request]
|`InvalidBody` (422); over 10 000 objects (413)
|422, 413

|*Body content*: the generated SHACL shapes (required slots, ranges, cardinalities, patterns)
|Create and replace (`Documents.validate`)
|`InvalidBody`, naming up to five slots
|422

|*Optimistic lock.* A write sends the version it read
|Replace, delete, rename, grants, delete tenant
|No `If-Match` (`PreconditionRequired`, 428); a stale one (`Conflict`, 409; nothing changed)
|428, 409

|*One aggregate per IRI*
|Create (`Session.add_graph`)
|A graph that already holds triples (`Conflict`)
|409

|*Loaded graphs.* A commit may register only graphs the policy mints under its own root, and none
another aggregate owns
|Create and replace with `loaded_graphs` (`Session._check_commit`)
|`InvalidIri`
|422

|*RDF file parses*
|`load_graph`
|`InvalidGraph`; nothing written
|422

|*Tenant label.* The root's label is the record's; it changes only through the label route
|Replace root (`Tenancy.vet_root`), create tenant
|`InvalidBody`
|422

|*Grants can be checked.* Targets are the tenant or its aggregates' graphs; assignees are IRIs; a
granted role exists at its target's level
|`PUT …/grants` (`AccessRules.validate_grants`)
|`InvalidGrant`, `UnknownRole`
|422

|*The consumer's own rules*: root validators and grant validators, passed to `install_service`
|Create tenant, replace root, rename (root validators); `PUT …/grants` (grant validators)
|Whatever the validator raises as `InvalidBody`
|422
|===

[#sweeps]
== Sweeps

[cols="1,4",options="header"]
|===
|Sweep |What it does

|Start-up sweep (`sweep`)
|Run once by the consumer before it serves. Finishes the deletion of `deleting` tenants and drops
databases and buckets no access record names. Never looks inside an active tenant.

|Live-tenant sweep (`kit.sweep_tenant`)
|Run by an operator. Inside one active tenant, finds loaded graphs no registry entry owns and blobs no
`rp:fileKey` names, older than one hour; a dry run unless `remove` or `remove_blobs` is set. Graphs
loaded for the tenant root are judged like any other.
|===
