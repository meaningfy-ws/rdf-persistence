= Serve the application
:description: Serve the generated API with FastAPI: the routes, the representations and the composition root.
:page-revised: 2026-11-10 by the developer

_How do I serve it over HTTP?_

`install_service` turns a FastAPI app into the generated API of your schema: every aggregate root
gets its routes, every tenant its checks. This page shows the composition root that calls it, the
adapters and the token verifier it needs, what it does at start-up, the `ServiceKit` it returns for
your own routes, and the routes it serves.

== The composition root

The *composition root* is the one place that builds the adapters and hands them to
`install_service`. The toy library's is `build_library_app` (in full in
`tests/library_app.py`; shortened here to two of its file routes):

[source,python]
----
# library/entrypoints/app.py
from pathlib import Path

from fastapi import FastAPI, Request, Response

from rdf_persistence import (
    Action,
    FileStore,
    Identity,
    ServiceSettings,
    Store,
    TokenVerifier,
    install_service,
)

from library.domain import generated

SCHEMA = Path("models/library.yaml")
ROLES = Path("models/library.roles.yaml")  # the roles file; rp-uml2linkml writes it, or write your own
REVIEW_WORKFLOW = Path("models/workflows/review.workflow.yaml")  # the books' review workflow
MIGRATIONS = Path("migrations")  # the folder `rp-generate` keeps the lock and the migration files in


def build_library_app(
    *,
    store: Store,
    files: FileStore,
    identity: Identity,
    verifier: TokenVerifier,
    settings: ServiceSettings,
) -> FastAPI:
    app = FastAPI()
    kit = install_service(
        app,
        schema=SCHEMA,
        generated=generated,
        store=store,
        files=files,
        identity=identity,
        verifier=verifier,
        rules=ROLES,
        settings=settings,
        workflows=[REVIEW_WORKFLOW],
        migrations=MIGRATIONS,
    )
    path = f"/{settings.tenant_segment}/{{t}}/scan-files/{{scan_id}}"

    async def bucket_after(request: Request, tenant_id: str, scan_id: str, action: Action) -> str:
        checked = await kit.require_aggregate(
            request.headers.get("authorization"), tenant_id, "scans", scan_id, action
        )
        return await kit.bucket_of(checked.caller_access.tenant)

    @app.put(path, status_code=204)
    async def put_file(t: str, scan_id: str, request: Request) -> Response:
        bucket = await bucket_after(request, t, scan_id, Action.MODIFY)
        await kit.files.put(bucket, scan_id, await request.body())
        return Response(status_code=204)

    @app.get(path)
    async def get_file(t: str, scan_id: str, request: Request) -> Response:
        bucket = await bucket_after(request, t, scan_id, Action.READ)
        return Response(await kit.files.get(bucket, scan_id), media_type="application/octet-stream")

    return app
----

`rules` is the path of the roles file: pass the path, and `install_service` loads it. Pass an
`AccessRules` built with `load_role_definitions` only when you change the definitions in code
before the service reads them. The file names here are those `rp-uml2linkml` writes; a
hand-written file may have any name.

`migrations` is the folder of your migration files. At start-up the service brings every database
to the version the schema runs, before it serves. A tenant whose migration failed is set aside:
its requests for data (its aggregates, files and listings) answer 503 with the problem
`tenant-behind`. Its record can still be read, its grants changed and the tenant deleted. A rename
answers 503 too, because it writes the tenant's root. A dump and the live sweep still work. The
other tenants are served. See xref:howto/migrate.adoc#startup[Change a schema that has stored data].

The routes for a scan's bytes are yours, because the toolkit serves no bytes; why, and the route
that writes the scan's record, are in xref:user-manual/files.adoc[Keep files].

[#adapters]
== The adapters and the settings

The adapters and the settings come from the deployment. These are the real ones, so a running
Fuseki, Zitadel and an S3 store are needed. For a toy service with none of them, build the same app
over the testkit's in-memory fakes, as in xref:user-manual/test.adoc#whole-service[The whole service
over the fakes]. The adapters of the store, the identity provider and the token verifier are async
context managers, so open them for the life of the app, and serve `app` inside the block:

[source,python]
----
import uvicorn

from rdf_persistence import (
    FusekiStore,
    JwksTokenVerifier,
    S3FileStore,
    ServiceSettings,
    ZitadelIdentity,
    zitadel_roles_claim,
)

settings = ServiceSettings(
    base="https://example.org/library/",   # IRIs and problem types are minted under it
    prefix="lib",                          # database and bucket names start with it
    tenant_segment="libraries",
    creator_role="librarian",
    roles_claim=zitadel_roles_claim(project_id),
)
async with (
    FusekiStore(fuseki_url, fuseki_user, fuseki_password) as store,
    ZitadelIdentity(issuer, service_token, organisation_id, project_id) as identity,
    JwksTokenVerifier(issuer, project_id, zitadel_roles_claim(project_id)) as verifier,
):
    files = S3FileStore(s3_endpoint, access_key_id, secret_access_key, region)
    app = build_library_app(
        store=store, files=files, identity=identity, verifier=verifier, settings=settings
    )
    server = uvicorn.Server(uvicorn.Config(app, port=8000))
    await server.serve()                   # runs the app's start-up, then serves until stopped
----

Run the whole block in one coroutine (`asyncio.run(main())`), so the adapters stay open while the
server runs and close when it stops.

To see traces and structured logs, install the OpenTelemetry SDK and call your telemetry set-up
first in this composition root, before the stores are built; the toolkit installs none itself.
See xref:howto/observability.adoc[See what the toolkit is doing].

== The token verifier

The verifier takes the issuer, the audience (the Zitadel project id) and the roles claim. It
refuses an issuer that is not `https` unless you pass `allow_insecure_issuer=True`, which is for
test containers only. In Zitadel, set each application to JWT access tokens: the verifier cannot
check opaque ones.

[#verifier-options]
Two more values have defaults (xref:adr/adr-004-signing-algorithms.adoc[ADR-004]). They are fields
of `JwksSettings`, the `jwks` group of `ToolkitSettings`, and you pass the group as `jwks=`:

* `allowed_algorithms`, the signature algorithms it accepts. The default is RS256, RS384, RS512,
  PS256, PS384, PS512, ES256, ES384, ES512 and EdDSA, which covers every key Zitadel can sign with.
  Give a shorter list to accept fewer. `JwksSettings` raises pydantic's `ValidationError` for an
  empty list, `none` or an `HS*` name in any case. The verifier raises `ValueError` when it is built
  for a name the installed PyJWT does not implement. A post-quantum algorithm is not accepted until
  the identity provider and PyJWT both ship it.
* `leeway_seconds`, the clock skew allowed on `exp` and `nbf`: 30 seconds by default, a number from
  0 to 300 (`ValidationError` otherwise). A token that expired up to that long ago is still
  accepted, so set `leeway_seconds=0` if a client counts on an exact expiry.

[source,python]
----
from rdf_persistence import JwksSettings

verifier = JwksTokenVerifier(
    issuer, project_id, zitadel_roles_claim(project_id),
    jwks=JwksSettings(allowed_algorithms=["ES256", "ES384"], leeway_seconds=10),
)
----

== What install_service does

`install_service` mounts the routes (<<routes>>), the problem responses and the OpenAPI document.
On start-up, before your own lifespan, it creates the system database if it is missing, guards the
IRI policy (xref:user-manual/iri-policy.adoc#policy-cannot-change[The policy cannot change]), creates the application database if the schema has an application class, migrates the system and application databases, runs the sweep (on every wired store, see xref:howto/tenant-stores.adoc#startup[Put tenants on several stores]), and migrates the tenants, each on its own store. It stops with `OSError` if the generated folder lacks the context, the shapes, a frame or
`openapi-components.json`, and with `LookupError` if the schema has no tenant root or not exactly
one access record class.

[#workflows]
If a class of your schema follows a workflow, pass the workflow files too, as a sequence of paths:
`install_service(app, ..., workflows=[Path("models/workflows/review.workflow.yaml")])`. They are checked
here, before the service serves. See xref:howto/workflow.adoc[Put a resource through review].

* *Paths.* A relative path is opened as given (`install_service` does not resolve it against the
  schema or the file that holds the call), so it is relative to the working directory of the
  process. Start the service from the same folder every time, or build the paths from
  `Path(__file__)`. This holds for `rules=` and `workflows=` alike.
* *Each file is listed.* `workflows=` takes the files, one path each. A folder or a glob is not
  expanded: it is a file that cannot be read, and stops the start with `InvalidWorkflow`.
* *A class names a workflow no file defines* (the file is left out of the list, or the class's
  `workflow` tag has another name): `InvalidWorkflow`, naming the class and the files given.
* *A workflow no class names* is accepted and loaded; it governs no class.
* *A wrong, stale or missing file* stops the start, naming the file. For a workflow file that is
  `InvalidWorkflow`: the file cannot be read or is not YAML, is no mapping, gives a key twice, is
  no valid workflow, or a transition names a role that no role definition has (the usual sign of a
  workflow file left from an older model). For the roles file it is `InvalidRoleDefinition`: it
  cannot be read, is not UTF-8, gives a key twice in an entry, or holds an invalid entry.

A model drawn in UML and converted with `rp-uml2linkml` has both files written for you; the
steps are in xref:howto/uml-to-linkml.adoc#serve[Generate the model from UML].

To react to commits (run a use case as a command, or call code after every commit), build a bus
and set `kit.bus`; see xref:howto/event-driven.adoc[React to changes with commands and observers].

[#smallest]
== The smallest composition root

The shortest call serves a schema with no workflow and the roles file as `rules`:

[source,python]
----
install_service(
    app,
    schema=Path("models/library.yaml"),
    generated=generated,
    store=store,
    files=files,
    identity=identity,
    verifier=verifier,
    rules=Path("models/library.roles.yaml"),
    settings=settings,
    migrations=Path("migrations"),
)
----

For a toy service, pass `FakeStore()`, `FakeFileStore()` and `FakeIdentity()` from
`rdf_persistence.testkit` as `store`, `files` and `identity` (see
xref:user-manual/test.adoc#whole-service[The whole service over the fakes]); nothing else needs to
run. Everything else has a default. `workflows` defaults to none, which stops the start when a class
names a workflow.

== The service kit

`install_service` returns the *`ServiceKit`*, for your own routes and domain services:

[cols="2,3",options="header"]
|===
|Member |Use
|`require(authorization, tenant_id, action)` |Verify the token and check `action` on the tenant;
returns an `Authorised` with the caller's `principal`, its `caller_access`, and the tenant IRI as
`checked_target`
|`require_aggregate(authorization, tenant_id, rp_path, aggregate_id, action)` |The same on one
aggregate, so a prohibition on it applies; returns an `Authorised` whose `checked_target` is the
aggregate IRI that was checked
|`session(tenant, principal)` |A session on the tenant's database (xref:user-manual/store-and-read.adoc[Store and read aggregates in a domain service])
|`bucket_of(tenant)` |The tenant's bucket name
|`tenancy`, `store`, `files`, `identity`, `view`, `settings` |The tenancy service, the ports (`store` is the `Store` you passed, wrapped as `ToolkitStore`), the loaded schema and the settings
|`tenant_iri(tenant_id)` |The tenant IRI of a tenant id taken from a path; `NotFound` if the IRI
policy does not mint such an id
|`iris` |The one `Iris` of the service, built from the settings and the schema; the services the kit
wires and its `rules` all use it
|`collaboration(authorised)` |An async context manager: comments, transitions, collections and
reverse references for the caller `require` authorised, each call checked (xref:howto/discussion.adoc[Comment on a resource], xref:howto/workflow.adoc[Put a resource through review])
|`remove_with_files(tenant, principal, iri, if_version)` |Remove an aggregate and the blobs only it
names (xref:user-manual/files.adoc#keep-a-files-bytes[Keep a file's bytes])
|`sweep_tenant(tenant, ...)` |Find, and optionally delete, the loaded graphs and blobs nothing
owns in a live tenant; a dry run by default (xref:user-manual/files.adoc#sweep-live-tenant[Sweep a live tenant])
|`dump_tenant(tenant, out)`, `restore_tenant(src, creator, store=...)` |Write a tenant to one
archive; create a new tenant from one (xref:howto/dump-restore.adoc[Back up or copy a tenant])
|`store_of(tenant)` |The store that holds the tenant's database (xref:howto/tenant-stores.adoc[Put tenants on several stores])
|`require_application(authorization, action)`, `application_session(principal)`,
`application_iri(cls)` |The check, the session and a new IRI for data that belongs to no tenant
(xref:howto/application-data.adoc[Keep data that belongs to no tenant])
|`bus` |The message bus commits are published to; set it once its handlers exist
(xref:howto/event-driven.adoc[React to changes])
|`event_bus`, `relay`, `hub`, `receive` |The event bus given to `install_service`, the relay that
carries every commit to it and to the event stream, the hub of the live streams, and what the event
bus delivers to (xref:howto/event-driven.adoc#relay[Carry commits to other deployments])
|`mapper`, `models` |The mapper and the generated classes, for a `UnitOfWork` (xref:user-manual/store-and-read.adoc[Store and read aggregates])
|`workflows` |The loaded workflow files (xref:howto/workflow.adoc[Put a resource through review])
|`gate`, `rules`, `verifier` |The token and access checks the routes run, the access rules, the
token verifier (`gate.caller` verifies a token where there is no tenant yet, as
xref:howto/dump-restore.adoc[the restore] does)
|`toolkit`, `max_body_bytes`, `max_restore_bytes` |The `ToolkitSettings` and the two size limits
of the settings (xref:howto/settings.adoc[Configure the deployment values])
|===

A route of your own that calls a domain service needs the caller's principal IRI as well. The
`Authorised` that `require` and `require_aggregate` return carries it. Here the route calls
`add_chapter` of xref:user-manual/store-and-read.adoc[Store and read aggregates]:

[source,python]
----
checked = await kit.require_aggregate(
    request.headers.get("authorization"), t, "books", book_id, Action.MODIFY
)
await add_chapter(
    kit, mapper, checked.caller_access.tenant, checked.principal, checked.checked_target, number
)
----

[#routes]
== The routes

The *router* serves every aggregate root of the schema that has an `rp_path`. A class added to the
model is served after a restart:

[cols="2,3",options="header"]
|===
|Route |Methods
|`/{tenant_segment}` |`GET` the caller's tenants; `POST` a new tenant
|`/{tenant_segment}/{t}` |`GET`, `PUT` the tenant's root object; `DELETE` the tenant
|`/{tenant_segment}/{t}/grants` |`GET`, `PUT` the grant set
|`/{tenant_segment}/{t}/label` |`PUT` the label
|`/{tenant_segment}/{t}/{rp_path}` |`GET` a listing; `POST` a new aggregate
|`/{tenant_segment}/{t}/{rp_path}/{id}` |`GET`, `PUT`, `DELETE` one aggregate
|`/{tenant_segment}/{t}/rp-events` |`GET` the tenant's changes as server-sent events (xref:howto/event-driven.adoc#sse[Follow a tenant in the browser])
|`/context.jsonld` |`GET` the generated JSON-LD context
|`/openapi.json` |`GET` the OpenAPI document (FastAPI's path, not under `prefix`)
|===

What a client sends and gets on each route (the token, the headers, the bodies, paging, the
problems and the event stream) is in xref:reference/http-api.adoc[The HTTP API].

A client creates a book with `POST /libraries/{t}/books` and a plain JSON body without ids:

[source,json]
----
{"label": "Dune", "description": "A planet.", "authors": ["Frank Herbert"], "chapters": [{"number": 1}]}
----

The answer is 201, with the stored book (ids minted), its `ETag` and a `Location`. A `PUT` of the
same body with `"id"` set and `If-Match` replaces it. Bodies are strict, and every error is an
RFC 9457 problem. Why the service follows these rules (headers, representations, strict bodies,
problems, listings) is explained in xref:architecture/api.adoc#serving[A lightweight API], and the order of the checks on a
`PUT` is in xref:architecture/api.adoc#anatomy[Anatomy of a request].

The generated TypeScript types describe the plain JSON a client sends and receives. A client that
sends `Accept` with another type gets the aggregate as JSON-LD, Turtle, N-Triples, N-Quads, TriG or
RDF/XML (see xref:architecture/api.adoc#representations[Representations]).

[#etag-proxy]
=== Behind a reverse proxy

*A reverse proxy must not weaken the `ETag`.* A write compares the `ETag` the client echoes in
`If-Match` with the stored version, and the comparison is strong: a weak tag (`W/"v7"`) never
matches, so the write answers 409. Some proxies turn a strong `ETag` weak when they change the body;
nginx does it when it compresses a response with gzip. Behind such a proxy every client that echoes
the tag gets 409 on every write, and no write succeeds. Either do not let the proxy compress the
service's responses (in nginx, `gzip off;` for the service's location), or make it pass the `ETag`
through unchanged (in nginx, a compressed response keeps a strong tag only when the location has
`gzip off;`). Test it: read an aggregate through the proxy with `Accept-Encoding: gzip`, as a
browser does (without it nginx does not compress, and the test passes behind the very proxy that
breaks real clients), then `PUT` it with the `ETag` you were given, and expect 200.
