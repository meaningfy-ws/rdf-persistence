= Generate the code
:description: The rp-generate manual: the [tool.rp-generate] entries, what it writes where, --check, exit codes, several targets and the command-line options.
:page-revised: 2026-11-10 by the developer

_How do I turn the model into code?_

This page is the manual of `rp-generate`, the command that turns the model written in
xref:user-manual/model.adoc[Write the model] into the generated package: its configuration, what it
writes where, its check mode, its exit codes and several targets in one project. Afterwards the
generated files sit beside the schema, ready for
xref:user-manual/generated-classes.adoc[Use the generated classes and guard them]. Why the toolkit
generates its models, and how the generator works inside, is in
xref:architecture/generation.adoc[Model to code].

[#configure]
== Configure it

Declare where each artefact goes, in a `[tool.rp-generate]` table of `pyproject.toml`:

[source,toml]
----
# pyproject.toml
[[tool.rp-generate]]
schema = "models/library.yaml"
package = "library.domain.generated"
migrations = "migrations"
typescript = "web/src/domain/generated"
toolkit-typescript = true  # this folder holds the toolkit's modules
diagrams = "docs/model"
regenerate-command = "make generate"  # optional

[[tool.rp-generate]]
schema = "services/loan_checks_response.yaml"
package = "library.services.generated"
typescript = "web/src/services/generated"  # imports the toolkit's modules from the entry above
----

A project with one entry may write it as a single `[tool.rp-generate]` table; the second entry is
only needed when a second folder receives TypeScript.

[cols="2,2,5",options="header"]
|===
|Key |Required |Value

|`schema` |always |the root LinkML schema file
|`package` |always |the Python import path of the generated package, a dotted identifier
|`migrations` |when the schema defines aggregate roots of its own |the folder of the schema lock and the migration files
|`python` |no |the folder that receives every Python-side file (see <<outputs>>); the `package` path when absent
|`typescript` |no |the folder of the TypeScript types; none are written when absent
|`toolkit-typescript` |no (default `false`; required on exactly one entry when two or more set `typescript`) |`true` makes this entry's `typescript` folder the one that holds the toolkit's shared modules (`rp_core.ts`, `rp_service.ts` and the rest); the other TypeScript entries import them from it. It needs `typescript` on the same entry
|`diagrams` |no |the folder of the Mermaid diagrams; none are written when absent
|`openapi` |no (default `true`) |`false` leaves out `openapi-components.json`
|`regenerate-command` |no |the command named when the freshness check fails; `rp-generate` when absent
|===

Without `schema` or `package`, `rp-generate` exits with code 2 and names the missing key; an
unknown key is refused the same way.

*Migrations.* A schema that defines aggregate roots of its own needs `migrations`, and its root
schema then carries a quoted `version:` (`version: "1"`), since an unquoted `1.10` is read as a
number and loses its zero. Without them the hard check fails. `rp-generate` keeps the lock,
`schema.lock.json`, in that folder, and when the version changes it drafts a migration there for
you to review (see xref:howto/migrate.adoc[Change a schema that has stored data]).

*`python`.* Set it only when the Python folder is not the `package` path, for example
`python = "src/library/domain/generated"`; `package` stays the import path.

*`openapi = false`* is safe only if you never call `install_service`
(xref:user-manual/serve.adoc[Serve the application]): it stops with `OSError` when the file is
missing.

*Paths.* `rp-generate` reads the `pyproject.toml` in the folder you run it from. It does not
search upward: from another folder it exits with code 2, unless you pass
`--project path/to/pyproject.toml`. Every path in `[tool.rp-generate]` is relative to that file,
not to the folder you run the command from, and it must stay inside its folder: an absolute path
or one with `..` is refused. The Python folder is the `package` path with the dots turned into slashes (`library/domain/generated`). It does not have
to exist: `rp-generate` creates it, and its parent folders, and writes an `__init__.py` into it
only. `library/` and `library/domain/` get none; Python imports them as namespace packages, so add
your own `__init__.py` only if a tool needs it.

[#run]
== Run it

Add a make target that runs `uv run rp-generate`; it may have any name, and it may be the target
that already runs your other generators. Set the optional `regenerate-command` to the command you
type to run that target, as in the example above: `make generate`. It is only shown, never run: when
generated code is stale, the freshness check ends with "run `make generate` to regenerate, then
commit the result". Without it, the check names `rp-generate`, which skips `uv run` and anything
else your target does. The make target in this manual is called `generate`:

[source,makefile]
----
generate:
	uv run rp-generate
----

Run it: it prints `rp-generate: generated 1 target(s), no problems`.

`rp-generate` first checks the schema (lint, then the boundary, hard and rules checks, then the
schema lock), and writes nothing if any target fails a check: the output of every target is moved
into place only when all of them pass. The rules they enforce are listed in
xref:user-manual/model.adoc#rules[The rules a schema follows], in full in
xref:architecture/generation.adoc#hard-check[The hard check].

[#outputs]
== What it writes

[cols="2,2,4",options="header"]
|===
|Folder |Files |What they are

|`python` (by default the `package` path, here `library/domain/generated/`)
|one module per schema module (`books.py`, `library.py`), `__init__.py`
|the generated classes. `__init__.py` is empty, unless schema modules import each other: then it completes their classes (<<module-cycles>>)
|`python`
|`shapes.ttl`, `context.jsonld`, one `<Class>.frame.jsonld` per aggregate root and per activity class
|the SHACL shapes, the JSON-LD context and the frames
|`python`
|`openapi-components.json` (unless `openapi = false`)
|the component schemas of the service's OpenAPI document
|`python`
|`rp-manifest.json`
|the hashes the freshness check compares
|`migrations`
|`schema.lock.json` and a drafted migration when the `version:` changes
|see xref:howto/migrate.adoc[Change a schema that has stored data]
|`typescript`
|one file per module the target owns, `index.ts`, `rp_service.ts`; a module another target writes as TypeScript is imported from that target's folder; in a project with several TypeScript entries, the toolkit's modules only in the entry with `toolkit-typescript`
|the TypeScript types
|`diagrams`
|one `.mmd` file per module
|the Mermaid class diagrams
|===

`rp_service.ts` holds the classes of the toolkit's eight served schemas, in this order
(`rp_iris_services.yaml` of the `iris` theme, `rp_persistence_services.yaml` of `persistence`,
`rp_migrations_services.yaml` of `migrations`, `rp_access_services.yaml` of `access`,
`rp_tenancy_services.yaml` of `tenancy`, `rp_events_services.yaml` of `events`,
`rp_collaboration_services.yaml` of `collaboration` and `rp_api_entrypoints.yaml` of `api`), among
them the API's wire types (`TenantCreate`, `TenantSummary`, `LabelUpdate`, `GrantSet`, `Page`,
`Migration`, `MigrationStep`, `EventEnvelope`, `Referrer` and `Problem`). The module name
`rp_service` and the names of the classes and enums of the served schemas are reserved
when a target renders TypeScript: a schema that uses one is refused, naming the clash. What each
file holds, and the extension that renders it, is in
xref:architecture/generation.adoc#extensions[Generated artefacts, extensions and where they go].

Commit the generated files together with the schema. Never edit them: to change the code, change
the schema and generate again.

[#module-cycles]
*Schema modules that import each other.* Two modules may refer to each other's classes, for
example `Book` in `app_books` with a slot whose range is `Shelf`, and `Shelf` in `app_shelves` with
a slot whose range is `Book`. `rp-generate` writes Python that loads whichever module is imported
first. The package's `__init__.py` is then not empty: it imports the modules, binds the classes they
only name in annotations, and completes the classes. Three rules follow:

* Import the package, never a module by its file path (`importlib` on the `.py` file, or running it):
  `__init__.py` must run first.
* Import a class from the module that declares it, or from the root module. `from .app_books import Shelf`
  runs when `Shelf` is declared in `app_shelves`, but `mypy --strict` refuses it, because
  `app_books` only names `Shelf` and does not export it.
* A class that needs a class of the other module while the module loads (a parent class, a default
  instance, a union alias) cannot be deferred. If each module needs one from the other this way,
  `rp-generate` exits 1 at the `python` step and writes nothing, with a message such as
  `app_a, app_b import each other and need app_a.Root, app_b.Base while they load (a parent class,
  a default instance or a union): put these classes in one module, or break the cycle`.
  Do one of the two: move the classes into one module, or break the cycle, for example by moving
  the parent class so that only one module needs a class of the other while it loads.

A file an earlier run wrote and this one does not, such as the module of a schema file you removed
or renamed, is deleted by the next run, unless it was edited since: then the run keeps it, says
`kept <file>: it changed since it was generated; delete it if it is stale` and exits 1, with the
new output already in place. Before you regenerate, `--check` reports the removed schema file as
`stale input: models/<file>.yaml (removed)`.

[#check]
== Check without writing: `--check`

The freshness check is `uv run rp-generate --check`. It writes nothing. It runs the same schema
checks as a generation, then compares the generated files with the hashes in each
`rp-manifest.json`: a changed input (the schema, or the toolkit's generator after an upgrade) or a
different `linkml` version is reported as stale, a changed output as edited by hand. Without the
`generate` extra it compares the hashes only.

On success it prints `rp-generate: checked 1 target(s), no problems` and exits 0. Before the first
generation it exits 1 with `no readable manifest: library/domain/generated/rp-manifest.json`.
xref:user-manual/generated-classes.adoc#guard[Guard the model in your tests] says how to run it in
your tests, in CI and as a pre-commit hook; the manifest itself is described in
xref:architecture/generation.adoc#guarding[Guarding the generated code].

[#exit-codes]
== Exit codes

[cols="1,5",options="header"]
|===
|Code |Meaning

|0
|Done: it prints `rp-generate: generated N target(s), no problems` (or `checked`, with `--check`).
|1
|Problems found, one line each on standard error, as `<schema>: <step>: [<rule>] <element>: <message>`:
a schema that breaks a rule of xref:user-manual/model.adoc#rules[The rules a schema follows], a
missing or unreadable `schema` file, a stale or edited file (`--check`), or a stale file kept
because it was edited.
|2
|It cannot start: a missing or unknown key, a refused path, no `[tool.rp-generate]` entry (and no
`--schema` and `--package` flags), a flag given with several entries, or, when generating, no
`generate` extra.
|===

[#technical-target]
== Keep technical models in a target of their own

One project may generate several targets. The usual reason is to keep technical models (a
request body, a setting, a wire shape) apart from the domain classes the toolkit stores, in a
folder and a package of their own, so a reader tells them apart by the path; the toolkit does this
for its own models (xref:architecture/generation.adoc#kinds[Two kinds of model]).

Write them in a schema annotated `module_kind: technical`, in a folder beside the domain schemas,
and give it its own entry. With two entries, `[tool.rp-generate]` becomes `\[[tool.rp-generate]]` on
each of them (an array of tables). An entry has no `kind` key: `rp-generate` derives the kind of a
target from its modules. A target is technical when every module it generates is annotated
`module_kind: technical`, and domain otherwise. If your `models/` folder holds a `technical` module
(xref:user-manual/model.adoc#more-metamodel[More of the metamodel]), move it into the new folder
first (`technical/export.yaml` below): a target generates one kind, and the check reads the modules
the target generates, which are the modules its root schema imports from its folder.

[source,toml]
----
# pyproject.toml
[[tool.rp-generate]]
schema = "models/library.yaml"
package = "library.domain.generated"
migrations = "migrations"

[[tool.rp-generate]]
schema = "technical/export.yaml"
package = "library.services.generated"
openapi = false
----

`rp-generate` generates both, in order, and writes nothing unless both pass. `migrations` is
optional on the technical entry: only a schema that defines aggregate roots of its own needs it,
and a technical module stores nothing.

The derived kind decides which folder the package may sit in: the segment before `generated` is
`domain` for a domain target, and `services`, `adapters` or `entrypoints` for a technical one.
When the package is in the wrong one, `rp-generate` exits 1 and names the entry's schema and the
package. Here `technical/export.yaml` lacks its `module_kind: technical` annotation, so the target
is domain, and its package is in a technical layer:

----
technical/export.yaml: boundary check: [target_kind] library.services.generated: is not in a folder a domain target allows: domain before generated; if its modules are technical, annotate them module_kind: technical
----

A package with no layer before `generated` (`library.generated`) fails the same way:

----
models/library.yaml: boundary check: [target_kind] library.generated: has no layer before generated: a domain target's package ends in <domain>.generated
----

A target whose root schema imports both a technical module and a domain one, such as a root in
`models/` that imports a `technical` module beside the domain ones, fails and names the technical
modules; split them into targets as above:

----
models/library.yaml: boundary check: [target_kind] generates technical modules export beside domain ones: a target generates one kind
----

Two limits:

* A technical model cannot use a class of your domain target, so one that holds a domain value
  stays in the domain target's folder.
* `install_service` reads the components of one generated package, the `generated=` you give it,
  which is the target with your aggregate roots: that target needs `openapi` on, and the technical
  target needs it only if you want its file. A request body that your domain uses stays in the
  domain target, without the `module_kind` annotation.
* `openapi-components.json` holds the schemas the toolkit's own routes serve. The routes you write
  yourself take their OpenAPI schemas from FastAPI, out of the Pydantic models you give them, not
  from that file.

[#options]
== Command-line options

include::partial$reference/rp-generate-usage.adoc[]

Run with no option, `rp-generate` generates every entry of `./pyproject.toml`.

* `--project` names another `pyproject.toml`; paths stay relative to that file's folder.
* `--schema`, `--package`, `--python-out`, `--typescript-out` and `--diagrams-out` override the
  keys `schema`, `package`, `python`, `typescript` and `diagrams` of the only entry. With no entry,
  `--schema` and `--package` together make one. With several entries, any of them exits with
  code 2.
* `--check` writes nothing (<<check>>).
* `--list-python-folders` prints the Python folder of each entry, relative to the folder you run
  it from, and exits; a make target can read it.
