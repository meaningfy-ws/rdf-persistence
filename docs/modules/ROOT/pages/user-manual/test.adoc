= Test the service
:description: Test the service over the testkit's fakes and against containers.
:page-revised: 2026-11-10 by the developer

_How do I test my application without servers?_

The testkit lets you run your whole service, or one domain service, in memory, with no store,
object store or identity provider running. This page lists its stand-ins, shows the toy library's
service built over them, and names the conformance suites that check an adapter of your own. The
guards that keep generated code untouched are in
xref:user-manual/generated-classes.adoc#guard[Guard the model in your tests].

== The fakes

`rdf_persistence.testkit` has in-memory stand-ins for the four ports:

[cols="2,3",options="header"]
|===
|Helper |Stands in for
|`FakeStore()` |a `Store` (a small in-memory SPARQL store)
|`FakeFileStore()` |a `FileStore`
|`FakeIdentity()` |an `Identity`
|`TokenSigner()` |the identity provider's keys: `issue(sub=…, roles=[…])` signs a token, and `transport` serves the keys to a `JwksTokenVerifier`. Generating its RSA key takes ≈ 0.03 to 0.06 s (measured 2026-11-16, 2048 bits); when many tests each build a signer, take one key per process from `shared_key()` (from `rdf_persistence.testkit`, cached) and pass it as `TokenSigner(key=…)` (each signer still starts with its own state). Use `new_key()` only where a test needs a key of its own, for example to show that a token signed by another key is refused
|`fake_session(store, *, tenant_iri, principal, clock, iris, listings)` |a real `Session` over a `FakeStore`,
for a domain service's unit test; pass `iris` to test under your own IRI policy, and
`listings=Listings(view)` (both from `rdf_persistence`) to use `find`
|===

[#whole-service]
== The whole service over the fakes

The toy library's router tests build the whole service over them (`tests/toy_service.py`).
`SCHEMA`, `ROLES`, `REVIEW_WORKFLOW`, `MIGRATIONS`, `generated` and `settings` are those of the composition root in
xref:user-manual/serve.adoc[Serve the application]; `TENANT_BODY` is a tenant create body as in
xref:user-manual/tenants.adoc#create-a-tenant[Create a tenant]:

[source,python]
----
import httpx
from fastapi import FastAPI

from rdf_persistence import JwksTokenVerifier, install_service
from rdf_persistence.testkit import FakeFileStore, FakeIdentity, FakeStore, TokenSigner

signer = TokenSigner()
settings = settings.model_copy(update={"roles_claim": signer.roles_claim})
verifier = JwksTokenVerifier(
    "https://idp.test", signer.audience, signer.roles_claim, transport=signer.transport
)
app = FastAPI()
kit = install_service(
    app,
    schema=SCHEMA,
    generated=generated,
    store=FakeStore(),
    files=FakeFileStore(),
    identity=FakeIdentity(),
    verifier=verifier,
    rules=ROLES,
    settings=settings,
    workflows=[REVIEW_WORKFLOW],
    migrations=MIGRATIONS,
)
headers = {"Authorization": f"Bearer {signer.issue(sub='ada', roles=[])}"}
async with app.router.lifespan_context(app):     # start-up: the system database, the policy guard, the migrations and the sweep
    transport = httpx.ASGITransport(app=app, raise_app_exceptions=False)
    async with httpx.AsyncClient(transport=transport, base_url="http://test") as client:
        created = await client.post("/libraries", json=TENANT_BODY, headers=headers)
----

`https://idp.test` is the issuer `TokenSigner` signs for. `ASGITransport` does not run the app's
lifespan, so the test enters it itself; without it the system database does not exist.

[#event-stream]
== Follow a tenant's event stream

_How do I test that a reader can follow a tenant's changes?_

`httpx`'s `ASGITransport` waits for the end of the response, and the route
`GET {prefix}/{tenant_segment}/{tenant}/rp-events` ends only when the follower leaves or
`max_lifetime_seconds` passes (see xref:howto/event-driven.adoc#sse[Follow a tenant in the browser]).
A test that follows the stream through `ASGITransport` hangs. `open_event_stream` opens the stream
in process, reads the response head and, if you ask, the first events, then leaves:

[source,python]
----
from rdf_persistence.testkit import open_event_stream

async def test_a_reader_follows_the_tenant(app, token, tenant):
    opened = await open_event_stream(
        app,                                         # the app install_service set up
        f"/api/libraries/{tenant}/rp-events",        # {prefix}/{tenant_segment}/{tenant}/rp-events
        headers={"Authorization": f"Bearer {token}"},
        events=0,                                    # how many events to wait for before leaving
        timeout=3.0,                                 # seconds
    )
    assert opened.status == 200
    assert opened.headers["content-type"].startswith("text/event-stream")
    assert opened.events == []
----

The signature is `open_event_stream(app, url, *, headers=None, events=0, timeout=3.0)`. It returns
an `OpenedStream`:

[cols="1,3",options="header"]
|===
|Field |Holds
|`status` |the HTTP status
|`headers` |the response headers, a dict with lower-case names
|`events` |a list of `StreamEvent`, each with `.id`, `.event` and `.data` (`None` when the event has no such field)
|===

The call returns as soon as one of these holds:

. The head arrived and `events=0`: it returns the head and `events == []`.
. `events` events arrived.
. The response ended: it returns the events so far, which may be fewer than you asked for. A refusal
  (401, 403 or 404) ends the response at once, so it returns its status with `events == []` and
  does not wait for the timeout.

If none holds within `timeout`, it raises `TimeoutError` naming the URL. The one deadline bounds the
head and the events together.

The other outcomes:

* The start-up of the app's lifespan is outside `timeout`: it counts the head and the events only.
* An app that raises before it sends the head: the call raises that exception.
* An app that raises after the head: the read ends with the events that came, and the call returns
  them without the exception.
* An app that ends without sending a response: the call raises `RuntimeError`.
* A negative `events` or a `timeout` of 0 or less: the call raises `ValueError`.

=== Hear a commit

A follower hears only the commits that come after it subscribes. To test that a commit reaches a
reader, start the call as a task, wait until the stream is subscribed, then commit, then await the
task:

[source,python]
----
import asyncio

stream = asyncio.ensure_future(
    open_event_stream(app, url, headers=headers, events=1)
)
# wait until the stream is subscribed (your fixture, never a fixed sleep)
await commit_a_change()
opened = await stream
assert opened.events[0].id == activity_iri
----

The `timeout` counts from the call, so when the test commits after starting the task, give it room
for those commits (a few seconds more than the commits take); the call still returns as soon as the
events came.

If the test can fail between starting the task and awaiting it, cancel the task in a fixture or a
`finally`, so that no stream is left running.

=== Prove that nothing came

Do not wait for a `TimeoutError` to show that a reader was not told about a change: it proves
nothing about order and slows the test. Commit a change the reader may see after the hidden one,
and assert that the first event is that sentinel. The stream delivers its events in order, so
nothing hidden came before it.

=== The app's lifespan

`open_event_stream` enters the app's lifespan for the length of the call only when the app has a
router lifespan and the toolkit's own lifespan has not started it already (it records this in
`app.state.rp_lifespan_started`). If your test already entered the lifespan, as in
<<whole-service,the whole service above>>, the helper does not enter it a second time. A raw ASGI
callable has no lifespan and gets none.

A test that holds several streams at once enters the app's lifespan itself, as the `service` fixture
of `tests/unit/api/conftest.py` does (`async with app.router.lifespan_context(app)`), so that the
helper does not enter and leave it once per call.

[#aim-a-fault]
== Aim a fault at the request

`FakeStore.on("update", error)` makes the next `update` raise, and the next `update` may not be
the request's: with the app's lifespan entered, the relay runs in the background and marks every
relayed activity with an `update` of its own. A relay round that starts first takes your fault, and
the request then succeeds, on some runs only. Run the request inside `kit.relay.paused()`: no round
starts while the block is open, so the request's own store call takes the fault. Commit inside the
block too, so that the pending activity is certain to be there:

[source,python]
----
service = ToyService()
async with service.app.router.lifespan_context(service.app):  # the relay runs only with the lifespan
    async with service.client() as client:
        async with service.kit.relay.paused():
            await client.post(f"{tenant}/books", json=body, headers=headers)  # a commit: an activity is pending
            service.store.on("update", StoreUnavailable("down"))
            answer = await client.post(f"{tenant}/books", json=body, headers=headers)
        assert answer.status_code == 503  # the request took the fault, on every run
        await testkit.wait_until_async(  # the relay runs its round on its own once the block closes
            lambda: activity_is_relayed(activity), "the activity is relayed"
        )
----

A wake-up during the block (every commit wakes the relay) makes one round after it, so the pending
activities are relayed once the block closes: wait for that, with a bounded wait, as above. Do not
call `run_once()` inside the block: it hangs.
The example is the feature test `tests/feature/test_testkit_faults.py`.

[#hold-writes]
== Hold concurrent writes

To test two writers that meet at one version, make their store calls meet with
`FakeStore.hold(operation, until, timeout=5.0)`. The first `until` calls of `operation` made inside
the block wait for each other; when the `until`-th arrives, they are released one by one in arrival
order, so the first arrival writes first and the second is refused by the version guard. The block
fails with `AssertionError` unless `until` calls arrived before the timeout released the waiters: a
call that comes after the timeout runs at once and does not count:

[source,python]
----
async with service.kit.relay.paused(), service.store.hold("update", until=2):
    a, b = await asyncio.gather(
        client.put(book, json=first, headers=headers),  # both carry the same If-Match
        client.put(book, json=second, headers=headers),
    )
assert sorted([a.status_code, b.status_code]) == [200, 409]
----

Hold `update` only inside `kit.relay.paused()`. The relay's own mark is an `update`: with the relay
running, it can be one of the calls that fill the hold, and the test becomes flaky. A waiting call
records nothing in `sent` and takes no armed fault until it is released, so `on` and `sent` see
the calls in release order. Calls after the `until`-th do not wait.

A hold that has not filled `timeout` seconds after its first call arrived releases its waiters, and
leaving the block then raises `AssertionError("hold('update', until=2) saw 1 call(s)")`: the test
learns that the second writer never came. An unknown operation or an `until` below 1 raises
`ValueError`, and a second hold on an operation that is already held raises `RuntimeError`. If the
block is left by an exception, the waiting calls are released and the exception propagates.

[#test-control]
== Test control for your project

The testkit carries the two tools the toolkit runs its own tests with, so your project does not copy
them. Both are plain modules run by name; they need the `pytest-testmon` and `pytest-xdist`
packages in your environment, and nothing else of the toolkit.

* `rdf_persistence.testkit.run_queue` takes one lock per user, so heavy runs of several
  repositories on one machine wait for each other, and replaces the argument `@workers` by a worker
  count taken from the cores and the free memory. `python -m rdf_persistence.testkit.run_queue
  --workers` prints that count.
* `rdf_persistence.testkit.selection_data` records which tests each source file reaches (the
  selection data of `pytest-testmon`) and swaps it in only when the recording run finished;
  `check` exits 0 for sound data and 3, 4 or 5 for damaged data, changed packages or no data.

In your Makefile:

[source,make]
----
QUEUE = uv run python -m rdf_persistence.testkit.run_queue --

test:
	$(QUEUE) pytest tests -n @workers

test-seed: export TESTMON_DATAFILE = .testmondata.seed
test-seed:
	$(QUEUE) python -m rdf_persistence.testkit.selection_data seed -- \
	  pytest tests --testmon --testmon-forceselect -n @workers -p no:randomly
----

The seed's clean, run and swap are one queued command, so no other session sees half-seeded data.
Add `.testmondata*` to `.gitignore`. Running the tests that a change reaches (`changed_tests`)
comes in a later release of the testkit; this section grows then.

== Check an adapter of your own

Before you rely on an adapter of your own, run the testkit's conformance suites against it:
`store_conformance`, `file_store_conformance` and `identity_conformance` under
`rdf_persistence.testkit`. Each has `CASES` and a `run_case` to run one of them on your adapter.
The toolkit runs the same suites on its fakes and on Fuseki, Garage, Zitadel and Redis in
containers; the fourth suite, `event_bus_conformance`, is for an event bus and runs on Redis. Its
`run_case` takes `poll_seconds` (default `POLL_SECONDS`, one second) for every wait of the case; a
bus that delivers within milliseconds can pass a shorter interval, such as `poll_seconds=0.05`.

To keep committed activities pending while a test looks at them, hold the relay with
`async with kit.relay.paused():`; no round runs inside the block, and `run_once()` called inside it
hangs, because the block holds the lock the round needs.
