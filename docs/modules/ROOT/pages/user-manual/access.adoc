= Control access
:description: Grant and check access per tenant and per aggregate; verify the caller's token; enforce your own rules on writes.
:page-revised: 2026-11-10 by the developer

_Who may do what?_

Access is checked per tenant and per aggregate, from roles you define, grants and prohibitions
stored in the tenant's access record, and the caller's verified token. This page shows how to
define the roles, grant them, what the check answers, and how to add rules of your own on tenant
writes. The token verifier itself is set up in xref:user-manual/serve.adoc[Serve the application];
why access works this way is in xref:architecture/access-control.adoc[Access control and identity].

== Define the roles

*Roles are data.* Write them in a YAML file. Each entry names a role, the level it applies at
(`system`, `tenant` or `aggregate`) and the actions it permits (`read`, `modify`, `delete`,
`administer`). The toy library's file (`tests/fixtures/library/library_roles.yaml` in the
toolkit's repository) is:

[source,yaml]
----
# models/library_roles.yaml
- {role: admin, level: system, actions: [read]}
- {role: librarian, level: tenant, actions: [read, modify, delete, administer]}
- {role: reader, level: tenant, actions: [read]}
- {role: app-editor, level: system, actions: [read, modify]}
----

A role that may change but not administer a tenant is one more entry; the toy has none. Extended
with this one, a `member` can delete the tenant's aggregates but not the tenant, which needs
`administer`:

[source,yaml]
----
- {role: member, level: tenant, actions: [read, modify, delete]}
----

`load_role_definitions(path)` reads and validates the file. A malformed entry, an entry with no
actions, or a role defined twice at one level raises `InvalidRoleDefinition`, which names the
entry. A `system` role comes from the token's global roles (the `roles_claim`); it is never
granted. The set of actions is fixed by the toolkit: an application cannot add one. Pass the
roles to `install_service` as `rules=AccessRules(load_role_definitions(path))`, or as the path
itself.

== Grant and prohibit

*Grants and prohibitions* live in the tenant's access record. `GET …/grants` answers the
`GrantSet` with its `ETag`; `PUT …/grants` with `If-Match` replaces it whole:

[source,json]
----
{
  "grants": [
    {"assignee": "https://idp.example.org/users/ada", "target": "https://example.org/library/libraries/6f1c…", "role": "librarian"},
    {"assignee": "https://idp.example.org/users/bob", "target": "https://example.org/library/libraries/6f1c…/books/0b7e…/graph", "action": "modify"}
  ],
  "prohibitions": [
    {"assignee": "https://idp.example.org/users/bob", "target": "https://example.org/library/libraries/6f1c…/books/0b7e…/graph", "action": "delete"}
  ]
}
----

* An *assignee* is a principal IRI. The JWKS verifier makes it from the token's issuer and
  subject: `{issuer}/users/{sub}`.
* A *target* is the tenant's IRI or an aggregate's graph IRI, `{root}/graph`. The level follows
  from the target.
* A *grant* gives exactly one of a `role` (defined at the target's level) or an `action`. Two
  grants with the same assignee, target and role or action are refused.
* A *prohibition* forbids one action and wins over every grant. A prohibition of `read` forbids
  every action, since each implies `read`.

*A refused `set_grants`.* `Tenancy.set_grants` and `PUT …/grants` check the new set the same way,
in one place: a role the roles file does not define at the target's level, or defines only at
system level, answers `UnknownRole` (422 `invalid-body` over HTTP) and writes nothing; a foreign
target or an assignee that is not an IRI answers `InvalidGrant`. Only the new set is checked, so a
tenant whose stored grants name a role that is no longer defined is not stuck: read the grants,
drop the grant the error names, and write the set again.

== What the check answers

*The check* runs on every tenant route, after the token is verified and before the route's own
code; your own routes run it with `kit.require` and `kit.require_aggregate`
(xref:user-manual/serve.adoc[Serve the application]). It answers in this order:

. The target is not the tenant or one of its aggregates: 404.
. The tenant is not `active`: 404.
. A prohibition in scope forbids the action: 403.
. The caller's grants in scope and its global roles permit no action at all: 404. A hidden tenant
  and a missing one answer alike.
. They do not permit this action: 403. Every other action implies `read`.

The scope is the tenant, plus the aggregate's graph for an action on one aggregate. A listing
needs `read` on the tenant and leaves out the aggregates a `read` prohibition hides from the
caller. Creating an aggregate needs `modify` on the tenant.

[#validators]
== Enforce your own rules on tenant writes

_How do I stop a write my application forbids, such as removing the last owner?_

Give `install_service` validators. A *grant validator* runs on every replacement of a tenant's
grants (`PUT .../grants`), with the old set, the new one and the caller. A *root validator* runs
when a tenant is created, its root is replaced or it is renamed, with the old root (`None` on
create), the new one and the caller; on create the caller is the creator, who gets the first grant.
To refuse, raise `InvalidBody`: the answer is 422 `invalid-body` with your message as its `detail`,
and nothing is written.

[source,python]
----
from pathlib import Path

from rdf_persistence import GrantSet, InvalidBody, Principal, install_service


def keep_a_librarian(old: GrantSet, new: GrantSet, who: Principal) -> None:
    if not any(g.role == "librarian" for g in new.grants or []):
        raise InvalidBody("a library keeps at least one librarian")


install_service(
    app,
    grant_validators=[keep_a_librarian],
    migrations=Path("migrations"),
    # ... and the other keyword arguments of the composition root
)
----

The other arguments are those of the composition root in
xref:user-manual/serve.adoc[Serve the application]; pass every argument by keyword.

Validators run in the order given, before the write; the first refusal stops it. They need no
lock: the write is conditional on the version the request sent (`If-Match`), so of two writes at
one version, both passing the rule, one lands and the other answers 409.

A validator is a plain function, not `async`: it runs on the event loop, so it must not block. A
coroutine function is refused when the service starts. It receives copies of the old and new
objects, so changing an argument has no effect on what is written. It returns nothing; returning a
value is a bug. Any exception other than `InvalidBody` or pydantic's `ValidationError` (also 422)
is a bug in the validator and answers 500, even another error of the toolkit such as `Forbidden`
or an `HTTPException`.

[#aggregate-validators]
== Enforce your own rules on aggregate writes

_How do I refuse a write to an aggregate that breaks a rule of my application, such as two members of one kind?_

Give `install_service` `aggregate_validators`: a mapping from a schema class name to a list of
rules. `ServiceKit` takes the same argument. A rule runs on every write of a root of that class, or of a
class derived from it. It receives the old root (`None` on create), the new root, the caller and a
*reader*. To refuse, raise `InvalidBody`: the answer is 422 `invalid-body` with your message as its
`detail`, and nothing is written.

[source,python]
----
from rdf_persistence import InvalidBody, install_service


def one_of_each_kind(old, new, who, reader):  # plain: ignores the reader
    kinds = [kind_of(i) for i in new.has_part or []]
    if len(kinds) != len(set(kinds)):
        raise InvalidBody("A shelf holds at most one collection of each kind.")


async def members_differ_in_class(old, new, who, reader):  # async: reads classes
    seen = [await reader.classes_of(i) for i in new.has_part or []]
    known = [c for c in seen if c]
    if len(set(known)) < len(known):
        raise InvalidBody("two members of one class")


install_service(
    app,
    aggregate_validators={"Shelf": [one_of_each_kind, members_differ_in_class]},
    # ... and the other keyword arguments of the composition root
)
----

`aggregate_validators` is a `Mapping[str, Sequence[AggregateValidator]]`, empty by default.
A rule is a function or a coroutine function; both take `(old, new, principal, reader)` and return
nothing. `old` and `new` are copies of the generated model, so changing them has no effect on what
is written. `new` is what is about to be written: for a class under a workflow, it carries the
state the toolkit kept.

Rules run in a fixed order: those of the most general class first, then those of the more specific
ones, and each list in the order given. The first refusal stops the write. If a root has two
types that are not on one line of descent (a `Shelf` that is also a `Book`) and a rule applies to
either, the write is refused with 422 naming both types, so a client cannot pick a type that
escapes a rule.

=== Ask the reader about other aggregates

`reader.classes_of(iri)` answers with the set of class names of the aggregate at `iri`: its own
types, not their ancestors; any class of the schema counts, the toolkit's too (a `Comment`). It answers an empty set when there is no such aggregate, when the
value is not an aggregate IRI (a literal, a foreign or a malformed IRI) and when the caller may not
read it. A hidden aggregate and an absent one look the same, so a rule cannot be used to find out
whether a hidden aggregate exists.

The reader answers for the caller of these writes: an HTTP create or replace (the tenant root's
PUT included), a rename, a workflow transition, a collection edit and a comment. A write with no
caller behind it reads every class: a message-bus handler, an `on_commit` handler or your own unit
of work. Then a message of a rule may name a class that the person behind the message cannot
read. For a comment, the reader judges the comment as any aggregate, not by its thread, so a rule
may see as unknown a comment that the thread would show.

Inside one unit of work, the reader sees the changes collected before the one being checked, and
not those collected after it. A member added earlier is seen with its types; one added later is
unknown. A member removed earlier is unknown too: `classes_of` answers empty and `aggregate`
answers `None`. Put the rule's dependencies in the order they should be seen.

=== Read a referenced aggregate

`await reader.aggregate(iri)` hands over the aggregate at `iri` as its generated model, with
its tracking when it is stored, or `None` in every case where `classes_of` answers an empty set,
and also when its root types name no single root class. The rule gets its own copy: changing it
has no effect on what a later rule or the write sees. The store is read once per transaction for
each aggregate, however many rules ask. For an aggregate that an earlier change of the same unit of
work added, the reader hands over the triples as collected, with no tracking.

[source,python]
----
async def due_after_publication(old, new, who, reader):
    book = await reader.aggregate(new.lends)  # a Loan names the Book it lends
    if book is not None and book.published and new.due < book.published:
        raise InvalidBody("a loan cannot be due before the book was published")
----

A model that does not decode, stored or collected, is a bug on your side and not the client's: the
answer is 500, a `RuntimeError` naming the aggregate.

The write now depends on the version of what it read:

* *The version dependence.* The commit fails with 409 `conflict`, naming the aggregate, if that
aggregate changed between the read and the commit. Where many writes name one aggregate and it is
edited often, expect more retries; nothing is lost, and the client retries after re-reading. If
the same transaction has already relied on the aggregate at another version, the read itself is the
409.
* *The rule runs on this side only.* A rule on the loan is not run again when the book changes, so
the book's edit can break the order the rule checked. Where that matters, put the symmetric rule on
the book: a rule on `Book` that refuses an edit that would break the order from the book's side,
for example one that moves `published` later than a due date you can read.
* *A remove after a read.* If one unit of work reads an aggregate in a rule and removes it
later, the rule judged it as it was, and the commit holds both changes.
* *A rule on the root it writes.* `reader.aggregate(new.id)` gives the stored copy, not the body
being written; `old` and `new` are the two states of that root.

=== Which writes run the rules

[cols="1,1",options="header"]
|===
|Run the rules |Do not run them

|The generic API's create and replace, the tenant root's PUT included
|Delete (it has rules of its own, <<delete-validators,below>>)

|A unit of work's commit
|Restore (`import_quads`)

|A message-bus handler
|Migrations

|A workflow transition
|The start-up sweep
|===

System and application sessions share the guard, so a rule on an application-level root runs
there too.

=== What start-up checks

The keys are checked when the service is built, so a mistake stops the start. A key must be a
class of the schema that is not a mixin and not one of the toolkit's own classes (such as
`TenantAccess`), and it, or a class derived from it, must be an aggregate root of your schema; the
tenant root counts. Otherwise start-up raises `ValueError` naming the key and the reason. A rule
that is not callable raises `TypeError`.

=== Errors

[cols="2,2",options="header"]
|===
|The rule |The answer

|Raises `InvalidBody` or pydantic's `ValidationError`
|422, with its message

|Raises any other exception (a bug)
|500: a `RuntimeError` that names the rule and the exception

|Returns a value (even from a coroutine)
|`TypeError`, 500

|The reader meets a store outage
|Passes as it is: 503, as for any write

|An aggregate that the reader handed over changed before the commit, or the transaction relied on it
at another version
|409, naming the aggregate; nothing is written

|An aggregate that the reader reads does not decode
|500: a `RuntimeError` naming it
|===

Outside HTTP, `InvalidBody` comes out of `commit` or the transition. A rule that is a
`functools.partial` is named by its representation.

=== Limits to know

* *A broken rule blocks every write of its class.* A rule that always raises a bug also blocks
transitions and bus handlers. The 500 names the rule; test your rules.
* *A refusal of the tenant root on create is a 422 and leaves nothing.* The database and the
bucket exist before the root is written, so the create drops the ones it made. Only if that drop
itself fails are they left for the start-up sweep. `root_validators` run first, before the
database exists.
* *A stale PUT.* If a rule refuses the body, the answer is 422, whatever the version. If the
rules accept it, the version check at commit answers 409, as without rules.
* *Cost.* Without `aggregate_validators`, nothing is decoded or read. With them, a replace reads
the stored root once, each `classes_of` call is one query, and each aggregate that `aggregate`
reads is one read and one decoding per transaction.

Tenant roots can have both kinds: `root_validators` run first, then the aggregate validators of
the root's class. A refusal by either is a 422.

[#delete-validators]
== Refuse the delete of an aggregate

_How do I refuse to delete a root while something holds it, such as a book that is on loan?_

Give `install_service` `delete_validators`: a mapping from a schema class name to a list of rules.
`ServiceKit` takes the same argument. A rule runs on every removal of a root of that class, or of a
class derived from it, before anything is removed. It receives the stored root, the caller and the
same *reader* the write rules get. To refuse, raise `Refused`: nothing is removed.

[source,python]
----
from rdf_persistence import Refused, install_service


def not_while_on_loan(old, who, reader):  # plain or async, as a write rule
    if old.status == "on_loan":
        raise Refused(f"{old.id} is on loan; return it before deleting it")


install_service(
    app,
    delete_validators={"Book": [not_while_on_loan]},
    # ... and the other keyword arguments of the composition root
)
----

`delete_validators` is a `Mapping[str, Sequence[DeleteValidator]]`, empty by default. A rule takes
`(old, principal, reader)` and returns nothing; `old` is a copy of the generated model, as stored,
tracking included. The keys are checked at start-up as those of `aggregate_validators` are, and rules
run in the same order: the most general class first. A stored root with types on two lines of
descent is a bug in the data, not the client's: when a rule applies to one of them, the delete is a
`RuntimeError` naming the root (500).

The reader works as for a write, and answers for the caller of the delete: `reader.aggregate(iri)` is
`None` for an aggregate the caller may not read, so a rule that depends on one the caller cannot see
sees it as absent. It sees what the transaction removed earlier as absent too.

*Every removal through a transaction runs the rules*, whichever way it is made: the generic `DELETE`
route, `Session.remove`, a unit of work's `remove`, the cascade of a collection and `remove_with_files`.
The comment records that go with a removed aggregate are dropped inside the removal and run no rule:
they are the toolkit's own and no key can name them.

=== Cascades and what a refusal says

A collection's cascade removes the collection and its members in one commit. If one member's rule
refuses, the whole commit is refused and nothing is removed, the collection included. The caller asked
to delete the collection and learns about the member that blocked it, so *write the message to name
its root*, as the example does (`old.id`): a message that does not say which member refuses leaves the
caller guessing. The refusal reaches a caller who may not read that member only as far as the message
you write, so do not put in it what the caller must not see.

=== Errors of a delete rule

[cols="2,2",options="header"]
|===
|The rule |The answer

|Raises `Refused`
|409 `refused`, with your message as its `detail`; nothing is removed

|The `If-Match` version is stale and the rule refuses
|409 `conflict` for the version, with no `detail`, as for a stale delete without rules

|Raises a plain `Conflict` (a version clash the reader met)
|409 `conflict`, with no `detail`

|Raises any other exception, `InvalidBody` included (a delete has no body to call invalid)
|500: a `RuntimeError` that names the rule and the exception

|Returns a value (even from a coroutine)
|`TypeError`, 500

|The reader meets a store outage
|Passes as it is: 503
|===

`refused` is the one 409 whose `detail` is sent, because the text is yours; a version conflict and a
key conflict carry none. Without `delete_validators`, a removal reads nothing more than before. With them, a removal of a root of a
class that has a rule reads the stored root once.
