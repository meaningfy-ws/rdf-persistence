= Configure the IRI policy
:description: Choose how the toolkit mints the IRIs of tenants, aggregates, parts and graphs.
:page-revised: 2026-11-10 by the developer

_How do I make my own IRIs?_

By default the toolkit mints a tenant as `{base}{tenant_segment}/{tenant_id}` and an aggregate as
`{tenant}/{rp_path}/{id}`, with owned parts and loaded graphs nested under their root, every id a
UUID. If your organisation fixes another shape, describe it as an *IRI policy* and put it on the
settings. This page shows how to set a policy, what each field may hold, why a policy cannot change
once a deployment has data, and how to mint IRIs under it in your own code. Choose the policy
before the first tenant is created.

== Set a policy

The policy is a record with a template per kind of IRI and the rule for each id:

[source,python]
----
from rdf_persistence import (
    IdKind, IdSpec, IriPolicy, Iris, JwksTokenVerifier, ServiceSettings, zitadel_roles_claim,
)

project_id = "..."                          # your Zitadel project id, as when serving
FLAT = "{base}{tenant_id}/{type}/{id}"
settings = ServiceSettings(
    base="https://example.org/",
    prefix="lib",
    tenant_segment="libraries",
    creator_role="librarian",
    roles_claim=zitadel_roles_claim(project_id),
    deployment="dev",                        # what {deployment} takes; needed only if a template uses it
    iri_policy=IriPolicy(
        tenant_template="{base}library/{tenant_id}",
        access_template="{base}{deployment}/library/{tenant_id}",
        principal_template="{base}{deployment}/user/{sub}",
        aggregate_template=FLAT,
        part_template=FLAT,
        loaded_graph_template=FLAT,
        tenant_id=IdSpec(kind=IdKind.RANDOM, length=7),
        object_id=IdSpec(kind=IdKind.RANDOM, length=13),
    ),
)
# the verifier mints principals: give it the same policy; open it with `async with`, as when serving
verifier = JwksTokenVerifier(issuer, project_id, zitadel_roles_claim(project_id), iris=Iris(settings))
----

A slot you leave out keeps its default. A tenant is then `https://example.org/library/p4x8k2m`,
a book `https://example.org/p4x8k2m/book/{13 characters}`, its chapter
`https://example.org/p4x8k2m/chapter/{13 characters}` and a graph loaded into it
`https://example.org/p4x8k2m/content/{13 characters}`: all flat, none nested under another. The
aggregate's named graph stays `{root}/graph`. The API paths keep their shape: the tenant is
`/libraries/p4x8k2m` and the book `/libraries/p4x8k2m/books/{13 characters}`, because the id in a
path is the last segment of the IRI. A path id the policy does not mint answers 404. The settings
and the verifier are those of xref:user-manual/serve.adoc[Serve the application].

== The fields

The fields of `IriPolicy`, with their defaults and the variables each template may use:

[cols="2,3,3",options="header"]
|===
|Field |Default |May use, and must
|`tenant_template`
|`{base}{tenant_segment}/{tenant_id}`
|`{base}`, `{deployment}`, `{tenant_segment}`, `{tenant_id}`; ends in `{tenant_id}`
|`aggregate_template`
|`{tenant}/{rp_path}/{id}`
|`{base}`, `{deployment}`, `{tenant}`, `{tenant_id}`, `{type}`, `{rp_path}`, `{id}`; names
`{tenant}` or `{tenant_id}`; ends in `{id}`
|`part_template`
|`{root}/parts/{id}`
|`{base}`, `{deployment}`, `{tenant}`, `{tenant_id}`, `{root}`, `{type}`, `{id}`; names
`{tenant}`, `{tenant_id}` or `{root}`; ends in `{id}`
|`loaded_graph_template`
|`{root}/content/{id}`
|as `part_template`; its `{type}` is `content`
|`access_template`, `meta_template`, `registry_template`, `provenance_template`
|`{tenant}/access`, `{tenant}/meta`, `{tenant}/registry`, `{tenant}/provenance`
|`{base}`, `{deployment}`, `{tenant}`, `{tenant_id}`; names `{tenant}` or `{tenant_id}`
|`activity_template`
|`urn:uuid:{id}`
|`{base}`, `{deployment}`, `{tenant}`, `{tenant_id}`, `{id}`; names `{tenant}` or `{tenant_id}`;
ends in `{id}`, always the activity's UUID (<<activity-iris>>); or the default as it is
|`principal_template`
|`{issuer}/users/{sub}`
|`{base}`, `{deployment}`, `{issuer}`, `{sub}`; ends in `{sub}`
|`tenant_id`, `object_id`
|a UUID
|an `IdSpec` (<<ids-and-types>>)
|===

`{tenant}` is the tenant's IRI, `{root}` the IRI of the aggregate root a part or a loaded graph
belongs to, `{tenant_id}` and `{id}` the ids, and `{base}`, `{deployment}` and `{tenant_segment}`
the settings of the same name. `deployment` (lower case letters and digits) is needed only when a
template uses `{deployment}`. A template that uses another variable, does not end as the table
says, or names no tenant is refused when the settings are built. So are templates under which a
tenant's access, meta, registry or provenance IRI equals another of them, the tenant's, or reads as
an aggregate or a loaded graph. The access record is not an aggregate: no session reads or commits
its graph, but a grant may still target it.

*The principal.* The verifier mints the principal, and you build it before the kit: with a
`principal_template` of your own, pass it the policy as `JwksTokenVerifier(..., iris=Iris(settings))`.
Without it the verifier mints the default `{issuer}/users/{sub}`, and grants to your principals
would never match, so `install_service` compares the `principal_template` of the verifier's `Iris`
with the settings' and refuses to start (`InvalidIri`) when they differ. A `principal_template`
without `{issuer}` gives one principal to the same `sub` of every identity provider; leave
`{issuer}` out only when one provider issues all your tokens. The verifier refuses a token whose
`sub` is empty, `.` or `..`.

The example policy above, kind by kind:

[cols="3,3,2",options="header"]
|===
|Kind |Template or setting |Now
|Tenant |`{base}library/{tenant_id}` |configurable
|Aggregate root, owned part, loaded graph |`{base}{tenant_id}/{type}/{id}` |configurable
|Tenant id |`random`, 7 characters of `[a-z0-9]` |configurable
|Object id |`random`, 13 characters of `[a-z0-9]` |configurable
|Database and bucket |`{prefix}-t-{tenant_id}` |fixed
|Access record, meta and registry graphs |`{base}{deployment}/library/{tenant_id}` for the access
record, `{tenant}/meta`, `{tenant}/registry` |configurable
|Principal |`{base}{deployment}/user/{sub}` |configurable; pass `iris=Iris(settings)` to the verifier
|Guard against a service started under another policy than its tenants were made under |`install_service` start-up
|enforced
|===

[#activity-iris]
== Activity IRIs

Every commit stores one activity record. By default its IRI is `urn:uuid:` and a UUID, which names
no tenant. Set `activity_template` to place it in the tenant, so a restore moves it with the
tenant's other data:

[source,python]
----
iri_policy=IriPolicy(activity_template="{tenant}/activity/{id}")
----

A commit in the tenant `https://example.org/library/p4x8k2m` then records
`https://example.org/library/p4x8k2m/activity/{UUID}`; transitions, comments, observers, the event
stream and `Last-Event-ID` use that IRI. `{id}` is always the activity's UUID: `object_id` does not
apply. `{tenant}` is already a full IRI, so write `{tenant}/activity/{id}` and not
`{base}{tenant}/activity/{id}`; `{base}{tenant_id}/activity/{id}` is allowed too. A command made with
`command()` carries a provisional `urn:uuid:` id; the commit places its UUID under the template
(xref:howto/event-driven.adoc[Build event-driven features]).

A template other than the default is refused, naming `activity_template`, when:

* it names neither `{tenant}` nor `{tenant_id}`, or does not end in `{id}`, or uses another variable;
* it has no scheme, or starts outside `{base}`, so a restore could not move it;
* it glues the tenant id to a neighbouring character (`{tenant}{id}`, `{tenant}x{id}`), as the
  restore reads templates;
* with an aggregate template that names no `{type}` or `{rp_path}` and UUID object ids
  (`{tenant}/{id}`), it would read an aggregate as an activity;
* a root class of the model, minted with a UUID, falls inside it (the service refuses to start).

Keep the activity segment apart from every `rp_path` and every class type. A root whose `rp_path`
equals the segment (`activity`) is refused at start-up when the kit builds the policy; a
consumer that builds its own `Iris` without the kit gets no such check, and the writes to that root
are refused instead. Under a flat part template such as `{base}{tenant_id}/{type}/{id}`, an owned
class whose `{type}` equals the segment is not detected at all.

*Choose it before the first start.* The template is part of the policy, so a deployment with data
cannot change it: the start refuses with `IriPolicyChanged` naming `activity_template`, and a
restore of a dump made under another template is refused the same way. Set it before the first
tenant is created.

In your own code, `Iris.activity(tenant, uuid)` mints the IRI, `Iris.is_activity(tenant, iri)` checks
it, `Iris.activity_uuid(iri)` reads the UUID back, and `Session.activity_iri(command_id)` answers the
IRI a command's commit will record.

[#policy-cannot-change]
== The policy cannot change

The policy cannot change once a deployment has data: their IRIs and graphs are stored under the old
policy. At start-up, before the sweep (which reads the access records through the policy),
`install_service` records the effective policy in the system database, in the graph
`{base}toolkit/iri-policy`. The effective policy has every default filled in and the settings'
`{base}`, `{deployment}` and `{tenant_segment}` written into the templates, so leaving a field unset
and setting it to its default are the same, and changing `base`, or the `deployment` of a template
that uses it, changes the policy. The first write is conditional and read back, so two instances that
start at once with different policies cannot both serve. On every later start it compares the
configured policy with the record and, when they differ, refuses to start with `IriPolicyChanged`
(a 503 `unavailable` if a route ever meets it), naming each differing field (`object_id.length`) and
logging it with `step: iri-policy`. A record that cannot be parsed, or more than one record, refuses
the start too, saying the record is unreadable. A system database that has access
records but no record is taken to hold the default policy: a non-default policy is refused there,
and the default is recorded. Moving stored data to a new policy is not supported.

== Ids and types

What else the policy fixes:

* `{type}` is the class's `rp_iri_type`, else its name in kebab case
  (xref:user-manual/model.adoc[Write the model]), and `content` for a loaded graph.
* An id is a UUID (`IdKind.UUID4`) or `length` characters of an `alphabet` (`IdKind.RANDOM`; 4 to
  32 characters, by default `0123456789abcdefghijklmnopqrstuvwxyz`). A drawn id that equals a word
  the templates use (a `{type}`, `content`, the deployment) is drawn again, and so is a tenant id
  whose access record or database already exists, at most five times.
* A schema in which two classes share an `rp_iri_type`, or one equals such a word, is refused.

== Mint IRIs in your own code

One `Iris` serves the whole service. `install_service` builds it from the settings and the schema
and hands it to every service it wires, to the kit (`kit.iris`) and to the access rules, even
rules you built yourself: `AccessRules.with_iris(iris)` answers a copy with the same role permits
under that policy. You never pass one to `install_service`. Inside a domain service, take it from
the kit: `kit.iris` (xref:user-manual/store-and-read.adoc[Store and read aggregates]). Outside a service, build one from the settings and the types of the
schema (needed only when a template uses `{type}`):

[source,python]
----
from rdf_persistence import Iris, load_schema
from rdf_persistence.schema.services.schema_structure import iri_types

root_types, owned_types = iri_types(load_schema("models/library.yaml"))
iris = Iris(settings, root_types, owned_types)
tenant = str(iris.mint_tenant())
book = iris.mint_aggregate(tenant, "book", "books")
----

and pass it to what you build: `new_part(..., iris=iris)`, `open_session(..., iris=iris)`,
`fake_session(..., iris=iris)`. `DEFAULT_IRIS` is the default policy, which an argument left out
uses.

The toy library's end-to-end test runs under the example policy against Fuseki, Garage and Zitadel:
`tests/e2e/test_library_policy.py`.

=== Changed in 0.3.0: the provenance graph

Upgrading from 0.2.x, three points. `provenance` is now a reserved class IRI type
(xref:user-manual/model.adoc[Write the model]), so a class that used it must be renamed. The
generated folder gains five frames (`Activity`, `Add`, `Remove`, `Replace` and the transition's
own), so run your regenerate target once and commit the result. A recorded policy from 0.2.x reads
as the default `{tenant}/provenance`, and that is not a change; but a deployment whose recorded
policy already uses `{tenant}/provenance` for another graph cannot start, and the only way out is a
new policy record.

=== Changed in 0.15.0: activity IRIs

The policy gains `activity_template`, default `urn:uuid:{id}`. A recorded policy or a dump from
before 0.15.0 reads as that default, so nothing changes until you set it, and a deployment that
already has data cannot set it (<<policy-cannot-change>>). `command()` now gives a provisional id:
a handler that stored `command.id` should store `Session.activity_iri(command.id)`, which is the
same text under the default policy.
