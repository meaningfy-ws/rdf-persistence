= UML conventions
:description: The conventions an Enterprise Architect class model follows so that rp-uml2linkml converts it into a toolkit-conformant LinkML schema: model2owl's UML conventions and the toolkit's own, each with its UML and the LinkML it becomes.

_Which UML conventions does a model for rdf-persistence follow?_

These conventions make an Enterprise Architect (EA) model convertible by `rp-uml2linkml`. They are
the UML conventions of
https://docs.ted.europa.eu/M2O/latest/uml/conceptual-model-conventions.html[model2owl], which the
converter relies on (<<model2owl>>), plus the toolkit's own (<<toolkit>>). A model element that no
convention maps stops the run (<<fails>>); a convention that only concerns presentation is a report
line, which `rp-uml2linkml --check` fails on (<<conventions>>). The names in the examples (`lib:Book`, `lib:Chapter`,
`lib:Shelf`, `lib:Loan`) belong to a small library model. Mermaid cannot put a colon in a
relationship label, so the diagrams write a role without its prefix (`hasChapter`, for
`lib:hasChapter`); in EA the role carries the prefix, as the YAML shows.

[#model2owl]
== The model2owl conventions the converter relies on

The converter reads these as model2owl defines them; follow the linked pages for the full text.

[cols="2,5,3",options="header"]
|===
|Convention |What the converter does with it |model2owl

|Prefixed names, and their case
|A class, attribute or role is written `pfx:Local`. A class or enumeration is in Pascal case
(`Book`); an attribute or role is in lower camel case (`hasChapter`) and becomes a snake-case slot
(`has_chapter`). An unprefixed name takes the prefixes file's `default_prefix`.
|https://docs.ted.europa.eu/M2O/latest/uml/conv-general.html[General]

|Declared prefixes
|Every prefix in a name is declared in the prefixes file (`--prefixes`). An unknown prefix fails the
run, once per prefix. A namespace the toolkit's metamodel names keeps the metamodel's prefix
(`dct:` is written `dcterms:`).
|https://docs.ted.europa.eu/M2O/latest/uml/conv-general.html[General]

|XSD datatypes
|An attribute is typed by an XSD datatype, or by an enumeration. Supported: `xsd:string`,
`xsd:normalizedString`, `xsd:anyURI` (`uri`), `xsd:boolean`, `xsd:date`, `xsd:dateTime`,
`xsd:time`, `xsd:integer`, `xsd:int`, `xsd:long`, `xsd:nonNegativeInteger` (`integer`, minimum 0),
`xsd:positiveInteger` (`integer`, minimum 1), `xsd:decimal`, `xsd:double`, `xsd:float`. Any other
type, and a class as a type, fails.
|https://docs.ted.europa.eu/M2O/latest/uml/conv-attributes.html[Attributes]

|Target roles and direction
|The association's target role names the slot, on the source class. A source role is optional; with
one, the association is drawn `Bi-Directional` and each end gives a slot. A dependency has a target
role only. The direction is `Source -> Destination` or `Bi-Directional`; no other is accepted.
|https://docs.ted.europa.eu/M2O/latest/uml/conv-conn-association.html[Associations]

|A dependency to an enumeration
|A dependency from a class to an enumeration, named by its target role, is a slot ranged by the
enum. A dependency to a converted class fails; one to a class that is not generated or outside the
package is a `range: uri` slot.
|https://docs.ted.europa.eu/M2O/latest/uml/conv-conn-dependency.html[Dependencies]

|A reused name is one property
|Two classes that use the same name with the same IRI share one slot, defined once. The same name
with another IRI fails.
|https://docs.ted.europa.eu/M2O/latest/uml/conv-attributes.html[Attributes]

|Definitions from notes
|The note of a class, attribute, enumeration literal or connector becomes its `description`. An
element with no note gets no description (never a placeholder) and one `no-note` line in the
report; `rp-generate` then names it, as it requires a description.
|https://docs.ted.europa.eu/M2O/latest/uml/conv-classes.html[Classes]
|===

[#toolkit]
== The toolkit's conventions

The converter writes the report `<root-name>.uml-report.txt` beside the schemas. Its lines are
named in each subsection.

[#root]
=== A root

An aggregate is the unit the toolkit stores and loads whole, and its root is the class the rest hangs
from. The converter derives the roots: a class is a root when it is concrete, in a module of kind
`domain`, and no composition's part (<<composition>>, also by inheritance). An enumeration, the
«tenant root» (<<tenant-root>>), a class of a not-generated stereotype and a toolkit class drawn in
the model are never roots. The converter lists each root, with its parts, in a `root` line of the
report (`root`, `Shelf`, `parts Book, Chapter, Page`; `no parts` for a class with none), so a class
that became a root only because nothing composes it is visible.

A root mixes in `AggregateRoot`, gets the default mixins (`--default-mixins`, `Described,Tracked`)
and an `rp_path`. A part gets the default mixins too; a class that is neither a root nor a part
(a class of an `access` or `technical` module, say) gets none. A name in `--default-mixins` that is
not a toolkit class fails (<<fails>>). The `rp_path` is the `rp_path`
tagged value when the class has one, else the plural of the class name in kebab case (`Book` →
`books`, `Library` → `libraries`, `Box` → `boxes`). The plural is simple and irregular nouns are not
guessed: `Shelf` becomes `shelfs`, so give it `rp_path=shelves` (<<tagged-values>>). Two roots with
one `rp_path` fail.

[mermaid]
....
classDiagram
  class Book["lib:Book"] {
    xsd:string dct:title [1..1]
  }
....

[source,yaml]
----
classes:
  Book:
    title: Book
    mixins: [AggregateRoot, Described, Tracked]
    annotations:
      rp_path: books
----

*The «root» stereotype is deprecated.* A model that still draws it is compared with the derived
roots, over the concrete classes of `domain` modules:

* the sets are equal: the schemas are those of a model that does not draw «root», and the report has
  one `deprecated-root` line (`model`, `2 «root» stereotypes agree with the derived roots; drop them`).
  The line is informational, so a model in this state passes `rp-uml2linkml --check`;
* a class drawn «root» that is a part, or a derived root that is not drawn «root», each fails with
  `[root_class] Chapter: drawn «root» but a part of Book` or `[root_class] Reader: a root (no
  composition's part) but not drawn «root»`;
* a «root» on an abstract class fails (`abstract «root»: drop it, the abstract-root rule derives
  it`), as the abstract-root rule of <<abstract>> derives it;
* a «root» in a module of another kind (an `access` class that is stored) keeps its old meaning
  (`AggregateRoot` and an `rp_path`) and is outside the comparison.

To leave the stereotype, draw the compositions first, keep «root» while `--check` is clean, then
remove it everywhere at once.

[#composition]
=== A composition

Which classes belong to an aggregate is drawn as compositions, never inferred from names, packages
or layout. A composition from a whole to a part means _stored together, consistent at every moment_.
The deletion test (xref:howto/uml-to-linkml.adoc#deletion-test[the guide]) decides whether a class is
a part: it cannot exist without its whole and goes down with it.

In EA a composition is a connector of type _Aggregation_ with the _strong_ (filled) diamond at the
whole. The diamond names the whole, so the direction the connector is drawn in does not matter. A
hollow diamond (a shared aggregation) fails, and so does one with a diamond at both ends or at
neither.

The composition is drawn beside an association between the same two classes. The association keeps
the property's role, multiplicity and note and gives the slot; the composition makes that slot
`owned` and inlined. The association is the one from the whole to the part (`Source -> Destination`,
or `Bi-Directional` with the role on the part's end), and the classes must be exactly the
composition's two: an association to a subclass or a superclass of the part does not count.

[mermaid]
....
classDiagram
  Shelf --> "0..*" Book : holds
  Shelf *-- Book
  Book --> "1..*" Chapter : hasChapter
  Book *-- Chapter
  Chapter --> "1..*" Page : hasPage
  Chapter *-- Page
  Reader --> "0..*" Book : borrows
....

[source,yaml]
----
slots:
  holds:
    slot_uri: lib:holds
    range: Book
    multivalued: true
    inlined_as_list: true
    annotations:
      owned: 'true'
  has_chapter:
    slot_uri: lib:hasChapter
    range: Chapter
    required: true
    multivalued: true
    inlined_as_list: true
    annotations:
      owned: 'true'
  has_page:
    slot_uri: lib:hasPage
    range: Page
    required: true
    multivalued: true
    inlined_as_list: true
    annotations:
      owned: 'true'
----

The depth is the depth of the compositions: `Page` is a part of `Chapter`, a part of `Book`, a part
of `Shelf`, and `Shelf` is the root. `Reader.borrows` has no composition, so it is a pointer
(<<pointers>>), and that one fails here, as `Book` is a part of `Shelf`.

Which compositions the converter accepts:

* *Several associations.* When two associations from the whole range over the part (two owned roles,
  or an owned role and an internal reference), write the role on the composition (EA's end role,
  equal to the association's role) to name the one it marks owned. With one association the role is
  not needed. With no association, or with several and no role, or with a role that names none, the
  run fails (<<fails>>). A note on the composition, or a role where it is not needed, is a
  `composition-named` convention line: the association carries the role and the note.
* *Inheritance.* A subclass of a part is a part. A whole may be abstract: its compositions apply to
  its concrete subclasses.
* *Recursion and sharing.* A composition may recurse (`Section` composes `Section`) and a part class
  may have several wholes (`Section` under `Book` and under `Journal`): each instance sits in one
  whole, and the class belongs to each aggregate that reaches it. Every part class must be reached
  from a root; one that is not, or a cycle of compositions that no root enters, fails, naming the
  classes.
* *Not accepted.* A composite association (an association whose end is composite, the form earlier
  versions read as ownership) fails, naming the fix: draw the composition beside a plain
  association. A whole or a part that is outside the converted packages, in an excluded package or a
  drawn toolkit class (<<toolkit-reuse>>) fails; so does an enumeration as a part, the «tenant root»
  as a part, and a domain whole that composes a part of a module of another kind.

The Boundary object of earlier versions no longer makes anything owned: only a composition does.
A boundary left in the model is an annotation. One that sits in a converted package and is not named
for a root (its name, after an optional `Aggregate:`, is the root's name) gets a `boundary-disagrees`
convention line; the converter reads no membership from it.

[#own-graph]
=== «own graph»

A composition stereotyped «own graph» makes its part separately stored but deleted with its whole.
In this release the part must be a class of a not-generated stereotype (<<not-generated>>, by
default `loaded graph`: a graph loaded for the whole's aggregate). Its slot on the whole is a URI
that is not owned and carries `rp_loaded_graph`, which marks its values as the IRIs of graphs loaded
for the whole and deleted with it. No class is generated for the part.

A class that is a part of a not-generated «own graph» part is stored inside that graph: it is left
out, with a `not-generated` line (`inside the own graph of ShapeReport`), and no slot is made to it. A
composition whose whole is not generated, or left inside, converts to nothing. A generalisation to or
from a class left inside fails.

[mermaid]
....
classDiagram
  class CountReport["lib:CountReport"] {
    <<loaded graph>>
  }
  ShelfCount --> "0..1" CountReport : countReport
  ShelfCount *-- CountReport : own graph
....

[source,yaml]
----
slots:
  count_report:
    slot_uri: lib:countReport
    range: uri
    annotations:
      rp_loaded_graph: 'true'
----

«own graph» on a part that is generated fails: a generated part stored apart needs a later change
(`dependent-aggregates`); until then mark the part with a not-generated stereotype or draw a plain
composition. A plain composition to a not-generated part fails too, since a not-generated part is
stored apart: use «own graph». Any other stereotype on a composition fails.

[#pointers]
=== Pointers target roots

An association that is not a composition's is a pointer to another aggregate. It ranges over a
root, the «tenant root», or an abstract class whose concrete subclasses are all roots. It may not
range over a part of an aggregate its holder does not belong to: the target of a pointer is the
aggregate, not a part in it. A pointer into an aggregate the holder is itself in (a `Chapter` that
points at another `Chapter` of its own book) is an internal reference and stays. A class that is no
part (a class of an `access`, `technical` or `value` module) is a plain target as before.

[mermaid]
....
classDiagram
  Reader --> "0..*" Shelf : borrowsFrom
  Reader --> "0..*" Book : borrows
  Shelf *-- Book
....

`Reader.borrows` fails: `[boundary_owned] Reader.borrows: points at Book, a part of Shelf; point at
Shelf`. Retarget it at `Shelf`. When `Book` is a part of two aggregates, the message names both
roots, and a pointer from a class that is in one of them is allowed.

One role IRI may not be owned on one whole and a pointer on another class: that splits one slot into
an owned and a referencing usage (`[boundary_owned] <role>: role <role> is owned on <whole> and a
pointer on <holder>`). Give the second use its own name. The toolkit's own slots (`dct:hasPart` of a reference collection, <<member-class>>)
are exempt.

[#realisation]
=== Realising an object's class

A role definition is an EA Object (<<roles>>) whose classifier is `rp:RoleDefinition`. A Realisation
connector from the Object to a class is accepted as the visible form of the classifier. It converts
to nothing. An Object with a Realisation and no classifier takes the Realisation's target as its
classifier. A Realisation to another class than the classifier fails (`[role_definition] <object>:
realises <class> but its classifier is <class>`), and so do two Realisations to different classes
(`realises <class> and <class>`). A Realisation is read by the types of its ends, not its direction, so one drawn from the
class to the Object counts as the Object's. A Realisation between two classes, or from a class, is
still a connector no convention maps. An Object outside the converted packages, or in an excluded
one, is skipped.

[mermaid]
....
classDiagram
  class librarian["librarian : rp:RoleDefinition"] {
    role = librarian
    level = tenant
    actions = read, modify
  }
  RoleDefinition <|.. librarian : realises
....

[#diagrams]
=== Diagrams

Only the names and the contents of the class diagrams of the converted packages are read, never their
positions or sizes. A diagram named `<package> · aggregates` (a middle dot, U+00B7, between spaces)
shows classes and compositions only, and the text before the suffix is the name of its package.
Any other class diagram of a converted package shows no composition. A diagram that breaks this
gives a convention line:

* `aggregates-diagram`: an aggregates diagram that shows an association or a dependency, an element
  that is no class, note, text or boundary (an enumeration, an Object, a state), or whose name does
  not begin with its package's name;
* `composition-diagram`: any other class diagram that shows a composition.

EA shows a connector on a diagram when both its ends are on it, unless the diagram hides it. So on
the aggregates diagram hide the associations, and on the others hide the compositions: the guide
(xref:howto/uml-to-linkml.adoc#diagram-kinds[Two kinds of diagram]) says how. Statechart diagrams
(<<workflows>>) are not read here.

[mermaid]
....
classDiagram
  note for Shelf "diagram: library · aggregates (compositions only)"
  Shelf *-- Book
  Book *-- Chapter
....

The converter writes nothing for a diagram: the convention line is the only effect, and it fails
`--check`.

[#conventions]
=== The conventions `--check` fails on

`rp-uml2linkml --check` (xref:howto/uml-to-linkml.adoc#check-model[the guide]) reads and converts
exactly as a run does, writes nothing, and exits 1 when the model has a problem or one of these
convention lines. A normal run writes the same lines in the report and never fails on them. The
report lines of the other kinds are informational: they never fail `--check`.

[cols="2,5,3",options="header"]
|===
|Kind |The convention it reports |Where

|`boundary-disagrees` |A boundary of a converted package named for no root. |<<composition>>
|`composition-named` |A composition carries a note, or a role its association already gives. |<<composition>>
|`aggregates-diagram` |An aggregates diagram that shows an association, an element that is no class, or
is named for another package. |<<diagrams>>
|`composition-diagram` |A class diagram that is no aggregates diagram and shows a composition. |<<diagrams>>
|`unprefixed-name` |A class, attribute or role written with no prefix (an enumeration literal has
`implicit-meaning`). |<<model2owl>>
|`unused-enumeration` |An enumeration that no dependency ranges over; it is generated all the same. |<<empty-enumeration>>
|`drawn-toolkit-parent` |A generalisation to a drawn toolkit class: say it with `rp_mixins=<Class>`
(<<tagged-values>>). A drawn `rp:RoleDefinition` that classifies Objects is not reported. |<<toolkit-reuse>>
|`tenant-required-pointer` |A required pointer from the tenant root or its parts to a class outside the
tenant's aggregate: the tenant cannot be created before the target exists. |<<tenant-root>>
|`no-note` |An element with no note. |<<model2owl>>
|`unspecified-multiplicity` |A connector end with no multiplicity, read as `0..*`. |<<multiplicity>>
|`implicit-meaning` |An enumeration literal with no prefix. |<<empty-enumeration>>
|===

`root`, `deprecated-root`, `not-generated`, `outside-link`, `excluded-link`, `toolkit-filled`,
`toolkit-slot-kept`, `role`, `workflow`, `derived-iri`, `external-list`, `ignored-tag`,
`ignored-stereotype` and `stale-file` are informational. A model that draws «root» (<<root>>) or
follows the reference-collection pattern of <<member-class>> still passes `--check`.

[#tenant-root]
=== A tenant root

A class stereotyped «tenant root» is annotated `graph: meta`. It gets no `AggregateRoot` and no
`rp_path`, but it takes the default mixins, and it is a root for the compositions (<<composition>>)
that start at it, so its parts are owned. It is never a part. A `graph` tagged value of `meta` is the same annotation;
one with another value is a problem, `[tenant_root] Library: graph: 'data' conflicts with the
«tenant root» stereotype, which is graph meta`.

[mermaid]
....
classDiagram
  class Library["lib:Library"] {
    <<tenant root>>
  }
....

[source,yaml]
----
classes:
  Library:
    title: Library
    mixins: [Described, Tracked]
    annotations:
      graph: meta
----

[#abstract]
=== Abstract classes

A class is abstract when EA's _Abstract_ flag is set or its stereotype is «Abstract» (any case).
It becomes `abstract: true`; the stereotype is not reported.

An abstract class is also an aggregate root of its own when it is the range of a generated slot and
all its concrete descendants are roots, counted through any abstract classes between them, so a
slot can point at "any of them". It then mixes in `AggregateRoot` and has no `rp_path` and no
default mixins; the concrete roots keep their own. A `unique_key` on it is scoped to the tenant
(`rp_unique_scope: tenant`), as on a root (<<tagged-values>>).

[mermaid]
....
classDiagram
  class Holding["lib:Holding"] {
    <<Abstract>>
  }
  class Book["lib:Book"]
  class Map["lib:Map"]
  Holding <|-- Book
  Holding <|-- Map
  Shelf --> "0..*" Holding : holds
....

[source,yaml]
----
classes:
  Holding:
    abstract: true
    mixins: [AggregateRoot]
  Book:
    is_a: Holding
    mixins: [AggregateRoot, Described, Tracked]
    annotations:
      rp_path: books
----

[#not-generated]
=== Classes that are not generated

A class whose stereotype is in the not-generated list produces no class. The list is
`--not-generated <stereotype>`, repeatable; its default is `loaded graph`, and naming any replaces
the default. A slot to such a class is `range: uri`, and the report has a `not-generated` line. An
enumeration with such a stereotype (`workflow states`, say) is not generated either, and nothing
points at it: a dependency to it, or an attribute typed by it, makes no slot. Each of these is one
`not-generated` line, the same as for a class.

A link that reaches a class the run leaves out is handled by where the class is:

* a not-generated class: the slot is `range: uri`;
* a class in an `--exclude-package` package (the option's path matches a package's path or its
  tail): no slot is made, and the report has an `excluded-link` line;
* a class outside the converted package that is not excluded: the slot is `range: uri`, and the
  report has an `outside-link` line.

[mermaid]
....
classDiagram
  class Vocabulary["lib:Vocabulary"] {
    <<loaded graph>>
  }
  Book --> "0..1" Vocabulary : classifiedBy
....

[source,yaml]
----
slots:
  classified_by:
    slot_uri: lib:classifiedBy
    range: uri
----

[#tagged-values]
=== Tagged values

A tagged value on a class tells the converter something the diagram cannot. The tag name picks the
meaning.

[cols="2,5",options="header"]
|===
|Tag |Becomes

|A class annotation named in the metamodel (as of this release: `graph`, `database`, `rp_path`,
`rp_iri_type`, `rp_unlabelled`, `rp_writes`, `rp_on_referenced_delete`, `workflow`)
|That annotation on the class. The names are those the metamodel marks as class annotations, read
at run time, so an annotation the toolkit adds later needs no change in the converter; see
xref:architecture/generation.adoc#annotations[Annotations] for the current set. Its value
is checked by the rules `rp-generate` uses, read without regard to case; a bad value fails the run
with `[class_annotation] Book: rp_writes: 'sometimes' is not one of ('service', 'toolkit')` (or
`rp_path: 'Books' does not match <pattern>` for `rp_path`, `rp_iri_type` and `workflow`, which take
a URL segment). A tag on a class overrides the annotation the converter derives, such as a root's
`rp_path`. `workflow` also adds the `UnderWorkflow` mixin.

|`rp_mixins=<Class>[,<Class>...]`
|The named toolkit classes, as mixins when the class is a mixin and as `is_a` when it is not
(`Activity`). The tag may repeat; the lists join. A class gets its mixins in one order, each once:
`AggregateRoot`, the `rp_mixins` names in tag order, the toolkit parents drawn as generalisations in
connector order, the default mixins, `UnderWorkflow`. An unknown name fails:
`[toolkit_mixins] Book: Nope is not a toolkit class; the toolkit classes are <the list>`.

|`unique_key = <name>: <a>, <b>[; nulls=equal]`
|A `unique_keys` entry over the named slots of the class: an attribute, a role or a reused toolkit
slot (<<toolkit-reuse>>), each by its slot name or its UML name. `<name>` is an identifier of ASCII letters, digits and underscores; the only clause is
`nulls=equal`, which writes `consider_nulls_inequal: false`. On a root the key is scoped to the
tenant (`rp_unique_scope: tenant`), and so is one on an abstract root (<<abstract>>). One key per tag; repeat the tag for more keys, each with its own
name. A bad tag fails with the tag text and the cause:
`[unique_key] Book: unique_key 'k: title, nothing': no attribute or role 'nothing' on Book`. The
other causes are `expected <name>: <attribute>, <attribute> [; nulls=equal]` (no colon, no attribute, or a clause
other than `nulls=equal`), `the name '1k' is not an identifier` and `a key of this name is declared
twice`.

|Any other tag
|Ignored, with an `ignored-tag` line (`tagged value rp_pth is not used`); a tag name is exact, so a
misspelt `rp_path` is such a tag. A tag named like a metamodel annotation that is not a class
annotation (`owned`, `rp_loaded_graph`) fails: `[class_annotation] Book: owned: tagged value is not a class annotation`.
|===

A part tagged `rp_unlabelled=true` gets `Described` only, with the annotation, so its `label` is
optional. On a root the tag adds only the annotation.

A stereotype on an attribute is not used: the attribute converts as usual and the report has an
`ignored-stereotype` line.

[mermaid]
....
classDiagram
  class Book["lib:Book"] {
    rp_mixins = StoredFile
    rp_writes = service
    unique_key = title_subtitle: title, subtitle
  }
  class Chapter["lib:Chapter"] {
    rp_unlabelled = true
  }
  Book *-- Chapter
....

[source,yaml]
----
classes:
  Book:
    mixins: [AggregateRoot, StoredFile, Described, Tracked]
    unique_keys:
      title_subtitle:
        unique_key_slots: [title, subtitle]
        annotations:
          rp_unique_scope: tenant
    annotations:
      rp_path: books
      rp_writes: service
  Chapter:
    mixins: [Described]
    annotations:
      rp_unlabelled: 'true'
----

[#toolkit-reuse]
=== Toolkit classes and slots, reused by IRI

A toolkit concept is drawn with its own IRI and the converter uses the toolkit's definition.

* A class drawn with a toolkit class's IRI (`prov:Activity`, or `rp:ReferenceCollection`) is the
toolkit's class, not generated. Drawn inside the converted subtree it is reported as
`not-generated	Activity	drawn as the toolkit's Activity, not generated`, and a slot that points at
it is `range: uri`; drawn outside the subtree, at the far end of a link, it is a class outside like
any other (<<not-generated>>). A generalisation to it has the effect of `rp_mixins`: a mixin class is mixed in, a
non-mixin becomes `is_a`. A root may be an `Activity`.
* An attribute or role whose IRI is a toolkit slot's `slot_uri` uses that slot, and no new one is
made; a `[1..1]` on a slot the toolkit does not already require becomes a `slot_usage` with
`required: true`. A bound on a slot the toolkit fills itself (`started_at_time`) is not carried: the
converter writes no slot and no `slot_usage` for it and reports
`toolkit-filled	Loan.started_at_time	the toolkit fills started_at_time; [1..1] is not carried`.
An attribute that differs from the toolkit slot in `multivalued` or in range keeps the toolkit's,
with a line such as
`toolkit-slot-kept	Book.label	the toolkit's label is kept; multivalued true is not carried`
(the other bounds are not compared).
* `dct:identifier` is the exception: it makes a new slot `identifier`
(`slot_uri: dcterms:identifier`), because `id` is the resource's IRI and stays so.

[mermaid]
....
classDiagram
  class Activity["prov:Activity"]
  class Loan["lib:Loan"] {
    xsd:dateTime prov:startedAtTime [1..1]
  }
  class Book["lib:Book"] {
    xsd:string dct:identifier [1..1]
  }
  Activity <|-- Loan
....

[source,yaml]
----
classes:
  Loan:
    is_a: Activity
    mixins: [AggregateRoot, Described, Tracked]
    annotations:
      rp_path: loans
  Book:
    slots: [identifier]
slots:
  identifier:
    slot_uri: dcterms:identifier
    range: string
    required: true
----

[#member-class]
=== A reference collection's member class

A reference collection collects aggregates of one class, its member class. Draw that class as a
`dct:hasPart` role from the collection to it. The class is a reference collection when it mixes
`ReferenceCollection` (or another toolkit class that brings `member_class`) in, by `rp_mixins` or a
generalisation, or when a domain class it generalises does. The role uses the toolkit's `has_part`, as any toolkit slot does (<<toolkit-reuse>>). The class
it points at is written as the collection's fixed `member_class`, so a collection of another class is
refused by the generated model and by its shape. No `toolkit-slot-kept` line is written for that
role's range, because the range is carried as the member class.

* A `dct:hasPart` role to the collection's own class that is its only role to a converted class
fixes the collection's own class as its member class (a collection of collections, DEC-2): see
below. Beside a role to another class, it is nesting: it stays the toolkit's `has_part` and is
reported as `toolkit-slot-kept` with its range, as before. Nesting is stated with `nests`.
* `dct:hasPart` roles to two different classes on one collection fail the run
(`[toolkit_slot] Shelf: dct:hasPart roles to Book and Map: a reference collection has one member class`).
* On a class that is not a reference collection, a `dct:hasPart` role is a plain use of the
toolkit's `has_part`.

[mermaid]
....
classDiagram
  class Shelf["lib:Shelf"]
  class Book["lib:Book"]
  Shelf --> "0..*" Book : hasPart
  note for Shelf "rp_mixins = ReferenceCollection"
....

[source,yaml]
----
classes:
  Shelf:
    mixins: [AggregateRoot, ReferenceCollection, Described, Tracked]
    slot_usage:
      member_class:
        equals_string: Book
----

An abstract collection may draw a `dct:hasPart` role to an abstract class while each concrete
subclass draws its own role to a class that descends from it. Then only the subclasses fix
`member_class`: two fixed values on one class contradict each other, and the generated subclass
would fail the type check. The abstract parent's role stays the toolkit's `has_part`, reported as
`toolkit-slot-kept` with its range. An abstract collection whose subclasses draw no role of their
own keeps its member class. A subclass's member class that does not descend from its parent's fails
the run (`[toolkit_slot] Shelf: dct:hasPart role to Chapter does not narrow Collection's member class
Resource: ...`).

[mermaid]
....
classDiagram
  class Collection["lib:Collection"] {
    <<abstract>>
  }
  class Resource["lib:Resource"] {
    <<abstract>>
  }
  Collection --> "0..*" Resource : hasPart
  Shelf --|> Collection
  Book --|> Resource
  Shelf --> "0..*" Book : hasPart
  note for Collection "rp_mixins = ReferenceCollection"
....

[source,yaml]
----
classes:
  Collection:
    abstract: true
    mixins: [ReferenceCollection, ...]   # no member_class: its subclasses fix it
  Shelf:
    is_a: Collection
    slot_usage:
      member_class:
        equals_string: Book
----

A collection of collections draws one `dct:hasPart` role, to its own class. That lone role fixes the
class as its own member class (DEC-2).

[mermaid]
....
classDiagram
  class Shelf["lib:Shelf"]
  Shelf --> "0..*" Shelf : hasPart
  note for Shelf "rp_mixins = ReferenceCollection"
....

[source,yaml]
----
classes:
  Shelf:
    mixins: [AggregateRoot, ReferenceCollection, Described, Tracked]
    slot_usage:
      member_class:
        equals_string: Shelf
----

The exception (OPEN-6): when another collection in the class's `is_a` lineage, an ancestor or a
descendant, has a member role, the lone role to its own class is nesting, as before. Take an abstract
`Folder` whose only role points at `Folder`, and its subclass `Album` with a role to `Photo`: `Album`
fixes `member_class: Photo`, `Folder` fixes none, and `Folder`'s role stays the toolkit's `has_part`,
reported as `toolkit-slot-kept`. Fixing both would contradict, and the run would fail "does not
narrow" for a model that converts today.

[mermaid]
....
classDiagram
  class Folder["lib:Folder"] {
    <<abstract>>
  }
  Folder --> "0..*" Folder : hasPart
  Album --|> Folder
  Album --> "0..*" Photo : hasPart
  note for Folder "rp_mixins = ReferenceCollection"
....

[source,yaml]
----
classes:
  Folder:
    abstract: true
    mixins: [ReferenceCollection, ...]   # no member_class; has_part is the toolkit's
  Album:
    is_a: Folder
    slot_usage:
      member_class:
        equals_string: Photo
----

[#multiplicity]
=== Multiplicity

Any `m..n` is accepted, with integers `0 <= m <= n` or `n = *`, and the shorthands `n` (`n..n`)
and `*` (`0..*`).

[cols="2,3",options="header"]
|===
|Multiplicity |Slot

|`m` of 1 or more |`required: true`
|`n` above 1, or `*` |`multivalued: true`
|`m` above 1 |`minimum_cardinality: m`
|`n` above 1 and not `*` |`maximum_cardinality: n`
|===

A missing multiplicity is `0..*`, with an `unspecified-multiplicity` line in the report. Write
`1..1` for exactly one. EA stores an attribute's blank multiplicity as `1..1`, the same as an
explicit one, so the converter takes an attribute's bounds as stored: set an optional attribute
explicitly (`0..1`). Only a connector's multiplicity can be missing.

[mermaid]
....
classDiagram
  class Book["lib:Book"] {
    xsd:string dct:title [1..1]
    xsd:string lib:subtitle [0..1]
    xsd:string lib:keyword [1..5]
  }
....

[source,yaml]
----
slots:
  title:     {slot_uri: dcterms:title, range: string, required: true}
  subtitle:  {slot_uri: lib:subtitle, range: string}
  keyword:   {slot_uri: lib:keyword, range: string, required: true, multivalued: true,
              maximum_cardinality: 5}
----

[#empty-enumeration]
=== Empty enumerations

An enumeration with literals is an enum: each literal becomes a permissible value keyed by its
local name in snake case (`lib:onLoan` → `on_loan`), with its `meaning`. A literal written without
a prefix takes the default prefix and an `implicit-meaning` line.

An enumeration with no literals stands for a controlled list kept outside the model. Any slot
ranged by it is `range: uri`, with an `external-list` line, and no enum is written.

[mermaid]
....
classDiagram
  class LoanStatus["lib:LoanStatus"] {
    <<enumeration>>
  }
  class Subject["lib:Subject"] {
    <<enumeration>>
  }
  Loan ..> LoanStatus : status
  Book ..> Subject : subject
....

[source,yaml]
----
slots:
  subject:
    slot_uri: lib:subject
    range: uri
----

`lib:LoanStatus` has literals and so becomes an enum. `lib:Subject` has none, so the slot
`subject` is a URI.

[#lang-string]
=== Language strings

An attribute typed `rdf:langString` (or `rdf:PlainLiteral`) is refused, never narrowed to `string`:
the toolkit has no language-string range yet (issue #209). When it has, the same attribute
converts with no change to the model.

[#packages]
=== Packages and modules

Each package that holds a class or enumeration becomes one module `<root-name>_<package>.yaml`
(`rare-books` → `app_rare_books`; a nested package `library/rare-books` →
`app_library__rare_books`), and the root schema `<root-name>.yaml` imports them all. Classes
directly in the `--package` package go to `<root-name>_main`.

Two packages whose classes refer to each other give two modules that import each other: a package is
never merged into another. `rp-generate` writes the Python of such modules so that they load
(xref:user-manual/generate.adoc#module-cycles[Schema modules that import each other]). A reference
is a slot's range, a generalisation, or a slot shared between packages
(<<shared-slots>>).

[mermaid]
....
classDiagram
  namespace catalogue {
    class Book["lib:Book"]
  }
  namespace shelves {
    class Shelf["lib:Shelf"]
  }
  Book --> Shelf : shelf
  Shelf --> Book : holds
....

[source,yaml]
----
# library_catalogue.yaml
imports:
  - library_shelves
classes:
  Book:
    slots: [shelf]
----

[source,yaml]
----
# library_shelves.yaml
imports:
  - library_catalogue
classes:
  Shelf:
    slots: [holds]
----

`library_catalogue` and `library_shelves` are two modules, each importing the other. The root schema
imports both, as for any other package.

[#module-kind]
A module is annotated `module_kind: domain` unless its package has a `module_kind` tagged value,
which is written as the annotation instead; a package's other tagged values are not read. The value
is one the toolkit's metamodel lists (`ModuleKind`: `domain`, `technical`, `access`, `value`, read
case-blind). `technical` fits only when every converted package is technical: a target generates
one kind, so `rp-generate` refuses technical modules beside domain ones (`target_kind`). A `value`
module needs `python_package` added by hand when another target imports it
(xref:architecture/generation.adoc#value-modules[Value modules]); the converter writes none. Any other
value fails the run
(`[package_module] access: module_kind: 'planet' is not one of ('domain', 'technical', 'access', 'value')`). An
application's access model is a package tagged `module_kind = access` whose classes generalise
`rp:TenantAccess`. `rp-generate`'s boundary rule then keeps the domain modules from importing it, while
the root schema imports it like any other module. Each package is its own module, so a module has
one kind; two sibling packages with one name share a module, and when their kinds differ the run
fails naming the module and both kinds (`its packages have the kinds access and domain`): rename
one of them. Packages of different kinds that import each other
are converted, each keeping its kind, and `rp-generate`'s boundary check then refuses the output,
naming the domain module and the access one it imports: break the import between those packages.

[mermaid]
....
classDiagram
  namespace access {
    class LibraryAccess["lib:LibraryAccess"]
  }
  class TenantAccess["rp:TenantAccess"]
  TenantAccess <|-- LibraryAccess
  note for LibraryAccess "package access: module_kind = access"
....

[source,yaml]
----
# library_access.yaml
annotations:
  module_kind: access
classes:
  LibraryAccess:
    is_a: TenantAccess
----

[#shared-slots]
=== A slot shared across packages

A name used in classes of several packages is one slot, defined once, in a home module: the module
that every other using module reaches by imports, directly or through others. When several modules
qualify, the first in path order is the home. A class in another module states a `slot_usage` only
for the limits (`required`, `multivalued` and the like), the range or the description in which it
differs from the slot. Placing the slot adds imports: each using module imports the home, and the
home imports the module of the slot's range. If these imports make two modules import each other,
they stay two modules that import each other (<<packages>>); nothing is merged. The home is chosen
from the imports there are once the slots are placed.

In the example, `lib:location` is used by `Book` (catalogue) and `Shelf` (shelves). The catalogue
already refers to the shelves, so the slot is defined in `library_shelves`, and `Shelf`, where it is
required, narrows it:

[source,yaml]
----
# library_shelves.yaml
slots:
  location:
    slot_uri: lib:location
    range: string
classes:
  Shelf:
    slots: [location]
    slot_usage:
      location:
        required: true
----

When the usages of a slot differ on a cardinality, each class states its own bound in its
`slot_usage`: the minimum always (`0` too, so an ancestor's `2` is not inherited), and the maximum
when it is finite. A class that redraws an ancestor's `2..*` role as `1` writes
`minimum_cardinality: 1`; one that redraws `0..5` as `0..1` writes `maximum_cardinality: 1`:

[source,yaml]
----
classes:
  Derived:
    is_a: Base
    slot_usage:
      part:
        required: true
        multivalued: false
        minimum_cardinality: 1
----

A role cannot be redrawn from a bounded ancestor's to an unbounded one (`0..5` to `0..*`; or `0..1`
to `0..*` when another class bounds the same role at another maximum, so the ancestor's 1 is
written), because LinkML would inherit the ancestor's maximum (R-31): the run fails with
`[cardinality_unbounded] Derived.part: ...`. A class that is not an `is_a` descendant is not
affected.

When no using module is reached by all the others, the run fails with
`[shared_slot_across_packages] location: used in library_catalogue, library_shelves and no one of them is imported by the others`.

[#roles]
=== A role definition

A role definition, the grant of a set of actions to a role at a level, is drawn as an EA Object
(an instance, not a class). Its classifier is the toolkit class `rp:RoleDefinition`, drawn once in
the converted packages like any toolkit class (<<toolkit-reuse>>); declare the `rp` prefix in the
prefixes file (`rp: https://meaningfy.ws/ns/rdf-persistence#`). The Object's run state, in EA's
_Run State_ dialog, sets three variables, each once, with the operator `=`:

[cols="1,4",options="header"]
|===
|Variable |Value

|`role`
|The role's name.

|`level`
|One of the toolkit's role levels: `system`, `tenant` or `aggregate`.

|`actions`
|Comma-separated, at least one, none twice: `read`, `modify`, `delete`, `administer` or
`annotate`.
|===

The converter does not copy these lists: it asks the toolkit's own `RoleDefinition` to judge each
Object, so the levels and the actions are always the toolkit's. It writes the definitions, sorted by
role and then level, to `<root-name>.roles.yaml` beside the schemas, in the format
`install_service(rules=...)` loads (xref:howto/uml-to-linkml.adoc#roles-file[the how-to]), and one `role` report line per definition:
`role` `<object name>` `<role> at <level>: <actions>`. A model that draws no role definition gets
no roles file.

Mermaid has no object diagram, so the diagram draws each Object as a box named
`<object> : <classifier>`, with its run-state values as the rows.

[mermaid]
....
classDiagram
  class librarian["librarian : rp:RoleDefinition"] {
    role = librarian
    level = tenant
    actions = read, modify, delete, administer
  }
  class member["member : rp:RoleDefinition"] {
    role = member
    level = tenant
    actions = read, annotate
  }
  class reader["reader : rp:RoleDefinition"] {
    role = reader
    level = tenant
    actions = read
  }
....

[source,yaml]
----
# library.roles.yaml
- role: librarian
  level: tenant
  actions:
  - read
  - modify
  - delete
  - administer
- role: member
  level: tenant
  actions:
  - read
  - annotate
- role: reader
  level: tenant
  actions:
  - read
----

A role definition that the toolkit would refuse stops the run, naming the Object (<<fails>>). The
converter then loads the staged file with the toolkit's `load_role_definitions`, as a last check;
if that refuses it, the run exits 1 with the loader's message and moves nothing.

[#workflows]
=== A workflow

A workflow, the states a class's objects pass through and who may move them, is drawn as an EA
_Statechart_ diagram. Draw it so:

* *The diagram.* A Statechart diagram that shows at least one state of the converted packages,
wherever the diagram itself sits; a Statechart diagram that shows none is not read. Its name is the workflow's name and
IRI. A diagram named `pfx:local` is the workflow `local` whose IRI is what `pfx` expands to, plus
`local`; the prefix is declared in the prefixes file like any other. A diagram named without a
prefix (`loan`) gets the IRI `schema_base` + `workflows/loan`, and one `derived-iri` report line
says so. Choose the name before the first data is stored: renaming the diagram to a prefixed name
later changes the workflow's IRI, which stored data refers to. The name follows the toolkit's name
pattern: a lower-case letter, then lower-case letters, digits and `-` (`loan`, `loan-review`).
* *The states.* One _State_ element for each state, named as the state is called, placed on the
diagram. A state sits on exactly one Statechart diagram. A substate, a state with entry, do or exit
behaviour, a final node or any other pseudostate is refused, not ignored.
* *The initial state.* One _Initial_ node, and one _StateFlow_ out of it to a state of the diagram,
with no tagged value. The state it reaches is the initial state.
* *The transitions.* Every other _StateFlow_ between two states of the diagram, with the tagged
values below. A flow with a name, a guard, a trigger, a stereotype or another tagged value is
refused.
* *The class.* A class tagged `workflow` (<<tagged-values>>) names the workflow of its objects by
the workflow's name. When the converted packages hold a Statechart diagram, every such tag must name
one of them; a diagram that no class names is only reported.

[cols="1,4",options="header"]
|===
|Tagged value of a StateFlow |Value

|`roles`
|Required. Comma-separated role names; each is a `role` of a role definition drawn in the converted
packages (<<roles>>), at any level. A role no definition draws fails the run, so draw and convert
the roles with the workflows (xref:howto/uml-to-linkml.adoc#workflows-file[the how-to] gives the
order).

|`comment_required`
|Optional, `true` or `false`, written exactly so. A transition that needs a comment from whoever
takes it.
|===

The converter asks the toolkit's own `Workflow` to judge the result, so the name pattern and the
rules of a workflow are always the toolkit's. It writes one file for each diagram, with the states
sorted by name and the transitions by their two states, to `workflows/<name>.workflow.yaml` under
`--out`, in the format `install_service(workflows=...)` loads, and a `workflow` report line:
`workflow` `<diagram>` `<n> states, <m> transitions`. A model that draws no Statechart diagram
writes no `workflows/` file. The converter moves each workflow file into `workflows/` on its own,
so the folder may hold other files; they are kept.

[mermaid]
....
stateDiagram-v2
  [*] --> requested
  requested --> approved : roles = librarian
  requested --> refused : roles = librarian, comment_required = true
  approved --> returned : roles = librarian, reader
  refused --> requested : roles = reader
....

The diagram is named `lib:loan`, `lib` standing for `https://example.org/ns/library/`, and the
roles `librarian` and `reader` are drawn as in <<roles>>. The label of an arrow lists the tagged
values of the StateFlow. The file it becomes:

[source,yaml]
----
# workflows/loan.workflow.yaml
id: https://example.org/ns/library/loan
workflow_name: loan
workflow_states:
- approved
- refused
- requested
- returned
initial_state: requested
workflow_transitions:
- from_state: approved
  to_state: returned
  transition_roles:
  - librarian
  - reader
- from_state: refused
  to_state: requested
  transition_roles:
  - reader
- from_state: requested
  to_state: approved
  transition_roles:
  - librarian
- from_state: requested
  to_state: refused
  transition_roles:
  - librarian
  comment_required: true
----

A diagram that the toolkit would refuse stops the run, naming the element (<<fails>>). As for the
roles, the converter then loads each staged file with the toolkit's `load_workflow`; if that
refuses one, the run exits 1 with the loader's message and moves nothing.

[#fails]
== What fails

The converter collects every problem, prints them sorted as `[<rule>] <element>: <reason>` (the
rule is `no_rule` for an element no convention maps, else the name of the rule that was broken, such
as `class_iri`, `class_annotation` or `unique_key`), writes nothing and exits 1. The lines go to
standard error. Fix the EA model and run again.

A connector one of whose ends is a note, a text or a boundary object, or a package, is ignored
whatever its type, so a comment drawn onto a class never fails the run. A connector of a type no
convention maps between two converted classes still fails.

[cols="3,4",options="header"]
|===
|What the model has |Fix in EA

|An association class (a class attached to an association)
|Draw an ordinary class with two associations, one to each end.

|An n-ary association (a diamond node), or any other element type: `Interface`, `Component`,
`Activity`, `DataType`, or an `Object` that is not a role definition (`[no_rule] <name>: Object of
<class>`)
|Model the relation as a class and use associations. Use only classes, enumerations, packages and,
for roles, Objects of `rp:RoleDefinition` (<<roles>>).

|A role definition Object whose run state is wrong: a variable other than `role`, `level` and
`actions`, one missing or given twice, an operator other than `=`, or text outside the blocks
(`[role_run_state] <object>: variable level is missing`)
|Set `role`, `level` and `actions` once each, with `=`, in the Object's run state (<<roles>>).

|A role definition the toolkit refuses: a level or an action it does not list, no action, or one
twice (`[role_definition] <object>: level: Input should be 'system', 'tenant' or 'aggregate' (given 'planet')`)
|Use a level and actions from the table in <<roles>>.

|Two role definitions with one role and level (`[role_duplicate] <object>: <role> at <level> is also
defined by <other>`)
|Keep one, or give the second another level.

|A Statechart diagram with no Initial node, two, or an Initial node with no flow or several leaving
it, or one whose flow carries a tagged value (`[workflow_initial] <diagram>: ...`)
|Draw one Initial node and one untagged flow from it to a state (<<workflows>>).

|A state on no Statechart diagram or on two (`[workflow_node] <state>: ...`); a node that is a
substate, a final node or another pseudostate, or a state with entry, do or exit behaviour
(`[no_rule] <node>: ...`)
|Place each state on exactly one diagram. Draw only States and one Initial node, flat.

|A transition that has no `roles`, names a role no role definition draws, has a tag other than
`roles` and `comment_required`, a `comment_required` that is not `true` or `false`,
leads into the Initial node, runs between two diagrams or repeats another between the same two
states (`[workflow_transition] requested -> approved: roles: archivist is not drawn as a role
definition`)
|Fix the tagged values, or draw the role definition (<<roles>>); keep one flow between two states.
A flow with a name, a guard, a stereotype or a trigger, or one that reaches outside the converted
packages, is `[no_rule]`: remove it.

|A diagram whose name breaks the toolkit's name pattern, whose states repeat a name, or that the
toolkit's `Workflow` refuses otherwise (`[workflow_definition] <diagram>: ...`); two diagrams with
one workflow name or one IRI (`[workflow_duplicate]`)
|Rename the diagram or the state; give each diagram its own name.

|With a Statechart diagram converted, a class whose `workflow` tag names no drawn workflow
(`[workflow_class] <class>: workflow: 'x' is drawn by no Statechart diagram`)
|Correct the tag, or draw the workflow. With no Statechart diagram converted, the tag is written as
it is, unchecked.

|A multiplicity that is not valid: `2..1`, `a..b`
|Write `m..n` with `m` not above `n`.

|Two or more generalisations to domain classes
|Keep one parent. Express the other as a slot, or as a toolkit mixin (`rp_mixins`).

|Two `is_a` sources: a domain parent and a toolkit class that is not a mixin (`Activity`), or two
such toolkit classes (`[no_rule] Book: two is_a sources, Series and Activity`)
|Keep one. Name a toolkit mixin instead of the second.

|A domain class named like a toolkit class, with another IRI
(`[class_iri] Activity: <your IRI> and <the toolkit's IRI> both map to Activity`)
|Rename the class.

|A name in `rp_mixins` or in `--default-mixins` that is not a toolkit class
(`[toolkit_mixins] Book: Nope is not a toolkit class; the toolkit classes are ...`; for the option,
the element is `--default-mixins`)
|Correct the name; the message lists the toolkit's classes.

|`dct:hasPart` roles from one reference collection to two different classes
(`[toolkit_slot] Shelf: dct:hasPart roles to Book and Map: ...`)
|Keep one role: a collection has one member class. Draw a second collection for the other class.

|A subclass's `dct:hasPart` role to a class that does not descend from its parent collection's
member class (`[toolkit_slot] Shelf: dct:hasPart role to Chapter does not narrow ...`)
|Point the subclass's role at a descendant of the parent's member class, or generalise the member
class to it.

|A package `module_kind` tagged value the metamodel does not list
|Use `domain` or `access` (`technical` only when every package is).

|Two sibling packages with one name and different `module_kind` values (<<module-kind>>)
|Rename one of the packages, or give both the same kind.

|Packages of different kinds that import each other: the conversion succeeds and `rp-generate`
refuses the output, naming the domain module and the access one (<<module-kind>>)
|Break the reference between the packages of different kinds.

|Classes that inherit both ways between two packages (a class of package A with a parent in B, and a
class of B with a parent in A): the conversion succeeds and `rp-generate` refuses the output at its
`python` step, naming the modules and the classes
(xref:user-manual/generate.adoc#module-cycles[Schema modules that import each other])
|Move the classes that inherit from one another into one package.

|An Aggregation connector that is shared (a hollow diamond), or whose diamond is at both ends or at
neither (`[boundary_owned] Shelf -> Book: a shared aggregation; draw a composition (strong) or a plain
association`; `[no_rule] A -> B: composition with no single diamond end`), or whose diamond value is
not 0, 1 or 2 (`[no_rule] A -> B: aggregate value 3`)
|Draw a composition: the strong diamond at the whole, and only there (<<composition>>).

|A composition with no association from the whole to the part (`[boundary_owned] Shelf -> Book: a
composition needs an association Shelf -> Book that names the role`); two or more such associations
and no role on the composition; a role on the composition that names none of them (`role r names no
association ...`)
|Draw the association beside the composition. With several, write the role on the composition
(<<composition>>). An association to a subclass or a superclass of the part does not count.

|A composite association: an association whose end is composite (`[boundary_owned] Shelf.holds: a
composite association; draw an Aggregation (composition) Shelf -> Book beside a plain association`)
|Replace it by a plain association and a composition (<<composition>>).

|A part class that no root reaches, or compositions that form a cycle no root enters
(`[boundary_owned] Section: no root reaches it (wholes Book, Journal)`; `compositions form a cycle
A → B → A that no root reaches`)
|Give the part a whole that a root reaches, or break the cycle.

|A composition whose end is outside the converted packages or in an excluded one, is a drawn toolkit
class or an enumeration, whose part is the «tenant root», or where a domain whole composes a part of
another module kind
|Compose converted domain classes only; a toolkit class is a mixin (`rp_mixins`) (<<composition>>).

|A stereotype on a composition other than «own graph» (`[no_rule] W -> P: connector stereotype S`);
«own graph» to a generated class; a plain composition to a not-generated class
|Use «own graph» for a part of a not-generated stereotype and a plain composition for a generated
one (<<own-graph>>).

|A generalisation to or from a class inside an own graph
|Remove the generalisation; the class is stored inside the part's graph (<<own-graph>>).

|A pointer at a part of an aggregate the holder is not in; a role owned on one whole and a pointer on
another class (<<pointers>>)
|Point at the aggregate's root, or give the pointer its own role name.

|A class drawn «root» that is a part, a derived root not drawn «root», or a «root» on an abstract
class (`[root_class] <class>: ...`); the «tenant root» as a part
|Make the drawn set equal the derived roots, or drop «root» (<<root>>).

|A Realisation from an Object to another class than its classifier, or to two classes
(`[role_definition] <object>: realises ...`); a Realisation from a class
(`[no_rule] A -> B: Realisation connector`)
|Realise the classifier only (<<realisation>>). Draw nothing from a class.

|A run with neither `--out` nor `--check`
|Pass `--out`, or `--check` (<<conventions>>); this is a usage error, exit 2.

|A class stereotype that is not `root`, `tenant root`, `Abstract` or in the not-generated list
|Remove the stereotype, or add it with `--not-generated` if the class is out of scope.

|A class with two stereotypes
|Keep one.

|A stereotype on a connector
|Remove it; a connector carries none of the toolkit's conventions.

|A generalisation from an enumeration, or to a class that is not converted; a slot held by an
enumeration
|Generalise classes that are converted, and keep an enumeration to its literals.

|A package that holds no class or enumeration to convert
|Name the package that holds the model in `--package`.

|No direction, a direction other than `Source -> Destination` or `Bi-Directional`; two roles on a
`Source -> Destination` association
|Set the direction in EA. For two roles, set `Bi-Directional`.

|An association with no role at either end, or a dependency with no target role
|Name the target role.

|A dependency to a converted class
|A dependency leads to an enumeration. For a class, use an association. A dependency to a class
that is not generated or outside the package is a `range: uri` slot and does not fail.

|An association whose destination end is composite (the whole is the destination)
|Draw the whole as the source: a plain association and a composition (<<composition>>).

|An attribute typed by a class, or by an XSD type not listed in <<model2owl>>
|Use an XSD datatype or an enumeration, or draw an association.

|`rdf:langString`
|Wait for issue #209, or type the attribute `xsd:string` and accept losing the language.

|A prefix not in the prefixes file, or two elements with one name and different IRIs
|Declare the prefix; rename one element.

|A slot name used in several packages where no one of them is reached by imports from all the
others (`[shared_slot_across_packages] location: used in ... and no one of them is imported by the
others`)
|Move the classes into one package, or make one package refer to the rest (<<shared-slots>>).

|A role redrawn as unbounded (`0..*`) on a class whose `is_a` ancestor draws the same role bounded
(`[cardinality_unbounded] Derived.part: Base.part is bounded at 5, ...`)
|Bound the role on the subclass (`0..5` or less), or unbind the ancestor's role (`0..*`).

|A tagged value with a bad value (`[class_annotation]`), a tag named like a metamodel annotation
that is not a class annotation, or a `unique_key` with a bad grammar, an unknown attribute or a
repeated name (`[unique_key]`)
|Fix the value; the message names the class, the tag and the cause (<<tagged-values>>).
