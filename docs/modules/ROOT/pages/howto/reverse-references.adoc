= Find who points at a resource
:description: How to list the aggregates that refer to a resource with Collaboration.referrers, what comes back, how referrers the caller may not read are counted, the errors, and the limits.

_Who points at this resource? Which books stand on this shelf? Is it still in use before I delete
it? Why is the list shorter than I expect, and what is `hidden_count`?_

This page shows how to ask a tenant which aggregates refer to one resource. It describes
`develop` as of 2026-11-14 (the change `collaboration-and-reference-collections`). The terms
tenant, aggregate, kit and IRI policy, and the names `kit`, `t` and `Action` in the snippets, are
those of xref:howto/adopt.adoc[Build an application]; the errors are imported from
`rdf_persistence`.

A *referrer* of a resource is an aggregate that has a stored slot holding the IRI of that resource.
The running example is the toy library: a book has a `shelf` slot that holds the IRI of a shelf, so
every book on shelf s1 is a referrer of s1. Nothing is stored on the shelf itself; the toolkit
finds the referrers by reading across the aggregates of the tenant.

== Ask for the referrers

A *collaboration* is the access-aware service the kit opens for one authorised caller. Check the
caller first, as for any read (see xref:howto/adopt.adoc#access[step 11]), then open the
collaboration with the answer and call `referrers` with the IRI of the resource:

[source,python]
----
checked = await kit.require_aggregate(
    request.headers.get("authorization"), t, "shelves", shelf_id, Action.READ
)
async with kit.collaboration(checked) as collab:
    found = await collab.referrers(checked.checked_target)

for item in found.referrers or []:
    print(item.referrer, item.referrer_class, item.referrer_slot)
# https://…/books/b1 Book shelf
# https://…/books/b2 Book shelf
print(found.hidden_count)    # 0
----

`kit.collaboration` takes the answer of `kit.require` or of `kit.require_aggregate`. The
collaboration acts as that caller, on that tenant. `referrers` checks again, itself, that the
caller may read the resource.

== What comes back

A `ReferrerList`, a generated model with two slots:

[cols="1,3",options="header"]
|===
|Slot |What it holds
|`referrers` |One `Referrer` per referrer and slot, sorted by the referrer's IRI, then by slot. `None` when there is none, so read it as `found.referrers or []`.
|`hidden_count` |The number of referrers the caller may not read. Always present; 0 when nothing is hidden.
|===

Each `Referrer` holds `referrer` (the IRI of the aggregate), `referrer_class` (the name of its
schema class, here `Book`) and `referrer_slot` (the name of the slot that holds the reference,
here `shelf`). A class or a slot the schema does not know is given as its IRI.

* A referrer that refers by two slots is listed twice, once per slot.
* When a part of an aggregate holds the reference, the item names the aggregate, with the part's
  slot. A note in a chapter of book b2 that is `about` book b1 makes b2 a referrer of b1:
  `(b2, Book, about)`.
* A resource nothing refers to gives no items and a `hidden_count` of 0.
* The tracking statements of a graph (its creator, its contributors) do not count.

== Narrow by class or by slot

Pass `class_name` to keep only the referrers of one schema class, `slot` to keep only the
references held by one slot, or both. Both take names of the schema, not IRIs.

[source,python]
----
found = await collab.referrers(b1_iri, slot="sequel_of")     # the sequels of b1; notes about b1 are left out
found = await collab.referrers(b1_iri, class_name="Shelf")   # no shelf refers to a book: nothing
----

[#hidden]
== Referrers the caller may not read

The list holds only the referrers the caller may read. The others are counted in `hidden_count`
and never named: no IRI, no class, no slot.

Say books b1 and b2 stand on shelf s1, and Bob is prohibited from reading b2. Bob gets one item,
b1, and a `hidden_count` of 1. A hidden referrer counts once, however many of its slots refer.

The count is there so that you can warn the caller that other uses exist ("one more item uses this
shelf") without telling what they are. It counts aggregates, while the list has one item per
referrer and slot, so the two do not add up to a total.

The count is the same whatever you narrow by: it answers the question without `class_name` and
`slot`. Ask for the shelves that refer to a book and you may get no item and a `hidden_count` of 1,
for a hidden book that refers to it. If the count followed the narrowing, a caller could ask class
by class and slot by slot and learn the class and slot of a referrer it may not read. How a read is
decided is in
xref:architecture/access-control.adoc[Access control and identity].

== Errors

[cols="1,3",options="header"]
|===
|Error |When
|`InvalidIri` |The IRI is not an aggregate IRI the IRI policy mints for the tenant.
|`NotFound` |The caller can see nothing of the resource.
|`Forbidden` |The caller may see the resource but not read it.
|`BadQuery` |`class_name` or `slot` is not a name of the schema.
|`DatabaseGone` |The tenant database does not exist.
|===

== Limits

* *No paging yet.* The whole result comes back in one answer. It is meant for hundreds of
  referrers, not more.
* *The tenant root is never listed as a referrer*, even if one of its slots holds the IRI.
* *An aggregate stored with no type is not found.* The mapper and the generic API always write the
  type; only triples written by hand can lack it.
* *`referrers` informs; it protects nothing.* The toolkit has no referential integrity: a delete is
  never refused because of referrers. To keep a shelf that still holds books, call `referrers`
  in your own delete route and refuse there, also when the list is empty and `hidden_count` is
  not 0. The answer of a delete check opens the collaboration as well: an action other than
  `read` implies `read`. Another request can still add a reference between your check and your
  delete; nothing locks the resource.
* *A graph loaded into an aggregate is not read.* Only the aggregate's own graph counts; a triple
  in RDF you loaded for it is not a reference.
* *Narrowing compares names, exactly.* `class_name="Book"` keeps the items shown as `Book`, not
  those of a subclass, and an item shown with an IRI matches no name.
* *`referrers` does not check that the resource exists.* A well-formed IRI of the tenant that no
  aggregate has gives an empty result, like a resource nothing refers to.
* *A comment's link to its target does not count.* The comments on a book are not its referrers.
  A comment that *references* a resource is a referrer of it, shown as `Comment` with the slot
  `comment_references`. It is listed only to a caller who may read the comment's target and sees
  the comment in that thread; otherwise it is counted in `hidden_count`. See
  xref:howto/discussion.adoc[Comment on a resource without editing it]. Transition records do not
  exist yet.
