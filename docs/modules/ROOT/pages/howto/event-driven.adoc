= React to changes with commands and observers
:description: How to model a use case as a command, send it through the in-process message bus, write a handler that changes aggregates and an observer that reacts after the commit, test them with the real bus, the errors, the limits, and how the relay carries commits to other deployments over Redis and to browsers over server-sent events.

_What is a command? How do I make something happen after a book is approved? Where is the history of
who did what? Why did my observer not run? Can an observer write? How do other deployments or a
browser follow my commits? Is a message delivered once?_

This guide builds an event-driven application on the toolkit: a *command* asks for a change, a
*handler* makes it, and an *observer* reacts to what was committed. The second part, <<relay>>,
carries the commits to other deployments and to browsers.

It assumes the model of xref:user-manual/model.adoc[step 3], the unit of work of
xref:user-manual/store-and-read.adoc[step 8], the service kit (`kit`) of
xref:user-manual/serve.adoc#the-service-kit[step 12] and the fakes of
xref:user-manual/test.adoc[step 13]. A *collaboration* (`collab`) is opened as in
xref:howto/reverse-references.adoc[Find who points at a resource]; the workflow is the one of
xref:howto/workflow.adoc[Put a resource through review]. In the snippets, `t` is the tenant id
taken from the path; `Action`, `MessageBus`, `bootstrap`, `command`, `Work`, `Activity`,
`Transition`, `UnitOfWork` and the errors are imported from `rdf_persistence`. The running example
is the toy library: a librarian approves a book and shelves books.

== The parts

A *command* is a request, written as a class of your model: a subclass of the toolkit's `Activity`.
Its slots are the request's data (`used_resource`, the book it is about; `shelf_note`, a note). You
build one with `command(ShelveBooks, used_resource=book, shelf_note="top shelf")`, which gives it
a provisional id of the form `urn:uuid:…`.

The id is provisional because the commit that serves the command places it under the
xref:user-manual/iri-policy.adoc#activity-iris[IRI policy]. Under the default policy the activity
keeps the id as it is. Under an `activity_template` such as `{tenant}/activity/{id}` the record, the
observers and the event stream get `<tenant>/activity/<uuid>`, with the same UUID. A handler that
stores the id (in an aggregate, or in a slot of a later command) asks the session for the placed
one, `work.session.activity_iri(cmd.id)`, which raises `ValueError` for an id that is no activity
id of this tenant. The logs of the bus show the provisional id; the record holds the placed one.

A *handler* is an async function that carries a command out. It gets the command and a `Work`
(the session, the caller's collaboration, a unit of work). One command goes to one handler: the
handler of its own class, or of the nearest ancestor class that has one.

An *activity record* is what the toolkit stores for every commit, whether a command caused it or
not: one `prov:Activity` in the tenant's provenance graph, with its start, its end, the principal
and, for each aggregate it touched, a *generation* (a new version) or an *invalidation* (a removed
or replaced version). It names the aggregates and their version tokens and never holds their
content. A commit made by a command is stored as an instance of the command's class; a commit made
without one is a plain `Add`, `Replace` or `Remove`, or an `Activity` when its changes are of more
than one kind. A record is never removed, not even with the aggregate it names.

An *observer* is an async function called after the commit with the completed activity. It is
registered for a class and also receives the activity of every subclass, so an observer of
`Transition` sees an `ApproveBook`, and an observer of `Activity` sees every commit.

[source]
----
bus.handle(command, collab) → handler → commit + activity record → observers of the class and its ancestors
----

== Model the commands

Put each use case that changes state in a module of its own, `<domain>_activities.yaml`, that
imports the domain module; the domain module never imports it, so the stored model stays free of
process concerns. The toy's is `books_activities.yaml`, shown as it is in the repository: a module
also needs its `title`, `description`, `prefixes` and `module_kind`.

[source,yaml]
----
id: https://example.org/ns/library/books_activities
name: books_activities
title: Book activities module
description: The use cases that change books, modelled as activities (rule P-0001); books.yaml never imports this module.
prefixes:
  lib: https://example.org/ns/library#
  linkml: https://w3id.org/linkml/
  rp: https://meaningfy.ws/ns/rdf-persistence#
default_prefix: lib
default_range: string
imports:
  - linkml:types
  - books
  - rdf_persistence/model/rp_provenance
  - rdf_persistence/model/rp_workflow
annotations:
  module_kind: domain

classes:
  ApproveBook:
    title: Approve book
    description: The command to approve a book, a workflow transition the toolkit's own handler carries out.
    class_uri: lib:ApproveBook
    is_a: Transition
  ShelveBooks:
    title: Shelve books
    description: The command to shelve a book, with a note on the shelf.
    class_uri: lib:ShelveBooks
    is_a: Activity
    slots: [used_resource, shelf_note]

slots:
  shelf_note:
    title: Shelf note
    description: A note the librarian leaves with the shelving.
    slot_uri: lib:shelfNote
    range: string
----

* *An extension specialises a standard command.* `ApproveBook is_a: Transition` has everything a
  transition has (`used_resource`, the book; `to_state`, the state to move to; `expected_version`,
  the version the caller read; `body_value`, an optional comment) and the toolkit's handler carries it
  out. You add slots only if your use case needs more. The stored record is an `ApproveBook`, so
  an observer can tell an approval from any other transition.
* *A use case over several aggregates is a bare `Activity` subclass.* `used_resource` is one IRI.
  If a command is about several books, declare a slot of your own for them, as `shelf_note` is a
  slot of its own.
* *Add the module to the root schema*: list `books_activities` under its `imports` (as for any
  module, see xref:user-manual/model.adoc[step 3]), then regenerate
  (xref:user-manual/generate.adoc[step 4]). The module declares
  no stored class, so it needs no generation target of its own.
* *Model no event classes.* The events are the toolkit's fixed set of PROV generations and
  invalidations; an observer reads them from the activity.

=== What the generator refuses

`rp-generate` stops, and names the class, when:

* a consumer class gives `slot_usage`, `ifabsent` or an attribute of its own to a slot the
  toolkit fills: the start, the end and the principal of an activity, its generations and
  invalidations, and for a transition its two states and its comment. A command does not set
  these; the bus refuses a command that arrives with one set (`InvalidBody`, before the handler
  runs).
* a command class has a slot that is both required and `payload`. A `payload` slot is data the
  command carries and the record does not keep (the comment text of a transition, for one); it is
  never required.
* a slot of a class that is not an activity ranges over an activity class of yours that is not an
  aggregate root. Stored data does not point at commands; the other way round is what the
  activity's `used_resource` is for. A slot may range over a toolkit activity class (`Activity`,
  `Transition`).

== Wire the message bus

The *message bus* is `kit.bus`, the in-process one of this page: it runs handlers and observers. (The
*event bus* of <<relay>> is another thing: the adapter that carries commits through a broker to other
deployments.) `bootstrap` builds the message bus from your handlers and observers, each registered under a class, and
from the dependencies they need:

[source,python]
----
from rdf_persistence import bootstrap, Activity, Work

from library.domain.generated.books import Book
from library.domain.generated.books_activities import ApproveBook, ShelveBooks


async def shelve_books(cmd: ShelveBooks, work: Work, shelf: str) -> None:
    uow = work.unit_of_work()
    book = await uow.get(Book, cmd.used_resource)
    book.shelf = shelf
    uow.add(book)
    await uow.commit()


async def notify_approval(activity: Activity, work: Work, mail: Mailer) -> None:
    await mail.send(f"{activity.generations[0].entity} was approved")


bus = bootstrap(
    mapper=kit.mapper,
    commands={ShelveBooks: shelve_books},
    observers={ApproveBook: [notify_approval]},
    shelf=SHELF_IRI,
    mail=mailer,
)
kit.bus = bus
----

* `commands` maps a class to its handler; `observers` maps a class to a list of observers. These
  two names, `limits` and `mapper` are `bootstrap`'s own, so a handler or observer cannot take a
  dependency of those names.
* Every parameter after `(command, work)` is a *dependency*, matched by its name to a keyword of
  `bootstrap` (`shelf`, `mail`; the annotation plays no part). A dependency no handler or observer names is a `ValueError`, and so is a
  handler or observer parameter with no default and no dependency, so a typo fails when the bus
  is built, not at the first message.
* The toolkit's handlers for `Transition`, `PostComment` and `PostReply` are added unless you
  register your own for the class. That is why `ApproveBook` needs no handler here.
* `mapper=kit.mapper` gives the bus the mapper that builds a command's record and the units of
  work. Without it `work.unit_of_work()` raises `RuntimeError`.
* *Set `kit.bus`* after you build the bus. The kit is built first (a handler's dependencies are
  often parts of it), so the bus comes second; `install_service(..., bus=bus)` does the same when
  you have the bus before the call, but the bus must be built with the kit's mapper, so the usual
  way is `kit.bus = bootstrap(mapper=kit.mapper, ...)` after the kit exists. The kit hands every commit of a tenant database or the
  application database to `kit.bus`, so the generic HTTP routes reach your observers too. With no
  bus, commits are recorded and nothing is handed over.
* A `limits=LimitSettings(max_messages=...)` keyword (default 100) bounds the commands one `handle` call runs; see
  <<limits>>. `SHELF_IRI` is the IRI of a stored shelf and `Mailer` stands for any class of yours;
  `Book.shelf` is the toy's slot that holds a shelf's IRI.

== Send a command

In a route of your own (`request`, `t` and `book_id` come from it, as in
xref:howto/discussion.adoc#post-a-comment[Post a comment]), check the caller as for any write, open the collaboration, build the command and hand it to the
bus:

[source,python]
----
checked = await kit.require_aggregate(
    request.headers.get("authorization"), t, "books", book_id, Action.MODIFY
)
async with kit.collaboration(checked) as collab:
    result = await kit.bus.handle(
        command(ShelveBooks, used_resource=checked.checked_target, shelf_note="top shelf"),
        collab,
    )
----

`handle` returns what the handler returns, and the handler's error reaches you unchanged
(`Conflict`, `Forbidden` and the rest, all imported from `rdf_persistence`, as is `InvalidBody`). A command with no handler along its class hierarchy
raises `LookupError("no handler for DeleteFile")`; a command with a toolkit-filled slot set
raises `InvalidBody`. The bus checks no access: the handler's calls do, as the collaboration
always does.

In the next snippet `book` is the book's IRI and `version` its token, read as in
xref:howto/workflow.adoc#make-a-transition[Make a transition]; `accepted` is a state of that
workflow. An `ApproveBook` carries the transition's data; the toolkit's handler calls the same
`collab.transition` as the page on workflows, and the record is an `ApproveBook`:

[source,python]
----
await kit.bus.handle(
    command(ApproveBook, used_resource=book, to_state="accepted", expected_version=version),
    collab,
)
----

== Write a handler

A handler changes aggregates through `work.unit_of_work()` and commits once:

* *One command, one commit.* The unit of work belongs to the command: its record carries the
  command's class and slots. A second commit with it is an error (`RuntimeError`). If a use case
  needs two commits, send a second command with `await work.send(...)` (see <<limits>>).
* *Several aggregates are one commit.* Add and change all the roots in the one unit of work, as in
  xref:user-manual/store-and-read.adoc#transaction[Save several aggregates at once]; one activity records them
  all.
* *Use the collaboration for what it owns.* `work.collaboration` is the caller's collaboration
  (`transition`, `comment`, `delete_cascade`); a handler that calls it instead of the unit of
  work is also one command, one commit. A call records the handled command only when you pass it
  (`command=cmd`), which `transition` and `comment` take; another call, such as `delete_cascade`,
  records a standard activity.
* *Keep free text and personal data in `payload` slots.* The record keeps a command's other slots
  for as long as the tenant exists, and is never removed.
* *Return what the caller needs.* `handle` returns it.

[#write-observer]
== Write an observer

An observer gets the completed activity and a `Work`. The activity is the generated model of the
stored record: its class, `id`, `was_associated_with`, `started_at_time`, `ended_at_time`, your
command's own slots, and `generations` and `invalidations`. It holds *references only*: the IRI of
each aggregate it touched, its class and its version token. To see the content, read it:

[source,python]
----
async def index_book(activity: Activity, work: Work) -> None:
    for generation in activity.generations or []:
        # get_graph returns the aggregate's triples (an rdflib Graph), its graph IRI and its version token
        graph, graph_iri, version = await work.session.get_graph(generation.entity)
        ...    # build whatever the observer builds from the graph
----

* *It runs after the commit*, in the same process, once per commit that the toolkit confirmed, with the
  observers of the nearest class first and, within a class, in the order you registered them.
* *It runs for every commit*, whatever caused it: a command, the generic `POST`, `PUT` and
  `DELETE` routes, a `UnitOfWork` of your own. Register for `Add`, `Replace` or `Remove` to see
  the generic ones.
* *Its error is logged with its name* and the other observers still run. It never undoes the
  commit and the caller does not see it.
* *It acts as the caller's principal, with the committing session's full reach.* The session is the
  one that committed, and a session checks no access: an observer can read and write anything in
  that database, not only what the caller could, and what it commits is recorded as the caller's
  activity. Check anything beyond the aggregates the activity names yourself: through
  `work.collaboration`, which checks access on every call, or through `kit.require`.
  `work.collaboration` is set only inside `handle` and only for a commit of that collaboration's
  session; for a commit made on another session it is `None`.
* *It can send a command* with `await work.send(command(...))`: the command runs after the
  current one, in the same `handle` call, with the caller's collaboration. If the handler then
  raises, the commands an observer queued are dropped; the commit and its publish stand.

== Test it

The bus is in process and has no I/O, so a test uses the real one on a fake store. The testkit's
`RecordingObserver` keeps the activities it was handed:

[source,python]
----
from rdf_persistence.testkit import RecordingObserver

async def test_shelving_is_observed(kit_with_fakes, collab):
    seen = RecordingObserver()
    bus = bootstrap(
        mapper=kit_with_fakes.mapper,
        commands={ShelveBooks: shelve_books},
        observers={ShelveBooks: [seen]},
        shelf=SHELF_IRI,
    )
    kit_with_fakes.bus = bus

    await bus.handle(command(ShelveBooks, used_resource=BOOK_IRI, shelf_note="top"), collab)

    assert [type(a) for a in seen.activities] == [ShelveBooks]
    assert seen.activities[0].generations[0].entity == BOOK_IRI
----

`kit_with_fakes` and `collab` are pytest fixtures you write: a kit built over `FakeStore` as in
xref:user-manual/test.adoc[step 13] (the test is async, as there) and a collaboration
opened on it. `BOOK_IRI` is a book you stored first. Test a handler by
its stored result (read the book back) and an observer by what it does; use `RecordingObserver`
when the thing to check is that it was called, and with what.

[#limits]
== Limits

* *At most once, in process.* An observer runs in the process that committed, after the commit. If
  the process stops between the commit and the observers, they never run, and nothing retries. The
  record stays in the provenance graph, but nothing replays it. Durable delivery to other
  deployments is the relay of <<relay>>; build nothing that needs it on this bus.
* *One command, one commit.* A second commit with the same command is refused. A handler that
  must change things in steps sends a command for each.
* *An observer should not write the aggregate it observes.* Its commit is a new activity that
  reaches the observers again, and two observers of one class can overwrite each other. Send a
  command, or write another aggregate.
* *`work.send` only works inside `handle`.* An observer of a commit made by a generic route (no
  `handle` call, so no collaboration to run the command with) that calls `work.send` gets a
  `RuntimeError`, which is logged as that observer's error. Do such work in the route, or write
  the route to call `bus.handle`.
* *The loop limit.* One `handle` call runs at most `limits.max_messages` commands (default 100): the first, and
  every one an observer or handler queued. The next raises `MessageLimitExceeded` ("message limit
  100 reached by <command class> <command id>") from `handle`, which does not log it, and the
  commands still queued are dropped. The place that handles the error logs it once: the kit's
  queue handler, or, for an HTTP route, the problem handler (a 500, "internal error answered"). An observer that commits again on its own session is stopped at the same limit,
  inside `handle` or not. When a `handle` that an observer calls itself joins the count and passes
  the limit, its error is logged by the commit's hook and not raised to the outer caller. A queued command's own error is logged and the queue goes on, because the
  caller's command already succeeded.
* *The false conflict.* A commit that applied, but whose graphs another writer overwrote before
  the toolkit could confirm it, is reported as a `Conflict` (see
  xref:architecture/commits.adoc#conflict[what a conflict means]). Its activity is recorded and not
  handed to the observers. A commit that applied but was overtaken in part is published once its
  activity is stored. Read again before retrying.
* *Observers have the session's full reach.* There is no service account: an observer acts as the
  caller's principal, and the session checks no access (see <<write-observer>>).
* *No handler for `Add`, `Replace`, `Remove`.* The toolkit records and publishes them but has no
  handler: they are what the generic routes and your own units of work produce. Register a
  handler of your own to send them as commands.

[#relay]
== Carry commits to other deployments and to browsers

The message bus above reaches observers in the process that committed. The *relay* reaches the
rest: other deployments of the toolkit through a broker, and browsers over server-sent events. Both
are built on the activity record, so what they carry is the same thin activity an observer receives
(references, never content).

Terms used below:

* *Event bus*: the toolkit's port to a broker (`EventBus`); `RedisEventBus` is its Redis
  implementation. Not to be confused with the message bus, `kit.bus`.
* *Pending mark*: a statement written on an activity record in the same update that stores the
  record, with the store's own clock. It says "not yet relayed"; the relay replaces it by a
  "relayed" time.
* *Application database*: the database for data that belongs to no tenant (see
  xref:howto/application-data.adoc[Keep data that belongs to no tenant]). It has a relay mark too,
  but no browser follows it.
* *Consumer group*: a Redis Streams name under which a reader shares the position in the stream.
  Each deployment reads the stream as one group, so it gets every entry once and the entries of
  one deployment are not split across others.
* *Toolkit principal*: the toolkit's own identity (not a person), used for work that no person's
  request started, such as handing a received message to the observers.

=== How the relay works

* The commit that records an activity also writes a pending mark on it. The relay is one task the
  service starts after its migrations. It visits the application database and every active tenant,
  reads the marked activities in order, publishes each to the event bus, replaces the mark by a
  "relayed" time, and offers the activity to the server-sent-events hub of <<sse>>.
* *When a round runs.* A commit made in this process wakes the relay at once. Otherwise a round
  runs every 5 seconds by default: that is `EventSettings.relay_interval_seconds`, which you set with
  `install_service(..., toolkit=ToolkitSettings(events=EventSettings(relay_interval_seconds=...)))`.
  So a commit made in another process waits up to that interval to be relayed.
* *At least once.* A mark is replaced only after the publish succeeded, so a crash between the two
  publishes the activity again at the next start. A failed publish stops that database for the
  round and is retried in the next, so no later activity of the database overtakes it.
* *Order.* The relay keeps one order, stated here once: *per aggregate*, the activities leave in
  the order the store applied the commits. Nothing is promised across aggregates, and a store clock
  stepped back can misorder one pair of changes.
* *Crash safety.* The mark is in the store with the record, so a commit is never lost to the relay:
  a process that stops after the commit is caught up by the next one. Only records marked by 0.4.0
  or later are relayed; history from before is not published.
* A record that cannot be decoded is marked as failed and logged at ERROR; the relay goes on with
  the next one.
* With no event bus the relay still runs: it feeds the server-sent events of <<sse>>.
* *One instance.* The relay assumes it is the only one for the stores. See <<relay-limits>>.

=== Install the extra and wire the event bus

The Redis event bus needs the extra `rdf-persistence[events]` (FastStream, pinned) and *Redis 8.4
or later*: redelivery uses a command older servers lack, and the consumer stops at start-up with
`StreamClaimUnsupportedError` on one. A consumer without the extra imports the toolkit unchanged;
only `rdf_persistence.events.adapters.redis_events` needs it.

In the examples, the `...` comments stand for what xref:user-manual/serve.adoc[step 12] passes
to `ServiceSettings` and `install_service`.

[source,python]
----
from rdf_persistence.events.adapters.redis_events import RedisEventBus

settings = ServiceSettings(
    # ... the settings of "Serve the application", and:
    deployment="library",                 # required with an event bus; lower case letters and digits
    public_url="https://library.example.org",
)
kit = install_service(
    app,
    # ... the other keyword arguments of "Serve the application"
    settings=settings,
    event_bus=RedisEventBus("redis://redis:6379", deployment=settings.deployment),
)
----

* *The URL above has no password and no TLS*, which suits a broker on the deployment's private
  network only. Elsewhere, give Redis a password and TLS and say so in the URL
  (`rediss://:<password>@<host>:6380`); every deployment on the broker reads every message (see
  <<relay-limits>>).
* *`deployment` is required with an event bus* (`install_service` raises `ValueError` without it)
  and *must be unique on a broker*. It is passed twice, and the two must be equal. In
  `RedisEventBus(deployment=...)` it names the deployment's consumer group; in the settings it is
  the origin written on each message this deployment publishes, which `receive` compares to skip
  its own messages. Nothing in the code checks that they are equal. A mismatch does not break the
  skipping of own messages (both sides of that comparison come from the settings), but the
  consumer group would then carry a different name from the origin: a group named like another
  deployment's makes the two split the stream between them, and each misses what the other took.
  Pass `settings.deployment` to both, as above, and keep the name unique on the broker.
* `public_url` is the address of the deployment seen from outside, without a trailing slash. A
  message carries a link to the JSON-LD context at `{public_url}{prefix}/context.jsonld`, where
  `prefix` is the path the service is mounted under (`install_service(prefix=...)`); with no
  `public_url` the link is relative (`{prefix}/context.jsonld`), which a consumer on another host
  cannot follow. Set it when other deployments read the messages. The server-sent events route
  sends the service's own context link in a `Link` header, as every other route does.
* `RedisEventBus` also takes two optional keyword arguments. `middlewares=` is a sequence of
  FastStream broker middlewares, passed to its `RedisBroker` unchanged
  (xref:howto/observability.adoc#redis[Trace the event broker] shows the telemetry middleware).
  `events=EventSettings(...)` groups the bus's own settings: `stream` (default `rp-events`),
  `retention_seconds` (default 7 days; older entries are trimmed after each publish),
  `claim_idle_seconds` (default 30, how long a failed message waits before it comes again) and
  `polling_interval_ms` (default 100). The relay and the hub read the same group (`relay_interval_seconds`,
  `publish_timeout_seconds`, `hub_queue_size`), which `install_service(toolkit=ToolkitSettings(events=...))`
  gives them.
* The service starts the bus's consumer with the app (receiving into `kit.receive`) and the relay
  after it, and stops both at shutdown.
* *A stream entry is FastStream's binary envelope.* The headers (tenant, origin, activity class,
  context link) and the body are written by FastStream, so read the stream with FastStream, not
  with a plain Redis client.

=== Receive what other deployments committed

A message from another deployment reaches `kit.bus` as if it were a commit here: the observers
registered for its class run, in a session of the toolkit principal on that tenant. That principal
is the toolkit's own identity, not the person who made the change (the activity's
`was_associated_with` names the person). So the usual caution of <<write-observer>> applies with the
whole reach of that session. Because no collaboration is open for such a message,
`work.collaboration` is `None` and `work.send` raises `RuntimeError` (logged as that observer's
error): an observer of a received message cannot send a command.

==== Two deployments, end to end

The sender `library` commits; the receiver `catalogue` reacts. Both run `install_service` with an
event bus on the same Redis.

[source,python]
----
# --- deployment "library" (the sender) ---
sender_settings = ServiceSettings(
    # ... the settings of "Serve the application"
    deployment="library",
    public_url="https://library.example.org",
)
install_service(
    app,
    # ... the other keyword arguments of "Serve the application"
    prefix="/api",
    settings=sender_settings,
    event_bus=RedisEventBus("redis://redis:6379", deployment=sender_settings.deployment),
)

# --- deployment "catalogue" (the receiver) ---
async def reindex(activity: Activity, work: Work) -> None:
    # work.collaboration is None here, and work.send would raise RuntimeError
    for generation in activity.generations or []:
        graph, _, version = await work.session.get_graph(generation.entity)
        ...    # update the catalogue's own index

receiver_settings = ServiceSettings(
    # ... the settings of "Serve the application", with the same tenant IRIs as the sender
    deployment="catalogue",
)
kit = install_service(
    app,
    # ... the other keyword arguments of "Serve the application"
    settings=receiver_settings,
    event_bus=RedisEventBus("redis://redis:6379", deployment=receiver_settings.deployment),
)
kit.bus = bootstrap(mapper=kit.mapper, observers={ApproveBook: [reindex]})
----

What the two must share:

* *The Redis URL and the `stream`* (the default `rp-events` on both, or the same `events.stream`).
* *The tenant IRIs.* A message names its tenant by IRI. The receiver skips a message for a tenant it
  has not got, so both deployments must mint the same IRI for the same tenant (the same IRI policy
  and tenant ids).
* *The class.* The receiver's schema must know the sender's activity class (`ApproveBook` here, from
  the same generated models). A toolkit class (`Add`, `Replace`, `Remove`, `Transition`) is always
  known; one the receiver lacks is skipped with a WARNING.
* *Different `deployment` names*, as above.

Each message also names the JSON-LD context that reads it, at the sender's `public_url`.

* A message whose headers are not a valid envelope (no tenant, origin or class) is dropped by the
  event bus before `receive`: logged at WARNING and acknowledged, since no deployment could handle
  it.
* A message whose origin is this deployment is skipped: its observers saw it at commit.
* A message the deployment cannot use is logged at WARNING and skipped, and the broker is told it
  is handled: an unknown class, a body that does not fit the class, a tenant this deployment does
  not have, or an application database with no application class. A message over the message bus's
  limit is logged at ERROR and skipped.
* *Which errors redeliver.* A tenant that is behind (its migration failed at start-up) and a store
  that does not answer are raised, so the message is not acknowledged and comes again after
  `events.claim_idle_seconds`, or at the next start. An error an *observer* raises is logged and acknowledged, as
  on the message bus.
* With no `kit.bus`, messages are skipped.

*Make observers idempotent by activity id.* At least once means a message may arrive twice (a crash
after the observer ran, before the acknowledgement). The toolkit does not de-duplicate; keep the
`id` of the activities you handled, or make the effect repeatable.

=== The guarantees, and every case that loses or repeats a delivery

Two guarantees, then the cases. *Ordering*, stated once: per aggregate, in the order the store
applied the commits; nothing is promised across aggregates.

[cols="2,2,3"]
|===
|Observer |Guarantee |Lost or repeated when

|In the process that committed (<<limits>>)
|At most once
|Lost: the process stops before the observers run, the commit was overtaken (the false conflict), or the observer raised.

|In another deployment, through the broker
|At least once
|Repeated: a crash after the observer ran and before the acknowledgement, or after the publish and before the mark is replaced. Lost: see the cases below.
|===

[cols="2,1,3"]
|===
|Case |Result |What happens and what to do

|An observer raises
|Lost
|Logged with the observer's name and acknowledged. Not retried, on the message bus and in a receiving deployment. Make the observer catch what it can recover from.

|A received message is unusable (unknown class, a body that does not fit, a tenant this deployment lacks)
|Lost
|Logged at WARNING, skipped and acknowledged. After you fix the schema or the tenant, the skipped activities are not replayed.

|A receiver is down for longer than the stream's retention (`events.retention_seconds`, 7 days)
|Lost
|The broker trims entries older than that after each publish. A receiver that comes back later misses them, and nothing republishes them. Keep the outage shorter, or read the provenance graph.

|Records from before 0.4.0
|Lost
|They have no pending mark, so the relay never publishes them and no browser can resume to them.

|The process stops between the commit and the observers
|Lost in process, kept for others
|The in-process observers never run. The pending mark is in the store, so the next start relays the activity to the broker and the browsers, and other deployments get it.

|A server-sent events reader gets an id again
|Repeated
|Within one connection the route sends an activity read from history once, not again from the live buffer. But a reconnect that resumes before it, or a relay re-offer after a crash, can repeat an id. The client drops ids it has seen.

|A slow server-sent events reader
|Lost, then resumed
|The connection is closed when 1000 events are queued for it; it reconnects with `Last-Event-ID` and gets what it missed (inside the window).

|Several instances of one deployment
|Repeated and missed
|Each instance runs a relay, so each publishes every activity: the broker carries it twice. A browser sees only the activities relayed by the instance it is connected to. Run one instance: see <<relay-limits>>.
|===

A change that applied but returned the false `Conflict` is relayed anyway (the change happened),
though the in-process observers did not see it. If you need at-least-once for your own commits,
observe them through another deployment (a second deployment on the same broker that receives what
the first one commits), or read the provenance graph.

*Loops across deployments.* An observer in deployment `catalogue` that commits on a message from
`library` makes a message `library` may react to, and the message bus's limit counts inside one
process only. Make an observer react only to the kinds of activity it does not itself produce.

=== Follow a tenant in the browser

The route `GET {prefix}/{tenant_segment}/{t}/rp-events` answers `text/event-stream`. `{prefix}` is
the `prefix` argument of `install_service` (empty by default), and `{tenant_segment}` is
`settings.tenant_segment`, `libraries` in the toy. The route needs no broker and no extra: the relay feeds it.

[source,bash]
----
# the sender above mounted its routes under prefix="/api"
curl -N -H "Authorization: Bearer $TOKEN" \
     -H "Last-Event-ID: urn:uuid:3f2c0b6e-5a1d-4c7e-9b8a-1d2e3f4a5b6c" \
     https://library.example.org/api/libraries/0b7c4e2a-6f1d-4b8e-9a3c-5d2e1f4a7b90/rp-events
----

The segment `rp-events` is under the toolkit's reserved `rp-` prefix, which the generator's
reserved-segment check keeps an aggregate from taking, so no aggregate's path can shadow it.

One event, as the stream sends it (the `data` is on one line in the stream; it is wrapped here):

[source]
----
id: urn:uuid:3f2c0b6e-5a1d-4c7e-9b8a-1d2e3f4a5b6c
event: Replace
data: {"id":"urn:uuid:3f2c0b6e-5a1d-4c7e-9b8a-1d2e3f4a5b6c",
       "was_associated_with":["https://idp.example.org/users/ada"],
       "started_at_time":"2026-11-16T09:30:00.120Z","ended_at_time":"2026-11-16T09:30:00.180Z",
       "generations":[{"activity":"urn:uuid:3f2c0b6e-5a1d-4c7e-9b8a-1d2e3f4a5b6c",
         "at_time":"2026-11-16T09:30:00.180Z",
         "entity":"https://example.org/library/libraries/0b7c4e2a-6f1d-4b8e-9a3c-5d2e1f4a7b90/books/7e1f9c3d-2a4b-4c6d-8e0f-1a2b3c4d5e6f",
         "entity_class":"http://purl.org/ontology/bibo/Book",
         "entity_version":"c41f7a2e-9b3d-4e8a-a6f1-2d5c8b0e7f13"}],
       "invalidations":[{"activity":"urn:uuid:3f2c0b6e-5a1d-4c7e-9b8a-1d2e3f4a5b6c",
         "at_time":"2026-11-16T09:30:00.180Z",
         "entity":"https://example.org/library/libraries/0b7c4e2a-6f1d-4b8e-9a3c-5d2e1f4a7b90/books/7e1f9c3d-2a4b-4c6d-8e0f-1a2b3c4d5e6f",
         "entity_class":"http://purl.org/ontology/bibo/Book",
         "entity_version":"5a9e2c71-4d8b-4f36-b1e0-9c7a3f2d6e48"}]}
----

* *`id`* is the activity's IRI. *`event`* is the activity class's bare name (`Replace`,
  `ApproveBook`). *`data`* is the activity's generated JSON (the model's `model_dump_json`), not
  compacted JSON-LD: the field names are the model's (`was_associated_with`, `generations`). The
  response's `Link` header names the JSON-LD context that reads it (the context of `settings.base`
  plus the prefix). The values above are made up, in the shapes the service gives them: the book's
  IRI as the default IRI policy mints it under `settings.base` (`libraries/<uuid>/books/<uuid>`),
  the principal as `{issuer}/users/{sub}`, and each `entity_version` a version token, a bare UUID
  (the `ETag` of the same version is that UUID in quotes).
* A comment line is sent every 15 seconds so a proxy does not close the stream.
* *The reader needs tenant `read`.* A person with grants on single aggregates and no tenant `read`
  is refused; they cannot follow the tenant. Inside the stream, the activity is *filtered* to what
  the reader may read: the aggregates they cannot read are removed from it. An activity is not sent
  when nothing is left of it, or when its `used_resource` (the resource a command names) is one
  the reader cannot read. Their access is re-read at most once a second, and the stream ends when
  it is withdrawn.
* *Resume with `Last-Event-ID`.* Send the `id` of the last event you got and the route sends what
  was relayed after it, then live events. The 7-day window is counted from the relay marks in the
  store (when the activity was relayed), so it holds with no broker and does not depend on the
  broker's retention. An id the server does not know, one from before 0.4.0, or one older
  than the window gets one `event: reset` with an empty `data:` line (an `EventSource`-style client
  does dispatch it). The client reloads what it shows, then keeps reading. A `Last-Event-ID` that
  is not an activity id (not `urn:uuid:` and a UUID) is treated as unknown: one `reset`, then live
  events; it is not an error.
* *A stream lasts 5 minutes.* The server ends it then (`sse.max_lifetime_seconds` of
  the toolkit settings, the `sse` argument of `add_events_route`), so a token that expired or was revoked is not outlived. The client
  reconnects with a fresh token and its last `Last-Event-ID`, and misses nothing. The stream ends
  at the first activity or keep-alive after the 5 minutes, so it can be up to 15 seconds longer.
* *A slow reader* is closed when 1000 events are queued for it; it reconnects with `Last-Event-ID`.
* *Repeated ids.* A client can get an id twice (a replay overlapping live events, or the relay
  offering an activity again after a crash). It drops ids it has already handled.

==== In the browser

The route takes the bearer token in the `Authorization` header only. The built-in `EventSource`
cannot send headers, so a browser uses a fetch-based client: `fetch` with a `ReadableStream`, or a
small library that does that. There is deliberately no token in the query string, where it would
leak into access logs.

[source,typescript]
----
import { fetchEventSource } from "@microsoft/fetch-event-source";

const url = "https://library.example.org/api/libraries/0b7c4e2a-6f1d-4b8e-9a3c-5d2e1f4a7b90/rp-events";
const seen = new Set<string>();          // ids already handled
let lastId: string | undefined;          // where to resume

// One stream; it resolves when the server ends it (after 5 minutes at most).
function follow(token: string, show: (activity: unknown) => void, reload: () => Promise<void>) {
  return fetchEventSource(url, {
    headers: {
      Authorization: `Bearer ${token}`,
      ...(lastId ? { "Last-Event-ID": lastId } : {}),
    },
    async onmessage(event) {
      if (event.event === "reset") {     // too old or unknown: reload, then keep reading
        seen.clear();
        await reload();
        return;
      }
      if (!event.data || seen.has(event.id)) return;   // keep-alive, or a repeated id
      seen.add(event.id);
      lastId = event.id;
      show(JSON.parse(event.data));      // the activity: event.event is its class name
    },
  });
}

// Keep following: each new stream takes a fresh token and resumes from lastId, so nothing is missed.
async function keepFollowing(
  freshToken: () => Promise<string>,
  show: (activity: unknown) => void,
  reload: () => Promise<void>,
) {
  for (;;) await follow(await freshToken(), show, reload);
}
----

The server ends each stream after 5 minutes so that it never outlives its token; `keepFollowing`
opens the next one. The library itself retries a dropped connection with the same token and sends
`Last-Event-ID` again. The `lastId` above is also for a new call after the page reloads; keep it
where the page can read it back.

[#relay-limits]
=== Limits of the relay

* *One instance.* Run one instance of a deployment: one process running the service (one uvicorn
  worker, one pod). Several workers or pods each run a relay, and each would publish every
  activity; each browser would also see only the activities its own instance relayed.
* *What a message reveals.* It names the IRIs of the aggregates, their versions, the principal, the
  time and the command's own slots that are not `payload`. Every deployment on the broker sees all
  of it, so the broker is inside your trust boundary. On server-sent events the filter removes the
  aggregates a reader may not see; an IRI that a slot names (a comment's) stays, as a reference.
* *No history before 0.4.0*, no replay of old records, and a restore never re-publishes the
  source's activities.
