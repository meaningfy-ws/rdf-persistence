= Generate the model from UML
:description: How to write the LinkML schemas of a model from an Enterprise Architect .qea file with rp-uml2linkml: the prefixes file, the command and its options, the exit codes, the report, and the rp-generate run that follows.

_How do I get the LinkML of my model from an Enterprise Architect (EA) UML model? What does the
converter write, what does it tell me, and what do I run next?_

This guide converts the class model you draw in EA into the LinkML schemas the rest of the toolkit
reads. The UML is then the source you edit, and the LinkML is written whole from it on every run: do
not edit the output by hand. `rp-generate` treats the result like any other schema, with the same
checks and targets (xref:architecture/generation.adoc#application-schema[What the application
writes]).

*Before you start:*

. An EA model saved as a `.qea` file (EA's SQLite format; an `.eap` file is not read). The converter
only reads the file, so it never changes your model. Save the model and close EA before you run it:
the converter reads the file as it is on disk, and a file EA is writing at that moment can be read
half old or refused (exit 2, `cannot be read`, step 2). Run it again once EA has saved.
. The toolkit installed with the `generate` extra, as for `rp-generate`: the package is
`rdf-persistence` and the extra `generate` (`uv add 'rdf-persistence[generate]'`, or
`pip install 'rdf-persistence[generate]'`). It puts `rp-uml2linkml` and `rp-generate` on your path.
If your project runs tools through uv, prefix every command here with `uv run`.
. A model that follows the xref:reference/uml-conventions.adoc[UML conventions]. Make it follow them
first: an element no convention maps stops the run. In short, a _root_ is a class stereotyped
«root», the entry point of an aggregate (the unit the toolkit stores and loads whole); a _part_ is a
class drawn inside the same aggregate boundary as its root; `Described` is the mixin that gives an
object a label and a description, and `Tracked` the one that carries the tracking
statements a commit writes about it. A root and its parts get both by default.

The names in the snippets (`lib:`, `Book`) belong to a small library model. In EA a name carries its
prefix: the class is `lib:Book`, an attribute `dct:title`, a role `lib:hasChapter`.

[#prefixes]
== 1. Write the prefixes file

The converter needs to know what each prefix in your EA names stands for. Write it as YAML. It is
not final: when the model gains a prefix, add it here (a missing one stops the run, see step 2).

[source,yaml]
----
schema_base: https://example.org/ns/library/   # a module's id is <schema_base><module name>
default_prefix: lib                            # the prefix of a name written without one
version: "1"                                   # the root schema's version, quoted
prefixes:
  lib: https://example.org/ns/library#
  dct: http://purl.org/dc/terms/
----

All four keys are required. Declare every prefix a name in the model uses, and the
`default_prefix` too: it must also be a key under `prefixes`, as `lib` is above. A name written
without a prefix takes it. The run stops at a prefix it does not find, with exit 1 (step 2). The
`xsd:` types of attributes need no entry. Name your prefixes as you like: where a namespace is one
the toolkit's own metamodel also names, the output uses the metamodel's prefix (your `dct:` is
written `dcterms:`).

[#run]
== 2. Convert

[source,shell]
----
rp-uml2linkml library.qea --package MODEL/library --prefixes prefixes.yaml \
  --out models/ --root-name library
----

When the model draws role definitions or workflows, `--package` must hold the packages of both
(<<workflows-file,the workflow files>> says why: a workflow may name only roles drawn in the same run).

The command reads the `.qea` and writes one schema file per package, a root schema
`<root-name>.yaml` that imports them all, and a report `<root-name>.uml-report.txt` into `--out`
(created when missing). In `--package MODEL/library`, `MODEL` is the root package of the model in
EA's project browser, and `/` separates a package from its parent.

A package becomes a module named `<root-name>_<package>`: the file is `<module name>.yaml` and the
schema `id` is `schema_base` plus the module name (the root schema's `id` is `schema_base` plus
`<root-name>`). The package is written below the `--package` package, in lower case with each run of
other characters (a space, a hyphen) one `_`, and `__` between a package and its subpackage:
with `--root-name library`, a package `Rare Books` directly below the `--package` package is
`library_rare_books`, and its subpackage `Maps` is `library_rare_books__maps`. Classes directly in the `--package` package go to `<root-name>_main`.
Packages that refer to each other are written as one module named after the first of them in path
order (`merged-cycle`). The
xref:reference/uml-conventions.adoc#packages[conventions page] gives the rest.

[cols="2,5",options="header"]
|===
|Option |Meaning

|`qea` |The `.qea` file. Required.
|`--package` |The package to convert, with its subpackages: a name, or a path from the model's root
package (`MODEL/library`) when the name is ambiguous. Required.
|`--prefixes` |The prefixes file of step 1. Required.
|`--out` |The folder to write into. Required.
|`--root-name` |The root schema's name (default `app`). It is also the prefix of every module file
and of the report.
|`--exclude-package` |A package path to leave out with its subtree; repeatable. A connector that
reaches an excluded package makes no slot (`excluded-link` in the report).
|`--default-mixins` |The toolkit mixins of a root and of its parts, comma separated (default
`Described,Tracked`). A name that is not a toolkit class is a model problem (exit 1).
|`--not-generated` |A stereotype whose classes and enumerations are not generated; repeatable. The
default is `loaded graph`; naming one or more replaces it, so name `loaded graph` again to keep it.
Quote a stereotype with a space: `--not-generated "loaded graph"`.
|===

The run ends in one of three ways:

[cols="1,5",options="header"]
|===
|Exit |What happened

|0 |The files are written. Read the report (step 3).
|1 |The model has problems. The converter prints every one, sorted, to standard error as
`[<rule>] <element>: <reason>`, and writes nothing. `<rule>` is the name of the rule that was
broken, or `no_rule` for an element no convention maps; an undeclared prefix is
`[class_iri] lib2:Chapter: prefix lib2 is not in the prefixes file`, or
`[cardinality_unbounded] Derived.part: ...` for an unbounded role under a bounded ancestor's (bound
the role, or unbind the ancestor's). Fix them in EA (the table in
xref:reference/uml-conventions.adoc#fails[What fails] names the fix for each) and run again. When
the model draws workflows, the converter also runs the check the service runs at start (<<whole-model>>);
a workflow it refuses is exit 1 as well, on one line,
`rp-uml2linkml: the written files would stop the service: <reason>`.
|2 |The setup cannot be used: an argument, the prefixes file (unreadable, not a mapping, a missing
key), a `.qea` path that does not exist (`<path>: no such file`), that cannot be read
(`<path> cannot be read: <reason>`) or that is not an EA `.qea`, a `--package` or
`--exclude-package` that is unknown or (for `--package`) matches more than one package, or an
`--out` that cannot be written (`cannot write <path>: <reason>`, naming the file or folder that
failed: a full disk, a file where the folder should be). A prefix the model uses but the file does
not declare is not this case: it is exit 1. One line on standard error, `rp-uml2linkml: <message>`.
|===

The files are staged in a folder inside `--out` and moved into place only when the whole run
succeeded, and the same model gives the same bytes, so a repeated run is safe and a diff of `--out`
shows what you changed in EA. After any failure, run it again. The report is moved last, so a run
that stopped part-way leaves no `<root-name>.uml-report.txt`: its absence tells you the write did not
finish. The converter deletes nothing of yours: a `<root-name>_*.yaml` left from an earlier run that
this run did not write stays, and is reported as `stale-file`. Delete it yourself when the package
it came from is gone.

A run that is killed (a power loss, a `kill -9`) can leave its staging folder, `.uml-write-<random>`,
in `--out`. The next run reports it as `stale-file` and does not delete it. Delete it yourself, and
add `.uml-write-*` to your project's `.gitignore` so that it is never committed.

Run the converter once at a time for one `--out`: two runs into the same folder at once are not
supported, and the last to move a file wins.

[#report]
== 3. Read the report

The report has one line per item, sorted: the kind, the element and a message, separated by tabs.
It records what the converter left out, assumed or did not use, so a line is a question to ask the
modeller, not a failure of the run. One kind, `no-note`, blocks the next step (see its row).
The element is named `Class` for a class or enumeration, `Class.attribute` for an attribute,
`Enum.literal` for a literal and `Source.role -> Target` for a connector (some connector lines stop
at `Source.role`).

----
no-note	Chapter	no note, so no description
not-generated	Vocabulary	stereotype loaded graph, not generated
----

[cols="2,5",options="header"]
|===
|Kind |What it means

|`no-note` |A class, enumeration, attribute, connector or enumeration literal has no note in EA, so the
element has no `description`. The converter writes no placeholder. `rp-generate` requires one and
refuses the schemas without it, so this line blocks step 4: add the note in EA. The kind covers
those elements only: a role object, a state and a transition need no note, and get no line.
|`unspecified-multiplicity` |A connector end has no multiplicity and was read as `0..*`. Write
`1..1`, `0..1` or the one you mean.
|`not-generated` |A class or enumeration with a stereotype of the `--not-generated` list produced
none, or a toolkit class drawn inside the converted package was used as the toolkit's own (`drawn as
the toolkit's Activity, not generated`). A slot that points at a class is a URI; a dependency to such
an enumeration, or an attribute typed by it, makes no slot.
|`excluded-link` |A connector reaches a class in an `--exclude-package` package, so no slot was made.
|`outside-link` |A connector reaches a class outside the converted package that is not excluded; the
slot is a URI.
|`external-list` |An enumeration has no literals, so it stands for a list kept outside the model; a
slot over it is a URI and no enum was written.
|`implicit-meaning` |An enumeration literal written without a prefix took the default prefix.
|`ignored-tag` |A tagged value on a class that no rule uses. The tag name is read exactly, so a
misspelt one (`rp_pth` for `rp_path`) is ignored, and the annotation it meant is not written.
|`ignored-stereotype` |A stereotype on an attribute that no rule uses.
|`toolkit-filled` |An attribute stands for a slot the toolkit fills itself (`started_at_time`) and
asks a bound of it (`[1..1]`). The slot is not written and the bound is not carried over.
|`toolkit-slot-kept` |An attribute stands for a toolkit slot but differs from it in `multivalued` or
in range; the toolkit's definition is kept and the difference is not carried over. A reference
collection's `dct:hasPart` role to another converted class is not reported for its range, which
becomes the collection's member class (xref:reference/uml-conventions.adoc#member-class[conventions page]).
|`merged-cycle` |Packages that refer to each other were written as one module, because separate
modules would import each other, whether the reference is a slot's range, a generalisation or a slot
shared between packages (xref:reference/uml-conventions.adoc#shared-slots[conventions page]). The
line names the packages.
|`role` |A role definition drawn as an Object was written to the roles file:
`<role> at <level>: <actions>` (<<roles-file>>). The level is where the role applies: `system`, `tenant`
or `aggregate`.
|`workflow` |A Statechart diagram was written as a workflow file:
`<n> states, <m> transitions` (<<workflows-file>>). A diagram that no class's `workflow` tag names is
reported too, as `named by no class`: not a failure, as the class may be in an excluded package.
|`derived-iri` |A Statechart diagram is named without a prefix, so the workflow's IRI was made from
`schema_base` and the name: `the IRI <iri> is derived from the diagram name`. Name the diagram with
a prefix (`lib:loan`) to choose the IRI, before the first data is stored.
|`stale-file` |A file of an earlier run is still in `--out` (step 2), or, when the run draws at
least one role, a `*.roles.yaml` other than `<root-name>.roles.yaml`, or, when it draws at least one
workflow, a `workflows/*.workflow.yaml` this run did not write. Also a `.uml-write-*` folder a
killed run left: `left by an interrupted run; delete it`.
|===

[#roles-file]
=== The roles file

When the model draws role definitions (xref:reference/uml-conventions.adoc#roles[conventions page]),
the converter also writes `<root-name>.roles.yaml` beside the schemas; a model that draws none gets
no such file. Hand the file to the service as the access rules, by its path:

[source,python]
----
from pathlib import Path

install_service(..., rules=Path("models/library.roles.yaml"))
----

The full call is in <<serve,step 5>>. `install_service` reads it with `load_role_definitions`. The file is rewritten whole on every run,
so change the roles in EA, never in the file. A file the service cannot read, or that holds an
invalid entry or a key given twice in an entry, stops the start with `InvalidRoleDefinition`, naming
the file and the entry.

[#workflows-file]
=== The workflow files

When the model draws Statechart diagrams (xref:reference/uml-conventions.adoc#workflows[conventions
page]), the converter also writes one `workflows/<name>.workflow.yaml` under `--out` for each; a
model that draws none gets no such file. Hand the files to the service, by their paths:

[source,python]
----
from pathlib import Path

install_service(
    ...,
    rules=Path("models/library.roles.yaml"),
    workflows=[Path("models/workflows/loan.workflow.yaml")],
)
----

The full call is in <<serve,step 5>>. `install_service` reads each with `load_workflow`. The files are rewritten whole on every run, so
change the workflows in EA, never in the files. The converter moves each into `workflows/` without
touching the other files there.

`<name>` is the workflow's name: the local part of the diagram's name, so the diagram `lib:loan`
is written to `workflows/loan.workflow.yaml`. A class's `workflow` tag names that local name
(`loan`), not the prefixed one.

A transition names the roles that may take it, and the converter accepts only roles that a role
definition drawn in the same run defines. Convert the roles and the workflows in one run: give
`--package` a package that holds both the package of the role definitions and the package of the
workflows, their common parent. If your model keeps the roles in a package you leave out with
`--exclude-package` (an access package, say), or outside the `--package` package, a workflow that
names them fails with
`[workflow_transition] <from> -> <to>: roles: <role> is not drawn as a role definition`. Bring that
package into the run, and fix what stops its conversion, before you rely on the workflows. A model
that leaves out the workflows' own package converts as before: a class's `workflow` tag is then
written as it is, unchecked.

[#whole-model]
=== The whole-model check

When the run draws at least one workflow, the converter, before it moves a file, loads the staged
files the way the service loads them at start (the roles file, every workflow file and the root
schema) and runs the service's own check on them. A set the service would refuse stops the run with
exit 1, writes nothing, and names the reason with the files as they would be under `--out`:

----
rp-uml2linkml: the written files would stop the service: <reason>
----

The usual reasons are a class whose `workflow` tag names a diagram that is not drawn in the run
(`class Lonely names workflow 'missing', which no file defines`) and two classes with one class IRI
that name different workflows. Fix the model in EA and run again. A run that draws no workflow does
not run the check.

[#next]
== 4. Check and generate

The converter checks that the model is convertible, not that the result is a valid toolkit model:
whether every part of an aggregate is reachable from its root, whether a class has a description,
and the other rules of `rp-generate` are the generator's checks. In the `pyproject.toml` of your
project, point the `[tool.rp-generate]` entry at the root schema (`schema = "models/library.yaml"`,
a path relative to that file; the keys are in
xref:user-manual/generate.adoc#configure[Configure it]) and run it from that folder:

[source,shell]
----
rp-generate --check
----

It lints and checks the schemas and writes nothing. It reads the schemas only: neither the roles
file nor the workflow files, so a clean check says nothing about them; the service reads them when
it starts (step 5). What it reports is for you to fix in EA, then
convert and check again. When it is clean, run `rp-generate` to write the code and the other
targets. Commit the converted schemas with the UML change that produced them, so that the diff of
the schemas shows what the model change did.

[#serve]
== 5. Start the service

The toy library draws its role definitions in a package `MODEL/library/Access` and the diagram
`lib:loan` in `MODEL/library/Loans`. Step 2 converted them in one run with their common parent,
`MODEL/library`, as `--package`, and wrote into `models/` the root schema `library.yaml`,
`library.roles.yaml` and `workflows/loan.workflow.yaml` (the pages on serving and testing use the
toy library's `review` workflow instead; a workflow file takes the name of its diagram). Once step 4
has generated the package, hand the files to the service by their paths:

[source,python]
----
from pathlib import Path

from rdf_persistence import install_service

from library.domain import generated

kit = install_service(
    app,
    schema=Path("models/library.yaml"),
    generated=generated,
    store=store,
    files=files,
    identity=identity,
    verifier=verifier,
    settings=settings,
    migrations=Path("migrations"),
    rules=Path("models/library.roles.yaml"),
    workflows=[Path("models/workflows/loan.workflow.yaml")],
)
----

`app` is your FastAPI app; `store`, `files`, `identity`, `verifier` and `settings` are the adapters
and settings your composition root builds, and every argument but `app` is passed by keyword.

* `migrations` is the folder of your migration files and of the schema lock `rp-generate` keeps;
  it must exist, or the service refuses to start (`InvalidMigration`). It is the `migrations` key
  of `[tool.rp-generate]`; when that key is set, step 4's `rp-generate` run writes the lock into the
  folder and so creates it. If you do not set the key, make an empty folder yourself.
* `generated` is the package that the `package` key of `[tool.rp-generate]` names (the import
  path, `library.domain.generated` here): import it, as above. `install_service` reads the
  context, the frames and the shapes from that package's folder, and stops with `OSError` when
  they are missing, so generate (step 4) before the service starts.
* A relative path (`Path("models/library.roles.yaml")`) is opened as given, so it is relative to
  the working directory of the process that starts the service, not to the file that holds the
  call. List each workflow file: a folder or a glob is not read. A file that is wrong, missing or
  left over from an older model stops the start; see
  xref:user-manual/serve.adoc#workflows[what a wrong file does].
* `install_service` starts no server: it wires the routes, the problem responses and the start-up
  work into your `app`, and you serve `app` yourself, for example with uvicorn. The adapters, the
  start-up and the routes are in xref:user-manual/serve.adoc[Serve the application].
* The real adapters need Fuseki, Zitadel and an S3 store. For a toy service, pass the testkit's
  in-memory `FakeStore()`, `FakeFileStore()` and `FakeIdentity()` instead
  (xref:user-manual/test.adoc#whole-service[The whole service over the fakes]), and serve `app` as
  in xref:user-manual/serve.adoc#adapters[Serve the application].
* `settings.creator_role` (`"librarian"` in the toy library) must name a role of the roles file:
  the creator of a tenant gets that role, so a name the file does not define gives the creator no
  rights. The settings are in xref:howto/settings.adoc[Configure the deployment values].

== Limits

* The converter reads `.qea` files only, not the XMI export model2owl reads, and writes schemas;
  it does not turn LinkML back into UML.
* A model element that no convention maps stops the run. The converter does not guess; the
  conventions page lists what is accepted.
* An attribute typed `rdf:langString` is refused until the toolkit has a language-string range
  (issue #209).
