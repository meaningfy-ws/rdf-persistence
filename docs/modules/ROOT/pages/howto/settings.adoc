= Configure the toolkit's deployment values
:description: The toolkit's timeouts, caches, limits and event settings as generated groups with defaults, how to pass them from the composition root, how to read them from environment variables, and the replacement of each removed keyword.

_Which values of the toolkit can I tune: the HTTP timeouts, the key cache of the token verifier, the
size limits, the event stream? Where do I set them, and can I read them from the environment?_

The toolkit's deployment values are generated settings models, one group for each concern, with the
value the toolkit always used as the default. Your composition root builds them once and passes
each group to the adapter or service that uses it. If you pass nothing, nothing changes. The models
are generated from `rdf_persistence/model/technical/settings/rp_settings.yaml`, one of the technical
groups of xref:architecture/generation.adoc#kinds[Two kinds of model]. This page describes `develop`
as of 2026-11-17 (the change `technical-models`).

[#groups]
== 1. The groups and their defaults

_What can I set?_

`ToolkitSettings` holds one of each group; `ToolkitSettings()` holds the defaults below. Every
duration is in seconds, at least 0.001 and at most one year (31,536,000; a zero, infinite or larger value is
refused); every count and size is at least 1; the leeway is 0 to 300; the JWKS cooldown is at least 1. If you upgrade from a release that took a keyword for a value, read
<<removed,section 4>> first.

[cols="1,2,1,3",options="header"]
|===
|Group |Slot |Default |What it sets

.3+|`http` (`HttpSettings`)
|`connect_timeout_seconds` |5.0 |The connection timeout of the Fuseki, JWKS, Zitadel and S3 clients
|`read_timeout_seconds` |30.0 |Their read timeout
|`max_attempts` |3 |The S3 client's retry attempts

.4+|`jwks` (`JwksSettings`)
|`ttl_seconds` |600.0 |How long the token verifier keeps the identity provider's keys
|`unknown_kid_cooldown_seconds` |10.0 |The shortest time between two key refreshes. At least 1 second, and not above `ttl_seconds`: `JwksTokenVerifier` refuses a longer cooldown when you build it, because the verifier would refuse every token for the difference
|`allowed_algorithms` |`RS256`, `RS384`, `RS512`, `PS256`, `PS384`, `PS512`, `ES256`, `ES384`, `ES512`, `EdDSA` |The JWS algorithms a token may be signed with. A list of at least one; `none` and every `HS*` name are refused, any other name is accepted here and the verifier checks it against the installed PyJWT when you build it
|`leeway_seconds` |30.0 |The clock drift a token's expiry and not-before times may have

|`directory` (`DirectorySettings`)
|`page_size` |100 |The users the Zitadel adapter reads in one request

.7+|`events` (`EventSettings`)
|`stream` |`rp-events` |The name of the Redis stream
|`retention_seconds` |604800.0 (7 days) |How long the stream keeps entries
|`claim_idle_seconds` |30.0 |How long a failed message waits before it comes again
|`polling_interval_ms` |100 |The consumer's polling interval
|`relay_interval_seconds` |5.0 |How often the relay looks for activities to publish
|`publish_timeout_seconds` |10.0 |How long one publish may take
|`hub_queue_size` |1000 |The events queued for one server-sent-events reader before its connection is closed

.4+|`sse` (`SseSettings`)
|`max_lifetime_seconds` |300.0 |How long one events connection lives
|`access_ttl_seconds` |1.0 |How long the caller's access is trusted before an open connection reads it again
|`keep_alive_seconds` |15.0 |The seconds of silence before a keep-alive comment is sent
|`resume_window_seconds` |604800.0 (7 days) |How far back `Last-Event-ID` resumes

.4+|`limits` (`LimitSettings`)
|`max_messages` |100 |The commands one `handle` call of the message bus runs
|`max_roots` |500 |The roots one commit holds (`CommitTooLarge` above it)
|`max_document_nodes` |10000 |The objects of a JSON-LD body
|`max_manifest_bytes` |65536 |The manifest of a tenant dump a restore reads
|===

`max_body_bytes` and `max_restore_bytes` are not here: they stay in `ServiceSettings`, the settings
you give `install_service` (its arguments are in xref:architecture/api.adoc#serving[Serving it]). The protocol
constants of the identity provider and the store (slugs, header names, paths) are not settings.

[#composition-root]
== 2. Pass them from the composition root

_How do I change a value?_

Build the settings once, where you build the adapters, and give each its group. `fuseki_url`,
`fuseki_user`, `issuer`, `roles_claim` and the other plain arguments below are your own values, as
you already pass them to these constructors:

[source,python]
----
from rdf_persistence import (
    FusekiStore,
    HttpSettings,
    JwksSettings,
    JwksTokenVerifier,
    LimitSettings,
    S3FileStore,
    ToolkitSettings,
    ZitadelIdentity,
)

settings = ToolkitSettings(
    http=HttpSettings(read_timeout_seconds=60),
    jwks=JwksSettings(leeway_seconds=10),
    limits=LimitSettings(max_roots=200),
)

store = FusekiStore(fuseki_url, fuseki_user, fuseki_password, http=settings.http)
verifier = JwksTokenVerifier(issuer, audience, roles_claim, jwks=settings.jwks, http=settings.http)
identity = ZitadelIdentity(
    issuer, service_token, organisation_id, project_id, http=settings.http, directory=settings.directory
)
files = S3FileStore(endpoint, access_key_id, secret_access_key, region, http=settings.http)
----

A group you leave out of `ToolkitSettings(...)` has its defaults, and a slot you leave out of a group
has its default. Each group is validated when you build it: `HttpSettings(read_timeout_seconds=0)`
raises a `ValidationError` naming the slot, and so does `JwksSettings(allowed_algorithms=["HS256"])`.
The settings are values, not shared state: to change one slot of a group you hold, build a new group
with `settings.http.replaced(read_timeout_seconds=60)`.

Then pass the whole object to the service. The kit hands each piece it builds its group (the mapper
its `limits`, the event hub and relay their `events`, the documents their `limits`, the events route
its `sse`):

[source,python]
----
from rdf_persistence import install_service

kit = install_service(
    app,
    # ... the other keyword arguments of step 12 (see below)
    store=store,
    verifier=verifier,
    identity=identity,
    files=files,
    toolkit=settings,
)
----

The other keyword arguments are those of xref:howto/adopt.adoc#serve[step 12 of "Build an
application"].

An adapter you build yourself, and the Redis event bus you hand to `install_service`, take their group
from you. Give them the same objects as the kit:

[cols="2,3",options="header"]
|===
|You build |Group parameter
|`FusekiStore`, `S3FileStore` |`http=`
|`JwksTokenVerifier` |`jwks=` and `http=`
|`ZitadelIdentity` |`http=` and `directory=`
|`RedisEventBus` (`rdf_persistence.adapters.redis_events`) |`events=`
|`Mapper`, `MessageBus`, `bootstrap` (a keyword of its own, beside the handler dependencies), `Documents`, `tenant_dump.restore` |`limits=`
|`EventHub`, `Relay` |`events=`
|`add_events_route` |`sse=`
|`ServiceKit`, `install_service` |`toolkit=` (the whole `ToolkitSettings`)
|===

[source,python]
----
from rdf_persistence.adapters.redis_events import RedisEventBus

bus = RedisEventBus("redis://redis:6379", deployment="library", events=settings.events)
----

[#environment]
== 3. Read them from the environment

_Can the values come from environment variables?_

Yes, when you ask. The toolkit reads no variable on its own, and importing it reads none. Install the
extra, and call `settings_from_env` at the composition root:

[source,shell]
----
uv add 'rdf-persistence[settings]'      # pydantic-settings
----

[source,python]
----
from rdf_persistence import ToolkitSettings, settings_from_env

settings = settings_from_env(ToolkitSettings)
----

A variable is the prefix `RP_`, the group, a double underscore and the slot; the case does not
matter:

[source,shell]
----
export RP_HTTP__READ_TIMEOUT_SECONDS=60
export RP_LIMITS__MAX_ROOTS=200
export RP_JWKS__ALLOWED_ALGORITHMS='["RS256", "ES256"]'    # a list is JSON
----

A variable you do not set leaves the default. `prefix="MYAPP_"` changes the prefix. The function
takes any generated settings model, so `settings_from_env(HttpSettings)` reads `RP_READ_TIMEOUT_SECONDS`.
The values are validated by the model: `RP_HTTP__READ_TIMEOUT_SECONDS=0` or an `HS256` in the list
raises a `ValidationError` naming the field, and nothing is built; the error does not repeat the value you set, so a secret in a variable stays out of logs. A list that is not valid JSON
raises `pydantic_settings.SettingsError` naming the group instead. A typo in the slot, as in
`RP_HTTP__READ_TIMEOUT_SECOND`, raises a `ValidationError` ("Extra inputs are not permitted"). A typo
in the group, as in `RP_HTP__READ_TIMEOUT_SECONDS`, or any other variable with the prefix, as in
`RP_FOO`, is ignored without a message and the default stays: check a value you set with
`print(settings.http)`. Without the extra the call raises
`ImportError`, naming `rdf-persistence[settings]`. No dotenv file and no secrets directory is read;
if you want one, read it yourself and build the settings from its values.

[#removed]
== 4. Moving from the old keywords

_My code passes a keyword that no longer exists._

Every per-value keyword and module constant that a group replaces is gone: there are no two ways to
say one value. A constructor given an old keyword raises `TypeError`; an old constant raises
`ImportError`. `bootstrap` takes handler dependencies by keyword, so `bootstrap(limit=...)` raises
`ValueError` ("no handler or observer names the dependency limit"), unless a handler declares a
dependency `limit`. The values are the defaults of the groups, so a call that passed the old default
needs no replacement.

The slots of the groups are numbers of seconds (`float`). Five old keywords took a `timedelta`:
`retention`, `claim_idle`, `access_ttl`, `resume_window` and `max_lifetime`. Convert them; a
`timedelta` is refused, and `retention=timedelta(days=7)` becomes:

[source,python]
----
from datetime import timedelta

EventSettings(retention_seconds=timedelta(days=7).total_seconds())
----

The other old duration keywords (`interval`, `publish_timeout`, `keep_alive`) were already seconds.

[cols="3,3",options="header"]
|===
|Removed |Replacement
|`JwksTokenVerifier(algorithms=, leeway_seconds=)` |`jwks=JwksSettings(allowed_algorithms=, leeway_seconds=)`
|`RedisEventBus(stream=, retention=, claim_idle=)` |`events=EventSettings(stream=, retention_seconds=, claim_idle_seconds=)`
|`Relay(interval=, publish_timeout=)` |`events=EventSettings(relay_interval_seconds=, publish_timeout_seconds=)`
|`EventHub(max_queue=)` |`events=EventSettings(hub_queue_size=)`
|`MessageBus(limit=)`, `bootstrap(limit=)` |`limits=LimitSettings(max_messages=)`
|`Mapper(max_roots=)`, `UnitOfWork(max_roots=)` |`Mapper(..., limits=LimitSettings(max_roots=))`; a `UnitOfWork` reads its mapper's limit and takes none
|`add_events_route(access_ttl=, keep_alive=, resume_window=, max_lifetime=)` |`sse=SseSettings(access_ttl_seconds=, keep_alive_seconds=, resume_window_seconds=, max_lifetime_seconds=)`
|The timeouts of `FusekiStore`, `JwksTokenVerifier`, `ZitadelIdentity` and `S3FileStore` (fixed before) |`http=HttpSettings(connect_timeout_seconds=, read_timeout_seconds=, max_attempts=)`
|The page size of `ZitadelIdentity` (fixed before) |`directory=DirectorySettings(page_size=)`
|The node limit of `Documents`, the manifest cap of `tenant_dump.restore` (fixed before) |`limits=LimitSettings(max_document_nodes=, max_manifest_bytes=)`
|`CONNECT_TIMEOUT_SECONDS`, `READ_TIMEOUT_SECONDS` (`adapters/_http.py`, `adapters/s3.py`), `MAX_ATTEMPTS` (`adapters/s3.py`) |`HttpSettings.connect_timeout_seconds`, `read_timeout_seconds`, `max_attempts`
|`JWKS_TTL_SECONDS`, `UNKNOWN_KID_COOLDOWN_SECONDS`, `DEFAULT_ALGORITHMS`, `DEFAULT_LEEWAY_SECONDS`, `MAX_LEEWAY_SECONDS` (`adapters/jwks.py`) |`JwksSettings.ttl_seconds`, `unknown_kid_cooldown_seconds`, `allowed_algorithms`, `leeway_seconds` (its bounds are the model's, 0 to 300)
|`POLLING_INTERVAL_MS` (`adapters/redis_events.py`) |`EventSettings.polling_interval_ms`
|`PAGE_SIZE` (`adapters/zitadel.py`) |`DirectorySettings.page_size`
|`ACTIVE_STATE`, `INACTIVE_STATE` (`adapters/zitadel.py`) |none for a consumer: the adapter compares the answer with the enum `ZitadelUserState` (`USER_STATE_ACTIVE`, `USER_STATE_INACTIVE`, and four more), in `rdf_persistence.adapters.generated.rp_wire`. An answer with a state outside the six is unreadable (`IdentityUnavailable`)
|`MAX_LIFETIME`, `ACCESS_TTL`, `KEEP_ALIVE_SECONDS`, `RESUME_WINDOW` (`entrypoints/sse.py`) |`SseSettings.max_lifetime_seconds`, `access_ttl_seconds`, `keep_alive_seconds`, `resume_window_seconds`
|`MAX_NODES` (`services/documents.py`) |`LimitSettings.max_document_nodes`
|`DEFAULT_MAX_ROOTS` (`services/mapper.py`) |`LimitSettings.max_roots`
|`MAX_MANIFEST_BYTES` (`services/tenant_dump.py`) |`LimitSettings.max_manifest_bytes`
|`PROJECTS`, `MACHINE_USERS`, `OWN_ORGANISATION`, `TOKEN_PATH` (`rdf_persistence.adapters.zitadel`) |the same names in `rdf_persistence.testkit.zitadel`; only the testkit used them
|===

Modules moved with it: the IRI and tenant-move modules, and the generated service records, left the
domain layer for `rdf_persistence.services`. `CHANGELOG.md` lists each old path with its new one.
Every name still imports from `rdf_persistence`, so only a deep import breaks.
