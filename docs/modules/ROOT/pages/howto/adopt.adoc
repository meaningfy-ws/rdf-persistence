= Build an application with rdf-persistence
:description: How an application adopts rdf-persistence: write its model in LinkML, generate its code, use the generated classes and guard them in its tests.

Status: *complete* (2026-11-06). Steps 1 to 7 cover modelling, generation, the generated classes and
the test guards; steps 8 to 13 cover the session, tenancy, files, access, the service and its tests
(stages 1 to 5 of the change `toolkit-v1-foundation`); step 14 covers the IRI policy. Every example
is modelled on the toy library of the toolkit's repository: `tests/fixtures/library/` (the model),
`tests/e2e/library_app.py` (the composition root) and `tests/toy_service.py` (the same service over
the fakes). Short answers to the usual questions, with links back here, are on
xref:questions.adoc[Common questions].

You write your domain once, as a LinkML schema. `rp-generate` turns it into Python classes, SHACL
shapes, a JSON-LD context and frames, TypeScript types and Mermaid diagrams. Your code works with
the generated classes, and the testkit fails your tests if anyone edits generated code or writes a
model by hand. The reasons behind this are in xref:architecture/generation.adoc[Model to code].

[#install]
== 1. Install

_How do I start an application?_

rdf-persistence is installed from its `develop` branch. The generators are needed at build time
only, so they go in the dev group, together with the test helpers:

[source,toml]
----
# pyproject.toml
[project]
name = "library"
version = "0.1.0"
dependencies = ["rdf-persistence"]

[dependency-groups]
dev = ["rdf-persistence[generate,testkit]", "hypothesis", "pytest"]

[tool.uv.sources]
rdf-persistence = { git = "https://github.com/meaningfy-ws/rdf-persistence", branch = "develop" }
----

Run `uv sync`. The `rp-generate` command is always installed. Without the `generate` extra, generating
exits with code 2 and says so, and `rp-generate --check` only compares the manifest (step 6).

== 2. Lay out the application

_Where do the model and the generated files go?_

[source,text]
----
models/                       the LinkML schema: a root schema and one file per module
library/domain/generated/     generated Python, shapes, context and frames (never edited)
library/services/             your domain services (step 8)
library/entrypoints/          your composition root and routes (step 12)
web/src/domain/generated/     generated TypeScript types (never edited)
docs/model/                   generated diagrams, one per module
tests/
----

Generated files go only in folders named `generated`, except the diagrams, which the file guard
(<<guard>>) does not look at. It fails on shapes, contexts, frames, JSON schemas, OpenAPI files or
`.ts` files (other than `*.test.ts` and `*.spec.ts`) found elsewhere in the folders you give it
(step 6).

[#model]
== 3. Write the model

_How do I model my domain?_

Split the schema into one file per module and a root schema that imports them. A *domain module*
holds one aggregate: its root class and the classes the root owns.

[source,yaml]
----
# models/books.yaml
id: https://example.org/ns/library/books
name: books
title: Books module
description: Books and their chapters; the book is the aggregate root.
prefixes:
  lib: https://example.org/ns/library#
  linkml: https://w3id.org/linkml/
  dcterms: http://purl.org/dc/terms/
default_prefix: lib
default_range: string
imports:
  - linkml:types
  - rdf_persistence/model/rp_core           # the toolkit's metamodel, resolved from the package
  - rdf_persistence/model/rp_annotations
annotations:
  module_kind: domain
classes:
  Book:
    title: Book
    description: A book held by a library; an aggregate root that owns its chapters.
    mixins: [AggregateRoot, Described, Tracked]
    slots: [author, chapters]
    annotations:
      rp_path: books                         # its path segment in the API
  Chapter:
    title: Chapter
    description: A chapter of a book; part of the book's aggregate.
    mixins: [Described]
    slots: [number]
    annotations:
      rp_unlabelled: true                    # known by its number, needs no label
slots:
  author:
    title: Author
    description: The author's name.
    slot_uri: dcterms:creator
  number:
    title: Chapter number
    description: The position of a chapter in its book.
    range: integer
    required: true
  chapters:
    title: Chapters
    description: The book's chapters; they live in the book's graph.
    range: Chapter
    multivalued: true
    inlined_as_list: true
    annotations:
      owned: true
----

`rp_path` names the class's collection in the API (`/libraries/{t}/books`) and nothing else: by
default it is also a word in the aggregate's IRI, but a custom IRI policy (<<iri-policy>>) may
leave it out. The word that stands for the class in an IRI is `{type}`, which is the class's
`rp_iri_type` annotation, or the class name in kebab case when there is none. Set it under
`annotations:`, like `rp_path`, on an aggregate root or an owned class, only when the IRIs must say
something other than the class name:

[source,yaml]
----
    annotations:
      rp_path: books
      rp_iri_type: volume                    # {type} is "volume", not "book"
----

It follows the same pattern as `rp_path`: a url segment of lower case letters, digits and hyphens.
Two classes may not share one, and `content`, `graph`, `parts`, `access`, `meta` and `registry` are
reserved by the IRI layout, so `rp-generate` refuses them. The toolkit's routes read `rp_iri_type`;
`new_part` does not (step 8).

[source,yaml]
----
# models/library.yaml — the root schema
id: https://example.org/ns/library
name: library
title: Library
description: The root schema of a library application.
prefixes:
  lib: https://example.org/ns/library#
  linkml: https://w3id.org/linkml/
default_prefix: lib
default_range: string
imports:
  - linkml:types
  - books
----

`rp-generate` refuses a schema that breaks these rules, and names the element at fault:

[cols="2,3",options="header"]
|===
|Rule |In the example
|Every class, slot, enum and permissible value has a `title` and a `description`, and every element an IRI (a `default_prefix`, or an explicit `class_uri` or `slot_uri`) |`title:` and `description:` everywhere; `default_prefix: lib`
|Every permissible value has a `meaning`, an IRI |(no enum here; see `Genre` in the toy library)
|An aggregate root includes `AggregateRoot` and `Described` and has an `rp_path` |`Book`
|Every other class is owned by a root, through a slot annotated `owned: true`, and includes `Described`; one without a label of its own says `rp_unlabelled: true` |`Chapter`, through `chapters`
|A slot that is not owned and ranges over a class points to an aggregate root; it is stored as that root's IRI |(see `scan_of` in the toy library)
|A module annotated `module_kind: domain` imports no module annotated `technical` or `access` |`books.yaml`
|No LinkML `rules`, `all_of` or `none_of`: the generated code would not enforce them |—
|===

More of the metamodel, each shown in the toy library under `tests/fixtures/library/` of the
toolkit's repository:

* *the tenant root*: one class annotated `graph: meta`, whose instance is the tenant itself
  (`library_tenant.yaml`);
* *a stored file*: a root that includes `StoredFile` (`scans.yaml`);
* *access*: a class with `is_a: TenantAccess`, in a module annotated `module_kind: access`
  (`library_access.yaml`), and the role definitions (`library_roles.yaml`).
* *technical*: a module annotated `module_kind: technical` may hold the request and response shapes
  of your own routes. Its classes need no owning root; they are generated in Python and TypeScript
  but never stored. A domain module may not import it; the root schema imports it.

The full list of annotations and mixins is in
xref:architecture/generation.adoc#metamodel[the metamodel].

== 4. Generate

_How do I turn the model into code?_

Declare where each artefact goes:

[source,toml]
----
# pyproject.toml
[tool.rp-generate]
schema = "models/library.yaml"
package = "library.domain.generated"
typescript = "web/src/domain/generated"
diagrams = "docs/model"
regenerate-command = "make generate"  # optional
----

Two keys are required: `schema` (the root LinkML file) and `package` (the Python import path of the
generated package). Without one, `rp-generate` exits with code 2 and names the missing key. The
others are optional:

* `typescript` and `diagrams` are folders; nothing is written when they are absent.
* `python` is the folder that receives every file listed below except the TypeScript and the
  diagrams. Set it only when that folder is not the `package` path, for example
  `python = "src/library/domain/generated"`; `package` stays the import path.
* `openapi = false` leaves out `openapi-components.json`. That is safe only if you never call
  `install_service` (step 12): it stops with `OSError` when the file is missing.

`rp-generate` reads the `pyproject.toml` in the folder you run it from. It does not search upward:
from another folder it exits with code 2, unless you pass `--project path/to/pyproject.toml`.
Every path in `[tool.rp-generate]` is relative to that file, not to the folder you run the command
from, and it must stay inside its folder: an absolute path or one with `..` is refused. The Python folder is
the `package` path with the dots turned into slashes (`library/domain/generated`). It does not have
to exist: `rp-generate` creates it, and its parent folders, and writes an `__init__.py` into it
only. `library/` and `library/domain/` get none; Python imports them as namespace packages, so add
your own `__init__.py` only if a tool needs it.

`rp-generate` prints `rp-generate: generated 1 target(s), no problems` and exits 0 when it is done.
It exits 1 when it finds problems: a schema that breaks a rule of step 3 (the message names the
element), or a missing or unreadable `schema` file. It exits 2 when it cannot start: a missing or
unknown key, a refused path, no `[tool.rp-generate]` entry, or, when generating, no `generate` extra.

Add a make target that runs `uv run rp-generate`; it may have any name, and it may be the target
that already runs your other generators. Set the optional `regenerate-command` to the command you
type to run that target, as in the example above: `make generate`. It is only shown, never run: when
generated code is stale, the freshness check (<<guard,step 6>>) ends with "run `make generate` to
regenerate, then commit the result". Without it, the check names `rp-generate`, which skips
`uv run` and anything else your target does. The make target on this page is called `generate`:

[source,makefile]
----
generate:
	uv run rp-generate
----

Run it: it prints `rp-generate: generated 1 target(s), no problems`.

The freshness check is `uv run rp-generate --check`. It writes nothing. On success it prints
`rp-generate: checked 1 target(s), no problems` and exits 0. Before the first generation it exits 1
with `no readable manifest: library/domain/generated/rp-manifest.json`. <<guard,Step 6>> says how to
run it in your tests and in CI.

Your regenerate target writes, under `library/domain/generated/`, one Python module per schema module
(`books.py`, `library.py`), `shapes.ttl`, `context.jsonld`, one `<Root>.frame.jsonld` per
aggregate root, `openapi-components.json` (the component schemas of the service's OpenAPI document)
and `rp-manifest.json`; the TypeScript types, one file per module plus `index.ts`, and
`rp_service.ts`, which holds the classes of the toolkit's `rp_service.yaml`, among them the API's wire
types (`TenantCreate`, `TenantSummary`, `LabelUpdate`, `GrantSet`, `Page` and `Problem`); and one
`.mmd` diagram per module. The module name `rp_service` and the names of the classes and enums of
`rp_service.yaml` are reserved when a target renders TypeScript: a schema that uses one is refused,
naming the clash. Commit them together with the schema. Never edit them: to change
the code, change the schema and generate again.

A file an earlier run wrote and this one does not, such as the module of a schema file you removed
or renamed, is deleted by the next run, unless it was edited since: then the run keeps it and says
`kept <file>: it changed since it was generated; delete it if it is stale`. Before you regenerate,
`--check` reports the removed schema file as `stale input: models/<file>.yaml (removed)`.

== 5. Use the generated classes

_What do the generated classes check?_

[source,python]
----
from pydantic import ValidationError

from library.domain.generated.books import Book, Chapter

book = Book(
    id="https://example.org/library/books/1",
    label="Dune",
    description="A science-fiction novel.",
    author="Frank Herbert",
    chapters=[Chapter(id="https://example.org/library/books/1/chapters/1", number=1)],
)

Book(id="https://example.org/library/books/2", label="No description")  # valid: a description is optional

book.chapters[0].number = "one"
# ValidationError: number: Input should be a valid integer (checked on assignment too)

Book(id="https://example.org/library/books/3", label="L", description="D", isbn="1")
# ValidationError: isbn: Extra inputs are not permitted
----

The fields come from the schema. `author` and `chapters` are in `books.yaml`. The `Described`
mixin adds `id`, `label` and `description`: `id` and `label` are required, `description` is optional
everywhere, an aggregate root included; a class annotated `rp_unlabelled: true` (`Chapter`) needs no `label`. The
`Tracked` mixin adds `created`, `modified`, `creator` and `contributor`: the session sets them
(step 8), never you. `AggregateRoot` adds no field; it marks the class as a root.

The class takes any text as an `id`, so the ids above show the checks, not what you can store: the
session refuses an aggregate IRI the toolkit would not mint (step 8), such as
`https://example.org/library/books/1`. Mint one with `kit.iris.mint_aggregate` (the kit comes in
step 12; outside a service, step 14 builds an `Iris`).

Every generated class derives from the toolkit's strict base, `RpModel`. It refuses unknown
fields, validates on assignment, and enforces the rules declared in the schema: `required`,
ranges, patterns, `exactly_one_of`, `any_of` and `unique_keys`. Each object, owned parts included,
has a required `id`: `Chapter(number=1)` fails with `id: Field required`. Only a request body to
the service may leave a part's `id` out. The service then mints its IRI, by default
`{root_iri}/parts/{uuid4}`, and keeps it across commits. Under a custom IRI policy the part template
decides. A JSON body's parts are typed by the schema's context, so nothing more is needed; a
JSON-LD body must give each part's `@type`, and when the part template has `{type}` an untyped part,
or one whose class is not owned, is a 422. In a domain service, build a part with `new_part`
(<<session>>). The metamodel's classes (`AggregateRoot`, `Described`, `Grant`, …) are imported
from `rdf_persistence`, never generated into your package.

Use the generated classes in your domain services. Do not declare models of your own: no
`BaseModel`, enum, dataclass, `TypedDict` or `NamedTuple` in `library/domain`, `library/services`
or `library/entrypoints`, outside `generated` (<<guard,step 6>> checks this). A model you need goes into the schema.

[#guard]
== 6. Guard the model in your tests

_How do I keep the model and the code from drifting apart?_

The testkit adds five checks to your test suite.

*Freshness.* Stop the test session if generated code is stale or was edited by hand:

[source,python]
----
# tests/conftest.py
pytest_plugins = ["rdf_persistence.testkit.freshness"]
----

At the start of every test run the plugin reads the `[tool.rp-generate]` entries of the
`pyproject.toml` in pytest's rootdir. For other files, list them one per line, relative to the
rootdir, in the pytest option `rp_generate_projects`. It compares the files with the hashes in each
`rp-manifest.json`; it regenerates nothing and needs no `generate` extra. When something is stale,
edited or missing, pytest stops before any test, with exit code 1:

[source,text]
----
generated code is not fresh:
pyproject.toml: edited by hand: library/domain/generated/books.py
run `make generate` to regenerate, then commit the result
----

*No hand-written models or artefacts*, *classes and shapes agree*, and *a round trip through
RDF*:

[source,python]
----
# tests/test_model.py
from pathlib import Path

from hypothesis import given, settings
from hypothesis import strategies as st

from rdf_persistence.testkit import (
    Conformance, aggregate, assert_models_generated, conformance_problems, round_trip,
)

ROOT = Path(__file__).parents[1]
SCHEMA = ROOT / "models" / "library.yaml"


def test_no_hand_written_models():
    assert_models_generated(ROOT / "library", roots=[ROOT / "library", ROOT / "tests"])


def test_classes_and_shapes_agree():
    assert conformance_problems(SCHEMA, ROOT / "tests" / "conformance" / "cases.yaml") == []


@settings(max_examples=25, deadline=None)
@given(data=st.data())
def test_a_book_survives_the_round_trip(data):
    conformed = Conformance.of(SCHEMA)
    round_trip(conformed, data.draw(aggregate(conformed, "Book")), "Book")
----

`assert_models_generated` makes two checks. It fails on a hand-written model, found in the
`domain`, `services` and `entrypoints` folders of the package you pass first (`ROOT / "library"`),
and names its file, line and class. It also fails on a generated artefact outside a `generated`
folder (step 2), found in the `roots` folders: shapes, contexts, frames, JSON schemas, OpenAPI files
and `.ts` files other than `*.test.ts` and `*.spec.ts`. `web/` is not in `roots` because a web
application holds hand-written `.ts` files; you may add any folder that holds no
hand-written `.ts` files. If you really need a type
that holds a foreign run-time object, pass it with `allow=["library/domain/<file>.py:<ClassName>"]`,
a path relative to the folder that holds the package (`ROOT` above).

`conformance_problems(SCHEMA, cases)` finds the generated classes and shapes by itself. It looks up the
folders above the schema file for a `pyproject.toml` whose `[tool.rp-generate]` entry has this
`schema` (`LookupError` if there is none), imports that entry's `package`, so it must be importable
in your tests (see below), and reads the shapes and the context from the Python folder. It returns a list of
problems, as text; the list is empty when every case passes. `Conformance.of(SCHEMA)` opens the same
classes and shapes as one object, which `aggregate` and `round_trip` take.

Nothing puts your project folder on the import path, and `library/` needs no `__init__.py`
(namespace package), so tell pytest where to find it:

[source,toml]
----
# pyproject.toml
[tool.pytest.ini_options]
pythonpath = ["."]
----

Without it the two tests that import the package fail with `ModuleNotFoundError: No module named
'library'`.

`conformance_problems` checks each case against both the generated class and the generated shape: the
valid instances must pass both, and the invalid ones must fail both. It also reports any
constraint kind your schema uses that no case covers, so the test fails until every kind has one.
A case names a kind, a class and instance files, whose paths are relative to the cases file. The example
schema uses four kinds:

[source,yaml]
----
# tests/conformance/cases.yaml
- kind: required
  class_name: Chapter
  valid: [instances/chapter-ok.yaml]
  invalid: [instances/chapter-no-number.yaml]
- kind: range_type
  class_name: Chapter
  valid: [instances/chapter-ok.yaml]
  invalid: [instances/chapter-number-text.yaml]
- kind: identifier
  class_name: Book
  valid: [instances/book-ok.yaml]
  invalid: [instances/book-no-id.yaml]
- kind: closed
  class_name: Book
  valid: [instances/book-ok.yaml]
  invalid: [instances/book-unknown-field.yaml]
----

Each instance is a small YAML object, for example:

[source,yaml]
----
# tests/conformance/instances/chapter-no-number.yaml
id: https://example.org/library/books/1/chapters/1
----

The others: `chapter-ok.yaml` adds `number: 1`, `chapter-number-text.yaml` has `number: one`,
`book-ok.yaml` has an `id`, a `label` and a `description`, `book-no-id.yaml` lacks the `id`, and
`book-unknown-field.yaml` adds a slot the class does not have (`isbn: "1"`).

`round_trip` takes an object, turns it into RDF, frames the RDF back into JSON and builds an object
from it. It fails with an `AssertionError`, `the objects differ after the round trip` or `the two
graphs differ` with the triples on each side, when the object that comes back is not equal to the
one that went in. `aggregate(conformed, "Book")` draws random valid books for it.

Each kind of constraint comes from one construct of the schema:

[cols="2,3",options="header"]
|===
|Kind |The schema construct
|`required` |a slot with `required: true`
|`cardinality` |`minimum_cardinality` or `maximum_cardinality` on a slot
|`range_type` |a slot whose range is a type (`string`, `integer`, …)
|`range_enum` |a slot whose range is an enum
|`pattern` |`pattern` on a slot
|`value_bounds` |`minimum_value` or `maximum_value` on a slot
|`identifier` |a slot with `identifier: true`
|`closed` |every schema with generated classes: they refuse unknown fields
|`exactly_one_of`, `any_of` |the keys of the same name on a class
|`unique_keys` |`unique_keys` on a class, or a keyed slot
|===

Where each check runs:

* *Tests:* the freshness plugin, which compares the manifest.
* *CI and pre-commit:* `uv run rp-generate --check` (step 4). It writes nothing and exits 1 when
  generated code is stale or was edited, and names the files. It makes the same comparison as the
  plugin and also lints the schema and runs its rule checks, which the plugin does not, so keep it
  in CI even when the tests run the plugin. The lint and rule checks need the `generate` extra (step
  1: `uv sync` installs it); without it the command compares the manifest only. A pre-commit hook for it:
+
[source,yaml]
----
# .pre-commit-config.yaml
repos:
  - repo: local
    hooks:
      - id: rp-generate-check
        name: rp-generate --check
        entry: uv run rp-generate --check
        language: system
        pass_filenames: false
        files: ^(models/|.*/generated/)
----

*The model's shape changes only on purpose.* The last reviewed shape of every class lives in a file
you commit; a model change fails this test until you refresh the file and review its diff:

[source,python]
----
# tests/test_model.py (continued)
import json
import os

from rdf_persistence.testkit import (
    Conformance, class_shapes, model_schema_diff, model_shape_diff, read_snapshot, snapshot_diff,
    write_snapshot,
)

SNAPSHOT = ROOT / "tests" / "model-shape.yaml"
COMPONENTS = ROOT / "domain" / "generated" / "openapi-components.json"


def test_the_model_shape_is_the_reviewed_one():
    current = class_shapes([SCHEMA])
    if os.environ.get("REFRESH_SNAPSHOT"):  # set it once after a deliberate change
        write_snapshot(SNAPSHOT, current)
    assert snapshot_diff(read_snapshot(SNAPSHOT), current) == []


def test_the_generated_classes_follow_the_schema():
    models = {m.__name__: m for m in Conformance.of(SCHEMA).models.values()}
    # the schema's own classes; those it imports from the toolkit are the toolkit's to check
    shapes = [s for s in class_shapes([SCHEMA]) if s.class_name in models]
    assert model_shape_diff(shapes, models.values()) == []


def test_python_and_json_schema_agree_on_what_is_required():
    components = json.loads(COMPONENTS.read_text())["schemas"]
    assert model_schema_diff(components, Conformance.of(SCHEMA).models.values()) == []
----

Refresh it with `REFRESH_SNAPSHOT=1 uv run pytest tests/test_model.py`, then review the diff of
`tests/model-shape.yaml` in your pull request. The second test compares each generated class with
the schema's induced slots, so stale or edited code fails even before the snapshot does. The third
compares each class's required fields with the `required` list of its JSON Schema in
`openapi-components.json`, so the Python and the API document cannot disagree on a required field.

== 7. Change the model

_How do I change the model later?_

. Edit the schema.
. Run your regenerate target.
. Add or adjust conformance cases if you used a new constraint kind; `conformance_problems` names any
  kind that has no case.
. Run the tests, then commit the schema and the generated code together.

When you remove or rename a schema module, the next run deletes the generated files of the old one
(step 4); you delete nothing by hand, unless that file was edited (step 4: the run keeps it).

The toolkit has no migration of stored data: it reads and writes the graphs as the model now
describes them. A stored aggregate that lacks a slot you made `required` fails to read with a
`ValidationError`; triples of a removed or renamed slot are ignored on read and dropped when the
aggregate is next committed. The service loads the model at start-up, so restart it to serve the
new one (step 12).

To upgrade rdf-persistence, which is installed from a git branch (step 1), run
`uv lock --upgrade-package rdf-persistence` and `uv sync`. Then, until you regenerate, the freshness
plugin and `rp-generate --check` fail with `stale input: rdf_persistence/...`, because the
manifest records the generator files it was made with, and with `stale: generated with linkml ...`
if the `linkml` version changed. Run your regenerate target and review the generated diff: a new
toolkit version can change the generated code.

[#session]
== 8. Store and read aggregates in a domain service

_How do I store and read an aggregate?_

Over HTTP the router stores and reads every aggregate for you (<<serve>>). Write code only for
rules that are more than CRUD, such as a check across two objects or a computed value. That code
works on the generated classes through a *session* and a *unit of work*:

* a `Session` reads and commits whole graphs of one tenant database, on behalf of one principal;
* a `Mapper` turns a generated object and its owned parts into triples and back;
* a `UnitOfWork(session, mapper)` gives object-level access: `get` a root, `add` a new or changed
  one, `commit`.

[source,python]
----
# library/services/books.py
from rdf_persistence import (
    Mapper,
    ServiceKit,
    UnitOfWork,
    generated_models,
    new_part,
)

from library.domain.generated import books
from library.domain.generated.books import Book, Chapter


def book_mapper(kit: ServiceKit) -> Mapper:
    """Build it once: it reads the schema the kit loaded."""
    return Mapper(kit.view, generated_models(books))


async def add_book(kit: ServiceKit, mapper: Mapper, tenant: str, principal: str) -> str:
    iri = str(kit.iris.mint_aggregate(tenant, "book", "books"))  # by the IRI policy (step 14)
    async with kit.session(tenant, principal) as session:
        work = UnitOfWork(session, mapper)
        work.add(Book(id=iri, label="Dune", description="A planet.", author="Frank Herbert"))
        await work.commit()
    return iri


async def add_chapter(
    kit: ServiceKit, mapper: Mapper, tenant: str, principal: str, book_iri: str, number: int
) -> None:
    async with kit.session(tenant, principal) as session:
        work = UnitOfWork(session, mapper)
        book = await work.get(Book, book_iri)       # NotFound if the book has no graph
        part = new_part(Chapter, book_iri, iris=kit.iris, tenant=tenant, number=number)
        book.chapters = [*(book.chapters or []), part]
        work.add(book)
        await work.commit()                          # Conflict if the book changed meanwhile
----

`tenant` is the tenant's IRI and `principal` the caller's IRI (<<access>> shows where both come
from). `kit.session(tenant, principal)` opens a session on that tenant's database; `kit.view` is
the schema the service loaded; outside a service, `load_schema(path)` loads one. Pass `generated_models` every module whose classes the mapper reads:
the roots you `get` and the parts they own.

What a commit does:

* A new root is written with `Session.add_graph`; a root read in this unit of work, with
  `Session.replace_graph` and the version it was read with. Each commit sends one SPARQL update
  of several `;`-joined operations, guarded by that version, then an `ASK` for the new version. A
  version that moved meanwhile raises `Conflict` and changes nothing.
* Each aggregate is committed on its own. With two changed roots, a conflict on the second leaves
  the first committed.
* The session writes the version and the tracking slots (`created`, `creator`, `modified`,
  `contributor`) as statements about the aggregate's graph, `{root}/graph`. Your code never sets
  them.
* An aggregate IRI must be one the toolkit would mint, by default `{tenant}/{rp_path}/{uuid4}`; a
  custom IRI policy may use the class's `{type}` instead of `{rp_path}`. Any other is refused
  (`InvalidIri`) before anything is sent. `kit.iris.mint_aggregate(tenant, type, rp_path)` mints one
  by the service's policy, `type` being the class's `{type}` (step 3). The module function
  `mint_aggregate_iri(tenant, rp_path)` mints the default layout only, which a custom policy
  refuses.
* A part's IRI is, by default, `{root}/parts/{uuid4}`. `new_part(Chapter, root, iris=kit.iris,
  tenant=tenant, ...)` mints it by the policy, and it stays the same across commits. Without `iris`
  it mints the default layout only, which a custom policy refuses. Its `{type}` is the kebab-case
  class name, not `rp_iri_type`, so under a part template with `{type}` a class that sets another
  `rp_iri_type` is refused (`InvalidIri`).

The session also works below the object level, on triples. Use it for what the mapper does not
cover:

[cols="2,3",options="header"]
|===
|`Session` method |What it does
|`get_graph(iri)` |The aggregate's triples, its graph IRI and its version token
|`add_graph(iri, triples, loaded_graphs=())` |Store a new aggregate; returns its first version
|`replace_graph(iri, triples, if_version, loaded_graphs=None)` |Replace it if it still has `if_version`; returns the new version
|`load_graph(iri, data, *, rdf_format)` |Parse an RDF file into a new graph of the aggregate (<<files>>)
|`remove(iri, if_version)` |Delete the aggregate, its loaded graphs and its registry entries
|===

Outside a service, `open_session(store, *, database, tenant_iri, principal, clock)` opens the
same session (`principal` is a `Principal`; the kit's `session` takes its IRI as a string) on a `Store` you hold. The kit's `session` calls it with the tenant's database name.

[#tenancy]
== 9. Create tenants

_How do tenants work?_

Each tenant has its own database and its own bucket. The system database holds one *access record*
per tenant: its label, state, database name, grants and prohibitions. Your schema names two
classes for this, as the toy library does:

[source,yaml]
----
# models/library_tenant.yaml (module_kind: domain): the tenant root, kept in the tenant's meta graph
classes:
  Library:
    title: Library
    description: A library; the tenant root.
    class_uri: schema:Library
    mixins: [Described, Tracked]
    slots: [city]
    annotations:
      graph: meta
      database: tenant
----

[source,yaml]
----
# models/library_access.yaml (module_kind: access): the access record
classes:
  LibraryAccess:
    title: Library access
    description: The access record of a library tenant; its grants are the metamodel's.
    class_uri: lib:LibraryAccess
    is_a: TenantAccess
----

A client creates a tenant with `POST /{tenant_segment}`. The body is a `TenantCreate`: the label,
and in `root` the slots of the tenant's root object:

[source,json]
----
{"label": "Ghent", "root": {"description": "Books for all.", "city": "Ghent"}}
----

The root's `label` is the tenant's: leave it out of `root`, or give the same one; another label is refused with 422.

The answer is 201 with a `TenantSummary` (`id`, `label`, `state`) and a `Location`. In code, the
same call is `kit.tenancy.create(label, root_slots, creator)`:

[source,python]
----
from rdf_persistence import Principal

summary = await kit.tenancy.create(
    "Ghent", {"description": "Books for all.", "city": "Ghent"}, Principal(id=principal)
)
----

What create does, in order:

. It mints the tenant IRI by the IRI policy (by default `{base}{tenant_segment}/{uuid4}`), drawing
  again, at most five times under any policy, when the id's access record or database already
  exists (otherwise `PersistenceError`, "no free tenant id"), and builds and validates both
  objects. A root that names an `id` or sets an `internal` slot is refused (422), and so is an
  invalid label. A refused request creates nothing.
. It creates the tenant's database and bucket, both named `{prefix}-t-{tenant id}` (the id without
  hyphens: for a UUID, its hex).
. It stores the root object in the tenant's meta graph.
. Last, it writes the access record, `active`, with one grant: the creator holds the settings'
  `creator_role` on the tenant.

A crash part way leaves a database or a bucket that no record names. The start-up sweep drops it.

*Delete* is `DELETE /{tenant_segment}/{t}` with `If-Match`. It needs `administer` on the tenant.
The version is the access record's: the `Record-ETag` of `GET /{tenant_segment}/{t}`, the `ETag`
of `GET …/grants`, or of the last `PUT …/grants` or `PUT …/label`. The tenant is marked `deleting`,
so from then on it answers 404. Then its database and bucket are dropped and its record is removed.
The sweep at the next start-up finishes a deletion that a crash interrupted.

`PUT …/label` renames the tenant; it needs `modify`. It writes the label to the root object and to
the access record, so both always read the same. Its `If-Match` is the record's version: any reader
finds it in the `Record-ETag` header of `GET /{tenant_segment}/{t}`, beside the root's own `ETag`.
For example, `GET /libraries/t` answers `ETag: "r7"` and `Record-ETag: "v2"`; then
`PUT /libraries/t/label` with `If-Match: "v2"` renames, and with an older version it answers 409.

The same read, and the read of any aggregate, also answers `Allowed-Actions`: the actions the caller
may take there, comma separated, in the order `read`, `modify`, `delete`, `administer`, for example
`Allowed-Actions: read, modify`. On a tenant, `delete` means you may delete the tenant, which needs
`administer`; on an aggregate there is no `administer`. Each item of `GET /{tenant_segment}` carries
the same list as `allowed_actions`. Show a button only when its action is listed; the server still
checks every write.

`GET` and `PUT /{tenant_segment}/{t}` read and replace the root object, like any aggregate. A `PUT`
whose `label` differs from the record's is refused with 422 `invalid-body`: the label changes only
through `PUT …/label`.

If your web app is served from another origin, its browser sees only the response headers your
CORS settings expose. The toolkit sets none; expose `ETag`, `Record-ETag` and `Allowed-Actions`
yourself, for example:

[source,python]
----
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://ui.example"],
    expose_headers=["ETag", "Record-ETag", "Allowed-Actions"],
)
----

[#files]
== 10. Keep files

_How do I keep uploaded files?_

The toolkit keeps two kinds of file.

*Bytes*, kept as they are. A root that includes the `StoredFile` mixin describes a kept file
(`file_name`, `media_type`, `byte_size`, `sha256`, `uploaded`, `uploaded_by`, `file_key`); the toy
library's `Scan` does. The bytes go to the tenant's bucket through the `FileStore` port:
`put(bucket, key, data)`, `get(bucket, key)` and `delete(bucket, key)`. The toolkit has no route
for the bytes, so you add one. `file_key` is `internal`: no request body can set it and no response
shows it, but a domain service can, since the mapper writes internal slots. The toy library keeps
the bytes under the scan's id instead. Its route is in <<serve>>.

*RDF*, parsed into a graph of its own. `Session.load_graph(iri, data, rdf_format=RdfFormat.TURTLE)`
parses the data in a worker thread and puts it into a new named graph, by default
`{iri}/content/{uuid4}` (the loaded-graph template of the IRI policy; `Session` takes the policy
as `iris=`).
Data that does not parse raises `InvalidGraph`, and nothing is written. The graph belongs to the
aggregate once a commit names it (a graph another aggregate owns is refused with `InvalidIri`):

[source,python]
----
from rdf_persistence import RdfFormat

async with kit.session(tenant, principal) as session:
    loaded = await session.load_graph(scan_iri, data, rdf_format=RdfFormat.TURTLE)
    graph, _, version = await session.get_graph(scan_iri)
    await session.replace_graph(scan_iri, graph, version, loaded_graphs=[loaded])
----

`replace_graph` with `loaded_graphs=None` keeps the loaded graphs already registered; a list
replaces them, and the graphs left out are emptied. `remove` empties every loaded graph of the
aggregate. Formats: `turtle`, `rdfxml`, `ntriples` and `jsonld`.

[#access]
== 11. Control access

_Who may do what?_

*Roles are data.* Write them in a YAML file. Each entry names a role, the level it applies at
(`system`, `tenant` or `aggregate`) and the actions it permits (`read`, `modify`, `delete`,
`administer`):

[source,yaml]
----
# models/library_roles.yaml
- {role: admin, level: system, actions: [read]}
- {role: librarian, level: tenant, actions: [read, modify, delete, administer]}
- {role: reader, level: tenant, actions: [read]}
- {role: member, level: tenant, actions: [read, modify, delete]}
----

A `member` can delete the tenant's aggregates but not the tenant: that needs `administer`.

`load_role_definitions(path)` reads and validates the file. A malformed entry, an entry with no
actions, or a role defined twice at one level raises `InvalidRoleDefinition`, which names the
entry. A `system` role comes from the token's global roles (the `roles_claim`); it is never
granted. The set of actions is fixed by the toolkit: an application cannot add one.

*Grants and prohibitions* live in the tenant's access record. `GET …/grants` answers the
`GrantSet` with its `ETag`; `PUT …/grants` with `If-Match` replaces it whole:

[source,json]
----
{
  "grants": [
    {"assignee": "https://idp.example.org/users/ada", "target": "https://example.org/library/libraries/6f1c…", "role": "librarian"},
    {"assignee": "https://idp.example.org/users/bob", "target": "https://example.org/library/libraries/6f1c…/books/0b7e…/graph", "action": "modify"}
  ],
  "prohibitions": [
    {"assignee": "https://idp.example.org/users/bob", "target": "https://example.org/library/libraries/6f1c…/books/0b7e…/graph", "action": "delete"}
  ]
}
----

* An *assignee* is a principal IRI. The JWKS verifier makes it from the token's issuer and
  subject: `{issuer}/users/{sub}`.
* A *target* is the tenant's IRI or an aggregate's graph IRI, `{root}/graph`. The level follows
  from the target.
* A *grant* gives exactly one of a `role` (defined at the target's level) or an `action`. Two
  grants with the same assignee, target and role or action are refused.
* A *prohibition* forbids one action and wins over every grant. A prohibition of `read` forbids
  every action, since each implies `read`.

*The check* runs on every tenant route, after the token is verified and before the route's own code. It
answers in this order:

. The target is not the tenant or one of its aggregates: 404.
. The tenant is not `active`: 404.
. A prohibition in scope forbids the action: 403.
. The caller's grants in scope and its global roles permit no action at all: 404. A hidden tenant
  and a missing one answer alike.
. They do not permit this action: 403. Every other action implies `read`.

The scope is the tenant, plus the aggregate's graph for an action on one aggregate. A listing
needs `read` on the tenant and leaves out the aggregates a `read` prohibition hides from the
caller. Creating an aggregate needs `modify` on the tenant.

[#validators]
=== Enforce your own rules on tenant writes

_How do I stop a write my application forbids, such as removing the last owner?_

Give `install_service` validators. A *grant validator* runs on every replacement of a tenant's
grants (`PUT .../grants`), with the old set, the new one and the caller. A *root validator* runs
when a tenant is created, its root is replaced or it is renamed, with the old root (`None` on
create), the new one and the caller; on create the caller is the creator, who gets the first grant.
To refuse, raise `InvalidBody`: the answer is 422 `invalid-body` with your message as its `detail`,
and nothing is written.

[source,python]
----
from rdf_persistence import GrantSet, InvalidBody, Principal, install_service


def keep_an_owner(old: GrantSet, new: GrantSet, who: Principal) -> None:
    if not any(g.role == "owner" for g in new.grants or []):
        raise InvalidBody("a project keeps at least one owner")


install_service(
    app,
    grant_validators=[keep_an_owner],
    # ... and the other keyword arguments of step 12
)
----

The other arguments are those of <<serve>>; pass every argument by keyword.

Validators run in the order given, before the write; the first refusal stops it. They need no
lock: the write is conditional on the version the request sent (`If-Match`), so of two writes at
one version, both passing the rule, one lands and the other answers 409.

A validator is a plain function, not `async`: it runs on the event loop, so it must not block. A
coroutine function is refused when the service starts. It receives copies of the old and new
objects, so changing an argument has no effect on what is written. It returns nothing; returning a
value is a bug. Any exception other than `InvalidBody` or pydantic's `ValidationError` (also 422)
is a bug in the validator and answers 500, even another error of the toolkit such as `Forbidden`
or an `HTTPException`.

[#serve]
== 12. Serve the application

_How do I serve it over HTTP?_

The *composition root* is the one place that builds the adapters and hands them to
`install_service`. The toy library's is `build_library_app`:

[source,python]
----
# library/entrypoints/app.py
from pathlib import Path

from fastapi import FastAPI, Request, Response

from rdf_persistence import (
    AccessRules,
    Action,
    FileStore,
    Identity,
    ServiceSettings,
    Store,
    TokenVerifier,
    install_service,
    load_role_definitions,
)

from library.domain import generated

SCHEMA = Path("models/library.yaml")
ROLES = Path("models/library_roles.yaml")


def build_library_app(
    *,
    store: Store,
    files: FileStore,
    identity: Identity,
    verifier: TokenVerifier,
    settings: ServiceSettings,
) -> FastAPI:
    app = FastAPI()
    kit = install_service(
        app,
        schema=SCHEMA,
        generated=generated,
        store=store,
        files=files,
        identity=identity,
        verifier=verifier,
        rules=AccessRules(load_role_definitions(ROLES)),
        settings=settings,
    )
    path = f"/{settings.tenant_segment}/{{t}}/scan-files/{{scan_id}}"

    async def bucket_after(request: Request, tenant_id: str, scan_id: str, action: Action) -> str:
        checked = await kit.require_aggregate(
            request.headers.get("authorization"), tenant_id, "scans", scan_id, action
        )
        return await kit.bucket_of(checked.caller_access.tenant)

    @app.put(path, status_code=204)
    async def put_file(t: str, scan_id: str, request: Request) -> Response:
        bucket = await bucket_after(request, t, scan_id, Action.MODIFY)
        await kit.files.put(bucket, scan_id, await request.body())
        return Response(status_code=204)

    @app.get(path)
    async def get_file(t: str, scan_id: str, request: Request) -> Response:
        bucket = await bucket_after(request, t, scan_id, Action.READ)
        return Response(await kit.files.get(bucket, scan_id), media_type="application/octet-stream")

    return app
----

The adapters and the settings come from the deployment. The adapters of the store, the identity
provider and the token verifier are async context managers, so open them for the life of the app:

[source,python]
----
from rdf_persistence import (
    FusekiStore,
    JwksTokenVerifier,
    S3FileStore,
    ServiceSettings,
    ZitadelIdentity,
    zitadel_roles_claim,
)

settings = ServiceSettings(
    base="https://example.org/library/",   # IRIs and problem types are minted under it
    prefix="lib",                          # database and bucket names start with it
    tenant_segment="libraries",
    creator_role="librarian",
    roles_claim=zitadel_roles_claim(project_id),
)
async with (
    FusekiStore(fuseki_url, fuseki_user, fuseki_password) as store,
    ZitadelIdentity(issuer, service_token, organisation_id, project_id) as identity,
    JwksTokenVerifier(issuer, project_id, zitadel_roles_claim(project_id)) as verifier,
):
    files = S3FileStore(s3_endpoint, access_key_id, secret_access_key, region)
    app = build_library_app(
        store=store, files=files, identity=identity, verifier=verifier, settings=settings
    )
    ...                                    # serve app, for example with uvicorn
----

The verifier takes the issuer, the audience (the Zitadel project id) and the roles claim. It
refuses an issuer that is not `https` unless you pass `allow_insecure_issuer=True`, which is for
test containers only. In Zitadel, set each application to JWT access tokens: the verifier cannot
check opaque ones.

`install_service` mounts the routes (<<routes>>), the problem responses and the OpenAPI document.
On start-up, before your own lifespan, it creates the system database if it is missing, guards the
IRI policy (see "The policy cannot change", below) and runs the sweep. It stops with `OSError` if the generated folder lacks the context, the shapes, a frame or
`openapi-components.json`, and with `LookupError` if the schema has no tenant root or not exactly
one access record class. `rules` may also be the path of the roles file.

It returns the *`ServiceKit`*, for your own routes and domain services:

[cols="2,3",options="header"]
|===
|Member |Use
|`require(authorization, tenant_id, action)` |Verify the token and check `action` on the tenant;
returns an `Authorised` with the caller's `principal`, its `caller_access`, and the tenant IRI as
`checked_target`
|`require_aggregate(authorization, tenant_id, rp_path, aggregate_id, action)` |The same on one
aggregate, so a prohibition on it applies; returns an `Authorised` whose `checked_target` is the
aggregate IRI that was checked
|`session(tenant, principal)` |A session on the tenant's database (<<session>>)
|`bucket_of(tenant)` |The tenant's bucket name
|`tenancy`, `store`, `files`, `identity`, `view`, `settings` |The tenancy service, the ports (`store` is the `Store` you passed, wrapped as `ToolkitStore`), the loaded schema and the settings
|`tenant_iri(tenant_id)` |The tenant IRI of a tenant id taken from a path; `NotFound` if the IRI
policy does not mint such an id
|`iris` |The one `Iris` of the service, built from the settings and the schema; the services the kit
wires and its `rules` all use it
|===

A route of your own that calls a domain service needs the caller's principal IRI as well. The
`Authorised` that `require` and `require_aggregate` return carries it:

[source,python]
----
checked = await kit.require_aggregate(
    request.headers.get("authorization"), t, "books", book_id, Action.MODIFY
)
await add_chapter(
    kit, mapper, checked.caller_access.tenant, checked.principal, checked.checked_target, number
)
----

[#routes]
The *router* serves every aggregate root of the schema that has an `rp_path`. A class added to the
model is served after a restart:

[cols="2,3",options="header"]
|===
|Route |Methods
|`/{tenant_segment}` |`GET` the caller's tenants; `POST` a new tenant
|`/{tenant_segment}/{t}` |`GET`, `PUT` the tenant's root object; `DELETE` the tenant
|`/{tenant_segment}/{t}/grants` |`GET`, `PUT` the grant set
|`/{tenant_segment}/{t}/label` |`PUT` the label
|`/{tenant_segment}/{t}/{rp_path}` |`GET` a listing; `POST` a new aggregate
|`/{tenant_segment}/{t}/{rp_path}/{id}` |`GET`, `PUT`, `DELETE` one aggregate
|`/context.jsonld` |`GET` the generated JSON-LD context
|===

A client creates a book with `POST /libraries/{t}/books` and a plain JSON body without ids:

[source,json]
----
{"label": "Dune", "description": "A planet.", "author": "Frank Herbert", "chapters": [{"number": 1}]}
----

The answer is 201, with the stored book (ids minted), its `ETag` and a `Location`. A `PUT` of the
same body with `"id"` set and `If-Match` replaces it. Bodies are strict, and every error is an
RFC 9457 problem; the rules are on
xref:architecture/api.adoc#serving[A lightweight API, Serving it], and the order of the checks on a
`PUT` is in xref:architecture/api.adoc#anatomy[Anatomy of a request].

The generated TypeScript types describe the plain JSON a client sends and receives.

== 13. Test the service

_How do I test my application without servers?_

`rdf_persistence.testkit` has in-memory stand-ins for the four ports:

[cols="2,3",options="header"]
|===
|Helper |Stands in for
|`FakeStore()` |a `Store` (a small in-memory SPARQL store)
|`FakeFileStore()` |a `FileStore`
|`FakeIdentity()` |an `Identity`

The toy library's router tests build the whole service over them (`tests/toy_service.py`):

[source,python]
----
import httpx
from fastapi import FastAPI

from rdf_persistence import AccessRules, JwksTokenVerifier, install_service, load_role_definitions
from rdf_persistence.testkit import FakeFileStore, FakeIdentity, FakeStore, TokenSigner

# SCHEMA, ROLES, generated and settings as in the composition root; TENANT_BODY as in step 9

    schema=SCHEMA,
    generated=generated,

async with app.router.lifespan_context(app):     # start-up: the system database, the policy guard and the sweep
    transport = httpx.ASGITransport(app=app, raise_app_exceptions=False)
    async with httpx.AsyncClient(transport=transport, base_url="http://test") as client:
        created = await client.post("/libraries", json=TENANT_BODY, headers=headers)
----

`https://idp.test` is the issuer `TokenSigner` signs for. `ASGITransport` does not run the app's
lifespan, so the test enters it itself; without it the system database does not exist.

Before you rely on an adapter of your own, run the testkit's conformance suites against it:
`store_conformance`, `file_store_conformance` and `identity_conformance` under
`rdf_persistence.testkit`. Each has `CASES` and a `run_case` to run one of them on your adapter.
The toolkit runs the same suites on its fakes and on Fuseki, Garage and Zitadel in containers.

[#iri-policy]
== 14. Configure the IRI policy

_How do I make my own IRIs?_

By default the toolkit mints a tenant as `{base}{tenant_segment}/{tenant_id}` and an aggregate as
`{tenant}/{rp_path}/{id}`, with owned parts and loaded graphs nested under their root, every id a
UUID (elsewhere on this page `{uuid4}` stands for such an id). If your organisation fixes another
shape, describe it as an *IRI policy* and put it on the settings. The policy is a record with a
template per kind of IRI and the rule for each id:

[source,python]
----
from rdf_persistence import (
    IdKind, IdSpec, IriPolicy, Iris, JwksTokenVerifier, ServiceSettings, zitadel_roles_claim,
)

project_id = "..."                          # your Zitadel project id (step 12)
FLAT = "{base}{tenant_id}/{type}/{id}"
settings = ServiceSettings(
    base="http://mwb.meaningfy.ws/",
    prefix="lib",
    tenant_segment="libraries",
    creator_role="librarian",
    roles_claim=zitadel_roles_claim(project_id),
    deployment="dev",                        # what {deployment} takes; needed only if a template uses it
    iri_policy=IriPolicy(
        tenant_template="{base}project/{tenant_id}",
        access_template="{base}{deployment}/project/{tenant_id}",
        principal_template="{base}{deployment}/user/{sub}",
        aggregate_template=FLAT,
        part_template=FLAT,
        loaded_graph_template=FLAT,
        tenant_id=IdSpec(kind=IdKind.RANDOM, length=7),
        object_id=IdSpec(kind=IdKind.RANDOM, length=13),
    ),
)
# the verifier mints principals: give it the same policy; open it with `async with` as in step 12
verifier = JwksTokenVerifier(issuer, project_id, zitadel_roles_claim(project_id), iris=Iris(settings))
----

A slot you leave out keeps its default. A tenant is then `http://mwb.meaningfy.ws/project/p4x8k2m`,
a book `http://mwb.meaningfy.ws/p4x8k2m/book/{13 characters}`, its chapter
`http://mwb.meaningfy.ws/p4x8k2m/chapter/{13 characters}` and a graph loaded into it
`http://mwb.meaningfy.ws/p4x8k2m/content/{13 characters}`: all flat, none nested under another. The
aggregate's named graph stays `{root}/graph`. The API paths keep their shape: the tenant is
`/libraries/p4x8k2m` and the book `/libraries/p4x8k2m/books/{13 characters}`, because the id in a
path is the last segment of the IRI. A path id the policy does not mint answers 404.

The fields of `IriPolicy`, with their defaults and the variables each template may use:

[cols="2,3,3",options="header"]
|===
|Field |Default |May use, and must
|`tenant_template`
|`{base}{tenant_segment}/{tenant_id}`
|`{base}`, `{deployment}`, `{tenant_segment}`, `{tenant_id}`; ends in `{tenant_id}`
|`aggregate_template`
|`{tenant}/{rp_path}/{id}`
|`{base}`, `{deployment}`, `{tenant}`, `{tenant_id}`, `{type}`, `{rp_path}`, `{id}`; names
`{tenant}` or `{tenant_id}`; ends in `{id}`
|`part_template`
|`{root}/parts/{id}`
|`{base}`, `{deployment}`, `{tenant}`, `{tenant_id}`, `{root}`, `{type}`, `{id}`; names
`{tenant}`, `{tenant_id}` or `{root}`; ends in `{id}`
|`loaded_graph_template`
|`{root}/content/{id}`
|as `part_template`; its `{type}` is `content`
|`access_template`, `meta_template`, `registry_template`
|`{tenant}/access`, `{tenant}/meta`, `{tenant}/registry`
|`{base}`, `{deployment}`, `{tenant}`, `{tenant_id}`; names `{tenant}` or `{tenant_id}`
|`principal_template`
|`{issuer}/users/{sub}`
|`{base}`, `{deployment}`, `{issuer}`, `{sub}`; ends in `{sub}`
|`tenant_id`, `object_id`
|a UUID
|an `IdSpec` (below)
|===

`{tenant}` is the tenant's IRI, `{root}` the IRI of the aggregate root a part or a loaded graph
belongs to, `{tenant_id}` and `{id}` the ids, and `{base}`, `{deployment}` and `{tenant_segment}`
the settings of the same name. `deployment` (lower case letters and digits) is needed only when a
template uses `{deployment}`. A template that uses another variable, does not end as the table
says, or names no tenant is refused when the settings are built. The verifier mints the
principal, and you build it before the kit: with a `principal_template` of your own, pass it the
policy as `JwksTokenVerifier(..., iris=Iris(settings))` (`Iris` is exported by `rdf_persistence`).
Without it the verifier mints the default `{issuer}/users/{sub}`, and grants to your principals
never match: `install_service` compares the `principal_template` of the verifier's `Iris` with the
settings' and refuses to start (`InvalidIri`) when they differ. A `principal_template` without
`{issuer}` gives one principal to the same `sub` of every identity provider; leave `{issuer}` out
only when one provider issues all your tokens. The verifier refuses a token whose `sub` is empty,
`.` or `..`. Templates under which a tenant's access, meta or registry IRI equals another of them,
the tenant's, or reads as an aggregate or a loaded graph are refused too. The access record is not an aggregate: no session reads or commits its graph, but a
grant may still target it.

The consumer's table:

[cols="3,3,2",options="header"]
|===
|Kind |Template or setting |Now
|Tenant |`{base}project/{tenant_id}` |configurable
|Aggregate root, owned part, loaded graph |`{base}{tenant_id}/{type}/{id}` |configurable
|Tenant id |`random`, 7 characters of `[a-z0-9]` |configurable
|Object id |`random`, 13 characters of `[a-z0-9]` |configurable
|Database and bucket |`{prefix}-t-{tenant_id}` |fixed
|Access record, meta and registry graphs |`{base}{deployment}/project/{tenant_id}` for the access
record, `{tenant}/meta`, `{tenant}/registry` |configurable
|Principal |`{base}{deployment}/user/{sub}` |configurable; pass `iris=Iris(settings)` to the verifier
|Guard against a service started under another policy than its tenants were made under |`install_service` start-up

|===

The policy cannot change once a deployment has data: their IRIs and graphs are stored under the old
policy. At start-up, before the sweep (which reads the access records through the policy),
`install_service` records the effective policy in the system database, in the graph
`{base}toolkit/iri-policy`. The effective policy has every default filled in and the settings'
`{base}`, `{deployment}` and `{tenant_segment}` written into the templates, so leaving a field unset
and setting it to its default are the same, and changing `base`, or the `deployment` of a template
that uses it, changes the policy. The first write is conditional and read back, so two instances that
start at once with different policies cannot both serve. On every later start it compares the
configured policy with the record and, when they differ, refuses to start with `IriPolicyChanged`
(a 503 `unavailable` if a route ever meets it), naming each differing field (`object_id.length`) and
logging it with `step: iri-policy`. A record that cannot be parsed, or more than one record, refuses
the start too, saying the record is unreadable. A system database that has access
records but no record is taken to hold the default policy: a non-default policy is refused there,
and the default is recorded. Moving stored data to a new policy is not supported.

What else the policy fixes:

* `{type}` is the class's `rp_iri_type`, else its name in kebab case (step 3), and `content` for a
  loaded graph.
* An id is a UUID (`IdKind.UUID4`) or `length` characters of an `alphabet` (`IdKind.RANDOM`; 4 to
  32 characters, by default `0123456789abcdefghijklmnopqrstuvwxyz`). A drawn id that equals a word
  the templates use (a `{type}`, `content`, the deployment) is drawn again, and so is a tenant id
  whose access record or database already exists, at most five times.
* A schema in which two classes share an `rp_iri_type`, or one equals such a word, is refused.

One `Iris` serves the whole service. `install_service` builds it from the settings and the schema
and hands it to every service it wires, to the kit (`kit.iris`) and to the access rules, even
rules you built yourself: `AccessRules.with_iris(iris)` answers a copy with the same role permits
under that policy. You never pass one to `install_service`. Inside a domain service, take it from
the kit: `kit.iris` (step 8). Outside a service, build one from the settings and the types of the
schema (needed only when a template uses `{type}`):

[source,python]
----
from rdf_persistence import Iris, load_schema
from rdf_persistence.services.schema_structure import iri_types

root_types, owned_types = iri_types(load_schema("models/library.yaml"))
iris = Iris(settings, root_types, owned_types)
tenant = str(iris.mint_tenant())
book = iris.mint_aggregate(tenant, "book", "books")
----

and pass it to what you build: `new_part(..., iris=iris)`, `open_session(..., iris=iris)`,
`fake_session(..., iris=iris)`. `DEFAULT_IRIS` is the default policy, which `mint_aggregate_iri`
and the other module functions use.

The toy library's end-to-end test runs under this table against Fuseki, Garage and Zitadel:
`tests/e2e/test_library_policy.py`.
