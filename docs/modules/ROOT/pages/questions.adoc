= Common questions
:description: Short answers to the questions people ask about rdf-persistence, each with a link to the page that goes deeper.

Each answer is one or two sentences and links to the page with the details. The questions follow
the sections of the site: the tutorial and the user manual, the how-to guides, the architecture,
and the developer manual.

== Finding your way

*I am new: where do I start?*::
With the tutorial. You model one aggregate, generate its code, store it and read it back, in
memory, with no server to run. See xref:tutorials/getting-started.adoc[Getting started].

*How do I build a whole application, step by step?*::
Follow the user manual: fourteen steps, in the order the work is done; other pages cite them by
number ("step 8"). See xref:user-manual/index.adoc[User manual: build an application].

*I know the basics; how do I use feature X?*::
Find the feature's guide, grouped by capability: data, collaboration and events, operations. Each
takes one task from start to finish. See xref:howto/index.adoc[How-to guides].

*Who is the toolkit for, and what do they do with it?*::
Four actors (the application developer, an API client, a system architect and the toolkit
developer), each with goals written as use cases that name the capabilities serving them. See
xref:requirements/use-cases.adoc[Use cases].

*What does the toolkit commit to, and where is each part documented?*::
Its `rp-*` capabilities. The requirements are in `openspec/specs/`; the docs list what each
capability covers and the pages that explain it. See
xref:requirements/capabilities.adoc[Capabilities].

*How is the toolkit built, and why?*::
A library and a generator in one wheel, layered `entrypoints | adapters → services → domain`, with
ports for the store, the file store, the identity provider, the token verifier and the event bus.
See xref:architecture/index.adoc[Architecture overview], which maps the rest of the architecture
section.

*Which models does the toolkit have?*::
The metamodel, which an application's schema imports and which is stored as RDF, with a generated
class diagram per module; and the technical schemas of the toolkit's own records, never stored as
RDF. See xref:architecture/models.adoc[Models].

*What is the exact name of a class, a function or an `rp-generate` option?*::
Look it up in the reference: the public Python API and the `rp-generate` usage, both generated
from the code, and where the settings, routes and Make targets are listed. See
xref:reference/index.adoc[Reference].

== Building an application

*How do I start an application?*::
Add `rdf-persistence` to your dependencies from its `develop` branch, with the extras `generate`
and `testkit` in the dev group, and run `uv sync`. See xref:user-manual/install.adoc[step 1].

*How do I model my domain?*::
Write one LinkML file per module: each domain module holds one aggregate, a root class that includes
`AggregateRoot` and `Described`, has an `rp_path`, and owns its parts through slots annotated
`owned: true`. See xref:user-manual/model.adoc[step 3] and
xref:architecture/generation.adoc#metamodel[the metamodel].

*Which UML conventions does a model for rdf-persistence follow?*::
model2owl's UML conventions plus the toolkit's own: «root» and «tenant root» classes, aggregates
drawn as boundary objects, class tagged values, multiplicity and empty enumerations. Each is shown
as UML and as the LinkML it becomes. See xref:reference/uml-conventions.adoc[UML conventions].

*I draw my model in Enterprise Architect: how do I get the LinkML from it?*::
Run `rp-uml2linkml` on the `.qea` file with a prefixes file; it writes the schemas and a report of
what it left out, and `rp-generate --check` then checks them. See
xref:howto/uml-to-linkml.adoc[Generate the model from UML].

*How do I turn the model into code?*::
Declare the outputs in a `[tool.rp-generate]` table of `pyproject.toml` and run `rp-generate`: it
checks the schema, then writes the classes, shapes, context and frames, and, when asked, the
TypeScript types and the diagrams. See xref:user-manual/generate.adoc[step 4].

*How do I change the model later?*::
Edit the schema, regenerate, run the tests and commit the schema and the generated code together;
if data is already stored, the schema also needs a new version (see _My schema changed and I have
stored data_ below). See xref:user-manual/change-model.adoc[step 7].

*How do I store and read an aggregate?*::
Over HTTP the generic router does it. In a domain service, open `kit.session(tenant, principal)`,
wrap it in a `UnitOfWork(session, mapper)`, `get` the root, change it, `add` it and `commit`. See
xref:user-manual/store-and-read.adoc[step 8].

*Can I save several aggregates at once?*::
Yes: change, add and `remove` the roots in one `UnitOfWork` and call `commit()` once, and all are
stored or none is. One commit holds at most 500 roots by default. See
xref:user-manual/store-and-read.adoc#transaction[Save several aggregates at once] and
xref:user-manual/store-and-read.adoc#transaction-batches[Save more than 500 aggregates].

*Can two aggregates share a key value?*::
Not if the root declares a `unique_keys` entry with `rp_unique_scope: tenant`: a commit that claims
a value another aggregate of the tenant holds raises `KeyConflict` (409 `key-conflict`) and writes
nothing. See xref:user-manual/store-and-read.adoc#key-conflict[Keep a value unique across
aggregates] and xref:user-manual/store-and-read.adoc#key-on-live-data[Add a key to live data].

*Can I stop an aggregate from being deleted while others refer to it?*::
Yes: annotate its class `rp_on_referenced_delete: refuse`. Removing it then raises `InUse` (a
`Conflict`, so do not retry it) and `DELETE …/authors/{id}` answers 409 `in-use`, naming the referrers
the caller may read and counting the rest; nothing is deleted. The check holds when the delete is
applied, not for a write that names the IRI afterwards. See
xref:user-manual/store-and-read.adoc#refuse-referenced[Refuse to delete an aggregate that others
refer to].

*Why did my commit raise `Conflict`?*::
Another writer changed or removed a root you change since you read it, or a root you add already
exists; nothing was written, and the toolkit never retries for you. Read the roots again in a new
unit of work and apply your edit if it still makes sense. See
xref:user-manual/store-and-read.adoc#handle-a-conflict[Handle a conflict] and
xref:architecture/commits.adoc#conflict[what a conflict means].

*How do tenants and access work?*::
Each tenant has its own database and bucket, and an access record in the system database with its
grants and prohibitions; every tenant route checks the caller's token, then its access. See
xref:user-manual/tenants.adoc[step 9], xref:user-manual/access.adoc[step 11] and
xref:architecture/access-control.adoc[Access control and identity].

*How does my UI know which buttons to show?*::
Read the `Allowed-Actions` header of a tenant or of an aggregate, or the `allowed_actions` of the
tenant's item in `GET /{tenant_segment}`; on another origin, expose the header in your CORS
settings. See xref:user-manual/tenants.adoc[step 9] and
xref:architecture/access-control.adoc#check[the check].

*How do I enforce my own rule on tenant writes, such as keeping one owner?*::
Pass `grant_validators` or `root_validators` to `install_service`; a validator raises `InvalidBody`
to refuse, the answer is 422 and nothing is written. See
xref:user-manual/access.adoc#validators[Enforce your own rules on tenant writes].

*How do I refuse a write to an aggregate that breaks a rule of my application?*::
Pass `aggregate_validators` to `install_service`: a mapping from a class name to rules, each
`(old, new, principal, reader)`, sync or async; a rule raises `InvalidBody` to refuse, the answer
is 422 and nothing is written. See
xref:user-manual/access.adoc#aggregate-validators[Enforce your own rules on aggregate writes]. To
answer with a problem of your own (extra fields, 409 or 422), see
xref:user-manual/access.adoc#refuse-with-own-problem[Refuse with your own problem].

*How do I refuse a delete?*::
Pass `delete_validators` to `install_service`: a mapping from a class name to rules, each
`(old, principal, reader)`, sync or async; a rule raises `Refused` to refuse, the answer is 409 `refused`
with your message as its detail and nothing is removed, a collection's cascade included. See
xref:user-manual/access.adoc#delete-validators[Refuse the delete of an aggregate].

*How do I serve it over HTTP?*::
Call `install_service` once in your composition root; it serves every aggregate root of the schema
that has an `rp_path`, and returns a `ServiceKit` for your own routes. See xref:user-manual/serve.adoc[step 12] and
xref:architecture/api.adoc#serving[Serving it].

*I write the front end: how do I call the service?*::
With a bearer token from the identity provider, plain JSON bodies, the `ETag` echoed in `If-Match`
on every write, and problem responses to read on failure. See xref:reference/http-api.adoc[The
HTTP API], the whole client contract on one page.

*How do I read back a graph I loaded?*::
Check the read with `kit.require_aggregate(..., Action.READ)`, then call
`session.loaded_graph(root_iri, graph_iri)` for a plain rdflib `Graph`; the session checks no access
itself. See xref:user-manual/files.adoc[step 10].

*How do I check that a name is not taken yet?*::
To have the commit refuse a duplicate, declare a unique key (above). To ask first, call
`session.find(Scan, file_name=name)`, which ignores prohibitions, so check each IRI with
`require_aggregate` before you show it. See xref:user-manual/files.adoc[step 10].

*How do I make my own IRIs?*::
Describe their shape as an `IriPolicy`, a template for each kind of IRI and a rule for each id, and
set it on `ServiceSettings.iri_policy`; the service then mints, checks and reads back every IRI by
it. See xref:user-manual/iri-policy.adoc[step 14].

*Why does my file root answer 405 on PUT?*::
A root that includes `StoredFile`, or carries the class annotation `rp_writes: service`, is written
only in your own route through a session, because the record and its bytes must change together;
the router serves only its `GET` and listing. See xref:user-manual/files.adoc[step 10] and
xref:architecture/api.adoc#serving[Serving it].

*How do I clean up orphans in a live tenant?*::
Run `kit.sweep_tenant(tenant)` as an operator command: it finds the loaded graphs no commit owns and
the blobs no `file_key` names, and removes them only when you pass `remove=True` or
`remove_blobs=True`. See xref:user-manual/files.adoc#sweep-live-tenant[Sweep a live tenant].

*How do I test my application with the testkit?*::
Use the fakes of `rdf_persistence.testkit` (`FakeStore`, `FakeFileStore`, `FakeIdentity`,
`fake_session`) and its `TokenSigner`, and add the model guards and the freshness plugin to your
test suite. See xref:user-manual/generated-classes.adoc#guard[step 6] and
xref:user-manual/test.adoc[step 13]. To follow a tenant's event stream in a test, use
`open_event_stream`; see xref:user-manual/test.adoc#event-stream[Follow a tenant's event stream].

*How do I queue and select my project's tests with the testkit?*::
Run your tests through `rdf_persistence.testkit.run_queue`, which queues heavy runs and sizes the
workers, and record the selection data with `rdf_persistence.testkit.selection_data seed`. See
xref:user-manual/test.adoc#test-control[Test control for your project].

== Using a feature

The guides are listed by capability in xref:howto/index.adoc[How-to guides].

=== Data

*Who points at this resource?*::
`collab.referrers(iri)` lists the aggregates whose slots hold that IRI; referrers the caller may not
read are counted in `hidden_count` and never named. See
xref:howto/reverse-references.adoc[Find who points at a resource].

*How do I group resources I do not own?*::
Mix `ReferenceCollection` (module `rp_collections`) into an aggregate root: it names its members by
IRI, by a rule, or both, and holds none of their triples. See
xref:howto/reference-collections.adoc[Group resources you do not own].

*My schema changed and I have stored data: what do I do?*::
Set a new quoted `version:` in the root schema and run `make generate`: `rp-generate` drafts a
migration file for you to review, and the service applies it at start-up, once per database,
before it serves. See xref:howto/migrate.adoc[Change a schema that has stored data].

*How do I store a part apart from its whole and still delete it with the whole?*::
Annotate the part's class `rp_dependent_on` with its pointer slot. A write of the part then checks
that the whole exists, and deleting the whole deletes its parts, transitively, in one commit. See
xref:user-manual/store-and-read.adoc#dependent-parts[Store a part apart from its whole].

*Where does data that belongs to no tenant go?*::
Into the application database, one per deployment: mark the class `database: application` in the
schema; access to it comes from global roles at level `system`. See
xref:howto/application-data.adoc[Keep data that belongs to no tenant].

=== Collaboration and events

*Can a reviewer comment without editing?*::
Yes: import the module `rp_discussion` and give the reviewer's role the action `annotate`, which is
not `modify`. `collab.comment(iri, text)` stores the comment as an aggregate of its own and leaves
the target untouched. See xref:howto/discussion.adoc[Comment on a resource without editing it].

*How do I put a resource through review?*::
Give its class a workflow, a YAML file of states and transitions, each with the roles that may make
it; `collab.transition(iri, to, if_version=...)` moves the resource and records the move. See
xref:howto/workflow.adoc[Put a resource through review].

*Why does my delete take comments with it, and not the history?*::
A comment is an aggregate about one aggregate, so every delete through the kit drops the comments
on it in the same request; a transition is an activity in the provenance graph, kept when its
aggregate goes. See xref:howto/discussion.adoc#delete[Delete] and
xref:howto/workflow.adoc#read-the-history[Read the history].

*How do I run a use case as a command?*::
Model it as a subclass of `Activity`, register a handler for it with `bootstrap`, set `kit.bus`, and
send it with `bus.handle(...)`; one command makes one commit. See
xref:howto/event-driven.adoc[React to changes with commands and observers].

*How do I run code after a commit?*::
Register an observer for an activity class with `bootstrap(observers=...)`: after each commit,
including those of the generic routes, it gets the completed activity, which references the
aggregates and never holds their content. See xref:howto/event-driven.adoc#write-observer[Write an
observer].

*Is an observer guaranteed to run?*::
Not in the process that committed, where delivery is at most once; observers in another deployment
get every commit at least once through the relay. See xref:howto/event-driven.adoc#limits[the
limits] and xref:howto/event-driven.adoc#relay[the relay].

*How do other deployments, or a browser, follow my commits?*::
Install `rdf-persistence[events]` and pass a `RedisEventBus` to `install_service`: the relay
publishes every commit to the other deployments, and a browser reads them as server-sent events.
See xref:howto/event-driven.adoc#relay[Carry commits to other deployments and to browsers].

=== Operations

*How do I change a timeout, a cache time or a limit of the toolkit, and read it from the environment?*::
Build a `ToolkitSettings` with the groups you need at the composition root and pass it as
`install_service(..., toolkit=settings)`. Each adapter you build takes its own group as well:
`http=` for the store, the file store, the verifier and the identity provider, `jwks=` for the
verifier, `directory=` for the identity provider and `events=` for `RedisEventBus`. With the `settings` extra, `settings_from_env` reads the
values from `RP_*` variables. See xref:howto/settings.adoc[Configure the toolkit's deployment
values].

*How do I back up or copy a tenant?*::
`kit.dump_tenant(tenant, out)` writes the tenant's graphs and files to one archive, and
`kit.restore_tenant(src, creator)` creates a new tenant from it, with a new id and new IRIs; grants
are not dumped. See xref:howto/dump-restore.adoc[Back up or copy a tenant].

*Can a tenant's data live on another server?*::
Yes: wire the other triple stores by name with `install_service(..., stores={...})` and create the
tenant on one with `kit.tenancy.create(..., store=name)`; a tenant never moves afterwards. See
xref:howto/tenant-stores.adoc[Put tenants on several stores].

*How do I see traces and structured logs from the toolkit?*::
Install the OpenTelemetry SDK, an exporter and the instrumentations in your composition root: the
toolkit uses the OpenTelemetry API only, so its spans are no-ops until you do. The log attribute
names changed in 0.5.0; see xref:howto/observability.adoc[See what the toolkit is doing] and
xref:howto/observability.adoc#old-to-new[the old-to-new names].

== Architecture and decisions

*Where is my data stored, and what happens when I create, read, replace or delete it?*::
Each tenant's aggregates are named graphs in its own database, its files are in its own bucket, and
its access record is in the system database. See
xref:architecture/data-flows.adoc[Where data lives and what each operation does].

*What happens when two people edit the same thing?*::
The second commit is refused and nothing of it is written: every aggregate has a version token, and
a commit is stored only if each root it changes is still at the version it read. See
xref:architecture/commits.adoc[How commits and conflicts work].

*Where is the record of who changed what?*::
Every commit writes one activity into the tenant's provenance graph, in the same request as the
change: its kind, times, principal and the versions of the aggregates it touched, never their
content. See xref:architecture/data-flows.adoc#commit[Committing several aggregates at once] and
xref:howto/workflow.adoc#read-the-history[Read the history].

*Why does the toolkit have its own SPARQL client?*::
rdflib's client is synchronous while the store port is async, has no test transport and cannot
express the guarded single-request commit. See xref:adr/adr-001-sparql-client.adoc[ADR-001].

*Why does the token verifier fetch and cache the keys itself?*::
PyJWT's `PyJWKClient` blocks the event loop, has no discovery and no transport or clock to inject,
and hits a failing provider on every call; PyJWT still checks every signature. See
xref:adr/adr-002-jwks-cache.adoc[ADR-002].

*Why FastAPI with a generated OpenAPI document, and not a spec-first library such as connexion?*::
The routes and the document both come from the LinkML schema, so a spec-first library would still
need a spec the toolkit produces, and would take FastAPI's access gate and SHACL validation away.
See xref:adr/adr-003-fastapi-not-connexion.adoc[ADR-003].

*Which token signature algorithms does the verifier accept, and how do I change them?*::
RS256, RS384, RS512, PS256, PS384, PS512, ES256, ES384, ES512 and EdDSA by default, never `none` or
`HS*`, with 30 seconds of clock leeway; set `allowed_algorithms` and `leeway_seconds` on
`JwksSettings`. See
xref:adr/adr-004-signing-algorithms.adoc[ADR-004] and
xref:user-manual/serve.adoc#verifier-options[the token verifier].

*Which representations can I ask for an aggregate in?*::
JSON (the default), JSON-LD, Turtle, N-Triples, N-Quads, TriG and RDF/XML for one aggregate; a
listing stays JSON and JSON-LD. See xref:adr/adr-005-representations.adoc[ADR-005] and
xref:architecture/api.adoc#representations[Representations].

*Where are decisions recorded?*::
Settled decisions are the xref:adr/index.adoc[architecture decision records]; earlier ones are in
the xref:architecture/open-decisions.adoc[decision log of 2026-11-05] and the
xref:architecture/index.adoc#decisions-taken[architecture overview], and each change's own in its
`design.md` under `openspec/changes/`. The ADR index explains the three places.

== What to expect, and the choices you make

=== Guarantees

*Generated code is fresh.*::
`rp-generate --check`, and the testkit's freshness plugin, fail when generated code is stale or was
edited by hand, and name the files. See
xref:architecture/generation.adoc#guarding[Guarding the generated code].

*Nothing drifts from the model.*::
`assert_models_generated` fails on a hand-written model class, and the file guard on shapes,
contexts, schemas or TypeScript outside a `generated` folder. See
xref:user-manual/generated-classes.adoc#guard[step 6].

*Classes and shapes agree.*::
`conformance_problems` checks every case against both the generated class and the generated shape, and
fails until every constraint kind your schema uses has a case. See
xref:user-manual/generated-classes.adoc#guard[step 6].

*No lost update.*::
Every write to an aggregate is guarded by its version, `If-Match` over HTTP and the version a
`UnitOfWork` read in code: a stale write is 409 or `Conflict`, never a silent overwrite. See
xref:architecture/commits.adoc[How commits and conflicts work].

=== Limits and behaviours you will meet

*Status codes.*::
A hidden tenant or aggregate answers 404 like a missing one, 403 means you may see it but not act,
and every error is an RFC 9457 problem; only the statuses that say what to fix in the request carry
a `detail`. See xref:architecture/api.adoc#serving[Serving it].

*Strict bodies.*::
A plain-JSON body may use only its class's slot names and the JSON-LD keywords, and hold only the
root and the owned parts reached from it. See xref:architecture/api.adoc#serving[Serving it].

*Internal slots.*::
A slot annotated `internal` (a file key, a database name) is refused in any body and never shown in
a response; a replace keeps its stored value. See xref:architecture/api.adoc#serving[Serving it].

*What the toolkit refuses.*::
At generation: a schema without titles, descriptions or IRIs, LinkML `rules`, `all_of` and
`none_of`, and a domain module that imports an access module. At run time: an aggregate IRI the
toolkit did not mint, a remote JSON-LD context, and a grant on a target outside the tenant or of a
role not defined at the target's level.

=== Decisions you make

[cols="2,4,2",options="header"]
|===
|Decision |Trade-off |Default

|Schema layout and modules
|One file per aggregate keeps diagrams small and the boundary check precise. Access rules go in a
module annotated `module_kind: access`, which domain modules may not import.
|One root schema importing one file per module

|Aggregate roots and owned classes
|A root is one named graph, versioned and committed whole. An owned class lives inside its root's
graph and has no route of its own; anything another aggregate points to must be a root. Exactly
one class is the tenant root (`graph: meta`).
|A class is owned unless it needs its own lifecycle, routes or access

|Roles and the creator role
|Roles are data in a YAML file (`role`, `level`, `actions`). The creator of a tenant gets
`creator_role`; give that role `administer`, or only a global role can change the tenant's grants.
|None: the file and `creator_role` are required

|Zitadel settings
|The API accepts only JWT access tokens, so each Zitadel application is set to the JWT token type,
and clients ask for the project audience and roles scopes. `roles_claim` must match the provider
(`zitadel_roles_claim(project_id)`).
|None: `roles_claim` is required

|File store
|Each tenant gets a bucket, created and deleted with the tenant. The toolkit has no route for
file bytes: you write it, checked through the kit.
|A bucket per tenant always; the bytes route is yours

|JSON-LD or an RDF serialisation
|Plain JSON is the easiest for clients and is JSON-LD through the `Link` header. A JSON-LD body
brings its own inline context (a remote one is refused). The five RDF serialisations (Turtle,
N-Triples, N-Quads, TriG, RDF/XML) are for one aggregate only: no body and no listing takes them
(xref:architecture/api.adoc#representations[the seven types]).
|Plain JSON

|The `openapi` switch
|`openapi = false` in `[tool.rp-generate]` skips `openapi-components.json`. A schema a service
serves needs it: `install_service` stops without it.
|`true`

|`max_body_bytes`
|Larger bodies cost memory and parse time; the node cap (`max_document_nodes` of the `limits`
group, 10 000 by default) applies whatever the size.
|1 MiB (1 048 576 bytes)
|===

== Developing the toolkit

*Where does a module live?*::
In a theme, and inside the theme in a layer: `rdf_persistence/<theme>/<layer>/<module>.py`, where a
new module goes to the lowest theme that uses it. See
xref:architecture/index.adoc#themes[Where a module lives] and
xref:architecture/index.adoc#layering[The contracts] for the import rules.

*How do I tell a technical model from a domain model?*::
By its path: the metamodel is `rdf_persistence/model/rp_*.yaml`, and a technical model (a request
body, a setting, a wire shape) is a schema under `rdf_persistence/model/technical/<theme>/`, which no
domain layer imports. See xref:architecture/index.adoc#models-in-themes[Where a model lives] and
xref:architecture/generation.adoc#kinds[Two kinds of model].

*How do I change a toolkit schema?*::
Edit the schema, run `make generate`, refresh the model-shape snapshot if a class changed, and
commit the schema and the generated code together. See
xref:develop/generator.adoc#change-a-toolkit-schema[Change a toolkit schema].

*How do I add a generator extension or a check rule?*::
An extension is a module in `rdf_persistence_generation/extensions/` with a `render` function and
its own test against the toy library; a check rule is a value in `rp_generation.yaml` with its code
in `checks/`. See xref:develop/generator.adoc#add-or-change-a-generator-extension[Add or change a
generator extension] and xref:develop/generator.adoc#add-a-check-rule[Add a check rule].

*Which tests do I run while developing?*::
`make test-changed`, which runs the tests the files you changed against `develop` reach, and
`make check-all` once, before the PR. See xref:develop/index.adoc#make-targets[Make targets] and
xref:develop/testing.adoc#test-control[How test runs are controlled].

*How are test runs controlled when several agent sessions share a machine?*::
The heavy lanes wait in one queue for the whole machine, their worker count follows the cores and
the free memory, builders run only the tests their change reaches, and each test process releases
library caches between tests. See xref:develop/testing.adoc#test-control[How test runs are
controlled].

*How do I run the checks, and how long do they take?*::
`make check-all` before every PR (about 6 minutes), and `make test-containers` when you touch
adapters or containers (about 3.5 minutes, needs Docker). See
xref:develop/index.adoc#how-long-the-checks-take[How long the checks take].

*How much code is there, and how many tests guard it?*::
At 0.15.0, about 37,000 lines (18,700 statements) of production code and 107,000 lines of tests:
about 5,200 test functions, run as about 10,300 tests. See
xref:develop/index.adoc#size[How big the code and the test suite are].

*How is a release cut?*::
release-please proposes it as a PR into `develop` from the Conventional Commits; you merge it and
fast-forward `main` to the tag by hand. See xref:develop/index.adoc#release[Cutting a release].

*How do agents work on this repository?*::
By skillery's delivery method (the `epic-delivery` skill): one epic session per EPIC, where the
lead runs a small team and the developer decides. What is specific here is on
xref:develop/agents.adoc[Working with agents].

*How do we keep review and checking from doubling the work?*::
The adversarial tester runs right after the riskiest task, lenses L4 and L5 are one review pass,
and the checker trusts the lead's full-suite run. See
xref:develop/agents.adoc#challenge[Keeping the challenge cheap].

*Why does a Bash command fail with "Polling loops are blocked"?*::
A hook denies `sleep` loops so agents stop waiting on their own background runs; run the command in
the foreground or in the background with its notice. See
xref:develop/agents.adoc#never-poll[Never poll].

== What could strengthen it in the future

These are possibilities, not commitments. Each is shaped as a candidate EPIC in
`openspec/changes/<id>/`, listed with a suggested order in `openspec/changes/README.md`. None is
planned: its PLAN waits for the decisions listed in its `inputs/seed.md`.

* *Detailed test profiling.* The check timings are rough; a profile of the slowest tests would show
  where the 5 minutes of unit and feature tests go.
* *A client library* over the generated TypeScript types and the OpenAPI document.
* *GraphQL*, read-only over the same schema and context (option C of
  xref:architecture/api.adoc[the API page]), *OpenFGA* as the decision engine, and property- or
  triple-level access.
* *A second store* (Oxigraph, Virtuoso) with a capability descriptor.
