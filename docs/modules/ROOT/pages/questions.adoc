= Common questions
:description: Short answers to the questions people ask about rdf-persistence, each with a link to the page that goes deeper.

Each answer is short and points to the page with the details. The answers describe the toolkit
on `develop` as of 2026-11-06 (the change `toolkit-v1-foundation`, stages 1 to 5).

== Using the toolkit

*How do I start an application?*::
Add `rdf-persistence` to your dependencies from its `develop` branch, with the extras `generate`
and `testkit` in the dev group, and run `uv sync`. Then write the model, generate, and wire the
service. See xref:howto/adopt.adoc#install[Build an application, step 1].

*How do I model my domain?*::
Write one LinkML file per module and a root schema that imports them. Each domain module holds one
aggregate: a root class that includes `AggregateRoot` and `Described` and has an `rp_path`, and the
classes it owns through slots annotated `owned: true`. `rp-generate` refuses a schema that breaks
the rules and names the element at fault. See xref:howto/adopt.adoc#model[step 3] and
xref:architecture/generation.adoc#metamodel[the metamodel].

*How do I store and read an aggregate?*::
Over HTTP, the generic router does it for you. In a domain service, open a session on the tenant's
database (`kit.session(tenant, principal)`), wrap it in a `UnitOfWork(session, mapper)`, then
`get` the root, change it, `add` it and `commit`. A commit made on stale data raises `Conflict`.
See xref:howto/adopt.adoc#session[step 8].

*Can I save several aggregates at once?*::
Yes. Add, change and `remove` the roots in one `UnitOfWork` and call `commit()` once: all are
stored or none is (a root is the root object of an aggregate), and a stale root raises `Conflict`
whose `iris` is a diagnosis of the roots that moved (xref:howto/commits.adoc#diagnosis[it can be
incomplete]).
`work.version(iri)` gives a root's version token. For triples, use `async with
session.transaction()`. A commit that used to leave the first roots written after a conflict now
leaves nothing. See xref:howto/adopt.adoc#transaction[Save several aggregates at once] and
xref:architecture/data-flows.adoc#commit[how the commit works]. One commit holds at most 500
roots by default (`max_roots`); more raises `CommitTooLarge`, and `commit(batches=True)` takes them
in several transactions (see xref:howto/adopt.adoc#transaction-batches[Save more than 500 aggregates]).

*Can two aggregates share a key value?*::
Not if the model forbids it. Declare a `unique_keys` entry on the root with
`rp_unique_scope: tenant`, and a commit that claims a value another aggregate of the tenant (of
the same type) holds raises `KeyConflict`, a 409 `key-conflict`, and writes nothing. See
xref:howto/adopt.adoc#key-conflict[Keep a value unique across aggregates] and, for data that
already has duplicates, xref:howto/adopt.adoc#key-on-live-data[Add a key to live data].

*What happens when two people edit the same thing?*::
The second commit is refused: every aggregate has a version token that changes on every write, and
a commit is stored only if each root it changes is still at the version it read and each new root
does not exist yet. Nothing is
overwritten silently, and nothing of the refused commit is written (bar the rare false conflict of a
removes-only commit). See
xref:howto/commits.adoc[How commits and conflicts work].

*Why did my commit raise `Conflict`?*::
Another writer changed (or removed) a root you change since you read it, or a root you add already
exists. Nothing was written (rarely, a false conflict; read again to see the truth).
`conflict.iris` and the message name the roots. Read them again in a
new unit of work, apply your edit if it still makes sense, and commit; the toolkit never retries
for you. See xref:howto/adopt.adoc#handle-a-conflict[Handle a conflict] and
xref:howto/commits.adoc#conflict[what a conflict means].

*How do tenants and access work?*::
Each tenant has its own database and bucket, and an access record in the system database that
holds its grants and prohibitions. The caller who creates a tenant gets the settings'
`creator_role` on it. Every tenant route checks the caller's token, then its access, before it runs. See
xref:howto/adopt.adoc#tenancy[step 9], xref:howto/adopt.adoc#access[step 11] and
xref:architecture/access-control.adoc[Access control and identity].

*Where is my data stored, and what happens when I create, read, replace or delete it?*::
Each tenant's aggregates are named graphs in its own database, beside a `meta` graph (the tenant's
root) and a `registry` graph (which graph belongs to which aggregate); its files are in its own
bucket; its access record is in the system database. Every write checks the token, the caller's
access, the IRI policy, the body and the version before it writes; an aggregate is written in one
SPARQL update. See
xref:architecture/data-flows.adoc[Where data lives and what each operation does].

*How does my UI know which buttons to show?*::
Read the `Allowed-Actions` header of a tenant or of an aggregate (for example `read, modify`), or the
`allowed_actions` of the tenant's item in `GET /{tenant_segment}`. If your web app is on another origin,
expose the header in your CORS settings. See xref:howto/adopt.adoc#tenancy[step 9] and
xref:architecture/access-control.adoc[Access control and identity].

*How do I enforce my own rule on tenant writes, such as keeping one owner?*::
Pass `grant_validators` or `root_validators` to `install_service`. A validator raises
`InvalidBody` to refuse: the answer is 422 and nothing is written. See
xref:howto/adopt.adoc#validators[Enforce your own rules on tenant writes].

*How do I serve it over HTTP?*::
Call `install_service` once in your composition root, with your FastAPI app, the schema, the
generated package, the four adapters, the role definitions and a `ServiceSettings`. It returns a
`ServiceKit` for your own routes. See xref:howto/adopt.adoc#serve[step 12] and
xref:architecture/api.adoc#serving[Serving it].

*How do I read back a graph I loaded?*::
Check the read with `kit.require_aggregate(..., Action.READ)`, then call
`session.loaded_graph(root_iri, graph_iri)` for a plain rdflib `Graph`. If a later request does not
hold `graph_iri`, `session.loaded_graphs(root_iri)` lists the aggregate's loaded graphs. The session
checks no access itself. See xref:howto/adopt.adoc#files[step 10].

*How do I check that a name is not taken yet?*::
Call `session.find(Scan, file_name=name)` and answer 409 when the list is not empty. `find` ignores
Prohibitions, so check each IRI with `require_aggregate` before you show it to anyone. See
xref:howto/adopt.adoc#files[step 10].

*Who points at this resource?*::
Check the caller with `kit.require_aggregate(..., Action.READ)`, open `kit.collaboration(checked)`
and call `collab.referrers(iri)`. It lists the aggregates whose slots hold that IRI, one item per
referrer and slot, with the class and slot names; `class_name` and `slot` narrow it. Referrers the
caller may not read are counted in `hidden_count` and never named. It only informs: a delete is
never refused because of referrers. See
xref:howto/reverse-references.adoc[Find who points at a resource].

*How do I group resources I do not own?*::
Mix `ReferenceCollection` (module `rp_collections`) into an aggregate root of your schema. It then
names its members by IRI in `had_member`, by a `membership_rule`, or both, and holds none of their
triples. Store the members before the collection: a save that names a member which is not stored,
or not of `member_class`, is refused. Read with `collab.members(iri)` and
`collab.collections_of(iri)`; `collab.delete_cascade(iri, if_version)` deletes the collection with
its members, all or nothing. See
xref:howto/reference-collections.adoc[Group resources you do not own].

*Can a reviewer comment without editing?*::
Yes. Import the module `rp_discussion` and give the reviewer's role the action `annotate`, which
is not `modify` and does not imply it. `collab.comment(iri, text)` stores a comment as an
aggregate of its own and leaves the target and its version untouched; `collab.thread(iri)` reads
the comments the caller sees, oldest first. A comment may be limited to an audience of roles,
answer another comment, and reference other aggregates. Deleting an aggregate deletes the
comments on it. See
xref:howto/discussion.adoc[Comment on a resource without editing it].

*How do I put a resource through review?*::
Give its class a workflow: a YAML file of states and transitions, each transition with the roles
that may make it. Mix `UnderWorkflow` (module `rp_workflow`) into the aggregate root, name the
workflow in the class annotation `workflow`, and pass the file to `install_service` with
`workflows=`. A new aggregate starts in the initial state; a plain write cannot change the state.
`collab.transition(iri, to, if_version=...)` moves it, if the caller holds one of the transition's
roles, and records the move; `collab.transitions(iri)` reads the history. See
xref:howto/workflow.adoc[Put a resource through review].

*How do I make my own IRIs?*::
Describe their shape as an `IriPolicy`: a template for the tenant, the aggregates, the owned parts
and the loaded graphs (for example `{base}{tenant_id}/{type}/{id}`) and the rule for each id (a
UUID, or so many random characters), and set it on `ServiceSettings.iri_policy`. The service then
mints, checks and reads back every IRI by the policy, and the API paths follow the last segment.
The access, meta and registry graphs and the principal IRI keep their defaults for now. See
xref:howto/adopt.adoc#iri-policy[step 14].

*Why does my file root answer 405 on PUT?*::
A root that includes `StoredFile`, or carries the class annotation `rp_writes: service`, is written
only through a session: the router serves its `GET` and listing but not its `POST`, `PUT` or
`DELETE`, because the record and its bytes must change together. Write it in your own route with
`kit.session(...)`, a `UnitOfWork` and `kit.files`. See xref:howto/adopt.adoc#files[step 10] and
xref:architecture/api.adoc#serving[Serving it].

*How do I clean up orphans in a live tenant?*::
Run `kit.sweep_tenant(tenant)` as an operator command. It finds the loaded graphs no commit owns
and the blobs no `file_key` names, older than one hour, and changes nothing unless you pass
`remove=True` (graphs) or `remove_blobs=True` (blobs). Pass `remove_blobs` only when every blob key
is stored in `file_key`. Delete a file aggregate with `kit.remove_with_files`, which removes its
blobs too. See xref:howto/adopt.adoc#sweep-live-tenant[Sweep a live tenant].

*How do I back up or copy a project?*::
Call `kit.dump_tenant(tenant, out)` to write the tenant's graphs (as N-Quads) and files to one
archive, and `kit.restore_tenant(src, creator)` to create a new tenant from it, with a new id and
new IRIs. The restorer alone gets the creator role; grants are not dumped. The archive must come
from the same schema version and IRI policy, and the graphs are held in memory. See
xref:howto/dump-restore.adoc[Back up or copy a project].

*How do I test my application with the testkit?*::
Use `FakeStore`, `FakeFileStore` and `FakeIdentity` in place of the adapters, `fake_session` for a
domain service, and `TokenSigner` with `JwksTokenVerifier` for tokens, all from
`rdf_persistence.testkit`. Add the freshness plugin and the model guards to your test suite. See
xref:howto/adopt.adoc#guard[step 6] and xref:howto/adopt.adoc#test-service[step 13].

== Developing the toolkit

*How do I change a toolkit schema?*::
Edit the schema under `rdf_persistence/model/` (or `rdf_persistence/model/service/rp_service.yaml` and
`rdf_persistence/generation/model/rp_generation.yaml`), run
`make generate`, refresh the model-shape snapshot if a class changed, and commit the schema and the
generated code together. See xref:develop/index.adoc#change-a-toolkit-schema[Change a toolkit
schema].

*How do I add a generator extension or a check rule?*::
An extension is a module in `rdf_persistence/generation/extensions/` with a `render` function, a
step in `steps.py`, a row in the extensions table and its own test against the toy library. A
check rule is a value in `rp_generation.yaml`, its code in `checks/` and two test schemas. See
xref:develop/index.adoc#add-or-change-a-generator-extension[Add or change a generator extension]
and xref:develop/index.adoc#add-a-check-rule[Add a check rule].

*Which tests do I run while developing?*::
`make test-changed`: it runs the tests of the files you changed against `develop`, in a few seconds to a minute. When
you are unsure what a change reaches, run `make test-fast` (about 3 minutes). `make check-all`
comes once, before the PR. See xref:develop/index.adoc#make-targets[Make targets] and
xref:develop/testing.adoc#slow[Slow tests].

*How do I run the checks, and how long do they take?*::
`make check-all` before every PR (about 6 minutes), and `make test-containers` when you touch
adapters or containers (about 3.5 minutes, needs Docker). See
xref:develop/index.adoc#how-long-the-checks-take[How long the checks take].

*How is a release cut?*::
release-please proposes it as a PR into `develop` from the Conventional Commits; you move the
changelog entries under the new version, merge the release PR, and fast-forward `main` to the tag
by hand. See xref:develop/index.adoc#release[Cutting a release].

*How do agents work on this repository?*::
By skillery's delivery method (the `epic-delivery` skill): a shaping session that ends in EPICs,
then one epic session per EPIC, where the lead runs a small team through a loop that scales with
the size of the EPIC, and the developer decides. What is specific here (the rules every brief
carries, the gates, the release) is on xref:develop/agents.adoc[Working with agents]; every test
follows the xref:develop/testing.adoc[testing checklist].

*How do we keep review and checking from doubling the work?*::
The adversarial tester runs right after the riskiest task, lenses L4 and L5 are one review pass,
and the checker trusts the lead's full-suite run. See
xref:develop/agents.adoc#challenge[Keeping the challenge cheap].

*Why does a Bash command fail with "Polling loops are blocked"?*::
A hook denies `sleep` loops so agents stop waiting on their own background runs. Run the command in
the foreground, in the background with its notice, or use the Monitor tool. See
xref:develop/agents.adoc#never-poll[Never poll].

*Where are decisions recorded?*::
Architecture decisions are on xref:architecture/open-decisions.adoc[Decisions of 2026-11-05] (D-1
to D-13) and in xref:architecture/index.adoc#decisions-taken[architecture v1] (O-1, O-2). The
decisions of the work in progress (PD-1 and on) are in `openspec/changes/<id>/design.md`; once a
change is archived, its requirements live in `openspec/specs/` and the change itself, decisions
included, in `openspec/changes/archive/` (toolkit v1: `2026-11-06-toolkit-v1-foundation`).

== What to expect, and the choices you make

=== Guarantees

*Generated code is fresh.*::
`rp-generate --check`, and the testkit's freshness plugin, fail when generated code is stale or was
edited by hand, and name the files. See
xref:architecture/generation.adoc#guarding[Guarding the generated code].

*Nothing drifts from the model.*::
`assert_models_generated` fails on a hand-written model class; the file guard fails on shapes,
contexts, schemas or TypeScript outside a `generated` folder. LinkML stays the one source.

*Classes and shapes agree.*::
`conformance_problems` checks every case against both the generated class and the generated shape, and
fails until every constraint kind your schema uses has a case. See
xref:howto/adopt.adoc#guard[step 6].

*No lost update.*::
Every write to an aggregate is guarded by its version: `If-Match` over HTTP, the version read by a
`UnitOfWork` in code. A stale write is 409 or `Conflict`, never a silent overwrite.

=== Limits and behaviours you will meet

*Status codes.*::
401 without a valid bearer token; 404 for a tenant or aggregate you may not see, and for one that
does not exist (they answer alike); 403 when you may see it but not act; 409 on a stale version;
428 when `If-Match` is missing; 413 for a body over `max_body_bytes` or over 10 000 objects and
list values; 415 and 406 for media types; 422 for an invalid body; 400 for a bad query string;
503 when the store or the identity provider is down; 500 `internal-error` for a fault of the
service. Only 400, 406, 413, 415, 422 and 428 carry a `detail`. See
xref:architecture/api.adoc#serving[Serving it].

*Strict bodies.*::
A plain-JSON body may use only its class's slot names and the JSON-LD keywords. Only the root and
the owned parts reached from it may appear. A create may not name an `id`; a replace may not name
another one. An IRI that SPARQL cannot carry (a space, `<`, `>`, a quote) is 422 in a body and 400
`bad-query` in a listing filter.

*Internal slots.*::
A slot annotated `internal` (a file key, a database name) is refused in any body, also in the body
that creates a tenant, and never shown in a response. A replace keeps the stored internal values of
the root and of the parts that persist, matched by IRI; a part sent without its IRI is a new
part, by design, so it has none to keep.

*What the toolkit refuses.*::
At generation: a schema without titles, descriptions or IRIs, LinkML `rules`, `all_of` and
`none_of`, and a domain module that imports an access module. At run time: an aggregate IRI the
toolkit did not mint, a remote JSON-LD context, a grant on a target outside the tenant, and a
grant of a role that is not defined at the target's level.

=== Decisions you make

[cols="2,4,2",options="header"]
|===
|Decision |Trade-off |Default

|Schema layout and modules
|One file per aggregate keeps diagrams small and the boundary check precise. Access rules go in a
module annotated `module_kind: access`, which domain modules may not import.
|One root schema importing one file per module

|Aggregate roots and owned classes
|A root is one named graph, versioned and committed whole. An owned class lives inside its root's
graph and has no route of its own; anything another aggregate points to must be a root. Exactly
one class is the tenant root (`graph: meta`).
|A class is owned unless it needs its own lifecycle, routes or access

|Roles and the creator role
|Roles are data in a YAML file (`role`, `level`, `actions`). The creator of a tenant gets
`creator_role`; give that role `administer`, or only a global role can change the tenant's grants.
|None: the file and `creator_role` are required

|Zitadel settings
|The API accepts only JWT access tokens, so each Zitadel application is set to the JWT token type,
and clients ask for the project audience and roles scopes. `roles_claim` must match the provider
(`zitadel_roles_claim(project_id)`).
|None: `roles_claim` is required

|File store
|Each tenant gets a bucket, created and deleted with the tenant. The toolkit has no route for
file bytes: you write it, checked through the kit.
|A bucket per tenant always; the bytes route is yours

|JSON-LD or Turtle
|Plain JSON is the easiest for clients and is JSON-LD through the `Link` header. A JSON-LD body
brings its own inline context (a remote one is refused). Turtle is for reading one aggregate only:
no body and no listing takes it.
|Plain JSON

|The `openapi` switch
|`openapi = false` in `[tool.rp-generate]` skips `openapi-components.json`. A schema a service
serves needs it: `install_service` stops without it.
|`true`

|`max_body_bytes`
|Larger bodies cost memory and parse time; the 10 000-node cap applies whatever the size.
|1 MiB (1 048 576 bytes)
|===

== What could strengthen it in the future

These are possibilities, not commitments. Each is shaped as a candidate EPIC in
`openspec/changes/<id>/`, listed with a suggested order in `openspec/changes/README.md`. None is
planned: its PLAN waits for the decisions listed in its `inputs/seed.md`.

* *Detailed test profiling.* The check timings are rough; a profile of the slowest tests would show
  where the 5 minutes of unit and feature tests go.
* *A client library* over the generated TypeScript types and the OpenAPI document.
* *Events*: an outbox, an event bus and server-sent events, deferred until a need reacts to a
  change in another aggregate.
* *GraphQL*, read-only over the same schema and context (option C of
  xref:architecture/api.adoc[the API page]), *OpenFGA* as the decision engine, and property- or
  triple-level access.
* *A second store* (Oxigraph, Virtuoso) with a capability descriptor, and schema migrations.
