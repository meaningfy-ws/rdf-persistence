:description: A stack of Docker microservices around one shared triplestore: zero-code JSON:API from a domain file, an authorizing SPARQL proxy and change deltas. Our reference architecture.

== Purpose and origin

*Built for* building user-facing linked-data web applications fast: microservices that never call each other and integrate through one shared triplestore, with Ember single-page front ends.
Published as "An Ecosystem of User-facing Microservices supported by Semantic Models" (USEWOD 2015). In production in Flemish government applications (lblod "lokaal mandatenbeheer", Kanselarij Kaleidos, rollvolet).

*Who and in which context.* Aad Versteden (author in every `.asd` and `package.json`) and colleagues, first at TenForce, later at redpencil.io.

*Design angle.* Declarative configuration; cross-cutting concerns (identity, authorization, change events) live in proxies around the store.

*Where each component fits.*

[cols="2,4,2",options="header"]
|===
|Component |Built for |Layer

|mu-cl-resources |Removing "repetitive and boring" CRUD back-end work through declarative configuration: a generic JSON:API for ember-data. No domain objects (not L1). |L4, L0 format
|sparql-parser |A Common Lisp rewrite of mu-authorization: authorization moved "into a layer on top of the SPARQL endpoint", plus delta generation. It breaks request atomicity. |L3 PEP, L6, L2 replication
|delta-notifier |Fan-out of raw deltas to subscribers; no persistence, ordering guarantee or policy filter. |L6
|mu-identifier |Session identification at the edge and caching of access groups; no OIDC. |L3 edge
|mu-dispatcher |Request routing (Elixir DSL); any reverse proxy covers it. |L4 gateway
|Templates (Python, JS) |Quick-starting a service: framework, SPARQL client, header forwarding; no persistence layer, the gap rdf-persistence fills. |L1 seam
|===

As a library for a Python stack it fits nowhere: it is a runtime platform. Its contracts are the reuse value.

== How it works

*Request path.* Browser → identifier (session cookie → `MU-SESSION-ID`) → dispatcher (Elixir routing DSL) → mu-cl-resources (JSON:API ↔ SPARQL) → sparql-parser (authorizing proxy, served as `database`) → Virtuoso by default; sparql-parser talks to any SPARQL 1.1 endpoint, or several (`connection/client.lisp:9-53`).
sparql-parser also sends deltas to delta-notifier, which calls subscribers such as `resource/.mu/delta`.
The blueprint is `mu-project/docker-compose.yml`. Applications talk to `database`, so the proxy is transparent to them.

*Domain → API.* Resources are declared in `domain.json` or Lisp `define-resource` (`domain-parsing.lisp:54-147`, `resource-model.lisp:605`): `class`, attributes `{type, predicate}`, relationships `{predicate, target, cardinality, inverse}`.
On create, all supertypes are written; listings match `VALUES ?class { <subclasses> }` (`call-implementation.lisp:117-118, 318-320`).
Routes are fixed `defcall`s for list, item, create, patch, delete and relationship links (`call-specification.lisp:14-504`).

*Reads.* SPARQL is assembled with `format` strings (no AST).
Lists page over `DISTINCT ?uuid` with a separate, cacheable `COUNT` (`response-generation.lisp:15-108`).
JSON:API `filter[...]` paths compile to property paths (`:exact:`, `:gt:`, `:has-no:`, …; `response-generation.lisp:196-328`). `filter[:or:]` is *claimed, not found in code* (that part of the pipeline was not fully read).
`include=a.b` builds one VALUES+UNION query, avoiding N+1 (`included-items.lisp:371-395`).

*Writes.* Every resource carries a `mu:uuid` literal; the IRI is `new-resource-base` + UUID, and the client cannot choose it (`call-implementation.lisp:95-98`).
PATCH deletes and reinserts only the properties sent (`:157-176`). Delete removes declared properties and links, incoming declared links too; undeclared triples stay (`:847-929`).
`with-update-group` joins updates with `;` into one request (`query-execution.lisp:18-30`), but sparql-parser re-splits it into batches of roughly 100 quads or 8000 characters (heuristics, not hard limits; `handle-update-unit.lisp:3-7, 704-718`). No transactions, no optimistic locking.

*Authorization (sparql-parser).* Group membership is a SPARQL SELECT over session data; each row becomes an access token whose parameters extend a graph IRI (`acl.lisp:66-95, 243-247`).
Reads are *graph-level*: the proxy strips `GRAPH` and dataset clauses and adds `FROM` for each readable graph (`acl.lisp:249-263`).
Writes are *triple-level by pattern*: each quad goes to the graphs whose type/predicate spec it matches (`acl.lisp:301-439`). Quads matching no spec make the operation fail with an error before it is written (default `+*unwritten-data-actions* '(:log :error)+`, `handle-update-unit.lisp:697-700, 740-766`); earlier operations in the same request may already be stored.

*Deltas.* sparql-parser emits `changeSets` with `insert`, `delete`, `effectiveInsert`, `effectiveDelete`, `sequenceId`, `origin`, `allowedGroups` in SPARQL-JSON term encoding (`delta/messenger.lisp:36-116`).
delta-notifier matches pattern rules, batches, folds and retries (`app.js:19-86`, `folding.js:8-53`). mu-cl-resources consumes deltas to clear its caches (`call-implementation.lisp:1180-1300`).

*Templates.* Python (Flask + SPARQLWrapper) and JS (Express) give a raw SPARQL client that forwards the `mu-*` headers (`helpers.py:115-164`, `sparql.js:13-120`). There is no ORM; that gap is where rdf-persistence fits.

== What to borrow

* *The JSON:API dialect* of mu-cl-resources: URL shapes, `filter[...]` grammar, `sort`, `include`, `fields`, 0-based `page[number]`, `meta.count`. Speaking it lets existing Ember/JS front ends work unchanged. semantic.works has no JSON:API Atomic Operations; if we offer them, they are our extension of the dialect.
* *`domain.json` v0.1 as an import format.* It maps cleanly to LinkML (resource → class, attribute → slot, `super` → `is_a`); a converter is cheap.
* *`mu:uuid` + base-IRI identity* as an optional minting strategy, for data visible to both stacks.
* *The delta format* (`changeSets`, effective inserts/deletes, sequence ids) as the change-event schema, plus a Python delta consumer for cache invalidation.
* *Header propagation* (`mu-session-id`, `mu-call-id`, `mu-auth-allowed-groups`, `mu-auth-sudo`, `mu-auth-scope`) as a pluggable request context on the SPARQL adapter.
* *Per-property delete/insert* as the default flush strategy; *batched include* via VALUES+UNION.
* *Policy ideas from sparql-parser:* SPARQL-defined groups, parameterised graph templates, type/predicate write dispatch, caller scopes, delta-only virtual graphs (`:sparql nil :delta t`).
* *Authorization outside the persistence layer*, behind a SPARQL-protocol proxy.
* *Edge sanitisation of internal security headers:* mu-identifier deletes client-sent `mu-auth-*`, session and call-id headers from requests and responses and reissues the ones it owns from a signed, encrypted session cookie (`mu-identifier/lib/proxy.ex:23-34`, `lib/manipulators/clear_mu_internal_keys.ex:5-15`, `add_custom_request_headers.ex:7-47`). We would use an allow-list instead of its deny-list.

== What to avoid

* *No transactions.* The proxy re-batches writes; a partial write is possible (`handle-update-unit.lisp:704-718`).
* *Trusted headers from internal callers.* sparql-parser takes `mu-auth-allowed-groups` from the request without recomputing it, and `mu-auth-sudo` bypasses the ACL (`acl.lisp:175-212, 253`).
Browsers cannot inject these: mu-identifier strips browser-sent `mu-auth-*` headers at the edge and reissues the ones it owns (`clear_mu_internal_keys.ex:5-15`, `add_custom_request_headers.ex:7-47`).
The risk is *internal* callers: any container on the Docker network, or any service port published past the identifier, can send `mu-auth-sudo` or forged groups straight to sparql-parser. The JS template's sudo opt-in is a client-side courtesy, not enforcement (`helpers/mu/sparql.js:17-23`).
The strip list is a deny-list, so a future `mu-*` header would pass through; mu-dispatcher strips nothing security-related.
* *World-writable default:* the default config grants `(read write)` on the public graph to group `"public"`.
* *String-assembled SPARQL* throughout mu-cl-resources.
* *Whole-store integration* couples services through the vocabulary, against aggregate boundaries.
* *Virtuoso bias in the defaults:* custom boolean datatype, `virtuoso-p` binding expansion, long-string-to-file workaround. Other SPARQL 1.1 stores are not excluded.
* *Silent cache staleness* when a writer bypasses sparql-parser.
* *Python template flaws:* module-global SPARQLWrapper clients mutated per request; no sudo or scope.
* *Lossy deltas.* sparql-parser queues deltas in an in-memory bus, lost on restart (`delta/message-bus.lisp`, `messenger.lisp:63-90`); delta-notifier answers 204 before delivering (`app.js:39-40`) and retries 0 times by default (`send-request.js:95`). No replay, so caches and reactive services go stale. Not suitable as an outbox.
* *Docs drift.* `POST /people/<uuid>` is a doc error (code posts to the collection, `call-specification.lisp:87`). delta-notifier still points to the Elixir mu-authorization. `mu-auth-used-groups` is *claimed (for mu-authorization), not found in sparql-parser* (`connection/server.lisp`). mu-dispatcher's `RemoveAcceptEncodingHeader` matches `"accept_encoding"` with an underscore, so it never fires (`remove_accept_encoding_header.ex:8`): *claimed, not working in code*.

== Authorization seams

* *The seam is a SPARQL-protocol proxy*, invisible to services except through headers. It is the closest existing match to DEC-8's "ACL-agnostic persistence behind an authorizing proxy".
* *Granularity:* graph-level reads, triple-pattern writes. Triple-level read confidentiality must be modelled by splitting data into graphs at write time.
* *How a Python service on rdf-persistence plugs in:* point the SPARQL adapter at `database`; forward `mu-session-id`, `mu-call-id`, `mu-auth-allowed-groups` per request and copy the latter back to the response; support `mu-auth-sudo` (gated) and `mu-auth-scope`; never rely on `GRAPH`/`FROM` (they are stripped); expect HTTP 500, not 403, for denied writes; make write batching idempotent.
* *Generating the config:* `define-prefixes` and `define-graph` type specs can come from LinkML `prefixes`, `class_uri` and `slot_uri` plus an annotation per class or slot. Group queries and grants are policy, not structure, and must be authored separately.
* *Verdict:* integrate sparql-parser as an *optional* external PEP (DEC-5 exception needed); do not make it the default for MWBv2 (fails DEC-5, Common Lisp, trusts headers from internal callers, no OIDC/JWT, graph-level reads only). For V5 it is the existing graph-level read proxy.

== Code-generation fit

* The domain file is an API mapping read at boot, not generated code. An external OpenAPI generator exists (`cl-resources-openapi-generator`, *claimed, not analysed*).
* *LinkML → `domain.json`* is straightforward: class → resource with `class`, slot with `slot_uri` + range → attribute, object slot with `multivalued` and `inverse` → relationship, `is_a` → `super`, id prefix → `new-resource-base`.
* *LinkML → sparql-parser `define-graph`* is feasible for the structural part (see above).
* *Front-end models* (ember-data, TS types) are written by hand; generating them from the model is a gap (G16).

== Variant fit

See xref:background/soa/variants.adoc[variants]. The contracts (JSON:API dialect, `domain.json`, delta format, `mu-*` header protocol) support every variant; the runtime components are needed only for V2.

[cols="2,1,5",options="header"]
|===
|Variant / approach |Fit |Why

|V1 Portable Python core |supports |Contracts as one service profile, import format and outbox format; sparql-parser optional as a graph-level PEP; mu-cl-resources and the identifier block (Lisp, no domain rules, no OIDC).
|V2 semantic.works-compatible |enables |Requires the dialect, sparql-parser, identifier and dispatcher; rdf-persistence replaces the Python template.
|V3 Fluree |partly: contracts support; sparql-parser blocks |sparql-parser would duplicate Fluree's native policies; contracts still usable (deltas adapted from Fluree commits).
|V4 GraphDB |partly: contracts support; sparql-parser blocks |sparql-parser splits GraphDB transactions and duplicates its access control; contracts still usable.
|V5 Graph-direct reads |enables |sparql-parser is an existing policy-aware read proxy (graph-level only; fails DEC-5); deltas can feed a read replica.
|A Runtime mapper |supports |ACL-agnostic behind the header protocol; LinkML ↔ `domain.json` converter.
|B Generated mapper and routes |supports |Generated routes can speak the dialect.
|C Generic service |enables |mu-cl-resources is the archetype: a generic service read from a domain file at boot.
|===

== Final verdict

*Compatible.* Honour the contracts (JSON:API dialect, `domain.json`, `changeSets`, `mu-*` headers); run the runtime only for V2 (sparql-parser optionally as a graph-level PEP; DEC-5 exception needed); adopt no code.

. *Security sits at two perimeters.* The identifier sanitises the browser edge, but sparql-parser trusts any internal caller's `mu-auth-sudo` and group headers: in a semantic.works deployment, network isolation _is_ the authorization boundary.
. *There is no atomicity and no durable change log.* The proxy re-splits updates into batches and deltas are best-effort (in-memory, retry 0). All-or-nothing writes or reliable events need our own unit of work and outbox, or another variant.
. *The value is the contract, not the code.* Zero-code JSON:API from a model, policy-driven graph placement and proxy-emitted deltas are the patterns to reproduce in Python/LinkML; reproducing the mu dialect exactly (UUID ids via `mu:uuid`) is the price of Ember compatibility.
