== Purpose and origin

* *Built for:* giving Python application developers a SQLModel-like ORM over RDF: Pydantic entities, a `with Session()` workflow, a fluent query builder and FastAPI helpers. README tagline: "The SQLModel of SPARQL"; targets: "knowledge-graph and metadata apps".
* *Who and when:* one author (GitHub `eddiethedean`; pyproject author "SparqlModel Contributors"). Released 2026-05-16 → 06-01 in a roadmap-driven burst (milestones in `docs/ROADMAP.md`, a "1.3 GA gate" checklist in `SPECS.md`). Built on the same author's triplemodel with opt-in Fuseki integration tests (`tests/conftest_fuseki.py`, not run in CI).
* *Design angle:* developer-experience-first and app-centric. The model lives in Python code. It is a single-process, single-writer design whose client-side mirror stands in for transactions and server round-trips. Not model-driven (no LinkML or ontology input) and not standards-driven (no SHACL, no named graphs).
* *Where it fits:* L1, L2 (partial) and L4 (partial). As a dependency it fits nowhere: it fails DEC-5 (0 stars, dormant), the mirror conflicts with DEC-8, and it does not build on rdflib (DEC-4). As an idea source it fits our L1 API surface (session, query DSL, depth loading, composition versus reference) and our L4 FastAPI glue.

== How it works

*Mapping.* Entities subclass `SPARQLModel`, a Pydantic model that subclasses triplemodel's `TripleModel`.
`Field("schema:name")` stores the predicate in Pydantic field metadata (`fields.py:26–33, 80–116`).
`Relationship(cascade=True)` means composition; `cascade=False` means a by-IRI reference (`fields.py:119–175`).
Triples are produced and parsed by triplemodel (`rdf_bridge.py`). One predicate per field is enforced (`model.py:79–96`).

*Identity.* `id: IRI | None`; a missing id is minted as `urn:uuid:<uuid4>` (`model.py:144–149`).
The identity map is keyed by `(class, IRI)` (`session_state.py:13–29`).

*Session.* `put()` writes immediately by default; only `put(flush=False)` queues (`session.py:250–263`).
`flush()` replays the queue; writes already sent stay in place on failure (`session.py:136–150`).
The class docstring says so: "Already-flushed writes are not rolled back" (`session.py:39–41`).

*Update strategy.* `put` deletes the "owned triples" (`rdf:type` plus mapped predicates) of the root and of each cascaded or orphaned child, then inserts the new graph (`session_core.py:196–210`, `graph.py:249–287`).
Triples on unmapped predicates survive.

*Querying.* A metaclass `__getattr__` returns `FieldRef` objects, so `Person.name == "x"` builds an AST (`model.py:25–38`, `expressions.py:44–110`).
`compile_where` turns it into `SELECT DISTINCT ?root` by string concatenation, with `OPTIONAL`, `NOT EXISTS`, `VALUES`, polymorphic types, ordering and paging (`compiler.py:773–898`).
Hydration is N+1: one `get_impl` per row, each possibly one CONSTRUCT over HTTP (`session_core.py:309–324`).

*Stores.* `MemoryStore` runs on pyoxigraph. `HttpStore` and `AsyncHttpStore` send `INSERT DATA` / `DELETE DATA` over httpx with retries on 502/503/504 (`http_common.py:59–71, 135–165`).
They keep a *local pyoxigraph mirror* that serves `get`, cascade and orphan detection (`http.py:24–47`).
Writes never carry a `GRAPH` clause (`http_common.py:290–301`).
DELETE and INSERT chunks go as separate POSTs, so a remote `put` is not atomic (`http.py:287–298`).

*Async.* Sync and async facades share one core (`session_core.py:478–595`).

== What to borrow

* The SQLModel-style surface: `with Session() as s`, `put/get/delete`, `Model.field == x` through metaclass `FieldRef`, and `.where().order_by().limit().all(depth=n)`.
* Owned-predicate updates: replace only mapped predicates and `rdf:type`; leave foreign triples alone (`graph.py:265–287`).
* Composition (`cascade=True`) versus reference (`cascade=False`) as the aggregate boundary, with orphan cleanup that protects shared references (`graph.py:153–208`; computed from the local graph, so incomplete under `HttpStore`, where an external referrer can be missed).
* Explicit `depth` eager loading instead of lazy proxies; predictable over HTTP.
* Sync and async facades over one shared core.
* Explicit open-world query switches (`use_not_exists_for_ne` and friends, `query_common.py:31–42`).
* FastAPI `SessionDep` and Accept-based Turtle/JSON-LD negotiation (`fastapi/__init__.py:72–149`).
* Actionable errors, e.g. `ConfigurationError: Person maps multiple fields to the same predicate` (`model.py:91–96`).

== What to avoid

* *Non-atomic remote writes.* Separate POSTs per chunk; a failure in the middle leaves the store half-updated and the mirror diverged (`http.py:287–298`).
* *A cache treated as truth.* `get`, cascade and orphan detection read the mirror; other writers are invisible; `sync_mirror()` reloads the whole default graph (`http.py:165–186`).
* *N+1 hydration* and an *O(N) full-graph scan* per orphan candidate (`graph.py:153–167`).
* *String-built SPARQL* (about 900 LOC compiler, custom escaping): a correctness surface. Literals are escaped and IRIs validated (`sparql_escape.py`); the real injection exposure is raw `execute()`, which has no parameter binding.
* *Stores that disagree:* `MemoryStore` returns `str(term.value)` (`memory.py:100`), `HttpStore` returns `term.value` (`sparql_json.py:53`).
* *Identity keyed by class:* one IRI under a parent and a subclass gives two objects (`session_state.py:22`).
* *A session that looks transactional* but is not.
* *Docs drift.* `docs/SPECS.md:349` describes a possible one-request DELETE+INSERT that the code never does (it always sends separate POSTs). SHACL via `triplemodel[shacl]` is *claimed, not found in code*: triplemodel removed that extra in 0.11.

== Authorization seams

* *Proxy-friendly SPARQL.* Plain `INSERT DATA` / `DELETE DATA` and `SELECT` / `CONSTRUCT`, with no `GRAPH` clauses. A graph-dispatching proxy (semantic.works style) breaks nothing; `rdf:type` travels with creates.
* *Identity propagation* is possible through `HttpStore(headers=, bearer_token=, client=)` (`stores/http.py:57–61, 88–104`), but only per store instance, not per request.
* *Blockers.* The FastAPI lifespan shares one store and one mirror across all requests (`fastapi/deps.py:85–92`), so data fetched for user A can be served to user B. A partial, ACL-filtered view also makes the owned-triples delete set wrong. A proxy that denies one chunk leaves a partial write.
* *Where a PEP would go.* Wrap `StoreProtocol.query/update_graph` (`stores/base.py:10–21`), or inject a filter into `QueryState.expressions` (`query_common.py:31`). Mirror reads bypass both; `mirror_mode="remote_authoritative"` with one store per request is the minimum.
* *Verdict.* The GRAPH-free statement style is borrowable; the mirror design is incompatible with DEC-8.

== Code-generation fit

*Feasible with a custom LinkML template.* The mapping is static and declarative:
`rdf_type` ← `class_uri`, `Field("pred")` ← `slot_uri`, `Relationship(model=, cascade=)` ← range plus `inlined`, `__prefixes__` ← `prefixes`, `X | None` ← `required`, `set[...]` ← `multivalued`, subclassing ← `is_a`.

Gaps for a generator:

* Entities must subclass `SPARQLModel`, so stock LinkML Pydantic output cannot be reused.
* `list[...]` means `rdf:List`; multivalued slots must become `set[...]`.
* `list[SPARQLModel]` (inlined multivalued objects) is unsupported.
* No hook for LinkML identifier patterns (`id_prefixes`, `structured_pattern`).
* No mapping for enums with `meaning:`, language-tagged slots or mixins; no SHACL hook.

== Final verdict

*Ideas.* Borrow the session/query developer experience and the composition-versus-reference cascade; never depend on it.

. Its `with SPARQLSession()` *is not a transaction*: `put` writes immediately, and remote writes are several non-atomic POSTs.
. `HttpStore`'s *shared local mirror is treated as truth*: it leaks data across users behind an authorizing proxy and makes cascade and orphan logic wrong under other writers.
. Its best idea is the *API shape*: `Model.field == x` expressions, explicit `depth`, owned-predicate `put`, and `cascade=True/False` as the aggregate boundary. Re-implement that shape over a persistence-free LinkML model and a single-request atomic store port.
