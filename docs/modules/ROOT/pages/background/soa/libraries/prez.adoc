== Purpose and origin

*Built for* publishing authoritative vocabularies, catalogues and spatial datasets as a read-only Linked Data API ("data-configurable Linked Data API … Content Negotiation by Profile", README:8; "read-only access", `config.py:85`).
Deployed for geological surveys and government agencies (Australian ones such as GSQ, GSWA and ICSM, and the British Geological Survey) and the OGC/AGLDWG ecosystem, judging by Kurrawong's public Prez UI themes (deployment evidence, not a user list); standards-aware clients and the Prez UI consume it.

*Who and in which context.* The RDFLib team with Kurrawong AI (authors in `pyproject.toml:4`), driven by data-publishing projects. The demo stack runs on Fuseki.

*Design angle.* Publishing-first, configuration over code: everything about the response shape lives in RDF (profiles, endpoints). Strict on standards (connegp, OGC API, CQL2).

*Where it fits.* L4 read side with L2 read adapters, and only as ideas. It fails DEC-5 (40 stars), and has no L1 domain, no writes and no L3 identity, so it cannot be the data-management service in any variant.
At most it could sit beside one as a public read-only publication endpoint, which needs a DEC-5 exception.

== How it works

*No domain objects.* Data stays as rdflib `Graph` or pyoxigraph `Store` end to end (`repositories/base.py:36-75`).
"Mapping" is the choice of triples to CONSTRUCT, driven by profile NodeShapes (`services/query_generation/shacl.py:135, 184, 256`).

*Repository port.* `Repo(ABC)` (`repositories/base.py:16-80`) has five read methods and three adapters: `RemoteSparqlRepo`, `PyoxigraphRepo`, `OxrdflibRepo`, plus a test double.
`get_data_repo` picks one from `settings.sparql_repo_type` via FastAPI `Depends` (`dependencies.py:124-148`). A separate pyoxigraph *system repo* holds profiles and endpoint definitions.

*Query generation.* `PrezQueryConstructor(ConstructQuery)` (`umbrella.py:64`) builds `CONSTRUCT { profile triples } WHERE { { SELECT ?focus_node … ORDER BY … LIMIT … OFFSET } profile patterns }` from typed grammar objects, not strings.
CQL2 JSON filters compile to SPARQL (`query_generation/cql.py`); facets and capped counts (">N") come from `facet.py` and `count.py`.

*Content negotiation.* `NegotiatedPMTs` (`connegp_service.py:97`) reads `_profile`/`_mediatype` then `Accept`/`Accept-Profile`, ranks profiles by class distance over `rdfs:subClassOf*` (`:358-441`), and emits `Link` headers for alternates (`:304`).
Renderers serialise Turtle, N-Triples, RDF/XML, JSON-LD, annotated `+anot` variants with labels, and GeoJSON (`renderers/renderer.py`).

*Routes.* FastAPI routers (`prez/routers/`), OGC API Features, and routes generated at runtime from RDF endpoint definitions (`custom_endpoints.py:206`).

*No writes.* `/sparql` accepts only a `query` form field (`routers/sparql.py:24-35`); `sparql_endpoint` is documented as read-only (`config.py:27`). No sessions or transactions.

== What to borrow

* *A repository port with three adapters* (remote SPARQL, pyoxigraph, oxrdflib) chosen in one DI function. Maps onto a cosmic-python store port; we add the write half.
* *A typed SPARQL AST* (`sparql-grammar`) instead of string templates (Q7). Evaluate as dependency or design reference.
* *Profiles as SHACL NodeShapes* defining a resource "view": the RDF analogue of an aggregate boundary, usable for the CONSTRUCT of `get()` and the triple set of `delete()`.
* *CONSTRUCT around a paged inner SELECT* for listings (`umbrella.py:64`); LDkit uses the same pattern.
* *Content negotiation by profile* and *annotated representations* (`+anot`) for the later JSON-LD middleware.
* *Pagination contract:* `page`/`limit`/`offset`, mutual exclusion with a clear 400, capped counts (`models/query_params.py:131-260`).
* *Query observability:* fingerprint and timing per store call (`remote_sparql.py:21, 86-100`); no OpenTelemetry spans or `traceparent` (D29 partial).

== What to avoid

* *An app, not a library:* `settings` globals are imported everywhere (`remote_sparql.py:286`), so pieces cannot be reused alone.
* *Git-pinned runtime dependencies* (`pyproject.toml:33-34`): a supply-chain and packaging risk if we depend on `sparql-grammar`.
* *Ambiguous governance* (RDFLib versus Kurrawong).
* *Store-specific search* (Jena Lucene/FTS) creeping in through config.
* *Permissive defaults:* CORS `allow_origins=["*"]` (`app.py:282-289`); the optional `/sparql` passthrough bypasses every Prez-level check.
* *Docs drift:* the GitHub page says the SPARQL endpoint "accepts POST requests, so users … could update the store". *Claimed, not found in code*: only `query=` is forwarded.

== Authorization seams

* *Present:* one service account to the store (basic auth, `dependencies.py:66-75`); the trusted-proxy gate (AZ23), a static shared-secret header for "only through my proxy" deployments (`middleware.py:200-209`); request correlation ids, not forwarded to the store.
* *No identity forwarding.* No end-user identity is read or forwarded to the store (`remote_sparql.py:79` sends only `Accept`). Its authorization contribution is the typed-query seam (AZ3, where a PEP could inject filters) and the trusted-proxy gate (AZ23), nothing more.
* *PEP sites:* (1) a FastAPI dependency that validates an OIDC JWT and asks an external PDP; (2) a `PolicyRepo(Repo)` decorator that forwards the user token or rewrites queries; (3) the typed AST, where a PEP can safely inject `FILTER`/`VALUES`/`GRAPH` on `?focus_node`.
* *Behind a proxy:* good fit, since data queries use no `GRAPH` clauses; but per-user credentials cannot be forwarded today.

== Code-generation fit

*Medium.* LinkML `gen-shacl` emits the NodeShapes that profiles reference. A thin generator could wrap classes into `prof:Profile` resources and derive endpoint hierarchies from class containment.
Profiles need data LinkML does not hold (formats, default profile), so `annotations:` or a side config is needed.

== Final verdict

*Ideas.*

. Prez is a *read-only publishing app*, not a library. It can never be the data-management service or carry writes, and it fails DEC-5 (40 stars).
. What is worth taking is *design*: a `Repo` port with three adapters, the typed SPARQL AST (the safest place for a query-rewriting PEP), CONSTRUCT around a paged SELECT, connegp by profile, and capped counts and facets.
. Prez has *no per-user identity* (one basic-auth service account; CORS `*`; the optional `/sparql` passthrough bypasses Prez). Behind any authorising design, treat it as "sees everything".
