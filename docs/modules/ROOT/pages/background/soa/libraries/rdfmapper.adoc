:description: A small decorator-based Python mapper with Spring-Data-style finders and SHACL generation over one rdflib Graph; no persistence, injection-prone queries.

== Purpose and origin

* *Built for:* getting a Python object model into RDF for research ETL pipelines without writing triples. It is the packaged successor of LambdaGeo's `simpot` (2022), used in `dbacademic-etl` to turn Brazilian academic open data into knowledge graphs (`docs/background.md`).
* *Who and when:* Felipe dos Santos Goiabeira's bachelor's thesis at UFMA (2025), advised by Sergio Souza Costa (LambdaGeo group). A JOSS-style paper is in the repository (`paper.md`); the 2026-09 date is only the latest commit.
* *Design angle:* JPA / Spring Data familiarity for non-Semantic-Web developers: annotations, derived finders, SHACL as a bonus. It *serialises* objects into a graph for one-way ETL rather than *persisting* them. That is why update, delete, identity and stores are missing: the use case never needed them.
* *Where it fits:* nowhere as a component. In L1 it would collide with our LinkML/Pydantic chain, because it needs hand-written decorated classes. It is an idea donor for L1 query convenience (Q8 derived finders) and L0 SHACL emission (which LinkML `gen-shacl` already covers). It fits no variant V1–V5 as a dependency and fails DEC-5 (0 stars).

== How it works

*Mapping.* Decorators (`@rdf_entity`, `@rdf_property`, `@rdf_one_to_one`, `@rdf_one_to_many`) turn getter stubs into `property` objects carrying ad-hoc attributes (`_rdf_predicate`, `_min_count` …) (`mapper.py:57–142`).
The decorated body is discarded. Getters read `self._<name>`, so users hand-write an `__init__` that sets backing fields.
Discovery scans `dir(obj)` for properties (`mapper.py:217–223, 292–298`). The class registry `_entities` is written but never read (`mapper.py:53`).

*Identity.* Objects must carry a `uri` (`mapper.py:207`); no minting, no blank nodes.
`from_rdf` bypasses `__init__` and uses a per-call `visited` dict as identity map and cycle breaker (`mapper.py:280–290`).

*Relationships.* 1-1 via `graph.value`, 1-n via `graph.objects` into an unordered list (`mapper.py:300–311`). No inverse.
Loading is eager over the whole reachable graph; `to_rdf` cascades every related object (`mapper.py:226–233`).

*Literals.* A hard-coded chain for bool, int, float, datetime, date and str (`mapper.py:148–179`). No language tags, no custom datatypes, no `Decimal`.

*Writing.* `to_rdf` always builds a new `Graph` (`mapper.py:206`). Storing means `graph += mapper.to_rdf(obj)`: additive only, no update or delete.

*Querying.* `RDFRepository.__getattr__` parses finder names (`repository.py:42–90`) and builds SPARQL by f-string interpolation of user values (`repository.py:146–152, 206`).
It runs on `rdflib.Graph.query`, then calls `from_rdf` per row: N+1 (`repository.py:167–170`).
`limit` / `offset` come without `ORDER BY` (`repository.py:162–165`).

*Validation.* `to_shacl` emits one NodeShape per class with path, datatype and min/max count (`mapper.py:322–383`).
The shape namespace is hard-coded to `http://example.org/shape/` (`mapper.py:340`); relationship properties get a wrong `sh:datatype xsd:string` (`mapper.py:367–379`).
`validate` calls pySHACL with `inference="rdfs"` (`mapper.py:385–422`), only when asked.

== What to borrow

* *Derived query methods* (Spring Data style: `find_by_*`, `count_by_*`, `_and_`, `_like`), as an optional convenience on top of a typed query builder (`repository.py:42–90`).
* *SHACL from model metadata* (`mapper.py:322`). For us it should come from LinkML `gen-shacl`, which already does this job better.
* The per-call visited dict for cycle-safe hydration.
* Clear errors where they exist: `ValueError: 'city' is not a valid rdf_property` (`repository.py:261`).

== What to avoid

* *SPARQL injection.* User values are interpolated into queries (`repository.py:149–152, 206`).
* *Type-unsafe filtering.* Typed values compare as plain strings; `find_by_age(age=25)` presumably matches nothing, and no test covers it (`repository.py:152`).
* *N+1 hydration* after every finder, plus `dir()` scans on every conversion.
* *Unstable pagination:* LIMIT/OFFSET without ORDER BY.
* *Metadata stashed on getter functions*, `_attr` backing-field conventions, and `__getattr__` magic as the only query API.
* *Raw errors leak:* a finder typo gives `AttributeError: type object 'Person' has no attribute 'nme'` (`repository.py:138`).
* *Hard-coded shape namespace* and wrong datatype on relationship shapes.
* *Claimed, likely broken in code:* compound filters with non-string values (README, `docs/guide/querying.md`). The LICENSE file the README links is not in the repository.

== Authorization seams

* *ACL-agnostic only by accident.* Reads go through `rdflib.Graph.query`, `graph.value` and `graph.objects` (`repository.py:169`, `mapper.py:303–313`). A `Graph` backed by rdflib's `SPARQLStore` pointed at an authorizing proxy would be filtered transparently, at the cost of one remote request per property per object (`mapper.py:300–313`).
* Credentials are then fixed per Graph; there is no request context (X13 absent). Writes never reach a store.
* *PEP sites if one were added:* query level in `_find_by` / `_count_by` (`repository.py:96, 172`), fragile because of string building; field level in the `from_rdf` property loop (`mapper.py:292–314`).
* *Verdict:* no designed seam; do not borrow the approach.

== Code-generation fit

*Poor.* LinkML `gen-pydantic` output cannot be used, because rdfmapper needs plain classes with decorated property stubs and `_name` backing fields.
A custom `gen-python` Jinja template could emit `class_uri` → `@rdf_entity`, `slot_uri` → `@rdf_property`, range class → `rdf_one_to_*`, cardinalities → `minCount` / `maxCount`.

Still missing:

* inheritance (`is_a` → `rdf:type` / `subClassOf`);
* an `identifier` slot named `uri`;
* enums, language strings and multivalued literal slots;
* ordered lists.

== Final verdict

*Ideas.*

Three things to remember:

. *It is an ETL serialiser, not a persistence layer:* no update, delete, identity, transaction or store access, so nothing in it can carry rdf-persistence's L1/L2.
. *Derived finders (`find_by_x_and_y`) are the one idea worth keeping*, only as optional sugar over a typed, parameter-bound query builder; its own implementation is injection-prone and string-typed (`repository.py:146-152`).
. *SHACL-from-model belongs to LinkML `gen-shacl`* in the MWBv2 chain, not to a mapper; rdfmapper confirms the idea but adds nothing LinkML lacks.
