= Evolution, testing and operations
:description: Day-2 concerns for rdf-persistence: schema evolution and data migration, testing against real RDF stores, and operations (backup, observability, upgrades, licences).

[IMPORTANT]
.Background, not a commitment
====
This page is part of the state-of-the-art study moved from the rdf-persistence repository (commit `43dc152`). It records options and leanings, not decisions. What rdf-persistence commits to is in xref:architecture/index.adoc[rdf-persistence architecture v1].
====

== Purpose of the angle

This angle covers day 2: what happens after the first release.
It asks three things: how the schema and the data evolve together, how we test against real RDF stores, and what operating each variant costs.
It is cross-cutting: L0 (schema versions), L1 (data transformation), L2 (migration runner, store administration) and L4 (contract tests).

Deep dives with clone and GitNexus index: semantic.works' `mu-migrations-service`, `linkml-map`, Alembic (the mainstream benchmark) and `testcontainers-python`.
Existing clones read without re-indexing: LinkML, rdflib, Oxigraph, Fluree (docs only).

*Headline findings.*

. *Day 2 is the weakest part of the RDF ecosystem.* The only RDF-native migration runner is `mu-migrations-service` (2 stars, stale, fails DEC-5): a ~220-line loop that runs ordered `.sparql` and `.ttl` files once and records them as triples.
. *Nothing turns a LinkML schema diff into SPARQL Update migrations.* (KGCL with kgcl-rdflib edits ontology terms, not instance data, and fails DEC-5.) LinkML has no schema-diff command. `linkml-map` transforms objects and tables between schema versions; its advertised SPARQL CONSTRUCT compilation is *claimed, not found in code*.
. *Alembic shows the shape to copy:* a version record in the store, ordered revision scripts with up and down, and an autogenerate step that diffs and is then reviewed by a human. For RDF the diff must be model against model (old LinkML against new), because the store has no explicit schema.
. *Testing tools are mature and pass DEC-5* (testcontainers, pytest-bdd, schemathesis, pytest-cov, pySHACL), but *no testcontainers module exists for any RDF store*. Every RDF project hand-writes its fixtures.
. *Operations:* OpenTelemetry has no SPARQL semantic conventions, so SPARQL calls appear only as plain HTTP spans. Backups are store-specific. Two licences bite at operation time: Fluree BUSL-1.1 and Zitadel AGPL-3.0.

== Deep-dive findings

=== mu-migrations-service (semantic.works)

One Ruby file (`web.rb`, ~220 lines). All four GitNexus flows start at `boot` (`web.rb:214-219`): wait for the database, then run migrations. Commit `44cdbdf`.

* *Discovery and order:* globs `/data/migrations/**/*.sparql` and `*.ttl` (`web.rb:139-140`), sorted by the first integer in the filename (`web.rb:27-32, 143-146`). Identity is the filename only.
* *Version record in the store:* each run writes `muMigr:Migration`, filename and `executedAt` triples into the application graph (`web.rb:89-97`). "Already run" is an `ASK` or paged `SELECT` (`web.rb:42-59, 163-188`).
* *Execution:* `.sparql` is sent verbatim as one update (`web.rb:65-67`). `.ttl` is inserted in batches into a temporary graph, then `ADD <tmp> TO <target>` and `DROP SILENT` (`web.rb:105-133`). The target never holds half-loaded data, provided the store executes `ADD` as one atomic operation. Batch size halves on error (`web.rb:117-123`). A sibling `.graph` file names the target graph (`web.rb:71-76`).
* *Authorization:* runs as sudo (`mu-auth-sudo` header, `web.rb:3,12`), so migrations bypass the PEP by design (AZ16).
* *Gaps (confirmed in code):* no checksum (an edited migration is silently skipped); no down migration; the record is written in a separate request after the migration, so a crash in between re-runs a non-idempotent `.sparql`; no lock against two instances; no dry-run; no post-migration validation; no tests.

*Scores:* C3 3 · C4 4 · C5 3 · C7 4 · C8 1 · C9 4 · C10 2 (C1 n.a.).

*Verdict: borrow ideas* (fails DEC-5). Borrow file-per-migration with timestamp ids, the migration log as triples in an admin graph, staging graph plus `ADD` for Turtle loads, adaptive batch size. Fix in ours: checksum, lock, record in the same request, dry-run, SHACL gate.

=== linkml-map

CLI `linkml-map` with `map-data`, `compile`, `derive-schema`, `invert`, `validate-spec` (`src/linkml_map/cli/cli.py:72-694`). Commit `09667a6`.
The core is `ObjectTransformer.map_object` (`transformer/object_transformer.py:378`) and `Session.transform` / `reverse_transform` / `invert` (`session.py:125-150`).
GitNexus confirms the inversion path through `inference/inverter.py`, which raises `NonInvertibleSpecificationError` when a spec cannot be inverted.

* A declarative transformation specification of class, slot and enum derivations, with expressions, unit conversion and pivots (`datamodel/transformer_model.py:168, 296, 397, 477`).
* Compilers: Python, SQL/DuckDB, Markdown, Graphviz. Inputs and outputs: dicts, YAML, JSON, CSV, Parquet, DuckDB. *No RDF loader or writer.*
* The model promises "translation of the specification into SPARQL CONSTRUCTs" (`transformer_model.py:84`). *Claimed, not found in code:* no SPARQL compiler in `compiler/`.

*Scores:* C3 3 · C4 4 · C5 5 · C6 5 · C7 1 · C8 3 · C9 3 · C10 3 (0.5.x, deprecations in flight).

*Verdict: integrate (offline, optional)* for migrations that reshape aggregates (split or merge classes, unit conversion, enum remaps): read old aggregates through rdf-persistence with the old generated model, `Session.transform`, write with the new model.
`invert` gives a down migration for free when the spec is invertible. Not for bulk data (one object at a time).
A SPARQL compiler for linkml-map is a plausible upstream contribution.

=== Alembic (benchmark)

* *Version table in the target database:* `alembic_version` (`runtime/migration.py:182-202`); `stamp` marks a revision without running it (`:548-561`).
* *Revision graph with up and down,* heads and branches (`migration.py:701, 994, 1220`).
* *Optional transaction per migration* (`migration.py:140-141`).
* *Autogenerate:* `compare_metadata` / `produce_migrations` (`autogenerate/api.py:45, 171`) run per-object comparator plugins (`compare/tables.py:82, 232`), then render a Python script for review. Renames are not detected; they show as drop plus add.
* *Offline mode* renders a migration as SQL without running it (`migration.py:138-161`), and `alembic check` fails CI when the model has changes no migration covers (`command.py:320`). Both matter for EV2 (dry run) and the proposed EV10.

LinkML already carries the rename hint Alembic lacks: `deprecated_element_has_exact_replacement` (IAO:0100001 "term replaced by", `linkml_runtime/linkml_model/mappings.py:102-106`).

*Verdict: borrow ideas:* version record, revision ids, up and down, stamp, autogenerate-then-review, comparator plugins.

=== testcontainers-python

46 community modules, including `neo4j`, `arangodb`, `keycloak`, `openfga`, `vault` and `toxiproxy`. *No module for Fuseki, GraphDB, Oxigraph, Virtuoso, Fluree or Zitadel* (no hits in `src/` or `docs/`). Commit `6146aa1` (v4.15.0).
The generic blocks are enough: `DockerContainer` with HTTP or log wait strategies (`core/wait_strategies.py:56, 155`) and `DockerCompose` for a whole semantic.works-style stack (`compose/compose.py:197, 318, 569, 577`).
xref:background/soa/libraries/rdfproxy.adoc[rdfproxy] already uses this pattern for Oxigraph and Fuseki (`rdfproxy/tests/conftest.py:59-112`).

*Scores:* C3 4 · C4 4 · C8 5 · C9 5 · C10 4.

*Verdict: adopt* as the integration-test substrate. We ship our own thin fixtures for RDF stores. `toxiproxy` injects network faults, so degradation under T1 and T4 can be tested honestly.

== Schema evolution and data migration

*What exists.* No Python RDF migration runner (the .NET `Sparql.Migrator` is dead). No LinkML diff among its ~50 CLI scripts (`linkml/packages/linkml/pyproject.toml:157-207`). `robot diff` works on the `gen-owl` output; KGCL offers a change vocabulary.
LinkML carries `version`, `deprecated` and replacement hints. `gen-owl` emits no `owl:versionIRI`; the ODK/ROBOT pipeline usually stamps it.
Post-migration checks: SHACL from `gen-shacl` with pySHACL, or store-native SHACL (Fluree, GraphDB, Jena).
Rehearsal: Fluree history and branches (S16) let a migration run on a branch, be validated, then merged; RDF Delta gives a patch log for point-in-time replay on Fuseki.

*Can a LinkML diff generate SPARQL Update migrations?* Not today, but most changes are mechanical because the mapping is declarative.

[cols="3,4,1",options="header"]
|===
|LinkML change |Generated SPARQL Update (sketch) |Automatic?
|`slot_uri` changed (rename with `deprecated_element_has_exact_replacement`) |`DELETE +{?s old: ?o}+ INSERT +{?s new: ?o}+ WHERE +{?s a C; old: ?o}+` |yes
|`class_uri` changed |The same on `rdf:type` |yes
|Enum value `meaning` changed |`DELETE`/`INSERT` on the IRI object |yes
|New required slot with `ifabsent` |`INSERT +{?s p default}+ WHERE +{?s a C FILTER NOT EXISTS {?s p ?x}}+` |yes
|Slot removed |`DELETE WHERE +{?s a C; p ?o}+`: destructive, needs explicit confirmation |gated
|Multivalued → single-valued, range or datatype change |Needs a cast or selection rule |scaffold + human edit
|Class split or merge, reshaped aggregate |linkml-map spec (object level) |human-authored
|`required` tightened, pattern added |No data change; the SHACL report lists violators |check only
|===

Every generated script runs per named graph (or `GRAPH ?g`) and is validated afterwards with the new schema's SHACL shapes.

*How it plugs into MWBv2 and an ACL-agnostic rdf-persistence.*

----
LinkML vN-1 ─┐                ┌─> migrations/NNNN-<slug>.sparql (+ .down.sparql, reviewed)
LinkML vN  ──┴─ schema-diff ──┤
                              └─> SHACL(vN) gate ──> rdf-persistence migrate (runner)
                                                       │ uses the store port (SPARQL Update)
                                                       │ runs as a privileged service identity
                                                       ▼ log: triples in an admin graph
----

* The runner is an entrypoint (`make migrate`) calling a service over the same store port as the app. It works with any SPARQL 1.1 store and stays ACL-agnostic: it authenticates as a dedicated service principal that the PEP, proxy or store policy allows. No bypass inside the library.
* Approach B adds generated pieces: SHACL per version, migration skeletons, golden fixtures (see xref:background/soa/angles/codegen.adoc[code generation]). Approach A still needs the runner and the diff. Approach C needs the runner most, since nothing typed catches drift.

*Gaps.* No Python RDF migration runner; no LinkML diff; no LinkML → SPARQL migration compiler; no lock or checksum discipline anywhere in RDF; nobody versions data graphs against the schema version.

*Observability.* OpenTelemetry semantic conventions have no SPARQL entry (GitHub code search over open-telemetry/semantic-conventions, 0 hits, 2026-11-03). httpx instrumentation gives one HTTP span per SPARQL call, but no query kind, graph or row count.
Add a thin decorator on the store port: `db.system=sparql` (proposed value), `db.operation` (SELECT, CONSTRUCT, UPDATE), query fingerprint (S14), named graph, result size, and `traceparent` propagation (Fluree joins the trace natively).

*Performance pitfalls.*

* N+1 on relationship traversal: batch with `VALUES` (Q9).
* Unbounded `CONSTRUCT` for aggregates: stream (S13), page by subject.
* `COUNT` / `len()` on remote datasets: rdflib 8 makes `len(dataset)` count quads and may send one remote request per graph (`rdflib/docs/upgrade7to8.md:14-32`).
* `OFFSET` paging degrades on large graphs.
* Batch-size limits on Virtuoso (T11); the mu-migrations halving loop exists for this.

*Features from this angle* (v4 ids):

* Evolution:
** EV1 a migration runner: ordered, immutable `.sparql` and `.ttl` files; the log of applied migrations as RDF in an admin graph.
** EV2 migration integrity: checksum per applied file, run lock, log written in the same request as the change, dry-run.
** EV3 a schema diff of two LinkML versions that generates SPARQL Update skeletons (renames, class and slot IRI changes, enum meanings, defaults).
** EV4 down migrations, written by hand or derived by inverting a mapping spec.
** EV5 object-level data transformation between schema versions (split, merge, reshape aggregates).
** EV6 a post-migration validation gate: the new version's SHACL must conform; golden counts.
** EV7 the schema version stamped in data or graphs and checked at startup, refusing to run on a stale store.
** EV8 a staged bulk load: temporary graph plus `ADD`/`MOVE`, adaptive batch size.
** EV9 migration rehearsal on a branch or snapshot before promotion (builds on S16).
** *EV10* (taxonomy v5): a pending-migration check in CI. The build fails when the LinkML schema changed and no migration (or an explicit "no data change" stamp) covers the diff. It is the cheapest guard against a schema release that silently strands existing data, and it needs only the diff of EV3, not the compiler, so it can ship in the first EPIC. Precedent: Alembic `check`.
* Developer experience and operations:
** D20 shipped test fixtures for RDF stores: testcontainers wrappers for Oxigraph, Fuseki, GraphDB and Fluree (refines D5 and D8).
** D27 fault-injection tests for store failures, such as a dropped connection mid unit of work.
** D28 API contract fuzzing from the generated OpenAPI.
** D29 store-port observability: OTel spans with query kind, fingerprint, graph and row count; `traceparent` propagation (refines S14).
** S23 an operations admin port: backup, restore, compact and stats per store adapter (extends S11 to remote stores).

== Open questions

. Is migration authoring generated-then-reviewed (Alembic style) or hand-written only? This decides whether the LinkML diff compiler is in scope for the first EPIC.
. Do data graphs carry the schema version, and per graph or per dataset?
. Should our runner stay file-compatible with mu-migrations (V2 reuse): `.graph` sidecar, filename-number ordering?
. Which principal runs migrations under DEC-8 (a Zitadel service account with a dedicated policy)? To be decided with the xref:background/soa/angles/authz.adoc[authorization angle].
. Is a SPARQL compiler for linkml-map worth contributing upstream rather than building the diff compiler alone?
. Does DEC-5 apply to test-only dependencies? (All recommended ones pass anyway.)

*Not checked.* GraphDB and Virtuoso backup and monitoring APIs (vendor docs not fetched); Fluree branch-merge behaviour on conflicting migrations (docs only); linkml-map performance on large datasets. No candidate code was run.

== Final verdict

*Verdict:* mu-migrations-service *ideas* · linkml-map *integrate* (optional, offline) · Alembic *ideas* (benchmark) · testcontainers-python *adopt* (test-only).

. *A migration is safe only when it is recorded in the same request as it runs.* Put the change and its log triple in one SPARQL Update request (inside an RDF4J transaction on V4). The runner refuses edited files by checksum and refuses to run twice at once.
. *The diff is model against model, and LinkML already holds the rename hint.* Generate SPARQL Update skeletons from vN-1 against vN (`deprecated_element_has_exact_replacement`, IRI changes, enum meanings). A human reviews every skeleton, the new version's SHACL is the gate, and linkml-map only reshapes aggregates.
. *We own the RDF test and ops glue.* Nothing upstream gives store fixtures, SPARQL spans or one backup interface across stores. Keep them thin, behind the store port: about one fixture and one admin method per adapter.
