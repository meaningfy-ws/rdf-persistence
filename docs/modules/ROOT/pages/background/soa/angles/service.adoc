= Data-management service and API (L4)
:description: Which API styles a data-management service over RDF can expose, what can be generated from LinkML today, and which contract an rdf-persistence service should speak.

[IMPORTANT]
.Background, not a commitment
====
This page is part of the state-of-the-art study moved from the rdf-persistence repository (commit `43dc152`). It records options and leanings, not decisions. What rdf-persistence commits to is in xref:architecture/index.adoc[rdf-persistence architecture v1].
====

== Purpose of the angle

A UI needs a data-management service over RDF and JSON-LD data: the role mu-cl-resources plays in semantic.works.
This page answers:
which API styles exist and what each costs the JavaScript developer;
what can be generated from a LinkML or SHACL model;
how pagination, filters, includes and framing work;
where the PEP sits;
how changes are notified;
and which styles our service should expose to stay coherent with semantic.works (JSON:API) and with JSON-LD clients.

Deep dives: API Platform core, Community Solid Server, LinkedDataHub, linkml-store.
Round 4 re-checked the round-3 code claims against the finished GitNexus indexes (API Platform's repo is named `core`), scored the four against taxonomy v3 and placed them on the system variants. Nothing was executed.
mu-cl-resources, Prez and OldMan are covered on their own pages:
xref:background/soa/libraries/semantic-works.adoc[semantic.works],
xref:background/soa/libraries/prez.adoc[Prez],
xref:background/soa/libraries/oldman.adoc[OldMan].

== Key findings

* *JSON:API is cheapest for the JS developer*, and it is what semantic.works speaks. IDs are opaque; no RDF knowledge is needed.
* *JSON-LD + Hydra is nearly as cheap* and is the only style with mature generic UIs generated from an RDF-aware contract (API Platform Admin, create-client).
* *LDP, GSP and SPARQL push RDF work into the browser.*
* *GraphQL has the best TS tooling but no portable RDF binding.* The DASH `graphql:` vocabulary is the closest thing; Fluree v4 says it is "shared with TopBraid EDG and GraphDB" (`fluree-db-graphql/src/lib.rs:14-15`).
* *The missing link in MWBv2 is a LinkML → service generator.* LinkML emits OpenAPI components only and GraphQL types only; nothing emits routes, a JSON:API configuration or Hydra API docs.
* *API Platform is a contract reference, not a security or transaction reference.* It ships only the row-filter *hook* (the application writes the filter), emits ETags but checks no `If-Match`, and has no JSON:API Atomic Operations. Conditional writes come from Community Solid Server and LinkedDataHub.
* *Nothing in this angle blocks V1–V4.* V1 with approach B gets the most help; V5 has only vendor or dormant read APIs; approach C has references (linkml-store, LinkedDataHub, mu-cl-resources) but no RDF-capable reusable implementation (see <<variant-fit>>).

== Deep-dive findings

=== API Platform core — the contract reference

*How it works.* PHP attributes (`ApiResource`, `ApiProperty`, operations) build one resource metadata collection. Every format is a projection of it:
`@context` (`JsonLd/ContextBuilder.php:53-82`), Hydra docs (`Hydra/Serializer/DocumentationNormalizer.php`), OpenAPI and JSON Schema, JSON:API schemas, GraphQL types, MCP tools.
Properties can carry `jsonldContext` and `genId` to map to predicate IRIs (`Metadata/ApiProperty.php:115, 211`).

* *Two state ports.* `ProviderInterface::provide(...)` and `ProcessorInterface::process(...)` (`State/`). Doctrine, Elasticsearch and Eloquent are adapters. The pipeline is a decorator chain: `ContentNegotiation → Read → Deserialize → Parameter → SecurityParameter` providers; `Write → Serialize → AddLinkHeader → Respond` processors. An RDF backend would be one provider and one processor delegating to an rdf-persistence repository. None exists in core.
* *Persistence adapters:* GitNexus lists `ProviderInterface` implementers for Doctrine ORM and ODM, Elasticsearch and Laravel Eloquent only; no RDF or SPARQL provider. A custom backend is a documented extension point.
* *PEP at four stages* (`Symfony/Security/State/AccessCheckerProvider.php`): `security` (before or after read), `securityPostDenormalize` (with `object` and `previous_object`), `securityPostValidation`, `securityAfterResolver` (GraphQL).
* *Property-level security exists:* `canAccessAttribute` evaluates `ApiProperty::security` with the object (`Serializer/AbstractItemNormalizer.php:527-540`) and disables normaliser caching for secured properties (`isCacheKeySafe`, `:548-551`).
* *Row-level filtering: core ships only the hook.* `QueryCollectionExtensionInterface::applyToCollection` lets an extension add WHERE clauses before pagination and count (`QueryCollectionExtensionInterface.php:26-33`). Core's five implementers are filter, order, eager-loading, filter-eager-loading and parameter extensions; none is a security filter. The application writes the policy filter itself (the documented `CurrentUserExtension` pattern).
* *No write preconditions:* `HttpCache/State/AddHeadersProcessor.php:34,66` only *emits* a response ETag (opt-in); nothing in `src/` checks `If-Match` or returns 412.
* *No JSON:API Atomic Operations:* grep `atomic` in `src/` finds nothing; JSON:API covers include, fields, page and filter only.
* *Pagination:* page or cursor per operation (`State/Pagination/Pagination.php:199`); Hydra `PartialCollectionView` links (`PartialCollectionViewNormalizer.php:53-93`); JSON:API `page`, `include`, sparse `fields` (`JsonApi/State/JsonApiProvider.php:110-130`).
* *Filters* are advertised as a `hydra:search` IriTemplate (`CollectionFiltersNormalizer.php:115-147`), so generated UIs discover them at runtime.
* *Notifications:* `PublishMercureUpdatesListener` publishes after Doctrine flush (`:101, :131`); private updates use the hub's JWT (`:50-53, :322-324`). GraphQL subscriptions ride the same hub.
* *JS side:* `api-doc-parser` feeds Admin (list, create, show, edit, filters, live updates) and create-client.

*Verdict: borrow the contract and integrate its JS tooling.* If our service emits Hydra docs, Hydra collections and an OpenAPI document shaped like API Platform's, Admin and create-client should work unchanged. *Not tested*; the claim rests on api-doc-parser's documented inputs.

=== Community Solid Server — the LDP and Solid reference

*How it works.*

* `ResourceStore` port with optional `Conditions` on every call, so ETag/If-Match is built in (`storage/ResourceStore.ts:28-68`, `storage/conditions/BasicETagHandler.ts`). A missing resource shows as 404 only to agents with Read; others get 401/403, so a denial hides existence (AZ33, `PermissionBasedAuthorizer.ts:56-72`), as in LinkedDataHub.
* A decorator chain of stores (converting, read-only, patching, monitoring, routing) over five `DataAccessor`s, wired by Components.js.
* SPARQL backend: one named graph per document (`SparqlDataAccessor.ts:70-76`, metadata in `meta:` graphs at `:181`); writes built with the sparqljs `Generator` AST, not strings (`:15`); quads outside the default graph rejected (`:131-134`). Works against a SPARQL 1.1 endpoint that supports Update with `GRAPH`; because of the one-graph-per-document layout, data stored in other layouts is not visible.
* PEP pipeline: credentials → required modes → permission readers → authorizer (`AuthorizingHttpHandler.ts:70-86`). The cleanest PEP/PIP/PDP split in this survey.
* PATCH: N3 Patch and SPARQL Update (`storage/patch/`).
* Notifications: store change maps → AS2 activities → WebSocket, Webhook and streaming-HTTP channels (`server/notifications/`). Spec fields confirmed from the file listing only.
* Gaps for a CRUD UI: no typed resources, no class-level query, filter, sort or page, no schema.

Scores: C1 3 · C2 5 · C3 2 · C4 2 · C5 5 · C6 1 · C7 3 · C8 5 · C9 5 · C10 3.

*Verdict: borrow ideas; integrate only when a Solid pod is itself required.* Borrow the PEP pipeline, ETag/If-Match on every write, Solid Notifications as an open L6 contract and N3 Patch as a standard patch body.
See also xref:background/soa/angles/authz.adoc[the authorization angle].

=== LinkedDataHub — low-code knowledge-graph platform

*How it works.*

* Writes are GSP on document graphs (`DocumentHierarchyGraphStoreImpl.java:347-948`); queries via `SPARQLEndpointImpl.java`.
* ETag and `If-Match` per RFC 9110 (`:409, :456, :586`, `evaluatePreconditions` at `:1810`). The README claims "A write guarded by `If-Match` loses no update", with formal models in `formal/http/` and `formal/acl/`; *the models exist but were not checked*.
* Validation with SPIN constraints (`ValidatingModelProvider.java:50-54, 210-244`); jena-shacl is a dependency.
* *The PEP is a request filter whose policy is a SPARQL query over WAC data*: `AuthorizationFilter.java:85-194` runs a configurable `DESCRIBE ?auth` over `acl:Authorization` triples (including `acl:accessToClass` with `rdfs:subClassOf*`), with a fail-closed default `VALUES` row (`WEB-INF/web.xml:61-104`).
* Identity: WebID client certificates and OIDC. UI: ontology-driven forms in XSLT on SaxonJS (80 files; form derivation not traced).

Scores: C1 4 · C2 4 · C3 2 · C4 2 · C5 4 · C6 3 · C7 4 (portability claimed; only `GraphStoreClient` seen) · C8 4 · C9 4 · C10 3.

*Verdict: borrow ideas.* The strongest DEC-8-shaped idea in this angle: ACL as RDF data plus a declarative, configurable, fail-closed SPARQL policy query. Also borrow GSP document CRUD, ETag semantics and formal models of the contract. Do not adopt the XSLT UI.

=== linkml-store — the LinkML-native API

*How it works.*

* Port `Client → Database → Collection` with `insert`, `upsert`, `delete`, `delete_where`, `update`, `query`, `query_facets`, `find` (`api/collection.py:197-506`).
* Backends in `api/stores/`; *no RDF or SPARQL backend* (grep over `src/`).
* The web API is generic, not per class (`webapi/main.py`): GET objects with a `where` JSON, `limit` and `offset` (`:321-390`), search, facets, schema, POST insert (`:709-725`). *No PUT, PATCH or DELETE routes and no auth dependency* (`:120-144`).
* Listing totals use a full `collection.find({})` (`:351`): costly on large stores.

Scores: C1 2 · C2 3 · C3 4 · C4 4 · C5 4 · C6 4 · C7 0 · C8 3 · C9 2 · C10 3.

*Verdict: borrow ideas; optional integration later.* An rdf-persistence store adapter for linkml-store would give LinkML users a uniform Python API over RDF. Its HTTP API is not a model for the UI service.

== Recommended options per architecture variant

The V-S1 to V-S5 options below are this angle's round-3 service shapes, not the system variants. They map roughly to V2, V1, V3, V5 and a Solid-only case.

[cols="2,5,3",options="header"]
|===
|Variant |Shape |Trade-off
|V-S1 semantic.works-compatible Python resources |Browser → gateway → generated Python resource service (JSON:API, mu dialect) → rdf-persistence → sparql-parser (PEP and deltas) → triplestore |Ember/WarpDrive or react-admin work unchanged; authorization entirely in the proxy
|V-S2 API-Platform-shaped standalone service |Browser → gateway (Zitadel) → generated FastAPI service with JSON-LD/Hydra (default) and JSON:API (profile), in-process PEP and query-filter hook → rdf-persistence → any SPARQL 1.1 store; deltas → Mercure/SSE or Solid Notifications |Zero-code back office via API Platform Admin; we own the PEP seams
|V-S3 DB-native JSON-LD |TS UI → thin proxy → Fluree (FlureeQL or GraphQL) |Fastest start; lock-in, BUSL, rdf-persistence bypassed on the UI path
|V-S4 SPARQL-direct + JS ORM |UI uses LDkit or Comunica against SPARQL behind a rewriting PEP |Least server code, most JS/RDF skill; backend domain rules bypassed. See xref:background/soa/angles/jsclient.adoc[JS client angle]
|V-S5 Solid pod |CSS with a SPARQL backend |Personal-data scenarios only
|===

Recommended contract for our service:

. *Primary: JSON:API in the mu-cl-resources dialect* (`filter[...]` with `:exact:/:gt:/:id:/:uri:/:has:`, `sort`, `include`, `fields`, `page[number|size]`, `meta.count`), plus the *Atomic Operations* extension mapped to one unit of work. The extension goes beyond the mu dialect: mu-cl-resources does not implement it, nor does API Platform, so existing Ember front ends will not send it.
. *Second representation: JSON-LD on the same routes*, by content negotiation: compact form with the LinkML context, IRIs as `@id`, optional framing per view, Hydra collections, a Hydra `ApiDocumentation` and a full OpenAPI.
. *SPARQL 1.1 protocol* as a read escape hatch behind the same PEP, or proxy-rewritten. No generated write API over SPARQL.
. *GraphQL: defer.* If needed, generate it from the same registry following the DASH `graphql:` vocabulary; Strawberry or Ariadne.
. *LDP/Solid: do not expose.* Borrow ETag/If-Match and the Solid Notifications envelope.
. *Notifications:* emit deltas from the commit (X12) and render them as mu delta POSTs and as SSE/Mercure or Solid channels; authorise subscriptions with the same PEP.
. *PEP placement:* three seams, no policy logic of our own: (a) request-context pass-through for proxy mode, (b) an endpoint-level hook (pre-read, post-denormalize, post-validate) calling an external PDP, (c) a listing-query filter hook applied before pagination and count.

Features from this angle (v3 ids): RAD1 zero-code resource service, U5 admin UI from API docs, RAD3 front-end scaffolds, RAD4 tiered exposure; G10 service routes, G11 Hydra docs, G12 GraphQL with mutations, G13 per-class filter grammar, U1 TS client from the contract; X17 multi-profile rendering, X18 atomic multi-operation write, X19 conditional requests, E9 standard notification channels, E1 publish after commit, X20 cursor pagination, X21 RDF patch bodies; AZ6 staged PEP hooks, AZ2 listing-query policy filter, AZ10 ACL as RDF with a SPARQL policy query, AZ7 separated PEP/PIP/PDP pipeline; E4 authorised subscriptions.

== Final verdict

*API Platform core, Community Solid Server, LinkedDataHub, linkml-store: ideas.* API Platform's JS tooling (Admin, create-client) is *integrate*; CSS is deployable only for pod products; linkml-store may later get an rdf-persistence store adapter.

. *Copy API Platform's shape, not its guarantees.* One resource registry projected to JSON:API, JSON-LD+Hydra, OpenAPI (and MCP), persistence behind two ports, security at fixed pipeline stages. It ships no row-level policy filter, no `If-Match` check and no Atomic Operations: we build AZ2, X19 and X18 ourselves.
. *The listing-query filter decides whether authorization is correct.* Per-document enforcement (CSS, LinkedDataHub) is fine for documents and unusable for class-level lists; API Platform leaves the row filter to the application. Only a policy injected before pagination and count gives correct totals: pick a PDP that returns a filter, or stay graph-level.
. *Documents are not resources.* LDP/GSP servers model one named graph per document: clean ETags, ACL inheritance and whole-graph PUT, but no server-side query, filter or page. A UI-facing service needs class-level resources (JSON:API/Hydra) over rdf-persistence. Borrow the document servers' concurrency and ACL ideas, not their storage layout.

== Open questions

. JSON:API ids: UUIDs (mu dialect, `mu:uuid`) or IRIs? IRIs align with JSON-LD but break existing semantic.works front-ends.
. Is API Platform Admin compatibility a goal, and how far should our Hydra follow its quirks?
. Fluree v4 (BUSL-1.1, new SPARQL Update, SHACL-tiered GraphQL): does it change the MWBv2 "accepted with reservations" verdict? Needs a separate check.
. Does the chosen PDP return a *filter* or only allow/deny? Only a filter gives correct paginated listings.
. Browser notifications: Mercure (simple hub, JWT) or Solid Notifications (standard, heavier)? Keep mu delta POSTs for back-end services?
. Is GraphQL needed at all, or do JSON:API `include` and `fields` cover the "GraphQL-like freedom" asked for?
. Who writes the row-level policy filter? API Platform shows the seam but ships no filter; ours must call the PDP from the listing-query hook.
