= JavaScript client and UI
:description: Which JavaScript and TypeScript libraries can consume the data-management service on the client, and which combination gives a coherent, maintainable frontend per architecture variant.

[IMPORTANT]
.Background, not a commitment
====
This page is part of the state-of-the-art study moved from the rdf-persistence repository (commit `43dc152`). It records options and leanings, not decisions. What rdf-persistence commits to is in xref:architecture/index.adoc[rdf-persistence architecture v1].
====

== Purpose of the angle

The MWBv2 UI is a TypeScript app, tested with Cypress and Gherkin. It consumes data from a generated Python data-management service (layer L5).
The question: which client libraries handle a JSON-LD (or other RDF-backed) contract, and which stack is easiest to keep alive?

Method: a desk scan of 45 candidates (GitHub and npm, 2026-11-03).
Four deep dives with clone, GitNexus index and code reading: jsonld.js, @api-platform/admin, shacl-form, LDO.
Round 4 re-read the same commits against taxonomy v3 and the system variants (nothing was executed).
xref:background/soa/libraries/ldkit.adoc[LDkit] was analysed earlier and is only compared here.

*Main finding.* Every RDF-native JS client is below DEC-5 (LDkit, LDO, LDflex, Alcaeus, shacl-form, shaperone, Soukai) or tied to Solid.
The DEC-5-passing RDF pieces are the interop layer only: jsonld.js, N3.js, RDF/JS types, Comunica, rdflib.js.
Every mature data layer, form generator and code generator is RDF-agnostic. It speaks REST/OpenAPI, JSON:API, GraphQL or Hydra.
Weekly downloads differ by four orders of magnitude: tens of millions for TanStack Query and openapi-typescript, hundreds for LDO and Alcaeus.

*Round-4 finding.* Most v3 additions are server-side, so the clients score mostly n.a.
LDO covers the most v3 features (client unit of work, generated context, push); @api-platform/admin covers the UI features.
No client sends preconditions (X19), idempotency keys (T9) or atomic batches (X18): the service must offer them and the generated client must wrap them.
V1, V3 and V4 share one L5 stack; no mature L5 tool blocks any of V1–V5 (see <<variant-fit>>).

== Deep-dive findings

=== jsonld.js

*How it works.* A facade (`lib/jsonld.js`) over one module per algorithm: `compact`, `expand`, `flatten`, `frame`, `toRDF`/`fromRDF`, `canonize` (`lib/jsonld.js:131-770`).
Resolved contexts are reused across calls only when the document loader marks them `static` (`lib/ContextResolver.js:84-100`); the bundled loaders set no tag, so each call refetches a remote `@context`. Serve the generated context from the bundle with a custom loader (X22).
Framing supports `@embed`, `@explicit`, `@requireAll`, `@omitDefault` and named-graph framing (`lib/frame.js:112-284`); this turns a flat CONSTRUCT result into a nested view model.
The document loader is pluggable and accepts custom headers, e.g. a bearer token (`lib/documentLoaders/xhr.js:19-30`).
`safe: true` fails on lossy constructs (`lib/jsonld.js:122-126`).
W3C conformance suites are wired in the test harness (`tests/test.js:1386-1387`); not run here. No first-party TS types (`@types/jsonld`).

*Scores* (reinterpreted for an interop library): C1 4 · C2 4 · C3 3 · C4 4 · C5 5 · C6 4 · C7 n.a. · C8 4 · C9 5 · C10 4.

*Verdict: adopt* as the client JSON-LD processor wherever the server emits JSON-LD. Generate contexts and frames from LinkML.
Risks: framing is heavy on large graphs (paginate); remote `@context` fetches are a network and security surface (bundle the context).

=== @api-platform/admin

*How it works.* `<HydraAdmin entrypoint=…>` reads Hydra docs (or OpenAPI through `<OpenApiAdmin>`) and guesses list, show, edit and create screens. It runs on react-admin, TanStack Query and jsonld.js.

* *Contract: compacted JSON-LD + Hydra.* `fetchHydra.ts` rejects bodies without `@id`; collections need `member`, `totalItems`, `view` (`dataProvider.ts:577-620`). Success bodies are used as-is; only error bodies are expanded.
* *Query string is the API Platform dialect, not pure Hydra:* `order[field]`, `page`, `itemsPerPage`, `field[]` (`dataProvider.ts:410-440`; `introspection/schemaAnalyzer.ts:19-43`). A Python backend must imitate it. The OpenAPI path (`<OpenApiAdmin>`) shares the same filter analyser, so it depends on the dialect too.
* *Field typing is tied to schema.org:* `identifier`, `email`, `url`, then the `xsd:` range; labels come from `schema.org/name` (`hydra/schemaAnalyzer.ts:18-66`). With `dct:title` or `skos:prefLabel` labels fall back to the id.
* Embedded objects with `@id` are cached by IRI, a client identity map (`dataProvider.ts:75-105`).
* Auth: `Authorization` header from a react-admin `authProvider`, set verbatim (`fetchHydra.ts`), so store the token with its `Bearer ` prefix; no built-in OIDC.
* Live updates: Mercure SSE patches the query cache (`dataProvider/useUpdateCache.ts:7-54`).
* ConstraintViolation lists become per-field form errors (`hydra/schemaAnalyzer.ts:70-95`).
* "Client-side validation of required fields" was not traced (lives in api-doc-parser, not read).

*Scores:* C1 4 · C2 4 · C3 4 · C4 3 · C5 4 · C6 3 · C7 n.a. · C8 4 · C9 4 · C10 3.

*Verdict: integrate* for the back office *if* the service emits Hydra in the API Platform dialect; otherwise borrow ideas.
The cheaper path is react-admin with `<OpenApiAdmin>` over the FastAPI OpenAPI document.

=== shacl-form

*How it works.* A framework-neutral web component `<shacl-form>` (`src/form.ts:35, 716`).
It takes shapes and values by attribute or URL, plus subject, namespace (IRI minting), named graph, language and mode `edit|view|query` (README:84-104).
The root shape is resolved from `dcterms:conformsTo`, then `rdf:type` / `sh:targetClass`, then the first node shape.
`validate()` runs shacl-engine on the root node (`src/form.ts:458-502`); `submit` fires only on valid data.
Extension points: `setRdfUrlResolver` (auth or backend hook), `setClassInstanceProvider`, `ResourceLinkProvider`, `registerPlugin` (`src/plugin.ts:65-75`).
Query mode builds SPARQL SELECT from the shape, with ordering, paging and facets (`src/query/sparql.ts`).

*JSON-LD output is per triple:* the hand-rolled `serializeJsonld` emits one node object per triple, with no `@context` and no named graph (`src/serialize.ts:23-46`). Valid, but not compacted; add a `jsonld.compact` step if the server expects compacted JSON-LD.
No test CI workflow was found.

*Scores:* C1 4 · C2 4 · C3 4 · C4 4 · C5 5 · C6 5 · C7 4 · C8 3 · C9 5 · C10 3.

*Verdict: borrow ideas or vendor-in* (fails DEC-5 on stars). The strongest shape-driven form component. Whether it renders all SHACL that LinkML `shaclgen` emits was not tested.

=== LDO (Linked Data Objects)

*How it works.* ES Proxies give typed, JSON-LD-shaped, mutable objects over an RDF/JS dataset (`packages/jsonld-dataset-proxy/src/ProxyContext.ts:54`).
A CLI generates TS types *and* a JSON-LD context from ShEx, and from SHACL via shacl2shex (`packages/cli/src/util/forAllShapes.ts:3-57`).
`startTransaction` / `commitTransaction` record a diff; `toSparqlUpdate` emits `DELETE DATA {…} INSERT DATA {…}` (`packages/ldo/src/methods.ts:233-358`, `rdf-utils/src/datasetChanges.ts:18-35`).
`commitToRemote` sends one update per resource in parallel; a failure leaves the other resources committed (`AggregateError`, `connected/src/ConnectedLdoTransactionDataset.ts:205-233`), so a commit is atomic per resource only.
Remotes are plugins (`connected/src/types/ConnectedPlugin.ts:10-35`); only Solid and NextGraph exist. There is no SPARQL-endpoint, REST or Hydra plugin.
`toJsonLd()` throws "Not Implemented" (`methods.ts:413-415`): JSON-LD output is *claimed by the API surface, not found in code*.

*Scores:* C1 3 · C2 5 · C3 4 · C4 2 · C5 4 · C6 5 · C7 2 · C8 3 · C9 3 · C10 2.

*Verdict: borrow ideas* (alpha 1.0.0-alpha.51, fails DEC-5): client unit of work by graph diff, types and context generated from one shape, one plugin per backend.
Risk: `DELETE DATA`/`INSERT DATA` patches carry no precondition, so lost updates are possible.

In every variant:

* Frontend auth is the same: an OIDC client obtains a token and one `authFetch` adds `Authorization: Bearer` for every library. L5 holds no policy; it only hides what the API reports as forbidden (U9).
* rdf-persistence must expose stable IRIs and ETags or version predicates, so optimistic writes fail cleanly. LDkit, LDO and shacl-form send no preconditions.
* orval and hey-api generate MSW handlers from the same OpenAPI for component and E2E tests.

The service side of these contracts is covered in xref:background/soa/angles/service.adoc[Data-management service]; TS type generation in xref:background/soa/angles/codegen.adoc[Code generation].

== Final verdict

*jsonld.js: adopt* (dependency wherever JSON-LD is on the wire). *@api-platform/admin: integrate* (optional back office, only if the service speaks the API Platform Hydra dialect; otherwise react-admin `<OpenApiAdmin>`). *shacl-form, LDO: ideas*.

. *The L5 stack is mainstream and RDF-agnostic; the RDF knowledge lives in the contract.* Generate OpenAPI, the JSON-LD context and frames, and SHACL from LinkML; use TanStack Query, orval or hey-api, zod, jsonld.js and oidc-client-ts. Every RDF-native JS client fails DEC-5 or is Solid-only.
. *Concurrency and atomicity are server duties.* No client library sends ETags, idempotency keys or atomic batches, and LDO commits are atomic per resource only. Design B11, X19, T9 and U13 into the service and wrap them once in the generated client.
. *Bundle the generated `@context` and process strictly.* jsonld.js refetches remote contexts unless the loader marks them static, and drops unmapped terms silently unless `safe: true` is set. A custom loader plus safe mode (X22, X23) prevents network coupling and silent data loss.

== Open questions

. Is the wire format compacted JSON-LD with a generated context, or must the UI see expanded IRIs? This decides whether jsonld.js is in the hot path.
. Will DEC-5 be relaxed for leaf UI components behind a replaceable seam (shacl-form, LDkit)? If not, forms come from JSON Schema and IRIs, language strings and `sh:class` pickers need custom widgets.
. Is a read-only, ACL-filtered SPARQL endpoint for the UI wanted (variant D)? If yes, the authorization angle must name the proxy.
. Is a generated back office in MWBv2 scope? Hydra adds a generator (G11) and dialect coupling.
. React or framework-neutral? semantic.works uses Ember; most mature options are React-first; shacl-form is neutral.
. Is FastAPI's OpenAPI a better source of TS types than LinkML `gen-typescript`? Recommended, not tested.
. Who provides preconditions, idempotency keys and atomic batches (X19, T9, X18)? No client library sends them, so the service must offer them and the generated client must wrap them.
. Does react-admin clear its query cache on logout? Its cache is not partitioned by user (AZ22); not verified.
