= Modelling and code generation (L0)
:description: What can be generated today along the UML → model2owl → LinkML chain, where the gaps are, and how generated code meets rdf-persistence.

[IMPORTANT]
.Background, not a commitment
====
This page is part of the state-of-the-art study moved from the rdf-persistence repository (commit `43dc152`). It records options and leanings, not decisions. What rdf-persistence commits to is in xref:architecture/index.adoc[rdf-persistence architecture v1].
====

== Purpose of the angle

The MWBv2 approach generates the backend from a model.
The chain under study: UML (Enterprise Architect, SEMIC conventions) → model2owl → OWL, SHACL and JSON-LD context → LinkML → generated Python domain, persistence, JSON-LD context, SHACL, TypeScript types and JSON Schema / OpenAPI.

This page answers: which generators exist, how good each output is, which known MWB gaps still hold, and what must be generated for rdf-persistence.

Deep dives: LinkML (monorepo, now including `linkml_runtime`), model2owl (OP-TED upstream and the meaningfy-ws `feature/linkml` branch), schema-automator, shacl2code.

== Key findings

* *LinkML is the only mature schema source that fans out to every target we need.* Its generated Pydantic classes are free of persistence code and already carry the RDF mapping (`class_uri`, `slot_uri`) as metadata. That is what a separate mapper needs.
* *No generator emits an RDF mapper, repositories or API routes from a LinkML or SHACL model*; the only mapper generator, LinkML `gen-sqla`, targets SQL. GitHub search found only 0-star personal repos.
* *Language-tagged strings are lost along the whole chain*: model2owl's LinkML export, schema-automator and LinkML's own RDF loader and dumper all drop the tag. model2owl's SHACL still declares `rdf:langString`; the loss starts at the LinkML step.
* *IRIs are typed as `str`*: `grep AnyUrl` over the LinkML monorepo returns 0 hits.
* *TypeScript output is still weak*: enums are declared, but enum-typed fields are emitted as `string`; dates map to `date`, which is not a valid TS type.
* *FastAPI's runtime OpenAPI is not clean when routes use LinkML Pydantic models*: every schema carries a non-standard `linkml_meta` object and IRIs are typed as plain `string`. LinkML's `gen-openapi` strips it (`openapigen.py:336-347`). Publish `gen-openapi` output, or strip it in a FastAPI `openapi()` hook (inferred from code, not observed at runtime).
* *model2owl has no LinkML output upstream.* The export lives on a fork branch 365 commits behind. The SHACL → LinkML route via schema-automator is now the better path.

== Deep-dive findings

=== LinkML

*How it works.* Each generator subclasses `Generator`, reads a `SchemaView` and renders Jinja2 (`linkml/utils/generator.py`).

* *Pydantic.* Templates can be overridden with `template_dir` (`pydanticgen/pydanticgen.py:233`); classes and fields can be injected (`:243-252`); output can be split per module (`:327, :379`).
* *RDF metadata in generated classes (verified).* `linkml_meta: ClassVar[LinkMLMeta]` holds `class_uri`; field `json_schema_extra` holds `slot_uri` (`class.py.jinja`, `attribute.py.jinja:18`). LinkML (1.10–1.12) emits `class_uri` and `slot_uri` by default; `range`, `inlined`, `multivalued`, `required` and `identifier` appear only with `metadata_mode=full` or `except_children` (`pydanticgen.py:975-1016`; `pydanticgen/template.py:191`). A runtime mapper either infers them from the type annotations or the build uses `metadata_mode=full`. Generated classes import only pydantic.
* *IRI typing.* `uri` and `uriorcurie` have `repr: str` (`types.yaml:125-148`), so fields are `str`. MWB gap still true.
* *TypeScript.* Enums are declared as `export enum` (`:49-62`), but `range()` never checks enums, so enum-typed fields are emitted as `string` (`:188-231`). `xsd:date` maps to `date`, an invalid TS type (`typescriptgen.py:25-31`). MWB gaps still true.
* *JSON-LD context and frame.* `jsonldcontextgen.py:83-86, 204-236` can emit a `.frame.jsonld` rooted at the tree-root class. New since the MWB evaluation; useful for an API returning framed JSON-LD.
* *SHACL.* `shaclgen.py` (971 LOC) emits closed shapes, class/datatype/nodeKind, cardinality, pattern, `sh:in`, SPARQL constraints. `--default-language` tags schema labels, not instance data.
* *OpenAPI.* `openapigen.py` fills `components/schemas` into a *user-supplied* template with `paths` (`:147-165, :537-600`). It does not generate operations. It strips generator bookkeeping (`linkml_meta`, `x-linkml-*`) from the published schemas (`:92, :336-347`); FastAPI's own OpenAPI does not (see Key findings).
* *GraphQL.* `graphqlgen.py` (121 LOC) emits types, scalars, enums; no `Query` or `Mutation`.
* *SQLAlchemy, the precedent for a separate mapper.* The default imperative template generates `Table(...)` objects and `map_imperatively(DomainClass, ...)` over the imported domain classes (`sqlalchemygen.py:68`). That is cosmic-python classical mapping. Relationship mappings are commented out. *No RDF analogue exists.*
* *RDF round-trip in `linkml_runtime`.* The dumper writes IRIs for identifier slots and blank nodes otherwise (`rdflib_dumper.py:129`), enum `meaning` as IRIs (`:91-104`), ordered multivalued as `rdf:List` (`:150-162`), and `rdf:type` automatically (`:163-172`). *It never writes a language tag.* The loader finds roots by `rdf:type` (`rdflib_loader.py:95`), resolves polymorphism via a type designator (`:115-122`), raises on unmapped predicates unless told not to (`:134-137`) and returns `o.value`, losing the tag (`:263-270`). It is an in-memory converter: no session, identity map, diff, SPARQL, named graphs or store port.
* *Instance typing.* JSON dumps carry only a top-level `@type` (`json_dumper.py:34-66`); nested types need a `designates_type` slot.

*Verdict: adopt* as the L0 source of truth and generator host.
*Extend* with custom Pydantic templates (IRI type, language-string type) and a new rdf-persistence generator that reads `linkml_meta` / SchemaView.
*Borrow* from the loader and dumper (type designator, pointer resolution, unmapped-predicate policy) but do not use them as the persistence layer.

=== model2owl

*How it works.* XSLT 3.0 on Saxon, driven by Make. Turns an EA XMI export into OWL core, OWL restrictions, SHACL, a JSON-LD context, an HTML glossary, a ReSpec config and an SVRL conventions report.
Upstream has no LinkML output. The fork branch `feature/linkml` (last commit 2025-02-25; 5 ahead, 365 behind) adds `src/linkML.xsl` and helpers.
GitNexus indexes XSLT poorly, so evidence comes from reading files.

Status of the MWB gaps on the fork branch:

Do not invest in the XSLT LinkML exporter; go SHACL → LinkML via schema-automator instead.
If the exporter stays, it must emit `meaning:` for enum values and a language-string type.

=== schema-automator

*How it works.* One importer engine per format in `schema_automator/importers/`.

* The new SHACL importer (`shacl_import_engine.py`, 986 LOC) handles explicit, implicit and split shapes across files (`merge_classes`, `:571`), maps `sh:class`, `sh:node`, `sh:datatype`, `sh:in` (`:515`), `sh:or`, `sh:xone`, qualified shapes and cardinality (`:554`). It drops `sh:sparql` (documented, `:40-60`). CLI `import-shacl` (`cli.py:553-580`).
* `rdf:langString` falls back to `string` (`:501`); the RDFS importer does the same (`rdfs_import_engine.py:362`).
* The OWL importer requires OWL functional syntax (`owl_import_engine.py:37-40`).

Scores: C1 3 · C2 3 · C3 3 · C4 3 · C5 5 · C6 4 · C8 3 · C9 4 · C10 3.

*Verdict: integrate at build time*: model2owl SHACL → `schemauto import-shacl` → curated LinkML overlay, with a check that LinkML `gen-shacl` stays equivalent to the model2owl SHACL.

=== shacl2code

*How it works.* Reads a SHACL+OWL model (JSON-LD) and generates bindings from templates (`src/shacl2code/model.py`, `lang/templates/`).
Generated Python is standalone (stdlib only): a `SHACLObject` base with typed property descriptors including `AnyURIProp` (`model.pyi.j2:68-330`), validation on assignment, an object set with identity by IRI and link resolution (`:512`), and pluggable JSON-LD encoder and decoder (`:394-590`).
It reads path, datatype, class, nodeKind, cardinality, pattern and hasValue (`model.py:337-409`). No `rdf:langString` support. No store, no SPARQL.

Scores: C1 2 · C2 3 · C3 3 · C4 4 · C5 1 · C6 3 · C8 3 · C9 3 · C10 3.

*Verdict: borrow ideas* (fails DEC-5): IRI-typed descriptors, object-set identity, encoder/decoder port, multi-language generation from one shape model.

=== Desk notes

* *linkml-store* has no RDF or SPARQL backend; its FastAPI is generic, not per model. See xref:background/soa/angles/service.adoc[the service angle].
* *datamodel-code-generator* (now in its own GitHub organisation) *+ fastapi-code-generator* (koxudaxi) would regenerate Pydantic from JSON Schema and *lose `linkml_meta`*. Use them only for route skeletons that import LinkML classes, or not at all (from docs, not code-checked).
* *LDO* (o-development, Jackson Morgan; Solid community) is the best TS-side idea (shape → typed proxy objects over an RDF/JS dataset). It is ShEx-based, but its CLI also accepts SHACL by converting it with `@jeswr/shacl2shex` (`packages/cli/src/util/forAllShapes.ts:3`). It fails DEC-5.
* *shacl-form, Sparnatural* are L5 consumers of generated SHACL. See xref:background/soa/angles/jsclient.adoc[the JS client angle].
* *SeMPyRO* shows demand for SEMIC application-profile Pydantic classes; generating them from model2owl SHACL would replace hand-writing.

== Recommended options per architecture variant

*Recommended chain:* UML → model2owl → OWL + SHACL + context → `schemauto import-shacl` (or curated LinkML) → LinkML → `gen-pydantic` with custom templates as the *domain layer*; the rdf-persistence mapper reads `linkml_meta` / SchemaView as the *adapters layer*; `gen-shacl` for write-time validation; `gen-jsonld-context --emit-frame` for the API; `gen-typescript` with a custom template (or LDO-style codegen) for the UI.

Generated code is built at build or test time and never edited. Pin the LinkML version and diff generated output in CI.

Nothing in L0 touches authorization. L0 may generate *policy inputs* (class and predicate lists per aggregate) for an external PEP, never policies (DEC-8). See xref:background/soa/angles/authz.adoc[the authorization angle].

== Open questions

. After UML, is curated LinkML or model2owl SHACL the master? This decides whether `import-shacl` runs once or on every build.
. Which language-string representation do we standardise: `dict[lang, str]`, `list[LangString]` or rdflib `Literal`? It needs a LinkML type, a template and mapper support.
. Contribute fixes upstream (TS enum typing, `date` → `Date`, `uri` → `AnyUrl` option) or keep custom templates?
. Generated mapper (approach B) or runtime mapper (approach A)? Does "generated, never-edited" extend to repositories and routes?
. Retire the meaningfy-ws `feature/linkml` XSLT exporter in favour of `import-shacl`?
. Publish the `gen-openapi` contract, or strip `linkml_meta` in a FastAPI `openapi()` hook? And generate Pydantic with `metadata_mode=full`, or let the runtime mapper infer `range`/`multivalued` from annotations?

*Not checked:* no generator was run; the FastAPI `linkml_meta` leak is inferred from Pydantic's `json_schema_extra` merge and LinkML's own stripping code; fastapi-code-generator, datamodel-code-generator, LDO, shacl-form and linkml-store claims come from READMEs and listings only.

== Final verdict

*LinkML (with linkml_runtime): adopt* as an L0 dependency; its generated Pydantic is the L1 domain layer, its runtime converter only ideas. *model2owl: build-time* (in-house UML → OWL/SHACL front end; DEC-5 exception needed; drop the fork's LinkML exporter). *schema-automator: build-time* (SHACL → LinkML import). *shacl2code: ideas.*

. *LinkML gives you the model and the metadata, not the persistence.* Generated Pydantic carries `class_uri`/`slot_uri`, but `range`/`multivalued`/`inlined`/`required`/`identifier` reach `linkml_meta` only with `metadata_mode=full` (or the mapper infers them from annotations). The RDF mapper, repositories and routes are ours to build (approach A or B).
. *Three gaps must be closed by us, in templates and the mapper, before the chain is lossless:* language-tagged strings (lost from the LinkML step on), IRI typing (`str`, not `AnyUrl`) and enum concept IRIs (`meaning`), plus the weak TS generator if TS types come from LinkML.
. *Pin and gate the chain.* Generator output changes between LinkML minors and two paths emit SHACL (model2owl, `gen-shacl`): pin versions, regenerate in CI, diff generated code (G27), check the two SHACL outputs stay equivalent (G30), and publish `gen-openapi` output or strip `linkml_meta` (G28).
