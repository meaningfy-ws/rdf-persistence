= Build versus reuse
:description: Per layer, what to adopt, integrate, stay compatible with, or build — the decision support for the next EPIC. The decision is the developer's.

[IMPORTANT]
.Background, not a commitment
====
This page is part of the state-of-the-art study moved from the rdf-persistence repository (commit `43dc152`). It records options and leanings, not decisions. What rdf-persistence commits to is in xref:architecture/index.adoc[rdf-persistence architecture v1].
====

This matrix is the end product of the review: per building-block layer, what already exists and
what has to be built. It is decision support, not a decision. Verdict vocabulary as in the
xref:background/soa/catalogue.adoc[tool catalogue]: *adopt* (dependency), *integrate* (run
next to our code through a standard contract), *compatible* (honour its contract without its
code), *build-time* (toolchain only), *ideas* (design only). Build items `BL-n` match the
xref:background/soa/architecture-analysis.adoc[architecture analysis]. V1–V5 are the system
variants and A–D the development approaches defined on
xref:background/soa/variants.adoc[architecture variants]. Components below the reuse
threshold (DEC-5) are marked *(DEC-5 exception)*: using them needs an explicit decision.

== What this says

* *The core to build is specific.* Eight core items, mostly at the L1–L3 seams (plus the outbox
  at L6 and the cross-cutting test kit) where nothing mature exists, plus companions that make the MWBv2 chain work end to end.
* *Nothing is built at the RDF, store, identity, policy-engine or JavaScript data-layer level.*
* *The riskiest builds* are the change-set compiler (atomicity and concurrency per store), the
  policy port (leaks through counts and single reads), and the migration chain — see
  xref:background/soa/risks.adoc[risks].
* *Optional items wait for a project need:* read models (V5), the generic service (approach C),
  the property-graph adapter.
