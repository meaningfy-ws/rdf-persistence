= Tool catalogue: purpose, origin and fit
:description: What each reviewed tool is for, who built it from which angle, and where it could fit in our architecture, if at all.

[IMPORTANT]
.Background, not a commitment
====
This page is part of the state-of-the-art study moved from the rdf-persistence repository (commit `43dc152`). It records options and leanings, not decisions. What rdf-persistence commits to is in xref:architecture/index.adoc[rdf-persistence architecture v1].
====

This page is the single register of every tool the review touched. A tool built from one angle
rarely fits another. Knowing *why* it exists is the fastest way to know where it can serve us.

*Layers:* L0 modelling and code generation · L1 domain and persistence · L2 stores and
transactions · L3 identity and authorization · L4 data-management service and API ·
L5 JavaScript client and UI · L6 change events.

*Fit:* *adopt* or *dependency* — build on it (*adopt* marks a final round-5 verdict) · *integrate* — run it next to our components through a
standard contract · *compatible* — honour its contract without its code · *ideas* — borrow
design only · *build-time* — a toolchain step, not a runtime part · *none* — no fit. Where a
round-5 report gave a final verdict, the Fit cell carries it.

*Variants:* the "Where it fits" cell ends with the system variants (V1–V5) and development
approaches (A–C) of xref:background/soa/variants.adoc[Variants] that the tool supports or
blocks.

*DEC-5:* a dependency needs more than 200 GitHub stars and a commit in the last 12 months
(packages of a qualifying organisation or monorepo inherit). It is recorded in the Fit cell where
it decides the fit; a licence is recorded where it is a constraint (BUSL, GPL, LGPL, AGPL).

Version: final (after round 5, 2026-11-03). Covers the twelve libraries of rounds 1–4, the candidates
of the five round-3 angle reports (authorization, code generation, data-management service,
JavaScript client and UI, stores and events) and of the four round-4 angle reports (DDD
boundaries, developer experience, property graphs, evolution and operations), with the round-5
corrections and final verdicts. Stars and dates are as of 2026-11-03;
details are in the raw reports under `openspec/changes/soa-python-rdf-orm/inputs/analysis/`.

|rdflib
|The general-purpose RDF toolkit for Python: graphs, parsers, serialisers (JSON-LD included), a SPARQL engine, remote SPARQL stores.
|RDFLib community, since 2002. Library-first, standards-complete.
|L1, L2
|adopt
|The RDF model under everything we write in Python. `SPARQLUpdateStore` already buffers edits and commits them as one request (T1); 7.5 adds an RDF4J client with transactions, 7.6 a GraphDB client with ACL management. `SPARQLUpdateStore` autoflushes before reads unless `dirty_reads=True`. Variants: V1–V5 (T1 in V1, T4 fallback in V2, T3 in V4); approaches A–C.

|pyoxigraph / oxrdflib
|A fast embedded SPARQL 1.1 store with atomic updates (multi-operation transactions in the Rust API only); oxrdflib puts it behind rdflib's store API.
|Thomas Pellissier Tanon (`CITATION.cff`), community project (Rust). Store-first, standards-strict.
|L2
|adopt
|Embedded and test store; rdflib API on Oxigraph's engine. Each Python update call is atomic. The in-memory store serialises writers; on disk (RocksDB) the guard read is not serialised with the write, so two concurrent guarded commits can both pass: the adapter must hold a write lock (T7). Variants: dev and test default in V1–V5; V5 replica.

|SPARQLWrapper
|Sending SPARQL 1.1 queries and updates to remote endpoints.
|RDFLib community. Protocol client.
|L2
|dependency
|Default remote client. Last release 2022; the rdflib httpx clients are the alternative. Variants: V1–V5 read path.

|LinkML
|One YAML schema as the source of truth, generated into Pydantic, JSON Schema, SHACL, OWL, TypeScript, JSON-LD context (and frames), OpenAPI components, GraphQL types.
|Started at Lawrence Berkeley National Laboratory (Chris Mungall's group) for biomedical standards (Biolink / NCATS Translator, Monarch); NCATS funds it. Data-exchange-first, many targets. `linkml_runtime` now lives in the same monorepo.
|L0 (L1 via runtime)
|adopt
|Model source and code generator of the MWBv2 chain. Generated Pydantic classes are persistence-free and carry `class_uri` / `slot_uri` metadata for our mapper (G1); the default `metadata_mode=auto` (LinkML 1.10–1.12) drops range, inlined, multivalued, required and identifier (G33). The only mapper generator (`gen-sqla`) targets SQL; the RDF mapper is ours. Language tags are lost from the LinkML step on. FastAPI's runtime OpenAPI from these classes carries `linkml_meta` and types IRIs as plain string: publish `gen-openapi` output or strip it (G28). No composition construct (aggregates need a convention, B1). Weak TS generator; no route, Hydra or lang-string support. Variants: V1–V5; enables approaches A and C, B needs our generator.

|pySHACL
|Validating RDF graphs against SHACL shapes.
|RDFLib community. Validation-first.
|L0, L1
|dependency
|Validation of generated shapes, of data before commit and after a migration (EV6). Variants: V1–V5.

|pydantic
|Typed, validated Python data classes.
|Pydantic project. General Python.
|L1
|dependency
|The shape of generated domain classes. Variants: V1–V5.

|PyLD
|JSON-LD 1.1 processing (expand, compact, frame) in Python.
|Digital Bazaar. Spec-reference implementation.
|L1, L4
|dependency
|Framing generated JSON-LD responses on the server. Variants: V1, V3, V4 (JSON-LD on the wire).

== Property graphs

Side question (DEC-14): can the same ports serve a labelled property graph? No Python mapper
targets both RDF and LPG today; the recommendation is to shape the seams (B8, PG1–PG4), not to
build an LPG adapter now.

|===
|Tool |Built for |Origin and angle |Layers |Fit |Where it fits

|neosemantics (n10s)
|Moving RDF in and out of Neo4j: import, export, vocabulary mapping, SHACL validation, light inference.
|Neo4j Labs, Jesús Barrasa. Store-side bridge (Cypher procedures).
|L2
|ideas
|Its RDF → LPG conventions are the reference for an LPG projection (PG2); lossy by default. Writes commit in independent batches of `commitSize` triples (default 25,000), so delete + import is not atomic: fit for an optional one-way export or rebuildable V5 replica for analysts, never a unit-of-work flush. Apache-2.0.

|An rdflib store that streams triples into Neo4j with the n10s conventions.
|Neo4j Labs, Jesús Barrasa. Bulk loader.

|linkml-store Neo4j adapter

|LinkML organisation; main author Chris Mungall. Schema-at-runtime collection API; node / edge projection.
