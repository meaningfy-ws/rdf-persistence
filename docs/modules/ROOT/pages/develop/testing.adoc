= Testing checklist
:description: The rules every test in rdf-persistence follows, given to every builder and adversarial tester.

These rules apply to every test written in this repository, by a person or an agent. Every
builder and adversarial tester brief points to this page (see
xref:develop/agents.adoc[Working with agents]). They were distilled from the tests of
rdf-fingerprinter and applied throughout toolkit v1.

_What makes a test acceptable here?_

== Where tests live

. A test lives in the tier folder of the layer it tests (`tests/unit/`, `tests/feature/`,
  `tests/integration/`, `tests/e2e/`, and `tests/perf/` for the wall-clock budgets run by
  `make test-perf`); the folder also gives the marker. Domain tests import no adapter, service or
  fake.
. Nothing outside the container and e2e tests touches the network (`testkit.no_network`). The
  exception in `tests/integration/network/` talks to a loopback server the test starts itself
  (a real listener on 127.0.0.1): it needs no container, and `make test-containers` runs it.

*Two pyramids.* There is one for each package. The library's is `tests/unit/`, `tests/feature/`,
`tests/integration/` and `tests/e2e/`. The generator's is the same four tiers under
`tests/generator/` (`tests/generator/unit/`, and so on), and its folders give the same markers.
Place a test by the module it tests, not by where it used to sit: a test of the library stays in
the library's pyramid, even if it uses the generator as a tool. A library test imports
`rdf_persistence_generation` only if it is listed in `TOOL_USERS` in
`tests/unit/tooling/test_library_tests_stay_apart.py`; that test fails on any other file, and on a stale
entry.

`make test-unit` and `make test-feature` leave out `tests/generator/` and measure the coverage of
`rdf_persistence`. `make test-generator` runs only `tests/generator/` and measures the coverage of
`rdf_persistence_generation`, with the same floor of 80 %. `make test` runs the three.

The generator lane runs the generator's unit, feature and integration tiers, the `slow` tests
included, and starts no container. The integration tier generates a library and runs `tsc` on the
generated TypeScript, so the lane needs Node 20 on the path; the CI job `test-generator` sets it
up with `actions/setup-node` before it runs `make test-generator`. The generator's end-to-end tier
serves a freshly generated library on Fuseki, so it runs in `make test-containers`, which also
runs the generator's integration tests, never in CI.

== Test doubles and data

[start=3]
. Prefer one fake that implements the real port, with a small API (`add`, `on(name, outcome,
  times)`, `sent`), over `MagicMock`. A test does not `monkeypatch.setattr` or `delattr` toolkit
  code (`rdf_persistence*`); it uses a real seam: a setting, a constructor argument, a subclass of a
  third-party class, or data. Five kinds of patch stay, each marked with a trailing `# X1` to `# X5`
  comment:
  `X1`, a configuration constant of the generator or the kit pointed at a copy;
  `X2`, an order or a hand-off no public result shows, observed by a pass-through spy or an
  instrumented lock;
  `X3`, a fault or defect no port can produce, injected to prove a guard catches it;
  `X4`, a random draw pinned;
  `X5`, an absent optional dependency.
+
A planted mutation in a generated file (to show a test bites) needs
`-p no:rdf_persistence_generation.testkit.{empty}freshness` on the `uv run pytest` line, because the
freshness plugin stops the run on a hand-edited generated file; revert the mutation before
anything else runs.
. Build model objects with small builder functions, through the generated models, never bare
  dicts. Shared read-only data is session-scoped; mutable state is function-scoped (`tmp_path`).
  Deviation from the checklist's rule 6 (a factory library): model objects come from the named
  builders of `tests/toy.py`, validated by the models.

== Assertions

[start=5]
. Assert on RDF by parsing it into a graph and comparing with `rdflib.compare.isomorphic`; on
  failure, print the graph diff. Never compare Turtle as strings.
. Every query, guard, check or policy rule gets a positive and a negative case in a parametrized
  table, plus a test that every rule in the catalogue has a row. Where one case stands for a
  class of inputs, a comment on that case says so in one form: `# Class: <what the class is>` for
  one class, `# Classes: <the classes>` for several, naming the case that stands for the others.
. Goldens are regenerated only by a make target. Turtle is compared by meaning, other formats by
  exact text, and the file set must match exactly.
. Hypothesis tests cover invariants (round-trip, order independence, bounds); CI runs them
  derandomized. Every other random generator is seeded.
. Gherkin uses business language, a Scenario Outline for variants and one shared step library.
  Each `Then` asserts one thing.
. One assert per idea, each with a message. No `and` chains.

== Time and containers

[start=11]
. No real sleeps or timing-based asserts. Inject the clock or the sleep; wait for eventual
  consistency with `testkit.wait_until`, or `testkit.wait_until_async` for an async probe. When
  one call can hang (a network call without its own timeout), pass `probe_timeout`: a call that
  takes longer counts as "not ready yet".
. Container tests start their containers once per session through fixtures, and each test
  namespaces its own data (a fresh dataset or bucket name). In CI a missing Docker is a failure,
  not a skip.

[#slow]
== Slow tests

_When is a test slow, and what do I do about it?_

A test is slow when its set-up and its call add up to 2 s or more, run alone
(`uv run pytest <node id> -p no:randomly --durations=0 -n 0`). Session start-up does not count.
`make test-fast` leaves slow tests out; `make test-changed` and `make check-all` run them.
CI does not run slow tests: it runs `make test-unit-ci` in 8 shards, balanced by the durations
in `.test_durations` (`make test-durations` refreshes them when the shards drift apart), and
`make coverage-combine` checks the floor on their union; so run the slow tests locally before a PR.

* Mark the test itself: `@pytest.mark.slow` on the function or the class. Never a module
  `pytestmark`: it would hide the fast tests of the file, and `tests/conftest.py` stamps the other
  markers by path.
* To find candidates, run `make profile-tests PROFILE_MARK="(unit or feature) and not slow"`. It
  lists the 15 slowest tests that are not marked yet.
* A module or session fixture that is slow to build is not a reason to mark: the tests that share
  it pay for it once. Mark a test only for its own time.

[#run-rules]
== Quarantine, timeouts, order and shared fixtures

_What does the runner do to my test, and what do I do about a test that breaks one of these?_

* *Quarantine.* A test that passes and fails on unchanged code (rule 14) is marked
  `@pytest.mark.quarantine` and carries a link to its issue in a comment. Every lane that selects
  `unit`, `feature` or `unit or feature` adds `and not quarantine`, so a quarantined test blocks
  nothing; nobody quarantines a test to hide a real failure. A skip that stands for a parameter
  combination that cannot happen is not a quarantine: remove the combination.
* *Timeout.* `pytest.ini` sets `timeout = 120` (seconds, `signal` method, fixture set-up not
  counted, so a container start is free). In every run, parallel (`pytest -n <workers>`) or serial
  (`-n 0`, or plain `pytest`), a hung test fails by name in its own process, the worker survives
  and the next test runs. (The `thread` method killed the worker, and under `--dist loadgroup`
  xdist never rescheduled its queued tests.) A test that legitimately takes longer carries
  `@pytest.mark.timeout(<seconds>)`; use a smaller `--timeout=<seconds>` to hunt a hang.
* *Random order.* `pytest-randomly` shuffles the order of tests and reseeds the random generators
  before every test, so a test that depends on another's leftovers fails soon. The seed is
  printed in the header of a run's output (`Using --randomly-seed=<n>`); replay a failing order
  with `uv run pytest --randomly-seed=<n> <paths>`. `-p no:randomly` switches the shuffle
  off, which timing runs need (see <<slow,Slow tests>>).
* *Shared fixtures.* The parallel lanes run `--dist loadgroup`: tests with the same
  `@pytest.mark.xdist_group("<name>")` run on one worker, in one process. A fixture shared by the
  tests of a class (class scope) is built once per worker, so tests that all use it must be
  in one group, or each worker builds its own copy; mark the class
  (`@pytest.mark.xdist_group("listing_read")` in `test_listing_routes_read.py` is the model). A
  group serialises its tests: use it only for class-shared state, never to hide an order
  dependency.

[#test-control]
== How test runs are controlled

_Several agent sessions share one machine: how do their test runs avoid slowing each other down?_

Four mechanisms, from `agent-test-control`:

* *One heavy run at a time.* Every parallel lane (`make test-unit`, `test-unit-ci`,
  `test-feature`, `test-generator`, `test-fast`, `test-durations`, `profile-tests`), plus
  `make test-containers` and `make test-seed`, runs pytest through `rdf_persistence/testkit/run_queue.py`. That module
  holds one lock per user, shared by every repository that user runs on the machine
  (`~/.cache/meaningfy/pytest.lock`). The seed's clean, run and swap are one queued run
  (`python -m rdf_persistence.testkit.selection_data seed -- pytest ...`), so another session never sees a half-seeded
  worktree. A run that finds the lock taken prints `waiting for the test queue: <folder> <target> <pid> <time>`
  once, where the time is when the holder started. When it starts it prints
  `test queue: waited <N>s`. The kernel frees the lock when the run ends, however it ends, so a
  killed run leaves nothing to clean up. There is no maximum wait. A run held far longer than its
  line in the xref:develop/index.adoc#how-long-the-checks-take[durations table] is stuck: a builder
  reports the waiting line to the lead, and the lead kills that pid. `TEST_QUEUE=<path>` moves the
  lock and `TEST_QUEUE=off` skips it. CI (`CI` set) does not queue. `make check-all` queues lane by
  lane, so another session's lane may run between two of its lanes. A builder meets the queue only
  when `make test-changed` falls back to `make test-fast`.
* *Workers from cores and memory.* A queued lane passes `-n @workers`, and the queue replaces it
  when the run leaves the queue: the cores minus 3 (on more than 6 cores), capped by the available
  memory divided by `PYTEST_WORKER_MB` (default 1536), at least 1. It prints
  `test queue: <N> workers (<cores> cores, <MB> MB available)`. `PYTEST_N=<n>` fixes the count for
  the queued lanes; it does not apply to `make test-changed`.
* *Only the tests a change reaches.* `make test-changed` runs without the queue, on at most
  `PYTEST_CHANGED_N` workers (default 4); a value that is not a positive integer exits 2. It never
  syncs the environment (`UV_NO_SYNC`, which its `make test-fast` fallback inherits), and it prints
  its hints before it falls back.
  ** With selection data, a changed Python file selects the tests that executed it. It uses
     pytest-testmon in read-only mode (`--testmon-nocollect --testmon-forceselect`), so the same
     changes select the same tests on every run.
  ** Every other file selects by folder: a file of `rdf_persistence/<theme>/` selects
     `tests/unit/<theme>/`, a test under a folder of `tests/unit/` that folder, a file under `docs/`
     the docs check. A file of the generator selects `tests/generator/` as well, because its tests
     run the generator in subprocesses testmon cannot see.
  ** It runs `make test-fast` itself (queued; its module exits 75 to ask for it) only for shared
     files: `pytest.ini`, `Makefile`,
     `.coveragerc`, `pyproject.toml`, `uv.lock`, schemas under `rdf_persistence/model/`, anything
     under `tests/fixtures/`, or a file no rule maps.
  ** A shared file the branch changed before the last seed no longer falls back. The seed records
     the commit it ran on (`.testmondata.commit`), and with sound data a shared file that does not
     differ from that commit prints `<path>: unchanged since the seed; its selection data covers it`
     instead, because the seed already ran with it. A shared file changed after the seed still
     falls back, and so does a non-Python one reverted since the seed. If git cannot read the
     recorded commit (pruned after a rebase), it prints `cannot read the seed's commit <sha>: …`
     and falls back as before.
  ** Without selection data it uses the folder rules for everything and prints
     `no test selection data in this worktree: run make test-seed`, which tells you
     the seed has not landed yet; carry on. It does the same when the data is damaged
     (`selection data is damaged: delete .testmondata and run make test-seed`) or the
     installed packages changed since the seed
     (`packages changed since the seed: run make test-seed`); report either to the
     lead.
  ** The lead seeds only a worktree where builders will work: the seed serves
     `make test-changed` alone and repeats the unit and feature tests `make check-all` runs anyway.
* *Memory released between tests.* `tests/conftest.py` enables the testkit's plugin,
  `rdf_persistence.testkit.memory_plugin`. After every test it clears the caches of
  linkml-runtime's `SchemaView` and FastAPI's dependency models, which otherwise keep every
  service a test built alive, and of `typing`, for code outside the toolkit that puts objects in
  `Annotated` metadata (the kit's own dependencies no longer do). At each module boundary it also collects garbage and returns
  freed memory to the system, and drops the shared service views of the schemas the module's kits
  were built from. `TEST_RELEASE=off` turns it off. A project that builds services with
  the toolkit in its tests enables it with one line in its root `conftest.py`:
  `pytest_plugins = ["rdf_persistence.testkit.memory_plugin"]`.

*The seed.* The lead runs `make test-seed` at stage start, after `make reindex`, in the background,
and again after `uv sync`. Builders start at once and use the folder rules until the seed lands.
The seed runs every unit and feature test once, slow tests included and without coverage, and
records what each one executed. Its data replaces the old data in one step, and only when the run
completed, so nobody reads partial data. The data stays in the worktree (`.testmondata`, ignored by
git) and is never copied to another one.

*Why `make check-all` is not also the seed.* Its unit and feature lanes run the same tests, so
recording the selection data in the same run would save the seed's minutes. It cannot:
pytest-testmon 2.4 refuses to run beside pytest-cov while branch coverage is on (`TestmonException`
in every worker), and `.coveragerc` turns branch coverage on for the floors. Turning it off would
change what the floors measure. The spike that showed it is
`openspec/changes/archive/2026-11-26-test-memory-followups/evidence/seed-spike.md`.

*What each role runs.* A builder runs the tests its edit touches (`uv run pytest <file>`) and,
once per task, `make test-changed check-quality`. A builder never runs, by hand, `make test-fast`,
`make test`, `make check-all`, `make test-seed` or `pytest --testmon`. It starts a long command as
a background run (the Bash tool's `run_in_background`) and waits for the completion notice the
harness sends when it ends, never `tail --pid`, `tail -f … | grep -m1` or a `timeout` around a
wait, and leaves `make generate` and `uv sync` to the lead. The lead runs the seed and the full
gates (xref:develop/agents.adoc#gates[The gates]).

*Copying it to another repository.* The pieces are:

* the testkit's `run_queue`, `selection_data` and `changed_tests` modules (a project uses them from
  the installed package, see xref:user-manual/test.adoc#test-control[Test control for your
  project]); of `tests/changed.py` only the classifier and the layout are ours, `changed_tests`
  holds the planner and `main()`;
* the Makefile's `PYTEST`, `PYTEST_N` and `PARALLEL` lines, the queued recipes, `test-changed` and
  `test-seed`;
* the `.testmondata*` line in `.gitignore`;
* the `pytest-testmon` pin;
* the testkit plugin line in the root `conftest.py`.

Their tests are `tests/unit/testkit/test_run_queue.py`, `test_selection_data.py` and
`test_memory.py`, and `tests/unit/tooling/test_lanes.py` and `test_changed.py`.

== The report

Every member that runs tests reports, for each make target it ran, the approximate wall-clock
time (pytest's "in N s" line is enough) and the number of tests. The lead keeps the
xref:develop/index.adoc#how-long-the-checks-take[durations table] current. Do not profile.
