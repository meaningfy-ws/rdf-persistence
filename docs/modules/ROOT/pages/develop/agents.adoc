= Working with agents
:description: What is specific to rdf-persistence when agents deliver its work: where the work lands, the rules every brief carries, the gates, the release, and the habits. The method itself is skillery's.

The method agents follow here (the shaping and epic sessions, the team and its briefs, the loop of
a stage scaled by appetite, the lead's authority, how questions are put to the developer,
verification and validation, and what to do when one of our own or an external library falls
short) is owned by skillery's `epic-delivery` skill, installed with the `meaningfy-building` bundle
(3.22.0 or later: the lean method, with the gate table and the lead owning impact, comes from that
version); shaping is `epic-planning`, and subagent dispatch and session hygiene are
`guardrails` (`meaningfy-core`). The explanation for people is skillery's
https://github.com/meaningfy-ws/skillery/blob/develop/docs/practice/ai-coding/working-with-agents.md[Working with agents].
`AGENTS.md` at the repository root says what the project is, how it is developed and its
principles; this page holds what the lead and the builders need beyond it here, with the reasons,
and the gate reference with timings.

== Common questions

*Who decides?*::
The developer. Agents draft, recommend and carry out; the lead is the only one who asks the
developer, in the format the `epic-delivery` skill sets.

*Can an agent commit and merge on its own?*::
Only when the developer grants it for a named epic, within the limits the `epic-delivery` skill
sets. Commits and PRs carry no AI attribution.

*What does a builder's report prove?*::
Not enough on its own. The lead reads the diff and re-runs a gate on an `epic-delivery` trigger;
`make check-all` before the PR catches a report that was wrong. See <<gates>>.

*What must every brief here say?*::
The standing rules and the report in <<brief>>.

== Where the work lands

* *Shaping session:* architecture pages and decision records under
  `docs/modules/ROOT/pages/architecture/`; the LinkML schema changes the design needs, if any; one
  OpenSpec change per EPIC in `openspec/changes/<id>/` (`proposal.md`, spec deltas,
  `inputs/seed.md` with the developer's answers), ordered in `openspec/changes/README.md`.
* *Epic session:* merged PRs into `develop`; the change archived into `openspec/specs/`
  (`openspec archive <id> --yes`); updated docs and the
  xref:develop/index.adoc#how-long-the-checks-take[durations table].
* Modelling can happen in both: concepts and their boundaries when shaping, the exact slots,
  constraints and generated code in the epic.
* A builder's task here can be a LinkML schema change or a generator extension, with its
  regenerated code in the same commit.

[#brief]
== What every brief carries here

On top of the brief the `epic-delivery` skill sets, every brief carries this checklist, pasted in
(the adversarial tester follows it too), so no builder opens a second page to load it:

. Models, not dicts; LinkML is the single source, never edit a generated file.
. A test lives in the tier folder of the layer it tests; the folder gives the marker.
. No network outside container and e2e tests; no real sleeps (inject the clock, `testkit.wait_until`).
. Prefer one fake of the real port over `MagicMock`; never patch toolkit code except the five
  marked kinds (`# X1` to `# X5`, see xref:develop/testing.adoc[the testing checklist]).
. Compare RDF as graphs (`rdflib.compare.isomorphic`), never as Turtle strings.
. Each rule or guard gets a positive and a negative case in one parametrized table.
. One assert per idea, each with a message.
. Mark a test `slow` on the test itself, never a module `pytestmark`.
. Report the files changed, the tests added, and each make target run with its time and test count.
. Tools: Serena for symbols, `ast-grep` for a shape, Grep for text; no impact run, no re-index (the
  lead's), no `s.shell`, no `s.mem`.

A builder in a worktree gets its absolute path named once in the brief, and activates it as its own
Serena project. The commit trace is in `AGENTS.md` (Working here).

[#tools]
== Which tool answers which question

One tool per question:

* Outline of a file, or a symbol's body: Serena's `serena_repl` with `s.lsp.get_symbols_overview`
  or `s.lsp.find_symbol` (with the body), not `Read` on a whole file. Who calls it:
  `s.lsp.find_referencing_symbols`. Replace or add a whole function: `s.edit.replace_symbol_body`
  or `s.edit.insert_after_symbol`.
* One code shape in many files: `ast-grep run -p '<pattern>' --lang python`; look at the matches,
  then add `-r '<rewrite>' -U`.
* Text in docs, YAML, AsciiDoc or the Makefile: Grep.
* Blast radius: GitNexus `impact` (repo `rdf-persistence`). The lead runs it as a gate; reviewers
  may run it read-only; builders do not.

Serena's limits: use only `s.lsp` and `s.edit`. Never `s.shell` (shell commands go through Bash,
where the hooks and permissions apply) and never `s.mem` (Serena memories are not used; `.serena/`
is git-ignored). Reviewers use only the read queries (`find_symbol`, `get_symbols_overview`,
`find_referencing_symbols`, `find_declaration`, `find_implementations`) and read-only GitNexus
queries; never `s.edit`, `rename_symbol`, `safe_delete_symbol` or GitNexus `rename`.

[#gates]
== The gates

The builder's task gate is one command, `make test-changed check-quality`, or
`make test-fast check-quality` after changing `domain` or a port in `services`, or when unsure what
the change reaches. The full gates, `make check-all` and `make test-containers`, are the lead's and
never run in a task; after the lead commits a schema change, `make check-generated`. A builder gets
a separate worktree only for overlapping parallel work, or when another session holds the checkout.

Why they are shaped this way (#111, measured over two weeks of sessions):

* The lead runs impact at stage start and before the stage's last commit, and builders run
  neither: builders re-indexing and checking every symbol cost more than it found, and was followed
  for about 5 to 7 % of edits anyway.
* The builder's task gate is one command (`make test-changed check-quality`, or the `test-fast`
  variant), so every report has the same shape and the lead does not re-run it without a trigger;
  re-running `make check-quality` after every task cost 61 runs for 21 PRs.
* `make test-containers` stays out of tasks: builders ran it 65 times, although the full suite is
  meant to run once before the PR.

The table is the reference for what each gate runs.

[cols="2,1,3",options="header"]
|===
|Gate |Who |When
|`make test-changed` |builder |After every task. It runs the tests of the files the task changed
against `develop` (set `BASE=<branch>` to compare with another; `PYTEST_N=<workers>` sets the
worker count), slow tests included. It falls back to `make test-fast` by itself when it cannot map
a change to tests
|`make test-fast` |builder |Instead of `make test-changed` when you are unsure what a change
reaches, or after changing `domain` or a port in `services`. It runs every unit and feature test
not marked `slow` (time: see the
xref:develop/index.adoc#how-long-the-checks-take[durations table])
|`make check-quality` |builder |After every task (≈ 1 min); it holds `make check-architecture`,
`make clean-code` and `make check-docs`
|`make check-all` |lead |Once per stage before the PR, and again after the fix pass: it already
holds `make test`, so never run both
|`make test-containers` |lead |With `make check-all`; never in a task
|`make check-generated` |lead |After committing a schema change (it compares against the commit)
|`openspec validate --all --strict` |both |Part of `make check-quality`
|The clarity gate (≥ 9/10) |lead |Before a PLAN's first task
|===

[#challenge]
== Keeping the challenge cheap

_How do we keep review and checking from doubling the work?_

The `epic-delivery` skill sets who challenges a stage and groups the review lenses by appetite.
Here three adjustments override it for any work, measured on a large stage (2026-11-09):

* *The adversarial tester runs right after the riskiest task*, the one that adds an invariant, a
  write order or concurrent writes, and again at the end if the stage is large. Both real defects of
  that stage sat in one task, and finding them at the end meant one large late fix.
* *Review lenses L4 and L5 are one pass; in the full review L1, L2 and L3 are never combined with
  each other*, whichever lenses the appetite's review set runs. About a third of the findings came
  from more than one lens, mostly L3, L4 and L5 together; L1, L2 and L3 each found something the
  others did not. The one exception is the stage pass below.
* *For MEDIUM and above, the full review runs once* (developer, 2026-11-15, widened from LARGE on
  2026-11-19, rule P-0005), at the end of the epic or of a series of stages; each stage gets one
  pass of L2 and L3 together, which still catches spec and structure drift while it is cheap to
  fix. An epic of one stage gets both on the same PR.
* *The checker reads the lead's `make check-all` result* and checks the briefs and decisions against
  the diff; it does not run the tests again.

The lead records accepted findings in `design.md` before they are fixed, and gives one fixer the
whole list.

== Merge and release

Each stage ends in one PR into `develop`, merged only on green CI. A release comes last, after the
change is archived, so no commit follows the tag. Release-please proposes the release and a person
merges it; the steps are in xref:develop/index.adoc#release[Cutting a release].

== Habits that keep sessions consistent

[#never-poll]
* *Never poll:* run a long command once in the background and wait for its notice, or use the
  Monitor tool. The `no-poll-loops` and `quiet-tools` hooks of `meaningfy-core` enforce it; this
  repository ships no hook of its own.

[#reindex]
* *Re-index GitNexus per stage, not per commit:* at the start of each stage, and again before an
  impact check on symbols an earlier task of the stage added or moved:
  `make reindex` (≈ 20 s). Per-commit runs cost 151
  re-indexes for 298 commits. If it errors (developer, 2026-11-09), do not retry or investigate:
  run `gitnexus clean --force`, then `gitnexus analyze --embeddings --force --skip-agents-md
  --skip-skills` (≈ 4 min, in the background), then revert anything it wrote to `AGENTS.md`,
  `CLAUDE.md` or `.claude/skills/`.
* *Durations from ordinary runs:* the
  xref:develop/index.adoc#how-long-the-checks-take[durations table] stays honest without the cost
  of profiling.

[#revised]
* *Pages the developer revised* (developer, 2026-11-10): when the developer says they revised a
  page, add `:page-revised: <date> by the developer` under its `:description:` line, or move the
  date forward. Only the developer's word sets or moves it. List them with
  `grep -rl ':page-revised:' docs/`; what changed since is `git log --since=<date> -- <page>`.
