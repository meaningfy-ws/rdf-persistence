= Working with agents
:description: What is specific to rdf-persistence when agents deliver its work: where the work lands, the rules every brief carries, the gates, the release, and the habits. The method itself is skillery's.

The method agents follow here (the shaping and epic sessions, the team and its briefs, the loop of
a stage scaled by appetite, the lead's authority, how questions are put to the developer,
verification and validation, and what to do when one of our own or an external library falls
short) is owned by skillery's `epic-delivery` skill, installed with the `meaningfy-building` bundle
(3.15.0 or later: the gate triggers and "builders run neither impact nor the change check" come
from that version); shaping is `epic-planning`, and subagent dispatch and session hygiene are
`guardrails` (`meaningfy-core`). The explanation for people is skillery's
https://github.com/meaningfy-ws/skillery/blob/develop/docs/practice/ai-coding/working-with-agents.md[Working with agents].
`AGENTS.md` at the repository root holds the rules agents load; this page gives the reasons
behind the ones specific to rdf-persistence, and the gate reference with timings.

== Common questions

*Who decides?*::
The developer. Agents draft, recommend and carry out; the lead is the only one who asks the
developer, in the format the `epic-delivery` skill sets.

*Can an agent commit and merge on its own?*::
Only when the developer grants it for a named epic, within the limits the `epic-delivery` skill
sets. Commits and PRs carry no AI attribution.

*What does a builder's report prove?*::
Not enough on its own. The lead reads the diff and re-runs a gate on an `epic-delivery` trigger;
`make check-all` before the PR catches a report that was wrong. See <<gates>>.

*What must every brief here say?*::
The standing rules and the report in <<brief>>.

== Where the work lands

* *Shaping session:* architecture pages and decision records under
  `docs/modules/ROOT/pages/architecture/`; the LinkML schema changes the design needs, if any; one
  OpenSpec change per EPIC in `openspec/changes/<id>/` (`proposal.md`, spec deltas,
  `inputs/seed.md` with the developer's answers), ordered in `openspec/changes/README.md`.
* *Epic session:* merged PRs into `develop`; the change archived into `openspec/specs/`
  (`openspec archive <id> --yes`); updated docs and the
  xref:develop/index.adoc#how-long-the-checks-take[durations table].
* Modelling can happen in both: concepts and their boundaries when shaping, the exact slots,
  constraints and generated code in the epic.
* A builder's task here can be a LinkML schema change or a generator extension, with its
  regenerated code in the same commit.

[#brief]
== What every brief carries here

On top of the brief the `epic-delivery` skill sets, every brief names:

* the standing rules: models, not dicts; LinkML is the single source; the
  xref:develop/testing.adoc[testing checklist] (the adversarial tester follows it too);
* the report expected: files changed, tests added, each make target run with its time and test
  count;
* how to work: the Tools section of `AGENTS.md` (which tool answers which question, and Serena's
  limits);
* that the builder skips its own impact step: the `implementer` agent's definition still tells it
  to re-index and run impact before every edit, which epic-delivery's stage loop and this repo
  give to the lead (skillery issue #254). Until that is fixed, only the brief stops it.

The commit trace is in `AGENTS.md` (Branches, commits, PRs).

[#gates]
== The gates

The rules are in `AGENTS.md` (Delivery). Why they are shaped this way (#111, measured over two
weeks of sessions):

* The lead runs impact and the change check once per task and builders run neither: builders
  re-indexing and checking every symbol cost more than it found, and was followed for about 5 to
  7 % of edits anyway.
* The builder's task gate is one command (`make test-changed check-quality`, or the `test-fast`
  variant), so every report has the same shape and the lead does not re-run it without a trigger;
  re-running `make check-quality` after every task cost 61 runs for 21 PRs.
* `make test-containers` stays out of tasks: builders ran it 65 times, although the full suite is
  meant to run once before the PR.

The table is the reference for what each gate runs.

[cols="2,1,3",options="header"]
|===
|Gate |Who |When
|`make test-changed` |builder |After every task. It runs the tests of the files the task changed
against `develop` (set `BASE=<branch>` to compare with another; `PYTEST_N=<workers>` sets the
worker count), slow tests included. It falls back to `make test-fast` by itself when it cannot map
a change to tests
|`make test-fast` |builder |Instead of `make test-changed` when you are unsure what a change
reaches, or after changing `domain` or a port in `services`. It runs every unit and feature test
not marked `slow` (time: see the
xref:develop/index.adoc#how-long-the-checks-take[durations table])
|`make check-quality` |builder |After every task (≈ 1 min); it holds `make check-architecture`,
`make clean-code` and `make check-docs`
|`make check-all` |lead |Once per stage before the PR, and again after the fix pass: it already
holds `make test`, so never run both
|`make test-containers` |lead |With `make check-all`; never in a task
|`make check-generated` |lead |After committing a schema change (it compares against the commit)
|`openspec validate --all --strict` |both |Part of `make check-quality`
|The clarity gate (≥ 9/10) |lead |Before a PLAN's first task
|===

[#challenge]
== Keeping the challenge cheap

_How do we keep review and checking from doubling the work?_

The `epic-delivery` skill sets who challenges a stage and groups the review lenses by appetite.
Here three adjustments override it for any work, measured on a large stage (2026-11-09):

* *The adversarial tester runs right after the riskiest task*, the one that adds an invariant, a
  write order or concurrent writes, and again at the end if the stage is large. Both real defects of
  that stage sat in one task, and finding them at the end meant one large late fix.
* *Review lenses L4 and L5 are one pass; L1, L2 and L3 are never combined with each other*,
  whichever lenses the appetite's review set runs. About a third of the findings came from more
  than one lens, mostly L3, L4 and L5 together; L1, L2 and L3 each found something the others did
  not.
* *The checker reads the lead's `make check-all` result* and checks the briefs and decisions against
  the diff; it does not run the tests again.

The lead records accepted findings in `design.md` before they are fixed, and gives one fixer the
whole list.

== Merge and release

Each stage ends in one PR into `develop`, merged only on green CI. A release comes last, after the
change is archived, so no commit follows the tag. Release-please proposes the release and a person
merges it; the steps are in xref:develop/index.adoc#release[Cutting a release].

== Habits that keep sessions consistent

[#never-poll]
The habits themselves are in `AGENTS.md`; the reasons:

* *Never poll:* the hook that denies `sleep` loops (`.claude/hooks/no_polling.py`) runs on plain
  `python3`, stdlib only, on purpose: it must not depend on the project's environment.
* *Re-index per stage, not per commit:* per-commit runs cost 151 re-indexes for 298 commits.
* *Durations from ordinary runs:* the
  xref:develop/index.adoc#how-long-the-checks-take[durations table] stays honest without the cost
  of profiling.
