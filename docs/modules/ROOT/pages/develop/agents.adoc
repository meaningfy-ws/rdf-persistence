= Working with agents
:description: What is specific to rdf-persistence when agents deliver its work: where the work lands, the rules every brief carries, the gates, the release, and the habits. The method itself is skillery's.

The method agents follow here (the shaping and epic sessions, the team and its briefs, the loop of
a stage scaled by appetite, the lead's authority, how questions are put to the developer,
verification and validation, and what to do when one of our own or an external library falls
short) is owned by skillery's `epic-delivery` skill, installed with the `meaningfy-building` bundle
(3.9.0 or later); shaping is `epic-planning`, and subagent dispatch and session hygiene are
`guardrails` (`meaningfy-core`). The explanation for people is skillery's
https://github.com/meaningfy-ws/skillery/blob/develop/docs/practice/ai-coding/working-with-agents.md[Working with agents].
`AGENTS.md` at the repository root is the short form that agents load. This page keeps only what
is specific to rdf-persistence.

== Common questions

*Who decides?*::
The developer. Agents draft, recommend and carry out; the lead is the only one who asks the
developer, in the format the `epic-delivery` skill sets.

*Can an agent commit and merge on its own?*::
Only when the developer grants it for a named epic, within the limits the `epic-delivery` skill
sets. Commits and PRs carry no AI attribution.

*What does a member's report prove?*::
Nothing on its own. The lead re-runs the <<gates>> and reads the diff.

*What must every brief here say?*::
The standing rules and the report in <<brief>>.

== Where the work lands

* *Shaping session:* architecture pages and decision records under
  `docs/modules/ROOT/pages/architecture/`; the LinkML schema changes the design needs, if any; one
  OpenSpec change per EPIC in `openspec/changes/<id>/` (`proposal.md`, spec deltas,
  `inputs/seed.md` with the developer's answers), ordered in `openspec/changes/README.md`.
* *Epic session:* merged PRs into `develop`; the change archived into `openspec/specs/`
  (`openspec archive <id> --yes`); updated docs and the
  xref:develop/index.adoc#how-long-the-checks-take[durations table].
* Modelling can happen in both: concepts and their boundaries when shaping, the exact slots,
  constraints and generated code in the epic.
* A builder's task here can be a LinkML schema change or a generator extension, with its
  regenerated code in the same commit.

[#brief]
== What every brief carries here

On top of the brief the `epic-delivery` skill sets, every brief names:

* the standing rules: models, not dicts; LinkML is the single source; the
  xref:develop/testing.adoc[testing checklist] (the adversarial tester follows it too);
* the report expected: files changed, tests added, each make target run with its time and test
  count.

Each task is committed by the lead with why, what and `Refs: <change-id> <task>`.

[#gates]
== The gates

Before handing out a task the lead checks the blast radius with GitNexus (re-indexing it if stale);
a HIGH or CRITICAL risk goes to the developer.

[cols="2,3",options="header"]
|===
|Gate |When
|`make check-all` |After every task and before every PR
|`make test-containers` |When adapters or containers change, and before a stage's PR
|`make check-generated` |After committing a schema change (it compares against the commit)
|`make check-architecture`, `make clean-code`, `make check-docs` |With every task; they take seconds
|`openspec validate --all --strict` |Part of `make check-quality`
|The clarity gate (≥ 9/10) |Before a PLAN's first task
|===

== Merge and release

Each stage ends in one PR into `develop`, merged only on green CI. A release comes last, after the
change is archived, so no commit follows the tag.

== Habits that keep sessions consistent

* Re-index GitNexus regularly: `gitnexus analyze --embeddings --skip-agents-md --skip-skills`.
* Take check durations from ordinary runs and keep the
  xref:develop/index.adoc#how-long-the-checks-take[durations table] current; no profiling.
* Open the docs with questions: when a page is added or changed, add or update the
  xref:questions.adoc[common question] it answers.
* Temporary files go in `temp/`; commits and PRs carry no AI attribution.
