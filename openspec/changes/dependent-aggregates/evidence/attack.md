# Attack on the PLAN of dependent-aggregates (2026-11-28)

Read: `proposal.md`, `design.md`, `tasks.md`, `specs/`, `features/`, `inputs/qa.md`; checked
against `persistence/services/session.py` (`Transaction.remove`, `_send_and_confirm`,
`_refuse_*`, `_diagnose`, `_reasons`, `request_text`/`START`), `persistence/services/mapper.py`
(`commit`, batches), `collaboration/services/reference_collections.py` (`delete_cascade`,
`_require_room`), `collaboration/services/write_guards.py` (`prepare_remove`),
`collaboration/services/referenced_removals.py` (`in_use`), `testkit/fakes.py` (`update`, `hold`).
Lead decisions OPEN-1 (validators run, all or nothing) and OPEN-2 (one activity, one invalidation
per removed aggregate) are taken as given.

Store atomicity, checked: `START` inserts the commit marker `WHERE { guards }` and every operation
is conditional on the marker, so guards are evaluated on the state *before* the request's own
operations. Fuseki runs one update request in one TDB2 write transaction (single writer); the fake
applies the request to a copy under no `await`, so it is atomic too. RISK-1's assumption holds for
both lanes; the findings below are about what the guards see, not about atomicity.
