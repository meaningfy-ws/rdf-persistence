## Context

`message-bus` (archived 2026-11-15) made every commit on a tenant or the application database
store one activity in the database's provenance graph (`Iris.provenance`) in the commit's own
update, and hand it, once confirmed, to the session's `on_commit` hook, which the kit routes to
`MessageBus.publish(activity, session)` (in-process observers). What is missing is everything
that crosses the process:

- nothing records whether an activity has left the process, so a crash after the commit and
  before a send loses it;
- there is no background task (`install_service`'s lifespan runs start-up steps and the sweep
  only), no `EventBus` port, no broker adapter;
- `MessageBus.publish` takes a `Session`: an incoming message has none;
- the only decoder of stored activities is `Transitions._decode`
  (`services/transitions.py:224`), fixed to `Transition`; nothing picks the most specific class of
  a stored activity, which carries its class and every ancestor as `rdf:type`;
- there is no streaming route; FastAPI 0.162 ships `fastapi.sse.EventSourceResponse`, so server-sent
  events need no library;
- `GET /context.jsonld` exists; the settings have no public address of the service (`base` is the
  IRI base for identifiers, not the service URL); `deployment` is optional;
- `toolkit_principal_iri(settings.base)` is the toolkit's own principal (`Tenancy._toolkit`);
  `Tenancy.tenants()` returns tenants in every state, and `Tenancy.behind` holds the tenants whose
  migration failed (their sessions raise `TenantBehind`).

Constraints: DEC-1 to DEC-10; the layers of AGENTS.md (port in `services`, adapter in `adapters`,
the composition root in `entrypoints`); models from LinkML; a single service instance (DEC-10,
PD-8b of v1).

## Goals / Non-Goals

**Goals:** an outbox that is the activity record (DEC-10) and survives a crash; one relay task
that publishes each recorded activity at least once, in commit order per aggregate; an `EventBus`
port with an in-memory fake and a FastStream Redis Streams adapter (DEC-6) passing one conformance
suite; incoming messages of other deployments handed to `MessageBus` (DEC-7); a server-sent-events
route per tenant with access filtering and `Last-Event-ID` resume within 7 days.

**Non-Goals:** the No-gos of the EPIC; several relay instances or a lease (DEC-10); RabbitMQ (DEC-6:
"if time allows", not planned here; a later change proves it in the same conformance suite);
tenant-level events (DEC-10); exactly-once; event-carried state (DEC-9); an AsyncAPI route (the
document is generated by the spike only, as evidence, PD-4); server-sent events of the application
database (no tenant to follow; its activities still go to the bus); a hop limit across deployments
(RISK-8).

## Decisions

Numbered PD-n (plan decisions). The EPIC's DEC-n are cited, not repeated. Two different buses
appear below: `MessageBus` (in process, `message-bus`; `install_service(bus=)`) and `EventBus` (the
broker port, this EPIC; `install_service(event_bus=)`).

- **PD-1 The pending mark (Q1).** The commit's `_record` operation adds one triple
  `<activity> rp:pendingSince ?now` to the provenance graph, in the same update, with
  `BIND (NOW() AS ?now)` in its `WHERE` (DEC-5, DEC-10). `NOW()` is the store's time when it applies
  the update; a store applies one update at a time per database (Fuseki: serialised write
  transactions), so the marks of one database follow the order the commits were applied in, not
  the order the clients read their clocks. The relay replaces the mark (PD-3). Only a marked
  activity is ever relayed, so records written before this EPIC are never published (No-go
  "replaying history"). The predicates of this EPIC (`rp:pendingSince`, `rp:relayedAt`,
  `rp:publicationFailed`) are store plumbing like `rp:commitMarker`: constants in
  `services/vocabulary.py`, not slots of `Activity`, so no generated model and no message carries
  them; reads of an activity's statements exclude them. Rejected: a "published" mark (would publish
  all existing history on first start); a separate outbox graph (two copies of the record); the
  activity's end time as the order (read by the client before the update is sent: a slow add of B
  after a remove of B would sort first).
- **PD-2 Which sessions mark.** A session marks exactly when it records (`record_activities=True`):
  tenant and application sessions. The system database records nothing and is never relayed.
  `record_activities=False` with a hook (tests, the cost measurement) marks nothing: such
  activities are only seen in process. An overtaken commit whose caller got the false `Conflict`
  of atomic-commit PD-4 has its activity and mark stored (one `INSERT`), so the relay publishes it:
  a change that happened is published, though in-process observers did not see it (this replaces
  "recorded, not published" of the `message-bus` "As built" table for the broker; the spec delta
  says so).
- **PD-3 The relay.** `services/relay.py` `Relay`, one `asyncio` task started by the lifespan after
  the sweep and the migrations, cancelled at shutdown. A round visits the application database and
  every tenant of `Tenancy.tenants()` whose state is `ACTIVE` and which is not in `Tenancy.behind`.
  Per database, in a `try` of its own (one database's failure never stops the others): read the
  pending activities (PD-5), and for each, in order: decode it (PD-16); `EventBus.publish` (if a bus
  is set); replace the mark by `rp:relayedAt ?now` (`NOW()` again, in one update); offer the activity
  to the hub (PD-9). A decode failure replaces the mark by `rp:publicationFailed ?now`, logged at
  ERROR, and the round goes on with the next activity (a poison record never stalls its database).
  A failed publish stops that database for this round (logged at WARNING; retried next round), so no
  activity overtakes an earlier one of the same database. Rounds: `wake()` sets an `asyncio.Event`;
  the loop waits for the event or `interval` seconds (default 5), clears the event, then runs one
  round, so a wake during a round causes exactly one more round and rounds never overlap. The kit's
  `on_commit` calls `wake()` after the in-process bus. `run_once()` runs one round under the same
  `asyncio.Lock` the loop takes (for tests and for no-loop use). An unexpected error in a round is
  logged at ERROR with its traceback and the loop goes on. Rejected: one task per tenant (unbounded
  tasks); a separate process (DEC-10).
- **PD-4 Spike first (DEC-6).** Task 1.1 proves with FastStream 0.7.8 and a real Redis: publishing
  a generated model's JSON with string headers to a stream; a consumer group with an explicit ack
  after the handler returns, so an unacked message is delivered again after a restart (from the
  group's pending list); trimming by age (`XADD … MINID` or `XTRIM`); and generating an AsyncAPI
  document from the subscriber. The result goes to `evidence/spike-faststream.md`. If any of the
  four fails with no fallback (RISK-1), the lead stops and reports to the developer before stage 2.
- **PD-5 Order (DEC-5).** In one database, pending activities are read ordered by
  `rp:pendingSince`, then by the version chain (an activity whose invalidation names a version that
  another pending activity generated goes after it), then by activity IRI. `pendingSince` is the
  store's apply order (PD-1); the chain settles two commits applied within one tick of the store
  clock. Only per-aggregate order is promised (rabbit-hole "Ordering across aggregates").
- **PD-6 The port.** `services/events.py`:

  ```python
  Receive = Callable[[Envelope, bytes], Awaitable[None]]

  class EventBus(Protocol):
      async def publish(self, envelope: Envelope, body: Activity) -> None: ...
      async def start(self, receive: Receive) -> None: ...   # begins consuming
      async def close(self) -> None: ...
  ```

  `Envelope` is a generated wire class (new, `rp_service.yaml`, all slots required): `tenant` (uri:
  the tenant IRI or the application IRI), `origin` (string: `settings.deployment`), `activity_class`
  (uri: the class IRI of the body), `context` (string: the context link, PD-7). The body is the
  activity's generated JSON (`model_dump_json(exclude_none=True)`), thin by construction (DEC-9). A
  broker carries the envelope as message headers. The fake `InMemoryEventBus` (`testkit/fakes.py`)
  keeps every sent message, delivers to the receiver of every started bus that shares its
  `InMemoryBroker` (two "deployments" in one test), redelivers an unacked message (its `receive`
  raised) when that bus is started again, and can be told to fail the next `publish`.
- **PD-7 The context link (Q6).** New optional settings slot `public_url` (uri, pattern
  `^https?://.+[^/]$`). `Envelope.context` is `{public_url}/context.jsonld`, else the relative
  `/context.jsonld` (`context_link(settings)`). The SSE response carries the same link in a `Link`
  header with `rel="http://www.w3.org/ns/json-ld#context"` (the existing `CONTEXT_REL`).
- **PD-8 The Redis adapter (DEC-6, Q7).** `adapters/redis_events.py` `RedisEventBus(url, *,
  deployment, stream="rp-events", retention=timedelta(days=7))` on FastStream's `RedisBroker`:
  publishes to one stream, trimmed to `retention` (the mechanism PD-4 proves); consumes with
  consumer group `deployment`, one consumer, ack after `receive` returns, no ack when it raises
  (redelivered from the pending list on the next start). Installed with the new extra
  `events = ["faststream[redis]==0.7.8"]` in `pyproject.toml`; nothing outside this module imports
  `faststream` or `redis` (an `.importlinter` contract), and `rdf_persistence/__init__.py` does not
  import it (a consumer without the extra imports the package unchanged; TC-31).
- **PD-9 The hub.** `services/event_hub.py`: the protocol `Offer` (`offer(tenant: str, activity:
  Activity) -> None`, synchronous) and `EventHub(max_queue=1000)` implementing it: per tenant IRI, a
  set of subscriber queues (`asyncio.Queue(max_queue)`), `subscribe(tenant)` as an async context
  manager yielding a queue. `offer` puts into every queue of that tenant and closes a full one (a
  sentinel; the stream ends; the client resumes with `Last-Event-ID`). The relay offers only tenant
  activities; application activities are not offered. In process, single instance (DEC-10; RISK-4).
- **PD-10 Incoming messages (DEC-7, Q2).** The kit's `receive(envelope, body)`:
  1. skip (DEBUG) when `envelope.origin == settings.deployment`: this deployment's in-process
     observers saw it at commit (at most once, RISK-9);
  2. with no `kit.bus`, skip (DEBUG);
  3. resolve the class with `activity_class_named(view, models, envelope.activity_class)` (PD-16);
     an unknown class, or a body that does not validate into it, is logged at WARNING and skipped;
  4. the tenant: `DatabaseGone` or `NotFound` (a tenant this deployment lacks) is logged at WARNING
     and skipped; `TenantBehind` is raised on (not acked: redelivered at the next start, after its
     migration);
  5. open `kit.session(tenant, toolkit principal)` (or `application_session` when `tenant` is the
     application IRI) and probe the store with one `ASK` on the provenance graph: a
     `StoreUnavailable` is raised on (not acked, redelivered);
  6. `kit.bus.publish(activity, session)`. Observer errors are logged by `MessageBus.publish` and the
     message is acked (RISK-9); `MessageLimitExceeded` is logged at ERROR and acked.
  Skipped messages are acked. Observers are idempotent by activity id (DEC-7); the toolkit does not
  de-duplicate.
- **PD-11 Server-sent events (Q3, Q5).** `GET {prefix}/tenants/{tenant}/events`, media type
  `text/event-stream`, requires `read` on the tenant (`kit.require`; RISK-5). Each event: `id` = the
  activity IRI, `event` = the class's name, `data` = the filtered activity's JSON. Filtering is
  `visible_part(activity, may_read) -> Activity | None` (`services`), applied to live and resumed
  events alike (DEC-3, DEC-5): generations and invalidations whose `entity` the caller may not
  `read` are removed; an activity whose `used_resource` it may not read, or with no part left, is
  not sent. The caller's access is re-read (`load_caller_access`) before an event or a keep-alive is
  sent when the last read is older than `access_ttl` (default 1 s); a re-read that raises
  (`Forbidden`, `NotFound`) ends the stream. A keep-alive comment every `keep_alive` (default 15 s).
  `access_ttl`, `keep_alive` and the clock are arguments of the route builder, defaulted by the kit.
- **PD-12 Resume (DEC-10, Q3).** With `Last-Event-ID` = an activity IRI, the route subscribes to the
  hub first (buffering), then reads from the provenance graph the activities whose `rp:relayedAt`
  is no earlier than the named one's and no earlier than `resume_window` (default 7 days) ago, the
  named one excluded, ordered by `relayedAt` then IRI; sends them filtered, then the buffer without
  the ids already sent, then live events. `relayedAt` is the store's time of the relay's update,
  which is also the order the hub was offered them, so an activity applied late but relayed after
  the named one is not missed. An unknown id, one with no `relayedAt` (from before this EPIC), or
  one older than `resume_window` sends one `event: reset` (no data): the client reloads what it
  shows, then live events.
- **PD-13 Retention (Q4).** Activity records are never deleted by this EPIC. "Pruning" is the
  replaced mark and the stream's trim. The rabbit-hole "Outbox growth" is answered by
  `message-bus`: the provenance graph grows with the history by design; this EPIC adds one triple per
  activity (`relayedAt`).
- **PD-14 Restore.** A restore drops every `rp:pendingSince`, `rp:relayedAt` and
  `rp:publicationFailed` triple before the import (`tenant_dump.restore`), so a restore never
  re-publishes the source's activities under their kept IRIs, and a resume never mixes the source's
  relay times.
- **PD-15 Wiring.** `install_service(event_bus: EventBus | None = None, …)` refuses an `event_bus`
  when `settings.deployment` is empty (`ValueError`: the origin and the consumer group need it;
  two deployments on one broker need different slugs, stated in the how-to). The kit holds
  `kit.relay` and `kit.hub` (always built); the lifespan starts `event_bus.start(kit.receive)` if
  given, then the relay; shutdown cancels the relay, then `event_bus.close()`. With no event bus the
  relay still runs: it replaces marks and feeds the hub, so SSE works without a broker.
- **PD-16 Decoding a stored activity.** `services/provenance.py`:
  `activity_class_of(view, models, types) -> type[Activity]`: among the schema classes whose
  `class_uri` (expanded by the schema view) is one of `types`, the most specific (the one with the
  most ancestors in `view.class_ancestors`), then `models.named(name)`; `LookupError` if none.
  `activity_class_named(view, models, class_iri)` is the same for one IRI.
  `decode_activity(view, models, mapper, iri, graph) -> Activity` decodes with
  `mapper.from_graph(cls, iri, graph, None)`, so a consumer subclass comes back with its own slots
  (unlike `Transitions._decode`, which stays as it is). The relay reads an activity's statements
  with a new template `READ_PENDING` beside `READ_ACTIVITIES` (any activity type; the parts through
  `rp:generation` and `rp:invalidation`; the plumbing predicates of PD-1 excluded).

## Algorithm / approach

A worked example, tenant T, deployment `lib`:

1. Ada replaces book B (v1 → v2). The commit's update stores activity `urn:uuid:a1` (`rp:Replace`,
   invalidation of B@v1, generation of B@v2) and `urn:uuid:a1 rp:pendingSince "…T10:00:00.120Z"`,
   then confirms. `on_commit`: in-process observers run, then `relay.wake()`.
2. The relay's round reads T's pending activities: `[a1]`. It decodes a1 as `Replace`, publishes
   envelope `{tenant: T, origin: lib, activity_class: rp:Replace, context:
   https://lib.example/context.jsonld}` with body `{"id": "urn:uuid:a1", "generations": [...], ...}`,
   replaces the mark by `rp:relayedAt "…T10:00:00.300Z"`, offers a1 to the hub. Bob's SSE stream
   (Bob may read B) sends `id: urn:uuid:a1`, `event: Replace`. Carol has a Prohibition of `read` on
   B: her filtered a1 has no part left, so nothing is sent.
3. The process dies after step 1, before the round. On start the relay's first round finds a1
   still pending and publishes it: at least once. `lib`'s own observers do not see it again
   (RISK-9).
4. The process dies after the publish and before the mark is replaced: a1 is published again with
   the same id; a consumer drops it by id (DEC-7).
5. Deployment `cat` subscribed to the same stream receives a1: origin `lib` ≠ `cat`, class
   `rp:Replace` known, T exists in `cat`'s store: its observers of `Replace` get a1 with a session
   on T as the toolkit principal. `lib`'s consumer group skips it (origin = own).
6. Bob's connection drops after a1; a2 and a3 are relayed; he reconnects with `Last-Event-ID:
   urn:uuid:a1`: he gets a2, a3 (relayed after a1) from the provenance graph, then live events.

Idempotency: every step is safe to repeat. The publish is at least once (a crash between publish
and mark repeats it with the same activity id); replacing an absent mark is a no-op; the hub offer
may repeat (an SSE client drops a repeated id); receiving is acked after the observers ran, so a
crash repeats it with the same id.

### Anti-patterns

| Don't | Do instead | Why |
|---|---|---|
| Build the message as a dict or hand-written JSON | `activity.model_dump_json()`; `Envelope` generated | Models, not dicts; LinkML single source (DEC-1) |
| Publish from `on_commit` directly to the broker | Only the relay publishes; `on_commit` wakes it | A crash between commit and send would lose the event |
| Replace the mark before the send succeeds | Send, then replace | At least once, never at most once |
| Order by the client's clock | The store's `NOW()` in the update (PD-1) | Client clocks are read before the update is applied |
| Let one record or one tenant stop the round | A `try` per database; a poison record marked failed | One bad record must not silence every tenant |
| Import `faststream` anywhere but `adapters/redis_events.py` | Keep it behind the port | The `events` extra stays optional (Q7) |
| Delete published activity records to prune | Replace only the mark; trim the stream | The records are the kept history (`message-bus`) |
| Check SSE access once at connect | Re-read at most every `access_ttl` (PD-11) | Grants change during a stream (seed, accepted 2026-11-06) |
| Await a slow SSE client inside the relay | Bounded queues; close a full one | One slow client must not stall the relay |
| A test that sleeps to wait for the relay | `testkit.wait_until` or `Relay.run_once()` | Flaky, slow tests |

## Error matrix

Levels: DEBUG for an expected skip, WARNING for a skipped message or a retried send, ERROR (with
traceback) for a failed round or a poison record.

| Failure mode | How it is detected | Expected handling |
|---|---|---|
| Refused commit (stale, invalid, forbidden, key conflict) | the update's guards fail | no activity, no mark: nothing relayed (TC-03) |
| Overtaken commit (false `Conflict`, atomic-commit PD-4) | `_diagnose` raises; the activity is stored | its mark is stored with it: the relay publishes it; in-process observers did not see it (PD-2, TC-03a) |
| Crash after commit, before `on_commit` or the round | the mark is still there at the next round | published by the first round after start (TC-12); own in-process observers miss it (RISK-9) |
| Crash after publish, before the mark is replaced | the mark is still there | published again, same activity id; consumers drop by id (TC-13) |
| Broker unreachable or `publish` raises | exception from `publish` | WARNING; that database stops for the round; retried next round; order kept (TC-14) |
| A pending activity cannot be decoded (class gone, migration shape) | `LookupError` / `ValueError` from PD-16 | ERROR; mark replaced by `rp:publicationFailed`; the round goes on (TC-15a) |
| Store unreachable during a round (`StoreUnavailable`) | exception from the query | ERROR; that database skipped; others go on (TC-16) |
| A tenant deleted between listing and reading (`DatabaseGone`) | exception | DEBUG; that tenant skipped this round (TC-15) |
| A tenant in `DELETING` or `behind` | its state; `Tenancy.behind` | not visited (TC-15) |
| Relay loop meets an unexpected error | the loop's `except` | ERROR with traceback; the loop goes on (TC-16) |
| Two commits of one aggregate pending in one round | PD-5 ordering | published in apply order (TC-11, TC-11a) |
| `event_bus` given with no `deployment` | `install_service` | `ValueError` at build (TC-21a) |
| Incoming message of own origin | `envelope.origin == deployment` | DEBUG; acked (TC-24) |
| Incoming message of an unknown class, or a body that does not validate | PD-16 / pydantic | WARNING; acked (TC-25) |
| Incoming message for a tenant this deployment lacks | `DatabaseGone` / `NotFound` | WARNING; acked (TC-26) |
| Incoming message for a tenant `behind` | `TenantBehind` | raised: not acked; redelivered at next start (TC-27a) |
| Store unreachable on receive | the probe `ASK` raises `StoreUnavailable` | raised: not acked; redelivered (TC-27) |
| An observer raises on an incoming message | `MessageBus.publish` logs it | acked; the other observers still run (RISK-9) |
| SSE client too slow (queue full) | `QueueFull` in `offer` | its stream ends; it resumes with `Last-Event-ID` (TC-36) |
| SSE caller's tenant `read` revoked mid-stream, busy or idle | the re-read raises | the stream ends at the next event or keep-alive (TC-35) |
| `Last-Event-ID` unknown, unrelayed, or older than the window | not found / no `relayedAt` / too old | one `reset` event, then live (TC-38) |
| A restore of a dump holding marks | the import | marks and relay times dropped; nothing re-published (TC-05) |
| `events` extra not installed | `import rdf_persistence` | works; only `adapters.redis_events` fails to import (TC-31) |

## Risks / Trade-offs

- **RISK-1 FastStream does not do what PD-8 needs** (manual ack in a group, redelivery of the pending
  list, headers, age trim). Likelihood low, impact medium. Mitigation: the spike (task 1.1) before
  any adapter code; fallback for a missing trim: an `XTRIM MINID` call through the broker's Redis
  client after each publish round; for redelivery: an `XAUTOCLAIM` at start through the same client.
  With no fallback, the lead stops and asks the developer (DEC-6 rejected redis-py alone).
- **RISK-2 Commit cost.** One more triple per commit, and one update per activity afterwards.
  Certain, impact low (`message-bus` measured no cost above noise for the record). Accepted.
- **RISK-3 Relay load with many tenants.** One query per tenant per round, every 5 s, idle or not.
  Medium for large deployments, impact low (one cheap `SELECT` on a small graph). Accepted for v1;
  `interval` is a constructor argument.
- **RISK-4 Several instances.** Two relays on one deployment would publish twice and each hub sees
  only its own rounds. Accepted by DEC-10 (single instance; lease deferred); the how-to says so.
- **RISK-5 SSE access.** One system-database read per connection per `access_ttl` at most; a reader
  whose grants are only on aggregates (no tenant `read`) cannot follow the tenant. Accepted; the
  how-to says so; a per-aggregate stream is a later change if a consumer needs it.
- **RISK-6 What a thin message reveals.** A message names IRIs, versions, the principal and the
  non-payload slots of a command (`message-bus` DEC-12). On the broker every subscribing deployment
  sees all of it: the broker is inside the trust boundary. On SSE the filter (PD-11) removes the
  parts about hidden aggregates; other IRIs a slot names (a comment's IRI) are references, not
  content, and are kept. Accepted; stated in the how-to.
- **RISK-7 Store clock.** `NOW()` ties within one store tick are settled by the version chain; a
  remove and an add of the same IRI applied within one tick keep IRI order. A store clock stepped
  back (NTP) can misorder one pair. Low likelihood, low impact; accepted.
- **RISK-8 Loops across deployments.** An observer of `cat` that commits on an incoming message
  produces a message `lib` may react to, and so on; `MessageBus`'s limit counts within one process
  only. Accepted for v1: the how-to tells consumers to make cross-deployment observers react only
  to the kinds they do not themselves produce; a causation header with a hop limit is a later
  change.
- **RISK-9 Two delivery guarantees.** In-process observers stay at most once (as `message-bus`
  built them: a crash before `on_commit`, an overtaken commit or an observer's error loses that
  delivery); other deployments get at least once, except an observer's own error, which is logged
  and acked. A consumer that needs at least once for its own commits observes them through another
  deployment or reads the provenance graph. Accepted; the how-to states both.
