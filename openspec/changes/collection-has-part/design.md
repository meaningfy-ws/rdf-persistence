# Design: collection-has-part

## Context

`ReferenceCollection` (`rdf_persistence/model/rp_collections.yaml`) states members with the slot
`had_member` (`slot_uri: prov:hadMember`). The code reads it in three places:
`vocabulary.HAD_MEMBER = predicate("had_member")` (`schema/services/vocabulary.py:183`),
`reference_collections.py:194` (`referrers`) and `:343` (`_direct`, behind `members`,
`collections_of`, `delete_cascade` and the hidden count), and `write_guards.py:89`. Everything else
follows from the model through `make generate`.

Facts that shape the PLAN:

- **F-1 Migration steps are generic.** A `MigrationStep` is three group graph patterns
  (`where`/`delete`/`insert`) that `migrations.py` wraps into one guarded update over every graph of
  a database except the stamps, loaded and registry graphs (`_STEP`, `migrations.py:50`). A
  predicate rewrite is one ordinary step: **no new step type is needed.** Constraints: full IRIs
  only (no prefixed names), no `?rp_*` variable, the toolkit's own predicates not in a template.
- **F-2 Version tokens rotate.** A migration with at least one step rotates the `rp:version` token
  of every graph of the database (`_ROTATION`); `1__2.yaml` had no step, so 2 → 3 is the first
  toolkit upgrade that does.
- **F-3 Order.** Start-up (`migration_runner.py:58`) and restore (`tenant_dump.py:244` →
  `migrate_dataset`) both run the toolkit's chain before the consumer's.
- **F-4 The toolkit's lock does not change** except `schema_version`: `ReferenceCollection` is a
  mixin, and `lock.py:69` locks concrete classes only.
- **F-5 A consumer's lock does change.** It locks each concrete collection class with its induced
  slots; the toy's lock (`tests/fixtures/library/migrations/schema.lock.json:573`) holds
  `lib:Shelf` with `prov:hadMember`. After the rename, `rp-generate` sees "slot removed
  (DESTRUCTIVE)" + "slot added (SAFE)": with the version unchanged it refuses
  (`lock_step._needs_version`); with it raised it drafts a `DROP prov:hadMember of lib:Shelf`
  step. That step is harmless after the toolkit's 2 → 3 (F-3: nothing left to drop).
- **F-6 `prov:Collection` is never stored.** The mapper types a graph with the concrete class only
  (`mapper.py:198`); the mixin's IRI appears only as the mixin NodeShape's `sh:targetClass` and the
  context term `ReferenceCollection`. Changing it (DEC-4, PD-8) moves no data.
- **F-7 The tutorial has no collection** (`docs/modules/ROOT/examples/getting-started/`): nothing
  to change there.
- **F-8 `tests/unit/test_combined_artefacts.py`** asserts the combined `shapes.ttl`,
  `context.jsonld` and toolkit lock are byte-identical to `tests/fixtures/v0_6_0/`. Any model
  change breaks it (PD-10).

## Goals / Non-Goals

**Goals**
- G-1: a saved collection states `dcterms:hasPart` per member and no `prov:hadMember`; every
  collection service reads it (spec scenario "members are stated with dct:hasPart").
- G-2: a tenant, application or system database at toolkit version 2 is moved to 3 at start-up,
  and a dump at version 2 on restore (spec scenarios "stored collections are migrated", "a dump
  at version 2 is restored").
- G-3: a consumer whose lock names a collection class has a documented, tested path (PD-5).

**Non-Goals**
- No per-class property, no dual reading (EPIC no-gos); no new step type (F-1).
- No generator check for two slots sharing one IRI (RISK-2 names it as a follow-up).

## Decisions

- **PD-1 Slot.** In `rp_collections.yaml`: prefix `dcterms: http://purl.org/dc/terms/`; slot
  `has_part`, title "Has part", `slot_uri: dcterms:hasPart`, range, multivalued and description
  as today; the class lists `has_part`; the module description drops "on PROV-O" for "membership
  with DCT". `vocabulary.HAS_PART = predicate("has_part")`; `HAD_MEMBER` is removed, not
  aliased (DEC-2).
- **PD-2 The migration** `rdf_persistence/model/migrations/2__3.yaml`, written before
  `make generate` so the drafted empty file never appears (`lock_step._write_draft` skips an
  existing file):

  ```yaml
  schema_id: https://meaningfy.ws/ns/rdf-persistence
  from_version: '2'
  to_version: '3'
  description: >-
    Reference collections state their members with dct:hasPart instead of prov:hadMember
    (collection-has-part DEC-1, DEC-3). Only a subject that states rp:memberClass, which every
    stored collection does (member_class is required), is rewritten.
  steps:
    - title: Restate the members of every reference collection with dct:hasPart
      where_pattern: >-
        ?collection <https://meaningfy.ws/ns/rdf-persistence#memberClass> ?class ;
        <http://www.w3.org/ns/prov#hadMember> ?member
      delete_pattern: ?collection <http://www.w3.org/ns/prov#hadMember> ?member
      insert_pattern: ?collection <http://purl.org/dc/terms/hasPart> ?member
  ```

  `rp.yaml` goes to `version: "3"` in the same commit (`load_chain` refuses a file that leaves
  the current version). Idempotent by design: every operation is guarded by the `"2"` stamp, so a
  second start or a second instance changes nothing (existing TC of rp-schema-migrations).
- **PD-3 Why `rp:memberClass` and not `a prov:Collection`:** no stored graph is typed with the
  mixin's IRI (F-6), and `member_class` is required, so `rp:memberClass` marks exactly the
  collections, whatever the mixin's IRI (DEC-4) and whatever the consumer's class IRI is.
- **PD-4 Rename is one task** (model, vocabulary, services, tests, regeneration, goldens): a
  half-renamed tree fails `check-freshness`, so it cannot be split into green commits.
- **PD-5 Consumer path** (F-5), stated in the release note and proved by TC-9 and TC-6: a
  consumer whose lock names a collection class (1) raises its schema `version:`, (2) runs
  `rp-generate`, which drafts `<old>__<new>.yaml` with one `DROP <http://www.w3.org/ns/prov#hadMember>`
  step per collection class, (3) may keep that step (it matches nothing after the toolkit's 2 → 3)
  or delete it, and commits the file and the lock. A consumer with no locked collection class
  (MWB2 today: its collection classes come with `v2-02` 2.1b) only regenerates.
- **PD-6 Release note.** Under `## [Unreleased]` → `### Changed` of `CHANGELOG.md`, in the 0.7.0
  style: "**BREAKING: reference collections state members with `dct:hasPart`**
  (`collection-has-part`, #199)", then: the slot and field `had_member` → `has_part` in Python,
  JSON, TypeScript and the API (listing filter `had_member` → `has_part`, sort keys
  `had_member`/`-had_member` → `has_part`/`-has_part`); `vocabulary.HAD_MEMBER` → `HAS_PART`; the
  toolkit's schema goes to version 3 and its migration rewrites stored members at start-up and on
  restore; every version token is rotated once, so a client holding one re-reads before a replace
  (409 otherwise); the PD-5 steps; the mixin's class IRI `prov:Collection` → `dcmitype:Collection` (DEC-4: the
  JSON-LD term `ReferenceCollection` and the mixin shape's target change, no stored data). The squash commit
  is `feat(collections)!: ...` with a `BREAKING CHANGE:` footer, so release-please
  (`bump-minor-pre-major`) proposes 0.8.0; the hand-written CHANGELOG entry is the release note
  (`skip-changelog: true`).
- **PD-7 Spec delta.** The delta gains a MODIFIED block for "A reference collection holds typed
  references it does not own" (its text names `prov:hadMember`) and a restore scenario. No
  `rp-schema-migrations` delta: the mechanism is unchanged; version 3 is an instance of its
  requirements (proposal.md's Capabilities no longer list it, logged there). The MODIFIED text
  names `dcmitype:Collection` (DEC-4).
- **PD-8 Class IRI** (DEC-4): in `rp_collections.yaml`, prefix
  `dcmitype: http://purl.org/dc/dcmitype/` and `ReferenceCollection.class_uri: dcmitype:Collection`,
  in task 1.1. It changes on regeneration only the mixin NodeShape's `sh:targetClass` and the
  context term `ReferenceCollection`; no lock entry (F-4), no stored data (F-6), no migration step.
- **PD-9 Toy lock** (owner, `inputs/qa.md` item 4): `git rm tests/fixtures/library/migrations/schema.lock.json`,
  then `make generate` writes it with `dcterms:hasPart`. The toy stays at version 1; TC-9 and TC-6
  prove the consumer path.
- **PD-10 Combined artefacts** (owner, item 5): in `tests/unit/test_combined_artefacts.py` drop
  `test_a_combined_artefact_is_byte_identical_to_its_0_6_0_copy` and delete
  `tests/fixtures/v0_6_0/{shapes.ttl,context.jsonld,schema.lock.json}`; keep
  `test_the_fixtures_hold_the_four_artefact_kinds` reworded to check the combined set is present in
  `core` (shapes, context, frames, the lock) and `test_no_frame_is_added_or_lost`. The lane that
  still proves the content: `make check-generated` in CI (committed artefacts equal a
  regeneration) and `tests/unit/testkit/test_shape_snapshot.py` in `make test-fast` (the model
  shape).

## Algorithm / approach

Worked example (toy, tenant at toolkit "2", library "1"):

```
GRAPH <…/shelves/s1> { <…/shelves/s1> a lib:Shelf ; rp:memberClass "Book" ;
                       prov:hadMember <…/books/b1>, <…/books/b2> ; rp:version "t1" }
GRAPH <stamps> { <https://meaningfy.ws/ns/rdf-persistence> <v.DATA_SCHEMA_VERSION> "2" }
```

After start-up: `s1` states `dcterms:hasPart` b1 and b2, no `prov:hadMember`, `rp:version` is a new
UUID, the stamp is `"3"`; the library's own chain then runs (none for the toy). `members(s1)`,
`collections_of(b1)`, `referrers(b1)` and `delete_cascade(s1)` behave as before. A graph
`<…/x> prov:hadMember <…/y>` without `rp:memberClass` is untouched.

### Anti-patterns

| Don't | Do instead | Why |
|---|---|---|
| Hand-edit `shapes.ttl`, `context.jsonld`, `books.ts`, a lock or a golden | Change the YAML, `make generate` / `make refresh-*` | `check-generated` fails and the next regeneration reverts it |
| Keep `HAD_MEMBER` as an alias or read both predicates | Remove it; read `HAS_PART` only | EPIC no-go "no dual reading"; a stale alias hides a missed reader |
| Select collections by `?c a <prov#Collection>` | `?c rp:memberClass ?class` (PD-3) | no stored graph carries the mixin type: the step would match nothing |
| Write `prov:hadMember` or `dcterms:` prefixed in the step | Full IRIs in angle brackets | `load_migration` refuses prefixed names |
| Write `2__3.yaml` after `make generate` | Write it first | generation would draft an empty `2__3.yaml` that then must be replaced |
| Update `tests/fixtures/v0_6_0/` to the new output | PD-10 | the folder claims to be what 0.6.0 shipped |
| Raise the toy's version to get past F-5 | Re-baseline its lock (PD-9) | ~10 tests edit `version: "1"` of the toy |

## Error matrix

| Failure mode | How it is detected | Expected handling |
|---|---|---|
| The step fails on one tenant (store error) | `migrate_database` raises | that tenant keeps v2 data and stamp, 503 `tenant-behind`; others migrate (existing rp-schema-migrations) |
| The step fails on the system or application database | start-up error | the service does not start; data unchanged (one atomic request) |
| Second start or second instance | stamp guard `"2"` | no-op (idempotent) |
| Client replaces with a pre-upgrade token | session version check | 409 Conflict; client re-reads (PD-6 says so) |
| Dump taken at toolkit "2" restored | `migrate_dataset`, toolkit first | migrated in memory, then checked (TC-10) |
| Dump taken at "3" restored on a "2" service | unknown version | refused, nothing created (existing) |
| Consumer regenerates without raising its version | `lock_problems` | refusal naming class and `prov:hadMember` (TC-9); release note says what to do |
| Consumer keeps the drafted DROP step | runs after the toolkit's step | matches nothing (TC-6) |
| Toolkit's 2 → 3 fails, consumer's chain holds the DROP step | `migrate_database` raises on the toolkit chain (`migration_runner.py:58`) | the consumer's chain never runs on that database, so the DROP cannot delete unmigrated members; tenant-behind |
| A reader still uses `.had_member` / `HAD_MEMBER` | reading `.had_member` raises `AttributeError`; passing `had_member=` raises a pydantic `ValidationError` (`extra="forbid"`, `base.py:18`) | test-fast and mypy (`check-types`) fail; grep in task 1.1 acceptance |
| Planted `prov:hadMember` in a v3 database | not read by any service | not a member (no dual reading); accepted |

## Risks / Trade-offs

- **RISK-1** (likely, low impact): every version token is rotated once at upgrade (F-2). Accepted;
  release note (PD-6).
- **RISK-2** (possible, medium): a consumer that follows "DCT for domain modelling" declares its own
  slot with `slot_uri: dcterms:hasPart`; two terms for one IRI make JSON-LD compaction pick one,
  and on a collection class two slots would share the predicate. Mitigation: the how-to says to
  reuse the toolkit's `has_part` slot for any other `dct:hasPart`; a generator check for shared
  slot IRIs is a follow-up issue the lead opens, out of this appetite.
- **RISK-3** (likely, low): `nested-collections` (#198) extends the same slot and files; it is
  ordered after this change (its DEC-3), so it rebases onto `has_part`.
- **RISK-4** (unlikely, high): a consumer's own data stating `rp:memberClass` and `prov:hadMember`
  on a non-collection subject would be rewritten. `rp:memberClass` is the toolkit's predicate;
  accepted.
- **RISK-5** (likely, low): the consumer lock break (F-5) on every consumer with a locked
  collection class. Mitigation PD-5 + TC-9.
