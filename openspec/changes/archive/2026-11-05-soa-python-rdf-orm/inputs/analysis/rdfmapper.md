## Summary

rdfmapper is a small academic mapper that grew out of a bachelor's thesis. Decorators
(`@rdf_entity`, `@rdf_property`, `@rdf_one_to_one`, `@rdf_one_to_many`) attach predicate metadata
to Python `property` getters. `RDFMapper.to_rdf` / `from_rdf` walk those properties to convert
between objects and a **fresh in-memory rdflib `Graph`**. `RDFRepository` derives SPARQL SELECTs
from method names (`find_by_x_and_y`, `count_by_x`), Spring-Data style. `to_shacl` emits a
NodeShape from cardinality metadata and validates it with pySHACL.

There is **no persistence layer**: no save, update or delete, no session, no store or endpoint
abstraction, no transactions. It is a serialiser plus a query helper over a single `Graph`.

- **Execution flows:** the only detected process is `to_rdf_many → to_rdf → _python_to_literal`.
  Querying runs `__getattr__` (repository.py:42) → `_find_by` (:96) → `graph.query(str)` (:169)
  → `mapper.from_rdf` per result row. That is an N+1 deserialisation over the same graph.
- **Dependency direction:** the repository depends on a mapper instance passed in as an untyped
  parameter (`mapper` has no annotation, repository.py:33) and on `rdflib.Graph`. There is no
  port/adapter split.

## Implementation principles

- **Mapping metadata.** Each decorator builds a `property` whose getter function carries ad-hoc
  attributes: `_rdf_predicate`, `_is_relationship`, `_relationship_type`, `_target_class`,
  `_min_count` and `_max_count` (mapper.py:57-142). The decorated method body is discarded. The
  getter and setter read and write `self._<name>`, so the user must hand-write an `__init__` that
  assigns `self._name` (README quick start). Discovery uses `dir(obj)` plus an
  `isinstance(prop, property)` scan (mapper.py:217-223, 292-298). There is no central metamodel:
  the class registry `_entities` (mapper.py:53) is written but never read.
- **Identity.** The object must carry a `uri` attribute (mapper.py:207). There is no minting
  strategy (`base_uri` is only a fallback) and no blank nodes. `from_rdf` bypasses `__init__` via
  `object.__new__` and sets `instance.uri` (mapper.py:288-289). The `visited` dict acts as a
  **per-call identity map** that also breaks cycles (mapper.py:280-290). It does not survive
  beyond one call.
- **Relationships.** 1-1 uses `graph.value`; 1-n uses `graph.objects` into a Python list, with no
  order kept (mapper.py:300-311). There is no n-m beyond 1-n on both sides, no inverse. Loading
  is eager and recursive through the whole reachable graph. On save, every related object is
  cascaded into the output graph (mapper.py:226-233).
- **Literals.** Conversion is hard-coded for bool, int, float, datetime, date and str
  (mapper.py:148-179). There are no language tags, no custom datatypes, and no `Decimal`. A str is
  emitted as a plain `Literal(value)`.
- **Serialisation and update.** `to_rdf` always builds a *new* `Graph` (mapper.py:206). Writing to
  a store means `graph += mapper.to_rdf(obj)`, which is additive. No diff, no deletion of stale
  triples, no update path.
- **Querying.** SPARQL is assembled by **f-string interpolation of user values**:
  `FILTER (?v = "{value}")`, `FILTER regex(?v, "{value}", "i")`, `?s <p> "{value}"`
  (repository.py:146-152, 206). Two consequences follow:
  1. It is open to SPARQL injection.
  2. Non-string values compare as plain strings. `find_by_age(age=25)` compares
     `"25"^^xsd:integer` against `"25"`, which SPARQL does not treat as equal, so it presumably
     matches nothing. No test exercises a non-string `find_by` (tests/test_rdfmapper.py:291-361).
  `limit`/`offset` are appended without an ORDER BY (repository.py:162-165), so pagination is
  non-deterministic. `group_by_count` takes a `cls` parameter that duplicates `entity_class`.
- **Store access.** Only `rdflib.Graph.query` is used (repository.py:169, 216, 278). There is no
  SPARQLWrapper, no remote endpoint and no Update. A `Graph` backed by `SPARQLUpdateStore` would
  work for reads only by accident of rdflib.
- **Validation.** `to_shacl` emits one NodeShape per class with `sh:path`, `sh:datatype`,
  `sh:minCount` and `sh:maxCount` per property (mapper.py:322-383):
  - The shape IRI namespace is hard-coded to `http://example.org/shape/` (mapper.py:340).
  - The datatype is guessed from the `__init__` signature annotations, defaulting to
    `xsd:string`, even for relationship properties (mapper.py:367-379). Relationship properties
    therefore get a wrong `sh:datatype xsd:string`.
  - `validate` delegates to `pyshacl.validate` with `inference="rdfs"` (mapper.py:385-422).
  Validation is explicit only; it does not run on construct or save.

### Proposed new features

- **Q6 Derived query methods**: finder methods generated from method names (`find_by_x_and_y`,
  `count_by_x`), as in Spring Data. Evidence: repository.py:42-90.
- **X6 SHACL shape generation from the host model**: in rdfmapper it is from class metadata
  (mapper.py:322). This is distinct from X4 because it targets RDF validators, not JS clients.
- **Q7 Safe parameter binding**: values reach SPARQL as `initBindings` or `Literal.n3()`, never
  string-concatenated. rdfmapper lacks it (repository.py:152), which shows the item is needed.

## JS-friendliness

None. There is no HTTP layer, JSON Schema, OpenAPI or TS output. JSON-LD is available only by
serialising the produced rdflib Graph.

## Reuse verdict for rdf-persistence: **borrow ideas** (do not adopt or extend)

- **Borrow:**
  - Derived query methods (Spring-Data style) as an optional convenience on top of a typed query
    builder.
  - SHACL generation from model metadata, though in rdf-persistence it should come from LinkML
    (`gen-shacl`) rather than host classes.
  - The per-call visited/identity dict for cycle-safe hydration.
- **Avoid:**
  - Metadata stashed on getter functions.
  - `_attr` naming conventions.
  - f-string SPARQL.
  - `__getattr__` magic as the only query API, because it is untypeable.
  - No store abstraction.
- At ~700 LOC with no persistence, no endpoint and no tests for typed filters, there is nothing
  worth depending on.

## Risks / anti-patterns observed

- **SPARQL injection**: user values are interpolated into queries (repository.py:149-152, 206).
- **Type-unsafe filtering**: typed values are compared as plain strings (repository.py:152).
- **N+1 hydration** after every finder (repository.py:168-170); `dir()` scans on every
  (de)serialisation.
- **Unstable pagination**: LIMIT/OFFSET without ORDER BY.
- **Hard-coded shape namespace** `http://example.org/shape/` (mapper.py:340); relationship
  properties get `sh:datatype xsd:string`.
- **Packaging gaps**: version mismatch (0.2.2 vs `__version__` 0.1.0); missing LICENSE file.

### (b) Developer experience deep-dive

- **Shortest complete example.** README "Quick start", **26 lines**: map, serialise, deserialise,
  query. Any write to a store is left to the user (`graph += mapper.to_rdf(p)`).
- **Concepts to learn: about 8.**
  1. The `RDFMapper` instance.
  2. `@rdf_entity`.
  3. `@rdf_property` (with min/max).
  4. `@rdf_one_to_one`.
  5. `@rdf_one_to_many` (with a lambda target).
  6. The mandatory `uri` attribute plus the `self._<name>` backing-field convention.
  7. `RDFRepository` and its finder-name grammar (`find_by_`, `_and_`, `_like`, `count_by_`).
  8. `to_shacl` / `validate`.
- **Typing and IDE.**
  - Decorated stubs (`def name(self): pass`) become untyped `property` objects, so the IDE
    shows `Any`.
  - Finders come from `__getattr__`, so there is no completion and mypy cannot check them
    (repository.py:42).
  - `mapper` is untyped (repository.py:33).
  - mypy runs in CI but only on the library.
- **Real error messages.**
  - Good: `ValueError: Missing value for field 'name'` (repository.py:136), and
    `ValueError: 'city' is not a valid rdf_property` (repository.py:261).
  - Bad: a typo in a finder field leaks a raw `AttributeError: type object 'Person' has no
    attribute 'nme'` from `getattr(cls, field_name)` (repository.py:138).
  - Bad: forgetting `self._name = ...` in `__init__` surfaces as
    `AttributeError: 'Person' object has no attribute '_name'` at serialisation time
    (mapper.py:74).
- **Docs.** A neat mkdocs site with guide pages and an API reference, plus a JOSS-style paper.
  There is nothing on stores, writes, updates or deletes, because the library has none.
- **Footguns.**
  - Typed finder values compare as strings (`age=25` presumably matches nothing).
  - SPARQL injection.
  - LIMIT/OFFSET without ORDER BY.
  - The SHACL namespace is hard-wired to `example.org`.
  - `to_rdf` silently cascades the whole reachable object graph.

### (c) Authorization seams

- **ACL-agnostic only by accident.** All reads go through `rdflib.Graph.query` and
  `graph.value` / `graph.objects` (repository.py:169; mapper.py:303-313). If the user passes a
  `Graph` backed by rdflib's `SPARQLStore` / `SPARQLUpdateStore`, configured with auth headers
  and pointed at an authorizing proxy, the proxy enforces read policy transparently. Credentials
  are then fixed per Graph, not per request: there is no request-context parameter anywhere
  (X13 absent). Writes never reach a store, so there is nothing to enforce on the write side.
- **PEP sites, if one were added:**
  - Query-level PEP: `RDFRepository._find_by` / `_count_by` (repository.py:96, 172), before the
    string is sent to `graph.query`. A policy FILTER or VALUES block would be injected there.
    It is fragile because queries are built by string concatenation.
  - Field-level PEP (A3): the property loop in `from_rdf` (mapper.py:292-314).
- **Verdict:** no designed seam; do not borrow its approach.

### (d) Layer coverage and codegen fit

- **Layers:**
  - L0 partial: SHACL emission from the code model (M13).
  - L1 partial: Data Mapper plus a read-only finder repository.
  - L2 minimal: a single rdflib Graph, no transactions.
  - L3, L4, L5, L6: none.
- **LinkML fit: poor.** LinkML `gen-pydantic` produces Pydantic `BaseModel` classes. rdfmapper
  needs plain classes with decorated property stubs and `_name` backing fields, so the generated
  output cannot be used. A custom Jinja template for `gen-python` could emit the decorators:
  `class_uri` → `@rdf_entity`, `slot_uri` → `@rdf_property`, range class → `rdf_one_to_*`, and
  `minimum_cardinality` / `maximum_cardinality` → `minCount` / `maxCount`.
  That would still be missing:
  - inheritance (`is_a` → rdf:type / subClassOf);
  - an `identifier` slot named `uri`;
  - enums, language strings and multivalued literal slots (only relations can be lists);
  - ordered lists.
  LinkML's own `gen-shacl` already does rdfmapper's SHACL job better.

### (b) Purpose and origin

- **Built for:** getting a Python object model into RDF for research ETL pipelines, without
  writing triples. It is the packaged successor of LambdaGeo's `simpot` (2022), which was used
  in `dbacademic-etl` to turn Brazilian academic open data into knowledge graphs
  (docs/background.md).
- **Who and when:** Felipe dos Santos Goiabeira's bachelor's thesis at UFMA (2025), advised by
  Sergio Souza Costa (LambdaGeo group). A JOSS-style paper is in the repo (paper.md); the latest
  commit is 2026-09.
- **Design angle:** JPA / Spring-Data familiarity for non-Semantic-Web developers — annotations,
  derived finders and SHACL as a bonus. It *serialises* objects into a graph for one-way ETL
  rather than *persisting* them. That explains why update, delete, identity and stores are
  missing: the use case never needed them.
- **Where it could fit:**
  - Nowhere as a component. In L1 it would collide with our LinkML/Pydantic chain, because it
    needs hand-written decorated classes.
  - As an idea donor for L1 query convenience (Q8 derived finders) and L0 SHACL emission, which
    LinkML `gen-shacl` already covers.
  - It fits no variant V1–V5 as a dependency, and it fails DEC-5 (0 stars).

### (c) Final verdict and what to remember

**Verdict: ideas.**

Three things a system architect must remember:
1. **It is an ETL serialiser, not a persistence layer.** There is no update, delete, identity,
   transaction or store access, so nothing in it can carry rdf-persistence's L1/L2.
2. **Derived finders (`find_by_x_and_y`) are the one idea worth keeping**, and only as optional
   sugar over a typed, parameter-bound query builder. Its own implementation is injection-prone
   and string-typed (repository.py:146-152).
3. **SHACL-from-model belongs to LinkML `gen-shacl` in the MWBv2 chain**, not to a mapper.
   rdfmapper confirms the idea but adds nothing LinkML lacks.
